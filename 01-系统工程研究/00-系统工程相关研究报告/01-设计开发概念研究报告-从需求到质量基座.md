## 0. 文档说明与术语约定

本文所有术语遵循以下约定（与国标 GB/T 19000—2016 官方译文略有差异，按约定统一；该标准等同采用 ISO 9000:2015，其修订版计划号 20264414-T-469、尚在起草，故本文条款号一律按 ISO 9000:2026）：

| 英文 | 本文用词 | 备注 |
|---|---|---|
| requirement | 需求 | GB/T 原文用"要求"，按约定统一为"需求" |
| need | 需要 | 与"需求"严格区分 |
| expectation | 期望 | 与"需求"严格区分 |
| specified requirement | 规定需求 | 验证（3.11.12）的参照 |
| object | 客体 | 3.5.3 |
| characteristic | 特性 | 3.10.1（跨标准分流见下表后注） |

本表 `characteristic` 行的「特性」取 **ISO 9000:2026 §3.10.1** 质量管理语境——"可区分的特征"，带 inherent／assigned 限定；**ISO 1087:2019 §3.2.1** 的 `characteristic`（*abstraction of a property*，**属性的抽象**）是同名不同物，属概念构造的抽象层——二者不可互替（22 号 §4.2、§4.4）。

**ISO 9000:2026 §3.5.1 需求定义**：明示的、通常隐含的或必须履行的需要或期望。
（stated / generally implied / obligatory 三者并列，无主次。）

**验证的参照 = 规定需求（specified requirement，即被明示的需求）。**

| 3.11.12 | 验证 verification | 通过提供客观证据（3.8.6），对规定需求（3.5.1）已得到满足的认定 |
| 3.11.14 | 确认 validation | 通过提供客观证据（3.8.6），对『**为特定预期用途或应用的需求**』（3.5.1）已得到满足的认定 |
| 3.11.1 | 确定 determination | 查明一个或多个特性（3.10.1）及特性的值 |
| 3.3.1 | 过程 process | 使用或转换输入以交付结果（3.7.1）的相互关联或相互作用的一组活动（3.2.12） |
| 3.2.11 | 项目 project | 为达成目标（3.7.11）而开展的独特过程（3.3.1） |

> 条款号按 ISO 9000:2026；中文按 2026 英文原文对应（国标 GB/T 19000—2016 的中文对应 2015 版）。其中 process §3.3.1 定义句改「使用或转换输入以交付结果」、project §3.2.11 收敛为一句（起止日期与受控活动移入注 1），其余各条定义句两版逐字未变。

**关键词汇关系**：质量（3.5.2）定义中同时引用"客体""固有特性""需求"——这三个词恰好也是设计开发（3.3.11）定义中的构件，三个概念由此互相咬合。

## 2. 设计与开发（3.3.11）：定义与详细解读

### 2.1 定义原文

> **设计和开发（3.3.11）**：将客体（3.5.3）的需求（3.5.1）转换为对其更详细的需求的一组过程（3.3.1）。
>
> *Design and development: set of processes (3.3.1) that transform requirements (3.5.1) for an object (3.5.3) into more detailed requirements for that object.*

```mermaid
flowchart LR
    A["客体的需求（输入）<br/>宽泛 · 通用 · 通常是研究的结果"] --> B["设计和开发（3.3.11）<br/>一组过程 · 需求转化"]
    B --> C["更详细的需求（输出）<br/>新的规定需求"]
```

### 2.2 四个构件逐一拆解

1. **客体（3.5.3）——设计开发的对象**
   可以是产品、服务、过程、系统，甚至管理体系本身。设计开发绝不局限于硬件产品——服务设计开发、过程设计开发同样成立（见注3）。

2. **需求（3.5.1）——输入必须是"需求"**
   输入是需求，不是点子、灵感或想法。创意不经过"表述为需求"这一步，就进不了设计开发的流程。需求 = 明示的、通常隐含的或必须履行的需要或期望。

3. **转换为——动词才是灵魂**
   输入与输出必须是**不同的东西**。流程走完了输出需求跟输入一个样——那不是设计开发，那是走流程。

4. **更详细的需求——唯一的判定标准**
   "更详细"是相对输入而言的。定义没说"更正确""更优化"，只说了"更详细"——设计开发的职责是把需求展开、分解、落到可实现和可验证的粒度；方案优劣由评审和验证把关。

   **"更详细"的三成分判据**（2026-08-25 精炼）：

   | 成分 | 回答的问题 | 判据类型 | 锚点 |
   |---|---|---|---|
   | **更具体** | 详细体现在哪？ | 表述判据：需求以**特性**来规定 | 3.3.11 注1（特性可区分→可测量→可验证） |
   | **更可实现** | 详细到什么程度够？ | 程度判据：**够实现为止** | §4 终点"可实现"（可直接执行） |
   | **更可验证** | 详细得对不对方向？ | 方向判据：落到特性上可测量可验证 | 注1 特性链（注意：不能作终点，§4.1） |

   **排除项："更可理解"**——两种解读都站不住：若指"文字浅显易懂"，与"详细"无关甚至相悖（详细≠好懂，"无歧义"是起点判据 8.3.3，不是"更详细"的内涵）；若指"可被下游理解执行"，已被"更可实现"吸收（§4.2"可直接执行"）。

   **一句话记忆**：具体到特性，详细到实现，验证是方向。

5. **一组过程（3.3.1）——性质与归类**
   ① 是"一组"（集合），不是单个活动，跨部门、跨阶段是常态；② 它的定义中心词就是"一组过程"（set of processes），且列在 §3.3"有关过程的术语"之下——**标准把设计开发定性为"过程"而不是"活动"**，这是它可管理、可审核、可控制的前提。

   > 〔按：本节定义是 ISO 9000:2026 §3.3.11 的**过程**口说；设计还有一处**产物**口说——ISO/IEC/IEEE 15288:2023 §3.13（GB/T 22032）把 design 定义为"系统元素及其关系的**规格**，**完整到足以支撑对架构的一次合规实现**"（24 号 §1.2）。两处口径不冲突、可并存，但落点不同：过程口说答"这组过程把需求变成什么"，产物口说答"设计产物本身是什么、细到什么程度"。故不可把设计产物直接读成"更详细的需求"——本节说的"设计输出 = 新的规定需求"（§2.4）与"设计描述"（DD）是同一物的两个面向：前者说它在**需求链上的身份**，后者说它的**产物形态**（24 号 §3.1）。又，该句里 *compliant implementation* 的主语是**实现**：设计的职责只是"**足够完整到足以支撑**"（*sufficiently complete to support*，15288:2023 §3.13），设计产物本身只承"条件性合规"（24 号 §10.7，呼应 §4.2）。〕

### 2.3 三个注的详细解读

**注1**（信息密度最高，四点）：

- **输入需求通常是研究的结果**——起点是探索性的：市场调研、技术预研、前代产品经验教训。这解释了设计开发天然带不确定性。
- **输入比输出更宽泛、更通用**——"宽泛"指概括程度：输入说"一台能低温运行的设备"，输出要落到"-40℃下连续工作72小时、误差≤±0.5℃"（输出更详细、更具体，呼应定义正文"更详细的需求"）。
- **需求通常以特性（3.10.1）来规定**——特性 = 可区分的特征。把抽象需求落到特性上，需求才变得可测量、可验证：

```mermaid
flowchart LR
    A["需求 3.5.1<br/>宽泛 · 抽象"] --> B["特性 3.10.1<br/>可区分的特征"]
    B --> C["可验证的规格<br/>落到可测特性上"]
```

  特性可区分 → 可测量 → 需求可验证。特性类别：物理 · 感官 · 行为 · 时间 · 人体工效 · 功能。

  **跨标准分流（22 号 §4.2／§4.4）**：本注的「特性」取 **ISO 9000:2026 §3.10.1** 质量管理语境（区别性特征，带 inherent／assigned 限定）；**ISO 1087:2019 §3.2.1** 的 `characteristic`（`abstraction of a property`，属性的抽象）是同名不同物，属**概念构造的抽象层**——二者不可互替（同 §0 表后注）。

  **命名层（22 号 §4.3～§4.5）**：特性被**命名**并配属性值后，才成为可登记、可对账的条目——这一步的术语锚是 **`attribute`（ISO/IEC 2382-17:1999 §17.02.12，*A named property of an entity*，实体的命名属性）**。其在术语学体系中的位置是**从 `property`（ISO 1087:2019 §3.1.3，*feature of an object*，对象的特征）分出的"命名层"侧支**（22 号 §4.5）——与 ISO 9000 §3.10.1 的**特性**分属两个语境：特性答"区别性特征是什么"，attribute 答"该特征叫什么名、取值多少"。

- **一个项目（3.2.11）中可有多个设计和开发阶段**——定义在项目内部是**递归**的：

```mermaid
flowchart LR
    A["输入需求<br/>宽泛"] --> B["设计开发<br/>阶段 1"]
    B --> C["中间需求<br/>细化中"]
    C --> D["设计开发<br/>阶段 2"]
    D --> E["输出需求<br/>更详细"]
```

  概念设计把客户需求变成系统需求，详细设计把系统需求变成部件规格，工艺设计把部件规格变成可生产、可检验的要求——每一级都在执行同一个 3.3.11。**每个阶段的输出需求，就是下一阶段的输入需求，直到需求足以支撑实现和验证。**

**注2——用词辨析**：英语里 design（设计）、development（开发）与 design and development 三者，有时完全同义，有时用来指整个设计开发的不同阶段（如 design 指概念/方案阶段，development 指详细化/实现阶段）。**用哪个词不重要，重要的是整体是一个需求转化过程。**

**注3——可加限定词**：为指明"设计开发什么"，可加修饰语，如**产品设计开发、服务设计开发、过程设计开发**。再次确认：设计开发的对象不限于产品。

### 2.4 从定义推出的关键结论

1. **"更详细"是判定设计开发是否发生的唯一试金石**。输入输出同样详细 = 没发生设计开发。这是判断"这个变更算不算设计开发"的核心抓手——只改外观颜色、不产生任何新需求细节的变更，严格说就不构成设计开发。
2. **设计输出 = 新的规定需求**。定义把输出明确为"需求"，所以设计输出文件（规格书、图纸、工艺文件）本质是规定需求集合，直接成为后续**验证（3.11.12）**的参照。
3. **需求 → 特性 → 可验证**是设计开发的"质量命脉"：需求不落到特性上，验证就没有对象。
4. **设计开发是递归的、可分阶段的**（注1），每一阶段都是完整的 3.3.11。

### 2.5 四个常见误区

| 误区 | 正解 |
|---|---|
| 设计开发 = 画图 / 创意活动 | 是需求转化的过程集合 |
| 只有硬件产品才有设计开发 | 产品、服务、过程都可（注3） |
| 输入需求必须一开始就完整明确 | 输入本来就宽泛，正是设计开发把它变详细 |
| 一个设计开发项目只有一个阶段 | 注1明确可以有多个阶段 |

## 3. 设计开发的内部机制：分解、分配与解耦

设计开发（3.3.11）承诺"将需求转换为更详细的需求"，且一个项目可有多个阶段、每一级都是完整的 3.3.11（注1）。但定义只说"更详细"，没说**怎么变详细**——这个"怎么"，就是**分解与分配**：分解把框架需求拆成更细的叶子，分配把叶子 1:1 搬到下一级的枝梢，分析检查每个枝梢是否充分承接。三个动作构成设计开发内部的**结对机制**，也带出一个关键问题——"分解规则"到底应该是什么样？

> 讨论中提出一个命题：
>
> "没有一个统一的规则，不同的框架定义分解分配给后续的框架定义，可以根据经验定义其独有的分解规则，才可以实现分解与分配解耦。"
>
> 这个命题**对了一半**。要辨清它，必须先把"分解规则"这个词拆成两种性质完全不同的东西。

### 3.1 关键辨析：内容规则 vs 形式判据

| 维度 | 内容规则（怎么切） | 形式判据（切得好不好） |
|------|-------------------|----------------------|
| 回答的问题 | 切法：按什么维度把需求切开 | 判据：切出来的条目合不合格 |
| 典型例子 | 按利益相关方拆 / 按流程拆 / 按能力拆 / 按职责拆 | 原子性、语义四查、指标三场景、候选声明、1:1、全覆盖 |
| 性质 | 领域经验 | 逻辑要求 |
| 适用范围 | 结对特有（每对结对不同） | 全链通用（所有结对相同） |
| 该不该统一 | **不该**——必须业务化、领域化 | **必须**——不统一则解耦失败 |

**一句话：独有的是切法（内容规则），统一的是判据（形式判据）。** 把两者混在"分解规则"一个词里，是一切误解的根源。

> 〔按：ISO 9000 的优先术语是 interested party，stakeholder 是其**许用术语**（2015 §3.2.3 索引标 admitted term；2026 §3.1.4 两词平列同行），GB/T 19000 译「相关方」；ISO/IEC/IEEE 15288（GB/T 22032）与 42010（GB/T 45630）的优先术语是 stakeholder，译「利益相关方」。**英文同词、中文分译两名**——实据在两处定义不同（9000 取「能影响／受影响／自认受影响」，15288 取「拥有权利、份额、主张或利益」），**理由在定义上，不在英文词上**。本文条款号按 ISO 9000:2026，所引国标中文出自 GB/T 19000—2016（等同采用 ISO 9000:2015）。**正文分流规则**：引 ISO 9000／所引国标中文（interested party）的**原文位保留「相关方」**；指 15288／42010 的 stakeholder 的**需求链位与角色位一律写「利益相关方」**——两名的理由在**标准归属与两处定义差异**上，不在英文词上。〕

### 3.2 内容规则为什么必须业务化（命题成立的一半）

不同结对、不同领域的"切法"天然不同，不可能有万能切法：

| 结对（**需求链，逐级更详细的需求**） | 业务切法 | 依据的领域经验 |
|------|----------|---------------|
| ① 原始需求 → 利益相关方需求 | 按利益相关方拆 | 法务 / 财务 / 业务，谁提出谁就是一类 |
| ② 利益相关方需求 → 业务流程 | 按流程阶段拆 | 发起 → 初审 → 校验 → 终审 → 签章 → 归档 |
| ③ 业务流程 → 系统需求 | 按系统能力拆 | 审批 / 校验 / 签章 / 归档 / 检索 |

**另一条链（不是上表的第 ④ 行）**：**架构 → 设计**——架构（**基本概念或属性 ＋ 实现与演化的管控原则**，42010:2022 §3.2）经**架构描述（AD）**表达，再由**设计定义过程**转化为**设计元素**（15288:2023 **§6.4.5.3 b)2)**：*Transform **architectural entities and relationships** into **design elements***）。它也有自己的"切法"（引擎／服务／台账，按职责内聚），但那属**设计定义的领域经验**，**不是"从系统需求拆出来"的下一级**。〔**勘误（2026-10-12·全库对齐轮）**：本表原列 4 行，第 ④ 行为「系统需求 → 架构描述（AD）｜按职责内聚拆｜引擎 / 服务 / 台账」——**该行已移出需求链表**（见上「另一条链」）。**两处错**：① **架构描述（AD）不是需求的下一级**——它是**架构的表达**、一份**工作产品**（42010:2022 §3.3；Introduction L177：架构本身 *intangible and abstract*），**不属需求细化链**；② **"引擎／服务／台账"是设计元素**（原举例本身没错），**其规格归设计定义过程**（15288 §3.13），不是从系统需求"拆"出来的。故本表读作**一条需求链（①→③）**＋**紧接其后的架构→设计链**，两者**并列、不可串成四级**。〕

要点：

1. **业务分解规则的本质**：把该领域"什么东西该是一件事"的知识，编码成切法指南。审批域知道"按流程节点拆"，硬件域知道"按物理边界拆"，检索域知道"按数据流拆"——这些是不可跨域迁移的经验。
2. **万能切法不存在**："按三个业务域切"只对特定系统成立，对另一个系统就是错的。试图写一条全项目通用的切法规则，是自欺欺人。
3. **业务化的价值**：首次拆对率提高、退回次数减少、领域专家可以直接参与分解规则的制定与评审。

### 3.3 形式判据为什么必须统一（命题不成立的一半）

如果连"切得好不好"的判据都各自定义，解耦反而彻底失败，四个理由：

1. **分配对账需要统一的账本语言。** 全覆盖、1:1、N:1 是对"所有结对送来的叶子"做机械检查的尺子。判据不统一，A 结对送来的叶子在 B 结对的下层无法对账——检查语言不一致，互相把门的前提（同一副门框）就不存在。
2. **退回诊断假设必须跨结对通用。** 退回机制的核心假设是"悬空叶子 = 欠分解（拆片）或缺枝（加枝）"，这个诊断对每个结对都成立，退回建议才能标准化。
3. **互相把门需要公共基线。** "分配检出来的问题，一半是分配自己的错，一半是上游的错"——这句话能成立，前提是上下游用同一套判据说话。
4. **解耦的对称性。** 分解的尺子和分配的尺子各自独立、各自可查，但两者之间必须有可比的公共基线；否则"这个结对拆得好不好"和"那个结对分得对不对"无法放在同一张桌面上讨论——这是回到耦合，而且是更糟的耦合（连共同语言都没有）。

### 3.4 解耦机制全景：三层规则体系

```
┌─────────────────────────────────────────────────────────────┐
│ 一条结对链上的规则体系                                        │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ L0 通用形式判据 · 所有结对共享（统一）                 │  │
│  │ 原子性 · 四查 · 指标三场景 · 候选声明 · 1:1 · 全覆盖   │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                             │
│  L1 结对内容指南 · 切法按业务经验各自定义（独有）            │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐          │
│  │① 按利益相关方 │ │② 按流程  │ │③ 按能力  │ │④ 按职责  │       │

│                                                             │

│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**两个关键装置，缺一不可：**

1. **候选声明（B4 字段）——接口耦合、判据独立。** 每片叶子在分解时必须声明一个候选枝梢 ID：分解"声明我归谁"，分配"验证对不对"。声明是给分配的输入，不是分解的验收。这是分解与分配之间唯一的耦合点——有它，分配不用猜；判据上，两把尺子依然各自独立。
2. **骨架先行——靶子。** 分解必须对着已约好的下层枝梢清单拆，候选声明才有枝梢可指。骨架就是"水电点位图"：两拨工人各自施工（工作解耦、可并行），共享一张图（信息耦合）。

### 3.5 业务规则的来源：退回闭环的经验沉淀

L1（结对内容指南）不是凭空拍出来的，它是**退回闭环的副产品**：

1. 分配发现悬空叶子 → 规则出分级报告（形式错→自动建议；语义错→双假设+证据）；
2. 人类裁决：欠分解（该拆片）还是缺枝（该加枝）；
3. 退回分解重拆，循环至三自检清零；
4. **每次裁决都是一条新的 L1 经验**——"这类需求以后按 X 拆"，沉淀进该结对的切法指南；
5. 下次同类问题第一次就拆对，首拆率随项目推进持续提高。

这就是"经验驱动"的规则演化：**L1 是项目自己的记忆，越用越准。**

### 3.6 定论

> **解耦 = 判据统一（L0，保证可对账）× 切法业务化（L1，保证切得对）× 契约共享（候选声明 + 骨架先行）。**
>
> 规则说明"分解成什么"，就让分配"有据可查"——从"猜谜"变"对账"。但"支持"是形式层面的：规则保证可分配性可被检查，正确分配永远属于人的语义裁决。

| 层 | 内容 | 统一性 | 作用 |
|----|------|--------|------|
| L0 | 形式判据 | 统一 | 让分配可对账、退回可诊断、把门有公基 |
| L1 | 业务切法 | 独有 | 让首次拆对率高、领域经验可复用 |
| L2 | 组织约定 | 本地化 | 让术语/命名/模板一致，降低沟通成本 |

### 3.7 与教材书的关系

本节源自第6章「设计开发落地：一棵树、三个动作」研读讨论。三个关联点：

- **第6章**：语义四查、指标三场景本身就是 L0 的雏形——它们是"元规则"（检查规则的规则），不规定具体怎么切；本节补充的是：**切法本身必须业务化（L1）**，这是第6章没有展开的部分。
- **第13章 配置管理**："每个文档结对是局部甲乙方，契约链的每一级都这么咬合"——候选声明 + 骨架先行，就是契约链在结对处的具体形态。
- **第8章 评审验证确认**：符合性分析收编进验证门禁后，"规则查形式、人裁语义、退回闭环"的整体结构依然成立，只是加了一道门禁。

## 4. 设计开发的终点：止于"可实现"

### 4.1 推导过程（四轮修正）

| 轮次 | 候选终点 | 为什么被修正 |
|---|---|---|
| 1 | 确认通过 | 错位：确认（3.11.14）的判定对象是**已可使用的客体**、发生在设计开发形式结束之后，而定义的设计开发锚定"需求"——它作不了 3.3.11 的内在终点 |
| 2 | 责任移交点（设计基线发布） | 只是制度动作，不是内在判据 |
| 3 | 可验证 | 逻辑倒置：验证（3.11.12）以"规定需求"为参照，而规定需求是设计开发的输出——**验证能发生，前提是设计开发已经结束** |
| 4 | **可实现** ✅ | 定义内部唯一的自然终止条件 |

**关键论证（为什么"可验证"不对，用验证定义反推）**：

- 3.11.12 验证 = 对**规定需求**已得到满足的认定 → 验证的前提是规定需求已经存在（设计开发已产出）。
- 把"可验证"当终点 = 让设计开发结束在验证的起跑线上——循环倒置。
- 且验证注1：客观证据可以是"文件评审"——几乎所有写清楚的需求都"可验证"，这个判据区分不了完成与未完成。

### 4.2 结论

> **设计与开发止于"可实现"：需求被细化到足以支撑客体实现、生产和服务提供可直接执行的程度（输出成为完整的规定需求）。**
>
> 验证与确认以这份规定需求为参照、在其后把关；"可实现"是入场券（必要条件），验证通过是及格线（符合），确认通过是目的达成——但**终点在验证之前**。

```mermaid
flowchart LR
    A["设计开发<br/>3.3.11 需求转化"] --> B["可实现的需求<br/>规定需求 · 终点"]
    B --> C["验证 · 确认 · 生产<br/>判定与实现 · 其后"]
```

> 〔按（第十轮·依 23 号补缺位）：确认落在"其后"不止是时序问题——§3.11.14 的确认**必须"用"**（注 3：使用条件**可真实可模拟**），因为其**判据是情境（预期用途 / 应用场合）而非条目**；隐含需求没有明示形式、在逻辑上无法被验证，只能被确认（23 号 §4.5、§3.6）。〕

### 4.3 实物产品的具体化：八个方案全部完成

> **实物产品的设计与开发，止于技术方案、物料采购方案、制造方案（工艺）、测试方案、交付方案、部署方案、操作方案、运维方案全部完成。**

```mermaid
flowchart TD
    A["设计开发的输出<br/>规定需求 · 可实现"] --> B["八个方案 = 一个输出的八个面向"]
    B --> C1["技术方案"]
    B --> C2["物料采购方案"]
    B --> C3["制造方案（工艺）"]
    B --> C4["测试方案"]
    B --> C5["交付方案"]
    B --> C6["部署方案"]
    B --> C7["操作方案"]
    B --> C8["运维方案"]
```

**八个方案的本质**：不是八件独立的事，而是一个东西的八个面向——**"规定需求"按下游环节的分配**：采购照着买、生产照着做、检验照着测、实施照着装、用户照着用、维护照着修。每个方案 = 给一个下游环节的"可实现需求"。这正是 8.3.5 b"满足后续产品和服务提供过程的需要"的完整展开。

**每个方案的条款落点**：

| 方案 | 条款落点 |
|---|---|
| 技术方案 | 8.3.5 d：规定对预期目的至关重要的特性 |
| 物料采购方案 | 8.4：外部提供的要求 |
| 制造方案（工艺） | 8.5.1：生产和服务提供的受控条件 |
| 测试方案 | 8.3.5 c：监视和测量要求 + 接收准则 |
| 交付/部署/操作/运维 | 8.5.1 及生存周期各环节 |

**用词精确性**："方案"不是"结果"——测试方案属于设计开发（规定测什么、判据是什么）；测试执行和测试结论属于验证（3.11.12）。停在"方案完成"正好守住"设计开发止于可实现"这条线。

**判据（可操作）**：

> **还有哪个环节会在执行时反问"这到底怎么做"？——有，设计开发就没结束。**
>
> **设计开发的终点，由"最后一个配齐的方案"决定，不由"第一个完成的技术方案"决定。**

**技术方案为什么不够**：技术方案只回答"客体本身长什么样、怎么实现"——它是八个方案里最先完成、最显眼的，但只是第一个面。只到技术方案就宣布终点，后果是连环空转：采购没有物料规格和合格准则（8.4 空转）、生产没有工艺依据（8.5.1 空转）、测试没有判据（验证无法启动）、交付/部署/操作/运维没有指令（产品出门即"失联"）。

### 4.4 三层次"可实现"

> 技术方案只是**原理层面**的可行，"真正实现并运行"是**事实层面**的证明——两者之间隔着整个验证与确认。

```mermaid
flowchart TD
    A["原理可实现<br/>技术方案 · 纸上可行"] --> B["方案可实现<br/>八方案齐备 · 设计开发终点"]
    B --> C["事实可实现<br/>造出来 · 运行 · 验证确认裁决"]
```

- **层1 原理可实现**：技术方案给的——只证明"从技术原理上走得通"，是纸上的。
- **层2 方案可实现**：八方案齐备给的——**设计开发终点**。从"原理可行"跨到"可执行指令齐备"。
- **层3 事实可实现**：验证/确认给的（终点之后）——"能否真正实现并运行"这个未知，由验证（对照规定需求）和确认（对照**为预期用途或应用的需求**）回答；确认的尺子主体**不在明示需求内**——明示的预期用途需求**同时是两把尺子**，这是 V&V 实践大量重叠的根源（23 号 §3.3）。

**设计开发的"诚实边界"**：设计开发交付的不是**事实**，而是**声明**——一份"可信的可实现声明"（八方案齐备、逻辑自洽、经评审/样机/仿真提高置信度），最终裁决权在终点之后的验证/确认。

## 5. 设计开发的起点：需求规格确立

### 5.1 结论

> **设计与开发的起点 = 一份满足"可转化"判据（完整、无歧义、不冲突、隐含需求已识别）的需求规格，被正式确立为设计输入的时刻。**

与终点对称：

```mermaid
flowchart LR
    A["起点 · 需求规格确立<br/>可转化 · 8.3.3"] --> B["设计开发<br/>3.3.11 需求转化"]
    B --> C["终点 · 方案齐备<br/>可实现 · 八方案"]
    C --> D["验证 · 确认<br/>其后把关"]
```

### 5.2 起点判据：需求"可转化"（8.3.3）

1. **完整**：功能、性能、以及由产品和服务性质导致的潜在失效后果——一个不缺；
2. **无歧义**：每个需求只能有一种理解；
3. **不冲突**：需求之间自洽（资源、法规、性能之间不打架）；
4. **隐含需求已识别**：最容易被忽略的一条——隐含需求（3.5.1）不会自己开口，需要组织主动识别（8.2.2）。起点最贵的部分：它没写进规格，却最决定规格对不对。

### 5.3 起点之前：研究

注1：输入需求"通常是研究的结果"。设计开发不始于"点子"，而始于"被研究确认过的需求"：

> 点子 / 灵感 / 想法 →（研究：市场调研、可行性分析、技术预研、客户需求识别）→ **确定的需求** → 设计开发开始

需求未确定就开工 = 拿半成品当原料——设计开发会白白转化一堆错误需求，终点越完美，偏离越远。**很多项目"设计得很辛苦、产品没人要"的根源：不是终点没管好，是起点没收好。**

### 5.4 起点与终点对称总表

| | 起点 | 终点 |
|---|---|---|
| 判据 | 需求**可转化** | 需求**可实现** |
| 含义 | 输入完整、无歧义、隐含已识别 | 八方案齐备、可执行指令配齐 |
| 资格 | 设计开发可以启动 | 设计开发可以结束 |
| 条款 | 8.3.3 设计输入 | 8.3.5 设计输出 |

> 设计开发始于"需求被确定"（可转化），止于"方案被配齐"（可实现）。起点没收好，转化的是错误需求；终点没守好，交付的是残缺声明。

### 5.5 需求规格是"要什么"，八方案是"怎么做"

- 需求规格 = **what**：客体的需求，宽泛、可转化；
- 终点八个方案 = **how**：怎么实现。

设计开发本质 = **what → how 的转化**。验证（3.11.12）就是拿 how（设计输出）对 what（输入规格）——起点规格的质量直接决定验证有没有靠谱的参照。

**补充：需求规格不止一份**——系统级规格 → 子系统级规格 → 部件级规格，每一级设计开发阶段的输入都是一份规格（呼应注1"多个阶段"）。"起点"是第一份：产品/系统级需求规格被确立的时刻。

## 6. 需求开发与设计开发的边界

**问题**：需求规格之前那段（需求调研、可行性研究、需求说明书 URS 等文档的开发）算不算设计与开发？

```mermaid
flowchart LR
    A["需要 · 期望<br/>顾客 · 市场 · 利益相关方"] --> B["需求开发<br/>8.2 需求确定"]
    B --> C["需求规格<br/>起点 · 可转化"]
    C --> D["设计开发<br/>8.3 需求转化"]
    D --> E["八方案齐备<br/>终点 · 可实现"]
```

### 6.1 三层答案

**概念上（ISO 9000）：算，而且同构。**
3.3.11 定义"不挑段"：顾客说"我要一台能低温运行的小型设备"，需求开发把它变成"工作温度-40℃、体积≤0.5m³、…"——这本身就是一次"需求变详细"。需求开发也是需求转化，同样具备 3.3.11 的定义特征。**它和设计开发是同一种认知活动的不同阶段**，只是转化发生在更靠前、更粗的层级。

**标准组织上（ISO 9001:2015）：可合可分，由组织策划决定。**〔该标准**库内无全文**——属「**库外来源·不可核**」；版本号按 2015 版标注，条款号照录、不作正本核证（台账 02 号 §五 G-21）。〕
- 需求确定（顾客沟通、要求确定、要求评审）→ **ISO 9001:2015 §8.2**；
- 设计开发 → **ISO 9001:2015 §8.3**。

这不是因为"需求开发不是需求转化"，而是**职责组织方式**：8.2 管"要什么"（面向顾客与市场），8.3 管"怎么实现"（面向技术与实现）。复杂组织常把需求开发作为设计开发第一阶段纳入 8.3；简单组织放在 8.2 即可。**两种策划都合规**。

**实用判据：看"客体"是否确立 / "特性"是否被规定。**
- 客体边界还没确立（还在定"我们要做什么产品"）→ 需求开发（ISO 9001:2015 §8.2）；
- 客体已确立、开始细化它的需求 → 设计开发（ISO 9001:2015 §8.3）。

用质量定义（3.5.2"客体（3.5.3）的固有特性"）加固：需求开发阶段，客体还没确立，**特性压根不存在**，质量没有承载体；设计开发阶段才开始"把需求落到客体固有特性上"。判据升级为更硬的一条：

> **特性是否被规定**——特性还没开始规定，是需求开发（ISO 9001:2015 §8.2）；特性开始被规定，才是设计开发（ISO 9001:2015 §8.3）。需求规格就是那道闸门。

### 6.2 必须补的提醒

不管这些文档（市场调研、可行性研究、URS）归 8.2 还是 8.3 第一阶段，**它们都是设计输入的来源，直接影响产品质量特性**——审核时"这些文档不在受控范围"过不去。它们可以不属于"设计开发"，但**不能不受控、不可追溯**。

## 6.5 需求与方案的结对设计：设计与开发的落地

> 本节把"设计与开发"从单侧（需求树内部）扩展到双侧：**需求文档族与方案文档族的结对**。总纲一句话：设计与开发落地为"需求 × 方案的结对设计"——**先拆好"要什么"，再想几个"怎么做"，对着核、挑一个、签字定稿**。

### 6.5.1 为什么是"结对"

需求文档（要什么）与方案文档（怎么做）天生成对出现——有需求就得有方案去满足它。§3 的分解/分配/分析机制发生在单侧（需求树内部）；结对六步把它扩展为**跨文档**的完整落地：需求侧把"要什么"拆细并验证，方案侧构思"怎么做"并裁决，中间靠"对需求"（分配）咬合成一份可执行的契约。

### 6.5.2 结对六步（白话版）

| # | 步骤 | 白话 | 概念归属 | 三动作的展开 | 锚点 |
|---|---|---|---|---|---|
| ① | **拆需求** | 把"要什么"（需求框架定义末级节点）拆成更细的"要什么"（需求详细定义） | 需求侧设计开发（ISO 9000 递归第一级） | 分解 · 做 | §3 分解；§6.1（概念同构）；3.3.11 注1 |
| ② | **验分解** | 检查拆得清楚、不打架、没漏、没越界——合格才往下走 | 可行性分析（分解的评审关） | 分解 · 验 | ISO 9001:2015 §8.3.3；§3.3 L0 |
| ③ | **出方案** | 基于**需求详细定义 + 组织资产 + 专业知识**，想出 **≥2 个**候选"怎么做"（方案框架定义） | 构思（发散 · 有方法——组织资产是"方法"的载体） | 分配 · 目标（先造树） | 16-§2；15288 §6.4.4 |
| ④ | **对需求** | 把每条"要什么"贴到方案对应的部分上，看覆盖全不全 | 分配（候选声明 · **只挂不细**） | 分配 · 做 | §3.3 候选声明；SEBoK allocate |
| ⑤ | **做裁决** | 按规则比较候选方案，挑一个，把选择的理由记下来 | 定义（画边界 · 终结漂浮） | 分析 · 对象（先定方案） | ATAM 效用树；ADR |
| ⑥ | **签定稿** | 定下最终方案：逐枝梢做符合性分析（语义+指标过）→ 利益相关方确认 → 冻结成基线 | 分析（入口关）+ 定义收敛 + 层级出口把关（**本层出条件性合规**） | 分析 · 核 + 封存 | 42010 certifying（**合规对象是架构**）；ISO 10007 |

> **出处补注（2026-09-21 与 30 号对齐）**：⑥「认证」对应 ISO/IEC/IEEE 42010:2022 architecting 动词链中的 *certifying proper implementation of*（§3.1）。**须补一层边界**：该动作的**合规对象是 architecture，不是 AD**——`certifying proper implementation of` 里 *implementation* 的主语是**实现**；本层产物是**工作产品**（方案框架定义），它只能出具**条件性合规**（合规的承担者是 implementation，本层的动作只是"层级出口把关"）——24 号 §10.7、§11.5；22 号 §6.4 互参。该标准的中文等同采标本为 **GB/T 45630-2025《系统与软件工程 架构描述》**（等同采用、2025-11-01 实施），是架构类术语的中文定名依据（30 号 §1.1、§8.2）。

**组织资产**（organizational process assets）：组织**跨项目**沉淀的可复用资产——模式库、参考架构、可复用组件、经验教训（lesson learned）、历史架构决策（ADR 库）、组织标准与模板。③"出方案"不是现场拍脑袋，而是**先查组织资产**——这正是构思三特征之"有方法"（16-§2.3）的组织化落地：方法不在个人脑子里，在组织资产库里（呼应 ISO 56000 家族的组织制度化与 §3.5"退回闭环的经验沉淀"：项目记忆 → 组织记忆）。

**口诀**：**拆 · 验 · 想 · 对 · 裁 · 签**。

```mermaid
flowchart TB
    A["① 拆需求<br/>把'要什么'（需求框架）拆成更细的'要什么'（需求详细）"]
    B["② 验分解<br/>检查拆得清楚、不打架、没漏、没越界"]
    C["③ 出方案<br/>基于需求 + 组织资产，出 ≥2 个候选'怎么做'"]
    D["④ 对需求<br/>把每条'要什么'贴到方案对应的部分，看覆盖全不全"]
    E["⑤ 做裁决<br/>按规则比较候选，挑一个，把理由记下来"]
    F["⑥ 签定稿<br/>定下最终方案，利益相关方确认，冻结成基线"]
    A --> B --> C --> D --> E --> F
    classDef req fill:#fdf6ec,stroke:#c9a44a,color:#4a3c28;
    classDef sol fill:#eef3f8,stroke:#5b7fa6,color:#2c3e50;
```

**三动作怎么长成六步**：三个动作要落地，每件都缺一样它特定的东西——分解缺"拆完没人检查"（②验分解），分配缺"搬去的那棵树还不存在"（③出方案，构思），分析缺"核的对象还没定、核完要封存"（⑤做裁决＋⑥签定稿）。于是三动作 × 各带一步缺的 = 六步：分解长成拆与验、分配长成想与对、分析长成裁与签。**构思不是三动作之外的第四样，而是分配缺的目标树——没有目标树，分配无处可搬。** 六步 = 三动作 + 三件每个动作缺的东西（验 · 想 · 裁）。

### 6.5.3 ② 可行性分析：检查什么

**一句话**：①拆完之后，检查"拆得合格吗"——**形式**上拆得规不规范（三查），**数值**上指标链断没断（两查）。

**第一件事：拆得规不规范（形式三查）——看形状，不动数值**

| 检查 | 问什么 | 不过怎么办 |
|---|---|---|
| **可转化**（入口） | 框架本身够格拆吗：完整 · 无歧义 · 不冲突 · 隐含已识别 | 退回需求开发（8.2）补识别 |
| **可分配**（出口） | 拆出来的叶子能用吗：原子性 · 全覆盖 · 1:1 · 候选声明 | 退回①重拆（悬空 = 拆片或缺枝） |
| **边界不越位**（深度） | 拆到"可被分配"为止了吗？再细就侵入方案层了 | 调粒度 |

**第二件事：指标链断没断（数值两查）——指标从框架一路分到方案，两处必须闭合**

指标分三个位置：框架末级节点（M）→ ①分解 → 需求详细条目（D_i）→ ④分配 → 方案框架末级节点（S_j）。

```mermaid
flowchart LR
    M["框架末级指标<br/>（M）"] -->|"①分解"| D["需求条目指标<br/>（D_i）"]
    D -->|"④分配"| S["方案末级指标<br/>（S_j）"]
    M -.->|"查 ①：分解闭合<br/>ΣD_i 组合回 M"| D
    D -.->|"查 ②：分配预判<br/>S_j ≥ D_i 留裕量"| S
```

| 检查 | 问什么 | 怎么查 | 不过怎么办 |
|---|---|---|---|
| **指标闭合**（分解） | 拆出来的指标组合，能回到框架指标吗？（整机 ≤10W → 各模块之和 ≤10W；误差、可靠性同理） | **计算 / 仿真**（②时即可算） | 退回①重新分配指标（哪块超了改哪块） |
| **分配预判**（分配） | 需求指标给方案留了满足空间吗？（方案末级 S_j 必须 ≥ 需求条目 D_i，且留裕量） | 组织资产比对（达得到吗）+ 冲突检查（同元素指标互斥）——②预判、④分配时验证 | 退回①平衡指标（太紧的放宽） |

**收束**：形式三查管"**拆得规不规范**"，数值两查管"**指标断没断**"——**后者更重要**：拆得再漂亮，指标闭合不了，模块做完系统照样不达标（指标闭合不过 = 返工全链；分配预判不过 = ③白想、④必然撞墙）。

**锚点**：3.11.1 确定（计算是确定手段）；15288:2023 **§6.4.6 系统分析**（建模/仿真评估。〔按：原记 §6.4.2 系笔误——§6.4.2 是"利益相关方需要和需求定义"，系统分析在技术过程末段，24 号 §8.4 引作 §6.4.6，号已核〕）；"仿真计算报告"（13-§7.1）是指标闭合的落档载体；组织资产（§6.5.2）是分配预判"可实现"的比对依据。

**概念定位**：分解 = "定义"动作的落地；可行性分析 = 它的评审关——是 16 号"评审与背书"在需求侧的投影。所以它不在 16 号生成六步里（16 号从架构驱动因素 ASR 起），是需求侧多出来的必要关口。可转化判据（8.3.3）在每个递归层级的输入处**复检**——呼应 §5.2 起点判据与 §5.5"需求规格不止一份"（系统级 → 子系统级 → 部件级，每级输入都是一份规格）。

### 6.5.4 三个精化点

1. **④先分配、⑤后权衡**：这里的分配是**轻量覆盖性映射**（候选声明：只挂不细），为⑤提供覆盖率 / 均衡性 / 冲突性证据；正式细化留到⑤选定之后、⑥定稿之前，避免被否掉的方案白做工。
2. **派生需求回流**：⑥定义方案会派生出对需求侧的新需求（接口约束、性能指标、可行性限制）——必须**回流需求基线 + 双向对账**，方案侧不能单方面定义。
3. **⑥"利益相关方确认"的双重身份**：拆成两个动作——**内部评审对质**（IEEE 1028 technical review：决策理由、备选死因）+ **利益相关方接收／背书**（"你认吗"——认的是这份**工作产品**，不是 §3.11.14 的确认）；通过才冻结基线（ISO 10007）。

> 〔按（第十轮·依 23 号对齐）：⑥ 的对象是**方案框架定义**——一份**工作产品**；§3.11.14 的确认须**通过提供客观证据**、且判定对象须**已可使用**，而工作产品**不能被"使用"**，故本层不发生**确认**；**验证则做得了**——15288:2023 §6.4.9 的验证对象含**人工制品**（方案框架定义即在例中），证据可为评审文件（§3.11.12 注 1）。工作产品层的替代判定是 IEEE 1028 的 **technical review**，结论只能是**条件性合规**——"合规的承担者是 implementation"（23 号 §10.3、§10.6 冲突 1 及其边界注；24 号 §10.7）。**确认不在本层接口发生**（其现场在使用态）：本层两个动作给出的是"**交付后由实现举证**"的指向。本节其余各处（§6.5.2 表、图、§10 结论 11）所称"利益相关方确认"即指这两个动作。〕

### 6.5.5 定位与递归

本六步是 ISO 9000:2026 §3.3.11 在**"需求 → 方案框架"这一个递归层**上的完整落地；向下还有"方案框架 → 方案详细"的下一级结对，重复同一六步（16-§5.2④ 分形递归）。每一级结对的输出（方案框架定义 + ADR）冻结为基线，就是下一级结对的输入——方案框架定义即该层级设计开发的输出，本质是"对方案的更详细需求"（规定需求，§2.4）。

> ⚠️ **层级澄清（与 §4 不冲突）**：⑥"冻结基线"是该递归层的**出口**，不是设计开发的最终终点——§4 的终点"可实现（八方案齐备）"是**多个递归层全部走完**后的总终点，仍由"最后一个配齐的方案"决定。方案框架基线只承诺"本层级的方案定义已定稿"，不承诺"八方案已齐备"。

> 〔按：本节所划递归层在 ISO/IEC/IEEE 15288:2023 口径下由**架构定义（§6.4.4）与设计定义（§6.4.5）两个过程**交替承担，两者**不是阶段而是可迭代并发**（24 号 §8.1、§8.2）；且**架构与设计的差别是种类（kind），不是粒度（granularity）**——架构描述与设计描述是两个平级的 artefact（同列 15288 §3.6 的 EXAMPLE。**术语提示**：artefact＝**人工制品**（15288:2023 §3.6：*work product (3.32) that is produced and used during a project to capture and convey information*）；与 42010 的 **work product（工作产品）**两册**互为属概念、方向相反**——15288 侧 artefact ⊆ work product、42010 侧 work product ⊆ artifact（§3.3 Note 1：*A work product is an artifact produced by a process*）；本项目仍作**分流译名**（指 15288 侧写「人工制品」、指 42010 侧写「工作产品」），**理由是所属标准不同、属概念层级不同**，不是「两个词不可互译」——凡指 AD 与架构视角自身，写「工作产品」：22 号 §12 第 34 行、§8.2），架构不是"更粗一档的方案 / 设计"，也不是"更靠前的那个概要"（24 号 §3.1、§14.1、§14.2）。故本节"方案框架定义"是**设计侧**产物，不因"框架"二字而升格为架构；架构约束之所以能落在本节链上，只因它经逐级转化后成为**规定需求**（24 号 §8.3），其自身的明示化、基线化与合规判定另循 24 号 §7.3 与第 10 章。〕

> 〔按（第十轮·依 23 号补缺位）：**链外参照**——本链的输入输出全在**派生链**上，而派生链**只承载 stated**（generally implied 不上链），故"链路自洽"只保证 **verification 与 review 侧**；确认的判据（**预期用途 / 使用情境**，主体是隐含需求）**在链外**，链的结构无法表征它——须**另建**（use specification / ConOps / 使用场景，不是逐条需求）并作 ⑥ 的**上游输入**，否则 ⑥ 认的只是链上自洽，不是"用起来对不对"（23 号 §9.1、§4.5、§10.7；02 号 QR-06 的 ConOps）。〕

> 💡 **为什么"确认后必须冻结"（2026-08-25 补）**：方案框架定义确认后必然还有后续——它是下一级结对的输入、后续几乎一定会被变更、多角色要基于它协作——因此必须从"自由态"进入"受控态"（ISO 10007：基线 = 进一步开发的**参照** + 变更控制的**基础**）。三个理由：**下游参照 / 变更控制 / 共同语言**。**"冻结" ≠ "锁死不许改"**——基线后改动走变更流程（CR → CCB 评估 → 批准 → 记录），不是不能改，是不能偷偷改。**顺序：确认 → 基线 → 下游使用**，不能乱（先用未确认的东西 = 风险后移；不确认就冻结 = 冻结了没人认的靶子）。唯一可不冻结的情况：确认后即归档、不再被引用、不再变更（真实产品研发里罕见）。

### 6.5.6 六步 ≡ ISO 9000:2026 §3.3.11 的完整实例

"设计（设计和开发）：将客体的需求转换为对其更详细的需求的一组过程"——结对六步正是这个定义的操作化展开，逐项同构：

| §3.3.11 构件 | 定义原文 | 六步对应 |
|---|---|---|
| 输入 | 对客体的需求 | ①输入：需求框架定义（末级节点） |
| 动作 | 转换为 | ①②③④⑤⑥ 六个动作 |
| 输出 | 对该客体更详细的需求 | ⑥输出：方案框架定义（本质是规定需求集合，§2.4） |
| 性质 | 一组过程（3.3.1） | 六个过程动作的集合 |

**为什么方案框架定义算"更详细的需求"**："要什么"是分层的，客体随层级细化——客户需求（概念层）→ 系统需求（框架层，即方案框架定义）→ 子系统需求（详细层）→ 部件规格；每一层都是对**同一客体**（在该层级粒度上）的更详细需求，每一层都在执行同一个 3.3.11（注1 递归性）。方案框架定义描述"系统这一层要什么"（元素、接口、约束），本质是规定需求。〔**勘误（2026-10-12·全库对齐轮）**：原句续作"——'要什么'本来就包含结构要求（**架构约束也是需求**）"，**已删**——**架构内容不是需求的一支**：架构＝**基本概念或属性 ＋ 管控原则**（42010:2022 §3.2），需求＝*need or expectation that is stated, generally implied or obligatory*（ISO 9000:2026 §3.5.1），**两类内容、两种合格判据**；架构与设计是需求过程的**输入与约束**（15288:2023 §6.4.3.1 的 *design constraints*、§6.4.4.1 输入五组），**不是需求的上级或下级**。〕

**两处超出字面定义的合理扩展**（不矛盾，须声明）：
1. **③⑤ 多方案权衡**——3.3.11 只承诺"更详细"（变细了没），不管"更好"（选对没；§4.2"方案优劣由评审和验证把关"）；多方案是"更好"的机制，是转换的合理子过程。
2. **⑥ 利益相关方接收／背书 + 冻结基线**——精确切分：六步 = 3.3.11（①②③④⑤ + ⑥"定稿"部分）+ 层级出口动作（⑥"接收／背书 + 冻结"= 工作产品层的**替代判定**（IEEE 1028 technical review，结论为**条件性合规**）+ ISO 10007 的投影）。与 §4"终点在验证之前"（全局终点）不矛盾——层级内允许轻量出口把关作为下一层入场券；**§3.11.14 的确认不在本层发生**，它瞄准的是该层实现出的客体，**交付后由实现举证**（23 号 §10.3、§10.6；24 号 §10.7）。

**收束**：定义承诺"需求变详细"，六步回答"怎么变详细"；定义不含的"更好"与"确认"，六步以子过程和出口动作补齐，不越界。

## 7. 质量（3.5.2）深入

### 7.1 质量定义与设计开发的关系

> **质量**：客体（3.5.3）的一组固有特性（3.10.1）满足需求（3.5.1）的程度。

质量定义里的三个词——客体、固有特性、需求——恰好就是设计开发定义（3.3.11）的三个构件：

```mermaid
flowchart LR
    A["需求 3.5.1<br/>要什么"] --> B["设计开发 3.3.11<br/>需求 → 特性化规定需求"]
    B --> C["质量 3.5.2<br/>特性满足需求的程度"]
```

**核心定位**：

> **设计开发 = 质量的定义者**（把需求落到客体固有特性上，3.3.11 注1）；
> **验证/确认 = 质量的度量者**（判定特性满足需求的程度，3.11.12 / 3.11.14）。

- 起点（需求规格确立）＝需求确定，特性尚未规定——质量还不可度量；
- 终点（八方案齐备）＝客体固有特性被完整规定、附接收准则——**质量被完整"定义"了**，从此可以度量；
- 验证/确认＝客观证据测量特性满足需求的程度——**质量的度量**。

设计开发的全程，本质是**从"需求确定"走到"质量定义完成"**。这也解释了 8.3.5 d 为什么要求输出"规定对预期目的至关重要的特性"。

**"固有"二字的含义**：质量只算**固有特性**（存在于客体中的，如功能、性能、材质），不算**赋予特性**（如价格、品牌、交付时间）。设计开发的范围也被"固有"框住——价格、交付周期这类赋予特性是 8.2 等其他过程的事，**设计开发管不着，也不该管**。

### 7.2 质量是"吻合度"，不是"特性 ÷ 需求"

```mermaid
flowchart LR
    A["固有特性<br/>客体的固有特性集合"] --- B["需求<br/>外部的判定集合（标尺）"]
```

1. **两边不同质，除不了**：特性在客体里，需求在客体外，不是一个量纲。需求是**标尺**，特性是**测量结果**——质量问的是"结果在标尺上的位置"，不是"标尺除以结果"。
2. **"满足"是符合性判定，不是数量比**：特性达到需求规定的水平 → 满足；达不到 → 不满足。这是吻合/符合的逻辑。
3. **"程度"是评价概念**：注1 说质量可用**差、好、优秀**修饰——形容词，不是数字。质量是被"认定"出来的，不是被"计算"出来的（靠验证/确认用客观证据判定）。
4. **比值直觉的错误推论**：特性**恰好满足**需求 → 质量成立；特性**超出**需求（过度设计）→ 满足程度并不增加，只增加成本和复杂度。**出了需求区间，质量不升反降。**

### 7.3 "程度"如何得出：确定（3.11.1）

```mermaid
flowchart LR
    A["确定特性值<br/>3.11.1 · 测量检验试验评审"] --> B["与需求比对<br/>符合性 3.5.9 · 接收准则"]
    B --> C["认定满足程度<br/>质量 3.5.2 · 差/好/优秀"]
```

**三步得出法**：
1. **确定特性值（3.11.1）**——查明特性及其值。手段：测量（定量）、检验（符合性确定）、试验（按需求确定规定特性）、评审、计算。产出叫**客观证据（3.8.6）**。
2. **与需求比对——判符合性（3.5.9）**——用**接收准则**（设计输出 8.3.5 c 里提前写好的判定标准）比对。
3. **认定满足程度——得出质量（3.5.2）**——综合一组特性的符合情况，认定程度。动作上就是验证（3.11.12）和确认（3.11.14）。

**三个关键性质**：
- "程度"是**认定**出来的，不是算出来的——需要评价者基于客观证据；
- **单项是二元（符合/不符合），整体是程度（差/好/优秀）**——整体程度按特性重要度综合评价（关键特性优先，8.3.5 d）；
- **标尺是设计开发提前定的**——接收准则写在测试方案里（终点八方案之一）。设计开发定标尺（特性+接收准则），验证/确认执行"读标尺"。

> **四个条款，一步不缺，程度才出得来**：工具在 3.11，标尺在 8.3.5，动作在 3.11.12 / 3.11.14。缺了测试方案里的接收准则，程度就永远只能"感觉"，不能"认定"。

### 7.4 质量能有具体分值吗？

**标准层面：没有。** 三个近亲都不是分值：

| 概念 | 条款 | 形态 |
|---|---|---|
| 质量 | 3.5.2 | 程度：差 / 好 / 优秀（注1，形容词） |
| 符合性 | 3.5.9 | 符合 / 不符合（二元判定） |
| 等级 | 3.5.4 | 分类分级（如高档/低档） |

注意：**等级高 ≠ 质量好**（3.5.4 注）——高档车可以是差质量，低档车可以是好质量。因为等级是"按不同需求分类"，质量是"满足各自需求的程度"。标准在整个评价体系里**刻意不用单点分值**：特性多维不同质，加不成一个数；隐含需求无法完整数值化；注1 明确质量用形容词修饰。

**组织层面：分值可以造，但它是组织的度量，不是标准概念。** 打分 = 定权重（特性重要度）→ 单项评分（接收准则映射分数）→ 加权汇总 → "85分"。三个前提，缺一个分就是假的：

1. **需求完整**（起点）——漏了需求，评分体系就没覆盖它；
2. **特性规定完整**（终点）——漏了特性，分值少算一项；
3. **证据可靠**（验证）——分数必须挂在客观证据上。

**最要命的一条**：**关键特性不能被摊平**——8.3.5 d 说"对预期目的至关重要的特性"要优先。加权公式若把安全性、可靠性这种一票否决的特性摊进平均数，安全项失分被其他项补回来，"85分"就是用假象掩盖致命问题。**分值的最大陷阱：它给了你一个精确的错误。**

### 7.5 质量、符合性、等级三者定位

- 符合性回答：满足了吗？（二元）
- 程度（质量）回答：满足到什么程度？（评价）
- 等级回答：按哪套需求分类？（分级）
- 三者共同点：都以"需求"为参照——而需求（标尺）是设计开发定出来的。

## 8. 质量与进度冲突的解决

### 8.1 先拆伪前提

**质量不是时间的函数**（3.5.2：质量 = 特性满足需求的程度，与花多少时间无必然关系）。而且**进度本身就是一种需求**（8.2.2：交付时间和交付条件也是顾客要求的一部分）。

所以"质量 vs 进度"本质是**同一份需求集合内部打架**：性能/功能需求 vs 交付时间需求。解法不是二选一，是**重新平衡这份需求集合**。

### 8.2 四步解法

```mermaid
flowchart LR
    A["冲突出现<br/>质量 vs 进度"] --> B["判真伪<br/>假冲突 → 改计划"]
    B --> C["调整需求集合<br/>正式变更 · 降非关键"]
    C --> D["保度量 · 交付<br/>验证确认可缩不可砍"]
```

1. **判真伪**：一半以上的"质量进度冲突"是估算失真、计划虚报、范围蔓延造成的假冲突——进度算错了，却怪质量太慢。假冲突，改计划，不动质量。
2. **用需求谈判，不用质量谈判**：调整的是需求集合（哪个需求可降、可删、可延），不是"质量原则"。必须走**正式变更**（ISO 9001:2015 §8.2.4 要求的更改 / §8.3.6 设计更改）：书面、评审、通知利益相关方。**口头"差不多就行"是最危险的变更形式**——需求被悄悄偷换，验证确认全在跟一个没被承认的靶子打。
3. **分清可妥协与不可妥协**：
   - 不可动：必须履行的需求（安全、法规——3.5.1"必须履行"一类）、关键特性（8.3.5 d 对预期目的至关重要的）；
   - 可动：非关键特性、性能裕量、**过度设计**——特性超出需求范围不增加质量，只增加成本。**砍过度设计，是唯一"既省时间又不伤质量"的操作**（不是牺牲质量，是给质量做减法）。
4. **度量环节可缩不可砍**：最蠢的赶进度方式是"先交付，验证确认后补"。验证/确认是质量的度量——砍掉等于不度量就宣布合格，风险全部后移成现场返工（失败成本是质量成本里最贵的）。正确姿势：**把验证范围缩到关键特性，而不是把验证整个砍掉**——只验关键的，别全验；但不验，不行。

### 8.3 三大禁忌

1. 砍验证/确认赶进度——最贵，风险后移，返工爆炸；
2. 口头改需求——最危险，需求被偷换，整个定义链失效；
3. 把"降需求"说成"降质量"——概念错。等级（3.5.4）≠ 质量（3.5.2）：降低需求水平（砍非关键）是合法变更；交付不满足已承诺需求的东西，才是真降质量。

### 8.4 正道：与利益相关方一起剪裁需求

> **单方面砍需求叫偷换，和顾客一起剪裁才叫变更——中间差着整个需求的所有权。**

```mermaid
flowchart LR
    A["需求集合（原始）<br/>明示 · 隐含 · 必须履行"] --> B["共同剪裁<br/>利益相关方参与 · 排序定夺"]
    B --> C["新需求基线<br/>剪裁留痕 · 验证参照更新"]
```

**为什么"一起"是硬要求**：

1. **需求的所有权在利益相关方手里**。需求（3.5.1）是"需要或期望"的表述——是利益相关方（尤其顾客）的资产，组织只是受托转化。单方面剪裁 = 拿别人的东西替别人做主：剪掉的那块可能恰是顾客最在乎的隐含需求——他没说，但你剪了，事后必炸。
2. **剪裁改变的是验证的靶子**。验证（3.11.12）对照"规定需求"——需求一剪，靶子就变了。不跟利益相关方一起剪，验证就是在打一个自己偷偷移动的靶子。
3. **剪裁的正确动作是"排序"，不是"删减"**。让利益相关方排优先级：命根子（不可动）、想要的（可降）、贪多的（可剪）。
4. **剪裁要留痕，剪下来的部分要存档**。走 ISO 9001:2015 §8.2.4 / §8.3.6 正式变更：剪了什么、为什么剪、谁决定的、哪天恢复——全部记录。剪掉的需求不是消失了，是**挂账**：本轮进度解了，下一轮迭代（持续改进、改型）时就是现成输入。**剪裁是暂存，不是销毁。**

**隐藏收益**：

> **当顾客被迫说"先保这个、砍那个"的时候，隐藏的需求和真实的优先级才第一次浮出水面。** 平时问"你还有什么要求"他答不出，但你说"进度不够，必须砍一样，砍哪个？"——他立刻知道答案。**进度冲突是隐含需求的显影剂。**

## 9. 三概念基座三角

### 9.1 三角关系

**需求、设计与开发、质量构成产品开发领域工作原理和方法的基座**——三者不是并列的三个概念，而是**互相咬合的三角**，每个定义里都引用另两个：

```mermaid
flowchart LR
    subgraph 基座三角
        A["需求 3.5.1<br/>输入 · 标尺"]
        B["设计与开发 3.3.11<br/>转化 · 特性化"]
        C["质量 3.5.2<br/>判据 · 度量"]
    end
    A -->|转化| B
    B -->|规定特性 · 验证参照| C
    C -->|满足 · 标尺| A
```

- **需求 = 输入**：定义"要什么"（标尺）；
- **设计与开发 = 转化**：把需求变成特性化的规定需求（制造标尺）；
- **质量 = 判据**：度量特性满足需求的程度（读标尺）。

一个产品开发流程，无非是"定标尺 → 造标尺 → 读标尺"。

### 9.2 基座的三层证据

1. **定义互相引用——拆不掉**：设计开发（3.3.11）引用需求（3.5.1）；质量（3.5.2）引用需求和特性（3.10.1）；设计开发注1说需求"以特性来规定"。抽掉任何一个，另外两个悬空。**自洽且不可拆。**
2. **角色不可替代**：需求管输入、设计开发管转化、质量管判据——原理层讲完了。
3. **能推出现有的全部方法——基座的终极检验**：
   - 需求管理、需求评审、变更控制（8.2）← 从"需求"推出；
   - 设计输入/输出、评审/验证/确认（8.3）← 从"设计开发 + 质量判据"推出；
   - 质量控制、质量策划、质量改进（3.2 系列）← 从"质量"推出。

### 9.3 两个精确化

1. **三角里还嵌着两个承重构件：客体（3.5.3）和特性（3.10.1）**。没有客体，质量定义（"客体的固有特性"）和设计开发定义（"对客体的需求"）无处安放；没有特性，需求落不到客体上，质量也无从度量。它们是三角内部的横梁。
2. **三个概念的层级不完全平级**：需求和质量是"元概念"（横跨一切领域，不只是产品开发）；设计开发是"领域机制"（需求和质量在产品开发场景里的中介桥梁）。**基座的最底层是"需求 + 质量"两个元概念，设计开发是架在它们之间的桥——桥是承重的，但地基是那两个元概念。**

### 9.4 工程方法论从基座长出

系统工程、软件工程、硬件工程、IPD、过程方法等，都是在这个基座上长出来的——但需要分类：

| 类别 | 方法论 | 与三角的关系 |
|---|---|---|
| 直接展开 | 系统工程（V模型）、软件工程、硬件工程、DFSS | 三角的工程化形态 |
| 流程框架 | IPD | 三角的流程化、组织化形态 |
| 运行容器 | 过程方法 | 三角的运行骨架（设计开发本身就是一组过程） |
| 扩展学科 | 可靠性工程、安全性工程 | 质量里"随时间/失效"的专门化 |

**逐个检验**：

- **系统工程（SE）**——三角最直接的"长子"：V模型左半边（需求→系统设计→详细设计）是需求逐级转化，右半边（部件验证→系统验证→确认）是质量判据逐级回收。**V 的左右两边就是设计开发和验证确认的镜像**。为什么 V 是 V？因为需求从哪一级分解下去，验证就必须从哪一级收回来。
- **软件工程 / 硬件工程**——三角 + 各自技术本体：需求工程、架构设计、测试（V&V）、需求追溯矩阵是三角直接展开；算法、物理、材料是**另一支根**。
- **IPD**——三角的生存周期展开：需求管理（OR/$APPEALS）→ 概念/计划/开发（设计开发）→ 验证/发布（质量判据）→ 生命周期〔按：末项「生命周期」是 IPD 阶段专名，保留〕。IPD 的技术评审点（TR）/决策评审点（DCP）为什么必须设？因为**质量判据不能等到最后才看，要在每个关口用"特性满足需求的程度"检查一遍**——TR 就是质量判据关口化的产物。
- **过程方法**——设计开发本身就是"一组过程"（3.3.11）；需求是过程输入，质量判据是过程输出要求。过程方法给三角装骨架系统。

**精确化（刹车）**：对管理/质量侧成立，对技术本体不成立：

> **工程 = 概念基座（需求-设计开发-质量，管"要什么、怎么证明做对"）× 技术本体（物理、材料、算法、化学，管"怎么做"）。**
> 三角长不出牛顿定律，也长不出快速排序——它长出的，是**如何组织"做什么"和"如何证明做对了"**的全部方法。

**终极检验——能不能解释"为什么长这样"**：

- V模型为什么是 V？→ 需求分解层级必须与验证回收层级对齐；
- IPD 为什么有 TR/DCP？→ 质量判据必须关口化，不能等最后；
- 为什么需求要追溯矩阵？→ 需求是质量标尺，标尺断了，度量就无据；
- 为什么变更要控制？→ 改需求就是改标尺，不改参照，验证就是打移动靶。

**每一个"为什么"都能从三角推出来——这就是"基座"和"几个相关概念"的区别。**

### 9.5 方法论光谱：管理侧 vs 技术本体

```mermaid
flowchart LR
    A["纯管理侧<br/>需求工程 · V模型 · IPD · 过程方法"] --- B["杂交种<br/>FMEA · 可靠性 · DFX · MBD"] --- C["纯技术本体<br/>TRIZ · 建模与仿真 · 算法 · 工艺"]
```

**技术本体不是一个方法论，是一整个知识家族**，分三层：

1. **知识本体（不是方法论）**：物理、化学、数学、材料科学——不提供"方法"，提供**规律**；
2. **方法层（纯技术方法论）**：建模与仿真（FEA/CFD）、TRIZ（发明问题解决）、算法与数据结构/设计模式、工艺方法、控制理论——共同特征：**换一个行业，这套方法要换**（方法跟着客体走，不跟着需求走）；
3. **杂交种**：FMEA（质量侧发问 × 技术侧作答）、可靠性工程（质量 × 失效率模型）、DFX（技术侧约束反向改进设计）、MBD/数字孪生（技术侧建模，服务验证）。

**一条判别标准，把任何方法论归位**：

> **看问题的主语是谁：**
> - 主语是"做不做得出、怎么做" → **技术本体**（跟着客体走）
> - 主语是"做没做对、值不值得、怎么保证" → **管理侧**（跟着需求/质量走）
> - 两者都在 → **杂交种**

真正的产品开发方法论，几乎都是两者站在光谱两端的杂交产物——**越靠中间，越值钱。**

## 10. 全篇核心结论速览

1. **设计与开发（3.3.11）** = 将客体的需求转换为更详细的需求的一组过程——本质是"需求的转化"，判定标准是"更详细"。
2. **起点** = 满足"可转化"判据的需求规格被确立为设计输入（8.3.3：完整、无歧义、不冲突、隐含需求已识别）。
3. **终点** = 止于"可实现"——实物产品具体化为技术、采购、制造、测试、交付、部署、操作、运维**八个方案全部完成**。终点由最后一个配齐的方案决定，不由第一个完成的技术方案决定。
4. **验证（3.11.12）/ 确认（3.11.14）** = 设计开发的看门人，判定对象是**已可使用的客体**（尺子：规定需求 / **为预期用途或应用的需求**），发生在终点之后——"可验证"因验证定义以设计输出为前提而不能作终点。
5. **质量（3.5.2）** = 客体固有特性满足需求的程度——是"吻合度"不是"除法"，标准给不了单点分值，组织可自定义但需满足：需求完整、特性完整、证据可靠、关键特性优先。
6. **设计开发 = 质量的定义者；验证/确认 = 质量的度量者**。"程度"由确定（3.11.1）→ 符合性比对（3.5.9，接收准则）→ 认定，三步得出。
7. **质量与进度冲突** = 需求集合内部打架（进度本身也是需求）——解法：判真伪、正式变更调整需求、砍过度设计、验证确认可缩不可砍；**正道是与利益相关方一起剪裁需求**（排序、留痕、挂账；进度冲突是隐含需求的显影剂）。
8. **基座三角** = 需求（输入·标尺）、设计开发（转化·造标尺）、质量（判据·读标尺）——定义互相引用、角色不可替代、能推出全部领域方法。承重构件：客体与特性；底层元概念：需求与质量。
9. **工程 = 概念基座 × 技术本体**——管理/质量侧方法论从三角长出，技术侧（物理、材料、算法、工艺）是另一支根；判别标准看问题主语。
10. **设计开发的内部机制 = 分解 + 分配 + 分析（需求"怎么变详细"）**：分解把框架需求拆成叶子、分配把叶子 1:1 搬到下一级枝梢、分析检查承接；解耦 = 切法（内容规则）业务化 × 判据（形式判据）统一 × 契约共享（候选声明 + 骨架先行）；L1 切法指南是退回闭环沉淀出的项目记忆，越用越准。（三动作是六步的内芯——展开与验证操作；完整流程见 #11）
11. **设计与开发的落地 = 需求 × 方案的结对设计六步（§6.5）**：拆需求 → 验分解 → 出方案 → 对需求 → 做裁决 → 签定稿（口诀：拆·验·想·对·裁·签）。②可行性分析三把尺子（可转化 / 可分配 / 边界不越位）；④候选声明"只挂不细"为权衡供证据；⑥评审对质 + 利益相关方确认后才冻结基线；派生需求必须回流需求侧双向对账。六步在"需求 → 方案框架"层级完整落地，向下逐层递归（方案框架 → 方案详细）。六步 = 三动作的扩展：分解长成拆与验、分配长成想与对、分析长成裁与签（③构思 = 分配缺的目标树）。
