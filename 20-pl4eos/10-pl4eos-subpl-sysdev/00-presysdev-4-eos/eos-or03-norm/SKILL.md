## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step 1：读表 B `已澄清`+`同意规范化` 选入文档，分味认支、长三棵树、定五个属性、并入已有树、做规范化检查与冲突检测、优先级初判 | 文本化/切分/澄清 → or00~or02 |
| Step 2：对话确认规范方案与五属性，要素机械检查后写回 01 与表 B | 规范化的相关方需求→业务流程/系统需求 分解分配 → 职责视角业务流程任务等 |
| Step 3：核对 01 三支、并入残留问题，判 `已规范化`／`规范化方案待确认` | 业务框架/业务方案/系统需求框架/产品框架 下游设计决策 |
| 生成 `@spr-` 条目 + 三支子索引 + `0.4 全景层条目行表` | 对冲突需求作裁决；对条目作设计决策 |
| 维护五属性、三支子索引、全景层条目行表；Step End 提交基线 | 写回资产文档（本步只以产品数据为据，不引、不写资产文档） |

**核心原则**：AI 只做分味认支与长树、结构化呈现冲突，不做冲突裁决、不做设计决策；**反馈走对话单轨**——AI 出方案后不结束对话，人类自然语言反馈、AI 即时确认写回；方案未确认的留在状态值上，由下一轮接着谈。人类不再编辑文档表达反馈。

### 三支与条目（分味认支——读文档的味，走对应的一支）

| 支 | 文档的味 | 树的各级（① → ② → ③） | 一条 ③（＝条目 `@spr-{seq}`） |
|----|---------|------------------------|------------------------------|
| 功能 | 业务需求文档（键＝文档级任务） | 文档级任务 → 任务节点 → 用例场景 | 一个提出者名下可独立确认的一条诉求 |
| 非功能 | 非功能需求文档（键＝适用对象＋主题） | 一级类目 → 分类维度 → 具体需求 | 一条可独立确认的非业务诉求 |
| 引擎 | 引擎需求文档（键＝可运行的能力） | 引擎级E2E业务 → 配置单元业务 → 配置信息组业务 | 一项可运行的能力诉求 |

> 文档级任务（PL5）对应引擎侧的配置信息组（PL5）——两支同为"可独立交付的末级单元"。业务需求支的 ① 带五个属性：所属业务域 × 所属主责角色 × 所属岗位级E2E业务 × 所属产品级E2E业务 × 所属构件级E2E业务，**AI 出方案、人类确认**。

## 二、操作流程

### Step Start · 为任务选择并校验需求文档

**一句话**：给出候选清单、过受理门槛、按状态路由，加载本次这一篇，就绪才进入 Step 1。

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 存在；校验表 B 表头与字段说明，不符时按既有口径修正或提示
2. `10-raw-files/` 中存在 `.chunk-*.md`，且存在 `status=clarified` 的需求文档
3. 确认处于 git 仓库且 AI 基线可用：`.scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
4. 给出**候选清单**：每份待处理需求文档一行（源文件名、子文件名、表 B 生命周期、AI建议）。人类选定其中一份；**本次运行只处理这一篇**
5. **按状态路由**（读表 B 该行的生命周期与人类决策）：`已澄清`+`同意规范化` → Step 1 生成方案；`规范化方案待确认` → 按重进入规则续做；`需退回澄清` → 按重进入规则反向路由；`已终止` → Step 1 给「置已废弃」方案；更后状态或人类决策为空 → 不进本轮，列入行动清单
6. **受理门槛**（表5-2）逐条校验；软提示项交人类定夺；缺什么补什么
7. **加载本次这一篇**（加载经济原则：只读本次这一篇、按需扩大，不默认全载全文）：正文区全文；frontmatter 的 `kind`、`label`、属性（所属业务域／文档级任务／适用对象／`topic`／能力诉求）；表 B 对应行；01 三支的现有节点与索引（定位并入基准）
8. 就绪 → Step 1；无待处理对象 → Step End

### Step 1 · 生成规范方案

**一句话**：读本篇的味走对应的一支，长成本支三级、并入已有树、做检查，出方案块（含五属性候选）。

1. **分味认支**：读 `kind`——业务需求文档走业务需求支、非功能需求文档走非业务需求支、引擎需求文档走引擎支
2. **长树**（按 SKILL 指南 §四 4.2／4.3／4.4；判据见附录 A.1）：
   - 业务需求支：立 **① 文档级任务**（取文档的键）→ 定**五个属性**（附录 A.2）→ 按「提出者／角色的一步」立 **② 任务节点** → 按「提出者 × 单一可确认性」拆 **③ 用例场景**
   - 非业务需求支：把文档主题落成 **② 分类维度** → 归 **① 一级类目** → 按单一可确认性拆 **③ 具体需求**
   - 引擎支：按「一项可运行的能力」拆 **③ 配置信息组业务**（锚到引擎）→ 归 **② 配置单元业务** → 归 **① 引擎级E2E业务**
3. **并入已有树**：逐节点按**落位检测规则**（附录 A.3）判确认／改进／补充／过时
4. **检查**：逐条目做**五项标准**、**冲突检测**、**优先级初判**，残留问题标 `待确认`（附录 A.4）
5. **写方案块**：方案写入 01 本支对应处，供人类阅读与讨论；五属性以候选值标 `[推断]` 一并列出。**本步无人类参与点**，不作状态写入 → Step 2

### Step 2 · 基于对话确认与写回

**一句话**：列出未确认清单，人类对话确认五属性与方案，要素机械检查后写回 01 与表 B。

1. **未确认清单**：把本轮新生成方案与状态为 `规范化方案待确认` 的遗留方案一并列出交人类讨论；五属性、条目、树三级都在此逐条确认
2. **逐条讨论与确认**：修改落在方案上即按讨论结果改；确认的单位是节点，可逐份给、也可一次全部确认；**五属性在此定下**
3. **要素机械检查**：三支各级节点非空；业务需求支 ① 带齐五个属性；条目带需求说明、来源定位与内联稳定标签；`@spr-` 编号跨三支连续无跳号。检查不过的就地补齐，无法补齐的回 Step 1 重排
4. **写回**（表5-3 四种情形）：已确认 → 写入 01 本支、表 B 生命周期写 `规范化方案待确认`（待 Step 3 判过关口）；未确认 → 写入 01、表 B 保持 `规范化方案待确认`；遗留方案按讨论结果推进或不改
5. **写的是 Y**：三支按确认结果落定、条目要素与五属性落定；维护 01 元数据、三支子索引、`0.4 全景层条目行表`
6. **也写的是状态文档表 B**：本篇对应行落定，先写表 B、再据此写 01 管理区
7. 已被下游消费过的条目本次被修订 → 维持原状态、版本递增 → Step 3

### Step 3 · 检查与判定

**一句话**：核对 01 三支与要素，判过没过关口。

1. **同指这一面**：业务需求支 ①②③ 三级与业务输出的对应完整；X 的业务需求文档整段进入功能树，一个不少
2. **要素这一面**：三支各级节点要素齐备；业务需求支 ① 带五个属性；条目有需求说明与来源定位；无隐藏遗漏
3. **判定**：通过 → 表 B 生命周期写 `已规范化`、AI建议写 `已完成`；检出问题 → 保持 `规范化方案待确认`，问题标 `待确认`，交 Step End 汇总
4. 判定所依据的 01 三支读不到时，`处置标记=待处置` 交 Step End 提示，不静默通过 → Step End

### Step End · 给出本轮任务成果总结

**一句话**：输出三区摘要、更新基线记录、提交本轮变更，结束。

**三区输出**：

```text
当前状态：<已规范化 / 规范化方案待确认 / 待处置 / 已废弃 / 无待处理对象>
  本轮规范化：<子文件名 → 生成 spr-XXX~spr-YYY（功能 N / 非功能 K / 引擎 M）>
  本轮五属性：<子文件名 → 已确认 N 条 / 待确认 K 条>
  本轮待确认：<子文件名 + 条数；无则写「无」>
  判定结论：<通过 / 检出待确认 N 处>

一、未确认的方案
  <子文件名 + 状态；无则写「无」，下一轮运行接着讨论>

二、待反馈（对话 / 线下均可）
  A. 对话反馈 → 运行本步时直接说同意 / 修改 / 废弃 / 退回澄清，AI 即时处理（Step 2）
  B. 线下反馈 → 对 `已澄清` 文档设 人类决策=同意规范化（表 B）

三、下一步
  本任务 → 选定新一批待处理需求文档重新运行
  下游   → 职责视角业务流程任务（取功能树 ①②③）
           引擎能力设计任务（取引擎树的配置信息组条目）
           非功能需求设计任务（取非功能树的具体需求条目）
```

**收尾**——更新状态文档的基线记录、提交本轮变更（`.scripts/ai-commit.sh`）。**结束**。

## 三、AI 标记约定

**`[推断]` 标注**：五属性候选、落位判定、条目靠上下文推定的部分，全量标 `[推断]`，交人类确认或下游重判。

**`[需裁决]` 标注**：五属性或落位判不出的项，标 `[需裁决]` 交人类。

**`[待复核]` / `[待处置]`**：`[待复核]` 标候选清单中归上存疑的行；`[待处置]` 标记查检出的问题。

**确认状态**：条目 `确认状态` 字段在人类确认后追加 `[同意]`。

**对话单轨纪律**：AI 出方案后不结束对话；人类自然语言反馈、AI 即时处理；未确认的留状态值，下一轮接着谈。人类不再编辑文档表达反馈。

## 附录A：判据速查

### A.1 三支转换（长树规则）

| 支 | ① | ② | ③（条目） |
|----|----|----|-----------|
| 功能 | **一个键**长出一个 ①（同键的篇并作一个），取文档的键 | **每个角色的工作看做一个步骤，一个步骤就是一个任务节点**；任务类型读正文（明示照判／给管理模式按模式／皆无按语义推断） | **提出者 × 单一可确认性**：一个提出者名下可独立确认的一条诉求成一个 ③，取正文原文 |
| 非功能 | ② 归入一级类目（质量特性／环境适应性／可实现性） | 取文档主题（`topic`），对齐分类维度取值 | **单一可确认性**：一条可独立确认的非业务诉求成一个 ③（三元组原子），只判维度不量化 |
| 引擎 | 按主能力域归入具体引擎 | 「可运行能力」归配置单元，边界以引擎现行定义为准 | **一项"可以运行的能力"**成一个 ③（配置信息组判据）；不预先命名编号、不分配配置单元 |

共同停止判据：**单一可确认性**——每条 ③ 可被相关方独立确认，不可则继续拆分或标待确认。**拆分纪律**：不做合并 / 保留原始出处 / 无法拆分标待确认（原文缺事实退回澄清任务）。

### A.2 五属性（业务需求支 ①）

**AI 出方案、人类确认**；不占树位、随节点携带，是 R／P 两树的坐标。

| 属性 | 取向 |
|------|------|
| 所属业务域 | 取文档的所属业务域 |
| 所属主责角色 | 该文档业务对象生命周期的主推动者；AI 据正文提出者推断 |
| 所属岗位级E2E业务 | 该主责角色的一个业务对象闭环；AI 据业务对象推断 |
| 所属产品级E2E业务 | P 树坐标；AI 据业务域与产品类型推断 |
| 所属构件级E2E业务 | P 树坐标，是其所属产品级E2E业务的子节点 |

### A.3 落位检测

| 关系 | 判定 | 处置 |
|------|------|------|
| 确认 | 节点已存在，本轮条目语义已被现有节点覆盖 | 追加承接条目引用，节点定义不动 |
| 改进 | 节点已存在，本轮条目扩展了它的边界 | 更新节点要素，不新建 |
| 补充 | 节点不在树上 | 新建节点，并整理其下的下级节点与条目 |
| 过时 | 树上已有节点本轮无条目覆盖，且并入后不再落入范围 | 标 `[需裁决]` 交人类——移除是架构决策，本任务不自行删 |

### A.4 检查与冲突检测

**五项标准**：完整性、主体明确、客体可识别、边界可判定、可测试性。按类型解读：非业务需求支的边界可判定 = 数值+单位+条件齐备（缺则标 `待确认`，本步不量化）、可测试性 = 目标值可验证（目标值由相关方经澄清确认；统计口径/测量方法/验收条件由非功能需求设计任务执行）。

**残留问题标 `待确认` 分两类**：条目不完整 → 本任务自解不回退；原文缺事实 → 标 `待确认（需退回澄清）`，人类设表 B `人类决策=需退回澄清` 后走反向路由（表 B 生命周期转 `澄清中`、frontmatter.status 转 `raw`、清理 01 对应节点，仅方案期）。

**冲突检测范围**（只结构化呈现，不做裁决）：层 A 同一切分内条目间 / 层 B 同原始文件跨切分条目间 / 层 C 与 01 既有条目的跨文件冲突。**冲突类型**：直接冲突（无法同时满足→`需确认`）/ 间接冲突（各自可行但行为不一致→`需调整`）/ 部分内容冲突（局部冲突→优先拆分）。

**优先级初判**：P0（合规/安全强制或系统基础能力被广泛依赖）/ P1（核心闭环必要、可分期）/ P2（常规增强）/ P3（可延后待定）；只用于分批排序与提示，不作交付承诺。

### A.5 表 B 取值

| 表 | 字段 | 取值 |
|----|------|------|
| 表 B | 生命周期 | 已澄清 → 规范化方案待确认 → 已规范化 → 已废弃（可反向退回 `澄清中`） |
| 表 B | AI建议 | 可以规范化 / 建议执行 / 已完成 / 建议终止（本步生命周期段取值；全集见状态文档表B） |
| 表 B | 人类决策 | 同意规范化 / 需退回澄清 / 空 / 已终止 |

条目状态（`待处理` 起）与三支子索引落 01 自身管理区，不另设状态表。

## 附录B：版本感知与写回

### B.1 写回前冲突检查

表 B 是人类与 AI 共同维护的表，01 由下游消费。AI 写回前：

1. **快照**——读取待更新行（表 B 生命周期）的当前值
2. **复核**——写回前重新读取；若与快照不符（人类在本次运行期间手工修改），标记 `[需确认]`，不覆盖，在 Step End 提示人类
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：AI 绝不覆盖非空的人类决策

### B.2 写回顺序（同步契约）

1. **先更新表 B**（权威源）
2. **再从表 B 推导**写入 01 管理区与三支子索引
3. 同步维护 01 元数据、三支子索引、`0.4 全景层条目行表`、域节点数

## 四、重进入规则

| 场景 | 处理 |
|------|------|
| 规范续做 | 表 B `生命周期=规范化方案待确认` → Step 1 续做、Step 2 续确认 |
| 反向路由（退回澄清） | `规范化方案待确认` 且 `人类决策=需退回澄清` → 表 B 生命周期→`澄清中`、AI建议→`需继续澄清`、frontmatter.status→`raw`；清理 01 对应节点；澄清任务重新标注（仅方案期） |

| 已规范化变更检测 | 表 B `生命周期=已规范化`：有方案改动 → 走变更路径（不走退回）；改动的条目为下游所消费 → 维持原状态、版本递增 |
