# eos-or01-chunk · 文本化的原始需求 → 需求文档（功能／非功能／引擎） · 按需求落点切分

> **设计依据**：[eos-or01-chunk.md](../eos-or01-chunk.md)（SKILL 指南——权威源）。本文档中「SKILL 指南」一律指此文件（`20-pl4eos/10-pl4eos-subpl-sysdev/00-presysdev-4-eos/eos-or01-chunk.md`）。
> **领域规范**：[91-eos-biz-eng-spec.md](../../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（业务对象与业务场景概念 §1.4、Step Start 入口条件、反馈交互、Step End 三区输出与变更传播通用协议）。
> **规则归属**：本文档只承载 AI 运行时执行指令（加载/写回/标注/速查）；所有设计规则、模板与字段定义以 SKILL 指南为准，命中规则冲突时以 SKILL 指南为准。

## 一、职责定位

### 1.1 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step Start：前置校验、给出候选清单交人类选定本批材料、按状态路由 | 原始材料文本化 → `eos-or00-textualize` |
| Step 1：分需求与指标、按文档级任务归业务需求、按适用对象与主题归非功能需求、按可运行的能力归引擎需求、划边界，出切分方案 | 模糊需求澄清 → `eos-or02-clarify` |
| Step 2：对话确认后逐篇输出 `.chunk-{seq}.md` 并写回状态文档表 A／表 B | 规范化的相关方需求条目规范化/分类/编号 → `eos-or03-norm` |
| Step 3：复核覆盖、归属与要素，检出待处置项 | 修改原文语义、补充需求内容、评价需求 |
| Step 4：对话裁决待处置项并写回 | 业务需求/引擎能力业务需求/非功能需求分配 → wft01 系列 |
| Step End：汇总本轮写回结果、三区摘要输出 | — |

**核心原则**：AI 在本步是"划断者"而非"理解者"——只按需求落点划出行文边界、定片名，不改一字、不补一字、不评一句；**方案由 AI 给、结论由人类在对话里下**，判不定的适用对象与主题由 AI 给候选、人类在对话中定，未确认的方案留在 `切分方案待确认`，由下一轮接着讨论。

### 1.2 上下游衔接

| 方向 | 对象 | 交接内容 |
|------|------|---------|
| 上游 | `eos-or00-textualize` | 正文区为纯原文的文本化文档；表 A 上 `人类决策=同意切分` 的材料是它的入口 |
| 下游 | `eos-or02-clarify` | 表 B `生命周期=已切分` + `AI建议=可以澄清` 的需求文档 → 设 `人类决策=同意澄清` 后进入 |
| 回向 | 人类 | 收本任务检出的缺陷材料——正文区带下游产物、损坏、读不了——修好或换掉源文件后重跑本步 |

## 二、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 为任务选择并校验材料 | 前置校验、给出候选清单、受理门槛、按状态路由 | **有**——从候选清单中选定 | 对话 | 受理结论 + 候选清单 | 状态文档（首次） |
| 1 | 基于材料生成切分方案 | 分需求与指标、归业务需求、归非功能需求、归引擎需求、划边界，出方案 | 无（AI 自动） | 统一 | 切分方案 | — |
| 2 | 基于对话确认切分方案 | 列出未确认清单、讨论修改；要素机械检查后写回成篇 | **有**——讨论与确认 | 对话 | 确认结论 + 未确认清单 | 状态文档、需求文档 |
| 3 | 检查并检出待处置项 | 复核覆盖、归属与要素，检出待处置项 | 无（AI 自动） | 统一 | 检查结论 + 待处置项 | 状态文档 |

| End | 给出本轮任务成果总结 | 汇总本轮写回结果、三区摘要输出 | **有**——查看结果摘要 | 对话 | 本轮成果总结 + 下一步 | — |

### Step Start · 为任务选择并校验材料

1. 检查 `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/` 存在；不存在则创建
2. 检查 `10-raw-files/` 存在；不存在则创建
3. 检查 `01-eos-sysdev-status.md` 存在；不存在则提示先运行 `eos-or00-textualize` 并结束
4. 状态文档已存在的，校验表 A／表 B 的表头与字段说明；不一致时按 §四 的字段表对齐
5. 确认处于 git 仓库且 AI 基线可用：`.scripts/ai-commit.sh` 存在；基线 = 状态文档的基线记录字段，或最近一次 AI 提交
6. `10-raw-files/` 中存在 `.textualized.md` 文档；不存在则提示先运行 `eos-or00-textualize` 并结束
7. 用 `ls 10-raw-files/` 与状态文档表 A 生成**候选清单**：每份待处理材料占一行，列出源文件名、生命周期、AI建议，人类选定本批处理的一份或多份
8. **按状态路由**（见 §4.7）——本任务自己的入口是 `人类决策=同意切分` 且生命周期 `已文本化`；`人类决策=已终止` 的进本批交 Step 1 给「置 `已废弃`」方案；生命周期为空且源文件仍在的进本批（走重进入）；`暂不切分` 或空的不进本批
9. **受理门槛**（见 §4.1）——逐文件判；不合的回退或跳过
10. 无待处理材料且无入口检出的存量 → 输出「无待处理对象」→ 退出；否则进入 Step 1

**加载经济原则**：用 `ls`/glob 扫描 `10-raw-files/` 与状态文档表 A／表 B 区域，不 Read 整个状态文档；切分分析时仅读取目标文本化文档的**正文区**（管理区不参与语义分析）。

### Step 1 · 基于材料生成切分方案

存量节点先于新输入处理。对每一份材料依次走 SKILL 指南第四章的五步：

1. **分需求与指标**——通读正文区每一句，按 §4.2 句类分流归入业务诉求／非业务诉求／引擎诉求／性能指标／非需求五类之一；「性能指标」指得出在给哪条需求打分，随那条需求走，不单独成篇
2. **归业务需求**——按 §4.3 数材料里的文档级任务，一份产物立一篇业务需求文档；该产物上的业务诉求连同它的性能指标一并归入。**不要求闭环**——诉求可以只是某个环节的一段，照样成篇
3. **归非功能需求**——按 §4.4 逐条判适用对象（四问，由小到大）与主题，两个键都相同才合一篇
4. **归引擎需求**——按 §4.3 判每条引擎诉求要的那项"可以运行的能力"，同一项能力合一篇引擎需求文档；落在平台侧、不是业务场景里的动作
5. **划边界成文档**——按 §4.5 定每篇的行号范围与片名，行号相对正文区基准（正文区第 1 行 = L1）

五步走完，本批每份材料都有一份切分方案：每一篇的行号范围、片名、键与理由。**方案写入文本化文档正文区原文之后**（模板见 §4.6），供人类阅读与讨论；**方案不作状态写入**，随方案一并交 Step 2。

**失败处置**：文本化文档读不到或正文区为空读不出诉求的，该份材料的 `处置标记` 记 `待处置` 交 Step 2，其余材料照常。

### Step 2 · 基于对话确认切分方案

1. 列出**未确认清单**——本轮新生成的方案 + 表 A 上状态为 `切分方案待确认` 的遗留方案，逐份给出处置建议，交人类讨论
2. 按讨论结果修改方案；人类确认后该份材料转为已确认。确认的单位是材料，可逐份给也可一次全部确认。**判不定的适用对象与主题在此定下**
3. **写回前的要素机械检查**——逐份检查：每篇行号范围连续、彼此不重叠、合起来覆盖全文；片名非空；键单一。检查不过的就地补齐；无法补齐的回 Step 1 重做
4. **写回**：

| 对象 | 讨论结果 | 写回动作 |
|------|---------|---------|
| 本轮生成或修订的方案 | 已确认 | 逐篇输出 `.chunk-{seq}.md`，写入 frontmatter 与管理区；清理正文区方案块；表 B 每篇追加一行；表 A 生命周期写 `已切分` |
| 本轮生成或修订的方案 | 未确认 | 方案块留在正文区，表 A 生命周期写 `切分方案待确认`，留作下一轮处理对象 |
| 遗留的待确认方案 | 已确认 | 推状态到 `已切分`，按讨论结果出篇 |
| 遗留的待确认方案 | 仍未确认 | 不动 |

5. 已被下游消费过的材料本次被修订的，需求文档已被澄清任务取用的维持原状态、版本递增；已被规范化任务消费的标为待下游重审
6. **写回顺序（同步契约）**：先更新状态文档表 A／表 B（权威源），再据此写需求文档管理区；两者不一致时以状态文档为准重建管理区
7. 写回前执行 §五 冲突检查

### Step 3 · 检查并检出待处置项

检查取三面：

- **覆盖这一面**——每篇取的是连续原文片段；片段之并覆盖全文，一段不漏；各篇行号不重叠
- **归属这一面**——业务需求文档确只装同一份文档级任务上的诉求；非功能需求文档确只装同一适用对象、同一主题上的诉求；引擎需求文档确只装同一项能力上的诉求；片名与它的键相符
- **要素这一面**——frontmatter 齐备、片名非空、管理区四项齐备、正文区只有原文片段

检出问题的在 `处置标记` 列记 `待处置`，按四类锚点归位：

| 类 | 锚在哪 | 例 |
|----|--------|----|
| 覆盖缺口类 | 材料 | 有段落未落进任何一篇；两篇行号相交；片序与材料行文次序不符 |
| 归属存疑类 | 方案块的篇 | 片名与材料自带的标题不符；同一篇里混了两个键；适用对象或主题的判据不足 |
| 键／味存疑类 | 方案块的篇 | 澄清或规范化任务退回的「疑似判错味或键」 |
| 要素缺项类 | 需求文档 | frontmatter 缺项、片名空、管理区不齐、正文区带非原文内容 |

产出检查结论与待处置项清单交 Step 4。本步无人类参与点。所依据的文本化文档读不到时，该份材料的 `处置标记` 记 `待处置` 交 Step 4 讨论，不静默通过。

### Step 4 · 基于对话裁决待处置项

1. 列出**待处置项清单**——每条写明锚在哪份材料或哪一篇上、属于哪一类、缺的是哪一样，交人类讨论
2. 逐条裁决：覆盖缺口类补齐缺口段或改边界；归属存疑类改片名或并入相邻的那一篇；键／味存疑类**清空表 A 生命周期值后重切**（味与键在本任务定，下游改不了）；要素缺项类就地补齐或回 Step 1 重做。结构性改动触及覆盖面的，材料留待下一轮重切
3. **复跑检查**——每执行一处修改即复跑 Step 3 的检查，范围限被改动的材料；改动触及需求文档篇数的，按 91 §A.5.3 的级联处理 `处置标记=待处置` 回 Step 1 重走。同一处反复退改超过一次的，停止处理，`处置标记=待处置` 留待下一轮
4. **写回**——判「补齐」的就地补段或改边界并重出受影响的篇；判「重切」的清空表 A 生命周期值后按 §六 重进入；判「终止」的清方案块、需求文档与表 B 记录置 `已废弃`。裁决完成的行清掉 `处置标记`。改动使某篇管理区变更的，一并写回

### Step End · 给出本轮任务成果总结

输出三区摘要（本次运行报告 + 下一步交接），结束：

```text
当前状态：<已切分 / 切分方案待确认 / 待处置 / 待人工处置 / 已废弃 / 无待处理对象>
  本轮已成篇：<N 篇，逐篇列「片名（功能／非功能）」>
  本轮待确认：<N 份，逐份列源文件名>
  本轮待人工处置：<N 份，逐份列「源文件名 → 缺陷与原因」>
  检查结论：<通过 / 检出待处置项 N 处，已裁决 M 处>

一、未确认的方案
  <本轮未确认 N 份：源文件名 + 状态；无则写「无」，下一轮运行接着讨论>

二、下一步
  本任务 → 选定新一批待处理材料重新运行
  下游    → 澄清任务（取本轮交出的需求文档）
```

收尾：更新状态文档的基线记录，提交本轮变更（`.scripts/ai-commit.sh`，author=EOS-AI + `[AI]` 前缀）。工作区无改动时跳过提交。

## 三、AI 标记约定

**增量与状态标记**：`[新增]`／`[变更]`／`[确认]`／`[需裁决]` 按 91 §A.3.1 执行。本任务另用三枚：`[待复核]` 标候选清单中归上存疑的行；`[待处置]` 标检查检出的问题；`[推断]` 标切分方案中由 AI 推定而未获确认的键。增量清单在 Step End 输出，不写入资产文档。

> 本任务**不写**任何确认标记到文本化文档或需求文档——人类不编辑文档表达反馈，结论一律在对话里下。

## 四、判据速查

### 4.1 受理门槛（Step Start 过滤）

| 跳过原因 | 判定条件 | 判定 |
|---------|---------|------|
| 不是文本化文档 | 文件名不以 `.textualized.md` 结尾 | 不可处理 → 输出提示、跳过 |
| 走错路径 | 文件名含 `.chunk-` | 路由错误 → 跳过，提示走澄清任务 |
| 上游未交干净 | 正文区带方案块或分析建议块 | 退回上游 → 交回文本化任务重做 |
| 已在处理流程中 | 表 A 该行生命周期为 `已文本化` 或更后 | 不可处理 → 跳过（重做须先清空该行生命周期值） |
| 已废弃 | 表 A 该行生命周期为 `已废弃` | 不可处理 → 跳过（重启须先清空该行生命周期值） |
| 不可读 | 源文件损坏或读不了 | 不可处理 → 登记失败、`处置标记=待人工处置`，不进本批 |
| 一次选定多份 | 本批跨了多份材料 | 软提示 → 逐份分别处理，不合并 |

### 4.2 句类分流（分需求与指标）

| 这一句说的是 | 判为 | 去向 |
|------------|------|------|
| 要能做什么——某个业务动作、某份产物上的操作 | **业务诉求** | 随它那张文档级任务 |
| 必须达到什么状态或程度，且指得出在给哪条需求打分 | **性能指标** | 随那条需求，不单独成篇 |
| 必须达到什么状态或程度，指不出在给哪条需求打分 | **非业务诉求** | 按适用对象与主题归并 |
| 要平台提供/扩展某项引擎能力或页面机制——配置引擎、配置页面、流程规则、构件与布局组件能力等 | **引擎诉求** | 随它要的那项能力 |
| 既无诉求也不含量化，是背景交代、术语定义、现状描述 | 非需求 | 留在原文里，随它所在的片段 |

> **性能指标不是非功能需求**——它是需求的部件。判「是不是指标」只问一句：它指得出在给哪条需求打分吗。

### 4.3 落点取值（归业务需求／归引擎需求）

**归业务需求——文档级任务取值**：文档级任务是这一群业务诉求所围绕的那个东西，**由本任务给出建议、人类在 Step 2 确认**，确认下来即为该篇的键与片名。原始需求多半不显式写出产物名，按三档取值：

| 档 | 材料的样子 | 键取什么 | 片名 |
|----|-----------|---------|------|
| 一 | 显式写出产物——单据、台账、清单、报告、记录、表册、图纸 | 那份产物 | 材料里怎么称呼就怎么称呼 |
| 二 | 未写出产物名，但指得出诉求围绕的东西（动作的宾语、被反复操作或产出的那一样） | 那个东西，用材料里的说法 | 那个说法，标 `[推断]` |
| 三 | 指不出——一组诉求横跨几样东西，或纯是接口、技术说明 | 退回材料自身的分组：节标题、编号 | 该组的标题 |

> 同一份产物上的多处诉求，**在材料里连续的部分合入同一篇**；被别的键隔开的另成一篇（两篇同键）。不同产物各立一篇。**不要求闭环**——诉求可以只是某个环节的一段。

**归引擎需求——能力取值**：引擎需求文档的键是它要的那项"**可以运行的能力**"，即配置信息组的判据（某组配置字段，共同提供一个可以运行的能力）。同样由本任务给出建议、人类确认，三档取值：显式写出能力或引擎的照用；未写出但指得出诉求围绕的那项能力的，用材料里的说法标 `[推断]`；指不出的退回材料自身的分组。**落在平台侧**——诉求指向平台自己提供/扩展的能力，不是业务场景里的动作（那归业务需求）；存疑的标 `[推断]` 交人类。

### 4.4 适用对象与主题（归非功能需求）

**适用对象四问**，由小到大判，先试最小的：

| 序 | 问 | 落点长什么样 | 归 |
|----|-----|------------|-----|
| 1 | 落点是不是某一份文档级任务，或它名下的业务动作、产物 | 约束里的动作名或产物名，能对上某篇业务需求文档的锚 | 该文档级任务 |
| 2 | 落点是不是某个业务域——域内全部，不指某一个场景 | 范围词：本域、各业务域、域内所有；或域名的出现 | 业务域 |
| 3 | 落点是不是平台的某项能力——与哪个业务域无关，平台自己提供 | 落点说的是平台自身提供的功能（目录管理、版本管理、血缘分析一类），不是某个业务场景里的动作 | 平台能力 |
| 4 | 以上都不缩小 | 落点是"系统""平台"整体，或泛得指不出来 | 全局对象 |

三条纪律：**落点从约束句里读，不从段落倒推**；**判到具体的那一个，不只是判到类**；**判不出的给建议、交人类定**。

**主题判据**（主题即这一篇非功能需求的分类维度，写在 `topic` 与片名上，不另设分类表）：

- 材料自带的节标题是首选（「性能要求」「安全要求」「可用性要求」，节标题即主题）；
- 材料不分节时看句内的质量属性词（性能、安全、可用性、可靠性、易用性、可扩展性、可运维性、合规、数据保留等）；
- 一条横跨两类时按其主取一个主题，在方案里写明取值理由，由人类确认；
- 判不出的给候选，交人类定。

**归并规则**：适用对象、主题两者都相同 → 在材料里连续的部分合入同一篇，被别的键隔开的另成一篇（两篇同键）；任一不同 → 分作两篇；已判为该条需求上的性能指标的随那条需求进同一篇。

### 4.5 边界与命名（划边界成文档）

| 情形 | 处理 |
|------|------|
| 行号边界落在段落中间 | 整段归入起始的那一篇 |
| 连续两篇之间有空白行 | 空白行归入前一篇 |
| 某一处切出来是空的 | 不输出空文件，那一处不成篇 |
| 性能指标句落在两篇之间 | 随它那条需求所在的那一篇 |
| 同一键在材料里被隔开 | 就着材料分成两篇，两篇同键 |
| 全文只有一篇 | 照样成篇，`total` 记 1 |

**片名**：业务需求文档写它那张文档级任务的名；非功能需求文档写「适用对象·主题」，如「全局对象·系统性能」；引擎需求文档写它要的那项能力的名；结构锚点成篇的写它那一节的标题。

### 4.6 切分方案与需求文档模板

**切分方案块**（写入文本化文档正文区原文之后）：

```markdown
╔═ 切分方案 ════════════════════════════════╗
║ 建议：切分为 3 份需求文档                   ║
║                                            ║
║ 001 · 业务需求文档 · 市场活动单             ║
║   行号：L120~L340                          ║
║   键：文档级任务「市场活动单」            ║
║   理由：同属一份文档级任务                ║
║                                            ║
║ 003 · 非功能需求文档 · 全局对象·系统性能    ║
║   行号：L481~L500                          ║
║   键：适用对象「全局对象」｜主题「系统性能」 ║
║   理由：同一适用对象、同一主题              ║
╚═════════════════════════════════════════════╝
```

> 判不定的适用对象或主题，在「键」行写候选，在「理由」行写明缺的是哪样证据，交 Step 2 对话定。

**需求文档**（`.chunk-{seq}.md`）：

```markdown
---
chunk:
  source: {原始文件名}.textualized.md
  original_source: {原始文件名}.{ext}
  seq: {序号}
  total: {总篇数}
  kind: {业务需求文档 | 非功能需求文档 | 引擎需求文档}
  label: {文档级任务名 / 适用对象·主题 / 能力名}
  range: {行号范围}
  # 非功能需求文档另带：applicable: {适用对象} / topic: {主题，即分类维度}
  # 引擎需求文档另带：capability: {能力诉求}
status: raw
---

| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 切分已执行 | 可以澄清 | 无 | 运行 eos-or02-clarify |

（本次切出的原文片段）
```

### 4.7 状态路由（Step Start 分流）

| 表 A 状态 | 走哪条路 |
|-----------|---------|
| `人类决策=同意切分` 且 生命周期 `已文本化` | 进本批，Step 1 生成切分方案 |
| `人类决策=已终止` | 进本批，Step 1 给「置 `已废弃`」方案，Step 2 确认后按 §六 处置 |
| `人类决策=暂不切分` 或空 | 不进本批，列入行动清单 |
| `生命周期` 为空 且 源文件仍在 | 进本批，按 §六 重进入分流 |
| 生命周期 `已切分`（已交出需求文档） | 不进本批，列入行动清单（后续在表 B） |
| 表 B 某片 `处置标记=待退回重切` | 其材料进本批，按 §六 重进入重切（片→材料经表 B `源文件` 列对应到表 A） |

### 4.8 状态文档列与取值（本任务写入的部分）

**表 A（材料级）**：

| 列 | 取值 / 写法 |
|----|------------|
| 内容摘要 | 一句话阶段摘要，如 `已切分 3 篇（见表 B）` |
| 生命周期 | `切分方案待确认` / `已切分` / `已废弃` |
| AI建议 | `审核切分方案` / `可以澄清` / `建议终止` |
| 操作指引 | 人类下一步应执行的操作 |

> `人类决策` 列是人类输入面，本任务只读不写：空（未处理）/ `同意切分` / `暂不切分` / `已终止`。表 A 的完整列定义与其余各表以状态文档自身为准。

**表 B（需求文档级）**：执行切分时为每篇追加一行——`源文件` 填原始文件名、`子文件` 填 `.chunk-{seq}.md`、`生命周期=已切分`、`AI建议=可以澄清`、`内容摘要` 填片名。完整列定义以状态文档自身为准。

## 五、写回与版本感知

### 5.1 写回前冲突检查

状态文档表 A 的人类决策列是人类与 AI 共同维护的面。AI 写回前执行冲突检查，防止覆盖人类手工修改：

1. **快照**——Step Start 记录待处理行的生命周期与人类决策当前值
2. **写回前复核**——写回前重读该行；与快照不符（人类在本次运行期间手工修改）的标 `[需复核]`、不覆盖，在 Step End 向人类提示
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段，AI 绝不覆盖非空的人类决策

### 5.2 写回顺序（同步契约）

1. **先更新状态文档表 A／表 B**（权威源）——表 A 转迁生命周期、更新 AI建议与操作指引；表 B 为每篇追加一行
2. **再据此写**需求文档管理区状态表（阶段/AI建议/待处理/操作指引）
3. 两者不一致时，以状态文档为准重建管理区

## 六、重进入规则

| 场景 | 处理 |
|------|------|
| 新进材料 | 表 A 上无对应行 → 按新材料处理 |
| 重新切分 | 生命周期被清空、源文件仍在 → 先查是否已被下游消费：未消费的清除旧需求文档与表 B 记录后重切；已消费的先输出变更影响声明，把受影响的下游对象标为待重审，再重切 |
| 方案重开 | 生命周期被清空、旧方案块仍留在正文区 → 清除旧方案块，正文区回归纯原文，重走方案 |
| 材料终止 | 人类决策 = `已终止` → 清除方案块使正文区回归纯原文，旧需求文档与表 B 记录置 `已废弃` |

> 重进入按 91 §A.7 变更传播协议处理（详见 SKILL 指南 §4.6）：新增材料不影响既有结果；重新切分若改变切分边界，必须列出受影响的需求文档、规范化的相关方需求与已消费的业务框架，不得静默声明"下游不受影响"。每次重进入以 Step Start 为入口，Step End 提交新基线。
