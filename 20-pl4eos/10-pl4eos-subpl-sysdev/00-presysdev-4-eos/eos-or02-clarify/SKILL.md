# eos-or02-clarify · 切分后的原始需求 → 澄清后的原始需求 · 出题与落答

> **设计依据**：[eos-or02-clarify.md](../eos-or02-clarify.md)（SKILL 指南——权威源）。本文档中「SKILL 指南」一律指此文件（`20-pl4eos/10-pl4eos-subpl-sysdev/00-presysdev-4-eos/eos-or02-clarify.md`）。
> **领域规范**：[91-eos-biz-eng-spec.md](../../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（产品数据文档结构 §11、Step Start 入口条件、反馈交互、Step End 三区输出与变更传播通用协议）。

## 一、职责定位

### 1.1 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step Start：前置校验、给出候选清单交人类选定本次一篇需求文档、受理门槛、按状态路由 | 原始材料文本化 → `eos-or00-textualize` |
| Step 1：通读正文、按两味判据认出说不清与该有却缺处、逐处成问，与既有清单对账 | 语义切分与切分方案执行 → `eos-or01-chunk` |
| Step 2：对话确认问题清单、收相关方答复、按答复写回正文并划去该条、写回 | 规范化的相关方需求条目规范化/分类/编号 → `eos-or03-norm` |
| Step 3：复核写回后的正文、并入新条目、判 `已澄清`／`澄清中` | 代替相关方确认业务事实、发明指标数值 |
| Step End：汇总本轮写回结果、三区摘要输出 | 把澄清内容扩展为设计方案或下游需求分解 |

**核心原则**：AI 在本步是"**出题者**"也是"**誊写着**"——通读正文、把说不清与该有却缺的地方认出来写成一句问题，答复到手再照答复写回；**答复来自相关方，经对话给出**（不在文档里写反馈）。判不定、答复不足的一律留条不落，交下一轮或退相关方。

### 1.2 上下游衔接

| 方向 | 对象 | 交接内容 |
|------|------|---------|
| 上游 | `eos-or01-chunk` | 正文区为纯原文片段的需求文档；表 B 上 `人类决策=同意澄清` 的文档是它的入口 |
| 下游 | `eos-or03-norm` | 表 B `生命周期=已澄清` + `AI建议=可以规范化` 的需求文档 → 设 `人类决策=同意规范化` 后进入 |
| 回向 | 人类 | 缺陷文档——正文区非连续片段、下游产物混入、损坏读不了——**拒绝受理**，`处置标记=待人工处置` 交人类重跑切分任务（切分后与澄清后是同一份产品数据的两个形态，二者之间不设退回） |
| 回向 | `eos-or03-norm` | 收下游退回的、原文层仍缺事实的需求文档，走 §六 反向路由重新出题 |

## 二、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 为任务选择并校验需求文档 | 前置校验、给出候选清单、受理门槛、按状态路由 | **有**——从候选清单中选定一篇 | 对话 | 受理结论 + 候选清单 | 状态文档（首次） |
| 1 | 出题 | 通读正文、认出不清与缺项、逐处成问，与既有清单对账 | 无（AI 自动） | 统一 | 澄清问题清单 | 需求文档 |
| 2 | 基于对话确认与落答 | 列出问题清单、讨论修改；收相关方答复、按答复写回正文并划去该条 | **有**——确认与答复 | 对话 | 确认结论 + 新正文 | 状态文档、需求文档 |
| 3 | 复核与判定 | 重读写回后的正文、并入新条目，判 `已澄清`／`澄清中` | 无（AI 自动） | 统一 | 判定结论 + 新条目 | 状态文档、需求文档 |
| End | 给出本轮任务成果总结 | 汇总本轮写回结果、三区摘要输出 | **有**——查看结果摘要 | 对话 | 本轮成果总结 + 下一步 | — |

### Step Start · 为任务选择并校验需求文档

1. 检查 `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/` 存在；不存在则创建
2. 检查 `10-raw-files/` 存在；不存在则创建
3. 检查 `01-eos-sysdev-status.md` 存在；不存在则提示先运行 `eos-or00-textualize`／`eos-or01-chunk` 并结束
4. 状态文档已存在的，校验表 B 的表头与字段说明；不一致时按 §四 的字段表对齐
5. 确认处于 git 仓库且 AI 基线可用：`.scripts/ai-commit.sh` 存在；基线 = 状态文档的基线记录字段，或最近一次 AI 提交
6. `10-raw-files/` 中存在 `.chunk-*.md` 需求文档；不存在则提示先运行 `eos-or01-chunk` 并结束
7. 用 `ls 10-raw-files/` 与状态文档表 B 生成**候选清单**：每篇待处理需求文档占一行，列出源文件名、子文件名、生命周期、未解决数、AI建议，人类选定其中一篇；**本次运行只处理这一篇**
8. **按状态路由**（见 §4.7）——本任务自己的入口是 `人类决策=同意澄清` 且生命周期 `已切分`；`生命周期=澄清中` 的进本轮续做（走重进入）；`人类决策=需退回澄清` 的进本轮重新出题；`人类决策=已终止` 的进本轮交 Step 1 给「置 `已废弃`」方案；`人类决策` 为空的不进本轮
9. **受理门槛**（见 §4.1）——判；不合的跳过、回退或退回
10. 无待处理需求文档且无入口检出的存量 → 输出「无待处理对象」→ 退出；否则进入 Step 1

**加载经济原则**：用 `ls`/glob 扫描 `10-raw-files/` 与状态文档表 B 区域，不 Read 整个状态文档；只读本次这一篇，出题与落答时仅读取该篇的**正文区与正文之后的澄清问题清单**（管理区不参与语义分析）。出题时遇「引用对象缺失」这一处，按需扩到源材料／同材料的其余片核对定义。

### Step 1 · 出题

存量节点先于新输入处理。对选中的这一篇依次走 SKILL 指南第四章的第一步：

1. **出题**——通读正文区，按 §4.2 两味判据逐处判定：**表述不清**（术语／主体客体／边界／信息）或**要素缺席**（缺少定量指标／分支缺对应面／引用对象缺失）；同一处属两类以上的仍只立一条。把每一处与**既有清单**对账（§4.5）：已在清单的不动、正文里新冒出的追加、清单里已无对应的划去。为每一条生成一句向相关方确认的问题（**问句规则**见 §4.3），非业务诉求的缺项按 §4.4 随带澄清质量属性与适用对象
2. 按 §4.6 **清单格式**把新条目补进正文区之后的清单，状态记 `待问`

清单**不作状态写入**，随它一并交 Step 2。通读后既无新认出、也无既有条目等着的，清单为空，该篇仍进 Step 2 交人类确认。

**失败处置**：正文区读不到或读不出诉求的，该篇 `处置标记=待人工处置` 交 Step 2，其余文档照常。

### Step 2 · 基于对话确认与落答

1. 列出**清单**——本轮新生成的条目 + 上一轮留下的、状态为 `待答` 的条目，逐条给出处置建议，交人类讨论
2. 人确认该不该问、问得对不对；确认即该条状态转 `待答`
3. **收答复与落答**——人类在对话里给出相关方确认的答复，按 §4.5 **落答规则**逐条写回：改该处正文、把该条从清单划去。可分批给、分批落
4. **写回前的要素机械检查**——检查：frontmatter 齐备；管理区四项非空或属合理空置；正文区有内容；清单格式合规。检查不过的就地补齐；无法补齐的 `处置标记=待处置` 留待下一轮
5. **写回**：

| 对象 | 讨论结果 | 写回动作 |
|------|---------|---------|
| 本轮生成的清单 | 已确认 | 条目状态转 `待答`；有答复的按答复写回正文并划去该条；表 B 生命周期写 `澄清中`、AI建议写 `需继续澄清` |
| 本轮生成的清单 | 未确认 | 清单写入正文区之后，表 B 生命周期写 `澄清中`，留作下一轮处理对象 |
| 遗留的清单 | 已确认 | 按答复写回正文、划去已答条目，按讨论结果推进 |
| 遗留的清单 | 仍未确认 | 不动 |

6. 已被下游消费过的文档本次被修订的，正文已被规范化任务取用的维持原状态、版本递增
7. **写回顺序（同步契约）**：先更新状态文档表 B（权威源），再据此写需求文档管理区；两者不一致时以状态文档为准重建管理区
8. 写回前执行 §五 冲突检查

### Step 3 · 复核与判定

检验取两件事：

- **复核这一面**——对写回后的正文**再读一遍**：① 写回波及了清单以外的内容，就地改回；② 因写回而新出现的问题，追加为清单条目，状态记 `待问`
- **判定这一面**——**复核后清单空即判澄清完成**：清掉正文区之后的清单（连同标题行）、`生命周期=已澄清`＋`AI建议=可以规范化`＋`status=clarified`；清单不空则保持 `澄清中`、`AI建议=需继续澄清`，未清部分留待下一轮

判定结论与新并入的条目交 Step End。本步无人类参与点。所依据的正文区读不到时，该篇 `处置标记=待人工处置` 交 Step End 提示，不静默通过。

### Step End · 给出本轮任务成果总结

输出三区摘要（本次运行报告 + 下一步交接），结束：

```text
当前状态：<已澄清 / 澄清中 / 待处置 / 已废弃 / 无待处理对象>
  本轮已澄清：<子文件名 / 无>
  本轮落答：<子文件名 → 划去 M 条；无则写「无」>
  本轮出题：<子文件名 → 新增 M 条，累计 K 条待答复>
  本轮待人工处置：<子文件名 → 缺陷与原因；无则写「无」>
  判定结论：<通过 / 检出待处置 N 处>

一、未确认的清单
  <子文件名 + 待答条数；无则写「无」，下一轮运行接着谈>

二、待答复
  <清单不空的篇：子文件名 + 各条问句；人类持此向相关方问明后，下一轮在对话里给答复>

三、下一步
  本任务 → 选定新一批待处理需求文档重新运行
  下游   → 规范化任务（取本轮交出的需求文档）
```

收尾：更新状态文档的基线记录，提交本轮变更（`.scripts/ai-commit.sh`，author=EOS-AI + `[AI]` 前缀）。工作区无改动时跳过提交。

## 三、AI 标记约定

**增量与状态标记**：`[新增]`／`[变更]`／`[确认]`／`[需裁决]` 与 `[推断]` 按 91 §A.3.1 执行。本任务另用两枚：`[待复核]` 标候选清单中归上存疑的行；`[待处置]` 标复核检出的问题。增量清单在 Step End 输出，不写入资产文档。

> 本任务**不写**任何确认标记到需求文档表达人类反馈——人类不编辑文档表达反馈，答复一律在对话里给；澄清问题清单是本任务自己的出题与记录处，不承载人类反馈。

## 四、判据速查

### 4.1 受理门槛（Step Start 过滤）

| 跳过原因 | 判定条件 | 判定 |
|---------|---------|------|
| 不是需求文档 | 文件名不以 `.chunk-` 命名 | 不可处理 → 输出提示、跳过 |
| 已在处理流程中 | 表 B 该行生命周期为 `已澄清` 或更后 | 不可处理 → 跳过（重做须先清空该行生命周期值） |
| 已废弃 | 表 B 该行生命周期为 `已废弃` | 不可处理 → 跳过（重启须先清空该行生命周期值） |
| 下游产物混入 | 正文区带分析建议块 | 路由错误 → 跳过，提示走规范化任务 |
| 不可读 | 正文区为空或读不出内容 | 不可处理 → 登记失败、`处置标记=待人工处置`，不进本轮 |
| 上次中断遗留 | 正文区之后残留上一轮的澄清问题清单 | 按 §六 重进入续做，不另起一轮 |

### 4.2 两味判据（出题认出什么）

说不清与该有却缺分两味：**表述不清**（说到了，读不出确切含义／范围／主体）与**要素缺席**（该有的一块没写）。

**表述不清四类**：

| 类 | 判据 | 例 |
|----|------|-----|
| 术语 | 业务或领域术语表述不明确，读不出确切含义与范围 | 「外购件」指哪些物料 |
| 主体客体 | 动作的主体或作用对象不可识别 | 「提出该需求」——由谁提出 |
| 边界 | 条件、范围、时限缺少边界 | 「试运行期」缺起止条件与时长 |
| 信息 | 缺来源、时间、提出方等元信息 | 缺来源日期与提出方 |

**要素缺席三类**：

| 类 | 判据 | 例 |
|----|------|-----|
| 缺少定量指标 | 有需求描述，缺性能指标的定量部分；判据＝指不出在给哪条需求打分（指得出的随那条需求走） | 「支持批量导入」缺单次上限 |
| 分支缺对应面 | 写了「当X时／正常情况」等条件或路径却缺其对应面，且对应面不能由上下文明显推出 | 只写「已审核」路径，「未审核／驳回」未提 |
| 引用对象缺失 | 文内引用了实体、流程或文档，全批需求文档里均无定义 | 引用「审批单」，全批无其定义 |

> **「引用对象缺失」的查法**——「无定义」的范围是**本篇所属那一份材料的全集**（同一份材料切出的全部需求文档，即源材料 `{原始文件名}.textualized.md`），不是这一篇。做法是按需扩大：grep 这个名、命中才读，不全量加载。

> 同一处属两类以上的仍只立一条。**性能指标不是非功能需求**，它是需求的部件。

### 4.3 问句规则与清单格式

每一条都携带一句可直接向相关方确认的问题：**一处一问**；**只问不答**（不给答案、不给指标数值、不给设计方案）；**可直接问**（能原样念给相关方听）。

```markdown
【澄清问题清单】本篇澄清完成时连同本行一并清除

| # | 位置 | 原片段 | 味·类 | 问句 | 状态 |
|---|------|--------|-------|------|------|
| 1 | 第 3 段 | 外购件 | 表述不清·术语 | 「外购件」的确切定义和范围是？ | 待答 |
| 2 | 第 12 段 | 支持批量导入 | 要素缺席·缺少定量指标 | 批量导入的单次上限（数值/单位/条件）是？ | 待问 |
```

- **状态**两值：`待问`（认出、还没交人确认）与 `待答`（人已确认、已问出、等答复）；落答一条即划去一条

### 4.4 非功能需求缺项随带澄清

涉及非业务诉求（质量诉求：实时／高效／安全／可靠等）的缺项，除要数值外还须一并澄清：

| 随带项 | 问什么 | 去向 |
|--------|--------|------|
| 质量属性准确表述 | 「快」指的是响应时间还是吞吐量 | 喂规范化任务的分类维度判定 |
| 适用对象 | 约束的是哪个场景、流程还是系统整体 | 喂规范化任务的适用对象线索 |
| 关注角色（必要时） | 谁提出或承受该质量诉求 | — |
| 定量指标 | 目标值＋单位＋条件 | 目标值由相关方确认 |

### 4.5 对账规则、落答规则与判据

**对账规则**（Step 1，出题与既有清单比对）：

| 情形 | 处置 |
|------|------|
| 清单里已有同一处 | 不动——不改它的问句，也不改它的状态 |
| 正文里冒出清单没有的新处 | 追加一条，状态记 `待问` |
| 清单里有、正文里已找不到对应处 | 该条随正文的变动作废，从清单划去 |

**落答规则**（Step 2）：

1. **只在所指处改**——每一条按相关方确认的答复写回
2. **其余一字不动**——原文其余部分照抄，不重写、不润色、不顺手补正
3. **答复不足则不落**——仍不足以说清的，该条留在清单上、状态仍记 `待答`，交下一轮再问
4. **落一条划一条**——写回完成即划去该条；全清后清单即空
5. **不越界**——写回只动清单所指的那一处；发现波及清单以外的内容，就地改回

**判据**（Step 3）：**复核后清单空**。清单上还躺着条目说明还有没说清的地方；复核又能生出新条目说明说清还没到头。两个条件合起来就是"问无可问、写无不清"。

> 清单空 → 清掉清单（连同标题行）、生命周期 `已澄清`、AI建议 `可以规范化`、frontmatter.status `clarified`；清单不空 → 保持 `澄清中`、AI建议 `需继续澄清`。**答复不足不落、清单未空**，都算仍在澄清。

### 4.6 清单与需求文档模板

**澄清问题清单**（写在需求文档正文区之后）：

```markdown
【澄清问题清单】本篇澄清完成时连同本行一并清除

| # | 位置 | 原片段 | 味·类 | 问句 | 状态 |
|---|------|--------|-------|------|------|
| 1 | 第 3 段 | 外购件 | 表述不清·术语 | 「外购件」的确切定义和范围是？ | 待答 |
```

**需求文档**（`.chunk-{seq}.md`，原地更新）：

```markdown
---
chunk:
  source: {原始文件名}.textualized.md
  original_source: {原始文件名}.{ext}
  seq: {序号}
  total: {总篇数}
  kind: {业务需求文档 | 非功能需求文档 | 引擎需求文档}
  label: {文档级任务名 / 适用对象·主题 / 能力名}
  range: {行号范围}
  # 非功能需求文档另带：applicable: {适用对象} / topic: {主题，即分类维度}
  # 引擎需求文档另带：capability: {能力诉求}
status: clarified
---

| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 已澄清 | 可以规范化 | 无 | 状态文档表 B → 该记录人类决策设为 `同意规范化` |

（澄清后的纯净正文）
```

### 4.7 状态路由（Step Start 分流）

| 表 B 状态 | 走哪条路 |
|-----------|---------|
| `人类决策=同意澄清` 且 生命周期 `已切分` | 进本轮，Step 1 出题 |
| `生命周期=澄清中` | 进本轮，按 §六 重进入续做 |
| `人类决策=需退回澄清`（规范化退回） | 进本轮，重新出题（`人类决策` 触发后清空） |
| `人类决策=已终止` | 进本轮，Step 1 给「置 `已废弃`」方案，Step 2 确认后按 §六 处置 |
| `人类决策` 为空 | 不进本轮，列入待选入澄清提醒 |
| `人类决策=同意规范化` 或更后 | 不进本轮，列入行动清单 |

### 4.8 状态文档列与取值（本任务写入的部分）

**表 B（需求文档级）**：

| 列 | 取值 / 写法 |
|----|------------|
| 内容摘要 | 一句话阶段摘要，如 `清单 3 条待答复` |
| 生命周期 | `澄清中` / `已澄清` / `已废弃` |
| AI建议 | `需继续澄清` / `可以规范化` / `建议终止` |
| 未解决数 | 当前澄清问题清单的条数（`unresolved_count`） |
| 操作指引 | 人类下一步应执行的操作 |

> `人类决策` 列是人类输入面，本任务只读不写：空（未处理）/ `同意澄清` / `同意规范化` / `需退回澄清` / `已终止`。完整列定义以状态文档自身为准。

## 五、写回与版本感知

### 5.1 写回前冲突检查

状态文档表 B 的人类决策列是人类与 AI 共同维护的面。AI 写回前执行冲突检查，防止覆盖人类手工修改：

1. **快照**——Step Start 记录待处理行的生命周期与人类决策当前值
2. **写回前复核**——写回前重读该行；与快照不符（人类在本次运行期间手工修改）的标 `[需复核]`、不覆盖，在 Step End 向人类提示
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段，AI 绝不覆盖非空的人类决策

### 5.2 写回顺序（同步契约）

1. **先更新状态文档表 B**（权威源）——转迁生命周期、更新 AI建议、未解决数与操作指引
2. **再据此写**需求文档管理区状态表（阶段/AI建议/待处理/操作指引）与 frontmatter.status
3. 两者不一致时，以状态文档为准重建管理区
