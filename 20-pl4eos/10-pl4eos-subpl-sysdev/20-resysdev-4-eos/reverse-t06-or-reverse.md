# 原始需求推导
**SKILL 指南ID**: reverse-t06 · **Step 6: Original Requirements Reverse Engineering**

> **概述**：从 业务框架 详细定义末级节点聚合为原始需求条目，建立完整的 规范化的相关方需求 → 业务框架 追溯关系。规范化的相关方需求 聚合应识别 EOS 的三源分类（引擎开发需求、业务配置需求、CAX工具需求）。
>
> **输入 → 输出**：业务框架 架构定义 + 详细定义 → 规范化的相关方需求 文档（`01-*.md`）
>
> **适用场景**：逆向工程第6步。5 层闭环至此完成：产品框架 → 系统需求框架 → 业务方案 → 业务框架 → 规范化的相关方需求。
>
> **版本**：v1.3 | **修订**：2026-08-28

---

## 一、设计角色

本步在设计链中承担的角色：
- **输入**：业务框架文档（bpl-biz + bpl-nfr），第5步决策记录
- **产出**：原始需求文档（`01-*.md`），5 层闭环至此完成：产品框架 → 系统需求框架 → 业务方案 → 业务框架 → 规范化的相关方需求

### 与三条工程化设计原则的关系

| 原则 | 在逆向工程中的体现（本步） |
|------|--------------------------|
| **详概分离** | 规范化的相关方需求 层仅需一份条目级需求文档（`01-*.md`），不需要单独的架构和详细定义。规范化的相关方需求条目按原子性要求分解到末级，功能与非功能分离 |
| **文档结对** | 业务框架 详细末级与 规范化的相关方需求条目形成本步的唯一一对文档结对。这是逆向工程的终点——从 业务框架 聚合回 规范化的相关方需求，完成 5 层闭环 |
| **基于资产** | 业务框架 详细末级是推导 规范化的相关方需求 的核心资产。从"谁提出了什么需求"反推"需求的原材料表述"。规范化的相关方需求条目按三源分类组织 |

## 三、操作流程

八阶段：分析活动 → 聚合 规范化的相关方需求 → 规范化的相关方需求 规范化 → 规范化的相关方需求 分解 → 冲突维护 → 映射更新 → 建映射 → 结果审核。

核心驱动逻辑：从"谁在什么场景下有什么需求"聚合回"原始的需求来源是什么"。

操作流程概览：

```
[阶段一] 分析活动         [阶段二] 聚合规范化的相关方需求           [阶段三] 规范化的相关方需求规范化
[阶段四] 规范化的相关方需求分解           [阶段五] 冲突维护         [阶段六] 映射更新
[阶段七] 建映射           [阶段八] 结果审核
```
