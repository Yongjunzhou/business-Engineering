## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| 接收同角色 FR-BIZ 规范化的相关方需求（≤10条），校验类型/数量/状态 | FR-ENG → `wft01-eng` |
| 按用户角色匹配已有业务流程概要 → 归入（Phase B）或待聚合池（Phase C） | NFR → `wft01-nfr` |
| 定义场景职责边界（= 主责角色的业务对象闭环）+ 业务链文档序列 + 引擎候选 + P 组装（WBS 归组/23 一致性/缺口推断） | 下游详细定义（字段级详设）→ `wft02-biz` |
| E2E 闭合检查 + 生成补充规范化需求材料 | 无规范化的相关方需求输入的治理业务流程概要不主动展开 |
| 人类确认后写回 23 资产 + 推进业务流程概要→`可以分解分配` + 规范化的相关方需求→`已分配` | 业务人员确认（人类线下活动） |
| 接收 wft02 退回的 `需wft01修订` 业务流程概要，按 SKILL 指南修订 | — |

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | `or03` | FR-BIZ 规范化的相关方需求写入 `01-*.md`，状态=`待处理`。通过 `## AI可以处理节点` 的"待 wft01-biz 处理"分节检测 |
| 下游 | `wft02-biz` | 消费 `可以分解分配`/`待补充分解分配` 的业务流程概要。缺陷时退回 `需wft01修订`+缺失说明 |
| 同级 | `wft01-eng`、`wft01-nfr` | 各自处理 FR-ENG / NFR，本 Skill 输入校验检出后退出并提示路由 |

## 二、操作流程

### Step Start · 前置校验与路由

**变更感知**（先于入口检测，检出人类线下修订）：

```bash
bash ../.scripts/detect-changes.sh ../../../80-pl4eos-2-eosdata/01-eos-specified-requirements.md
bash ../.scripts/detect-changes.sh ../../../80-pl4eos-2-eosdata/02-eos-business-summary-architecture.md
```

检出 `HAS_CHANGES=1` → AI 检查变更行，判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入"待反馈处理"分节；自由文本 → 标记 `[需确认]`；格式/排版 → 忽略。**先变更感知再入口判定**——纯线下修订若不先检出，会被误判"无待处理对象"退出（详见 human spec §5.1 变更感知）。

**入口检测**（按 [91 规范 §A.4](../91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)）：

```bash
# 1. 读取待处理节点
bash ../.scripts/read-section.sh ../../../80-pl4eos-2-eosdata/01-eos-specified-requirements.md "AI可以处理节点"
bash ../.scripts/read-section.sh ../../../80-pl4eos-2-eosdata/02-eos-business-summary-architecture.md "AI可以处理节点"
```

**输入校验**（按顺序，命中即退出）：

| 条件 | 判定 | 动作 |
|------|------|------|
| 规范化的相关方需求状态=`需退回重切` | 不可处理 | 输出退回记录 → **退出** |
| 规范化的相关方需求状态≠`待处理` | 不可处理 | 输出当前状态 → **退出** |
| 规范化的相关方需求分属多个角色 | 不可处理 | 输出角色分布 → **退出** |
| 规范化的相关方需求类型含 FR-ENG/NFR | 路由错误 | 输出类型分布 + 路由指引 → **退出** |
| 同角色规范化的相关方需求 >10 条 | 软提示 | 输出超限提示 → 人类确认 |
| 无任何待处理 | — | 输出"无待处理对象"→ **退出** |

**退回优先**：存在 `需wft01修订` 业务流程概要 → 检查人类是否提供改进方案（§A.4 退回门禁）。已提供 → 读取缺失说明，走 Phase B 修订。未提供 → 输出缺失说明 → **退出**。

### Step 2 · 方案反馈处理

**触发条件**：Step Start 检出 `需wft01修订` 业务流程概要，或上一轮 Step End 的反馈等待中人类提出修改意见。

**反馈双轨**（人类任选其一，详见 SKILL 指南 §5.3）：①AI 对话反馈——Step End 后不结束对话，直接回复修改意见，AI 即时处理；②线下文档修订——打开 `01/02-*.md` 在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]` 或直接编辑方案内容（自由文本），经 Step Start 变更感知 git diff 检出后按 §A.5 处理。两轨等价均落账（追 `[已处理]`）。

**处理规则**：

1. 从当前轮次对话上下文或退回缺失说明中读取人类反馈意图
2. **逐条处理**（按人类反馈内容）：
   - AI 输出方案后人类直接回复修改意见 → 在当前轮次继续对话处理，不重新走 Step Start
   - wft02 退回的 `需wft01修订` → 下一轮 Skill 调用时走 Step Start 退回优先
3. 修改后检查是否仍满足该业务流程概要所承接的规范化的相关方需求
4. 修改导致结构性变更（边界/引擎/PL6-B 增删）→ 按需重入 Step 3
5. 全部条目获人类认可 → 业务流程概要 → `可以分解分配`

**本 Skill 特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义）：

| 特化维度 | wft01-biz 值 |
|---------|-------------|
| 锚点需求 | 当前业务流程概要所承接的全部规范化的相关方需求条目（FR-BIZ）——人类反馈理解和修订均以规范化的相关方需求为最终锚点 |
| 操作条目 | 场景职责边界 + 业务链各 PL5 输出文档 + 按三独立展开的 PL6-B 正文条目 |
| 推进目标 | 人类「整体确认」→ 业务流程概要推进至 `可以分解分配` |
| 清除条件 | 已有 `[已处理]` 条目默认跳过；仅当本轮新输入满足任一条件时清除回待处理：直接上游节点 / 同层边界重叠 / 定义被修订 |
| 级联触发条件 | 修改导致结构性变更（边界/拆分合并/引擎变更/PL6-B 增删）→ 标记受影响条目 `[需重设计]` |
| 资产对齐级联 | 方案变更影响 23B 引用 → 更新受影响资产的 Q 判定和引用路径 |

### Step 3 · 场景业务设计

#### Phase A — 规范化的相关方需求路由

对每条新规范化的相关方需求：
1. 从已加载的规范化的相关方需求节点块（Step 1 通过 `read-node.sh` 获取）中读取 `**所属角色**` 字段——角色已在需求规范化（or03）时标注
2. 轻量提取：文档名称 + 触发动作（够路由即可）
3. 宿主匹配——规范化的相关方需求的文档名称 + 描述职责落入已有业务流程概要的场景职责边界 → Phase B；否则 → 待聚合池 → Phase C

待聚合池按**触发动作相似 + 文档名称重叠**分组。

#### Phase B — 修订已有业务流程概要

**执行顺序**：
1. **要素提取**——从本轮规范化的相关方需求提取文档名称和支撑引擎
2. **边界匹配检查**——确认规范化的相关方需求在业务流程概要边界内（[§3.2.3](../eos-wft01-biz-spr2bpl.md#323-phase-b-边界匹配检查)）（详见 human spec）：
   - 边界内 → 进入关系检测
   - 边界扩展 → 更新边界陈述 + `[推断]`
   - 退回规范化 → 输出拆分建议，规范化的相关方需求→`需退回重切`
   - 宿主误匹配 → 退回待聚合池
3. **业务链关系检测**——比对已有基线（[§3.3.5](../eos-wft01-biz-spr2bpl.md#335-phase-b-业务链关系检测)）（详见 human spec）：
   - 确认（文档匹配+引擎相同+来源非规范化的相关方需求明示）→ 来源升级
   - 无新增（文档匹配+来源已为规范化的相关方需求明示）→ 追加引用+增量合并
   - 引擎变更（文档匹配+引擎不同）→ 更新引擎+变更原因
   - 补充（文档不匹配）→ 新增到业务链
   - 过时（基线文档未被本轮覆盖）→ `[过时]`+保留不删
4. **变更影响声明**——判定变更类型（[91 规范 §A.7](../91-eos-biz-eng-spec.md#a7-变更传播协议)），按 [SKILL 指南 §4.2](../eos-wft01-biz-spr2bpl.md#42-业务流程概要变更传播协议) 实例化格式写入业务流程概要节点末尾
5. **P 组装重跑**——业务链拓扑变化时（新增/过时/引擎变更/边界扩展）按 SKILL 指南 §3.3.3 重跑 P 组装（WBS 归组 + 23 一致性 + 缺口推断，判据见附录 A.7），更新业务流程概要节点的 P 组装结论；结构性缺口入 Step 4 补充规范化的相关方需求回路

#### Phase C — 新建业务流程概要

**执行顺序**：

1. **确定业务域**——从已加载的规范化的相关方需求节点块的 `**所属角色**` 字段获取角色名。若 Step 1 已加载的角色索引中有该角色的业务域信息则直接引用；否则用 `bash ../.scripts/read-node.sh ../../../80-pl4eos-2-eosdata/21-eos-stakeholder-roles.md ROLE-<ID>` 加载角色定义块查找。若 21 文件中无该角色或角色定义中无业务域字段，标记 `[推断]` 并基于角色职责语义匹配
2. **定义端到端边界**——识别触发→追踪自然终点→闭合验证→边界检查（[§3.2.2](../eos-wft01-biz-spr2bpl.md#322-端到端边界定义)）（详见 human spec）
3. **判定业务流程概要类型**——D 或 PCA（判据见附录 A.1）
4. **逐文档要素提取**：
   - **a. 封面模式**——正文变更是否需要审批/发布/版本追溯？→ 是=正式 / 否=轻量
   - **b. 支撑引擎**——按正文数据类型匹配功能引擎候选，全量 `[推断]`（引擎清单从 25 资产动态读取）
   - **c. 任务类型**——零个或一个（计划/流程/工单）。规范化的相关方需求明示→直接捕获；规范化的相关方需求只提管理模式（如"需要审批"）→ 判定类型 + 标注 `[待wft02推断]`；规范化的相关方需求缺失活动节点描述→推断类型 + 标注 `[待wft02推断]`。**R4 约束**：场景业务中第一个有任务类型的文档，任务类型必然是计划（该文档=**开发/记录类文档**，闭环从它启动；PCA 场景另有计划清单文档，两者不同实例，[§2.2.1](../eos-wft01-biz-spr2bpl.md#221-定义与生成方式)）
   - **d. 任务主要节点**——有任务类型时，捕获/推断任务主要节点（业务语言），**供人类确认业务流转关系**（谁审批/通过后到哪），作为 wft02 引擎化的业务锚点。正式文档节点附着封面、轻量文档附着正文实体；规范化的相关方需求明示则捕获，否则标注 `[待wft02推断]`
   - **e. PL6-B 正文条目**——先判定正文是否为集合容器，再按三独立（判据见附录 A.3）逐类判定；轻量文档原子正文行不重复展开。规范化的相关方需求只提管理模式（如"需要看板展示"）或信息不足→推断条目类型 + 条目名称标 `[待wft02推断]`
   - **f. 23B 对齐判定**（P 组装 ①）——逐文档 Q1/Q2/Q3 判定（判据见附录 A.4）
5. **确定文档序列**——按业务流转顺序排列
6. **组装业务流程概要**——写入 `02-*.md`，完整要素见 [§2.1.2](../eos-wft01-biz-spr2bpl.md#212-业务流程概要节点要素与职责边界)（详见 human spec）
7. **P 组装**——按 SKILL 指南 §3.3.3 执行：① 23B Q1/Q2/Q3 判定（步骤 4.e 已逐文档完成）→ ② PL4 WBS 归组（数据依赖链硬判据 + 完成耦合，判据见附录 A.7）→ ③ 23 一致性检查（归属冲突/误新建/误引用）+ 缺口推断（按构件产品数据清单完整性做名称级比对，**不依赖任务类型/引擎**）。组装结论写入业务流程概要节点的 P 组装结论；结构性缺口标注 `[推断-待规范化的相关方需求确认]` 入 Step 4 补充规范化的相关方需求回路。Phase B 修订时业务链拓扑变化同样重跑（见 Phase B 步骤 5）

**写入业务流程概要节点时**，为每个条目初始化空的 `确认状态` 字段。

### Step 4 · 规范化的相关方需求增补

按每个业务流程概要独立执行。新建 → 全量检查；修订 → 仅当链拓扑变化时重验闭合。

**1. E2E 闭合检查**——D 闭合（需求提出→需求满足）；PCA 闭合按 [91 §2.7](../91-eos-biz-eng-spec.md#27-pca-场景的-pca)——业务链**必须包含计划清单输出文档**（正文条目三独立展开 PL6-B）+ 承载 C/A 的输出文档（指标/看板/风险/问题清单），**C/A 本身为任务链运行时结果、不作为规范化的相关方需求缺口**。缺口不脑补 → 生成补充规范化需求材料。

**2. 要素机械检查**——逐文档确认非空或有合理空置原因：文档名称/用途/封面模式/引擎/开发方式/任务类型/任务关系（信息不足标 `[待wft02推断]`）/PL6-B（信息不足标 `[待wft02推断]`）/生命周期/支持信息/交互信息/P 组装（Q 判定 + WBS 归组 + 缺口推断）。

**3. 补充规范化需求材料生成**——闭合缺口 + **P 组装结构性缺口**（构件产品数据清单未覆盖，附录 A.7 ③）时生成补充规范化需求材料，写入 `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/<YYYYMMDD>-<场景业务名称>补充原始需求材料.md`，登记到材料状态表。

## 附录A：判据速查

### A.1 业务流程概要类型判定

**概念锚点**：场景业务（业务流程概要）= 一个主责角色的一个业务对象闭环——业务对象与主责角色一一对应（主推动者：提出需求 / 负责完成 / 确认结果），配合角色是闭环内流程环节、不单独成业务流程概要（[91 §1.4](../91-eos-biz-eng-spec.md#14-业务场景)）。D 与 PCA 两种类型：

| 类型 | 典型动作词 | 闭合规则 |
|------|-----------|---------|
| **执行类（D）** | 创建/提交/审批/交付/验收/退货/对账 | D 闭合——从需求提出到需求满足，文档间以输入-输出传递链为主 |
| **管理类（PCA）** | 策划/计划/监控/度量/分析/识别/纠正/改进 | PCA 闭合——业务链**必须包含计划清单输出文档**（正文条目三独立展开 PL6-B，首条目=策划）+ P 定义型文档（指标/看板清单）；C/A 为任务链运行时结果（指标度量→看板呈现→风险/问题条目） |

D 和 PCA 处理逻辑**流程骨架同构**（场景业务→文档序列→每文档封面/正文/任务/引用），差异在文档模式（PCA 含计划清单）与闭合形态（[§5.5](../eos-wft01-biz-spr2bpl.md#55-step-4--规范化的相关方需求增补)）。类型仅影响引擎推断偏好（D 产品数据类 / PCA 业务管理类优先，计划引擎 @engine-task 两场景共用）——引擎权威校验以任务类型↔引擎映射为准（wft02 §3.2）。

### A.2 封面模式判定

问：该文档是否有独立于正文 CRUD 的生命周期（需要审批流转/版本追溯/派发验收/独立状态变迁）？
- **是** → 正式文档（有封面，DocumentCover 表一行 + 正文 1:1）
- **否** → 轻量文档（无封面，正文即文档）

### A.3 PL6-B 三独立判定

| 条件 | 判据 | 正例 | 反例 |
|------|------|------|------|
| ① 独立名称 | 在文档内有固有称谓 | ✓ "订单及时率"、"采购预警" | ✗ 物料行（"序号1"不是名称） |
| ② 独立定义要素 | 有独立业务约束/规则/格式 | ✓ 指标有口径/维度/目标值 | ✗ 物料行的编码/数量由文档字段结构定义 |
| ③ 独立生命周期 | 独立于父文档的状态变迁 | ✓ 指标需审批后发布 | ✗ 物料行随申请单创建/删除 |

三项全满足 → 展开 PL6-B。轻量文档原子正文行不重复判定。

### A.4 23B 对齐判定 Q1/Q2/Q3

### A.7 P 组装（WBS 归组 / 23 一致性 / 缺口推断）

本 Skill 末级（文档）完整性的双闸之一——R 闭环（Step 4 闭合检查）+ **P 审查补漏**（本判据）。逐文档执行三步：

**① 23B 对齐判定**（Q1/Q2/Q3，见 A.4）——确定 PL2（E2E 项目业务）/PL3（构件类型）归属。

**② PL4 WBS 归组**——将同一构件类型（PL3）下的输出文档按业务模块归纳分组（PL3 与 PL5 之间），命名取文档名称/用途/支撑引擎共性。**硬判据 = 数据依赖链**：归入同一 WBS 的交付类文档，正文数据须在同一数据依赖链上（前一文档正文数据成为后一文档输入）→ 组内文档满足**完成耦合**；跨链不归组；管理类文档（指标/看板/风险/问题/计划清单）按其支撑的交付链归属。

**③ 23 一致性检查 + 缺口推断**——组装后校验 ① 与 ② 是否矛盾（检出而非静默覆盖）：

| 不一致类型 | 判定 | 动作 |
|-----------|------|------|
| 归属冲突 | Q2/Q3 建议归属与 WBS 推导的 PL2/PL3 不一致 | 标注 `[23归属冲突]` + 两者路径对比 → 提示人类裁决 |
| 误新建 | Q3 建议新建，组装上下文发现已有条目（同名/同义且职责覆盖）可承接 | 降为 Q2 + 记录降级原因和已有条目路径 |
| 误引用 | Q1 引用已有条目，组装后发现职责边界不能覆盖当前文档 | 升为 Q2/Q3 + 记录升级原因 |

矛盾项 Step 5 暂不写回 23（待人类裁决后下一轮处理）。

**缺口推断**：对每个构件类型，读取 23 资产 P 侧**产品数据清单**（该构件应有的输出文档集合，名称级），与业务流程概要业务链做**名称级比对**——清单文档已在业务链 → 视为已覆盖；未在 → **结构性缺口**，标注 `[推断-待规范化的相关方需求确认]`，由 Step 4 补充规范化需求材料补回。**不依赖任务类型/引擎**。
