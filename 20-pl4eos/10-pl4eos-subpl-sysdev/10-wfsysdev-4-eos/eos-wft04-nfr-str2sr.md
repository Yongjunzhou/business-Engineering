# 非功能需求框架 → 非功能需求方案
**SKILL 指南ID**: wft04-nfr

> **概述**：接收已确认的 bpl-nfr 非功能需求框架，经前置校验、材料加载和反馈处理后，生成系统侧非功能需求架构（SysReq-NFR）和页面非功能需求。该方案承接 wft01-nfr 分类需求清单中相关方经澄清确认的目标值（[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解) 需求=需求描述+性能指标），展开为可验证的量化约束、分层约束表、页面约束包、22 具体需求资产和 06 系统需求概要。
>
> **输入 → 输出**：bpl-nfr 节点（`可以NFR设计` / `待补充NFR设计`）/ 有反馈的 SysReq-NFR 节点 → SysReq-NFR 架构节点 + 量化指标 + 分层约束表 + 七种页面类型及具体页面 ID 的 NFR 约束 + wft05-eng NFR 约束包（含版本与变更声明）+ 22 具体需求写回 + 06 系统需求概要 + bpl-nfr 推进为 `已NFR设计` + SysReq-NFR 推进为 `已验证冻结`
>
> **适用场景**：瀑布式系统设计第4步 · 非功能需求路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v5.15 | **修订**：2026-08-28

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于架构师和验证者——「指标可验证，约束分层正确，目标页面与实现组件可追溯」。把 bpl-nfr 转化为系统侧 SysReq-NFR 架构和页面非功能需求，将约束绑定到 91 规范七种页面类型之一或具体页面 ID，并关联 CU/pa-eng 组件和 06 详细定义，形成供 wft05-eng 单一实现消费并支持追溯验证的 NFR 约束包。

**目标**：

1. **生成非功能需求架构**——按 22 分类维度和系统约束边界生成或复用 SysReq-NFR 节点，保证每条 bpl-nfr 分类需求项有唯一系统侧宿主
2. **生成量化约束**——承接相关方经澄清确认的目标值，展开为可验证的指标（单位/统计口径/测量方法和验收条件）；目标值缺失或信息不足时标记待确认，不伪造确定值
3. **生成页面非功能需求**——把 NFR 约束落到全局、业务域、srb-biz、CU、pa-eng 组件和页面对象，形成 wft05-eng 可消费的约束包
4. **写回 22 具体需求资产**——复用、升级或新增 22 具体需求条目及指标集，保留 bpl-nfr / SysReq-NFR 追溯
5. **展开 06 详细定义**——将确认后的 SysReq-NFR 量化约束写为可验证系统需求概要，供后续验证与实现使用

本 Skill 负责：

1. **接收**——接收人类选中的一批 bpl-nfr 节点（≤5 个），校验状态为 `可以NFR设计` / `待补充NFR设计`；状态/类型不符时退出并提示
2. **量化**——消费 bpl-nfr 分类需求清单，承接相关方确认的目标值，逐项展开系统级量化指标（指标名称/单位/统计口径/测量方法/验收条件）；目标值缺失时标记待确认，不伪造确定值
3. **归架构**——按 22 分类维度、约束对象和语义内聚度匹配或新建 SysReq-NFR 节点，保证每条分类需求项有唯一系统侧宿主
4. **分层**——生成分层约束表，明确约束范围、适用链路、约束对象、消费目标、影响级别和影响点
5. **落页面**——对影响业务操作体验、界面行为、页面性能、安全、可访问性、审计提示等诉求，生成页面非功能需求
6. **落账**——写回 22 具体需求资产、06 系统需求概要、05 SysReq-NFR 节点和 bpl-nfr 消费版本
7. **推进**——人类确认后 bpl-nfr → `已NFR设计`，SysReq-NFR → `已验证冻结`
8. **退回**——当 bpl-nfr 分类边界、角色语境或适用范围线索不足时，将节点退回为 `需wft01修订` 并附缺失说明

本 Skill 不负责：

1. 修改 wft01-nfr 已确认的角色语境、NFR 分类边界或规范化的相关方需求分组；发现问题时退回 wft01-nfr
2. 设计业务场景、输出文档或功能表单（→ biz 路径）
3. 设计引擎场景、CU 详细定义或前后端组件结构（→ eng 路径）
4. 修改 22 已确认分类维度本身；本 Skill 写入的是具体需求、指标集、引用和候选升级
5. 替代人类确认无法从 bpl-nfr 或资产推断出的目标值

### 1.2 与上下游的衔接

**上游 wft01-nfr**：提供已确认 bpl-nfr，包含角色语境、22 分类路径、NFR 分类需求清单、适用对象线索、待量化线索和变更影响声明。本 Skill 在 Step Start 中通过 `02-*.md` 的 `## AI可以处理节点` 分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)）检测待处理 bpl-nfr 节点，定位并读取节点块（按 [§A.3.3](91-eos-biz-eng-spec.md#a33-产品数据文档与资产文档读取与写回约定) 读取协议执行）。重入时读取 bpl-nfr 版本号和变更声明，按无变更/增量型/修订型/结构型处理。若 bpl-nfr 分类边界或适用对象不足，本 Skill 退回为 `需wft01修订`（[§A.4.3](91-eos-biz-eng-spec.md#a43-规则二退回节点的门禁) 退回门禁）。

**下游消费方**：wft05-eng 消费 CU/pa-eng 组件/运行机制相关 NFR 约束（含页面 NFR 和分层约束表）。06 系统需求概要供验证与追溯使用。SysReq-NFR 的分层约束表是下游消费 NFR 的唯一入口。NFR 约束全部流向 eng 路径——性能/安全/可用性等非功能质量约束由平台的引擎层保障，不进入 biz 路径（业务配置链）。

**时序说明**：wft01-nfr / wft04-nfr 可与 eng 路径前三步并行。wft04-nfr 可先设计全局、共享、业务域级约束，并为 bpl-eng/CU/页面级约束记录目标候选；相关目标尚未形成时不得虚构目标 ID，节点保持 `待目标绑定`。biz 路径的功能表单/窗口标签页或 eng 路径的配置页面 srb-biz 可定位后，wft04-nfr 完成目标绑定并确认首版 NFR 约束包。该约束包是 wft05-eng 首次启动的必备前置输入：未取得已确认的首版约束包时，wft05-eng 不得开始产品架构设计。首版被消费后，约束包版本递增可触发 wft05-eng 按变更声明和约束行 ID 增量重入。

**一句话**：本节讲 SysReq-NFR——定义与宿主匹配锚点、节点完整要素；完备性判据见 §三 3.4。

**定义**：SysReq-NFR 是 bpl-nfr 在系统需求层的结构化表达，末级节点为**非功能需求方案**。它回答"系统需要满足哪类非功能质量、以什么指标验证、约束哪些业务/平台对象、由哪些下游设计对象消费"。NFR 路径分工见 [91 规范 §10.5](91-eos-biz-eng-spec.md#105-nfr-路径-skill)。

| 约束对象 | 全局、业务域、srb-biz、CU、pa-eng 组件、页面级对象 |
| 指标口径 | 目标值、单位、统计口径、测量方法 |
| 适用链路 | `biz` / `eng` / `共享` |

**节点完整要素**（写入 `05-*.md` SysReq-NFR 节点块）：

| 要素 | 说明 |
|------|------|

| 量化指标 | 量化指标清单（§2.2） |
| 约束结构 | 分层约束表 + 页面 NFR 清单（§2.3） |
| 资产对齐 | 22 具体需求写回项 + 06 详细定义引用 |
| 检查状态 | 闭环检查结果 + 版本号 / 确认状态 |

### 2.2 量化指标

**一句话**：量化指标是 SysReq-NFR 的核心条目——承接 bpl-nfr 相关方确认的目标值，展开为可验证的指标定义。

量化指标是 SysReq-NFR 的核心条目，承接 bpl-nfr 中相关方经澄清确认的目标值，展开为可验证的指标定义。每条指标至少记录：

| 字段 | 说明 |
|------|------|
| 指标名称 | 可验证的非功能指标 |
| 目标值 / 单位 | 明确阈值、范围或布尔要求；无法确定则标记 `待确认` |
| 统计口径 | 时间窗口、样本范围、百分位、业务条件或环境条件 |
| 测量方法 | 压测、审计检查、日志统计、模拟、外部认证、人工检查等 |
| 验收条件 | 满足/不满足的判断标准 |
| 来源 bpl-nfr | 需求项 ID 与消费版本 |
| 22 具体需求引用 | 复用或新增的 `@nfr-xxx-REQ-yy` |
| 确认状态 | 人类反馈字段 |

模糊诉求处理原则：可依据 22 具体需求模板、同类场景和行业常识推断时标记 `[需裁决]` 并给出依据；无法推断时保留 `待确认`，不得推进到写回。

### 2.3 分层约束与页面 NFR

**一句话**：本节讲 SysReq-NFR 的约束结构——分层约束表（2.3.1）、页面 NFR（2.3.2）、22 具体需求资产（2.3.3）。

#### 2.3.1 分层约束表定义

**一句话**：每个 SysReq-NFR 节点必须带分层约束表，供 wft05-eng 消费。

每个 SysReq-NFR 节点必须带分层约束表，供 wft05-eng 消费：

| 约束范围 | 适用链路 | 约束对象 | 消费目标 | 影响级别 | 影响点 | 说明 |
|----------|----------|----------|----------|----------|--------|------|

字段取值：

| 字段 | 取值 |
|------|------|
| 约束范围 | `全局` / `业务域` / `srb-biz` / `CU` / `pa-eng组件` / `页面级` |
| 适用链路 | `biz` / `eng` / `共享` |
| 约束对象 | EOS、业务域名、srb-biz ID、目标引擎+CU 类型、组件类型、七种页面类型之一或具体页面 ID |
| 消费目标 | `wft05-eng:CU/组件约束` / `wft05-eng:页面级约束` / `wft05-eng:共享约束` |
| 影响级别 | `阻断型` / `非阻断型` / `待判定` |
| 影响点 | 配置项、配置规则、配置可达性、验收标准、页面交互、页面性能、权限/审计、组件边界、接口机制、运行约束机制等 |

填写约束：

1. 一行只表达一个约束对象和一个消费目标的关系。
2. 阻断型约束必须填写影响点。
3. 待判定约束必须说明待判原因。
4. 影响面大时优先使用全局或业务域，不强制枚举所有 srb-biz。
5. 明确影响引擎实现时，至少补一行 `适用链路=eng` 的 CU 或 pa-eng 组件约束。
6. NFR 约束仅流向 eng 路径——所有约束行消费目标均为 `wft05-eng`，不进入 biz 路径。

#### 2.3.2 页面非功能需求

**一句话**：页面 NFR 是分层约束表中 `约束范围=页面级` 的特化条目，绑定七种页面类型之一或具体页面 ID。

页面 NFR 是分层约束表中 `约束范围=页面级` 的特化条目，覆盖页面类型、交互行为和用户可感知质量。页面类型必须从 91 规范定义的七种类型中选择：菜单标签页、场景标签页、窗口标签页、全屏单据页、辅助栏标签页、弹窗页面、配置页面。

典型类型：

| 类型 | 示例 |
|------|------|
| 页面性能 | 首屏加载、列表查询、下钻切换、弹窗响应、批量操作反馈 |
| 页面安全 | 字段脱敏、按钮权限、行列权限、敏感操作二次确认 |
| 易用性/工效 | 操作步数、错误提示、批量处理、键盘可达性、认知负荷 |
| 可访问性 | 对比度、焦点顺序、读屏标签、无鼠标操作 |
| 可恢复性 | 草稿保存、异常重试、重复提交防护 |
| 可观测性 | 操作日志、审计轨迹、错误定位信息 |

页面级约束应引用 91 规范定义的页面类型及其层级，并按需关联辅助栏、分屏、下钻、菜单和引擎生成模型。能落到具体功能表单、窗口标签页、配置页面或其他页面时写具体 ID；暂不能定位时写页面类型或业务域，并标记 `[需裁决]`。

#### 2.3.3 22 具体需求资产

**一句话**：wft04-nfr 写回 22 的对象是**具体需求及其指标集**，不是分类维度本身。

wft04-nfr 写回 22 的对象是**具体需求及其指标集**，不是分类维度本身。

| 判定 | 条件 | 动作 |
|------|------|------|
| 复用 | 22 已有同义具体需求，指标口径兼容 | 引用已有 `@nfr-xxx-REQ-yy` |
| 升级候选 | 候选区存在同义候选，且本轮指标集完整 | 状态→已确认，补充指标集和来源 |
| 新增 | 无同义具体需求或候选 | 新建具体需求条目，挂到已有分类维度 |
| 回退 | 指标集不完整或口径无法确认 | 回退 Step 3，不写入 22 |

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲设计的逻辑——为什么用 SysReq-NFR 承接 bpl-nfr（3.1 转换原理）、怎么从 bpl-nfr 提取要素（3.2）、怎么量化推断（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四。

### 3.1 转换原理：为什么用 SysReq-NFR 承接需求

**bpl-nfr 是分类化的质量诉求，SysReq-NFR 要可验证**。bpl-nfr 的 NFR 分类需求项只表达了"哪类质量、约束什么对象"，缺少可验证的指标口径——目标值由相关方经 or02 澄清确认（[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)），但统计口径、测量方法、验收条件需系统侧设计。本 Skill 的转换正是把 bpl-nfr 层（`02-*.md`）的分类需求项，变成 SysReq-NFR 层（`05-*.md`）的可验证指标与可消费约束。

**承接单位 = SysReq-NFR（非功能需求方案），因为指标必须挂到唯一系统侧宿主**。一条 bpl-nfr 分类需求项展开为指标后，必须归属到唯一的 SysReq-NFR 节点（22 分类维度 + 约束对象 + 指标口径锚定，§2.1），避免同一质量诉求被多处实现、口径漂移。宿主唯一同时保证**约束可追溯**——从指标经分层约束表到 wft05-eng 消费对象，全程可验证。

**量化 + 可消费，不是复述**。本 Skill 不只复述 bpl-nfr 的目标值，还展开统计口径/测量方法/验收条件，并组织为 wft05-eng 可消费的分层约束包。目标值缺失或不可验证时，不伪造确定值——标记 `待确认` 或 `[需裁决]`（§3.3.1）。

**SysReq-NFR 通过变更声明增量响应上游**。bpl-nfr 因新规范化的相关方需求修订（版本递增）时，本 Skill 重入按变更影响声明分流：无变更不动、增量型只量化新需求项、修订型修订受影响指标、结构型等人类裁决（§4.2）。这是本 Skill 的核心运行模型：**消费版本追踪 + 变更类型分流**，避免每次上游变动全量重做。

### 3.2 NFR 架构要素提取规则

**一句话**：本节讲从 bpl-nfr 提取 SysReq-NFR 要素的规则——量化指标生成（3.2.1，含分解规则）、分层约束判定（3.2.2）、Phase B 宿主匹配（3.2.3）、B/C 分工差异（3.2.4）。Phase B（修订已有 SysReq-NFR）与 Phase C（新建 SysReq-NFR）共用——先看 3.2.4 的 B/C 分工差异表，再读细节更顺。

下文 §3.2.1~§3.2.4 的提取规则同时适用于 Phase B（修订已有 SysReq-NFR）与 Phase C（新建 SysReq-NFR）。

#### 3.2.1 量化指标生成

**一句话**：逐 bpl-nfr 分类需求项生成量化指标；多对象指标按分解规则切子指标（四类运算）。

逐 bpl-nfr 分类需求项生成量化指标：

| 输入线索 | 处理 |
|----------|------|
| 规范化的相关方需求 明示数值或布尔约束 | 直接采信，记录来源 |
| 规范化的相关方需求 有比较词或质量方向 | 基于 22 具体需求模板和同类场景推断，标记 `[需裁决]` |
| 规范化的相关方需求 有验证语义但无目标值 | 生成测量方法和待确认目标值 |
| 无可验证线索 | 标记缺口，回退补充 NFR，不推进写回 |

量化输出必须包含指标名称、目标值/单位、统计口径、测量方法、验收条件、来源 bpl-nfr、22 具体需求判定和确认状态。

**分解规则**——逐条量化指标判定「约束对象」是否多对象（约束范围判定见 §3.2.2）。仅当一条量化指标需约束多个对象类型、且指标可按运算关系切分时，进行分解。分解运算四类（wft05-eng 消费、wft06 守恒核对的依据）：

| 分解运算 | 适用指标 | 预算方向 | 处理 |
|---------|---------|---------|------|
| **加法** | 响应时间等可切分指标 | Σ 子目标 ≤ 系统目标 | 按组件类型切预算：父指标 + N 条子指标（各约束对象类型），父→子引用标注；候选子预算基于 22 模板/同类场景推断，标 `[需裁决]`，人类确认后入约束包 |
| **乘法** | 可用性等可切分指标 | Π 子目标 ≥ 系统目标 | 按组件类型切可用性目标，父→子引用标注；候选子目标标 `[需裁决]` |
| **弱链** | 吞吐量/并发等 | 每子目标 ≥ 系统目标 | **不切预算**，逐对象类型指派（各承接全量） |
| **职责分布** | 安全/审计/权限/易用性等 | 无守恒 | **不切预算**，逐对象类型指派职责 |

**多对象识别**：约束对象类型按 91 §8.5 三类组件（前端/后端/平台服务）+ srb-biz/CU/页面级判定；一条指标同时影响多个对象类型时为多对象。加法/乘法指标的多对象情形生成子指标（组件类型级）；弱链/职责分布指标的多对象情形逐对象类型生成约束行、不切预算。**单对象指标不分解**，一条到底（保持原约束范围）。子指标目标到组件类型级，不预判具体组件（`待wft05映射`，见 §5.5）。**记录**：父指标记「分解运算 + 子指标引用」，子指标记「父指标引用 + 分解运算 + 目标对象类型」。

#### 3.2.2 分层约束判定

**一句话**：对每条量化指标判定约束范围（六类），确定消费目标。

对每条量化指标判定约束范围：

| 约束范围 | 判定线索 | 典型消费 |
|----------|----------|----------|
| 全局 | 影响 EOS 整体运行质量 | wft05-eng |
| 业务域 | 只影响某业务域或产品类型 | wft05-eng |
| srb-biz | 指向具体功能性系统需求 | wft05-eng |
| CU | 指向配置单元、配置规则或配置可达性 | wft05-eng |
| pa-eng组件 | 指向前后端组件类型、接口或运行机制 | wft05-eng |
| 页面级 | 指向七种页面类型之一、具体页面 ID、交互行为或页面体验 | wft05-eng |

#### 3.2.3 Phase B SysReq-NFR 宿主匹配检查

**一句话**：Phase B 修订已有 SysReq-NFR 时，按 `22 分类维度 + 约束对象 + 指标口径` 匹配已有宿主。

Phase B 修订已有 SysReq-NFR 时，按 `22 分类维度 + 约束对象 + 指标口径` 匹配已有宿主：

| 结果 | 判定 | 动作 |
|------|------|------|
| Q1 复用宿主 | 已有 SysReq-NFR 分类、约束对象和指标口径兼容 | 追加指标和追溯，标记 `[确认]` |
| Q2 扩展宿主 | 已有宿主可承载但边界需扩展 | 修订宿主，标记 `[变更]` |
| Q3 新建宿主 | 无合适宿主 | 新建 SysReq-NFR |
| 宿主冲突 | 多个宿主均可承载或语义不内聚 | 标记 `[需裁决]` |

#### 3.2.4 Phase B（修订）与 Phase C（新建）的提取差异

**一句话**：B/C 分工差异——判定范围、量化基线、宿主匹配、分层约束、22 重识别、变更传播六个维度。

| 维度 | Phase B 修订已有 SysReq-NFR | Phase C 新建 SysReq-NFR |
|------|---------------------------|------------------------|
| 判定范围 | SysReq-NFR 已承接的全部 bpl-nfr + 本轮新 bpl-nfr | 待聚合池本组 bpl-nfr |
| 量化指标基线 | 以已有量化指标清单为基线，仅扫描本轮新需求项 | 从零构建 |
| 宿主匹配 | 执行宿主匹配检查（§3.2.3），可能检出 Q1/Q2/Q3/宿主冲突 | 无需匹配，直接新建 |
| 分层约束 | 增量合并新指标 → 更新分层约束表行 | 全量判定（§3.2.2） |
| 22 重识别 | 合并重识别可能导致已有指标的 22 判定变更——标记 `[22判定变更]` 并附变更原因 | 全量判定，无此问题 |
| 变更传播 | 需输出变更影响声明（§4.2） | 写"首版，无变更" |

### 3.3 NFR 量化推断规则

**一句话**：本节讲逐指标的推断规则——量化指标推断（3.3.1）、页面 NFR 推断（3.3.2）、Phase B 关系检测（3.3.3）。以下推断规则对 Phase B/C 通用，承接 §3.2 提取的线索后执行量化、锁定和关系检测。

#### 3.3.1 量化指标推断

**一句话**：对每个 bpl-nfr 分类需求项提取线索 → 匹配 22 模板 → 生成六要素指标；信息不足标待确认。

对每个 bpl-nfr 分类需求项：

1. 提取待量化线索（数值、比较词、验证条件、约束对象线索）。
2. 匹配 22 具体需求模板和同类场景的指标口径。
3. 生成目标值/单位/统计口径/测量方法/验收条件。
4. 信息不足时标注 `待确认`，不得伪造确定值；能推断时标注 `[需裁决]` 并给出依据。
5. 判定 22 具体需求归属：复用/升级候选/新增/回退（§2.3.3）。

#### 3.3.2 页面 NFR 推断

**一句话**：当指标影响用户可感知页面行为时，必须生成页面 NFR。

当指标影响用户可感知页面行为时，必须生成页面 NFR：

| 页面线索 | 输出 |
|----------|------|
| 页面类型明确 | 绑定七种页面类型之一，说明约束行为 |
| srb-biz 明确 | 引用具体 srb-biz，并绑定功能表单/窗口标签页/配置页面等具体页面 ID |
| 只知道业务域 | 写业务域级页面约束，标记 `[需裁决]` |
| 影响辅助栏/分屏/下钻/面包屑 | 明确关联 91 的交互模型要素 |
| 影响权限/审计/安全提示 | 同时生成页面 NFR 条目和 eng 权限/审计实现约束，均装入 wft05-eng NFR 约束包 |

页面 NFR 条目包含九项：指标 ID / 页面类型 / 具体页面 ID（暂缺时标记待目标绑定）/ 约束内容 / 量化目标 / 测量方法 / 影响点 / 消费目标 / 确认状态。

#### 3.3.3 Phase B 量化指标关系检测

**一句话**：Phase B 修订时把本轮生成的量化指标与基线比对——六种关系（确认/无新增/指标口径变更/22判定变更/补充/过时）。

Phase B 修订已有 SysReq-NFR 时，宿主匹配通过后，将本轮生成的量化指标与 SysReq-NFR 已有量化指标清单比对。比对锚点为**指标名称+22分类维度匹配**。

> 内部细分结论写在变更影响声明的变更项说明字段中，方便下游追溯每条指标变化的细类。

| 关系 | 判定 | 处理（内部细分结论） |
|------|------|---------------------|
| 确认 | 指标匹配 + 22 分类一致 + 来源升级 | 追加 bpl-nfr 引用（`确认`） |
| 无新增 | 指标匹配 + 22 分类一致 + 所有来源已确认 | 增量合并口径/测量细节（`改进`） |
| 指标口径变更 | 指标匹配 + **目标值/统计口径/测量方法变化**（bpl-nfr 修订导致） | 更新指标定义 + 变更原因，不新增指标（`指标口径变更`） |
| 22 判定变更 | 指标匹配 + **22 具体需求判定不同**（合并重识别导致） | 更新 22 判定 + 变更原因（`22判定变更`） |
| 补充 | 指标不匹配 | 新增量化指标（`新增`） |
| 过时 | 基线已有指标 **未被**本轮需求项覆盖（需求项移除导致） | 追加说明"请确认是否移除"，保留该指标不删除——移除是架构决策，由人类在反馈中触发（`过时`） |

关系检测前先基于**全部 bpl-nfr 重新判定 22 归属**——新需求项可能改变指标特征导致 22 判定变更（表中 `22判定变更` 行）。

`[调整]` 是与关系类型正交的叠加标记：已有指标的目标值/统计口径/测量方法变化，在关系标记之外叠加 `[调整]`。

**共享指标一致性检查**（Phase B 修订完成后执行）：扫描所有涉及多引擎/多组件共享的量化指标（同一 SysReq-NFR 宿主内不同约束对象共享的指标），检查同一指标 ID 的目标值、统计口径和测量方法是否保持一致。不一致时以最新需求为准对齐，标记 `[共享指标对齐]` 并附原因。该检查是 `eng一致`（§3.4 完备性判据）闭环检查项的前置操作。

## 四、节点演进：生命周期与变更传播

**一句话**：本章讲 SysReq-NFR 节点设计与确认后的演进机制——双生命周期（4.1，bpl-nfr 侧 + SysReq-NFR 侧 + 上游变更分流）与变更传播（4.2，修订后写变更影响声明告诉下游 wft05-eng）。

### 4.1 SysReq-NFR 节点生命周期

**一句话**：本 Skill 同时管理两条生命周期线——上游 bpl-nfr（消费并推进）与自身 SysReq-NFR（产出），本 Skill 的写回范围见下。

wft04-nfr 同时管理两条生命周期线：bpl-nfr（上游节点，本 Skill 消费并推进）和 SysReq-NFR（本 Skill 产出节点）。通用模型见 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型)。

**bpl-nfr 侧**（wft01-nfr ←→ wft04-nfr）：

```
可以NFR设计 ──wft04锁定──→ 在NFR设计 ──wft04完成──→ 已NFR设计
     ↑                         │                         │
     │                         │               wft04退回  │
     │                         │                         ↓
     └─── wft01修订 ───── 需wft01修订 ←───────────────┘
```

**SysReq-NFR 侧**（wft04-nfr 产出 → 验证与 wft05-eng 消费）：

```
待确认方案 ──目标未就绪──→ 待目标绑定 ──完成绑定──→ 待确认方案
     │                                                   │
     └──────────────────人类确认+落账────────────────────→ 已验证冻结
                                                             │
                                               验证/消费退回   ↓
                              待确认方案 ←── wft04修订 ── 需wft04修订
```

**上游变更**（新 规范化的相关方需求 修订触发两条线的补全迁移）：

```
bpl-nfr 侧：已NFR设计 ──新规范化的相关方需求修订──→ 待补充NFR设计 ──wft04补全──→ 已NFR设计
SysReq-NFR 侧：已验证冻结 ──新规范化的相关方需求修订──→ 待补充NFR验证 ──wft04补全──→ 已验证冻结
```

**本 Skill 的写回范围**：SysReq-NFR `待确认方案` / `待目标绑定` / `待补充NFR验证` / `需wft04修订`。`在NFR设计` 由本 Skill 锁定期间设置，`已验证冻结` 由本 Skill 完成目标绑定、人类确认和落账后写入。

本 Skill 在首次消费 bpl-nfr 时记录 `bpl-nfr 消费版本：v{N}`；重入时若 bpl-nfr 当前版本大于消费版本，则读取变更影响声明并增量处理。

下游退回 `需wft04修订` 时：读取验证或消费方的缺陷说明 → 按人类改进方案修订 SysReq-NFR（走 Phase B 修订流程）→ 人类确认 → 重新推进。根因在 bpl-nfr 时退回 wft01-nfr。

### 4.2 SysReq-NFR 变更传播协议

**一句话**：每次修订已有 SysReq-NFR 后写变更影响声明——四类变更（无/增量/修订/结构）各告诉下游 wft05-eng 该怎么做（含约束包版本）。

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板、增量清单与变更影响声明的分工）见 [91 规范 §A.7](91-eos-biz-eng-spec.md#a7-变更传播协议)。

**本 Skill 的变更影响声明格式**，每次修订已有 SysReq-NFR 后写入 SysReq-NFR 节点末尾（`05-*.md` 中 SysReq-NFR 节点块内）：

```text

- [新增] / [变更] / [确认] / [需裁决] ...
  说明字段中记录细分原因：量化指标新增 / 指标口径变更 / 22判定变更 / 过时 / 宿主冲突等

对应 wft05-eng NFR 约束包：<约束包 ID / 包版本>
wft05-eng 消费状态：待消费 / 已消费 / 需重消费
wft05-eng 已消费版本：<包版本；未消费则写"尚未消费">

对 wft05-eng 已消费版本的影响：
  受影响约束行：<约束行 ID + 受影响原因>（指标口径变更 / 新增约束 / 失效约束等）
  不受影响约束行：<约束行 ID>

建议下游动作：
  - 无变更：无需任何动作，约束包保持有效
  - 增量型：wft05-eng 增量消费新增约束行即可
  - 修订型：修订受影响约束行的承接 → 标记 [来自上游变更]
  - 结构型：输出影响范围，等人类裁决后再处理；含分类维度变化时下游需重新匹配约束
```

## 五、操作流程

**一句话**：一次运行 = Step Start 入口路由 → Step 1 材料加载 → Step 2 反馈处理 → Step 3 非功能需求架构设计 → Step 4 页面与分层约束设计 → Step 5 闭环检查 → Step 6 资产落账与状态推进 → Step End 输出与对话反馈。反馈走自然语言对话（§5.3），跨轮余留由 AI 标记持久化（§5.3 状态机）。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 前置校验与路由 | 变更感知 + 入口检测、输入校验、退回优先路由 | 无（AI 自动） | 统一 | 就绪 / 结束 | — |
| 1 | 设计材料加载 | 安全复查 + 读 AI 可以处理节点 + 加载 bpl-nfr/05/22 资产 | 无（AI 自动） | 统一 | bpl-nfr / 05 / 22 / 06 / srb-biz与页面线索 | — |
| 2 | 方案反馈处理 | 读"待反馈处理"分节 + 对话处理人类修改意见 | **有**——对话反馈修改意见 / 整体确认 | 对话 | 调整后的 SysReq-NFR 方案 | `05` |
| 3 | 非功能需求架构设计 | 量化指标 + 22 具体需求候选 + 宿主匹配 | 无（AI 产出，之后对话反馈） | 统一 | SysReq-NFR + 量化指标 + 22 候选 | `05` |
| 4 | 页面与分层约束设计 | 分层约束表 + 页面 NFR + 下游约束包 | 无（AI 产出，之后对话反馈） | 统一 | 分层约束表 + 页面 NFR + 下游约束包 | `05` |

| End | 运行结束输出 | 三区摘要输出 + 等待人类反馈 | **有**——查看摘要、对话反馈 | 对话 | 人类下一步操作提示 | — |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话 = AI 输出后需要你说句话（反馈或确认）才继续。Step 1/3/4/5/6 为运行内自动步骤；Step 2 / Step End 为人机交互步骤（对话反馈，见 §5.3）。

**反馈机制一句话**：反馈走**自然语言对话**（AI 产出方案后不结束对话，§5.3）；跨轮余留反馈由 AI 标 `[修改]`/`[驳回]` 入"待反馈处理"分节（§5.3 状态机）；人类线下修订经 Step Start 变更感知（git diff，§5.1 变更感知）检出后纳入"待反馈处理"分节；AI 每轮写回提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

### 5.1 Step Start

**一句话**：先变更感知（检出人类线下修订并纳入待反馈分节），再按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策路由（退回优先 → 反馈处理 → 新输入），无待处理对象即退出。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 bpl-nfr）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

**入口判定**（在变更感知后执行）：按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策流程执行。先读取 `02-*.md`/`05-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表，再按以下顺序处理：

#### 5.1.1 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| bpl-nfr 状态不是 `可以NFR设计` / `待补充NFR设计` | 状态不符（硬退出） | 输出不合格节点及当前状态 → **退出** |
| bpl-nfr 分类边界或角色语境明显缺失 | 要素缺失（硬退出） | bpl-nfr → `需wft01修订`，输出缺失说明 → **退出** |
| 选中 bpl-nfr >5 个 | 超建议阈值（软提示） | 输出超限提示 → 人类确认后继续或退出 |
| 无任何入口条件满足 | 无待处理对象（硬退出） | 输出”无待处理对象”→ **退出** |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

#### 5.1.2 退回优先（§A.4.3 门禁）

存在 `需wft04修订` 的 SysReq-NFR 节点（来自”待下游退回处理”分节）：
- 读取退回节点的缺失说明，检查其中是否含人类标注（`[修改]` / `[同意]`）或下游 Skill 产出的具体改进指引
- 已提供 → 通过门禁，定位受影响 SysReq-NFR，进入 Step 2 按 SKILL 指南修订
- 未提供（仅含概括性退回原因或无人类标注）→ 输出缺失说明 + 提示提供改进方案 → **退出**

#### 5.1.3 反馈处理

存在”待反馈处理”分节中的 SysReq-NFR 节点（确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2 处理（§5.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 bpl-nfr，Step End 时提示。

#### 5.1.4 新 SysReq-NFR 路由

有未处理的 bpl-nfr 节点（来自”待 wft04-nfr 处理”分节）→ 进入 Step 1→Step 3，逐节点执行 Phase A 消费与变更感知，匹配已有 SysReq-NFR 宿主（§5.4.1）或进入待聚合池新建。

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 SysReq-NFR 的量化指标/分层约束/页面 NFR。Step 3 的 Phase C 宿主匹配必须基于 Step 2 修改后的最新 SysReq-NFR 内容，不得使用缓存旧状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

### 5.2 Step 1 · 设计材料加载

**一句话**：把本轮要处理的材料加载齐——先安全复查（git diff 检非预期修改），再读 AI 可以处理节点，最后按需索引导航。变更感知已在 Step Start 完成（§5.1）。

加载产品数据与资产文档遵循 [91 规范 §A.3.3](91-eos-biz-eng-spec.md#a33-产品数据文档与资产文档读取与写回约定) 的统一读取协议：AI可以处理节点优先 → 索引导航。

**步骤一：安全复查**

Step Start 已检出人类反馈并纳入"待反馈处理"分节（§5.1 变更感知）。此处按 §A.3.3 R0a 做加载前安全检查：`detect-changes.sh` 检出人类非预期修改时标记 `[需确认]`，不自动推进。

**步骤二：优先读取**（通过 `## AI可以处理节点` 定位本轮入口）：

入口判定通过后（§5.1.1），从 `## AI可以处理节点` 对应分节获取待处理节点 ID 列表：
- 有新输入 → 读「待 wft04-nfr 处理」分节
- 有待处理反馈 → 读「待反馈处理」分节
- 有下游退回 → 读「待下游退回处理」分节

逐节点：Bash("grep -n '@{节点ID}' 目标文件") 定位行号 → Read 节点块。

**步骤三：索引导航**（AI可以处理节点无待处理时，或按域浏览时）：

1. Bash("grep -n '索引行数：' 目标文件") → 定位索引行号 L
2. 从 L 提取 N → Read 业务域索引
3. 按锚点 Read 域内索引 → 获取节点 ID 列表
4. 按需：Bash("grep -n '@{节点ID}' 目标文件") → 定位行号 → Read 节点

**加载清单**（按需扩大 - 仅在索引缺失、候选冲突、资产全貌不足以判断边界或追溯关系断裂时）：

1. `02-*.md` STR 树画像 / 状态队列 / 节点索引 — 定位本轮 bpl-nfr 正文块（含角色语境、分类需求清单、适用对象线索）
2. `05-*.md` SysReq 树画像 / 状态队列 / 节点索引 — 定位已有 SysReq-NFR 节点块，同时读取 srb-biz 节点 ID 清单和页面/功能线索
3. `06-*.md` 系统需求概要索引 — 定位写入目标
4. `22-eos-nfr-taxonomy.md` — NFR 分类维度/具体需求/候选条目清单（运行时动态读取，不缓存）
5. `25-eos-engine-models.md` — 引擎/CU 类型/布局组件/构件和页面生成线索（只读）
6. `91-eos-biz-eng-spec.md` — 页面类型、辅助栏、分屏下钻、CU/构件关系和通用协议
7. `11-eos-nfr-constraint-package.md` — 已有 wft05-eng NFR 约束包（Phase B 修订已有 SysReq-NFR 时读取：约束行 ID / 上一版本 / 消费状态）

**按需扩大规则**（[91 规范 §11.12](91-eos-biz-eng-spec.md#1112-按需读取规则)）：

- bpl-nfr / SysReq-NFR 正文块 — 按 ID 从索引定位
- 候选 SysReq-NFR 块 — 按同 22 分类维度/同约束对象/同指标口径筛选，用于宿主匹配
- 反馈重入 — 仅读取条目的确认状态字段及反馈指向块，不做全量重读
- 扩大触发：索引缺失 / 候选冲突 / 资产全貌不足以判断边界 / 追溯关系断裂时

> 禁止行为：不得在常规 Step 运行中默认加载完整文件正文；不得将 `疑似` 或 `待确认` 节点的 ID 作为下游强依赖（§A.3.3 R3）。

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `05-*.md`/`06-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.7），保证下一轮 diff 只含人类变更。

**本 Skill 的条目**：量化指标 + 分层约束表行 + 页面 NFR + 22 写回项 + 06 详细定义。各条目的 `确认状态` 字段位于 `05-*.md` SysReq-NFR 节点块各条目正文中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3~4 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.3）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足 bpl-nfr 需求 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 满足冻结条件则推进 SysReq-NFR → `已验证冻结` → **提交基线并更新 HEAD（机制见 §5.7，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

> **原则**：反馈处理不是对人类标注的机械执行，而是以 bpl-nfr 分类需求清单为锚点的方案修订。AI 在 Step 2 中与 Step 3~4 同为设计者——先理解人类反馈在 bpl-nfr 需求语境中的含义，再执行修订，最后检查修订后的 SysReq-NFR 是否仍满足 bpl-nfr 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 本 Skill 的锚点是 bpl-nfr 分类需求清单——反馈处理以 bpl-nfr 需求理解为锚，不脱离上游需求内容自行修订 |
| **操作条目** | 量化指标 + 分层约束表行 + 页面 NFR + 22 写回项 + 06 详细定义。各条目的 `确认状态` 字段写入 `05-*.md` SysReq-NFR 节点的对应条目中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → SysReq-NFR → `已验证冻结`，bpl-nfr → `已NFR设计`。存在 `[修改]`/`[驳回]` 且无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需进入 Step 3~4 重做 |
| **清除条件** | 已有 `[同意]`+`[已处理]` 默认跳过。仅当本轮新输入满足**任一**条件时清除 `[已处理]`（保留 `[同意]`）：<br>1. 新输入为该条目的直接上游节点（如新 bpl-nfr 分类需求项是量化指标/页面 NFR 的来源）<br>2. 新输入与条目同属一个架构层级且边界重叠（如同属一个 SysReq-NFR 宿主，新需求项改变已有条目的范围或归属）<br>3. 新输入导致条目定义被修订（变更影响声明标注为修订型/结构型，§A.5.3 Step 1） |
| **级联触发条件** | 量化指标或被驳回/修改导致指标口径变更、分层约束拓扑变化或 22 判定变更 → 触发需求级联检查（重验修改后 SysReq-NFR 是否仍满足 bpl-nfr 需求）→ 通过后触发资产对齐级联 |

### 5.4 Step 3 · 非功能需求架构设计

**一句话**：核心设计步——Phase A 消费感知与宿主匹配（§5.4.1），Phase B 修订已有 SysReq-NFR（§5.4.2），Phase C 从零新建（§5.4.3）。

设计规则来源：本节 Phase A~C 引用的提取规则见 §3.2、量化推断规则见 §3.3、宿主匹配规则见 §3.2.3、变更声明见 §4.2。

#### 5.4.1 Phase A：bpl-nfr 消费感知与宿主匹配

逐 bpl-nfr 检查消费版本——首次消费→全量设计，版本递增→按变更声明执行增量/修订/结构型分流；分类边界或角色语境不足→退回 wft01-nfr。版本确认后，按 22 分类维度 + 约束对象 + 指标口径匹配已有宿主：

| 条件 | 路由 |
|------|------|
| 已有 SysReq-NFR 分类维度 + 约束对象 + 指标口径兼容 | 归入该宿主 → Phase B |
| 不满足 | 进入待聚合池 → Phase C |
| 多个宿主均可承载或语义不内聚 | 标记 `[需裁决]` |

待聚合池按**同一 22 分类维度 + 同一约束对象类型**分组（`{22分类维度, 约束对象类型, bpl-nfr列表}`）。此阶段仅粗略分组，量化指标生成和完整要素提取在 Phase C 执行。

#### 5.4.2 Phase B：修订已有 SysReq-NFR

1. **要素提取**：从 bpl-nfr 分类需求清单提取待量化线索、适用对象线索和 22 分类路径。已有指标口径仅追加不重定
2. **宿主匹配检查**：确认 bpl-nfr 需求仍在 SysReq-NFR 宿主范围内。Q1→追加指标和追溯；Q2→修订宿主+变更声明；宿主冲突→标记 `[需裁决]`。Phase A 匹配是候选筛选、Phase B 是精确匹配——宿主扩展时不得回退 Phase A 重选宿主，继续完成 Phase B 并标记 `[推断]` 供人类裁决
3. **重判定与关系检测**：基于全部 bpl-nfr 重新量化指标，比对已有基线判定六种关系（§3.3.3）。新增/变更指标→更新分层约束表行；影响页面体验→生成页面 NFR；22 判定变更→更新具体需求归属
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 SysReq-NFR 节点末尾

#### 5.4.3 Phase C：新建 SysReq-NFR

1. **确定 22 分类路径** → 一级类目 → 分类维度 → 具体需求归属判定
2. **生成量化指标** → 逐需求项提取待量化线索 → 匹配 22 模板和同类场景 → 目标值/单位/统计口径/测量方法/验收条件。信息不足时标注 `待确认`，不伪造确定值
3. **判定分层约束** → 六类约束范围 → 适用链路 → 约束对象 → 消费目标 → 影响级别 → 影响点
4. **生成页面 NFR** → 影响用户可感知页面行为时绑定页面类型/srb-biz/业务域 → 约束内容 → 量化目标 → 测量方法 → 消费目标
5. **装配分层约束包** → 生成唯一的 wft05-eng NFR 约束包，按全局/业务域/srb-biz/页面级/CU/pa-eng 组件/共享七组独立组织，引用分层约束表行
6. **组装 SysReq-NFR** → 22 分类路径 + 量化指标清单 + 分层约束表 + 页面 NFR + 22 写回项 + 06 引用，写入 `05-*.md`

### 5.5 Step 4 · 页面与分层约束设计

**一句话**：对每个 SysReq-NFR 实例执行分层约束设计——分层约束表生成（1）、页面 NFR 生成（2）、wft05-eng 约束包装配（3）、要素机械检查（4）。

Step 4 按每个 SysReq-NFR 实例独立执行。新建 SysReq-NFR → 全量设计；修订已有 SysReq-NFR → 仅当量化指标或约束范围变更时重验分层，要素机械检查始终针对变更节点执行。

**1. 分层约束表生成**

基于 Step 3 产出的量化指标，对每条指标按 §3.2.2 的约束范围判定表判定分层（全局/业务域/srb-biz/CU/pa-eng组件/页面级）。每条分层约束记录约束行 ID、约束范围、约束对象、量化指标引用、影响级别和消费目标。无法确定约束范围时标注 `[推断]`。

**2. 页面 NFR 生成**

当指标影响用户可感知页面行为时，按页面线索逐条生成页面 NFR——线索→输出映射按 §3.3.2 页面 NFR 推断判定，页面类型与典型维度见 §2.3.2。每个页面 NFR 写入九项：指标 ID / 页面类型 / 具体页面 ID（或待目标绑定）/ 约束内容 / 量化目标 / 测量方法 / 影响点 / 消费目标 / 确认状态。所有页面 NFR 标注 `[推断]`，经由人类确认后方可落账。

**3. wft05-eng NFR 约束包装配**

Step 4 末尾生成一个且仅一个 wft05-eng NFR 约束包，只引用分层约束表行 ID 和页面 NFR 条目，不复制正文。分解后的子指标（§3.2.1）作为独立约束行装配，标注「分解运算 + 父指标引用」。`适用链路=biz/eng/共享` 表示约束影响的业务、平台或共享语境，不表示 NFR 直接流向 biz 路径。

约束包头必须记录：`约束包 ID`、`包版本 vN`、`生成时间`、`来源 SysReq-NFR ID/版本`、`上一版本`、`变更类型（首版/无变更/增量型/修订型/结构型）`、`新增行`、`修订行`、`删除/失效行`、`消费目标=wft05-eng`、`消费状态（待消费/已消费/需重消费）`、`wft05-eng 已消费版本`。消费状态与已消费版本由 wft05-eng 消费后回写（本 Skill 发布时写 `待消费`，不自行置 `已消费`）。

约束包正文按以下七组分别列示，不合并业务域与 srb-biz：

1. 全局约束
2. 业务域约束
3. srb-biz 约束
4. 页面级约束（页面对象 + 指标 ID + 约束行 ID）
5. CU 约束（目标引擎 + CU 类型 + 指标 ID + 约束行 ID）
6. pa-eng 组件约束（组件类型 + 指标 ID + 约束行 ID）
7. 共享约束

首版包版本为 `v1`、变更类型为 `首版`、消费状态为 `待消费`。后续包版本必须递增并声明相对上一版本的新增、修订、删除/失效行；若 wft05-eng 已消费旧版且存在有效变化，消费状态写为 `需重消费`。

**首版发布门禁**：全局/共享约束可以没有具体对象 ID；业务域约束必须绑定业务域；bpl-biz/bpl-eng/CU/页面级约束必须绑定已存在的目标 ID。pa-eng 组件级约束在 PA 尚未生成时只记录组件类型与映射条件，标记 `待wft05映射`，不得虚构 PA ID。存在未满足上述条件的阻断型约束时，SysReq-NFR 保持 `待目标绑定`，不得发布首版约束包。

**4. 要素机械检查**（逐 SysReq-NFR，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 每条量化指标的约束范围 **已判定**，约束行 ID/约束对象/影响级别/消费目标 **已记录**
- [ ] 影响用户可感知页面行为的指标 **已生成**页面 NFR
- [ ] 每个页面 NFR 的九项要素 **齐全**
- [ ] 下游约束包装配视图 **已生成**，只引用行 ID 不复制正文
- [ ] wft05-eng 消费包覆盖的约束范围 **无遗漏**
- [ ] 约束包 ID、版本、上一版本、变更类型、增量清单和消费状态 **已记录**

### 5.6 Step 5 · 闭环检查与变更声明

**一句话**：对每个 SysReq-NFR 执行七项闭环检查 + 缺口处理 + 要素机械检查 + 变更影响声明。

Step 5 按每个 SysReq-NFR 实例独立执行。新建 SysReq-NFR → 全量检查；修订已有 SysReq-NFR → 仅当量化指标、约束范围或页面 NFR 变更时重验闭环，要素机械检查始终针对变更节点执行。

**1. 闭环检查**

- [ ] 宿主唯一：每条 bpl-nfr 分类需求项有唯一 SysReq-NFR 宿主
- [ ] 分层正确：全局/业务域/srb-biz/CU/pa-eng组件/页面级未错层
- [ ] 页面可消费：影响页面体验的 NFR 已生成页面级约束
- [ ] eng 一致：不同引擎/组件间共享指标保持同一指标 ID、目标值和测量方法
- [ ] 22 可落账：具体需求写回项指标集完整、分类路径明确
- [ ] 06 可验证：详细定义包含来源、指标、测量、验收和追溯

**2. 缺口处理**

| 类型 | 典型场景 | 动作 |
|------|---------|------|
| 可当场补齐 | 指标定义不全 / 约束范围未判定 / 页面 NFR 缺失 | 本 Skill 内补齐后重验 |

**3. 要素机械检查**（逐 SysReq-NFR，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 缺口处理 **已分流**，无未裁决的边界情况
