## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| 接收FR-ENG 规范化的相关方需求节点（≤10条），校验类型/状态/主责能力域 | FR-BIZ 业务场景和输出文档设计 → `wft01-biz` |
| 识别主责能力域（引擎专属/平台共享）+ 配置/治理目标 + 可独立验收结果 | NFR 分类与量化 → `wft01-nfr` / `wft04-nfr` |
| 按三元组（能力域+目标+验收结果）匹配已有 bpl-eng | 配置信息组的操作活动定义（配置操作/系统处理/运行期能力）→ `wft02-eng` |
| 名称级识别配置信息组候选 + 分解为配置信息组（框架说明，业务流程框架末级节点；结构判定级）+ 分配配置信息组到 CU 承接（含收敛判定/骨架判定）+ 构建能力链 + 完备性检查 | 系统需求框架（功能表单+框架说明）→ `wft03-eng`；系统需求概要（功能表单组件及其业务）→ `wft04-eng` |
| 装配 R 上下文（支撑 CU 来源判定与追溯链前端锚点） | 前后端组件、接口和实现边界 → `wft05-eng` |
| 检出能力链缺口 → 生成补充 FR-ENG 材料 | 操作活动定义展开 → `wft02-eng`（业务流程概要）承接已分配 CU 详设 |
| 人类确认后推进 bpl-eng→`可以详细定义` + 规范化的相关方需求→`已分配` | — |
| 接收 wft02-eng 退回的 `需wft01修订` bpl-eng，按 SKILL 指南修订 | — |

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | 规范化的相关方需求预处理（`or03`） | FR-ENG 规范化的相关方需求节点 写入 `01-*.md`，状态=`待处理`。通过 `## AI可以处理节点` 的"待 wft01-eng 处理"分节检测。wft03-biz 产生的 FR-ENG 候选线索须先经人类确认+完整通过 or00→or03 才能进入 |

| 同级 | `wft01-biz`、`wft01-nfr` | 各自处理 FR-BIZ / NFR，本 Skill 输入校验检出后退出并提示路由 |

## 二、操作流程

### Step Start · 前置校验与路由

**变更感知**（先于入口检测，检出人类线下修订）：

```bash
bash ../.scripts/detect-changes.sh ../../../80-pl4eos-2-eosdata/01-eos-specified-requirements.md
bash ../.scripts/detect-changes.sh ../../../80-pl4eos-2-eosdata/02-eos-business-summary-architecture.md
```

检出 `HAS_CHANGES=1` → AI 检查变更行，判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入"待反馈处理"分节；自由文本 → 标记 `[需确认]`；格式/排版 → 忽略。**先变更感知再入口判定**——纯线下修订若不先检出，会被误判"无待处理对象"退出（详见 human spec §5.1 变更感知）。

**入口检测**（按 [91 规范 §A.4](../91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)）：

```bash
bash ../.scripts/read-section.sh ../../../80-pl4eos-2-eosdata/01-eos-specified-requirements.md "AI可以处理节点"
bash ../.scripts/read-section.sh ../../../80-pl4eos-2-eosdata/02-eos-business-summary-architecture.md "AI可以处理节点"
```

**输入校验**（按顺序，命中即退出）：

| 条件 | 判定 | 动作 |
|------|------|------|
| bpl-eng 状态=`需wft01修订` 且人类未提供改进方案 | 退回方案缺失 | 输出 wft02-eng 缺失说明 → **退出** |
| 规范化的相关方需求 状态≠`待处理` | 不可处理 | 输出当前状态 → **退出** |
| 规范化的相关方需求 类型为 FR-BIZ | 路由错误 | 输出类型分布 + 路由指引（→ `wft01-biz`）→ **退出** |
| 规范化的相关方需求 类型为 NFR | 路由错误 | 输出类型分布 + 路由指引（→ `wft01-nfr`）→ **退出** |
| 规范化的相关方需求 为业务配置实例 | 不适用 | 标记并提示 → **退出** |
| 规范化的相关方需求 是 wft03-biz 线索但未转规范化的相关方需求节点 | 未正式化 | 提示先确认并写入 `01-*.md` → **退出** |
| 规范化的相关方需求 无法判定唯一主责能力域或独立验收结果 | 归属不明 | 标记 `需澄清` → **退出** |
| 规范化的相关方需求 >10 条 | 软提示 | 输出超限提示 → 人类确认 |
| 无任何待处理 | — | 输出"无待处理对象"→ **退出** |

**退回优先**：存在 `需wft01修订` bpl-eng → 检查人类是否提供改进方案。已提供 → 读取缺失说明，走 Phase B 修订。未提供 → 输出缺失说明 → **退出**。

### Step 2 · 方案反馈处理

**触发条件**：Step Start 检出 `需wft01修订` bpl-eng，或上一轮 Step End 的反馈等待中人类提出修改意见。

**反馈双轨**（人类任选其一，详见 SKILL 指南 §5.3）：①AI 对话反馈——Step End 后不结束对话，直接回复修改意见，AI 即时处理；②线下文档修订——打开 `01/02-*.md` 在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]` 或直接编辑方案内容（自由文本），经 Step Start 变更感知 git diff 检出后按 §A.5 处理。两轨等价均落账（追 `[已处理]`）。

**处理规则**：

1. 从当前轮次对话或退回缺失说明中读取人类反馈意图
2. **逐条处理**——AI 输出方案后人类直接回复 → 当前轮次继续；wft02 退回 → 下一轮走 Step Start 退回优先
3. 修改后检查是否仍满足 规范化的相关方需求 需求
4. 结构性变更（边界/能力链/分解分配重组）→ 按需重入 Step 3
5. 全部条目获认可 → bpl-eng → `可以详细定义`
6. **元信息维护**：

```bash
bash ../.scripts/update-meta.sh ../../../80-pl4eos-2-eosdata/02-eos-business-summary-architecture.md bump-version
bash ../.scripts/update-meta.sh ../../../80-pl4eos-2-eosdata/02-eos-business-summary-architecture.md update-head
```

**AI 处理反馈规则**：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令 | 定位条目 → Edit 修改 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论 | 解释理由，不自动修改，继续等待决策 |
| 整体确认 | 全部条目追加 `[同意] [已处理]` → **整理反馈总结** → 推进状态 → Step 5 落账 → 结束 |
| 模糊意见 | 尝试具体化追问 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

### Step 3 · 场景业务设计

#### Phase A — 规范化的相关方需求 溯源与路由

对每条新 规范化的相关方需求：
1. 提取触发来源、能力诉求、运行期结果、主责能力域（详见 human spec §3.2.1）
2. **路径归属判定**——规范化的相关方需求 实际为业务文档/流程 → 退回 `wft01-biz`；规范化的相关方需求 为性能/安全等约束 → 退回 nfr 路径；规范化的相关方需求 仅为配置数据 → 标记不进入
3. **宿主匹配**——规范化的相关方需求 的三元组（主责能力域+配置/治理目标+独立验收结果）落入已有 bpl-eng → Phase B；否则 → 待聚合池 → Phase C

待聚合池按**主责能力域（引擎）**分组。

#### Phase B — 修订已有 bpl-eng

1. **要素提取**——从本轮 规范化的相关方需求 提取触发来源、能力诉求、运行期结果、主责能力域
2. **场景匹配检查**——确认 规范化的相关方需求 与 bpl-eng 的三元组一致（详见 human spec §3.2.4）：

| 匹配结果 | 动作 |
|---------|------|
| 场景匹配（三元组一致） | 进入 CU 承接关系检测 |
| 同域不同场景 | 匹配其他 bpl-eng 或触发 Phase C 新建 |
| 共享依赖 | 写入依赖关系，不复制 CU |
| 主责不匹配 | 退回待聚合池 |

3. **分解分配重识别**——从本轮 规范化的相关方需求 重新名称级识别并分解配置信息组（框架说明）（§3.3.1）、重分配 CU 承接（收敛判定，§3.3.2），再执行 CU 承接关系检测——比对已有基线，判定确认/无新增/引擎归属变更/补充/过时（详见 human spec §3.3.4）：

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | CU匹配+引擎相同+来源非规范化的相关方需求明示 | 来源升级 |
| 无新增 | CU匹配+全部已规范化的相关方需求明示 | 追加引用+增量合并 |
| 引擎归属变更 | CU匹配+引擎不同 | 更新引擎+变更原因 |
| 补充 | CU不匹配 | 新增到候选清单 |
| 过时 | 基线CU未被本轮覆盖 | `[过时]`+保留不删 |

4. **变更影响声明**——判定变更类型，写入 bpl-eng 节点末尾

#### Phase C — 新建 bpl-eng

1. **确定主责能力域**——从 规范化的相关方需求 语义提取，判定为引擎专属或平台共享
2. **定义能力场景范围**——配置/治理目标 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认（终点=规范化的相关方需求 显式覆盖、不得在终点后扩展，详见 human spec §3.2.3）
3. **构建能力链**——按四段排列（配置意图→系统处理→运行期产出→可用确认）
4. **装配 R 上下文**——从 规范化的相关方需求 触发来源与 23/24 资产装配业务运行对象/配置角色/触发事件/状态影响（详见 human spec §3.2.2）
5. **分解为配置信息组（框架说明）**——名称级识别配置信息组候选，逐候选按"可以运行的能力"分解为配置信息组（框架说明，业务流程框架末级节点；结构判定级），逐候选标注来源类型、粒度判断（详见 human spec §3.3.1）
6. **分配配置信息组到 CU 承接**——逐配置信息组找 CU 承接（1:1），执行收敛判定（复用/新增/拆分/合并）+ 对照 25 盘存骨架判定（复用/改进/新增）+ 引擎归属判定（详见 human spec §3.3.2~§3.3.3）
7. **标注 规范化的相关方需求 类型**——逐条 规范化的相关方需求 判定五种 FR-ENG 规范化的相关方需求节点 类型之一（配置生成类/构件扩展类/布局组件扩展类/横切治理类/运行支撑类），不用于划分 bpl-eng 边界
8. **组装 bpl-eng**——写入 `02-*.md`，完整要素见 human spec §2.1.2

### Step 4 · FR-ENG 需求增补

按每个 bpl-eng 独立执行。新建 → 全量检查；修订 → 仅当能力链拓扑变化时重验闭合。

**1. 能力链闭合检查**——四段：配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认。配置/治理意图段缺失→`补充规范化的相关方需求`；系统处理要求段缺失→`补充规范化的相关方需求`；运行期制品/构件/功能段缺失→`补充规范化的相关方需求`；可用性确认段缺失（判据不明确）→`澄清项`。

**2. 分解分配完备检查**（前置门禁·追溯完整）——每个配置信息组（框架说明）已分配 CU；每条 CU 承接可追溯 bpl-eng 与 规范化的相关方需求；需求侧无锚的缺口 CU 已生成补充 FR-ENG 材料；每个 CU 承接的配置信息组（框架说明）清单可覆盖其全部能力点（详见 human spec §3.4/§5.5）。

**3. 要素机械检查**——引擎名称/场景边界非空、R 上下文已装配、能力诉求/运行期结果有标注、追溯链（规范化的相关方需求→bpl-eng→配置信息组（框架说明）→CU 承接）完整、配置信息组候选清单非空且逐条标注来源类型和粒度判断、配置信息组（框架说明）已分解、CU 承接关系完整、变更影响声明已写入。

## 附录A：判据速查

### A.1 bpl-eng 归组三元组 + FR-ENG 规范化的相关方需求节点 五种类型

**归组锚点**：`主责能力域 + 配置/治理目标 + 可独立验收结果`。主责类型分引擎专属和平台共享。

**规范化的相关方需求 类型**（不用于划分 bpl-eng 边界，仅作 规范化的相关方需求 级特征标注）：

| 类型 | 触发源 | 场景终点 |
|------|--------|---------|
| 配置生成类 | 配置人员提出或维护引擎配置 | 配置通过校验并在运行期生效 |
| 构件扩展类 | 业务页面需要新增构件能力 | 目标布局组件可渲染该构件 |
| 布局组件扩展类 | 现有布局组件无法承载 | 新/扩展组件可被引擎调用 |
| 横切治理类 | 权限/审计/版本等治理需要 | 横切规则对目标对象稳定生效 |
| 运行支撑类 | 业务页面需要引擎能力调用 | 引擎能力可被调用并产生可追溯结果 |

### A.2 能力链四段

```
配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认
```

### A.3 CU 候选来源类型

| 来源类型 | 性质 | 含义 |
|---------|------|------|
| `规范化的相关方需求明示` | 需求侧 | 规范化的相关方需求 文本直接说出该 CU |
| `规范化的相关方需求隐含` | 需求侧 | 不推出该 CU 则能力链存在逻辑缺口 |
| `构件缺口推断` | 需求侧 | 现有构件无法满足，推断需要新构件配置 CU |
| `布局组件缺口推断` | 需求侧 | 现有布局组件无法承载，推断需要新布局组件配置 CU |
| `同类引擎推断` | 资产侧·模式参照 | 同引擎类型已有 bpl-eng 的类似 CU 模式 |
| `模型线索推断` | 资产侧·复用承接 | 25 资产已有匹配 CU 定义（需求已锚定时承接，不构成需求证据） |

> 非 `规范化的相关方需求明示` 来源均标注 `[推断]`。资产侧参照（`同类引擎推断`/`模型线索推断`）不构成需求证据，不得单独作为缺口 CU 的承接依据（SKILL 指南 §3.1 缺口锚定边界）。

### A.4 CU 候选粒度判断

| 判定 | 说明 |
|------|------|
| `可展开` | 粒度适合 wft02-eng 直接展开 |
| `过粗待拆` | 需要拆分为多个独立 CU |
| `过细待并` | 应合并到已有 CU |
| `边界待确认` | 与已有 CU 的边界不清 |

> **骨架判定**（对照 25 盘存，与来源类型/粒度判断并行标注 `[推断]`）：`复用` = 25 已有类型承接；`改进` = 扩展已有类型能力边界；`新增` = 盘存无承接，需设计新 CU 类型或新引擎——**人机协同设计决策点**：AI 基于语义理解提建议附判据理由 → 人类审核/思考/决策/反馈 → AI 落实（详细设计由 wft02-eng 展开）。25 是记录层，不裁决。

### A.5 Phase B 场景匹配结果

| 结果 | 判定 | 动作 |
|------|------|------|
| 场景匹配 | 三元组一致 | 进入 CU 承接关系检测 |
| 同域不同场景 | 能力域相同但目标/验收不同 | 匹配其他 bpl-eng 或新建 |
| 共享依赖 | 能力由已有共享 bpl-eng 提供 | 写入依赖关系，不复制 CU |
| 主责不匹配 | 规范化的相关方需求 归属其他能力域 | 退回待聚合池 |

### A.6 Phase B CU 承接关系检测

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | CU匹配+引擎相同+来源非规范化的相关方需求明示 | 来源升级 |
| 无新增 | CU匹配+全部已规范化的相关方需求明示 | 追加引用+增量合并 |
| 引擎归属变更 | CU匹配+引擎不同 | 更新引擎+变更原因 |
| 补充 | CU不匹配 | 新增到候选清单 |
| 过时 | 基线CU未被本轮覆盖 | `[过时]`+保留不删 |

### A.7 bpl-eng 完备性判据

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 能力链闭合 | 配置意图能走到运行期可用 | 生成补充 FR-ENG |
| 主责归属明确 | 只有一个主责能力域 | 标记 `需澄清` |
| 场景可独立验收 | 目标和结果可独立判定 | 合并或降为依赖 |
| 共享不重复 | 共享 CU 只在共享 bpl-eng 定义一次 | 删除重复 CU |
| 分配完备（前置门禁·追溯完整） | 每个配置信息组（框架说明）已分配 CU；每条 CU 承接可追溯 bpl-eng 与 规范化的相关方需求 | 无锚配置信息组走补充 FR-ENG 回路 |
| 配置信息组清单完整 | 每个 CU 承接的配置信息组（框架说明）清单可覆盖其全部能力点 | 补充分解或标记 `[需裁决]` |
| CU 可展开 | CU 承接足以让 wft02-eng 定位并详设 | 标记 `[需裁决]` |
| 缺口层级正确 | 构件/布局组件/CU 级区分清楚 | 改写缺口说明 |
