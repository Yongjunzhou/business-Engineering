P0 是平台引擎产品，归属流程与 IT 域。构件为引擎，末级节点为配置信息组（CU 为 PL4 可独立选配的配置单元，由配置信息组构成，对齐 91 §3.1 P0 PL 树）。P0 产品定义见 [91 规范 §5.1](91-eos-biz-eng-spec.md#51-a1产品)，CU 功能本质见 [91 规范 §3.3](91-eos-biz-eng-spec.md#33-配置单元) 与 [§4.3](91-eos-biz-eng-spec.md#43-cu-与布局组件及构件的对应关系)，eng 路径分工见 [91 规范 §8.2](91-eos-biz-eng-spec.md#82-业务流程开发wft02-eng)。

```text
流程与 IT 域
  → P0 平台引擎产品
    → 引擎（@engine-xxx）
      → CU（配置单元 · PL4 选配单元）
        → 配置信息组（PL5 · P0 产品树末级）
```

CU 是引擎内可独立选配的配置单元（PL4），由若干配置信息组（PL5，P0 产品树末级节点）构成——每组提供一项可独立交付/验收的能力。按 91 规范，CU 定义一组可配置能力：配置人员通过后续功能表单维护各组配置信息；系统校验并保存；运行时，引擎按 CU 定义生成或渲染制品、构件及其功能。本 Skill 承接已分配 CU，逐配置信息组定义操作活动定义（配置操作/系统处理/运行期能力），不设计具体页面。

#### 2.2.1 定义与详细设计要素（操作活动定义）

每个 CU 用以下要素定义其配置能力。**CU 的配置信息组清单+结构判定级框架说明由 wft01-eng 在框架设计时产出**（每个配置信息组 = **某组配置字段，这组字段共同提供一个可以运行的能力**），本 Skill 承接该清单+框架说明并**展开每组为操作活动定义**——配置操作、系统处理、运行期能力均以配置信息组为单位、按**步骤化三段式**说明（基准=PDF v1.5.2）；配置入口与 FR-ENG 性能指标留在 CU 级。叙事链为”配置人员操作 → 系统处理 → 业务人员操作”。

**CU 级要素**：

| 要素 | 定义口径 | 描述方式 |
|------|---------|---------|
| 配置入口 | 配置人员在哪个配置页面维护该 CU（一个 CU 对应一个页面；复合页内的子页面即完整页面） | 页面职责、配置对象、配置类别；不设计具体 UI 布局 |
| FR-ENG 性能指标 | CU 配置后运行期需达到的性能指标 | 以可验证方式描述（定量指标或二元判定）；供 wft03-eng 系统需求框架、wft05-eng 平台产品架构承接指标输入；不设计实现 |

**配置信息组级要素——操作活动定义**（每个配置信息组按以下三方面、步骤化说明）：

| 要素 | 定义口径 | 描述方式 |
|------|---------|---------|
| 配置操作 | 配置人员如何编辑该组配置信息 | **以步骤序列说明**——从配置入口到提交的完整步骤序列，每步含**操作对象+约束+联动**（如”在画布选中节点→填名称/类型→校验→点确定”）；**配置信息组标题=组名+字段全集（含枚举）** |
| 系统处理 | 系统内部如何处理该组配置信息 | ① **编辑时处理**——设计会话中编辑该组时系统如何**校验→写载件→阻断**（对齐统一保存机制，§2.2.1 注）；② **生效后响应**——该组配置信息随版本发布装载后系统应①…②…③…：装载→界面反馈→运行期语义，**载件类型显式标注**（配置/数据/界面/构件/实例/支撑）；不写实现算法 |
| 运行期能力 | 系统基于该组配置信息为业务人员提供的能力 | **以业务人员操作过程说明**（操作页面 + 操作处理，**分支规则显式化**——如”通过→…；驳回→…；事件→…”）；**提供业务人员可操作能力的组必填**，以系统处理为主的组显式标注 |

**主语判据**：配置操作主语=配置人员、系统处理主语=系统、运行期能力主语=系统对业务人员交付。系统处理与运行期能力的分水岭在**对内/对外**——系统处理是系统内部行为（校验、事件触发、超时调度、状态维护），运行期能力是系统对外交付、业务人员可感知可操作的能力。

> **统一保存机制**（对齐 PDF v1.5.2，2026-08-19 定，全 bpd-eng 适用）：流程设计采用”设计会话+全局保存”模型，配置保存分三类粒度——**标量/父级配置**（节点基本信息、办理人、阅知人、征集/子流程、超时、任务标题、全局变量等）：编辑即时写入当前设计会话，由画布顶部全局”保存/保存&模拟/保存&发布”统一落库（增量持久化，仅写脏数据）；**子表行配置**（节点事件、操作按钮、子业务校验、表单校验规则、必传文档清单等）：每行独立保存（行级 CRUD 落库为子表行，落库即时生效于当前版本配置、不阻塞后续编辑），行内校验即时，同一子表类型接口跨宿主复用；**版本级动作**：保存=增量落库+版本级汇总校验（秒级），保存&模拟/保存&发布=全量校验+发布装载，重型校验可异步执行。**因此本 Skill 中”配置操作”的”保存”统一指：标量组=确认写入设计会话；子表行组=确认保存该行。真正的落库/装载由统一机制处理，不逐组重复描述”落库 XX 表”。**

> **系统标识生成规则**（对齐 PDF v1.5.2，2026-08-19 定）：节点/连接线/网关/按钮标识由系统自动生成、只读显示、不可手动修改——节点 key={类别短码}{版本内递增序号}（审批→appr01、征集→col01、子流程→sub01、开始→start、结束→end）；网关 key={类型短码}{序号}（排他→xgw01、并行→pgw01、包容→bgw01）；连接线 key=line{序号}；按钮 key=btn_{类型短码}{序号}（通过→btn_pass01、驳回→btn_reject01、事件→btn_evt01）。约束：仅字母/数字/下划线、字母开头（BPMN XML NCName 合法）；不含 ${ / # /空格/中文；版本内唯一；类别变更时 key 自动重生成并同步引用（按钮目标节点/连线/事件参数）；序号含已删除不复用。

**配置信息组说明模板**（步骤化三段式）：

> ### 配置信息组：{组名}（{该组包含的配置项全集，含枚举}）
> **配置操作**：
> 步骤1：……（操作对象+约束）；
> 步骤2：……（操作对象+约束）；
> 步骤N：点击确定，写入设计会话 / 子表行保存。
> **系统处理**：
> - 编辑时处理：校验…… → 写入设计会话（配置载件）；阻断条件……
> - 生效后响应：随版本发布装载后，系统应：① ……（载件类型）；② ……（载件类型）
> **运行期能力**（提供业务人员可操作能力的组写，以业务人员操作过程说明；以系统处理为主的组不填此项）：
> - 操作页面：……
> - 操作处理：步骤1：……（分支：通过→…；驳回→…；事件→…）

**三条规则**：① 组的分界按**可以运行的能力**——由 wft01-eng 在框架设计时确定（分组判据见 [wft01-eng §3.3.1](eos-wft01-eng-spr2bpl.md)），本 Skill 承接配置信息组清单+结构判定级框架说明；详设时若发现分组与 CU 承接冲突：组粒度可调整（合并/拆分组）→ 标注 `[调整]`（不改 CU 承接关系，§3.3.3）；结构冲突（某组无法在该 CU 下展开）→ 退回 wft01-eng（§3.3.3）；② 运行期能力非必填——某组只提供系统处理、不提供业务互动能力时，显式标注”以系统处理为主”，不硬凑运行期能力；③ **步骤化纪律**——配置操作以步骤序列写（每步含对象+约束+联动）、编辑时处理以”校验→写载件→阻断”写、生效后响应一律编号式（”随版本发布装载后，系统应①…②…③…”）且**载件类型显式标注**。

**载件分类**（系统处理·生效后响应的生成物，承载配置所定义的能力）：数据载件（物理表/字段）、配置载件（配置记录，如 FlowNodeConfig 行）、界面载件（功能表单/窗口标签页/菜单入口）、构件载件（操作按钮/状态标签/指标图示/看板视图）、实例载件（流程实例/流程任务/工单/计划任务/指标结果记录）、支撑载件（定时任务/通知/催办消息/审计日志）。实体引擎 CU 以数据载件为主（生成表、字段），功能引擎 CU 生成其余各类载件。

**示例：@flow-cu-node-config**（流程节点配置单元，按操作活动定义说明；步骤化形态=PDF v1.5.2 样板）：

**CU 级**：
- 配置入口：配置页面=流程设计器·节点配置面板（wft03-eng 据此组织功能表单，本 Skill 只定职责）
- 统一保存机制：节点配置采用”设计会话+全局保存”（标量组写入设计会话、子表行组行级保存、版本级动作全量校验，§2.2.1 注），下列示例的”点击确定”即写入设计会话 / 保存子表行

**配置信息组（操作活动定义）**：

> ### 5.1 节点基本信息/类型组（节点名称、节点key、节点类别[审批/征集/子流程]、节点类型[单人/多人并行]）
> **配置操作**：
> 步骤1：在 BPMN 画布中选中任务节点，右侧打开节点配置面板；
> 步骤2：填写节点名称（必填，同一版本内不重名）、节点key（系统自动生成只读，规则见上）；
> 步骤3：选择节点类别（审批/征集/子流程），面板字段随类别切换；
> 步骤4：选择节点类型（单人/多人并行）；
> 步骤5：点击确定，写入设计会话。
> **系统处理**：
> - 编辑时处理：校验节点名称不冲突、节点类别合法；节点 key 按规则自动生成，类别变更时自动重生成并同步所有引用；更新设计会话中该节点配置（配置载件）
> - 生效后响应：随版本发布装载后，系统应：① 节点类别/节点类型装载（配置载件）；② 节点背景色按配置完整度更新（灰=新建/白=完整/黄=缺必填项，构件载件）；③ 运行期按节点类别决定该节点的办理形态
> **运行期能力**：
> - 操作页面：该节点办理单据页（渲染绑定表单）
> - 操作处理：实例流转到该节点，系统按办理人配置生成待办并分派；业务人员打开办理单据页，看到该节点的办理形态（审批/征集/子流程）

> ### 5.4 操作项/办理意见组（通过/驳回/事件按钮、目标节点、意见配置、应用条件、驳回后重提策略）
> **配置操作**：
> 步骤1：在节点配置面板的”审批按钮”区勾选本节点的操作项按钮集（默认：通过一个；驳回/事件可选添加，同类按钮节点内不重名）；
> 步骤2：单击按钮行单元格→行内编辑修改属性；右键”编辑”→打开按钮编辑弹窗（按钮名称/类型/目标节点/意见/事件/条件/重提策略）；
> 步骤3：通过/驳回类按钮配目标节点（通过→后续节点或跳转指定节点；驳回→前节点/发起人/指定节点）；
> 步骤4：配置意见（意见可编辑=是→必填/可空+默认文案；否→锁定默认文案，默认意见必填）；
> 步骤5：配置按钮事件（选填）——校验/前置/后置 3 槽位，各配同步/异步与异常处理；
> 步骤6：配置应用条件（条件表达式，选填，满足才显示该按钮）；
> 步骤7：配置驳回后重提策略（全部失效/仅驳回节点重审/指定重审起点）；
> 步骤8：子表行保存——每个按钮为子表行，点”确定”即保存该行（行级落库）。
> **系统处理**：
> - 编辑时处理（行级保存）：校验按钮名称节点内不重名、目标节点有效、意见配置联动合法、应用条件可解析；删除唯一通过按钮时提示（不阻断行级保存，版本级校验在全局保存/发布时阻断）；校验按钮事件绑定服务已注册、同步后置事件可回滚
> - 生效后响应：随版本发布装载后，系统应：运行期在办理单据页按配置渲染按钮构件（构件载件）；业务人员点击按钮后，按配置驱动该节点办理结果（写 task_result）
> **运行期能力**：
> - 操作页面：该节点办理单据页 + 办理弹窗
> - 操作处理：步骤1：打开办理单据页，看到按配置渲染的通过/驳回/事件按钮（或列表右键菜单）；步骤2：点击”通过”→触发表单/子业务/引用校验 + VALIDATE 校验→记录 task_result 并流转；步骤3：点击”驳回”→不触发表单/VALIDATE 校验，仅校验意见与驳回目标有效→记录驳回 task_result→流转到驳回目标节点；步骤4：点击”事件”→仅执行按钮绑定事件，不记录 task_result、不完成任务、不流转；步骤5：其余办理操作——移交（意见必填）、加签/减签（多实例节点）、传阅（生成待阅）、取回（下一步未审批时）

> ### 5.7 超时流转组（是否超时处理、超时时长(天)、超时审批意见、超时异常通知人）
> **配置操作**：
> 步骤1：在节点配置面板开启”是否超时处理”（默认否；开启后显示超时相关字段）；
> 步骤2：填写超时时长（天，正整数，必填）；
> 步骤3：填写超时审批意见（多行文本，系统自动提交时使用）；
> 步骤4：选择超时异常通知人（默认=流程管理员）；
> 步骤5：点击确定，写入设计会话。
> **系统处理**：
> - 编辑时处理：校验超时时长合法（开启时必填）
> - 生效后响应：随版本发布装载后，系统应：① 定时任务扫描超时待办，到期自动提交（办理人=系统管理员，意见=配置意见）；② 超时审批逐条执行（各自留超时记录/日志）；③ 节点表单必填未填报→不允许触发超时（标记”超时失败待处理”，向办理人+管理员推送）
> **运行期能力**（以系统处理为主）：超时未办时业务人员收到催办/超时通知；超时自动审批——多人任意随机选一、多人全部逐个提交

并单独定义**引擎状态迁移**：配置草稿、已校验、已发布、已装载、已停用、已回滚等状态及其触发条件；不得仅隐含在”系统处理”描述中。

| 依赖类型 | 示例 | 处理 |

| 引擎内依赖 | 流转规则配置依赖流程节点配置 | 在 bpd-eng 中写明先后关系 |
| 跨引擎依赖 | 流程配置依赖实体字段、权限规则 | 引用依赖引擎/CU，不改主归属 |
| 布局组件/构件依赖 | 流程 CU 运行期需要按钮构件、节点构件 | 说明被渲染的布局组件/构件 |
| 治理依赖 | 发布、版本、审计、回滚、监控 | 若缺失则生成补充 FR-ENG（§5.5 3），由 wft01-eng 判定新增 |

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲详设的逻辑——为什么用 P0 配置单元承接 bpl-eng（3.1 转换原理）、怎么提取要素（3.2）、怎么详设 CU 与校验依赖（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四，操作步骤见 §五。

### 3.1 转换原理：为什么用 P0 配置单元承接 bpl-eng

**bpl-eng 描述"需要什么平台能力"，bpd-eng 回答"用哪些配置单元怎么实现"**。bpl-eng 是平台能力场景的业务定义（配置/治理目标 + 能力链 + 配置信息组（框架说明） + CU 承接关系，wft01-eng 产出）；bpd-eng 把这些已分配的 CU 展开为可被系统需求框架（srb）承接的 P0 配置单元 bpd-eng——详细定义每个 CU 的配置信息组（操作活动定义：配置操作/系统处理/运行期能力 + 引擎状态迁移）、建立依赖关系。承接单位 = P0 配置单元 bpd-eng，CU 是其细分节点（与 bpl-biz 下辖输出文档的层级关系完全对称，[91 规范 §8.2](91-eos-biz-eng-spec.md#82-业务流程开发wft02-eng)）。

**承接已分配 CU 做业务流程概要，不是重新设计**。wft01-eng 已完成设计——分解（名称级识别→配置信息组（框架说明，结构判定级））、分配（配置信息组→CU 承接，含收敛判定复用/新增/拆分/合并 + 对照 25 盘存的骨架判定）、分析（完备性）；本 Skill 承接其产出，只做**业务流程概要**：读取 CU 承接关系（含引擎归属），展开操作活动定义（配置操作/系统处理/运行期能力，步骤化三段式）、配置入口、依赖与状态迁移。本 Skill **不重复收敛**（不重新判定 CU 新增/拆分/合并）、**不重复判定引擎归属**（承接 wft01 的设计结论）——承接关系是**设计结论**（wft01 权威），详设时若发现承接缺陷（配置信息组无法在该 CU 下展开、引擎归属错判、承接缺失）退回 `需wft01修订`，不静默改。

**配置信息组清单+结构判定级框架说明承接自 wft01 的框架设计，本 Skill 展开为操作活动定义**。wft01-eng 在框架设计时按"可以运行的能力"名称级识别配置信息组候选、拆成配置信息组（框架说明，[wft01-eng §3.3.1](eos-wft01-eng-spr2bpl.md)）；本 Skill 承接该清单+框架说明，为每个配置信息组定义操作活动定义——配置操作（步骤序列）、系统处理（**编辑时处理 + 生效后响应**，统一保存机制）、运行期能力（§2.2.1），并定义 CU 级配置入口、FR-ENG 性能指标与引擎状态迁移。CU=**页面单位**（操作/维护边界）、配置信息组=**能力单位**（运行期边界）的两级分工由 wft01 框架设计确定；本 Skill 详设时若发现分组与 CU 承接冲突：组粒度可调整 → 标注 `[调整]`（§3.3.3）；结构冲突（某组无法在该 CU 下展开）→ 退回 wft01-eng（§3.3.3）。

**详设层缺口经补充 FR-ENG 或退回 wft01 处理，不脑补承接**。已分配 CU 的**操作活动定义、依赖或状态迁移缺口**（配置入口缺失、配置操作步骤缺失、系统处理缺段、运行期能力不可定义、依赖断点）由本 Skill 识别——能形成补充需求文本的生成补充 FR-ENG 材料（§5.5 3），需人类补充业务配置意图的标记 `[需裁决]`；**承接缺陷**（CU 承接关系/配置信息组清单无法在该 CU 下展开）属 wft01 设计层问题，退回 `需wft01修订`（§5.5 1），不脑补 CU 承接。**25 盘存是资产，不是需求源**——本 Skill 详设新增配置信息组/载件时对照 25 盘存判定复用/改进/新增（骨架判定，对齐通用设计规范 §2.3 文档结对骨架），但承接关系本身已在 wft01 确定。

**详设层变更以 `[调整]` 标注**。承接关系确定后，本 Skill 详设过程中对 CU 的**操作活动定义内容（配置操作步骤/系统处理/运行期能力）**的扩展（配置能力扩展）属详设层变更——以 `[调整]` 标注并写变更原因（§3.3.3），不改变 CU 承接关系；CU 承接关系本身的变更（新增/拆分/合并/归属变更）退回 wft01-eng 重新分配，本 Skill 不静默改承接。新增配置信息组/载件的粒度设计（§2.2.1/§3.3）同属详设内容——落地走文档结对骨架（对照 25 盘存判定复用/改进/新增），由 wft03-eng 承接验证可消费性。

**这套原理方法为什么可行**：它以**可验证性**为锚——每个设计决策都追问"下游能否验证、追溯是否完整、变更能否传播"。承接关系（wft01 设计结论）与详设内容（本 Skill 定义）分离，保证"设计决策与设计过程不分离"（决策在 wft01、详设在 wft02）；操作活动定义（配置操作/系统处理/运行期能力，步骤化三段式）是"配置→系统处理→运行期生效"的微闭环，缺一段即不可配置或不可验证；"运行期能力可消费"出口闸门（运行期制品/构件/功能、指标和配置入口足以让 wft03-eng 组织系统需求框架，§3.4）把可消费性落为硬判据，不足则保持待确认方案；**追溯完整性永远优先**——承接关系必须可追溯 bpl-eng 与 规范化的相关方需求，承接缺陷退回 wft01 而非脑补；权威归信息最全的一方且只归其信息全的部分（设计→wft01-eng，详设→wft02-eng，系统需求框架→wft03-eng）。判据全部可机械判定，操作全部有明确输入输出与执行模式（§5 Step 布局表），原理→判据→操作三层一一咬合，且与 91 规范、biz 路径同一套协议运转。

### 3.2 要素提取规则

**一句话**：本节讲从 bpl-eng 提取 bpd-eng 要素的规则——目标引擎与能力域确定（3.2.1）、R 上下文承接（3.2.2）、Phase B 宿主匹配检查（3.2.3）。Phase B（修订已有 bpd-eng）与 Phase C（新建 bpd-eng）共用以下规则——先看 3.2.4 的 B/C 分工差异表，再读细节更顺。

#### 3.2.1 目标引擎与能力域确定

从 bpl-eng 读取并确认：

| 提取项 | 说明 |
|--------|------|
| 主责类型 | `引擎专属` / `平台共享` |
| 主责能力域 | bpl-eng 唯一主责引擎或共享能力域 |
| 场景能力类型（FR-ENG 规范化的相关方需求节点 类型） | bpl-eng 场景的配置生成/构件扩展/布局组件扩展/横切治理/运行支撑类型 |
| 依赖 bpl-eng | 本场景消费的其他引擎专属或平台共享能力场景 |

路由规则：

| 情况 | 处理 |
|------|------|
| bpl-eng 主责能力域唯一且场景边界与 bpd-eng 一致 | 进入宿主匹配（Phase B）或新建（Phase C） |
| 主责能力域相同但独立场景不同 | 匹配其他 bpd-eng 或新建，不按同域强行合并 |
| bpl-eng 主责能力域不明确或能力域混杂 | 标记 `[推断]`，必要时退回 wft01-eng |
| CU 属于依赖的共享 bpl-eng | 不在当前 bpd-eng 重复定义，建立依赖引用 |
| bpl-eng 缺少能力链或 CU 承接关系 | 退回 wft01-eng，不进入 bpd-eng 设计 |

#### 3.2.2 R 上下文承接

Phase C 新建 bpd-eng 时，从 bpl-eng 节点承接 wft01-eng 已装配的 R 上下文（概念见 §2.3）：

1. **读取 R 产品/场景**：从 bpl-eng 的 R 上下文块读取业务运行对象/治理对象及 R 产品/场景引用。
2. **读取配置/支撑角色**：从 bpl-eng 的场景边界陈述中读取配置人员或支撑角色。
3. **读取触发事件与状态影响**：从 bpl-eng 的触发追溯与能力链”运行期可用性确认”段分别读取。
4. **校验触发追溯链**：`R／P 业务运行对象/治理对象/构件缺口/布局组件缺口/横切阶段 → bpl-eng → P0 bpd-eng → CU` 的追溯链字段完整。

若 R 上下文信息不足，标注 `[推断]` 并记录缺失项；若缺失到无法判断 CU 来源，退回 wft01-eng（R 装配缺失）。

#### 3.2.3 Phase B 宿主匹配检查

Phase B 修订已有 bpd-eng 时，按目标引擎和主责能力域匹配已有 bpd-eng：

按以下顺序匹配：

1. 同一 P0 产品路径（流程与 IT 域 → 同一引擎）。
2. 同一目标引擎（@engine-xxx）。
3. 同一主责能力域或互补主责能力域。
4. CU 清单可归入同一 bpd-eng。

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| Q1 直接归入 | 同一主责能力域、同一能力场景、边界一致 | 追加 bpl-eng 来源，标记 `[确认]` |
| Q2 扩展归入 | 同一能力场景，但 CU 能力边界扩展 | 扩展 bpd-eng，写变更声明 |
| Q3 新建 | 无可用 bpd-eng 宿主 | 新建 P0 bpd-eng 节点 |
| 共享依赖 | CU 已由平台共享 bpl-eng 定义 | 只记录依赖和消费关系，不复制 CU |
| 冲突 | 同一 CU 被多个主引擎争用或 P0 路径不一致 | 标记 `[需裁决]` |

#### 3.2.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 bpd-eng | Phase C 新建 bpd-eng |
|------|-------------------|-----------------|
| 判定范围 | bpd-eng 已承接的全部 bpl-eng + 本轮新 bpl-eng | 待聚合池本组 bpl-eng |
| CU 承接基线 | 以已有 CU 承接为基线，仅扫描本轮新 bpl-eng 的已分配 CU | 从零承接 |
| R 上下文 | 增量合并新 bpl-eng 中的 R 信息，已有上下文仅追加不重建 | 全量承接（§3.2.2） |
| 宿主匹配 | 执行宿主匹配检查（§3.2.3），可能检出 Q1/Q2/Q3/冲突 | 无需匹配，直接新建 |
| 详设处理 | 承接新 CU + 定义操作活动定义（详设变更见 §3.3.3） | 全量详设（§3.3.2） |
| 依赖重识别 | 合并重识别可能导致已有依赖关系变更——标记 `[依赖变更]` 并附变更原因 | 全量识别，无此问题 |
| 变更传播 | 需输出变更影响声明（§4.2） | 写”首版，无变更” |

### 3.3 CU 详细定义与依赖校验规则

**一句话**：本节讲逐 CU 的详设规则——CU 承接读取（3.3.1）、配置信息组与操作活动定义（3.3.2）、详设变更处理（3.3.3）、依赖定义与闭合校验（3.3.4）。Phase B（修订已有 bpd-eng）与 Phase C（新建 bpd-eng）共用以下规则。CU 收敛判定、来源类型与关系检测已上移 wft01-eng（设计归属重构 DP5），本 Skill 不重复执行。

#### 3.3.1 CU 承接读取

**读取 CU 承接关系**：从当前操作范围内的 bpl-eng 读取 CU 承接关系（wft01-eng 分配产物，含收敛判定/骨架判定/引擎归属，[wft01-eng §2.4](eos-wft01-eng-spr2bpl.md)），去重后形成 CU 清单，每个 CU → bpd-eng 中一个配置单元节点。多个 bpl-eng 的 CU 承接指向同一 CU 时归入同一节点（要素收敛）。

**校验承接结构完整**：每条 CU 承接须含承接的配置信息组（框架说明）清单与引擎归属；缺失时退回 wft01-eng。本 Skill **不重新收敛**、**不重新判定引擎归属**——承接关系是 wft01 设计结论（§3.1），只校验详设可行性。

#### 3.3.2 配置信息组与操作活动定义

对每个已分配 CU，承接 wft01 的配置信息组清单+结构判定级框架说明（§2.2.1），逐配置信息组展开操作活动定义：

| 定义项 | 口径 | 说明 |
|--------|------|------|
| 操作活动定义 | 承接 wft01 的配置信息组清单+框架说明，逐组展开配置操作（步骤序列）/系统处理（编辑时处理+生效后响应）/运行期能力（分支显式化） | 组清单与 wft01 承接保持一致；详设时可标注 `[调整]`（合并/拆分组粒度），不改 CU 承接关系 |
| 配置入口 | 配置人员在哪个配置页面维护该 CU | CU 级，页面职责/配置对象/配置类别，不设计 UI |
| FR-ENG 性能指标 | CU 配置后运行期需达到的性能指标 | CU 级，定量指标或二元判定；供 wft03-eng 系统需求框架、wft05-eng 平台产品架构承接指标输入 |
| 系统处理 | 编辑时处理（校验→写载件→阻断）+ 生效后响应（生成载件，载件类型显式标注） | 逐组定义，对齐统一保存机制 |
| 运行期能力 | 系统对业务人员交付的能力 | 以业务人员操作过程说明，分支规则显式化；以系统处理为主的组显式标注 |
| 引擎状态迁移 | 配置草稿/已校验/已发布/已装载/已停用/已回滚等状态及触发条件 | CU 级，单独定义 |

详设新增配置信息组/载件时对照 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景) 盘存判定复用/改进/新增（骨架判定，人机协同设计决策点——AI 附判据理由，流水线开发者审核决策，对齐通用设计规范 §2.3 文档结对骨架）。

#### 3.3.3 详设变更处理

承接关系确定后，bpd-eng 修订时处理两类详设层变更：

| 变更类型 | 触发 | 处理 |
|----------|------|------|
| **配置能力扩展** | 已有 CU 的操作活动定义内容（配置操作步骤/系统处理/运行期能力）扩展 | 修订 CU 操作活动定义，叠加 `[调整]` 标注 + 写变更原因。不新增/不拆分 CU（CU 承接关系不变） |
| **承接关系变更** | 新 bpl-eng 携带的已分配 CU 与已有承接冲突（承接缺失/引擎归属错判/配置信息组无法在该 CU 下定义） | 不静默改——退回 `需wft01修订`，携带缺失说明，由 wft01-eng 重新分配（wft01-eng §3.3.4 关系检测） |

> 上表与 wft01-eng 的收敛判定/关系检测是两个层面：wft01 管**承接关系**（CU 新增/拆分/合并/归属变更），本 Skill 管**承接内容**（详设定义变更）。配置能力扩展不改变承接关系，由本 Skill `[调整]` 处理。

#### 3.3.4 依赖定义与闭合校验

依赖概念与分类见 §2.4。对 bpd-eng 的依赖关系定义并执行四步闭合校验：

1. **引擎内**：定义 CU 间先后配置关系，缺失前置 CU 时标记依赖断点。
2. **跨引擎**：定义引用引擎/CU（wft01 已判定归属），校验在 25 或已有 bpd-eng 中存在，不存在时标记 `[推断]` 依赖。
3. **布局组件/构件**：定义运行期能力中的构件/组件，校验可追溯到来源 CU 或 25 中的布局组件/构件定义。
4. **治理**：定义发布、版本、审计、权限、回滚等横切依赖，校验在 bpd-eng 或 25 中有覆盖，缺失时生成补充 FR-ENG（§5.5 3）。

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|

## 四、CU bpd-eng 节点演进：生命周期与变更传播

**一句话**：本章讲 bpd-eng 节点设计与确认后的演进机制——生命周期（4.1，节点状态四态主线 + 上游变更分流 + 本 Skill 写回范围）与变更传播（4.2，修订后写变更影响声明告诉下游 wft03-eng）。

### 4.1 bpd-eng 节点生命周期

### 5.1 Step Start

**一句话**：先变更感知（检出人类线下修订并纳入待反馈分节），再按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策路由（退回优先 → 反馈处理 → 新输入），无待处理对象即退出。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 bpl-eng）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

**入口判定**（在变更感知后执行）：读取 `02-*.md`/`04-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表，再按以下顺序处理：

| # | 入口条件 | 检测方式 | 对应分节 |
|---|---------|---------|---------|
| ① | **有新输入** | AI可以处理节点「待 wft02-eng 处理」分节非空 | §11.7 |
| ② | **有待处理反馈** | AI可以处理节点「待反馈处理」分节含本 Skill 产出节点 | §11.7 |
| ③ | **有下游退回节点** | AI可以处理节点「待下游退回处理」分节含状态为 `需wft02修订` 的节点 | §11.7 |

三类均不满足 → 输出"无待处理对象"→ **退出**。

#### 5.1.1 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| bpl-eng 不是 P0 类型 | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft02-biz` 或 nfr 路径 → **退出** |
| bpl-eng 状态不是 `可以详细定义` / `待补充详细定义` | 状态不符（硬退出） | 输出不合格节点及当前状态 → **退出** |
| bpl-eng 缺少场景边界、能力链或触发追溯 | 要素缺失（硬退出） | bpl-eng → `需wft01修订`，输出缺失说明 → **退出** |
| bpl-eng 无已分配 CU 或承接结构不完整（缺配置信息组（框架说明）清单） | 承接不完整（硬退出） | 输出"输入不足"提示 → bpl-eng → `需wft01修订`，输出缺失说明 → **退出** |
| 选中 bpl-eng >5 个 | 超建议阈值（软提示） | 输出超限提示 → 人类确认后继续或退出 |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

**锁定写回**：输入校验通过后，将承接的 bpl-eng 状态写为 `在详细定义`（锁定态，本 Skill 消费展开期间，对齐 91 §A.6 锁定态=下游写入 与 wft01 §4.1）；完成操作活动定义且人类确认后推进 `已详细定义`（§5.6）。

#### 5.1.2 退回优先（§A.4.3 门禁）

存在 `需wft02修订` 的 bpd-eng 节点（来自"待下游退回处理"分节）：
- 检查人类是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注 `[修改]`/`[同意]` 或下游 Skill 产出的具体改进指引）
- 已提供 → 通过门禁，读取 wft03-eng 的缺失说明，按 SKILL 指南走 Phase B 修订（§5.4.2），人类确认后推进为 `可以srb设计`
- 未提供 → 输出 wft03-eng 的缺失说明 + 提示提供改进方案 → **退出**

#### 5.1.3 反馈处理

存在"待反馈处理"分节中的 bpd-eng 节点（条目确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`，标记定义与写入者见 §5.3）→ 进入 Step 2 处理（§5.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 bpl-eng，Step End 时提示。

#### 5.1.4 新 bpl-eng 路由

有未处理的 bpl-eng 节点（来自"待 wft02-eng 处理"分节）→ 进入 Step 1→Step 3，逐节点执行 Phase A 宿主匹配（§5.4.1），归入已有 bpd-eng（→Phase B）或待聚合池（→Phase C）。

**执行顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 bpd-eng 的 P0 路径/CU 清单/配置能力/依赖关系。Step 3 的 Phase A 宿主匹配必须基于 Step 2 修改后的最新 bpd-eng 内容，不得使用缓存旧状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类反馈的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `02-*.md`/`04-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.6），保证下一轮 diff 只含人类变更。

**本 Skill 的条目**：P0 产品路径 + 每个 CU（含配置入口/操作活动定义/FR-ENG 指标）+ 每条依赖 + 每条缺口补需。各条目的 `确认状态` 字段位于 `04-*.md` bpd-eng 节点块各条目正文中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.3）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.6），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

**触发条件**：Step Start 检出 `需wft02修订` bpd-eng，或上一轮 Step End 的反馈等待中人类提出修改意见。

**处理规则**：

1. 从当前轮次对话上下文或退回缺失说明中读取人类反馈意图
2. **逐条处理**（按人类反馈内容）：
   - AI 输出方案后人类直接回复修改意见 → 在当前轮次继续对话处理，不重新走 Step Start
   - wft03 退回的 `需wft02修订` → 下一轮 Skill 调用时走 Step Start 退回优先
3. 修改后检查是否仍满足该 bpd-eng 所承接的 bpl-eng 需求
4. 修改导致结构性变更（P0 路径/CU 清单/配置能力/依赖重组）→ 按需重入 Step 3
5. 全部条目获流水线开发者认可 → bpd-eng → `可以srb设计`

按 [91 规范 §A.5.3](91-eos-biz-eng-spec.md#a53-ai-处理流程) 的流程处理人类自然语言反馈：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足 bpl-eng 需求 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 推进 bpd-eng 至 `可以srb设计` → **提交基线并更新 HEAD（机制见 §5.6，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

> **原则**：反馈处理不是对人类标注的机械执行，而是以 bpl-eng 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解人类反馈在 bpl-eng 需求语境中的含义，再执行修订，最后检查修订后的 bpd-eng 是否仍满足 bpl-eng 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

**锚点需求**：bpl-eng 节点——反馈处理以 bpl-eng 场景业务需求（引擎归属、能力链、CU 承接关系）为锚，不脱离 bpl-eng 内容自行修订。

**操作条目**（写入 `04-*.md` bpd-eng 节点对应条目的 `确认状态` 字段）：

- 每条依赖
- 每条缺口补需

**推进目标**：
- 全部条目 `[同意]`+`[已处理]` → bpd-eng → `可以srb设计`
- 存在 `[修改]`/`[驳回]` 且无 `[需重设计]` → 保持 `待确认方案`

**清除条件**：已有 `[同意]`+`[已处理]` 的条目默认跳过。仅当本轮新输入满足以下任一条件时，清除 `[已处理]`（保留 `[同意]`）使其回到待处理：

3. 新输入导致条目定义被修订（变更影响声明标注为修订型或结构型，§A.5.3 Step 1）

**级联触发条件**：P0 产品路径或 CU 详设变更（配置能力扩展 `[调整]`、承接冲突）、依赖关系变更 → 触发需求级联检查（重验 bpd-eng 是否仍满足 bpl-eng 需求）→ 通过后触发资产对齐级联。

### 5.4 Step 3 · P0/CU bpd-eng 设计

#### 5.4.1 Phase A：bpl-eng 宿主匹配

对每个 bpl-eng 节点，按目标引擎和主责能力域匹配已有 bpd-eng（详见 §3.2.3），逐节点做宿主匹配：

|------|------|

| 不满足 | 进入待聚合池 → Phase C |
| 同一 CU 被多个主引擎争用或 P0 路径不一致 | 标记 `[需裁决]` |
| CU 属于依赖的共享 bpl-eng | 不进入本 bpd-eng（共享能力按独立 bpd-eng 建模，消费方只记录依赖，见 §3.2.1 路由规则） |

#### 5.4.2 Phase B：修订已有 bpd-eng

1. **要素提取**：从本轮 bpl-eng 增量合并 R 上下文（产品/场景引用、业务运行对象、配置/支撑角色、触发事件、状态影响）和 CU 承接关系（详见 §2.3.1、§3.3.1）。已有上下文仅追加不重建
2. **宿主匹配检查**：确认 bpl-eng 仍在 bpd-eng 宿主范围内（详见 §3.2.3）。Q1 直接归入→追加来源；Q2 扩展归入→扩展 bpd-eng + 变更声明；冲突→标记 `[需裁决]`。Phase A 匹配是候选筛选、Phase B 是精确匹配——宿主扩展时不得回退 Phase A 重选宿主，继续完成 Phase B 全部处理并标记 `[推断]` 供人类裁决
3. **CU 详设与变更处理**：承接已分配 CU，定义操作活动定义（配置操作/系统处理/运行期能力）、配置入口、FR-ENG 指标和引擎状态迁移（详见 §3.3.2）；执行详设变更处理——配置能力扩展 `[调整]`、承接关系冲突退回 `需wft01修订`（详见 §3.3.3）；不设计页面
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 bpd-eng 节点末尾（详见 §4.2）

#### 5.4.3 Phase C：新建 bpd-eng

1. **确定 P0 产品路径** → 从 bpl-eng 读取目标引擎和主责能力域 → 流程与 IT 域 → 引擎 → CU（详见 §3.2.1）
2. **承接 R 产品业务流程上下文** → 读取 wft01-eng 装配的 R 上下文（业务配置人员 → bpl-eng → 配置活动序列 → 运行期能力可用；R 产品/场景引用、触发事件和状态影响），校验字段完整（详见 §3.2.2）
3. **承接已分配 CU** → 读取 bpl-eng 的 CU 承接关系 + 配置信息组（框架说明）清单，校验清单完整（详见 §3.3.1）
4. **定义 CU 详细设计（操作活动定义）** → 配置信息组（配置操作/系统处理/运行期能力，步骤化三段式）/配置入口/FR-ENG 指标/引擎状态迁移（详见 §3.3.2）
5. **输出页面推导线索** → 为每个 CU 记录配置角色、入口职责、配置对象、活动顺序和运行支撑需求，交由 wft03-eng 组织系统需求框架（功能表单）
6. **校验依赖并组装 bpd-eng** → P0 路径 + R 页面序列 + CU 详细设计 + 依赖 + 缺口材料，写入 `04-*.md`

### 5.5 Step 4 · 引擎需求增补

Step 4 按每个 bpd-eng 实例独立执行。新建 bpd-eng → 全量检查；修订已有 bpd-eng → 仅当详设内容变化（配置能力扩展/承接冲突）时重验闭合，要素机械检查始终针对变更节点执行。变更影响声明在 Step 3 Phase B 产出（§5.4.2 / §4.2），本节负责详设缺口识别与补需。

**1. 缺口识别与分类**

逐 bpd-eng 检查四类缺口，按来源分流：

- **上游缺口**（退回 wft01-eng）：bpl-eng 场景边界缺失、能力链不闭合 → 退回 `需wft01修订`，携带缺失说明
- **承接缺陷**（退回 wft01-eng）：CU 承接关系或配置信息组清单无法在该 CU 下展开（承接缺失、引擎归属错判、分组与 CU 承接冲突，§3.1）→ 不静默改，退回 `需wft01修订`，由 wft01-eng 重新分配
- **配置能力缺口**（生成补充材料）：配置入口缺失（不知道配置人员从哪里配置）→ 生成补充 FR-ENG；配置操作步骤缺失（缺少关键步骤/对象/约束）→ 标记 `[需裁决]`，需要人类补充业务配置意图；系统处理缺失（缺少编辑时处理/生效后响应）→ 生成补充 FR-ENG；运行期能力缺失（缺少制品/构件/功能）→ 生成补充 FR-ENG；FR-ENG 性能指标缺失（缺少运行期需达标的指标）→ 生成补充 FR-ENG
- **依赖缺口**（生成补充材料）：CU 间依赖断点 → 标记依赖断点并生成补需；跨引擎依赖无对应引擎模型 → 标记 `[推断]` 依赖并生成补充 FR-ENG（§5.5 3），不设计新引擎/CU 模型记录
- 缺口 → 进入「补充 FR-ENG 材料生成」。不因缺口脑补节点——缺口就是缺口

**2. 要素机械检查**（逐 bpd-eng，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

| 检查项 | 判据 | 标注方式 |
|-------|------|---------|
| R 上下文 | 产品/场景引用 / 业务运行对象 / 配置角色 / 触发事件 / 状态影响 **完整**（承接自 bpl-eng） | 缺失项写入 `[覆盖缺口]` |
| P0 产品路径 | 流程与 IT 域 → 引擎 → CU **到位** | 同上 |
| CU 承接 | **非空**，每条承接含配置信息组（框架说明）清单（承接自 bpl-eng） | 漏标时补充 |
| CU 操作活动定义 | 每个需详设 CU 的配置信息组（配置操作/系统处理/运行期能力）/配置入口/FR-ENG 指标 **已定义** | 不足时标注 |
| CU 依赖关系 | 引擎内 / 跨引擎 / 布局组件与构件 / 治理 **已定义并校验**，断点已标记 | 断点标注 |
| 变更影响声明 | **已写入**（首版写”首版，无变更”；格式见 §4.2） | 缺失时补充 |

**3. 补充 FR-ENG 材料生成**

闭合缺口时生成，写入独立材料文件：

| 字段 | 说明 |
|------|------|

| 缺口类型 | 上游缺口 / 承接缺陷 / 配置能力缺口 / 依赖缺口 |
| 补充需求文本 / 推断依据 | 详细说明 |
