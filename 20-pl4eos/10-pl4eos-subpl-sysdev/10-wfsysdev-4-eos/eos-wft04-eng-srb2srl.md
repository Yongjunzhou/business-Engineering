### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台开发人员——「这个功能表单的区域内由哪些组件构成、每个组件的业务是什么、有哪些问题需留待 pa-eng 判断」。承接 wft03-eng 产出的系统需求框架 srb-eng，展开为系统需求概要 srl-eng——判定区域内布局组件与构件、定义组件业务（功能级不写实现）、标注 pa-eng 层收敛项，为 wft05-eng 设计前后端组件提供完整输入。

> **三层定位（按 EOS 流水线系统设计规范 §8.1）**：本 Skill 属于第1层（流水线设计）活动——在 EOS 流水线设计层将 wft03-eng 产出的系统需求框架 srb-eng 展开为系统需求概要 srl-eng；产出物经 wft05-eng 展开为 pa-eng 后，以设计规范/AI SKILL 形态交付第2层（构件开发），最终由第3层 EOS 开发者（确认者/用户）使用。本 Skill 的执行分工按 EOS 流水线系统设计规范 §8.3：流水线开发者（主导者/审核者）审核 AI 的组件业务方案并决策变更路径，AI（执行者）执行标准操作流程，EOS 开发者（确认者/用户）确认交付物可用性。

### 2.1 功能组件业务

**一句话**：本节讲功能组件业务的概念——定义与要素（2.1.1）；完备性判据见 §三 3.4。

#### 2.1.1 定义与要素

功能组件业务是功能表单**区域内**具体组件及其业务的详细定义，是系统需求概要（04 层）的详细条目。**04 vs 03**：03 到区域/TAB/弹窗入口，04 到区域内具体组件+业务（布局组件/构件，功能级不写实现）。**04 vs 05**：04=功能组件业务（页面元素），05=产品组件（前端/后端/平台服务，07 pa-eng）。

**功能组件业务条目要素**（写入 `06-*.md` srl-eng 节点块）：

- 组件名称 / 所属功能表单 / 所在区域（TAB/弹窗入口）
- 布局组件类型（多级横版/列表/单据/辅助栏/弹窗/指标/看板）或构件类型（展示/交互/数据/反馈）
- 组件业务（功能级不写实现）——承载的操作活动清单（承接 03 操作活动清单）、数据来源、交互行为、状态反馈
- pa-eng 层收敛项（§2.3）
- 确认状态

> **边界**：本 Skill 定义组件**业务**（功能级）——布局/交互/数据/反馈的业务语义，不写实现（不写代码、不写数据库表、不写接口协议）；组件**实现**归 wft05-eng（07 pa-eng）与构件开发流水线。

### 2.2 布局组件与构件

#### 2.2.1 定义与正交关系

**布局组件**：多级横版、列表、单据、辅助栏、弹窗、指标页面、看板页面（树形表格是列表页面的呈现变体）通过布局组件组合表达功能表单**区域内**的承载方式。布局组件判定自 wft03-eng 收缩前 §2.2.1/§3.2.3 迁入。

**布局组件可选范围**：

| 布局组件 | 典型用途 |
|----------|----------|
| 多级横版 | 多层级配置对象、主从配置、流程/规则设计器 |
| 列表页面 | 配置对象集合、发布记录、版本记录、执行记录 |
| 单据页 | 单个配置对象编辑、参数维护、规则详情 |
| 辅助栏 | 详情预览、上下文摘要、引用关系、校验结果 |
| 弹窗页 | 选择、确认、局部参数编辑、冲突处理 |
| 指标页面 | 运行状态、质量指标、发布影响、异常趋势 |
| 看板页面 | 运行看板、任务看板、发布状态、异常汇总 |

**构件完整性分类**（四类须分别检查；无需求时写明"不适用"，不得只列按钮类构件）：

| 类别 | 典型构件 |
|------|----------|
| 展示类 | 列定义、字段布局、图表类型、卡片、树节点、阶段/里程碑 |
| 交互类 | 功能按钮、右键菜单、快捷键、下钻、行选中、TAB 切换 |
| 数据类 | 筛选器、排序器、分页器、导入、导出 |
| 反馈类 | 通知提示、进度条、状态标签、校验提示 |

> 布局组件与构件的详细定义见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)，eng 路径分工见 [91 规范 §8.4](91-eos-biz-eng-spec.md#84-系统需求详细开发wft04-eng)。

### 2.3 pa-eng 层收敛项

**pa-eng 层收敛项是本 Skill 在组件业务条目中标注的「待 pa-eng 设计判断的问题线索」——pa-eng 本身（前后端组件）由 wft05-eng 设计**。本 Skill **不设计组件**，只把需要 wft05 判断的问题传递过去；不得预选同步/异步、存储归属或实现机制。

| 收敛项 | 示例 | 标注 |
|--------|------|------|
| 组件边界 | 发布按钮构件是否复用公共构件 | `pa-eng层收敛-组件边界` |
| 接口问题 | 发布动作是否存在跨组件交互待判定 | `pa-eng层收敛-接口` |
| 数据问题 | 配置版本、发布记录、审计记录需要持久化能力 | `pa-eng层收敛-数据` |
| 运行问题 | 装载、缓存刷新、回滚、重试等需要下游确定机制 | `pa-eng层收敛-运行` |
| NFR 问题 | 关联的 NFR 约束由 wft05-eng 消费约束包后决策 | `pa-eng层收敛-NFR` |

> **载件是 pa-eng 收敛项的主要来源**：wft02-eng 详设的配置信息组"系统处理·生效后响应"生成的载件（数据/配置/界面/构件/实例/支撑载件），经 03 操作活动清单承接后由 wft05-eng 判断如何由前后端组件承接——前端组件承接配置展示/交互，后端组件承接配置处理与业务逻辑。本 Skill 只标注问题线索，不设计载件的实现。

| 操作活动清单（承接 02 标注入口） | 组件的承载操作活动清单（业务语义） |
| 页面编排框架（区域/TAB/弹窗入口） | 组件的所在区域（TAB/弹窗入口） |

#### 2.4.2 承接页面编排框架

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲系统需求详细设计的逻辑——为什么用组件业务承接系统需求框架（3.1 转换原理）、怎么提取组件要素（3.2）、怎么定义组件业务与标注 pa-eng 收敛（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四，操作步骤见 §五。

### 3.1 转换原理：为什么用组件业务承接系统需求框架

**系统需求框架描述"这个功能表单如何编排、页面上有哪些可执行活动"，系统需求概要回答"区域内由哪些组件构成、每个组件的业务是什么"**。wft03-eng 产出的系统需求框架 srb-eng（功能表单清单+页面编排框架+操作活动清单）是组件业务的承接锚——本 Skill 承接该框架，判定区域内布局组件/构件并定义组件业务，供 wft05-eng 设计 pa-eng（前后端组件）。承接单位 = 功能组件业务条目（04 层详细条目）。

**04 组件业务是 05 推断前后端组件的依据**。wft05-eng 从组件业务推断前端容器组件/交互构件/状态反馈组件、后端服务组件——组件业务的完整性直接决定 pa-eng 可消费性（出口闸门）。

**04 不越权设计**。本 Skill 定义组件业务（功能级），不写实现（不写代码/数据库/接口协议）；pa-eng 组件设计归 wft05-eng，pa-eng 层收敛项只标注问题线索不设计。发现系统需求框架不足（组件无法在该区域内定义）→ 退回 `需wft03修订`；发现操作活动定义不足 → 经 03 退回 `需wft02修订`，不脑补。

**这套原理方法为什么可行**：它以**可验证性**为锚——组件业务以功能表单为边界（页面单位）承接系统需求框架，每个组件可被 wft05-eng 承接为 pa-eng 组件、追溯链（组件→功能表单→配置信息组→CU→bpd-eng→bpl-eng→OR）完整、变更可传播；权威归信息最全的一方且只归其信息全的部分（系统需求框架在 03、组件业务在本 Skill、pa-eng 组件在 wft05）；判据全部可机械判定，操作全部有明确输入输出与执行模式（§5 Step 布局表），原理→判据→操作三层一一咬合，且与 91 规范、biz 路径同一套协议运转。

### 3.2 要素提取规则

**一句话**：本节讲从系统需求框架提取组件要素的规则——组件候选生成（3.2.1）、布局组件判定（3.2.2）、构件识别（3.2.3）、宿主匹配检查（3.2.4）。Phase B（修订已有系统需求概要）与 Phase C（新建系统需求概要）共用以下规则——先看 3.2.5 的 B/C 分工差异表，再读细节更顺。

#### 3.2.1 组件候选生成

对每个功能表单的每个区域（TAB/弹窗入口），按页面编排框架与操作活动清单生成组件候选：

| 页面编排框架 / 操作活动清单 | 组件候选 |
|----------------|---------------|
| 区域内有列表/版本记录/执行记录 | 列表布局组件（列表页面）+ 数据类构件（筛选器/排序器/分页器） |
| 区域内有单个配置对象编辑 | 单据布局组件（单据页）+ 交互类构件（按钮/右键菜单） |
| 区域内有主从/层级对象 | 多级横版布局组件 + 辅助栏（详情/上下文） |
| 区域内有临时选择/确认/冲突 | 弹窗布局组件 |
| 区域内有运行指标/异常趋势 | 指标/看板布局组件 |
| 操作活动清单有校验/发布/装载 | 反馈类构件（状态标签/校验提示/进度条） |

#### 3.2.2 布局组件判定

在页面编排框架基础上，独立判断区域内需要哪些布局组件：

| 判定条件 | 布局组件 |
|----------|----------|
| 需要展示对象集合、版本记录或执行记录 | 列表页面 |
| 需要编辑单个配置对象或参数组 | 单据页 |
| 需要并列展示多层主从对象 | 多级横版 |
| 需要上下文、详情、校验结果或引用关系 | 辅助栏 |
| 需要临时选择、确认、局部参数或冲突处理 | 弹窗页 |
| 需要展示运行指标、发布影响或异常趋势 | 指标页面 |
| 需要展示运行状态概览、任务分布或发布汇总 | 看板页面 |

#### 3.2.3 构件识别

在布局组件判定之后，按展示/交互/数据/反馈四类独立识别构件（四类定义见 §2.2.1）：

| 类别 | 识别线索 |
|----------|----------|
| 展示类 | 需展示哪些字段/图表/树/阶段 |
| 交互类 | 需哪些按钮/右键/快捷键/下钻/TAB |
| 数据类 | 需哪些筛选/排序/分页/导入/导出 |
| 反馈类 | 需哪些通知/进度/状态标签/校验提示 |

#### 3.2.4 宿主匹配检查

按 `引擎 + CU + 功能表单 + 区域内组件` 匹配已有系统需求概要条目：

| 结果 | 判定 | 动作 |
|------|------|------|
| 复用 | 组件类型和业务职责匹配 | 追加 bpd-eng/CU 来源，标记 `[确认]` |
| 扩展 | 组件类型一致，但业务或 pa-eng 收敛项扩展 | 全量重写该组件条目，保留历史引用，输出变更声明 |
| 新建 | 无可匹配的组件 | 新建系统需求概要条目 |
| 冲突 | 组件职责冲突或跨区域复用边界不清 | 标记 `[需裁决]` |

#### 3.2.5 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B（修订） | Phase C（新建） |
|------|----------------|-----------------|
| 判定范围 | 系统需求概要已承接全部 bpd-eng/CU + 本轮新 bpd-eng/CU | 待聚合池本组 bpd-eng/CU |
| 组件清单基线 | 已有清单为基线，仅扫描新功能表单是否引入新组件 | 从零构建 |
| 组件候选 | 增量生成（仅新功能表单/新区域触发） | 全量生成（§3.2.1） |
| 宿主匹配 | 执行匹配检查（§3.2.4），可能检出复用/扩展/新建/冲突 | 无需匹配，直接新建 |
| 组件业务 | 基线基础上增量合并（关系检测见 §3.3.2） | 全量定义 |
| 变更传播 | 输出变更影响声明（§4.2） | 写"首版，无变更" |

### 3.3 组件业务定义与 pa-eng 收敛项标注

**一句话**：本节讲组件业务定义的规则——组件业务要素（3.3.1）、Phase B 系统需求概要关系检测（3.3.2）。Phase B（修订已有系统需求概要）与 Phase C（新建系统需求概要）共用以下规则。

#### 3.3.1 组件业务要素

对每个布局组件/构件，按 §2.1.1 的条目要素定义组件业务（功能级不写实现）：

| 要素 | 定义口径 | 描述方式 |
|------|---------|---------|
| 组件名称 / 所属功能表单 / 所在区域 | 组件的定位 | 名称 + 所属功能表单 + 区域（TAB/弹窗入口） |
| 布局组件类型 / 构件类型 | 组件种类 | 布局组件（七种之一）或构件（展示/交互/数据/反馈） |
| 组件业务 | 组件做什么（功能级） | 承载的操作活动清单（承接 03）、数据来源、交互行为、状态反馈——**不写实现** |
| pa-eng 层收敛项 | 留待 wft05 判断的问题 | 组件边界/接口/数据/运行/NFR 标注（§2.3） |

**组件业务定义模板**：

> ### 组件：{组件名称}（{布局组件/构件类型}）· 所属 {功能表单} · 区域 {区域}
> **组件业务**：
> - 承载操作活动：{操作活动清单，承接 03 标注入口}
> - 数据来源：{展示/编辑哪些数据}
> - 交互行为：{用户如何交互}
> - 状态反馈：{结果/错误如何反馈}
> **pa-eng 层收敛项**：{`pa-eng层收敛-*`，无则"无"}

#### 3.3.2 Phase B 系统需求概要关系检测

宿主匹配通过后，将本轮生成的组件与系统需求概要已有清单比对。比对锚点为**组件类型 + 组件业务匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 组件匹配 + 类型一致 + 来源升级（新 CU→已有组件） | 追加 bpd-eng/CU 来源 |
| 无新增 | 组件匹配 + 类型一致 + 所有来源已确认 | 增量合并新 CU 的细节（如有） |
| 组件业务扩展 | 组件匹配 + 类型一致 + 业务/pa-eng 收敛项边界扩展 | 全量重写，保留历史引用 |
| 补充 | 组件不匹配 | 新增系统需求概要条目 |
| 过时 | 基线已有组件**未被**本轮功能表单覆盖 | 保留在清单中，标注`过时`，由人类裁决移除 |

> 关系检测前先基于**全部功能表单**重新判定组件类型——新功能表单可能改变组件职责。`[调整]` 是与关系类型正交的叠加标记，用于组件业务/pa-eng 收敛项有变化时。

## 四、srl-eng 详细节点演进：生命周期与变更传播

**一句话**：本章讲系统需求概要节点设计与确认后的演进机制——生命周期（4.1，节点状态四态主线 + 上游变更分流 + 本 Skill 写回范围）与变更传播（4.2，修订后写变更影响声明告诉下游 wft05-eng）。

### 4.1 系统需求概要节点生命周期

系统需求概要节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转。状态名映射按 §A.6 通用六态自声明（见下方主线流转与写回范围）。**03/04 文档承载 srl-eng，状态机接力**：03 写功能表单框架→`可以详细定义`、04 写组件业务→`已详细定义`。并行推进规则（SR 线与 pa-eng 线互不阻塞）同 §A.6。

**主线流转**（wft03-eng → wft04-eng → wft05-eng）：

```
可以详细定义 ──wft04锁定──→ 在详细定义 ──本Skill完成──→ 已详细定义 ──wft05锁定──→ 在pa-eng设计 ──wft05完成──→ 已pa-eng架构
   （wft03 写入）                 │                     （wft05 写入）
                                  │
                                  └─ 内部：产出系统需求概要 → 待确认方案 ──人类确认──→（确认后 srl-eng 推进至 已详细定义）
```

下游退回：已pa-eng架构/已详细定义 ──wft05退回──→ 需wft04修订 ──本Skill修订+人类确认──→ 已详细定义

> 注：`可以详细定义` 状态由 wft03-eng 写入（03 写功能表单框架），本 Skill 承接后**锁定为 `在详细定义`**（消费展开期间），完成组件业务并人类确认后推进为 `已详细定义`（04 写组件业务）。

**上游变更**（新系统需求框架汇入触发系统需求概要修订）：

```
可以详细定义 ──新系统需求框架修订──→ 可以详细定义（版本递增，本 Skill 未消费）
在详细定义   ──新系统需求框架修订──→ 在详细定义（版本递增，本 Skill 增量处理）
已详细定义   ──新系统需求框架修订──→ 待补充详细定义 ──本 Skill 补全──→ 已详细定义
```

**本 Skill 写回范围**：`待确认方案` / `在详细定义` / `已详细定义` / `待补充详细定义` / `需wft04修订`。`可以详细定义` 由 wft03-eng 写入。

**下游退回处理**：读取 wft05-eng 缺失说明 → 按人类改进方案修订（走 Phase B）→ 人类确认 → srl-eng → `已详细定义`。根因在系统需求框架时退回 wft03-eng。

| 6 | 资产写回与落账 | 06 写回 + 25 系统需求概要引用 + 推进 srl-eng 状态 + 提交基线 | 无（AI 自动，写回已确认节点） | 统一 | 06/25 写回 + 状态推进 | `06/25` |

### 5.1 Step Start · 前置校验与路由

> 入口条件与优先级判定遵循 [91 规范 §A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新系统需求框架）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

#### 5.1.1 入口检测

读取产品数据中的 `## AI可以处理节点` 分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口：

| # | 条件 | 检测方式 |
|---|------|---------|
| ① | **有新输入** | 「待 wft04-eng 处理」分节非空 |
| ② | **有待处理反馈** | 「待反馈处理」分节含本 Skill 产出节点 |
| ③ | **有下游退回** | 「待下游退回处理」分节含 `需wft04修订` 的节点 |

三类均不满足 → 输出"无待处理对象" → **退出**。

**退回门禁**（条件③时）：退回节点缺失说明中是否含人类改进方案（`[修改]`/`[同意]` 或下游 Skill 的具体指引）。已提供 → 通过。未提供 → 输出缺失说明，提示提供改进方案 → **退出**。

#### 5.1.2 输入校验

入口检测通过后进行校验。逻辑上不可能的条件为**硬退出**，数量/归属模糊条件为**软提示**：

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| srb-eng 不是 eng 路径系统需求框架节点 | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft03-biz` 或 nfr 路径 → **退出** |
| srb-eng 状态不是 `可以详细定义`/`待补充详细定义` | 状态不符（硬退出） | 输出不合格节点及当前状态 → **退出** |
| 系统需求框架缺少任一项（功能表单清单/操作活动清单/页面编排框架） | 要素缺失（硬退出） | srb-eng → `需wft03修订`，输出缺失说明 → **退出** |
| 选中 srb-eng >5 个 | 超建议阈值（软提示） | 输出超限提示 → 人类确认后继续或退出 |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

**锁定写回**：输入校验通过后，将承接的 srb-eng 状态写为 `在详细定义`（锁定态，本 Skill 消费展开期间，对齐 91 §A.6 锁定态=下游写入 与 wft03 §4.1）；完成组件业务且人类确认后推进 `已详细定义`（§5.7）。

#### 5.1.3 分流处理

按优先级顺序执行（源于 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序)）：

**① 退回优先**：存在 `需wft04修订` 且门禁通过 → 读取缺失说明，按 SKILL 指南走 Phase B（§5.4.2），确认后推进为 `已详细定义`

**③ 新系统需求框架路由**：有未处理系统需求框架 → 进入 Step 1 → Step 3，逐节点执行 Phase A 宿主匹配（§5.4.1）

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类反馈的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `06-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.7），保证下一轮 diff 只含人类变更。

**本 Skill 的操作条目**：布局组件 + 构件 + 组件业务 + pa-eng 收敛项。各条目的 `确认状态` 字段写入 `06-*.md` srl-eng 节点块中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3/4 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.1 入口②）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

按统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以系统需求框架为锚点的方案修订。先理解人类反馈在系统需求框架语境中的含义，执行修订后检查系统需求概要是否仍满足系统需求框架的需求。

按 [91 规范 §A.5.3](91-eos-biz-eng-spec.md#a53-ai-处理流程) 的流程处理人类自然语言反馈：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足系统需求框架 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 推进 srl-eng 至 `已详细定义` → **提交基线并更新 HEAD（机制见 §5.7，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

**特化参数**：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 系统需求框架 srb-eng——不脱离系统需求框架自行修订 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → `已详细定义`。存在 `[修改]`/`[驳回]` 无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需重做 Step 3~5 |
| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过。仅在新输入满足以下任一时，清除 `[已处理]`（保留 `[同意]`）回到待处理：<br>• 新输入是条目的直接上游节点（如新系统需求框架是系统需求概要来源）<br>• 新输入与条目同属一个架构层级且边界重叠（如新组件改变已有组件的类型或业务）<br>• 新输入导致条目被修订（变更影响声明标注修订型或结构型） |
| **级联触发条件** | 组件清单/布局组件/构件变更；组件业务新增/删除/类型变更；pa-eng 收敛项边界变化 → 触发需求级联检查 → 通过后触发资产对齐级联 |
| **资产对齐级联** | 方案变更影响 25 资产时更新对齐结论——系统需求概要变更 → 更新 25 系统需求概要引用（由 Step 6 维护） |

### 5.4 Step 3 · 系统需求详细设计

#### 5.4.1 Phase A：组件候选生成与宿主匹配

对每个功能表单的每个区域，按页面编排框架与操作活动清单生成组件候选（规则见 §3.2.1），然后逐组件做宿主匹配：

| 组件职责冲突或跨区域复用边界不清 | 标记 `[需裁决]` |

待聚合池按 `{引擎, CU, 功能表单, 区域, 组件候选列表}` 分组。此阶段仅粗略分组，布局组件判定和完整要素提取在 Phase C 执行。

#### 5.4.2 Phase B：修订已有系统需求概要

1. **要素提取**：从本轮系统需求框架提取组件类型、布局组件线索和组件业务候选（§3.2.1、§3.3.1）。已有组件业务仅追加不重建
2. **宿主匹配检查**：确认系统需求框架仍在系统需求概要职责范围内（§3.2.4）。复用 → 追加来源；扩展 → 全量重写保留历史；冲突 → `[需裁决]`。Phase A 是候选筛选，Phase B 是精确匹配——职责扩展时不得回退 Phase A 重选宿主
3. **重判定与关系检测**：基于全部功能表单重判组件类型与布局组件（§3.2.2、§3.2.3），比对基线判定五类关系（§3.3.2）。新增/变更组件业务 → 定义要素；pa-eng 收敛项 → 写入标记
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 srl-eng 节点末尾（§4.2）

#### 5.4.3 Phase C：新建系统需求概要

1. **判定布局组件** → 在页面编排框架基础上独立判断区域需要的布局组件组合（§3.2.2）
2. **识别构件** → 按展示/交互/数据/反馈四类独立识别（§3.2.3）
3. **定义组件业务** → 逐组件定义承载操作活动/数据来源/交互行为/状态反馈（§3.3.1，功能级不写实现）
4. **标注 pa-eng 层收敛项** → 组件边界/接口/存储/运行机制/NFR 均标注 `pa-eng层收敛-*`（§2.3）
5. **组装系统需求概要** → 写入 `06-*.md`：组件名称/所属功能表单/所在区域/布局组件或构件类型/组件业务/pa-eng 收敛项（完整要素见 §2.1.1）
