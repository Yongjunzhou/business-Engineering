# 规范化非功能需求 → 非功能需求框架
**SKILL 指南ID**: wft01-nfr-or2str

> **概述**：接收正式 规范化非功能需求，经前置校验、材料加载和反馈处理后，将非结构化非功能诉求转化为 bpl-nfr 非功能需求框架方案。该方案以"哪个角色在什么业务/平台语境下关注哪类非功能质量"为锚，完成非功能需求框架、需求清单和 22 分类资产对齐，并识别非功能诉求缺口形成补充 规范化非功能需求 材料。
>
> **输入 → 输出**：规范化非功能需求条目（≤10 条）/ 有反馈的 bpl-nfr 节点 → bpl-nfr 非功能需求框架方案（角色语境 + NFR 分类路径 + NFR 分类需求清单 + 22 分类对齐 + 补充 NFR 缺口）+ 规范化的相关方需求 推进为 `已分配` + bpl-nfr 推进为 `可以NFR设计`
>
> **适用场景**：瀑布式系统设计第1步 · 非功能需求路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v6.3 | **修订**：2026-08-28

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于非功能需求相关方——「你听懂了我关心的质量属性、适用语境和约束对象」。
>
> 把非结构化的 规范化非功能需求 转化为结构化的 bpl-nfr 非功能需求框架方案。不仅要**对内归组**——将分散的质量诉求按角色+语境+分类维度聚为分类需求清单；更要**向外延伸**——识别同一角色语境下的非功能诉求缺口和 22 分类资产对齐关系，为下游 NFR 量化设计（wft04-nfr）提供可展开的输入。

### 2.1 非功能需求框架（bpl-nfr）

**一句话**：本节讲 bpl-nfr——定义与归组锚点（2.1.1）、节点完整要素（2.1.2）；完备性判据见 §三 3.4。

#### 2.1.1 定义与分类

**一句话**：给 bpl-nfr 下定义——一个角色在一个语境下关注的一类非功能质量，四元组归组锚点决定其边界。

bpl-nfr 是 规范化非功能需求 在相关方需求层的结构化表达，末级节点为**非功能需求框架**。它回答"哪个角色在什么业务/平台语境下关注哪类非功能质量属性"。NFR 路径分工见 [91 规范 §10.5](91-eos-biz-eng-spec.md#105-nfr-路径-skill)。

bpl-nfr 的归组锚点为四元组：

| 锚点 | 说明 |
|------|------|
| 用户角色 | 提出或承受该非功能诉求的角色、外部系统或保障者 |
| 业务/平台语境 | 业务域、产品类型、bpl-biz/bpl-eng 线索或横切平台能力 |
| NFR 分类维度 | 22 资产中的一级类目 + 分类维度 |
| 适用对象线索 | 可能约束的 bpl-biz、bpl-eng、业务域、平台能力或全局对象（页面类型/具体页面 ID 仅作适用范围线索备注、不进归组键——页面 NFR 绑定由 wft04-nfr 任务 5 执行） |

#### 2.1.2 架构与属性

**一句话**：本节分两块看——bpl-nfr 内部由什么构成（NFR 分类需求项 + 22 分类对齐），以及写入 `02-*.md` 的节点完整要素。

bpl-nfr 的内部条目为 NFR 分类需求项（§2.2），分类锚定为 22 分类资产对齐（§2.3）。

bpl-nfr 节点完整要素（写入 `02-*.md` bpl-nfr 节点块）：

- bpl-nfr ID / 名称 / 角色 / 业务域或平台语境 / 链身份
- 来源 规范化的相关方需求 清单
- 22 分类路径与对齐判定
- NFR 分类需求清单
- 适用对象线索汇总
- 完备性检查结果
- 补充 NFR 材料引用
- 变更影响声明
- 版本号 / 确认状态

### 2.2 NFR 分类需求项

**一句话**：本节讲 bpl-nfr 的内部单元——NFR 分类需求项：定义与记录字段（2.2.1）；推断规则见 §三 3.3。

每个 bpl-nfr 节点内部按需展开为多个 NFR 分类需求项——它们是 wft04-nfr 量化设计的直接消费单元。§2.2 定义需求项是什么（数据字段），§3.3 定义如何推断它们。

#### 2.2.1 定义与记录字段

**一句话**：给 NFR 分类需求项下定义——bpl-nfr 内部逐条记录的质量诉求，字段清单如下。

NFR 分类需求项是 bpl-nfr 的内部条目。wft01-nfr 只把 规范化的相关方需求 转为可被 wft04-nfr 消费的分类化诉求，不生成系统级阈值。

每个需求项至少记录：

| 字段 | 说明 |
|------|------|
| 需求项名称 | 定性质量诉求的短名称 |
| 定性期望 | 规范化的相关方需求 中表达的性能、安全、可用性、易用性等期望 |

| 确认状态 | 人类反馈字段 |

### 2.3 22 分类资产对齐

**一句话**：本节讲 bpl-nfr 的归属锚——22 分类资产：定义与状态敏感性（2.3.1）；Q1~Q3+ 判定与三准则评审规则见 §三 3.3.4。

#### 2.3.1 定义与状态敏感性

**一句话**：22 资产是 NFR 分类的权威来源；wft01-nfr 只对齐分类维度（写回 22 疑似），不写具体需求。

22 资产是 NFR 分类与具体需求资产的权威来源（`22-eos-nfr-taxonomy.md`），在 EOS 设计过程中由 or03/wft01/wft04 三级精炼逐步积累。wft01-nfr 只对齐**分类维度**——Q1~Q3+ 判定与三准则评审（§3.3.4），不写具体需求及指标集（具体需求写回由 wft04-nfr 负责，见 [91 规范 §9.2](91-eos-biz-eng-spec.md#92-系统非功能需求设计wft04-nfr)）。

状态取值与敏感性：`已确认` 可稳定引用；`候选`（or03 标注、待 wft01 评审）/ `疑似`（wft01 三准则评审通过、待人类确认）只能作为线索，引用时标记 `[需裁决]`；`废弃` 不得作为归属。

> **承接 or03 候选待写**：or03 规范化时对无匹配 22 的 规范化非功能需求 会在 规范化的相关方需求 上下文（分析建议块/规范化的相关方需求 节点 `22 分类维度` 段）标注 `候选待写`——wft01-nfr 承接该标注纳入评审（聚类精炼 + Q1~Q3+ 判定 + 三准则评审），机制详见 §三 3.3.4。

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲设计的逻辑——为什么用 bpl-nfr 承接需求（3.1 转换原理）、怎么从 规范化的相关方需求 提取要素（3.2）、怎么推断分类需求项与 22 对齐（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四。

### 3.1 转换原理：为什么用 bpl-nfr 承接需求

**规范化非功能需求 是逐条质量诉求，bpl-nfr 要结构化**。规范化非功能需求 是用户口吻的逐条非功能诉求（如"列表查询要 2 秒内响应"、"要支持高峰期并发"），只有语义、没有架构位置——它约束哪个角色、在什么业务/平台语境、属于哪类非功能质量，都需要设计出来。本 Skill 的转换正是把 规范化非功能需求 层面（`01-*.md`）的诉求，变成 bpl-nfr 架构层面（`02-*.md`）的非功能需求框架节点。

**承接单位 = bpl-nfr（非功能需求框架），因为非功能诉求是"某角色在某种语境下关注某类质量"**。一条 规范化非功能需求 总蕴含"谁、在什么语境、关注什么质量"。把诉求归入"一个角色 + 一个语境 + 一个分类维度"（bpl-nfr 四元组，§2.1.1），诉求就获得架构位置；把 bpl-nfr 展开为"多个 NFR 分类需求项 + 22 分类对齐"，诉求就有了可展开的量化基础。角色+语境+分类维度同时保证**适用对象可追溯**——诉求约束全局、业务域还是具体 bpl-biz/bpl-eng/平台能力，必须落在某个可消费对象上（§3.4 完备性判据）。

**推断 + 补全，不是转录**。本 Skill 不只复述 规范化非功能需求 已说的质量诉求，还识别其指向的完整角色语境和分类归属。识别出的是"规范化非功能需求 蕴含的质量分类"；识别不出、但同角色语境下缺失的分类缺口，进入完备性检查补全，不脑补节点（§3.4 / §5.5）。

**bpl-nfr 通过补充 规范化非功能需求 渐进收敛到完整角色语境**。初次创建的 bpl-nfr 常只覆盖诉求的一段——适用对象线索缺失、验证语义缺失、同类语境缺口等。缺口不脑补节点，而是经完备性检查生成补充 规范化非功能需求 材料（§5.5）→ 经规范化的相关方需求预处理链返回为新一轮 规范化非功能需求 → Phase A 宿主匹配归入该 bpl-nfr（§5.4.1）→ Phase B 边界扩展（§3.2.3 边界扩展行）→ 版本递增（§4.1 上游变更）。多轮循环后 bpl-nfr 收敛到完整分类。这是本 Skill 的核心运行模型：**边界收敛与补需外推互为镜像**，由"补充 规范化非功能需求"这条回路衔接。

### 3.2 NFR 要素提取规则

**一句话**：本节讲从 规范化的相关方需求 提取 bpl-nfr 要素的规则——角色语境确定（3.2.1）、22 分类路径判定（3.2.2）、Phase B 边界匹配（3.2.3）。Phase B（修订已有 bpl-nfr）与 Phase C（新建 bpl-nfr）共用以下规则——先看 3.2.4 的 B/C 分工差异表，再读细节更顺。

要素提取是 bpl-nfr 设计的基础操作——从 规范化的相关方需求 文本中提取角色语境、分类路径、边界和适用对象。§3.2 给出提取规则，Phase B（修订）和 Phase C（新建）共用。两者的执行差异见 §3.2.4。

#### 3.2.1 角色语境确定

**一句话**：逐条 规范化的相关方需求 提取关注角色、语境、非功能诉求、待量化线索与适用对象，并按路由规则判定路径归属。

逐条 规范化的相关方需求 提取以下要素：

| 提取项 | 说明 |
|--------|------|
| 关注角色 | 操作用户、外部系统、运维保障者、管理者等 |
| 业务/平台语境 | 业务域、产品类型、bpl-biz/bpl-eng 线索、平台能力或全局 |
| 非功能诉求 | 性能、安全、可用性、易用性、可靠性、可部署性等 |
| 待量化线索 | 数值、比较词、验证词、约束条件；只记录不定指标 |
| 适用对象线索 | 全局/业务域/bpl-biz/bpl-eng/平台能力（页面类型/具体页面 ID 仅作适用范围线索备注，见 §2.2.1） |

路由规则：

| 情况 | 处理 |
|------|------|
| 规范化的相关方需求 实际要求业务流程、输出文档或业务规则 | 退回 `wft01-biz` |
| 规范化的相关方需求 实际要求引擎能力、CU、组件或平台治理功能 | 退回 `wft01-eng` |
| 规范化的相关方需求 只给出具体配置数据 | 标记为业务配置实例，不进入 NFR 设计 |
| 规范化的相关方需求 描述质量属性、运行约束或可验证非功能期望 | 进入 wft01-nfr |

#### 3.2.2 22 分类路径判定

**一句话**：Phase C 新建 bpl-nfr 时，从 22 资产动态读取分类清单，按诉求语义匹配分类维度。

Phase C 新建 bpl-nfr 时，从 22 资产动态读取一级类目和分类维度清单（每次运行时读取、不缓存），按 规范化的相关方需求 的非功能诉求语义匹配分类维度。wft01 仅有 规范化的相关方需求 文本信息，22 分类维度归属**全量标注 `[推断]`**，最终判定在 wft04 的量化设计中校验。

判定流程：

1. 匹配一级类目：性能/安全/可用性/易用性/可靠性/可部署性/...
2. 在一级类目下匹配分类维度：规范化的相关方需求 语义与分类维度定义的语义相似度。
3. 无法匹配已有分类维度 → 22-Q3（新增分类维度建议）。
4. 一级类目也无法承载 → 22-Q3+（新增一级类目 + 分类维度建议）。

#### 3.2.3 Phase B 边界匹配检查

**一句话**：Phase B 修订已有 bpl-nfr 时，检查本轮 规范化的相关方需求 是否在 bpl-nfr 节点边界内。

Phase B 修订已有 bpl-nfr 时，检查本轮 规范化的相关方需求 是否在 bpl-nfr 节点边界内。边界 = 同一角色 + 同一业务/平台语境 + 同一 22 分类维度。

按以下顺序匹配：

1. 同一用户角色或同类承受者。
2. 同一业务/平台语境。
3. 同一 22 分类维度。
4. 适用对象线索不冲突。

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| 直接归入 | 新 规范化的相关方需求 只补强已有需求项 | 追加来源，标记 `[确认]` |
| 新增需求项 | 角色语境和分类不变，但新增分类需求 | 加入清单，标记 `[新增]` |
| 边界扩展 | 适用范围线索扩展但仍属同一分类 | 修订 bpl-nfr，输出变更声明 |
| 分类冲突 | 分类维度需改变或跨维度 | 标记 `[需裁决]`，必要时拆分 |
| 宿主误匹配 | 不属于同一角色语境或分类维度 | 退回待聚合池或新建 |

#### 3.2.4 Phase B（修订）与 Phase C（新建）的提取差异

**一句话**：B/C 分工差异——判定范围、基线、边界定义、要素提取、22 重识别、变更传播六个维度。

| 维度 | Phase B 修订已有 bpl-nfr | Phase C 新建 bpl-nfr |
|------|------------------------|---------------------|
| 判定范围 | bpl-nfr 已承接的全部 规范化的相关方需求 + 本轮新 规范化的相关方需求 | 待聚合池本组 规范化的相关方需求 |
| 分类需求清单基线 | 以已有需求清单为基线，仅扫描本轮新 规范化的相关方需求 | 从零构建 |
| 边界定义 | 执行边界匹配检查（§3.2.3），可能检出直接归入/新增需求项/边界扩展/分类冲突/宿主误匹配 | 执行角色语境确定+22分类路径判定（§3.2.1+§3.2.2） |
| 要素提取 | 在基线基础上增量合并（关系检测见 §3.3.3） | 全量提取 |
| 22 重识别 | 合并重识别可能导致已有需求项的 22 判定变更——标记 `[22判定变更]` 并附变更原因 | 全量判定，无此问题 |
| 变更传播 | 需输出变更影响声明（§4.2） | 写"首版，无变更" |

### 3.3 NFR 分类需求项推断规则

**一句话**：本节讲逐需求项的推断规则——清单提取（3.3.1）、标注与来源（3.3.2）、Phase B 关系检测（3.3.3）、22 对齐判定与三准则评审（3.3.4）。

要素提取之后，下一步是推断——从已提取的要素中生成分类需求清单、标注来源类型、检测与基线的关系（Phase B 时）、判定 22 对齐并评审新分类维度。§3.3 定义这三类推断操作。

#### 3.3.1 分类需求清单提取

**一句话**：从操作范围内的全部 规范化的相关方需求 识别非功能质量诉求，去重收敛为分类需求清单，逐需求项判定 22 分类路径。

**识别 NFR 分类需求清单**：从当前操作范围内的全部 规范化的相关方需求 中识别非功能质量诉求。去重/收敛后形成分类需求清单，每个需求项 → bpl-nfr 中一个分类条目。多条 规范化的相关方需求 指向同一需求项时归入同一项（要素收敛）。

**逐需求项判定 22 分类路径**：从 22 资产动态读取一级类目和分类维度（每次运行时读取、不缓存），根据需求项的定性期望语义匹配。wft01 仅有 规范化的相关方需求 文本信息，22 判定**全量标注 `[推断]`**（Q3/Q3+ 标注 `[需裁决]`），定位为供下游 wft04 校验的**候选建议**而非最终判定。

> **待量化线索的处理**：wft01-nfr 只记录 规范化的相关方需求 中相关方已确认的目标值（数值、比较词和验证条件），**不将其转为系统量化指标**；系统侧指标设计（统计口径/测量方法/验收条件）由 wft04-nfr 产出。例如 规范化的相关方需求 说"页面查询要在2秒内响应"（目标值已在 or02 澄清中由相关方确认），wft01 记录 `待量化线索：规范化的相关方需求提到"2秒内"和"页面查询响应"`，量化指标（如 P95 响应时间 ≤ 2000ms）由 wft04 产出。

#### 3.3.2 需求项标注与来源类型

**一句话**：逐需求项判定要素并标注；定义四种来源类型（证据强度）。

对每个分类需求项逐项判定要素并标注。标注字段见 §2.2.1。

**来源类型定义**（NFR 分类需求项）：

| 来源类型 | 含义（含示例） |
|----------|---------------|
| `规范化的相关方需求明示` | 规范化的相关方需求 文本中直接说出该非功能质量诉求。如"采购单列表查询要在2秒内响应" → "页面查询响应时间"需求项 |
| `规范化的相关方需求隐含` | 规范化的相关方需求 未直接说出，但不补充则质量期望存在逻辑缺口。如"支持高峰期使用"→隐含并发性能需求 |
| `同类语境推断` | 同角色同业务域已有 bpl-nfr 的类似 NFR 分类模式，当前 规范化的相关方需求 语境与之高度相似时推断。如已有"采购订单管理"含"操作审计追溯"需求项 → 新建"采购合同管理"时推断也需要 |
| `资产线索推断` | 22 资产中已有与当前角色语境匹配的分类维度，但 规范化的相关方需求 未提及。如 22 资产已有"数据安全"分类维度位于当前角色语境下 → 推断应存在 |

#### 3.3.3 Phase B 需求项关系检测

**一句话**：Phase B 修订时把本轮提取的需求项与基线比对——五种关系（确认/无新增/22判定变更/补充/过时）。

Phase B 修订已有 bpl-nfr 时，边界检查通过后，将本轮提取的需求项与 bpl-nfr 已有分类需求清单比对。比对锚点为**需求项名称+22分类维度匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 需求项匹配 + 22 分类一致 + 至少一个来源非 `规范化的相关方需求明示` | 来源升级（`规范化的相关方需求隐含`→`规范化的相关方需求明示`、`同类语境推断`→`规范化的相关方需求明示`、`资产线索推断`→`规范化的相关方需求明示`），内部细分结论=`确认` |
| 无新增 | 需求项匹配 + 22 分类一致 + 所有来源已为 `规范化的相关方需求明示` | 追加 规范化的相关方需求 引用 + 增量合并新 规范化的相关方需求 中的定性期望/待量化线索（如有新内容），内部细分结论=`改进` |
| 22 判定变更 | 需求项匹配 + **22 判定不同**（合并重识别导致） | 更新 22 判定 + 内部细分结论=`22判定变更` + 变更原因。不新增需求项 |
| 补充 | 需求项不匹配 | 新增到分类需求清单，来源=`规范化的相关方需求明示`，内部细分结论=`新增` |
| 过时 | 基线已有需求项 **未被**本轮 规范化的相关方需求 覆盖（边界扩展触发语境重追踪后，基线中某些需求项不再落入新的 NFR 范围） | 内部细分结论=`过时` + 追加说明"边界扩展后未落入新的 NFR 分类范围，请确认是否移除"。保留该需求项在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 规范化的相关方需求 重新判定 22 分类路径**——新 规范化的相关方需求 可能改变需求项特征导致 22 判定变更（表中 `22判定变更` 行）。来源证据强度只升不降：`规范化的相关方需求隐含`/`同类语境推断`/`资产线索推断` → `规范化的相关方需求明示`，在 `确认` 行触发。

`[调整]` 是与关系类型正交的叠加标记：已有需求项的定性期望/适用范围线索/待量化线索变化，在关系标记之外叠加 `[调整]`。

#### 3.3.4 22 分类资产对齐判定与三准则评审

**一句话**：本节讲分类需求项如何归属到 22 分类资产——Q1~Q3+ 对齐判定（找匹配/需扩展/候选新增）与三准则评审（新分类维度能否写入 22）。

**Q1~Q3+ 对齐判定**——逐分类需求项判定其与 22 分类维度的对齐关系：

| 判定 | 条件 | 动作 |
|------|------|------|
| `22-Q1` | 规范化的相关方需求 语义明确落入已有已确认分类维度 | 引用已有分类维度 |
| `22-Q2` | 规范化的相关方需求 是已有分类维度的子类、扩展场景或边界细化 | 引用已有分类维度 + 提出候选扩展说明，等待 wft04 校验 |
| `22-Q3` | 现有一级类目可承载，但缺少分类维度 | 提出候选新增分类维度建议，标记 `[需裁决]`，不作为资产事实 |
| `22-Q3+` | 现有一级类目也无法承载 | 提出候选新增一级类目 + 分类维度建议，标记 `[需裁决]`，不作为资产事实 |

**三准则评审**——Q3/Q3+ 候选与承接 or03 `候选待写` 的新分类维度，在写回 22 前须经三准则评审（三准则全过 → 写回 22 疑似，待人类在 22 反馈区确认；任一不过 → 22 反馈区建议废弃，不写回）：

| 准则 | 判定 |
|------|------|
| **可复用性** | 该分类维度在 ≥1 条 规范化非功能需求（同角色或跨语境）中稳定出现，非一次性诉求；或与已有分类维度边界不重叠但有独立语义价值 |
| **可定义性** | 能给出清晰的名称和定义，与 22 资产既有分类维度边界不重叠（边界差异明确可述） |
| **可验证性** | 下游 wft04-nfr 可据此量化展开（有对应质量属性、可验证指标路径），非空泛质量主张 |

评审时机：承接 or03 `候选待写` 与自身检出的 Q3/Q3+ 候选，均在 Step 3 聚类精炼名称与定义后评审，Step 5 按评审结果写回（详见 §5.5 与 §5.6）。

### 3.4 完备性判据

**一句话**：判据汇总表——按五项核对 bpl-nfr 是否完备；实际执行在 §5.5 Step 4。

| 检查项 | 通过标准 | 不通过处理 |
|--------|----------|------------|

| 分类资产对齐明确 | 22 判定已完成，Q3/Q3+ 有三准则评审结论 | 标记 `[需裁决]` |

## 四、节点演进：生命周期与变更传播

**一句话**：本章讲 bpl-nfr 节点设计与确认后的演进机制——生命周期（4.1，节点状态四态主线 + 上游变更分流 + 本 Skill 写回范围）与变更传播（4.2，修订后写变更影响声明告诉下游 wft04）。

### 4.1 bpl-nfr 节点生命周期

**一句话**：本节讲节点状态怎么走——四态主线（待确认方案→可以NFR设计→在NFR设计→已NFR设计）+ 上游变更三条分流；本 Skill 的写回范围见下。

bpl-nfr 节点在 wft01-nfr 与 wft04-nfr 之间沿统一生命周期流转。通用四态主线 + 上游变更三分流规则见 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型)。

**主线流转**（wft01-nfr ←→ wft04-nfr）：

```
待确认方案 ──人类确认──→ 可以NFR设计 ──wft04锁定──→ 在NFR设计 ──wft04完成──→ 已NFR设计
     ↑                        ↑                         │
     │                        │               wft04退回  │
     │                        │                         ↓
     └─── wft01修订 ────── 需wft01修订 ←───────────────┘
```

**上游变更**（新 规范化的相关方需求 汇入触发 bpl-nfr 修订）：

```
可以NFR设计 ──新规范化的相关方需求修订──→ 可以NFR设计（版本递增，wft04 未消费）
在NFR设计   ──新规范化的相关方需求修订──→ 在NFR设计（版本递增，wft04 增量处理）
```

**本 Skill 的写回范围**：`待确认方案` / `可以NFR设计` / `待补充NFR设计` / `需wft01修订`。`在NFR设计` 和 `已NFR设计` 由 wft04-nfr 写入和推进。

下游退回 `需wft01修订` 时：读取 wft04-nfr 的缺失说明 → 按人类改进方案修订 bpl-nfr（走 Phase B 修订流程）→ 人类确认 → bpl-nfr → `可以NFR设计`。

### 4.2 bpl-nfr 变更传播协议

**一句话**：每次修订已有 bpl-nfr 后写变更影响声明——四类变更（无/增量/修订/结构）各告诉下游 wft04 该怎么做。

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板、增量清单与变更影响声明的分工）见 [91 规范 §A.7](91-eos-biz-eng-spec.md#a7-变更传播协议)。

**一句话**：一次运行 = Step Start 入口路由 → Step 1 材料加载 → Step 2 反馈处理 → Step 3 角色 NFR 分类设计 → Step 4 补充 NFR 与变更声明 → Step 5 资产写回与落账 → Step End 输出与对话反馈。反馈走自然语言对话（§5.3），跨轮余留由 AI 标记持久化（§5.3 状态机）。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 前置校验与路由 | 变更感知 + 入口检测、输入校验、退回优先路由 | 无（AI 自动） | 统一 | 就绪 / 结束 | — |

| 2 | 方案反馈处理 | 读"待反馈处理"分节 + 对话处理人类修改意见 | **有**——对话反馈修改意见 / 整体确认 | 对话 | 调整后的 bpl-nfr 方案 | `02` |
| 3 | 角色 NFR 分类设计 | Phase A 路由 / B 修订 / C 新建 bpl-nfr | 无（AI 产出，之后对话反馈） | 统一 | bpl-nfr 节点方案（分类 + 需求清单） | `01/02` |

**反馈机制一句话**：反馈走**自然语言对话**（AI 产出方案后不结束对话，§5.3）；跨轮余留反馈由 AI 标 `[修改]`/`[驳回]` 入"待反馈处理"分节（§5.3 状态机）；人类线下修订经 Step Start 变更感知（git diff，§5.1 变更感知）检出后纳入"待反馈处理"分节；AI 每轮写回提交基线（§5.6），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

### 5.1 Step Start

**一句话**：先变更感知（检出人类线下修订并纳入待反馈分节），再按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策路由（退回优先 → 反馈处理 → 新输入），无待处理对象即退出。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 规范化的相关方需求）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

**入口判定**（在变更感知后执行）：按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策流程执行。先读取 `01-*.md`/`02-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表，再按以下顺序处理：

#### 5.1.1 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 规范化的相关方需求 状态不是 `待处理` | 状态不符（硬退出） | 输出不合格条目及当前状态 → **退出** |
| 规范化的相关方需求 类型为 FR-BIZ | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft01-biz` → **退出** |
| 规范化的相关方需求 类型为 FR-ENG | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft01-eng` → **退出** |
| 规范化的相关方需求 为业务配置实例 | 实例标记（硬退出） | 标记并提示不进入 NFR 设计 → **退出** |
| 规范化的相关方需求 >10 条 | 数量超限（软提示） | 输出超限提示 → 人类确认后继续或退出 |
| 规范化的相关方需求 混入多个无关角色语境 | 边界混杂（软提示） | 输出边界混杂提示 → 人类确认拆分后继续或退出 |
| 无任何入口条件满足 | 无待处理对象（硬退出） | 输出"无待处理对象"→ **退出** |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

#### 5.1.2 退回优先（§A.4.3 门禁）

存在 `需wft01修订` 的 bpl-nfr 节点（来自"待下游退回处理"分节）：
- 检查人类是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注或下游 Skill 的具体改进指引）
- 已提供 → 通过门禁，读取 wft04-nfr 的缺失说明，按 SKILL 指南走 Phase B 修订流程
- 未提供 → 输出 wft04-nfr 的缺失说明 + 提示提供改进方案 → **退出**

#### 5.1.3 反馈处理

存在"待反馈处理"分节中的 bpl-nfr 节点（确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2 处理（§5.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 规范化的相关方需求，Step End 时提示。

#### 5.1.4 新 bpl-nfr 路由

有未处理的 规范化的相关方需求条目（来自"待 wft01-nfr 处理"分节）→ 进入 Step 1→Step 3，逐条执行 Phase A 语境提取与路由（§5.4.1），归入已有 bpl-nfr（→Phase B）或待聚合池（→Phase C）。

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 bpl-nfr 的角色语境/分类维度/需求清单。Step 3 的 Phase B 宿主匹配必须基于 Step 2 修改后的最新 bpl-nfr 内容，不得使用缓存旧状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

### 5.2 Step 1 · 设计材料加载

**一句话**：把本轮要处理的材料加载齐——先安全复查（git diff 检非预期修改），再读 AI 可以处理节点，最后按需索引导航。变更感知已在 Step Start 完成（§5.1）。

加载产品数据与资产文档遵循 [91 规范 §A.3.3](91-eos-biz-eng-spec.md#a33-产品数据文档与资产文档读取与写回约定) 的统一读取协议：AI可以处理节点优先 → 索引导航。

**步骤一：安全复查**

Step Start 已检出人类反馈并纳入"待反馈处理"分节（§5.1 变更感知）。此处按 §A.3.3 R0a 做加载前安全检查：`detect-changes.sh` 检出人类非预期修改时标记 `[需确认]`，不自动推进。

**步骤二：优先读取**（通过 `## AI可以处理节点` 定位本轮入口）：

入口判定通过后（§5.1.1），从 `## AI可以处理节点` 对应分节获取待处理节点 ID 列表：
- 有新输入 → 读「待 wft01-nfr 处理」分节
- 有待处理反馈 → 读「待反馈处理」分节
- 有下游退回 → 读「待下游退回处理」分节

逐节点：Bash("grep -n '@{节点ID}' 目标文件") 定位行号 → Read 节点块。

**步骤三：索引导航**（AI可以处理节点无待处理时，或按域浏览时）：

1. Bash("grep -n '索引行数：' 目标文件") → 定位索引行号 L
2. 从 L 提取 N → Read 业务域索引
3. 按锚点 Read 域内索引 → 获取节点 ID 列表
4. 按需：Bash("grep -n '@{节点ID}' 目标文件") → 定位行号 → Read 节点

**加载清单**（按需扩大 - 仅在索引缺失、候选冲突、资产全貌不足以判断边界或追溯关系断裂时）：

1. `01-*.md` 树画像 / 状态队列 / 节点索引 — 定位本轮 规范化非功能需求条目正文块及追溯线索
2. `02-*.md` STR 树画像 / 状态队列 / 节点索引 — 定位本轮 bpl-nfr 节点块，同时读取相关 bpl-biz/bpl-eng 索引用于适用范围线索
3. `21-eos-stakeholder-roles.md` — 角色定义、业务域和角色类型线索
4. `22-eos-nfr-taxonomy.md` — NFR 一级类目/分类维度清单（运行时动态读取，不缓存）

**按需扩大规则**（[91 规范 §11.12](91-eos-biz-eng-spec.md#1112-按需读取规则)）：

- 规范化的相关方需求 / bpl-nfr 正文块 — 按 ID 从索引定位

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `01-*.md`/`02-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.6），保证下一轮 diff 只含人类变更。

**本 Skill 的条目**：角色语境 + 每个 NFR 分类需求项 + 每条 22 分类建议 + 每条补充 NFR 缺口。各条目的 `确认状态` 字段位于 `02-*.md` bpl-nfr 节点块各条目正文中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.3）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.6），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足 规范化非功能需求 需求 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 推进 bpl-nfr 至 `可以NFR设计` → **提交基线并更新 HEAD（机制见 §5.6，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

> **原则**：反馈处理不是对人类标注的机械执行，而是以 规范化非功能需求 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解人类反馈在 规范化非功能需求 需求语境中的含义，再执行修订，最后检查修订后的 bpl-nfr 是否仍满足 规范化的相关方需求 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 本 Skill 的锚点是 规范化非功能需求——反馈处理以 规范化非功能需求 需求理解为锚，不脱离 规范化的相关方需求 文本内容自行修订 |
| **操作条目** | 角色语境 + 每个 NFR 分类需求项 + 每条 22 分类建议 + 每条补充 NFR 缺口。各条目的 `确认状态` 字段写入 `02-*.md` bpl-nfr 节点的对应条目中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → bpl-nfr → `可以NFR设计`。存在 `[修改]`/`[驳回]` 且无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需进入 Step 3 重做 |
| **级联触发条件** | 角色语境或被驳回/修改导致 NFR 分类维度变更、22 分类拓扑变化或需求清单重组 → 触发需求级联检查（重验修改后 bpl-nfr 是否仍满足 规范化非功能需求 需求）→ 通过后触发资产对齐级联 |

**处理规则**：

1. 从当前轮次对话上下文或退回缺失说明中读取人类反馈意图
2. **逐条处理**（按人类反馈内容）：
   - AI 输出方案后人类直接回复修改意见 → 在当前轮次继续对话处理，不重新走 Step Start
   - wft04 退回的 `需wft01修订` → 下一轮 Skill 调用时走 Step Start 退回优先
3. 修改后检查是否仍满足该 bpl-nfr 所承接的 规范化非功能需求 需求
4. 修改导致结构性变更（角色语境/分类维度/需求清单重组）→ 按需重入 Step 3
5. 全部条目获流水线开发者认可 → bpl-nfr → `可以NFR设计`

按 [91 规范 §A.5.3](91-eos-biz-eng-spec.md#a53-ai-处理流程) 的流程处理人类自然语言反馈：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足 规范化非功能需求 需求 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

### 5.4 Step 3 · 角色 NFR 分类设计

**一句话**：核心设计步——Phase A 语境提取与路由（§5.4.1），Phase B 修订已有 bpl-nfr（§5.4.2），Phase C 从零新建（§5.4.3）。

#### 5.4.1 Phase A：规范化的相关方需求 语境提取与路由

对每条新 规范化的相关方需求 做两件事：先确定它的路径归属（NFR / biz / eng），再确定它的宿主归属（已有 bpl-nfr / 待聚合池）。

**Step ① 路径归属判定** → 从 规范化的相关方需求 语义提取关注角色、业务/平台语境、非功能诉求和适用对象线索（提取项见 §3.2.1），按以下规则分流：

| 规范化的相关方需求 实际描述 | 路由 |
|------------|------|
| 业务流程、输出文档或业务规则 | 退回 `wft01-biz` |
| 引擎能力、CU、组件或平台治理功能 | 退回 `wft01-eng` |
| 具体配置数据（非质量属性） | 标记为业务配置实例，不进入 NFR 设计 |
| 质量属性、运行约束或可验证非功能期望 | 进入 wft01-nfr，继续 Step ② |

**Step ② 宿主匹配** → NFR 路径确认后，逐条判断该 规范化的相关方需求 属于哪个 bpl-nfr：

| 条件 | 路由 |
|------|------|
| 规范化的相关方需求 的角色 + 业务/平台语境 + 22 分类维度落入已有 bpl-nfr 的分类边界 | 归入该 bpl-nfr → Phase B |
| 不满足 | 进入待聚合池 → Phase C |

待聚合池按 **同一角色 + 同一语境 + 同一 22 分类维度** 分组（`{角色, 语境, 22分类维度, 规范化的相关方需求列表}`）。此阶段仅粗略分组，需求项去重和完整要素提取在 Phase C 执行。

#### 5.4.2 Phase B：修订已有 bpl-nfr

Phase B 将新 规范化的相关方需求 归入已有 bpl-nfr。四步按序执行，完成后节点状态保持 `待确认方案`。

**Step ① 要素提取** → 从本轮 规范化的相关方需求 提取关注角色、业务/平台语境、非功能诉求、待量化线索和适用对象线索。先提取后检查——分类维度冲突时需输出分类裁决项。（要素定义见 §3.2.1）

**Step ② 边界匹配检查** → 确认 规范化的相关方需求 仍在 bpl-nfr 分类边界内（规则见 §3.2.3）。以匹配结果分流：

| 匹配结果 | 动作 |
|---------|------|
| 直接归入（仅补强） | 追加 规范化的相关方需求 来源 |
| 新增需求项 | 加入分类需求清单 |
| 边界扩展 | 更新适用范围线索 + 输出变更声明 |
| 分类冲突 | 标记 `[需裁决]`，必要时拆分 |
| 宿主误匹配 | 退回待聚合池，留待下一轮 |

> Phase A 匹配是候选筛选，Phase B 是精确匹配。边界扩展时 **不得** 回退 Phase A 重选宿主——继续完成 Phase B 全部处理并标记 `[推断]` 供人类裁决。宿主误匹配时不修改原 bpl-nfr，直接退回待聚合池。

**Step ③ 需求项关系检测** → 比对已有基线，判定确认/无新增/22判定变更/补充/过时。详见 §3.3.3 关系检测表。

**Step ④ 变更影响声明** → 判定变更类型（无变更/增量型/修订型/结构型），写入 bpl-nfr 节点末尾。格式见 §4.2。

#### 5.4.3 Phase C：新建 bpl-nfr

Phase C 将待聚合池中同一分组的 规范化的相关方需求 聚合为一个新的 bpl-nfr 节点。五步按序执行：

**Step ① 确定角色语境** → 从 规范化的相关方需求 语义提取关注角色、业务/平台语境、链身份。（提取规则见 §3.2.1）

**Step ② 判定 22 分类路径** → 按"一级类目 → 分类维度 → Q1/Q2/Q3/Q3+"顺序判定。全量标注 `[推断]`。（判定规则见 §3.2.2 与 §3.3.4）

**Step ③ 生成分类需求清单** → 识别需求项 → 去重收敛 → 逐项判定来源类型与待量化线索 → 标注字段。（规则见 §3.3.1、§3.3.2）

**Step ④ 执行完备性检查** → 五项检查：角色语境清楚 / 分类维度单一 / 适用对象有线索 / 待量化线索保留 / 分类资产对齐明确。（判据见 §3.4）

**Step ⑤ 组装写回** → 合并角色语境 + 22 分类路径 + 分类需求清单 + 适用对象线索汇总 + 完备性检查结果，以 `待确认方案` 状态写入 `02-*.md`。（完整要素见 §2.1.2）

### 5.5 Step 4 · 补充 NFR 与变更声明

**一句话**：对每个 bpl-nfr 做完备性检查——闭合（5.5.1）、要素机械检查（5.5.2）、补充 NFR 材料（5.5.3）、22 分类资产触发（5.5.4）。

Step 4 按每个 bpl-nfr 实例独立执行。新建 bpl-nfr → 全量检查；修订已有 bpl-nfr → 仅当分类维度拓扑变化（新增/过时/维度归属变更）时重验闭合，要素机械检查始终针对变更节点执行。

#### 5.5.1 NFR 闭合检查

逐 bpl-nfr 检查 NFR 分类需求清单的三类闭合（分类缺口、适用范围缺口、验证语义缺口）。检查结果按以下类型分流：

| 检出条件 | 缺口类型 | 处理动作 |
|---------|---------|---------|
| 关注角色缺失——不知道谁提出/承受该非功能约束 | `[需澄清]` | 不生成补充材料（无法确定角色语境） |
| 适用对象缺失——不知道约束全局、业务域、bpl-biz、bpl-eng 还是平台能力 | `补充规范化的相关方需求` | 进入补充 NFR 材料生成 |
| 可验证语义缺失——不知道通过什么现象证明该质量已满足 | `澄清项` | 进入补充 NFR 材料生成 |
| 分类维度冲突——同一 规范化的相关方需求 无法稳定归入已有 22 分类维度 | `分类裁决` | 输出分类裁决项，不自行并入 |
| 一个 规范化的相关方需求 混合多个 NFR 维度 | `拆分建议` | 输出拆分建议，退回 规范化的相关方需求预处理 |

> 不因缺口脑补节点——缺口就是缺口。检出缺口后如实进入「补充 NFR 材料生成」（§5.5.3）。

#### 5.5.2 要素机械检查

逐 bpl-nfr，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全：

| # | 检查项 | 不通过时 |
|---|--------|---------|
| ① | 用户角色 / 业务域或平台能力语境 / NFR 一级类目 **非空** | 标记 `[覆盖缺口]` + 缺失说明 |
| ② | NFR 分类需求清单 **非空**，逐项标注定性期望、适用范围线索和来源类型 | 同上 |
| ③ | 22 分类资产对齐（Q1/Q2/Q3/Q3+）**到位**，`[推断]` 标记已写入推理依据，Q3/Q3+ 已有三准则评审结论 | 同上 |
| ④ | 变更影响声明 **已写入**（首版写"首版，无变更"） | 同上 |

#### 5.5.3 补充 NFR 材料生成

闭合缺口时生成。写入 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/<YYYYMMDD>-<bpl-nfr名称>补充原始需求材料.md`，包含：材料编号 / 来源 bpl-nfr / 来源 规范化的相关方需求 / 缺口类型 / 补充需求文本 / 推断依据 / 建议类型（`补充规范化的相关方需求` / `澄清项` / `拆分建议` / `分类裁决`）/ 确认状态。同时登记到 `01-eos-sysdev-status.md` 表 A（生命周期=`已登记`）。文件引用写入 bpl-nfr 节点的完备性检查结果。

#### 5.5.4 22 分类资产触发检查

从 22 资产比对当前 bpl-nfr 的分类维度引用，判定当前批次 bpl-nfr 是否触发了 22 分类资产增补需求（当前批 bpl-nfr 使用了 22 中不存在的分类维度，或 Q3+ 候选分类建议指向新的维度定义）。缺分类定义且触发时 → 对候选分类维度执行聚类精炼 + 三准则评审（§3.3.4），形成 22 分类建议（不直接固化），在 Step End 中提示人类审查后录入 22 资产。不生成补充 规范化的相关方需求 材料、不登记 规范化的相关方需求 状态表、不自动补。

### 5.6 Step 5 · 资产写回与落账
