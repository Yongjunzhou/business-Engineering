# comformed-2-91spec · §11 合规收束

> **设计依据**：[91-eos-biz-eng-spec.md](../91-eos-biz-eng-spec.md) §十一（权威源）
> **适用文档**：01~07 产品数据文档 + 21~28 资产文档。08、09 保留原格式，不适用。
> **触发方式**：对话式编辑结束后，人类回复「合规收束」或直接调用本 Skill。

---

## 一、职责定位

### 1.1 目的与目标

> **主要目的**：对话式编辑产品数据/资产文档后，逐条核对文档当前状态与 91 规范 §11 规则的差距——可从文档自身统计得出的偏差自动修复，需要理解变更语义的由 AI 判定后维护，超出自动处理范围的汇入异常报告供人类确认。

**目标**：

1. 自动修复可统计偏差——索引行数、节点计数、待裁决计数、元数据字段（版本号/日期/HEAD hash）
2. 校验节点格式完整性——自适应目标文档实际使用的节点表示格式，不做预设
3. 校验 @id 体系——前缀合规、本文件内定义点存在、跨文件引用可追溯
4. 基于 git diff 识别本轮变更——同步 AI可以处理节点 分节、追加 AI最近变更 记录
5. 版本递增并提交——文档回到 §11 合规状态，HEAD hash 成为下次变更感知的锚点

| 负责 | 不负责（路由指向） |
|------|-------------------|
| 适用范围内的文档（01~07、21~28）收束 | 08/09——保留原格式，不适用 §11 |
| 可统计偏差自动修复 | 文档内容正确性——由各 wft* Skill 在设计过程中保证 |
| 格式完整性校验——自适应文档实际使用的节点表示格式 | 格式迁移（块式↔表单式）——由人类决策后手动执行 |
| @id 前缀校验 + 本文件内定义点/引用点交叉比对 | 业务语义审查——由人类在各轮对话编辑中确认 |
| 基于 git diff 同步 AI可以处理节点 + AI最近变更 | 资产变更的级联影响分析——由各 Skill 的变更传播协议处理（§A.7） |
| 不可自动处理项汇入异常报告 | — |

### 1.2 与上下游的衔接

本 Skill 不处于设计接力链（wft01→wft02→...→wft06）中——它是**对话式编辑和 Skill 写回之后的合规收束点**。任何对 §11 适用文档的修改，最终通过本 Skill 确保文档回到合规状态。

| 方向 | 触发方 | 交接内容 |
|------|--------|---------|
| 上游 | 人类（对话式编辑） | 一轮或多轮对话中对目标文档的任意编辑——增/删/改节点、变更状态、标注反馈。通过 `git diff`（§11.10）感知变更 |
| 上游 | 任意 wft* Skill（§10.3~§10.5） | Skill 运行完成后对产品数据/资产文档的写回。写回协议见 §11.11 |
| 下游 | git | 合规收束完成后自动 commit。commit 后的 HEAD 写入 `**HEAD @上次 AI 运行**`（§11.10），成为下次对话的变更感知锚点 |

## 二、§11 合规要素基础

> 本章定义合规收束的操作对象——§11 合规要素及其有效状态。各要素的权威定义见 [91 规范 §十一](../91-eos-biz-eng-spec.md#十一产品文档结构读写及反馈)。如何检查与修复见第三章。

### 2.1 文档元数据

文档开篇的三个元数据字段（§11.2），由 AI 在每次写回时维护（§11.11）：

| 字段 | 格式 | 有效状态 |
|------|------|---------|
| `**文档版本**` | `v{主版本}.{次版本}` | 次版本每次收束递增；主版本由人类手动管理 |
| `**修订日期**` | `YYYY-MM-DD` | 最近一次修改日期 |
| `**HEAD @上次 AI 运行**` | 7 位 hex commit hash | 必须等于 `git rev-parse --short HEAD` |

### 2.2 自描述索引

`索引行数：{N}`（§11.2），N 为紧跟其后的索引表格的总行数（含表头）。AI 以此为入口发现索引表格的规模，不依赖行号（§11.9 R13）。

### 2.3 分组索引

`## 业务域索引` 或 `## 角色索引`（§11.2~§11.3）——文档的顶层导航表。每行对应一个分组（域/角色组），列出该分组的节点数和锚点入口。列头决定分组维度，不同文档可能使用不同列头（如 `域 \| 节点数 \| 入口` 或 `角色组 \| 节点数 \| 入口`）。

### 2.4 域级/角色组级组织

每个分组在文档中占据一个独立节（§11.3），结构为：

```
## {分组名称} {#anchor}
### {分组名称}产品索引          ← 该分组内按产品/项目维度的二级索引
### 产品正文块 / {产品名}        ← 节点正文区
```

**有效状态**：
- `## {名称}` 必须有 `{#anchor}`，且锚点与分组索引入口列一致（§11.3 R1）
- 产品索引的 `节点数` 和 `待裁决数` 必须与实际节点数量一致
- 正文块组织方式取决于节点表示格式（见 §2.5）

### 2.5 节点

节点是文档的核心内容单元（§11.4）。同一文档内所有节点统一采用一种表示格式。

**块式表示**：`##### @{id} 节点名称` 为 heading，后跟 `**字段**` 行。必要字段：`**类型**`、`**父节点**`、`**确认状态**`。有子条目时还须有 `**子条目状态**`（汇总子条目的确认状态分布）。

**表单式表示**：节点为横表中的一行，13 个字段为列——`节点ID / 节点名称 / 节点层级 / 层级名称 / 父节点ID / 复用方式 / 复用节点ID / 输入 / 输出 / 节点说明 / 生命周期状态 / AI建议 / 人类反馈`。`节点层级` ∈ {L1, L2, L3, L4, L5, L6}；`复用方式` ∈ {原创, 复用, 改进, —}。

### 2.6 ID 体系

@id 是节点的全局唯一标识（§11.5）。分三个层面：

| 层面 | 规则 | 定义位置 |
|------|------|---------|
| **ID 前缀** | 每个 @id 的前缀标识其归属文档类型（如 `@bp-`→bpd-biz 节点、`@engine-`→引擎、`@node-`→构件类型）。已知前缀列表见 §11.5 | §11.5 |
| **定义点** | 每个 @id 在唯一位置被定义——块式文档为 `##### @{id}` heading，表单式文档为横表中"节点ID"首列等于该 @id 的行 | §11.9 R13a |
| **引用点** | 其他节点通过父节点/复用节点/输入/输出等字段引用该 @id——此时该 @id 不出现在"节点ID"首列，仅表明被引用关系 | §11.9 R13a |

复用/改进节点的原创追溯：沿 `复用节点ID`（表单式）或 `**复用节点**`（块式）逐级追溯，直至找到 `复用方式=原创` 的节点（§11.9 R13b）。

### 2.7 AI最近变更

`## AI最近变更` 节（§11.6）——记录 AI 最近对本文档的写回操作。五列：`时间 / 操作 Skill / 操作类型 / 节点 ID / 变更摘要`。保留最近 30 条（§11.6 R8），由 AI 在每次写回时追加（§11.6 R7）。人类不直接修改此表。

### 2.8 AI可以处理节点

`## AI可以处理节点` 节（§11.7）——按 Skill 分节列出所有当前可被处理的节点。每个分节（`### 待 {Skill名称} 处理`）包含一个五列表：`节点 ID / 标题 / 优先级 / 当前状态 / 所属域（或所属角色）`。分节内容由各 Skill 在写回时自动维护（§11.7），确保与节点实际状态一致。

标准分节集合见 §11.7；不同文档的实际分节取决于该文档被哪些 Skill 消费。

### 2.9 人类反馈标注

人类对节点的确认/修改/驳回意见（§11.8）。标注载体取决于节点表示格式——块式文档写在 `**确认状态**` 字段，表单式文档写在 `人类反馈` 列。

**有效值**：`[同意]` / `[修改]：{修改内容}` / `[驳回]：{驳回理由}` / `[需裁决]：{待决事项}` / 空（未标注）。人类可跨文档任意位置写非结构化反馈，AI 通过 `git diff`（§11.10）检测后标记 `[需确认]`（§11.8 R16）。

### 2.10 领域规则

| 规则 | 说明 |
|------|------|
| **R1** | 自动修复仅限可从文档自身统计得出的偏差。需要理解变更语义的由 AI 判定后写入，不自动执行 |
| **R2** | 节点格式（块式/表单式）由文档实际内容决定。本 Skill 不做预设分类，运行时自动检测 |
| **R3** | 不可自动处理的偏差汇入异常报告（❌错误 / ⚠️警告 / ℹ️提示），不阻塞收束流程 |
| **R4** | 版本号始终递增次版本。主版本号由人类手动管理 |

## 三、操作流程

### Step 布局总览

| Step | 名称 | 产出 | 写资产 |
|------|------|------|--------|
| Step Start | 前置校验与路由 | 变更范围 + 文档结构特征 | — |
| Step 1 | 材料加载 | 目标文档关键区域 + 节点列表 | — |
| Step 2 | 机械扫描与自动修复 | 自动修复写入 + 格式异常清单 | 目标文档（机械修复） |
| Step 3 | 语义判定与维护 | AI可以处理节点同步 + AI最近变更追加 + 异常报告 | 目标文档（语义维护） |
| Step End | 版本收束与提交 | 版本递增 + commit + 变更摘要 | 目标文档（版本/HEAD） |

---

### Step Start · 前置校验与路由

**入口**：人类回复「合规收束」或直接调用本 Skill。

**校验条件**（按顺序，命中即退出）：

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 目标文档为 08 或 09 | 不可处理 | 输出"08/09 保留原格式，不适用 §11"→ **退出** |
| 目标文档不在 01~07、21~28 范围内 | 不可处理 | 输出适用范围 → **退出** |
| `**HEAD @上次 AI 运行**` 缺失或为空 | 不可处理 | 输出"缺少变更感知锚点，请至少完成一次 AI 写回后再收束"→ **退出** |
| `git diff <hash>..HEAD -- <目标文件>` 无变更 | 无需收束 | 输出"文档无变更，无需收束"→ **退出** |

**变更感知**：

```bash
HASH=$(grep 'HEAD @上次 AI 运行' <目标文件> | grep -oP '[a-f0-9]{7,}')
git diff $HASH..HEAD -- <目标文件>
```

产出变更范围（变更文件列表 + 各文件 diff 行号范围）。

**结构嗅探**（不预设文档类型，运行时检测）：

```bash
# 索引类型
grep '## 业务域索引'     → 按业务域组织
grep '## 角色索引'       → 按角色组组织
# 若两者均无 → 报告"缺少分组索引"，仍继续后续步骤

# 节点格式
grep -c '^##### @'      → N 个块式节点
grep -c '^| @'          → M 个表单式节点

# 确认状态载体（用于 Step 2 和 Step 3 定位状态字段）
grep '确认状态'          → 块式
grep '人类反馈'          → 表单式

# AI可以处理节点分节列表（用于 Step 3 知道往哪些分节写）
grep '^### 待' <目标文件>
```

**多文件处理**：人类指定了多个目标文件时，逐文件执行 Step 1→Step 3，最后统一 Step End。

### Step 1 · 材料加载

**加载目标文档**（按需，不加载完整正文）：

```bash
# 1. 自描述索引
grep -A1 '自描述索引' <目标文件>

# 2. 分组索引（业务域索引或角色索引）
# 先由 Step Start 嗅探到的索引类型确定 heading 名，再读表格
grep -A $((N+1)) '## {索引类型}' <目标文件>

# 3. AI最近变更
grep -A 32 '## AI最近变更' <目标文件>

# 4. AI可以处理节点
grep -A 200 '## AI可以处理节点' <目标文件> | grep -B 0 -A 200 '^## ' | head -n -1
# （读到下一个 ##  为止）

# 5. 逐分组加载——按分组索引的锚点列表，逐分组读：
#    分组 heading → 产品索引 → 节点区（块式=heading列表，表单式=横表行）
```

**加载规则参考**：91 规范 §11 规则集（§11.1~§11.12），用于 Step 2 逐条核对。

**按需扩大原则**：仅在索引无法定位、引用跨文件、或人类明确要求时扩大读取范围。禁止默认全量加载（§11.12）。

---

### Step 2 · 机械扫描与自动修复

> 逐条核对文档状态与 §11 规则的差距。仅修复可从文档自身统计/正则得出的偏差。

#### 2.1 §11.1 文档区域顺序

**检查方式**：读文档所有 `## ` 和 `### ` heading 的出现顺序，对比 §11.1 要求的区域顺序——元数据 → 自描述索引 → 分组索引 → AI最近变更 → AI可以处理节点 → 正文区。

**自动修复**：AI最近变更节缺失→自动创建空表。其余区域缺失或顺序错乱→报告。

#### 2.2 §11.2 自描述索引

**检查方式**：统计分组索引表格的实际行数（含表头），与 `索引行数：{N}` 比对。

**自动修复**：不一致→写回实际行数。入口锚点无法定位→报告。

#### 2.3 §11.3 域级/角色组级组织

**检查方式**：逐分组统计实际节点数（块式=数 heading，表单式=数横表数据行）和待裁决节点数（搜索 `需裁决`），与产品索引的数值比对。

**自动修复**：不一致→写回实际值。同时更新分组索引的节点数汇总。锚点缺失或与索引入口不一致→报告。

#### 2.4 §11.4 节点格式

按 Step Start 嗅探到的节点格式执行对应检查：

**块式**：

| 检查 | 方法 | 处理 |
|------|------|------|
| `##### @{id}` 格式合规 | 正则 `^##### @[a-z][a-z-]*-\S` | 不符合→报告 |
| `**类型**` 字段存在 | 逐节点检查 | 缺失→报告 |
| `**父节点**` 字段存在 | 逐节点检查 | 缺失→报告 |
| `**确认状态**` 字段存在 | 逐节点检查 | 缺失→报告 |
| `**子条目状态**` 汇总准确 | 有子条目时统计子条目确认状态分布→比对 | 不一致→**自动写回** |

**表单式**：

| 检查 | 方法 | 处理 |
|------|------|------|
| 横表列数一致（预期 13） | 逐横表统计 `\|` 分隔的列数 | 不一致→报告 |
| `节点ID` 首列 `@` 开头 | 检查首列值 | 不符合→报告 |
| `节点层级` ∈ {L1~L6} | 逐行检查列值 | 非法值→报告 |
| `复用方式` ∈ {原创, 复用, 改进, —} | 逐行检查列值 | 非法值→报告 |

#### 2.5 §11.5 @id 前缀 + §11.9 定义点/引用点

**检查方式**：提取文档中所有 @id，逐 ID 检查前缀是否在已知列表中（`@bp- @srf- @srn- @doc- @engine- @node- @prod- @domain- @spr- @str- @nfr- @role-`）。再对每个引用字段中出现的 @id，验证其定义点存在（本文件内）。

**自动修复**：无。未知前缀→报告；本文件内定义点无法定位→报告；跨文件引用→报告"需人工确认"。

#### 2.6 §11.6 AI最近变更

**检查方式**：统计记录条数，检查五列齐全。

**自动修复**：超出 30 条→删除最旧行。列不齐或超链接格式异常→报告。

#### 2.7 §11.7 AI可以处理节点

**检查方式**：检查分节名、条目五列齐全、同一节点不跨分节重复。

**自动修复**：无。列不齐或重复→报告。分节内容的增删移由 Step 3 处理。

#### 2.8 §11.8 人类反馈格式

**检查方式**：读确认状态载体（Step Start 已嗅探——块式=`**确认状态**`，表单式=`人类反馈` 列），逐节点检查值是否在有效值集合内。

**自动修复**：无。非法值→报告。

#### 2.9 §11.10 变更感知锚点

**检查方式**：`**HEAD @上次 AI 运行**` 与 `git rev-parse --short HEAD` 比对。

**自动修复**：不一致→写入当前 HEAD。

#### 2.10 执行自动修复 + 汇总异常

上述检查中标记为"自动写回"的项目，**直接 Edit 写入目标文档**，不询问人类：

| 序号 | 规则 | 操作 |
|------|------|------|
| A1 | §11.2 | `索引行数` 写回实际行数 |
| A2 | §11.3 | 各分组产品索引的 `节点数`、`待裁决数` 写回实际值 |
| A3 | §11.3 | 分组索引的 `节点数` 汇总写回 |
| A4 | §11.4 | 块式文档 `**子条目状态**` 汇总值写回（若不准确） |
| A5 | §11.10 | `**HEAD @上次 AI 运行**` 写回当前 HEAD |

标记为"报告"的偏差收集为格式异常清单，汇入 Step 3 的异常报告。

### Step 3 · 语义判定与维护

> Step 2 修完了可从统计得出的偏差。本节处理需要理解变更语义的维护——哪些节点变了、应该怎么同步 AI可以处理节点 和 AI最近变更。

#### 3.1 变更分类

基于 Step Start 的 `git diff` 结果，逐变更块判定。使用 Step Start 嗅探到的确认状态载体来读状态字段：

| 变更类型 | 判定标准 | 后续动作 |
|---------|---------|---------|
| 新增节点 | diff 中出现新的节点定义点 | → 3.2 同步 AI可以处理节点 |
| 删除节点 | diff 中节点定义点被删除 | → 3.2 同步 + 3.3 检查引用 |
| 状态变更 | 确认状态字段值前后不同 | → 3.2 同步 AI可以处理节点 |
| 内容变更 | 节点存在，状态未变，其他字段/列值变化 | → 3.4 追加 AI最近变更 |
| 索引/元数据变更 | 由 Step 2 自动写回产生 | → 跳过 |

#### 3.2 AI可以处理节点 同步

逐变更节点，按以下规则同步到 `## AI可以处理节点` 对应分节（分节列表由 Step Start 嗅探获得）：

| 变更 | 操作 |
|------|------|
| 新增，确认状态=待处理/疑似 | 加入对应的 Skill 处理分节 |
| 新增，确认状态=已确认 | 不加入（已确认无需处理） |
| 确认状态从需裁决变为已确认/同意 | 从"待反馈处理"移除 |
| 确认状态变为需裁决 | 加入"待反馈处理" |
| 确认状态变为已废弃 | 从所有分节移除 |
| 删除节点 | 从所有分节移除 |
| 人类新增 `[修改]`/`[驳回]` 标注 | 加入"待反馈处理" |

**块式文档额外处理**：若节点含子条目且子条目有增减——检查 Step 2 的 A4 是否已覆盖；若未覆盖（如子条目散布在多个独立 heading 中），手动重算并写回父节点 `**子条目状态**`。

#### 3.3 引用完整性检查

对本轮变更节点引用的 @id（父节点/复用节点/输入/输出字段中的引用），检查：
- 目标定义点在本文件→验证可定位（Step 2 已做，此处仅确认）
- 目标定义点在其他文件（如 @engine-*→25 号、@bp-*→04 号）→报告"跨文件引用，请人工确认"
- 目标在任何文件均无法定位→报告"悬空引用"

#### 3.4 AI最近变更 追加

为本轮每个有实质内容变更的节点生成一条记录：

| 列 | 生成方式 |
|------|---------|
| 时间 | 当前日期 |
| 操作 Skill | 对话编辑 → `对话编辑`；Skill 运行后收束 → `{skill-name}（收束）` |
| 操作类型 | `新增` / `变更` / `删除`，含 `[→](#@id)` 超链接 |
| 节点 ID | 被操作节点的 @id |
| 变更摘要 | 基于 diff 内容和对话上下文，一句话总结 |

**全文档级变更**（大量节点同时变动）：节点 ID 填 "—"，超链接指向 `[](#)`，摘要写整体描述。追加后 >30 条 → 删最旧记录。

#### 3.5 异常报告汇总

合并 Step 2 收集的格式异常 + Step 3 发现的语义异常，按三级输出：

| 级别 | 含义 | 示例 |
|------|------|------|
| ❌ 错误 | 明确违反 §11 规则 | 横表列数不对；节点缺失 `**类型**` 字段；同一 @id 有多个定义点 |
| ⚠️ 警告 | 可能有问题 | 悬空引用；跨文件引用无法自动验证；@id 前缀不在已知列表 |
| ℹ️ 提示 | 建议关注 | AI最近变更 达 30 条上限；文档含混合格式（同时存在块式和表单式节点） |

## 四、AI 标记约定

增量清单使用 91 规范 §A.3.1 的四类标记：

| 标记 | 本 Skill 含义 | 示例 |
|------|-------------|------|
| `[新增]` | 本轮新增了该节点 | `[新增] @bp-proc-001 — 采购申请流程节点` |
| `[变更]` | 本轮修改了内容或状态 | `[变更] @node-budget — 生命周期状态：需裁决→已确认` |
| `[删除]` | 本轮删除了该节点 | `[删除] @node-obsolete — 已废弃构件` |
| `[需裁决]` | 异常报告中需人类裁决的项 | `[需裁决] @node-budget 归属待裁定——经营规划或财务管理` |

**增量清单示例**：

```text
[变更] @srf-proc-apply-001 — 确认状态：空→[同意]
[新增] @bp-proc-apply-002 — 新增采购审批节点（父节点 @bp-proc-apply-001）
[变更] @node-budget — 生命周期状态：需裁决→已确认，人类反馈：[同意]
[新增] @node-supplier-eval — 新增供应商评估构件（L6，父节点 @prod-procurement-product）
```
