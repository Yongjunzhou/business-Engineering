### 2.1 pa-eng 组件架构

**一句话**：本节讲 pa-eng 组件架构的概念——定义与层级（2.1.1）、架构与属性（2.1.2）；完备性判据见 §三 3.4。

#### 2.1.1 定义与层级

pa-eng 是 P0 平台引擎产品的产品架构，末级节点为**前端组件、后端组件、平台服务组件**。pa-eng 从系统需求概要 srl-eng、FR-BIZ 指标约束包和 NFR 约束包推导，回答各组件业务由什么组件承接、业务 IPO 指标和非功能质量指标由什么软件能力保障。布局组件与构件定义见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)，eng 路径分工见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-平台产品架构开发wft05-eng)。wft05-eng 的组件设计从它们出发，不重新定义页面需求：

- **布局组件**：平台 UI 的结构层次（多级横版、列表、单据、弹窗、指标、看板页面、辅助栏等）
- **构件**：安装在布局组件上的公共功能单元（功能按钮、右键菜单、快捷键、列定义、字段布局、图表类型、钻取等）

> **04 vs 05**：04=功能组件业务（页面元素，布局组件/构件 + 组件业务），05=产品组件（前端/后端/平台服务，07 pa-eng），**04 组件业务是 05 推断前后端组件的依据**。

#### 2.1.2 架构与属性

pa-eng 组件架构由三类组件、四类平台架构决策、组件依赖和 SR 详细定义构成。

每个 pa-eng 组件节点至少包含（写入 `07-*.md` pa-eng 节点块）：

- pa-eng ID / 名称
- 来源 srl-eng / 功能表单 / 组件业务 / CU 追溯
- 组件归属与组件类型
- 组件职责边界
- 组件类型（前端/后端/平台服务）及所承接的构件、活动或 NFR 约束行
- 前后端依赖关系
- 接口、事件或状态边界摘要
- NFR 约束行 ID、实现策略与消费版本
- 可用性子目标 / 响应时间设计预算（分解运算与组件级预算，如适用）
- FR-BIZ 指标行 ID、承接组件与消费版本
- SR 详细定义引用
- 23 / 25 引用
- 确认状态
- 生命周期状态

### 2.2 平台架构归属

**一句话**：本节讲组件的复用层级判定——定义与五类归属（2.2.1）。

#### 2.2.1 定义与五类归属

平台架构归属判定组件的复用层级和架构位置。判定遵循两条核心规则：

- **归属优先级**：可跨引擎复用 → 公共构件/公共平台服务；承接特定 CU 语义 → 引擎专属组件；其余归入布局组件扩展或运行支撑模块
- **共享能力追溯**：已有独立 bpl-eng/CU 的共享能力 → 组件追溯到该共享 bpl-eng，消费引擎只记录依赖。无独立配置/治理场景的技术能力 → 不补建 bpl-eng，直接形成公共构件或平台服务组件

| 归属 | 判定 | 典型组件 |
|------|------|----------|
| 引擎专属组件 | 只服务某个引擎或 CU 的配置/运行能力 | 流程发布服务、看板指标聚合服务 |
| 布局组件扩展 | 扩展列表、单据、弹窗、指标、看板页面、辅助栏等布局组件 | 树表配置容器、配置详情辅助栏 |
| 公共构件 | 功能按钮、右键、快捷键、列定义、字段布局、图表、钻取等可复用构件 | 发布按钮、回滚按钮、引用钻取 |
| 公共平台服务 | 权限、审计、版本、发布、调度、通知等跨引擎能力 | 审计服务、版本服务、任务调度服务 |
| 运行支撑模块 | 监控、回滚、日志、错误恢复、任务执行等运行期支撑 | 运行日志模块、错误恢复模块 |

### 2.3 三类组件与 NFR

**一句话**：本节讲三类组件定义与 NFR 装配——前端组件（2.3.1）、后端组件（2.3.2）、NFR 装配（2.3.3）、平台服务组件与四类平台架构（2.3.4）。组件推断规则见 §3.3。

三类组件在架构层级的定义见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-平台产品架构开发wft05-eng) 组件类型注解。本节在其定义锚点之上，以操作视角展开组件推断规则：

- **前端组件**——UI 层实现单元，承载显示、交互和页面状态。
- **后端组件**——服务层实现单元，承载校验、保存、发布、运行处理。
- **平台服务组件**——基础设施层部署单元，承载全局/共享/业务域级 NFR。

#### 2.3.1 前端组件定义

前端组件承载显示、交互、页面状态和用户操作入口。

| 来源 | 前端组件类型 | 设计要点 |
|------|--------------|----------|
| 页面类别 | 配置维护、配置管理、发布生效、运行支撑、治理追溯容器 | 容器职责、状态、上下文 |
| 布局组件 | 多级横版、列表页面、单据页、辅助栏、弹窗页、指标页面、看板页面 | 布局组合与复用边界 |
| 构件 | 按钮、右键菜单、快捷键、钻取、导入导出入口 | 入口、可见性、可操作性 |
| 操作活动 | 进度反馈、结果提示、错误提示、二次确认、状态刷新 | 活动体验与状态反馈 |

#### 2.3.2 后端组件定义

后端组件承载页面操作背后的校验、保存、发布、运行处理和治理能力。

| 操作活动 | 后端组件类型 | 设计要点 |
|----------|--------------|----------|
| 校验 | 配置校验、依赖校验、权限校验、冲突检查 | 校验边界、错误返回 |
| 保存 | 配置存储、版本记录、草稿管理 | 幂等、版本、一致性 |
| 发布/装载 | 发布编排、运行态生效、缓存刷新、影响范围计算 | 同步/异步、回滚点 |
| 回滚/停用 | 历史版本恢复、停用控制、回滚审计 | 安全边界、影响范围 |
| 审计/追溯 | 变更记录、操作日志、引用关系、运行日志 | 可追溯、查询性能 |
| 运行支撑 | 状态机、规则执行、调度、指标聚合、错误恢复 | 可靠性、可观测性 |

#### 2.3.3 NFR 装配

NFR 仅从 wft04-nfr 产出的 wft05-eng NFR 约束包消费。首次消费全量加载；包版本递增时按变更影响声明处理增量、修订或结构型变化。每条约束保留约束行 ID、消费版本、范围和目标对象。约束行可携带「分解运算 + 父指标引用」（四类运算规则见 wft04-nfr §3.2.1）：可用性子目标（组件类型级）绑定到对应组件并作为验收目标；响应时间类 E2E 目标由组件设计预算（记 pa-eng/SRD 作为设计决策）共同保证，约束包不硬切分。消费完成后将本 Skill 消费的包版本与消费状态（已消费）回写约束包头（wft04-nfr 定义的单写者字段）。

FR-BIZ 性能指标仅从 wft03-biz 产出的 FR-BIZ 指标约束包消费。每条指标保留来源 FR-BIZ、来源业务功能表单/窗口标签页、目标引擎/CU、适用条件、统计口径、测量方法、包版本和消费版本。FR-BIZ 指标与 NFR 指标分别承接、分别验证，不得合并改类。

| NFR 影响点 | 承接位置 |
|------------|----------|
| 性能/并发 | 后端发布、装载、运行支撑组件；前端状态反馈 |
| 安全/权限 | 前端可见/可操作规则；后端鉴权与权限校验 |
| 审计/追溯 | 后端审计组件；前端引用关系/日志查询入口 |
| 可用性/可靠性 | 后端重试、补偿、回滚、降级 |
| 可观测性 | 运行日志、指标、告警、追踪 |
| 兼容性/易用性 | 前端容器、构件交互、提示和校验体验 |

阻断型 NFR 必须改变组件边界、接口或运行机制；只写备注不得进入正式冻结。

#### 2.3.4 平台服务组件与四类平台架构

平台服务组件承接全局、共享和业务域级 NFR，是与前端组件、后端组件并列的第三类 pa-eng 末级节点。每个组件至少定义：组件名称、职责、来源 NFR 约束行 ID、实现策略（自研/外购/云服务）、依赖组件、消费方、验收口径。

NFR 映射必须形成四类平台架构决策：

| 架构 | 决策内容 |
|------|----------|

| 通信架构 | 协议、同步/异步、消息、超时、重试与幂等 |
| 数据架构 | 持久化、缓存、一致性、备份恢复、数据生命周期 |
| 安全架构 | 身份、权限、加密、审计、密钥与边界防护 |

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲组件设计的逻辑——为什么用三类 pa-eng 组件承接系统需求概要 srl-eng（3.1 转换原理）、怎么提取组件要素（3.2）、怎么推断组件（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四，操作步骤见 §五。

### 3.1 转换原理：为什么用三类 pa-eng 组件承接系统需求概要 srl-eng

**系统需求概要 srl-eng 描述"区域内由哪些组件构成、每个组件的业务是什么"，pa-eng 回答"为支撑这些，需要哪些软件组件、由什么组件承接组件业务与操作活动、业务 IPO 指标和非功能质量指标由什么软件能力保障"**。wft04-eng 产出的系统需求概要 srl-eng 是组件设计的输入锚——本 Skill 承接该 srl-eng（含 pa-eng 层收敛项），展开为三类 pa-eng 组件需求定义，供追溯验证与构件开发。承接单位 = pa-eng 组件（末级节点），前端/后端/平台服务是其细分类型。

**pa-eng 层收敛项是待 pa-eng 设计判断的问题线索，本 Skill 只承接设计组件**。wft04-eng 在系统需求概要 srl-eng 的组件业务条目中标注 pa-eng 层收敛项（组件边界/接口/数据/运行/NFR 的待判断问题），不设计组件；本 Skill 承接这些收敛项，给出组件归属、接口、存储、运行机制与 NFR 承接的结论。**载件（wft02 详设的组系统处理产物，经 wft03 系统需求框架、wft04 系统需求概要逐级承接）是 pa-eng 收敛项的主要来源**——由本 Skill 判断如何由前后端组件承接：前端组件承接配置展示/交互，后端组件承接配置处理与业务逻辑。

**三类组件各司其职**。前端组件（UI 层实现单元）承接页面显示、交互与页面状态；后端组件（服务层实现单元）承接校验、保存、发布、运行处理与治理能力；平台服务组件（基础设施层部署单元）承接全局/共享/业务域级 NFR。FR-BIZ 指标与 NFR 指标分别承接、分别验证。

**推断不是转录，也不越权设计**。本 Skill 不只复述系统需求概要 srl-eng，还要在组件上下文推断组件形态（归属/类型/职责边界/依赖）、制定平台架构决策；但组件推断必须有组件业务依据——组件对应关系不明确或组件业务缺失时退回上游，不静默补判。本 Skill 只定义需求，不设计实现方案、不写接口协议、不规定数据库表结构（→ 构件开发流水线）。

**这套原理方法为什么可行**：它以**可验证性**为锚——每个 pa-eng 组件可由追溯验证验证、追溯链（组件→系统需求概要→系统需求框架→配置信息组→CU→bpd-eng→bpl-eng→OR）完整、变更可传播；权威归信息最全的一方且只归其信息全的部分（系统需求框架在 wft03、系统需求概要在 wft04、组件设计在本 Skill、验证在追溯验证）；判据全部可机械判定，操作全部有明确输入输出与执行模式（§5 Step 布局表），原理→判据→操作三层一一咬合，且与 91 规范、biz/nfr 路径同一套协议运转。

#### 3.3.4 Phase B 组件关系检测

Phase B 修订已有 pa-eng 时，组件匹配通过后，将本轮生成的组件与 pa-eng 已有组件清单比对。比对锚点为**组件归属+组件职责+承接对象匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 组件匹配 + 归属/职责一致 + 来源升级（srl-eng 引用→新活动确认） | 追加 srl-eng 引用，内部细分结论=`确认` |
| 无新增 | 组件匹配 + 归属/职责一致 + 所有来源已确认 | 增量合并新 srl-eng 中的活动细节/NFR（如有新内容），内部细分结论=`改进` |
| 组件职责扩展 | 组件匹配 + 归属一致 + 新增活动、NFR 或接口边界 | 扩展已有组件，全量重写受影响定义 + 内部细分结论=`组件职责扩展` + 变更原因 |
| 归属变更 | 组件匹配 + **平台架构归属不同**（公共化或专属化） | 更新归属 + 内部细分结论=`归属变更` + 变更原因 |
| 补充 | 组件不匹配 | 新增 pa-eng 组件，内部细分结论=`新增` |
| 过时 | 基线已有组件 **未被**本轮 srl-eng 覆盖（页面/活动移除导致组件不再被需要） | 内部细分结论=`过时` + 追加说明"对应页面/活动已不再需要此组件，请确认是否移除"。保留该组件在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 srl-eng 重新判定归属**——新 srl-eng 可能改变组件特征导致归属变更（表中 `归属变更` 行）。

`[调整]` 是与关系类型正交的叠加标记：已有组件的职责边界/接口/NFR 承接变化，在关系标记之外叠加 `[调整]`。

### 3.4 完备性判据

**一句话**：本节讲 pa-eng 完备性判定——覆盖检查（正式冻结前的逐项检查）与正式冻结条件。

**覆盖检查**：

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 组件业务覆盖 | 每个组件业务有前端组件承接 | 补充前端组件 |
| 操作活动覆盖 | 每个操作活动有前端入口和后端处理承接 | 补充组件或标注 pa-eng 收敛 |
| 组件覆盖 | 每个布局组件/构件有复用/扩展/新建结论 | 补充组件结论 |
| pa-eng 收敛 | 所有 pa-eng 层必收敛项已闭合 | 补充收敛，不推进冻结 |
| NFR 承接 | 阻断型 NFR 已改变组件边界、接口或运行机制 | 重新设计组件边界，只写备注不得冻结 |
| FR-BIZ 承接 | 约束包 Q1 行均有组件承接结论（承接组件/消费版本） | 补充组件承接或标记待规范化的相关方需求节点 |
| 平台架构 | 部署/通信/数据/安全四类决策完整并可追溯 | 补充平台架构决策 |
| 依赖闭合 | 三类组件依赖无未裁决断点 | 补充依赖或标记 `[需裁决]` |
| 平台服务覆盖 | 全局/共享/业务域级约束均有平台服务组件或平台架构决策承接 | 补充平台服务组件 |
| SRD 完整 | 每个 pa-eng 组件有 SR 详细定义或明确无需 SRD 的理由 | 补充 SRD |

**正式冻结条件**（全部满足方可推进 pa-eng 为 `待追溯验证`）：

1. 来源系统需求概要 srl-eng 已确认，状态为 `已详细定义`。
2. 组件业务、构件和操作活动均有组件承接。
3. pa-eng 层必收敛项已闭合。
4. 阻断型 NFR 已影响组件边界、接口或运行机制，而不只是备注。
5. FR-BIZ 指标约束包 Q1 行均有组件承接结论（承接组件/消费版本），Q2/Q3/Q4 缺口行已关联 FR-ENG 候选线索或规范化的相关方需求节点 或待裁决。
6. 三类组件依赖关系闭合，无未裁决循环依赖。
7. SR 详细定义完整、可验证。
8. 人类已确认全部 pa-eng 条目。

不满足时只能形成阶段性 pa-eng，不推进 srl-eng 为 `已pa-eng架构`。

### 5.1 Step Start · 前置校验与路由

> 入口条件与优先级判定遵循 [91 规范 §A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 srl-eng）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

#### 5.1.1 入口检测

读取产品数据文档中的 `## AI可以处理节点` 对应分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口条件：

| # | 入口条件 | 检测方式 | 对应分节 |
|---|---------|---------|---------|
| ① | **有新输入** | AI可以处理节点「待 wft05-eng 处理」分节非空 | §11.7 |
| ② | **有待处理反馈** | AI可以处理节点「待反馈处理」分节含本 Skill 产出节点 | §11.7 |
| ③ | **有下游退回节点** | AI可以处理节点「待下游退回处理」分节含状态为 `需wft05修订` 的节点 | §11.7 |

三类均不满足 → 输出"无待处理对象"→ **退出**。

**退回门禁**（满足条件③时）：检查退回节点的缺失说明中是否包含人类改进方案（人类标注 `[修改]`/`[同意]` 或下游 Skill/验证流程产出的具体改进指引）。已提供 → 通过门禁。未提供 → 输出缺失说明 + 提示提供改进方案 → **退出**。

#### 5.1.2 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| srl-eng 的所属路径不是 `eng`，或节点类型不是 `系统需求概要` | 类型不匹配（硬退出） | 输出类型分布；业务功能表单、窗口标签页等业务侧页面组件不得进入本 Skill → **退出** |
| srl-eng 状态不是 `已详细定义` | 状态不符（硬退出） | 输出不合格节点及当前状态 → **退出** |
| srl-eng 缺少组件业务、pa-eng 收敛项或 CU 追溯中任一项 | 要素缺失（硬退出） | srl-eng → `需wft04修订`，输出缺失说明 → **退出** |
| wft05-eng NFR 约束包缺失、版本不可判定或变更声明缺失 | 约束包缺失（硬退出） | 输出约束包缺失说明，退回 wft04-nfr 补齐 → **退出** |
| 本轮涉及的 FR-BIZ 指标约束包缺失、版本不可判定或变更声明缺失 | 约束包缺失（硬退出） | 输出缺失说明，退回 wft03-biz 补齐 → **退出** |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

**锁定写回**：输入校验通过后，将承接的 srl-eng 状态写为 `在pa-eng设计`（锁定态，本 Skill 消费展开期间，对齐 91 §A.6 锁定态=下游写入 与 §4.1 主线流转）；完成三类组件设计且正式冻结后推进 `已pa-eng架构`（§5.8）。

#### 5.1.3 分流处理

按 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序) 定义的优先顺序执行（退回优先 → 反馈处理 → 新输入路由）：

1. **退回优先**：存在 `需wft05修订` 的 pa-eng 节点（且门禁通过）→ 定位受影响 pa-eng/SRD/srl-eng，进入 Step 2 按 §5.3.1 根因分流表判定处理
