# 三路径双向追溯与跨链验证
**SKILL 指南ID**: wfwft06 · **Step 6: Bidirectional Traceability Verification**

> **概述**：验证 biz、eng、nfr 三条异构路径的完整追溯关系，输出追溯矩阵和验证报告；同时验证功能表单/窗口标签页及 FR-BIZ 指标与 eng 平台能力之间的跨路径分配，以及 nfr 约束包到 eng pa-eng 的消费闭环。biz 在 05 形成兼具业务配置需求与配置业务系统 pa-eng 身份的功能表单/窗口标签页；eng 在 07 形成平台软件 pa-eng；nfr 形成 SysReq-NFR 与约束包。
>
> **输入 → 输出**：已确认的 biz 业务配置需求 + eng pa-eng + nfr 约束包及其上游设计文档/决策记录 → 三路径追溯矩阵 + 跨链映射 + 验证报告
>
> **适用场景**：瀑布式系统设计第6步（最终验证步骤）；支持 biz 单链、eng 单链、nfr 单链、跨链和全链五种验证批次。
>
> **版本**：v3.9 | **修订**：2026-08-28

## 一、设计角色

本步在设计链中承担的角色：
- **输入**：验证批次指定范围内的 biz/eng/nfr 设计文档、约束包、状态与决策记录
- **产出1**：追溯矩阵（`08-*.md`）——三路径各自的端到端映射，外加 biz→eng 能力覆盖和 nfr→eng pa-eng 约束消费映射
- **产出2**：验证报告（`09-*.md`）——含验证结论、问题清单、建议措施

### 与三条工程化设计原则的关系

| 原则 | 在本步中的体现 |
|------|--------------|
| **详概分离** | 本步不涉及新的分解或架构定义，仅验证各层已有产出的映射关系和链路完整性。追溯矩阵是验证层面的交叉索引，不包含架构或详细定义内容 |
| **文档结对** | 分别验证 biz、eng、nfr 三条异构路径；不得为追求形式对称而虚构 biz pa-eng 或第二个 NFR 消费方 |
| **基于资产** | 验证前按批次范围加载已有产品数据文件、约束包和决策记录，在既有数据基础上检查映射正确性 |

### 三路径结对关系

| 路径 | 端到端链路 | 本步验证内容 |
|------|------------|-------------|
| biz | FR-BIZ 规范化的相关方需求 → bpl-biz → bpd-biz 输出文档/PL6 → 功能表单/窗口标签页 | 需求承接、配置业务系统 pa-eng 完整性、FR-BIZ 指标分配、来源追溯和 `可构件开发` 门禁 |
| eng | FR-ENG 规范化的相关方需求节点 → bpl-eng → CU bpd-eng → 系统需求框架 srb-eng → 系统需求概要 srl-eng → pa-eng 三类组件 | bpl-eng 主责能力域唯一、共享依赖不重复、CU 配置能力、页面/构件覆盖、系统需求框架/系统需求概要 srb-eng→pa-eng 承接和 `待追溯验证` 门禁 |

#### 跨路径接口验证（EOS 特有）

| 验证项 | 来源链 | 目标链 | 验证内容 |
|--------|--------|--------|---------|
| biz→eng 能力与指标覆盖 | eng pa-eng（引擎能力） | biz 功能表单/窗口标签页及 FR-BIZ 指标约束包 | 业务页面是否使用已定义的引擎/CU/组件能力？FR-BIZ 指标是否逐行被软件组件承接？FR-ENG 缺口是否已正式回流和处理？ |
| nfr→eng 约束消费 | NFR 约束包 | eng pa-eng 组件/平台架构决策 | 约束行是否被唯一消费？阻断型 NFR 是否实际改变组件边界、接口或运行机制？ |

> **验证前提**：第1~5步全部完成。本步是瀑布式流程的最后一步，负责检查全链路完整性。发现的断点不在此步修复，而是记录到验证报告中供回溯修正。

核心驱动逻辑：先按验证批次确定路径范围，再按各路径真实层级检查唯一分配、聚合合理性和双向追溯，最后执行跨路径接口验证。不得用统一的 `规范化的相关方需求→SR→bpd-biz→SysReq→pa-eng` 模板套用三条路径。

### 3.1 Step Start · 验证批次与前置门禁

验证批次包含：`批次ID / 验证类型 / biz范围 / eng范围 / nfr范围 / 当前状态 / 人类决策`。验证类型及门禁如下：

| 验证类型 | 必备范围 | 就绪门禁 |
|---------|---------|---------|
| biz单链 | biz | 功能表单/窗口标签页已确认且状态=`可构件开发`；FR-BIZ 指标约束包版本可判定 |
| eng单链 | eng | pa-eng 状态=`待追溯验证` |
| nfr单链 | nfr | SysReq-NFR=`已验证冻结`，约束包已发布；验证消费闭环时还须有已消费版本 |
| 跨链 | biz + eng，可选 nfr | 关联 biz 需求与 eng pa-eng 均已确认；涉及 NFR 时约束包已被目标 pa-eng 消费 |
| 全链 | biz + eng + nfr | 上述三条单链门禁全部满足 |

无验证批次或 `人类决策≠同意进入wft06` 时退出。批次范围之外的节点不得因本轮验证改变状态。

### 3.2 Step 1~2 · 分析活动与按需加载

1. 读取批次范围、各路径节点索引、AI最近变更、待确认项和决策记录。
2. biz 加载 `01/02/04/05/06` 中与选定 bpl-biz/配置需求相关的节点块 + FR-BIZ 指标约束包（`10-eos-fr-biz-constraint-package.md`）。
3. eng 加载 `01/02/04/05/06/07/23` 中与选定 bpl-eng/CU/系统需求框架 srb-eng/系统需求概要 srl-eng/pa-eng 相关的节点块。
4. nfr 加载 `01/02/05/06`、分层约束表、wft05-eng NFR 约束包（`11-eos-nfr-constraint-package.md`）及 wft05 消费记录。
5. 跨链验证额外加载 25 引擎模型和 biz 需求中的能力参照/FR-ENG 缺口线索。

### 3.3 Step 3 · 分配与宿主约束验证

| 路径 | 检查链路 |
|------|---------|
| biz | FR-BIZ 规范化的相关方需求→bpl-biz；bpl-biz→bpd-biz 输出文档/PL6；bpd-biz→功能表单/窗口标签页；FR-BIZ指标→引擎/CU |
| eng | FR-ENG 规范化的相关方需求节点→bpl-eng；bpl-eng→CU bpd-eng；CU→系统需求框架 srb-eng；系统需求框架→系统需求概要 srl-eng；系统需求概要→pa-eng 组件 |
| nfr | 规范化非功能需求→bpl-nfr；分类需求项→唯一 SysReq-NFR；约束行→唯一约束包条目→pa-eng 消费结论 |

“1:1”只在该层规则确实要求唯一分配时使用；允许聚合的环节验证唯一宿主和反向来源完整性，不机械要求一对一。

### 3.4 Step 4 · 聚合合理性验证

对每个聚合节点检查语义内聚、边界一致和规模合理性。`2~5 条/节点`仅作风险提示，不作为普遍硬门禁；若对象模型明确规定其他基数，以对象级规则为准。

### 3.5 Step 5 · 三路径双向追溯

对每个映射环节执行：Q1 正向目标存在、Q2 反向来源存在、Q3 语义/指标不降级。结果标记：✅完整、⚠️待确认、❌中断、❓证据不足。

- biz 正向：`FR-BIZ 规范化的相关方需求→bpl-biz→bpd-biz→功能表单/窗口标签页→FR-BIZ指标分配`；反向相反。
- eng 正向：`FR-ENG 规范化的相关方需求节点→bpl-eng→CU bpd-eng→系统需求框架 srb-eng→系统需求概要 srl-eng→pa-eng`；反向相反。
- nfr 正向：`规范化非功能需求→bpl-nfr→SysReq-NFR→约束行→约束包→pa-eng消费结论`；反向相反。

### 3.6 Step 6 · 跨路径接口验证

**biz→eng 能力与指标覆盖**：逐条功能表单/窗口标签页及 FR-BIZ 指标约束行核对引擎、CU、系统需求框架 srb-eng、系统需求概要 srl-eng 与 pa-eng 能力。每条指标保留 FR-BIZ 类型和来源，验证组件承接、适用条件、统计口径、测量方法和消费版本（wft05-eng 记录到 pa-eng 节点的承接组件/消费版本须与约束包行一致）。缺口行（Q2/Q3/Q4）须关联 FR-ENG 候选线索或FR-ENG 规范化的相关方需求节点 或待裁决结论（三可）；候选线索或规范化的相关方需求节点 只有在经过 or00→or03 形成规范化的相关方需求节点 并获得处理结论后，才算闭环。

**nfr→eng pa-eng 消费**：逐约束行核对包版本、消费版本、目标组件/平台决策和验收口径。携带「分解运算」的约束行核对预算守恒（加法 Σ子≤父 / 乘法 Π子≥父 / 弱链 每子≥父 / 职责分布 无守恒），并核对约束包消费状态已由 wft05-eng 回写（`已消费`）。阻断型 NFR 只写备注、未改变组件边界/接口/运行机制时判定为 ❌。

### 3.7 Step 7 · 符合性分析完整率

按路径检查全部方案节点的符合性分析字段和跨层指标一致性。biz 检查功能表单/窗口标签页及 FR-BIZ 指标约束包；nfr 检查量化六要素、目标绑定和消费版本；eng 检查 pa-eng 对 FR-ENG、FR-BIZ 和 NFR 三类指标的承接不降级。

### 3.8 Step 8 · 生成产出与追溯态推进

1. 在 `08-*.md` 分节生成 biz、eng、nfr 三条追溯矩阵及两个跨路径接口矩阵。
2. 在 `09-*.md` 生成总体结论、逐路径结果、问题清单和回退建议。
3. **eng 追溯态推进**：仅将本批次范围内、Q1/Q2/Q3 全通过且无 ⚠️/❌/❓ 的 pa-eng 从 `待追溯验证` → `验证中` → `已验证冻结`。
4. **nfr 追溯态**：SysReq-NFR 已由 wft04-nfr 落账时冻结（`已验证冻结`），本步仅对消费闭环做确认，不重复推进状态。
5. **不通过处理**：追溯不通过的 pa-eng 置 `需wft05修订`（或按实际根因 Skill 对应退回态）；报告必须指向实际根因 Skill，不统一回退 wft01。

### 3.9 Step End · 输出交互

输出批次ID、验证类型、三路径通过率、跨路径接口结论、已验证冻结 pa-eng/SysReq-NFR、保持验证中 pa-eng、建议回退 Skill 和待人类裁决项。

### 启动方式

> 开始瀑布式 wft06（或 wfwft06）

AI 动作序列：读取本文件 → 读取验证批次 → 按路径范围加载资产 → 执行三路径追溯及所需跨路径验证 → 生成 08/09 → 推进符合条件的 pa-eng/SysReq-NFR 追溯态 → 通知人类审核。

## 四、AI 执行指南

### 4.1 跨步骤上下文管理

| 继承内容 | 说明 | 保存位置 |
|---------|------|---------|
| 架构决策 | 合并/拆分、分类方式、层级结构 | 上一步的决策记录 |
| 编号体系 | 所有已分配的 ID 和编号规则 | 各产品数据文件 |
| 待确认项 | 上一步标记的 ⚠️ 项 | 汇总清单 |
| AI推断记录 | AI 自行判断补齐的内容 | 决策记录文件的 AI推断项 |

**回溯修正**：如果在第 N 步发现需要修改第 M 步（M < N）的产出：
1. 评估影响范围（见 AI决策框架 §7.2 跨步骤影响范围表）
2. 定位到受影响的具体步骤和节点
3. 修改后检查下游映射是否需要同步调整
4. 标注变更记录

### 4.2 AI 经济原则

1. **执行顺序不可逆**：分析活动 → 加载资产 → 1:1 验证 → N:1 验证 → 双向追溯验证 → 符合性分析验证 → 产出矩阵+报告 → 闭环检查。核心驱动力：先理解有哪些资产再验证，先验证单个约束（1:1）再验证整体链路（双向追溯）
2. **基于资产优先**：验证前必须按批次加载所需产品数据、约束包和决策记录，理解各路径节点和映射关系后再开始逐项验证
3. **资产路径已知**：本步的资产是 `../../80-pl4eos-2-eosdata/` 下 01~09 号文件、NFR 约束包和决策记录，按验证批次范围读取
4. **wft06 与 wft01~wft05 的本质区别**：wft01~wft05 是"创建/定义"步骤，wft06 是"验证"步骤。wft06 不产生新的架构节点或映射，而是检查已有映射的正确性和完整性。发现的断点不在此步修复，而是记录到验证报告中供回溯修正

## 七、审查流程

### 7.1 审核要点

- [ ] 验证报告中的未通过项和待确认项（⚠️、❌、❓），按 biz/eng/nfr 分别审核
- [ ] ✅/⚠️/❌/❓ 四层标记完整：断点已标记 ❌ 未忽略
- [ ] biz、eng、nfr 三条路径均按本批次范围覆盖追溯验证
- [ ] 各路径追溯链路是否存在断点
- [ ] biz→eng 能力覆盖和 nfr→eng pa-eng 消费接口均已验证
- [ ] 符合性分析完整率是否 100%
- [ ] 性能指标跨层是否一致（产品架构不低于 SysReq 要求）
- [ ] 回溯修复方案的影响范围是否评估完整，建议回退步骤是否合理
- [ ] ❌ 标记的映射错误是否需要跨步骤回溯修正

### 7.2 审查修复流程

**审查输入**：AI 完成指定步骤后，输出产物供 rule-conformance-review 审查。审查报告包含：
- 通过/未通过的项目清单
- 问题定位（涉及的具体文件、章节、编号）
- 问题类型（结构性/内容性/格式性）

**AI 修复流程**（按优先级处理）：
1. **格式性问题**（编号错误、格式不规范）→ 直接修复，不需要人工确认
2. **内容缺失**（某节为空、映射不完整）→ 补充内容，标注修复说明
3. **结构性问题**（粒度不匹配、分类错误）→ 提出修复方案，标注 ⚠️ 待确认
4. **跨步骤一致性问题** → 参考AI决策框架的跨步骤影响范围表进行影响范围评估，列出所有受影响的下游节点

**影响范围评估**：

| 问题定位 | 影响范围 | 修复策略 |
|---------|---------|---------|
| 某步的架构定义 | 本层 + 下游已建立映射的节点 | 修改后同步更新映射 |
| 详细定义 | 下层方案 | 修改后检查下层是否受影响 |
| 映射关系 | 所有关联节点 | 需重新运行追溯验证 |
| 编号变更 | 全链路 | 需逐层更新引用，重新验证 |
