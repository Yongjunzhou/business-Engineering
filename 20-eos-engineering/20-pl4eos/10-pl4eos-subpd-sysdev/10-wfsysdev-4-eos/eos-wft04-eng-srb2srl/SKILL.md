### Step 3 · 系统需求详细设计

#### Phase A — 组件候选生成与宿主匹配

逐功能表单的每个区域，按页面编排框架与操作活动清单生成组件候选，然后按 `引擎+CU+功能表单+区域内组件` 匹配已有系统需求概要：

| 条件 | 路由 |
|------|------|
| 组件类型+业务落入已有系统需求概要 | 归入 → Phase B |
| 不满足 | 待聚合池 → Phase C |
| 组件职责冲突或跨区域复用边界不清 | `[需裁决]` |

#### Phase B — 修订已有系统需求概要

1. **要素提取**——从本轮系统需求框架提取组件类型、布局组件线索和组件业务候选
2. **宿主匹配检查**——复用→追加来源；扩展→全量重写保留历史；冲突→`[需裁决]`
3. **重判定与关系检测**——基于全部功能表单重判组件类型与布局组件，比对基线判定五类关系：

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 组件匹配+类型一致+来源升级 | 追加 bpd-eng/CU 来源 |
| 无新增 | 组件匹配+全部已确认 | 增量合并细节 |
| 组件业务扩展 | 类型一致+业务/pa-eng收敛项边界扩展 | 全量重写，保留历史 |
| 补充 | 组件不匹配 | 新增系统需求概要条目 |
| 过时 | 基线组件未被本轮覆盖 | `[过时]`+保留不删 |

4. **变更影响声明**——判定变更类型，写入 srl-eng 末尾

#### Phase C — 新建系统需求概要

1. **判定布局组件**——在页面编排框架基础上独立判断区域需要的布局组件组合（附录 A.3）
2. **识别构件**——按展示/交互/数据/反馈四类独立识别（附录 A.4）
3. **定义组件业务**——逐组件定义承载操作活动/数据来源/交互行为/状态反馈（附录 A.5，功能级不写实现）
4. **标注 pa-eng 层收敛项**——组件边界/接口/存储/运行机制/NFR 均标注（附录 A.6）
5. **组装系统需求概要**——写入 `06-*.md`

### Step 4 · 组件业务定义与 pa-eng 收敛项

**1. 组件业务定义**——对每个布局组件/构件，按 §3.3.1 要素定义组件业务（承载操作活动[承接 03 操作活动清单]/数据来源/交互行为/状态反馈，功能级不写实现）。**承接 03 的承载操作活动不标 `[推断]`**（操作活动清单已在 wft03-eng 组织确认），**数据来源/交互行为/状态反馈等设计推断标 `[推断]`**。

**2. pa-eng 层收敛项标注**——逐组件检查五类（附录 A.6），存在则写入 `pa-eng层收敛-*` 标记。载件（wft02 系统处理产物，经 03 操作活动清单承接）是主要来源——供 wft05 判断由前后端组件承接。本 Skill 不设计 pa-eng 组件——只传递待处理问题。

**3. 要素机械检查**——组件名称/所属功能表单/所在区域已定义、布局组件类型/构件类型已判定、组件业务已定义、pa-eng 收敛项已标注、所有区域与操作活动清单均被组件承接。

### A.3 布局组件判定

| 判定条件 | 布局组件 |
|----------|----------|
| 需要展示对象集合、版本记录或执行记录 | 列表页面 |
| 需要编辑单个配置对象或参数组 | 单据页 |
| 需要并列展示多层主从对象 | 多级横版 |
| 需要上下文、详情、校验结果或引用关系 | 辅助栏 |
| 需要临时选择、确认、局部参数或冲突处理 | 弹窗页 |
| 需要展示运行指标、发布影响或异常趋势 | 指标页面 |
| 需要展示运行状态概览、任务分布或发布汇总 | 看板页面 |
