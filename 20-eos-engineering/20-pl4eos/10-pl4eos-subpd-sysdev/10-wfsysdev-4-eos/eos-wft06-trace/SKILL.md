# eos-wft06 · 三路径双向追溯与跨链验证

> **设计依据**：[eos-wft06-trace.md](../eos-wft06-trace.md)（SKILL 指南——权威源）
> **领域规范**：[91-eos-biz-eng-spec.md](../91-eos-biz-eng-spec.md)

## 一、职责定位

### 负责与不负责

| 负责 | 不负责 |
|------|--------|
| 按验证批次确定路径范围（biz单链/eng单链/nfr单链/跨链/全链） | 创建新的架构节点或映射（本步仅验证已有映射） |
| 按三条异构路径分别执行分配验证、聚合验证、双向追溯 | 修复发现的断点（记录到验证报告供回溯修正） |
| 跨路径接口验证：biz→eng 能力与指标覆盖 + nfr→eng pa-eng 消费 | 改变批次范围外节点的状态 |
| Q1/Q2/Q3 三维度判定 + ✅/⚠️/❌/❓ 四层标记 | — |
| 生成 08 追溯矩阵 + 09 验证报告 + pa-eng/SysReq-NFR 追溯态推进（eng pa-eng `待追溯验证`→`验证中`→`已验证冻结`；nfr 仅对消费闭环确认，不重复推进） | — |

**wft06 与 wft01~wft05 的本质区别**：wft01~wft05 是"创建/定义"步骤，wft06 是"验证"步骤——不产生新架构节点，仅检查已有映射的正确性和完整性。

## 二、三路径异构追溯链

| 路径 | 端到端链路 | 验证重点 |
|------|------------|---------|
| biz | FR-BIZ 规范化的相关方需求 → bpl-biz → bpd-biz 输出文档/PL6 → 功能表单/窗口标签页 → FR-BIZ 指标分配 | 需求承接、pa-eng 完整性、`可构件开发` 门禁 |
| eng | FR-ENG 规范化的相关方需求节点 → bpl-eng → CU bpd-eng → 系统需求框架 srb-eng → 系统需求概要 srl-eng → pa-eng 三类组件 | 主责能力域唯一、共享不重复、CU 配置能力、系统需求框架/系统需求概要 srl-eng→pa-eng 承接、`待追溯验证` 门禁 |
| nfr | 规范化非功能需求 → bpl-nfr → SysReq-NFR → 约束行 → 约束包 → pa-eng 消费结论 | 宿主唯一、约束包完整、pa-eng 承接闭环 |

**跨路径接口**：

| 验证项 | 内容 |
|--------|------|
| biz→eng 能力与指标覆盖 | 业务页面是否使用已定义的引擎/CU/组件能力？FR-BIZ 指标是否逐行被组件承接（含消费版本）？FR-ENG 缺口行是否关联三可（候选线索/规范化的相关方需求节点/待裁决结论）？ |
| nfr→eng pa-eng 消费 | 约束行是否被唯一消费？分解预算是否守恒（加法 Σ子≤父 / 乘法 Π子≥父 / 弱链 每子≥父 / 职责分布 无守恒）？消费状态是否已由 wft05-eng 回写（`已消费`）？阻断型 NFR 是否实际改变组件边界/接口/运行机制？ |

## 三、操作流程

### Step Start · 验证批次与前置门禁

读取验证批次（批次ID/验证类型/biz范围/eng范围/nfr范围/人类决策）。

| 验证类型 | 就绪门禁 |
|---------|---------|
| biz单链 | 功能表单/窗口标签页已确认且 `可构件开发`；FR-BIZ 约束包版本可判定 |
| eng单链 | pa-eng 状态=`待追溯验证` |
| nfr单链 | SysReq-NFR=`已验证冻结`，约束包已发布；验证消费闭环时还须有已消费版本 |
| 跨链 | biz+eng 均已确认；涉及 NFR 时约束包已被消费 |
| 全链 | 上述三条门禁全部满足 |

无验证批次或 `人类决策≠同意进入wft06` → 退出。

### Step 1~2 · 加载资产

按批次范围加载：

| 路径 | 加载文件 |
|------|---------|
| biz | `01/02/04/05/06` 中与选定 bpl-biz/bpd-biz/需求相关的节点块 + FR-BIZ 指标约束包（`10-eos-fr-biz-constraint-package.md`） |
| eng | `01/02/04/05/06/07/23` 中与选定 bpl-eng/CU/系统需求框架 srb-eng/系统需求概要 srl-eng/pa-eng 相关的节点块 |
| nfr | `01/02/05/06`、分层约束表、wft05-eng NFR 约束包（`11-eos-nfr-constraint-package.md`）及 wft05 消费记录 |
| 跨链 | 额外加载 25 引擎模型和 FR-ENG 缺口线索 |

### Step 3~5 · 三路径验证

**Step 3 · 分配与宿主验证**——逐路径检查唯一分配/唯一宿主。允许聚合的环节验证反向来源完整性，不机械要求 1:1。

**Step 4 · 聚合合理性验证**——检查 N:1 聚合是否语义内聚、边界一致。`2~5条/节点`仅作风险提示。

**Step 5 · 双向追溯**——对每个映射环节执行 Q1/Q2/Q3：

| 维度 | 检查内容 |
|------|---------|
| Q1 正向 | 出发节点是否标注了分配目标（→下层方案节点）？ |
| Q2 反向 | 目标节点是否标注了承接来源（←上层需求节点）？ |
| Q3 跨层一致性 | 语义/指标是否不降级？ |

四层标记：✅ 链路完整 / ⚠️ 待确认 / ❌ 链路中断 / ❓ 证据不足。

### Step 6 · 跨路径接口验证

**biz→eng**：逐条功能表单/窗口标签页及 FR-BIZ 指标约束行核对引擎、CU、系统需求框架 srb-eng、系统需求概要 srl-eng 与 pa-eng 能力，验证组件承接、统计口径、测量方法和消费版本（pa-eng 节点承接组件/消费版本须与约束包行一致）。缺口行（Q2/Q3/Q4）须关联 FR-ENG 候选线索或FR-ENG 规范化的相关方需求节点 或待裁决结论（三可）；候选线索或规范化的相关方需求节点 只有经 or00→or03 形成规范化的相关方需求节点 并获处理结论才算闭环。

**nfr→eng**：逐约束行核对包版本、消费版本、目标组件/平台决策和验收口径。携带「分解运算」的约束行核对预算守恒（加法 Σ子≤父 / 乘法 Π子≥父 / 弱链 每子≥父 / 职责分布 无守恒），并核对约束包消费状态已由 wft05-eng 回写（`已消费`）。阻断型 NFR 只写备注、未改变组件边界/接口/运行机制时判定为 ❌。

### Step 7 · 符合性分析完整率

按路径检查全部方案节点的符合性分析字段和跨层指标一致性。biz 检查功能表单/窗口标签页及 FR-BIZ 指标约束包；nfr 检查量化六要素、目标绑定和消费版本；eng 检查 pa-eng 对 FR-ENG、FR-BIZ 和 NFR 三类指标的承接不降级。

### Step 8 · 生成产出与追溯态推进

1. `08-*.md` 分节生成 biz/eng/nfr 三条追溯矩阵 + 两个跨路径接口矩阵
2. `09-*.md` 生成总体结论、逐路径结果、问题清单和回退建议
3. **eng 追溯态推进**：仅将批次范围内 Q1/Q2/Q3 全通过且无 ⚠️/❌/❓ 的 pa-eng 从 `待追溯验证` → `验证中` → `已验证冻结`
4. **nfr 追溯态**：SysReq-NFR 已由 wft04-nfr 落账时冻结（`已验证冻结`），本步仅对消费闭环做确认，不重复推进状态
5. **不通过处理**：追溯不通过的 pa-eng 置 `需wft05修订`（或按实际根因 Skill 对应退回态）；报告指向实际根因 Skill，不统一回退 wft01

### Step End · 输出交互

输出批次ID、验证类型、三路径通过率、跨路径接口结论、已冻结 规范化的相关方需求、保持验证中 规范化的相关方需求、建议回退 Skill 和待人类裁决项。
