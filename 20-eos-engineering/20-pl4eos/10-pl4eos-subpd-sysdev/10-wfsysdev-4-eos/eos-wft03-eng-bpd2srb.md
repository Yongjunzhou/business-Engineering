### 2.1 功能表单 srb-eng

**一句话**：本节讲系统需求框架 srb-eng 的概念——定义与分类（2.1.1）、架构与属性（2.1.2）；完备性判据见 §三 3.4。

#### 2.1.1 定义与分类

功能表单是配置、治理或运行支撑人员直接使用的页面单元，用来维护 CU 配置、触发引擎处理、查看发布/运行结果或处理异常。它**不同于** biz 路径面向业务角色的功能表单和窗口标签页（eng 功能表单承接配置操作+配置能力运行的操作页面，两链**同名同层、内容异质、非共享资产**）。

**功能表单清单含两类**（03 输出）：

| 功能表单类别 | 来源 | 说明 |
|----------|------|------|
| **配置类** | 02 CU 配置入口 | 配置人员在哪个页面维护该 CU（一个 CU 对应一个页面；复合页内的子页面即完整页面；流程设计器等多功能表单的**编排容器**，非单个复合功能表单） |
| **运行类** | 02 运行期能力操作页面 | 办理单据页 / 待办清单 / 征集待办 / 待阅清单等 |

功能表单按职责分为五类（由 AI 根据 CU 操作活动定义判定）：

| 页面类别 | 用途 | 典型来源 |
|----------|------|----------|
| 配置维护页 | 维护 CU 配置要素 | 配置入口、配置操作 |
| 配置管理页 | 管理配置版本、状态、引用关系 | 系统处理、治理依赖 |
| 发布生效页 | 校验、发布、装载、回滚、停用 | 系统处理 |
| 运行支撑页 | 查看运行期能力、刷新、重试、处理异常 | 运行期能力 |
| 治理追溯页 | 审计、影响范围、引用关系、操作日志 | 横切治理依赖 |

> 布局组件与构件的详细定义见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)，eng 路径分工见 [91 规范 §8.3](91-eos-biz-eng-spec.md#83-系统需求框架开发wft03-eng)。

#### 2.1.2 架构与属性

系统需求框架设计涉及两个**相互独立**的维度，不能互相替代（布局组件判定下移 wft04-eng，本 Skill 只到区域/TAB/弹窗入口级别）：

| 维度 | 来源 | 回答的问题 | 进入 srb-eng 的字段 |
|------|------|------------|------------------|
| 页面类型 | 91 规范 §1.1.1 | 是否属于硬代码开发的功能表单？ | `页面类型=功能表单` |
| 页面类别 | 91 规范 §8.3 | 承担哪种配置职责？ | `页面类别` |

> 页面类别判定规则见 §3.2，页面编排框架见 §2.3.1，操作活动清单见 §2.3.2。

**srb-eng 节点完整要素**（写入 `05-*.md` srb-eng 节点块）：

- 页面 ID / 名称 / 页面类型（固定为功能表单）/ 页面类别 / 使用角色（来源 bpd-eng R 上下文）

- 操作活动清单（承接 02 标注入口）· 权限、状态、版本、发布约束
- 确认状态

### 2.2 页面类型与页面类别

#### 2.2.1 定义与正交关系

**页面类型**：本 Skill 的末级节点固定为**功能表单**。配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页是**页面类别**（职责分类），不是新的页面类型。

每个 srb-eng 必须同时写明：**`页面类型=功能表单`** + **页面类别**。

**功能表单粒度**：子页面即完整页面；流程设计器等多功能表单是**编排容器**（承载多个 CU 配置信息组的页面编排，非单个复合功能表单）。布局组件组合与构件识别下移 wft04-eng（[91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界) 定义）。

### 2.3 页面编排框架

#### 2.3.1 页面编排框架

页面编排框架回答：一个 CU 或一组强依赖 CU 的功能表单如何组合使用。**它组织的正是 CU 的配置信息组操作活动定义——CU 操作活动是其所有配置信息组操作活动的集成，页面编排框架把该集成组织为页面层的组合方式**。

**要素**（03 到区域/TAB/弹窗入口级别，区域内具体组件下移 04）：
- 功能表单清单
- 区域 / TAB / 弹窗入口（页面内编排级别）
- 页面间跳转和上下文传递
- 权限、状态、版本和发布依赖
- 与来源 CU、承载配置信息组清单的对应关系

#### 2.3.2 操作活动清单（承接 02 标注入口）

操作活动是用户在功能表单上执行的可验证动作，**承接自配置信息组操作活动定义**。本 Skill 输出**操作活动清单**——逐活动标注**承接 02 的标注入口**（配置操作/系统处理/运行期能力），**不重复步骤**（步骤化三段式已在 wft02-eng 详设）：

| 字段 | 说明 |
|------|------|
| 活动名称 | 如新建配置、校验配置、发布配置 |
| 承接 02 标注入口 | 承接配置操作 / 系统处理 / 运行期能力的引用，不重复步骤 |
| 适用页面类别 | 配置维护页 / 配置管理页 / 发布生效页 / 运行支撑页 / 治理追溯页 |

操作活动清单承接配置信息组操作活动定义（三类对应）：

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲系统需求框架设计的逻辑——为什么用功能表单承接 CU 操作活动定义（3.1 转换原理）、怎么提取页面要素（3.2）、怎么承接操作活动清单（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四，操作步骤见 §五。

### 3.1 转换原理：为什么用功能表单承接 CU 操作活动定义

**CU 操作活动定义描述"这个配置单元配置什么、系统怎么处理、运行期产出什么"，系统需求框架 srb-eng 回答"为支撑这些，需要哪些功能表单、每页如何编排（区域/TAB/弹窗入口）、页面上有哪些可执行活动"**。wft02-eng 详设的配置信息组操作活动定义是功能表单内容的承接锚——本 Skill 承接该定义，组织为页面形态的系统需求（系统需求框架 srb-eng），供 wft04-eng 展开组件业务、wft05-eng 设计 pa-eng（前后端组件）。承接单位 = 功能表单（末级节点，框架说明为结构判定级）。

**配置信息组是 P0 产品树的末级节点（PL5，能力单元），设计分工各司其职**。wft01-eng 业务流程框架锚定配置信息组（框架说明）清单并给出结构判定级框架说明（配置什么、运行期提供什么）；wft02-eng 业务流程概要承接后展开操作活动定义（配置操作/系统处理/运行期能力，步骤化三段式）；本 Skill 系统需求框架承接 wft02 详设后的操作活动定义组织为功能表单。**CU 操作活动 = 其所有配置信息组操作活动的集成**——功能表单以 CU 为边界，页面编排框架组织的正是该集成（若按组分页，集成关系就碎了）。

**操作活动清单是承接，不是再定义业务**。本 Skill 把配置信息组操作活动挂载为页面操作活动清单——配置操作 → 配置维护活动、系统处理 → 校验/发布生效活动、运行期能力 → 运行支撑活动。每个活动**标注承接 02 的标注入口、不重复步骤**（步骤化三段式已在 wft02-eng 详设）。**发现组操作活动不足 → 退回 `需wft02修订`；发现组结构/框架缺陷 → 经 wft02 退回 `需wft01修订`**，不脑补。

**03 纯框架，只组织页面**。本 Skill 只做**结构判定级**页面组织——页面职责/页面类别/使用角色/承载关系/操作活动清单/页面编排框架；**布局组件/构件与 pa-eng 层收敛项下移 wft04-eng**（系统需求概要），不在本 Skill 判定。pa-eng 是 wft05-eng 的设计产出，wft04-eng 标注 pa-eng 层收敛项作为 wft05 设计 pa-eng 的输入。

**推断不是转录，也不越权设计**。本 Skill 不只复述配置信息组操作活动定义，还要在页面上下文推断页面形态（页面类别/页面编排框架）；但页面推断必须有操作活动依据——CU 未承载但页面必需的，标注依据不足退回上游，不静默补判。

**这套原理方法为什么可行**：它以**可验证性**为锚——功能表单以 CU 为边界（页面单位）承接集成操作活动，每个功能表单可被 wft04-eng 承接为组件业务、追溯链（功能表单→配置信息组→CU→bpd-eng→bpl-eng→OR）完整、变更可传播；权威归信息最全的一方且只归其信息全的部分（操作活动定义在 wft02、系统需求框架在本 Skill、组件业务在 wft04、组件设计在 wft05）；判据全部可机械判定，操作全部有明确输入输出与执行模式（§5 Step 布局表），原理→判据→操作三层一一咬合，且与 91 规范、biz 路径同一套协议运转。

**一句话**：本节讲操作活动清单承接的规则——活动类型与标注（3.3.1）、Phase B 功能表单关系检测（3.3.2）。Phase B（修订已有 srb-eng）与 Phase C（新建 srb-eng）共用以下规则。

#### 3.3.2 Phase B 功能表单关系检测

宿主匹配通过后，将本轮生成的功能表单与 srb-eng 已有清单比对。比对锚点为**页面类别 + 页面职责匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 页面匹配 + 类别一致 + 来源升级（新 CU→已有页面） | 追加 bpd-eng/CU 来源 |
| 无新增 | 页面匹配 + 类别一致 + 所有来源已确认 | 增量合并新 CU 的细节（如有） |

| 补充 | 页面不匹配 | 新增功能表单 srb-eng |
| 过时 | 基线已有页面**未被**本轮 CU 覆盖 | 保留在清单中，标注`过时`，由人类裁决移除 |

> 关系检测前先基于**全部 CU** 重新判定页面类别——新 CU 可能改变页面职责（如类别变更）。`[调整]` 是与关系类型正交的叠加标记，用于页面职责/操作活动清单有变化时。

```
     ↑                        ↑                         │
     │                        │               wft04退回  │
     │                        │                         ↓

```

```
在详细定义   ──新bpd-eng/CU修订──→ 在详细定义（版本递增，wft04 增量处理）
```

**本 Skill 写回范围**：`待确认方案` / `可以详细定义` / `待补充详细定义` / `需wft03修订`；`在详细定义` 和 `已详细定义` 由 wft04-eng 写入和推进；bpd-eng 侧 `在srb设计`（Step Start 锁定）`/已srb设计`（Step 6 推进）由本 Skill 写入（对齐 wft02 §4.1 与 91 §A.6 锁定态=下游写入）。

## 五、操作流程

**一句话**：一次运行 = Step Start 入口路由 → Step 1 材料加载 → Step 2 反馈处理 → Step 3 系统需求框架设计 → Step 4 页面编排与操作活动清单 → Step 5 覆盖自查与变更声明 → Step 6 资产写回 → Step End 输出与对话反馈。反馈走自然语言对话（§5.3），跨轮余留由 AI 标记持久化。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 前置校验与路由 | 变更感知 + 入口检测、输入校验、退回优先路由 | 无（AI 自动） | 统一 | 就绪 / 结束 | — |
| 1 | 设计材料加载 | 安全复查 + 读 AI 可以处理节点 + 加载 bpd-eng/srb-eng/资产 | 无（AI 自动） | 统一 | bpd-eng / srb-eng / 资产全景 | — |
| 2 | 方案反馈处理 | 读"待反馈处理"分节 + 对话处理人类修改意见 | **有**——对话反馈修改意见 / 整体确认 | 对话 | 调整后的 srb-eng | `05` |
| 3 | 系统需求框架设计 | Phase A 路由 / B 修订 / C 新建 + 页面类别判定 | **有**——设计决策审核（页面类别/页面职责），对话反馈 | 统一（AI 产出带判据理由）+ 对话 | 功能表单清单 + 类别 + 页面职责 + 承载关系 | `05` |
| 4 | 页面编排与操作活动清单 | 页面编排框架（区域/TAB/弹窗入口）+ 操作活动清单（承接 02 标注入口） | **有**——设计决策审核（页面编排框架/操作活动清单），对话反馈 | 统一（AI 产出带判据理由）+ 对话 | 页面编排框架 + 操作活动清单 | `05` |
| 5 | 覆盖自查与变更声明 | 覆盖自查 + 缺口处理 + 变更影响声明 | 无（AI 自动） | 统一 | 自查结论 + 变更影响声明 | `05` |
| 6 | 资产写回与落账 | 05 写回 + 25 功能表单能力引用 + 推进 bpd-eng/srb-eng 状态 + 提交基线 | 无（AI 自动，写回已确认节点） | 统一 | 04/05/25 写回 + 状态推进 | `04/05/25` |
| Step End | 运行结束输出 | 三区摘要输出 + 等待人类反馈 | **有**——查看摘要、对话反馈 | 对话 | 人类下一步操作提示 | — |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话 = AI 输出后需要你说句话（反馈或确认）才继续。Step 1/5/6 为运行内自动步骤——其中 **Step 3/4 是设计步骤（人机协同交互密度最高处）**：AI 承接配置信息组操作活动定义，基于对配置需求与已有资产的语义理解产出系统需求框架方案并附判据理由，人类在 Step End/Step 2 对系统需求框架设计决策（页面类别/页面编排框架/操作活动清单）审核、思考、决策、反馈，AI 落实；Step 2 / Step End 为人机交互步骤（对话反馈，见 §5.3）。

**反馈机制一句话**：反馈走**自然语言对话**（AI 产出方案后不结束对话，§5.3）；跨轮余留反馈由 AI 标 `[修改]`/`[驳回]` 入"待反馈处理"分节（§5.3 状态机）；人类线下修订经 Step Start 变更感知（git diff，§5.1 变更感知）检出后纳入"待反馈处理"分节；AI 每轮写回提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

### 5.1 Step Start · 前置校验与路由

> 入口条件与优先级判定遵循 [91 规范 §A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 bpd-eng）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

#### 5.1.1 入口检测

读取产品数据中的 `## AI可以处理节点` 分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口：

| # | 条件 | 检测方式 |
|---|------|---------|
| ① | **有新输入** | 「待 wft03-eng 处理」分节非空 |
| ② | **有待处理反馈** | 「待反馈处理」分节含本 Skill 产出节点 |
| ③ | **有下游退回** | 「待下游退回处理」分节含 `需wft03修订` 的节点 |

三类均不满足 → 输出"无待处理对象" → **退出**。

**退回门禁**（条件③时）：退回节点缺失说明中是否含人类改进方案（`[修改]`/`[同意]` 或下游 Skill 的具体指引）。已提供 → 通过。未提供 → 输出缺失说明，提示提供改进方案 → **退出**。

#### 5.1.2 输入校验

入口检测通过后进行校验。逻辑上不可能的条件为**硬退出**，数量/归属模糊条件为**软提示**：

> **消费前提（出口闸门再验证）**：bpd-eng 推进为 `可以srb设计` 前已通过 wft02-eng 出口闸门（[wft02-eng §3.4](eos-wft02-eng-bpl2bpd.md#34-完备性判据)——运行期制品/构件/功能、指标和配置入口足以组织系统需求框架）。此处输入校验对该判据做再验证，配置信息组操作活动定义须含配置操作、系统处理、运行期能力与 FR-ENG 指标。

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| bpd-eng 不是 P0 类型 | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft03-biz` → **退出** |
| bpd-eng 状态不是 `可以srb设计`/`待补充srb设计` | 状态不符（硬退出） | 输出不合格节点及当前状态 → **退出** |
| 配置信息组操作活动定义缺少任一项（配置操作/系统处理/运行期能力/FR-ENG 指标） | 要素缺失（硬退出） | bpd-eng → `需wft02修订`，输出缺失说明 → **退出** |
| CU 依赖不闭合且 AI 无法阶段性说明 | 依赖断点（硬退出） | bpd-eng → `需wft02修订`，输出依赖断点 → **退出** |
| 选中 bpd-eng >5 个 | 超建议阈值（软提示） | 输出超限提示 → 人类确认后继续或退出 |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

**锁定写回**：输入校验通过后，将承接的 bpd-eng 状态写为 `在srb设计`（锁定态，本 Skill 消费展开期间，对齐 91 §A.6 锁定态=下游写入 与 wft02 §4.1）；完成系统需求框架且人类确认后推进 `已srb设计`（§5.7）。

#### 5.1.3 分流处理

按优先级顺序执行（源于 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序)）：

**① 退回优先**：存在 `需wft03修订` 且门禁通过 → 读取缺失说明，按 SKILL 指南走 Phase B（§5.4.2），确认后推进为 `可以详细定义`

**② 反馈处理**：存在 `待确认方案` + 未处理反馈 → 进入 Step 2（§5.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 bpd-eng，Step End 时提示

**③ 新 bpd-eng 路由**：有未处理 bpd-eng → 进入 Step 1 → Step 3，逐节点执行 Phase A 宿主匹配（§5.4.1）

> **顺序约束**：Step 2（反馈）必须早于 Step 3（新增设计），因为反馈可能改变 srb-eng 的页面清单/类别/页面编排/操作活动清单。Phase A 匹配须基于 Step 2 修改后的最新 srb-eng 内容。

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类反馈的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `05-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.7），保证下一轮 diff 只含人类变更。

**本 Skill 的操作条目**：功能表单 + 页面编排框架 + 操作活动清单 + 承载关系。各条目的 `确认状态` 字段写入 `05-*.md` srb-eng 节点块中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3/4 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.1 入口②）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

按统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以配置信息组操作活动定义为锚点的方案修订。先理解人类反馈在 CU 操作活动定义语境中的含义，执行修订后检查 srb-eng 是否仍满足配置信息组操作活动定义的需求。

按 [91 规范 §A.5.3](91-eos-biz-eng-spec.md#a53-ai-处理流程) 的流程处理人类自然语言反馈：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足配置信息组操作活动定义 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 推进 srb-eng 至 `可以详细定义` → **提交基线并更新 HEAD（机制见 §5.7，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

**特化参数**：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 配置信息组操作活动定义——不脱离操作活动定义自行修订 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → `可以详细定义`。存在 `[修改]`/`[驳回]` 无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需重做 Step 3~5 |

### 5.4 Step 3 · 系统需求框架设计

#### 5.4.1 Phase A：页面候选生成与宿主匹配

对每个非占位 CU，按操作活动定义生成五类功能表单候选（规则见 §3.2.1），然后逐功能表单做宿主匹配：

| 页面职责冲突或同一 CU 被多个功能表单争用 | 标记 `[需裁决]` |

待聚合池按 `{引擎, CU, 页面类别, 页面候选列表}` 分组。此阶段仅粗略分组，页面类别判定和完整要素提取在 Phase C 执行。

#### 5.4.2 Phase B：修订已有 srb-eng

1. **要素提取**：从本轮配置信息组操作活动定义提取页面职责、页面编排线索和操作活动候选（§3.2.1、§3.3.1）。已有页面职责仅追加不重建
2. **宿主匹配检查**：确认配置信息组操作活动定义仍在 srb-eng 职责范围内（§3.2.3）。复用 → 追加来源；扩展 → 全量重写保留历史；冲突 → `[需裁决]`。Phase A 是候选筛选，Phase B 是精确匹配——职责扩展时不得回退 Phase A 重选宿主
3. **重判定与关系检测**：基于全部 CU 重判页面类别与页面编排框架（§3.2.2、§2.3.1），比对基线判定五类关系（§3.3.2）。新增/变更操作活动 → 标注操作活动清单
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 srb-eng 节点末尾（§4.2）

#### 5.4.3 Phase C：新建 srb-eng

1. **确定页面类型与类别** → 页面类型固定为功能表单；按职责判定五类页面类别之一（§3.2.2）
2. **定义页面职责** → 页面类别 + 页面用途 + 配置对象 + 使用角色（使用角色承接自 bpd-eng 的 R 上下文，配置或支撑角色）
3. **定义承载关系** → 来源 CU + 承载配置信息组清单（§2.4.2）
4. **承接操作活动清单** → 逐活动标注承接 02 的标注入口（§3.3.1），不重复步骤
5. **组装 srb-eng** → 写入 `05-*.md`：页面 ID/名称/类型/类别 + 使用角色 + 来源 bpd-eng/CU + 页面职责 + 承载关系 + 操作活动清单 + 页面编排框架（完整要素见 §2.1.2）

### 5.5 Step 4 · 页面编排与操作活动清单

> 按每个 CU 或强依赖 CU 组独立执行。新建 → 全量设计；修订 → 仅当配置信息组操作活动定义变更或页面拓扑变化时重验编排。
