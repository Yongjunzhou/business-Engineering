## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| 接收≥1个 bpl-biz 节点（`可以分解分配`/`待补充分解分配`），校验状态/类型/数量/跨域 | bpl-eng → `wft02-eng-bpl2bpd` |
| 按产品路径+用户角色匹配已有 bpd-biz 节点——同路径同角色归入同一 bpd-biz（Q1/Q2），无则新建（Q3） | NFR → `wft04-nfr-str2sr` |
| R 角色场景视角——推断 SL4 角色职责 + 输出文档需求定义 + 表单使用顺序 + 23A/24 对齐判定 | 下游 srb-biz 架构设计展开 → `wft03-biz` |
| P 输出产品视角——消费 wft01 P 组装（PL 路径 + WBS 归组）+ 引擎校验 + 文档方案 + 活动设计 + 权限 + PL6-B + 任务关系引擎化 | 业务人员确认（人类线下活动） |
| 汇聚业务缺口，生成补充规范化需求材料 + 登记 材料状态表 | PL6-B 条目字段详细建模 → `wft03-biz` |
| 人类确认后写回 23/24/27/28 资产（Q1/Q2/Q3 均直接写入，不二次确认） | — |
| 锁定 bpl-biz→`在分解分配`（Step 3 开始处理时）+ 推进 bpd-biz→`可以srb设计` + bpl-biz→`已分解分配` | — |
| 接收 wft03 退回的 `需wft02修订` bpd-biz 节点，按 SKILL 指南修订 | — |

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | `wft01-biz` | 产出 bpl-biz 节点（`可以分解分配`/`待补充分解分配`），含业务链文档序列 + 任务类型/节点（业务语言）+ 引擎候选建议（全量 `[推断]`）+ PL6-B 条目名称级捕获 + **P 组装结论（PL 路径 + WBS 归组 + 23 一致性）**。通过 `## AI可以处理节点` 的"待 wft02-biz 处理"分节检测 |

## 二、操作流程

### Step Start · 前置校验与路由

**变更感知**（先于入口检测，检出人类线下修订）：


检出 `HAS_CHANGES=1` → AI 检查变更行，判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入"待反馈处理"分节；自由文本 → 标记 `[需确认]`；格式/排版 → 忽略。**先变更感知再入口判定**——纯线下修订若不先检出，会被误判"无待处理对象"退出（详见 human spec §5.1 变更感知）。

**入口检测**（按 [91 规范 §A.4](../91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)）：

```bash

```

三类入口节点：
- **待 wft02-biz 处理** → 新 bpl-biz 节点
- **待反馈处理** → 人类退回的 bpd-biz 条目
- **待下游退回处理** → `需wft02修订` 的 bpd-biz 节点

**输入校验**（按顺序，命中即退出）：

| 条件 | 判定 | 动作 |
|------|------|------|
| bpd-biz 状态=`需wft02修订` 且人类未提供改进方案 | 退回方案缺失 | 输出 wft03 缺失说明 → **退出** |
| 无任何待处理节点 | 无待处理对象 | 输出"无待处理对象"→ **退出** |
| bpl-biz 状态≠`可以分解分配`/`待补充分解分配` | 状态不符 | 输出状态分布 → **退出** |
| 选中节点含 bpl-eng/bpl-nfr 类型 | 类型不匹配 | 输出类型分布 + 路由指引 → **退出** |
| 选中 bpl-biz >5 个 | 超建议阈值（软提示） | 输出建议分批 + 节点列表 → 人类确认 |

**退回优先**：存在 `需wft02修订` bpd-biz 节点 → 检查人类是否提供改进方案。已提供 → 读取缺失说明，走 Step 3~5 修订。未提供 → 输出缺失说明 → **退出**。

**反馈处理**：存在"待反馈处理"分节中 bpd-biz 节点（确认状态=`[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2。

**新 bpl-biz 路由**：有未处理 bpl-biz → 进入 Step 1→Step 3，按产品路径+用户角色匹配已有 bpd-biz（Q1/Q2 归入 / Q3 新建）。

> **执行顺序**：Step 2（反馈处理）必须先于 Step 3（新增设计）——反馈可能改变 bpd-biz 的产品路径、业务清单或权限结论。

### Step 3 · 角色场景视角 bpd-biz 设计

以 bpl-biz 场景职责边界为锚，落成 R 角色场景视角 bpd-biz。核心工作：给每个 bpl-biz 的 SL5 场景业务确定 SL4 角色职责归宿。

> **bpl-biz 锁步**：开始处理每个 bpl-biz 前，将 `02-*.md` 对应节点状态写为 `在分解分配`（活动说明，防并发重入）；Step 6 推进 `已分解分配`。

#### 3.1 推断 SL4 角色职责

| 判定 | 条件 | 动作 |
|------|------|------|
| **Q1 复用** | 已有同名/同义 SL4 且职责范围一致 | 直接引用，bpl-biz 归入该 SL4 |
| **Q2 扩展** | 已有相近 SL4 但需扩展其职责边界 | 扩展已有 SL4 + 归纳新 bpl-biz |
| **Q3 新建** | 无匹配的已有 SL4 | 新建 SL4 角色职责节点，写入 `04-*.md` |

SL3 角色类型从 bpl-biz 用户角色直接映射，不重复判定。SL4 占级规则：角色仅一个 SL5 时 SL4 不独立占级，已有 SL4 可扩展边界容纳新 L5 节点（Q2），无法归入时新建（Q3）。

Q1/Q2 归入已有 SL4 时，将本轮新 bpl-biz 的输出文档清单与该 SL4 下已有内容逐项比对——确认则升级来源、补充则全量重新展开（非增量追加）、无新增则仅加引用、矛盾则记录待人类裁决。

#### 3.2 输出文档需求定义

场景业务的需求由 bpl-biz 定义，Step 3 将其分解分配到各输出文档——每个输出文档承接一部分场景职责。对 bpl-biz 业务链中的每个输出文档，确定：

- **文档职责**：该文档在场景中承担什么角色（如"承载申请数据""记录审批结果""汇总指标"）
- **信息来源**：数据从哪个前序文档流入，或由用户直接录入
- **输出去向**：产出物被哪个后续文档消费，或直接交付给用户

SL5 与 bpl-biz 1:1 映射，场景职责复用 bpl-biz 的场景职责边界。将上述分配结果连同触发动作和上下文传递点按 bpl-biz 的业务链顺序写入 bpd-biz 节点。

**表单使用顺序**（bpd-biz 只定义场景边界和表单使用顺序，§2.2.1）：按 bpl-biz 业务链顺序排列该场景业务使用的功能表单/主子表单，定义使用先后顺序与上下文传递点（如"采购申请单录入 → 审批记录审批 → 采购订单生成"），标注 `[推断]`。页面组件/菜单编排由 wft03-biz 设计。

完成写入后执行 23A/24 对齐判定（规则见附录 A.1），写入 `04-*.md`。

### Step 4 · 输出产品视角 bpd-biz 设计

将 bpl-biz 的输出文档清单落成 P 输出产品视角 bpd-biz。分五个 Phase 执行。

#### Phase A — 引擎校验与消费 P 组装

**① 引擎候选建议校验**（权威，§3.2）：对每个输出文档，基于 bpd-biz 上下文逐文档校验 wft01 的引擎候选建议：

| 校验结果 | 判定条件 | 动作 |
|---------|---------|------|
| **确认** | 候选引擎与 bpd-biz 展开后的文档职责和处理模式完全匹配 | 去掉 `[推断]` 标记 |
| **修正** | 候选引擎部分匹配但需调整 | 写入修正后引擎 + 修正原因 + **同步修正任务类型** + 去掉 `[推断]` |
| **推翻** | 候选引擎与 bpd-biz 展开后不兼容，且 25 资产中无可替代引擎 | 标注 `[引擎待确认]` + 不兼容原因 → Step End 提示人类裁决 |

**② 消费 P 组装结论**：PL1（业务域）从 bpl-biz 读取；PL2（E2E 项目业务）/PL3（构件类型）/PL4（WBS 归组）/23 一致性结论由 wft01 的 P 组装完成（[wft01-biz §3.3.3](eos-wft01-biz-spr2bpl.md#333-bn-资产对齐判定与-bn-组装)），本 Skill 直接读取 bpl-biz 节点的 P 组装结论，**不重复归组、不重复做 23 一致性检查**。若 wft01 尚未产出 P 组装结论（旧版本 bpl-biz），AI 基于输出文档性质和校验后引擎类型推断 PL 路径，标注 `[推断]` 并在 Step End 提示补跑 wft01。

**③ 23 一致性检查（已上移 wft01）**：wft01 的 P 组装在 23B Q 判定 + WBS 归组完成后校验两者是否矛盾——归属冲突（`[23归属冲突]` 提示人类裁决）、误新建（降为 Q2）、误引用（升为 Q2/Q3），矛盾项由 wft01 暂不写回 23。本 Skill 只消费其结论，Step 6 写回时不设「23 例外」。

#### Phase B — 输出文档方案定义

对每个输出文档，PL 路径和支撑引擎确定后，定义文档的完整结构方案。

**正式文档方案**：

| 要素 | 定义内容 |
|------|---------|
| **封面字段** | DocumentCover 表映射——单据号/标题/状态/版本/创建人/部门/日期等。按文档类型裁剪（流程文档添加审批字段、计划文档添加计划周期字段） |
| **正文实体结构** | 内容实体的字段集——字段名/字段类型/约束/CRUD。从 bpl-biz 输出文档的 `业务链文档序列` 提取 |
| **主子/下钻关系** | 关联文档下钻的 1+N 子文档列表——子文档名称/关联方式（1:N 主子组装）。由正文实体结构中的子实体/关联文档导出，供 wft03 场景标签页 TAB 编排消费；无则写"无" |
| **支撑引擎** | 由 Phase A ① 校验后的引擎结论直接引用，不再重新判定 |
| **支持信息引用** | 引用关系——引用文档名称/引用方式（只读/更新）/引用用途。去重 |

**轻量文档方案**：无封面，正文实体结构定义同正式文档；支撑引擎由校验后结论直接引用。全部方案内容标注 `[推断]`，经人类确认后方可落账。

#### Phase C — 任务活动设计 + 看板指标设计

**任务活动设计**（仅针对 bpl-biz 已确认的有任务类型输出文档——计划/流程/工单）：

| **无变更** | 本轮新输入全部走来源确认或引用追加；无新增/改进/边界扩展/结构调整 | 下游无需任何动作 |
| **增量型** | 仅新增业务/场景要素，已有业务/产品路径/功能表单结构均未改动 | 已有 srb-biz 节点不受影响，仅需映射新业务 |
| **修订型** | 已有业务/场景要素被修改；产品路径与功能表单结构未变 | 对应 srb-biz 节点需局部调整 |
| **结构型** | 产品路径需新增 SL2/PL2 节点或跨业务域重组、菜单新增/合并/拆分 | srb-biz 结构可能重塑，需人类裁决后方可处理 |

判定优先级：结构型 > 修订型 > 增量型 > 无变更。Q2 在已有路径下扩展子节点属修订型。

### A.6 覆盖自查清单

Step 5 末尾使用，逐项打勾，发现遗漏仅标注不回退——写入 `[覆盖缺口]` 及缺失说明：

### A.7 bpd-biz 节点生命周期状态流转

**主线流转**（wft02-biz ←→ wft03-biz）：

```
待确认方案 ──人类确认──→ 可以srb设计 ──wft03锁定──→ 在srb设计 ──wft03完成──→ 已srb设计
     ↑                      ↑                       │
     │                      │              wft03退回 │
     │                      │                       ↓
     └──── wft02修订 ──── 需wft02修订 ←─────────────┘
```

**上游变更分流**（bpl-biz 修订触发 bpd-biz 重入）：

```
可以srb设计 → 可以srb设计（版本递增，wft03 未消费）
在srb设计   → 在srb设计（版本递增，wft03 增量处理）
已srb设计   → 待补充srb设计 → wft03补全 → 已srb设计
```

wft02-biz 写入 `待确认方案`/`可以srb设计`/`待补充srb设计`/`需wft02修订`；wft03 写入 `在srb设计`/`已srb设计`。

### A.8 PL6-B 三独立判定

| 条件 | 判据 | 正例 | 反例 |
|------|------|------|------|
| ① 独立名称 | 在文档内有固有称谓 | ✓ "订单及时率"、"采购预警" | ✗ 物料行（"序号1"不是名称） |
| ② 独立定义要素 | 有独立业务约束/规则/格式 | ✓ 指标有口径/维度/目标值 | ✗ 物料行的编码/数量由文档字段结构定义 |
| ③ 独立生命周期 | 独立于父文档的状态变迁 | ✓ 指标需审批后发布 | ✗ 物料行随申请单创建/删除 |

三项全满足 → 展开 PL6-B。轻量文档原子正文行不重复判定。

### A.9 任务节点引擎化类型→引擎映射

| 任务类型 | 引擎 | 节点转化 |
|---------|------|---------|
| 计划 | @engine-task | 角色→引擎角色配置，动作→引擎动作配置，状态变迁→引擎状态配置 |
| 流程 | @engine-flow | 同上。wft01 已捕获节点直接映射；`[待wft02推断]` 节点设计完整序列（含系统自动节点/异常路径/超时处理） |
| 工单 | @engine-workorder | 同上 |

wft01 已捕获节点是业务流转确认结果（供人类确认过），wft02 在此基础上映射引擎 CU、**不重新推断业务流转**；发现缺陷 → 标注 `[需裁决]` 或退回 wft01（详见 SKILL 指南 §2.5.1/§5.5.3）。

全部节点标注 `[推断]`，未经人类确认不得落账。
