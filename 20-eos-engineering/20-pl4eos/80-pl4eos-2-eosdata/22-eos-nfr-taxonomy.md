## AI读取文档说明

本文件是 NFR 资产文档，分类维度和具体非功能需求会随 规范化的相关方需求、业务框架和系统需求框架设计持续增长。AI 读取本文件时应按需读取，不应默认读取全部 NFR 正文。

默认读取顺序：

1. 读取文档元信息和本说明，确认本文档是 NFR 分类和具体需求资产的权威来源。
2. 读取 `0. NFR资产全貌`，了解分类规模、来源和生命周期状态。
3. 读取 `1. NFR状态与处理队列`，确认候选分类、疑似条目、具体需求审阅和人类决策。
4. 读取 `2. NFR索引 / 分片索引`，按 NFR ID、一级类目、生命周期状态或来源 Skill 定位目标块。
5. 仅读取目标 NFR 正文块、必要追溯关系和需要写回的反馈区。

扩大读取范围仅在以下情况允许：

- 候选 NFR 与多个已有分类边界冲突。
- 需要执行 bpl-nfr 聚类、SysReq-NFR 量化或全局去重。
- 索引缺失或 NFR ID 无法定位。
- 人类明确要求通读 NFR 资产。

禁止事项：

- 不得在常规 Skill 运行中默认读取全部 NFR 正文块。
- 不得将候选或疑似 NFR 直接作为已确认资产强依赖。
- 不得将旧历史正文作为当前 NFR 资产参与判断。

## 3. 规则区 / 口径区

### 3.1 NFR资产口径

1. NFR 分类和具体需求是发现型资产，不是一次性封闭枚举。
2. 已确认条目可作为 bpl-nfr、SysReq-NFR 和 pa-eng 非功能约束的稳定引用。
3. 候选、疑似和待确认条目只可用于比对、查重和审阅，不应作为强依赖。
4. 新增分类应说明与既有分类的边界差异；新增具体需求应说明指标口径和适用场景。
5. 具体需求条目应挂接到已确认或待确认分类下，不应悬空。

### 3.2 Skill读写契约摘要

| Skill | 操作 | 说明 |
|-------|------|------|
| `or03` | 读 + 判 | 用已确认分类匹配 规范化的相关方需求 中的 NFR 判 @nfr-xxx，无法匹配时在 规范化的相关方需求 上下文标注候选待写（**不写回 22**） |
| `wft01` | 读 + 承接评审写回 | 承接 or03 候选待写标注（规范化的相关方需求 上下文），聚类精炼 + 三准则评审后写回 22（候选/疑似）；对 bpl-nfr 聚类评审 |
| `wft04` | 读 + 量化 | 将 bpl-nfr 细化为 SysReq-NFR，复用或新增具体需求及指标集 |

## 4. 正文节点块

> 正文区按"一级类目（父）→ 分类维度（子）→ 具体需求（孙）"三级标题组织。
>
> **状态**取值：
> - `已确认`：经过 EOS 设计实践验证的分类维度或具体需求
> - `候选`：or03 在 规范化的相关方需求 分析中识别的未匹配已有分类的新维度，待 wft01 评审
> - `疑似`：wft01 三准则评审通过新追加的分类维度，待人类确认
> - `废弃`：经评估不再适用的分类维度
>
> 候选/疑似条目可选附加字段：
> - **bpl-nfr 引用**：引用此条目的 bpl-nfr 节点编号列表（wft01 Step 5 维护，跨轮增量追加）
>
> **来源**取值：`附录B`（继承自通用规范） / `EOS 特有`（EOS 设计过程中新增）
>
> **EOS 适用性**：`适用`——需关注；`不适用`——与 EOS 产品形态无关；`待定`——待定，留待设计过程检验

### 6.3 详细 Skill 读写契约

### 通用操作规范：三段式循环

各技能对 22 号资产的操作统一遵循"使用→丰富→修订"三段式循环。单次技能执行内完成完整循环，无需跨技能传递。

```
技能执行开始
  │
  ① 使用资产 ────→ 加载 22 正文区，按需要筛选：
  │                  ├─ 生命周期状态=已确认 → 做匹配参考
  │                  ├─ 生命周期状态=候选/疑似 → 做比对/查重
  │                  └─ 生命周期状态=废弃 → 不做处理
  │                  └→ 对输入材料逐条比对
  │                      ├─ 匹配 → 标注 ID
  │                      └─ 不匹配 → 暂存"待丰富"
  │
  ② 丰富资产 ────→ 对暂存材料做分析/聚类/精炼
  │                  └→ 将可沉淀的新资产写入 22：
  │                      ├─ 新分类维度 → #### @cand/疑似/nfr-xxx
  │                      └─ 新具体需求 → ##### @xxx-REQ-xx
  │
  ③ 修订标注 ────→ 重新加载 22（刚写入的内容已可用）
  │                  └→ 用新资产标注之前未匹配的材料
  │
技能执行结束
```

### 各技能操作表

| Skill | 阶段 | 操作 | 说明 |
|-------|------|------|------|
| **or03** | Step 1 加载 | 读已确认+候选 | 加载 22 已确认条目做 NFR 分类匹配参考，候选条目做查重避免重复标注 |
| | Step 3 比对 | 使用资产 | 对每条 规范化非功能需求 比对 22 已确认类目：匹配→标注 @nfr-xxx；无匹配→检查候选区是否有同义候选(有则跳过，无则标候选待写) |
| | Step 3 判定 | 入分流 | 同一条 规范化的相关方需求 需求表达清晰可复用→标具体需求候选待写；仅有关注点无需求模式→标分类候选待写 |
| | Step End 标注 | 修订标注 | 候选待写标注留在 规范化的相关方需求 上下文（分析建议块/规范化的相关方需求 节点），**不写回 22**；由 wft01-nfr 承接评审后写回 |
| **wft01** | Step 1 加载 | 读全部 | 加载已确认→归类依据；候选→待精炼；疑似→待进一步确认；反馈区→待处理 |
| | Step 3 归并 | 使用资产 | 按角色×分类聚类时，匹配 22 已确认条目做归类；**承接 or03 候选待写标注（规范化的相关方需求 上下文）纳入评审**；匹配候选→将当前 规范化的相关方需求 纳入候选的 规范化的相关方需求 来源集 |
| | Step 3 精炼 | 丰富资产 | 聚类后处理候选：用多条 规范化的相关方需求 精炼候选分类的名称和定义；三准则评审→通过则升格为 `#### @nfr-xxx`(状态=疑似)，未通过→反馈区建议废弃（具体需求写回归 wft04，见 §9.2） |
| | Step 5 写回 | 丰富资产 | 按 22 分类对齐结果写回：Q1→定位已有分类维度追加 bpl-nfr 引用（去重）；Q2→引用已有维度+候选扩展说明（标注 `[推断]`）；Q3/Q3+ 与承接 or03 候选待写→聚类精炼 + 三准则评审：通过→写回 22 分类维度（状态=疑似，标注 `[推断]`，待人类在反馈区确认），未通过→反馈区建议废弃（不写回）。**不写系统量化指标**（量化由 wft04-nfr 负责），**不写具体需求**（具体需求写回归 wft04-nfr）。更新概览表+最近变更 |
| | Step 5 修订 | 修订标注 | 重读刚升格的分类 ID，修正之前"未匹配"规范化的相关方需求 的标注 |
| **wft04** | Step 1 加载 | 读已确认+疑似+具体需求 | 加载 22 替换原附录B引用。已确认→SysReq-NFR 分类依据；疑似→细化中验证；候选具体需求→细化参考；反馈区→待处理 |
| | Step 3 量化 | 使用资产+丰富资产 | 逐条 bpl-nfr 分类需求项做量化：检查 22 中是否有同分类下的候选需求→有则复用结构并补 EOS 指标值，更新状态；无则判断复用价值后写入新具体需求条目 |
| | Step 6 落账 | 丰富资产 | 批量写入：完善指标集的新需求 + 追加的新需求 + 06 详细定义。更新概览表+最近变更 |
| | Step 6 修订 | 修订标注 | 无（wft04 不涉及 规范化的相关方需求 标注修订） |

### 反馈与决策区处理

所有技能统一读取反馈与决策区，筛选来源Skill=自己的待处理条目，执行对应操作后更新正文区状态和最近变更。

### 状态迁移

```
or03                     wft01                          wft04
 候选待写标注 ──────────→  承接候选→三准则评审         细化 NFR 需求
  ├─ 匹配22已确认         ├─ 通过→追加疑似              ├─ 已有需求→引用细化
  │   → 引用已确认       │   (候选→已采纳)             ├─ 发现新需求→追加具体需求
  └─ 无匹配              └─ 未通过→废弃候选             └─ 完善指标集
      → 候选待写(不写回)        ↓
                         写回 22 → 反馈与决策区（人类审阅）←────────────┘
                             │
                         ├─ 确认   → 状态=已确认
                         ├─ 修改   → 调整后确认
                         └─ 废弃   → 状态=废弃
```
