## 一、对 EOS 平台建设的指导意义

### 1.1 方法论层面的指导意义

讨论文档的核心贡献不是工具选型，而是提供了一套**思考指标和看板的正确方式**。以下方法论可以直接指导 EOS 的指标与看板体系建设。

#### 1.1.1 指标的三段式分层

讨论文档将"指标"拆分为三个独立阶段：

```
指标定义（设计层）  →  指标结果（存储层）  →  指标图示（展示层）
"量什么、怎么量"      "量出来是多少"        "让人看懂"
```

**对 EOS 的指导意义**：

07号文档将指标定义、责任书、实例、结果混在同一个菜单树下，缺少清晰的层次边界。三段式分层可以帮助 EOS 理清：
- **定义层**：管口径——这个指标是什么、怎么算、数据从哪来、有哪些维度。变更频率：月/季度。
- **目标层**：管标准——不同组织在不同时间的目标值是多少。变更频率：年初规划 + 季度微调。（讨论文档将这一层从定义层中独立出来，这是对的——目标和口径的变更节奏完全不同，耦合在一起会导致改个目标值就要改指标定义。）
- **结果层**：管实测——某个周期内实际算出来/填报上来的值是多少。变更频率：每次计算/填报产生新数据，历史数据不可变。

**07号文档需要调整的点**：目前 `indicator_def` 表上同时挂了计算口径字段（聚合函数、维度配置）和目标值字段（`target_value`、`alert_value`），应该拆分为两张表——`metric_definitions`（口径）和 `kpi_targets`（目标值，含组织+时间维度）。

#### 1.1.2 预计算 vs 即时计算的区分

```
预计算路径：数据写入时就算好聚合值 → 查询时直接读 → 毫秒级，但丢失原始明细
即时计算路径：保留原始明细 → 查询时现场聚合 → 秒级，但可下钻到每一行业务数据
```

**对 EOS 的指导意义**：

EOS 的业务 KPI 场景中，这两种模式天然对应两种已有的能力，不需要引入新存储引擎：

| 模式 | EOS 中的实现 | 适用场景 |
|------|------------|---------|
| **预计算** | 定时任务 → 执行聚合 SQL → 写入指标结果表 | KPI 看板的 Stat 卡片、趋势图（读已算好的值） |
| **即时计算** | 用户在图表上点击下钻 → 直接跳转实体列表页（带筛选条件） | 看到异常值后想查"哪些实例拉低了指标" |

关键设计点：**预计算结果表中存的是聚合值，用户下钻时不重新查结果表，而是把聚合查询的筛选条件（时间范围 + 维度值）转换为实体列表的筛选条件，直接查业务表。** 这样不需要引入 ClickHouse，利用 EOS 已有的实体列表 + 条件筛选能力即可。

#### 1.1.3 看板的两段式模型

```
看板定义（配置规格）  →  看板图示（渲染结果）
Dashboard Definition    Dashboard
```

**对 EOS 的指导意义**：

08号文档已经有看板定义（`board_def` + `board_version` + `board_page` + `board_chart_layout`），但缺少"看板图示"这个阶段的独立描述。补充这个区分后：
- **看板定义**：存储在数据库中，是配置数据（哪几个图表、怎么排列、什么过滤条件）
- **看板图示**：定义渲染后的视觉效果，用户实际看到的页面
- **看板清单图示**：看板目录页中每个看板的摘要卡片（只渲染第一行 Stat 面板），不展开完整看板

#### 1.1.3.1 看板图示与相关概念的辨析

讨论文档和08号文档中涉及多个与"看板渲染"相关的概念，容易混淆。此处逐一厘清。

**（1）看板图示 vs 看板预览**

| | 看板图示 | 看板预览 |
|------|---------|---------|
| **英文** | Dashboard (Visualization) | Preview |
| **来源** | 讨论文档的两段式模型（定义→图示） | 08号文档的配置Tab交互 |
| **本质** | 看板定义渲染后的**最终产物** | 配置过程中的**临时效果** |
| **受众** | 业务用户（终端消费者） | 配置人员（看板设计者） |
| **数据** | 真实全量数据 | 可用采样数据（取前100条） |
| **交互** | 完整（联动、筛选、下钻、翻页、轮播全部可用） | 可能不完整（下钻目标可能尚未发布） |
| **出现场景** | 菜单入口 / 全屏大屏 | 看板配置Tab中点击"预览" |
| **生命周期** | 发布后持续存在 | 编辑完成后不再需要 |

**一句话**：看板预览是配置人员在设计阶段的临时验证工具，看板图示是业务用户日常使用的正式产物。

**（2）看板图示 vs 看板摘要卡片**

讨论文档 §二十九 引入了一个中间形态——看板摘要卡片：

| | 看板图示 | 看板摘要卡片 |
|------|---------|------------|
| **完整度** | 完整（所有行、所有面板） | 裁剪（仅渲染第一行概览面板，通常是 Stat 阵列） |
| **出现位置** | 菜单入口 / 全屏大屏 | 看板清单 > 切换到"图示视图" |
| **目的** | 深度诊断决策 | 快速扫览、并排对比多个看板 |
| **受众** | 所有业务用户 | 管理者（一次扫览多个看板状态） |
| **渲染方式** | 活渲染（实时查询，完整图表引擎） | 同样活渲染（只是裁剪了渲染范围，数据仍是实时的） |

**（3）看板图示 vs 缩略图**

两者有本质区别：

| | 看板图示 | 缩略图 |
|------|---------|------|
| **本质** | 一个**完整的、可交互的**页面 | 一张**静态的、不可交互的**截图 |
| **数据** | 实时查询，每次打开都是最新值 | 生成时刻的快照，不会更新 |
| **交互** | 图表联动、筛选、下钻、翻页全部可用 | 点击最多只能跳转到完整看板 |
| **渲染方式** | 浏览器完整渲染图表引擎 | 通常是 PNG/JPG 图片 |
| **典型尺寸** | 自适应屏幕 | 固定小尺寸（如 300×200px） |

看板摘要卡片容易让人误解为"截一张缩略图"，但它不是——它是活渲染的，只是裁剪了渲染范围（只出第一行）。08号文档 §5.1.4 中"多页画布"底部的页面缩略图才是传统意义上的缩略图（静态截图，用于配置态导航）。

**（4）三个概念的定位关系**

```
看板定义（dashboard_definitions + dashboard_panels）
  │
  ├── 配置态 ──→ 看板预览      （配置人员：右侧实时预览，或点击"预览"按钮）
  │
  └── 发布态 ──→ 看板图示      （业务用户：菜单打开，完整渲染）
                    │
                    └── 裁剪版 ──→ 看板摘要卡片  （管理者：看板清单图示视图中的第一行概览）
```

三者数据来源相同（同一份 `dashboard_definitions` + `dashboard_panels`），区别在于**渲染完整度、出现场景和目标受众**。

#### 1.1.4 看板 vs 指标图示的三条不可约简差异

讨论文档指出了指标清单的图示模式与看板之间的三个本质区别：

| 序号 | 差异 | 指标图示模式 | 看板 |
|------|------------|------|------|
| 1 | 同一指标多次出现 | 不能（一行指标=一张图） | 能（设计师决定） |
| 2 | 非指标内容 | 不能（数据源只能是指标表） | 能（文本/图片/iframe） |
| 3 | 跨指标运算 | 不能（每图一条查询） | 能（面板级组合多指标） |

**对 EOS 的指导意义**：

这三条差异帮助 EOS 明确了**什么场景用指标图示、什么场景用看板**：
- **指标图示**：探索性场景。"我想看看支付域的所有指标最近趋势如何"——筛选业务域→切换到图示网格→扫一眼。这是系统自动映射的，不需要手工编排。
- **看板**：固化场景。"支付总监每天早上要看这4个数字、2张趋势图"——这是人工编排好的，面向特定受众，有叙事结构（从上到下、从宏观到微观）。

**08号文档需要补充的点**：目前08没有"从指标图示一键固化为看板"的路径。用户在图示模式中筛选出一组有价值的指标后，应该能一键保存为看板定义，形成"探索→固化→定期查看"的闭环。

#### 1.1.5 下钻终点的四种取值

讨论文档将"从聚合值点下去能看到什么"抽象为四种情况：

| 序号 | 取值 | 含义 | EOS 中的实现 |
|------|------|------------|------------|
| 1 | **业务数据** | 可下钻到原始业务记录，一行一条 | 跳转实体列表页，带筛选条件 |
| 2 | **统计结果** | 可下钻到按某维度拆分的聚合值 | 弹出分组图表（按部门/时间拆分） |
| 3 | **外部链路** | 可跳转到外部系统详情 | 跳转到流程详情/工单详情/日志平台 |
| 4 | **无下钻** | 点击无反应 | 纯展示的 Stat 卡片 |

**对 EOS 的指导意义**：

这是一个实用的交互设计规范。07和08号文档目前完全没有下钻终点的概念。应该在图表组件配置中增加一个"下钻行为"字段，取上述四种值之一，指导前端渲染点击行为。

**对"下钻终点"概念的重新解读：**

"下钻终点"这个词有误导性——它的本意不是标记"不能再往下走了"，而是标记**"点击后下一层渲染成什么形态"**。不同形态能继续往下走的能力是不同的。

| 取值 | 点击后渲染成 | 还能继续往下点吗 | 为什么 |
|------|------------|:---:|------|
| **业务数据** | 实体列表页（一行一条业务记录） | 能 | 列表页里的每条记录本身可点击——点进详情、点进关联实体。这是 EOS 实体引擎自带的能力，不需要额外配置。 |
| **统计结果** | 另一个图表（换了分组维度） | 能，但受限 | 每次下钻换一个维度（总量→按部门→按岗位），维度穷尽了就没得拆了。而且如果数据来自预计算的结果表，原始明细已被聚合丢弃，到不了单条记录。 |
| **外部链路** | 跳转到外部系统页面 | 取决于外部系统 | EOS 管不了了——跳过去之后，外部系统支持什么交互就是什么。 |
| **无下钻** | 点击无反应 | 不能 | 设计上就不期望交互。 |

那为什么不能靠"用户配置下一级，一路往下点、点不动就是终点"来替代这个字段？两个原因：

**原因一：预计算结果无法到明细。** 指标"支付成功率"= COUNT(成功订单) / COUNT(全部订单)，这个聚合执行时原始订单明细已被丢弃，结果表里只有一行聚合值。用户点击下钻时，能按下一级维度拆分（看各岗位的成功率），但永远到不了具体哪几笔订单失败。这不是因为"没配置下一级"，而是因为数据源本身不支持。如果不显式标注，用户点了三次还在看聚合图表，会困惑"为什么别的指标能点到订单列表，这个不行？"。

**原因二：跨数据源跳转的上下文断裂。** 聚合图表（来自指标结果表）→ 下钻到实体列表（来自业务表，另一个数据源）→ 继续下钻到流程详情（来自流程引擎，又一个系统）。这条链路上每跳的数据源都变了，查询条件要翻译、字段要映射。显式声明每跳的形态，等于在配置时就标注了链路结构，方便配置人员理解和维护。

**EOS 实际只需要区分两种：** EOS 的所有业务数据都在 Oracle/MySQL/KingbaseES 的实体表中，不涉及 Prometheus TSDB 那种"原始数据被不可逆丢弃"的情况。所以 EOS 可以简化为：图表组件配置中，"下钻行为"选一个——①跳转实体列表（带筛选条件）②按维度拆分（弹出新聚合图表）③跳转外部URL ④无交互。选①时，实体引擎天然支持继续往下点；选②时，维度穷尽后自然停止。不需要额外声明"终点"，只需要声明"形态"。

#### 1.1.6 指标定义的六个维度

讨论文档提出一个完备的指标定义包含六个维度：

| 序号 | 维度 | 回答的问题 | EOS 对应字段 |
|------|-----------|------------|------------|
| 1 | 度量对象 | 量什么属性？ | 指标名称 + 描述 |
| 2 | 度量方法 | 从哪里取数、怎么算？ | 数据源 + 聚合字段 + 聚合函数 + 计算范围 |
| 3 | 单位与精度 | 数值以什么单位表达？ | 07缺少此字段 |
| 4 | 统计口径 | 原始数据如何聚合？ | 聚合函数 + 时间窗口 |
| 5 | 采集机制 | 数据如何获取与传输？ | 计算方式(auto/manual/formula) |
| 6 | 判定标准 | 什么值算好、什么值算差？ | 目标值/警戒值（07为扁平字段，应升级为三维模型） |

**对 EOS 的指导意义**：07号文档的指标定义字段基本覆盖了前五个维度，但**单位字段缺失**（目前只能从聚合字段的类型推断），**判定标准维度**需要从扁平字段升级为 `kpi_targets` 三维模型。

### 1.2 EOS 尚未考虑、需要补充的功能事项

以下按优先级排列。

#### P0：必须补充（影响核心架构）

| # | 事项 | 来源 | 说明 |
|---|------|------|------|
| 1 | **指标定义增加所属四字段** | 讨论文档 §二十四/二十六 | `business_domain`（业务域）、`owner_org_node_ids`（所属组织节点，数组）、`owner_team`（管理团队）、`owner_person`（负责人）。这四个字段决定了"谁可以看到这个指标"和"指标目录默认筛选展示哪些"。07号文档完全没有组织和人员归属字段。 |

| 3 | **指标定义与目标值分层** | 讨论文档 §二十六 | 定义层（`metric_definitions`）、目标层（`kpi_targets`）、结果层（`indicator_result` + 快照）三层独立。变更频率不同（口径月/季度变，目标年初+季度微调，结果每次计算产生），耦合在一起会导致改目标值就触发指标定义的版本变更。 |
| 4 | **图表组件的下钻配置** | 讨论文档 §十六/二十二 | 图表组件配置中增加"下钻行为"字段（业务数据/统计结果/外部链路/无下钻），指定点击图表元素后的行为。本质是声明"下钻后渲染成什么形态"，而非标记"停在哪里"——详见 §1.1.5 重新解读。当前08只有简单的"下钻目标：页面模型"，缺少这个语义抽象。 |

| # | 事项 | 来源 | 说明 |

| 5 | **指标清单 ↔ 图示网格切换** | 讨论文档 §二十七 | 指标清单页面增加"列表视图"和"图示视图"两个标签页。列表视图：Excel 风格列头筛选（业务域、所属组织、周期、状态等）。图示视图：将筛选后的指标渲染为卡片网格，每个卡片展示该指标的当前值 + sparkline 趋势线。筛选条件和排序在切换时保持。 |

| 9 | **看板定义增加所属和可见范围字段** | 讨论文档 §二十九 | `dashboard_definitions` 增加 `business_domain`、`owner_org_node_ids`、`owner_team`、`owner_person`、`visible_to_org_nodes`。owner 决定"归谁管"，visible 决定"谁能看"——两者可以不同。 |

## 二、讨论文档存在的问题

### 2.1 与 EOS 平台存在的矛盾

#### 2.1.1 技术栈预设与 EOS 多数据源架构冲突

讨论文档预设的技术栈：

```
Prometheus（采集+TSDB） + Grafana（可视化） + ClickHouse（即时计算） + K8s CronJob（定时任务）
```

EOS 平台的实际情况：

```
EOS 数据源抽象层 → Oracle / 人大金仓 / MySQL / (未来可能 Doris)
EOS 图表渲染 → eCharts 自研（08已有完整设计）
EOS 调度 → 海豚调度器（07已有提及）
EOS 部署 → 传统虚拟机 / Docker Compose（不一定有 K8s）
```

逐一分析矛盾：

**（1）Prometheus 与业务 KPI 的模型冲突**

| 序号 | 维度 | Prometheus 的设计假设 | EOS 业务 KPI 的实际情况 |
|------|----------------------|------------------------|------------------------|
| 1 | 采集频率 | 每 15 秒自动 pull | 每天/每周/每月定时计算 |
| 2 | 数据来源 | 服务暴露 `/metrics` 端点 | 通过数据源抽象层执行 SQL 聚合 |
| 3 | 保留期 | 7~30 天（Block 过期删除） | 至少 13 个月（用于同比），审计需要 2 年以上 |
| 4 | 数据模型 | `(name, labels, value, timestamp)` 四元组，单值无状态 | 一条结果有一个原始值、一个申诉值、一个确认值；有 pending→active→appealed→locked 生命周期状态 |
| 5 | 基数约束 | label 基数决定内存开销，禁止高基数 label | 组织维度（部门/岗位/人员）天然就是高基数的，且需要作为查询维度 |

Prometheus 是为**机器产生的高频运维指标**设计的，不是为**人工管理的低频业务 KPI** 设计的。将 Prometheus 引入 EOS 指标体系，等于用一套领域模型去套另一领域的场景。

**（2）Grafana 与 EOS 自研图表体系的冲突**

08号文档已经定义了一套完整的图表组件体系（16 种类型，基于 eCharts 自研渲染），包含图表联动、过滤组件、多页画布、公共链接分享、版本管理等。引入 Grafana 会导致：
- 两套图表渲染引擎并存
- 两套认证/权限体系
- 两套交互规范（EOS 右键菜单 vs Grafana 面板编辑）
- 用户体验割裂（iframe 嵌入，性能不可接受）

讨论文档在 §二十七 的"实现技术栈"中也承认了这一点——"不建议用 Grafana iframe 嵌入，筛选出 50 个指标 = 50 个 iframe 性能不可接受"。但整份文档仍然以 Grafana 为主要可视化方案进行讨论，前后矛盾。

**（3）ClickHouse 的过度引入**

EOS 的业务 KPI 数据量估算：

```
指标定义：几百条
每周期结果：几百个考核对象 × 几十个指标 = 几千到几万条
每年：几万到几十万条
```

MySQL/Oracle/KingbaseES 加合理的索引和分区完全够用。引入 ClickHouse 需要部署集群、搭建数据同步管道、团队掌握新的运维技能——性价比极低。

而且 EOS 的下钻机制不需要扫描明细表现场聚合。下钻的正确实现是：**把聚合查询的筛选条件转换为实体列表的查询条件，直接打开实体列表页**。07号文档 §3.1.3 中提到的 Doris 快照方案（周期末生成一次快照用于长期归档）已经足够务实。

**（4）K8s CronJob 的环境假设错误**

EOS 是一个低代码平台，不假设客户跑在 Kubernetes 上。很多企业客户部署在传统虚拟机环境。EOS 已经有自己的调度基础设施（海豚调度器），应该复用平台已有能力。

#### 2.1.2 场景偏差：运维监控 vs 业务 KPI

讨论文档几乎所有的例子和论述都来自运维监控领域：

| 序号 | 讨论文档使用的例子 | 所属领域 |
|-------------------|---------|---------|
| 1 | `http_request_duration_ms` | API 延迟监控 |
| 2 | `cpu_usage_percent` by `host` | 服务器 CPU |
| 3 | `error_rate` by `region` | 错误率按机房 |
| 4 | `api_requests` 明细表 | 请求日志 |
| 5 | OpenTelemetry SDK 埋点 | 应用性能监控 |
| 6 | Prometheus Exemplar → trace_id → tracing 系统 | 分布式追踪 |

而 EOS 管理的是业务 KPI：

| 序号 | 07号文档的例子 | 所属领域 |
|---------------|---------|---------|
| 1 | 科研计划完成率 | 项目管理 |
| 2 | 部门综合 KPI | 绩效考核 |
| 3 | 安全得分 | 合规管理 |
| 4 | 月度生产完成率 | 制造执行 |
| 5 | 责任书（考核对象+周期+权重） | 绩效管理 |

两类指标的根本差异：

| 序号 | 比较维度 | 运维指标 | 业务 KPI |
|---------|---------|----------|----------|
| 1 | **产生方式** | 代码自动埋点 | 定时 SQL 聚合 / 人工填报 |
| 2 | **更新频率** | 秒级 | 天/周/月 |
| 3 | **基数规模** | 百万级时间序列 | 百~千个指标 |
| 4 | **维度** | 机房/服务/接口（低基数，几十到几百） | 部门/岗位/人员（组织树，天然高基数） |
| 5 | **下钻需求** | 跳到日志/tracing 查看单次请求 | 跳到实体列表页查看具体业务记录 |
| 6 | **告警模式** | 即时（P95 > 500ms 立刻通知） | 周期内评估（月度过半才开始，支持申诉） |
| 7 | **数据状态** | 无状态，每次采样独立 | 有状态：pending→active→appealed→locked |
| 8 | **审计需求** | 弱 | 强（绩效考核涉及薪资，需要完整审计链） |
| 9 | **目标值特征** | 通常全局恒定（SLO） | 按组织×时间差异化（不同部门、不同季度的目标不同） |

讨论文档在 §十四花了大量篇幅讲 Gauge/Counter/Histogram/Summary 四种 Prometheus 指标类型如何取值，但这四种类型对标的是"CPU 温度""HTTP 请求总数""API 延迟分位数"——没有一种对应到"业务 KPI 的申诉/确认/锁定"这个三值模型。

#### 2.1.3 与 07/08 号文档缺少对接

讨论文档第三十一章把自己封装为"91 规范引擎的 CU 增强方案"，但没有做真正的差异分析：

- 07号文档已有的字段，哪些保留、哪些修改、哪些废弃？没有说。
- 07号文档的"责任书"概念（指标定义→责任书→实例→结果）是一个完整的考核闭环。讨论文档用 `kpi_targets`（三维阈值立方体）替代了这个闭环中的一部分，但申诉确认流程、KPI 总得分计算、责任书实例的自动生成——这些在讨论文档中没有对应物。
- 08号文档的图表组件体系（16 种类型、图表配置、版本管理、公共链接）与讨论文档的看板面板体系是什么关系？并存还是替代？没有讨论。

这不是说讨论文档的方案一定比 07/08 差，而是说**讨论文档没有解释为什么用新方案替代旧方案，甚至连旧方案的存在都没有提及**。这使得它读起来像是一份从零设计的新系统方案，而不是对现有系统的演进建议。

#### 2.2.6 责任书体系被忽略

07号文档的核心主线是：指标定义 → 责任书定义（绑定考核对象+周期+指标+权重） → 责任书实例（每个考核周期自动/手动生成） → 指标结果（计算/填报 → 申诉 → 确认 → 锁定）。

这是一个完整的、经过设计的考核管理闭环。讨论文档用 `kpi_targets`（三维阈值立方体）覆盖了其中的"目标值管理"环节，但对于以下 07 的核心能力完全没有讨论：

- 责任书定义：考核对象类型（部门/岗位/职位/用户/全组织）、考核周期类型（月度/季度/半年度/年度/自定义）
- 实例生成机制：周期首日 0:00 自动生成 vs 手动触发
- 指标构成权重：复合 KPI = Σ(子指标 × 权重)
- 申诉/确认流程：被考核方申诉 → 主管审核 → 确认值
- 结果锁定：周期到期自动锁定，锁定后不可变更
- 解锁：系统管理员或考核主管审批解锁

讨论文档如果定位为对 07 的补充和增强，就应该在这些已有设计的基础上做增量，而不是用一套新的表结构（`kpi_targets`）覆盖其中一个环节后对剩余环节保持沉默。

## 三、总结

### 应该吸收的核心方法论

1. **指标三段式**：定义层（口径）→ 目标层（标准）→ 结果层（实测），三层独立、变更节奏不同
2. **预计算/即时计算分离**：看板读预计算结果（快），下钻走实体列表即时筛选（不需要新存储引擎）
3. **下钻行为**：四种取值（业务数据/统计结果/外部链路/无下钻），本质是声明"下钻后渲染成什么形态"而非"停在哪里"。EOS 可简化为两种：跳转实体列表 vs 切换聚合维度。详见 §1.1.5。
4. **看板 vs 指标图示的边界**：三条不可约简差异，决定了什么时候用自动映射、什么时候用人工编排
5. **看板两段式**：定义（配置）→ 图示（渲染），区分配置数据和渲染结果
6. **所属四字段**：业务域 + 所属组织 + 管理团队 + 负责人，决定"谁能看到什么"
7. **列表 ↔ 图示切换**：筛选条件跨视图保持，从表格探索到图形感知的自然过渡

### 应该搁置的工具选型

| 序号 | 工具 | 建议 | 理由 |
|------|------|------|------|
| 1 | Prometheus | **不引入** | 模型假设（高频采集、短保留、单值无状态）与业务 KPI 根本冲突 |
| 2 | Grafana | **不引入** | EOS 已有 eCharts 自研图表体系，引入反而造成体验割裂 |
| 3 | ClickHouse | **暂不引入** | 当前数据量 MySQL 完全够用，等到亿级再评估 |
