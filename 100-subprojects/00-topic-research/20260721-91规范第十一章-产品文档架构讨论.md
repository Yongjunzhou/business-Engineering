- 同一个文件里既有索引、状态字段、反馈区、AI最近变更（给AI用的），又有架构正文（给人类看的）
- 人类打开文件看到的是噪音（状态字段、反馈区、变更记录）

## 三、"表单化"需求

### 3.1 需求描述

有人希望23号资产应有一个表单化的文档，直接给出从业务域到文档业务的节点。表单中：
- 构件是资产，可以复用
- 构件下的文档也是资产

### 3.2 架构含义

这意味着当前23号资产从 heading 层级树变成**表单/表格**（每一行是独立的扁平节点），并且构件和文档都升级为**独立可复用资产**——有独立ID（`@node-*`、`@doc-*`）、可跨域引用。

目标表单大约长这样：

```
业务域 | E2E项目 | 构件(资产) | 构件ID | 文档(资产) | 文档ID | 实现策略 | 来源引擎 | 复用来源
───────|────────|───────────|────────|───────────|────────|─────────|─────────|─────────
产品生产|生产产品 | 生产计划   |@node-mfg-plan|生产计划表|@doc-mfg-plan|平台配置|@engine-task|—
产品生产|生产产品 | 生产工单   |@node-work-order|生产工单|@doc-work-order|平台配置|@engine-workorder|—
采购管理|采购产品 | 采购订单管理|@node-po|采购订单  |@doc-po    |平台配置|@engine-flow|—
售后服务|服务产品 | 维修工单   |@node-repair|维修工单  |@doc-repair|平台配置|@engine-workorder|@doc-work-order（复用）
```

### 3.3 表单化能否从当前23号资产机械生成

逐列分析：

| 目标列 | 当前23号有没有 | 能否机械生成 |
|--------|-------------|------------|
| 业务域 | ✅ `## {域名称}` heading | ✅ 直接提取 |
| E2E项目 | ✅ `### 产品正文块 / {E2E项目名}` | ✅ 直接提取 |
| 构件（资产） | ✅ `#### {构件名称}` | ✅ 直接提取 |
| 构件ID | ✅ `@node-*` | ✅ 直接提取 |
| 文档（资产） | ⚠️ `**输出**：{文本}` | ⚠️ 有名称，无ID |
| 文档ID | ❌ 当前是自由文本，不是资产 | ❌ 不存在 |
| 实现策略 | ✅ `**实现策略**` 字段 | ✅ 直接提取 |
| 来源引擎 | ✅ `**来源模型**` 字段 | ✅ 直接提取 |
| 复用来源 | ❌ 文档复用关系无法表达 | ❌ 不存在 |

**结论：能生成半成品。** 阶段1（机械转换）全自动，阶段2（资产化标注——给文档分配ID、识别复用关系）需要AI推断+人类确认。

## 四、23号资产与26号资产的引用关系

### 4.1 26号资产的定位

[26号资产](../20-pl4eos/80-pl4eos-2-eosdata/26-eos-document-definitions.md) 是文档资产清单。其规则区 §3 明确写道：

> `23` 的输入文档 / 输出文档列应引用本文档 ID，不直接写长定义。

**设计意图已存在，但物理实现还差一步**——26号资产目前只有骨架（仅一个 `@doc-template` 模板条目），实际文档条目尚未填充。

### 4.2 完整的引用架构

```
26号资产（文档定义——权威源）              23号资产（表单化——引用方）
┌──────────────────────────┐          ┌──────────────────────────────────────┐
│ @doc-purchase-order      │          │ 业务域  │ E2E项目 │ 构件    │ 文档ID   │
│   名称：采购订单          │◄─────────│ 采购管理│采购产品 │采购订单 │@doc-     │
│   包含字段：单号/日期/... │  引用    │         │         │管理     │purchase- │
│   产出方：@node-purchase- │          │         │         │         │order     │
│             order         │          │ 产品生产│生产产品 │生产计划 │@doc-     │
│   消费方：...             │          │         │         │         │prod-plan │
│   生命周期：创建→审批→... │          │ ...     │ ...     │ ...     │ ...      │
└──────────────────────────┘          └──────────────────────────────────────┘
```

**23号表单的"文档ID"列不是自生成的，而是对26号资产的引用。** 这意味着表单化23不能独立存在——它依赖26号资产先有文档条目。

### 4.3 修正后的生成路径

```
步骤1：从23提取（机械）
  解析所有 @node-* 节点 → 得到 [域, E2E项目, 构件, 构件ID, 输出文本, 实现策略, 来源引擎]

步骤2：26匹配（查表）
  对每行的"输出文本"：
    → 检索26号资产索引表，按名称/语义匹配已有 @doc-*
    → 命中 → 填入文档ID列
    → 未命中 → 文档ID列标记 [→待26新增]，同时生成候选 @doc-* ID

步骤3：26补齐（人机协作）
  对步骤2中未命中的文档：
    → 在26号资产状态队列追加"新增文档资产"条目
    → 人类或AI填充文档定义（字段结构、生命周期、消费方）
    → 确认后生效，23表单行回填正式 @doc-*

步骤4：表单生成
  所有文档ID就绪 → 渲染完整表单
```

### 4.4 一般化：资产间引用模式

23引用26不是个例。回看资产全景：

| 资产 | 定义什么 | 被谁引用 |
|------|---------|---------|
| 24 业务资产 | 业务域/E2E项目/角色/WBS | 23、04、05 |
| 25 引擎资产 | 引擎定义/CU定义 | 23、04、05 |
| 26 文档资产 | 文档定义 | 23、04、05 |
| 28 看板指标资产 | 指标/看板定义 | 23、04、05 |

**每对引用关系都是一个"ID列引用另一个文件"的模式。** 第十一章如果只讲"单个文件的内部结构"，就漏掉了跨文件的资产引用架构。

## 五、核心洞察：读写分离

### 5.1 根本矛盾

当前 §11 把 AI 的工作台和人类的阅读台硬塞进同一个文件格式。分离后：

```
当前 §11 模型（一体两面）              分离后的模型
─────────────────────────             ─────────────────
                                      
  01-eos-original-requirements.md       AI 工作区（单文件或多文件，§11格式）
  ├── 元数据（版本/HEAD）               ├── 自描述索引
  ├── 自描述索引                        ├── AI最近变更
  ├── 业务域索引                        ├── AI可以处理节点
  ├── AI最近变更                        ├── 反馈区
  ├── AI可以处理节点                    └── 域正文块（heading树/表单）
  ├── 域正文块（含反馈区）
  └── 附录                              人类阅读区（单文件，纯架构）
                                        ├── 一张干净的表单或结构化正文
     人类和AI看同一份                    │   业务域|E2E项目|构件|文档|引擎
     → 索引对人是噪音                    │   （无索引/无状态/无反馈区）
     → 反馈区对人是噪音                  │
     → 状态字段对人是噪音              ──生成/同步──→ 人类打开即读
```

### 5.2 人类阅读文件的定义

人类阅读文件是**纯架构内容**的干净呈现：

- 不含：自描述索引、AI最近变更、AI可以处理节点、确认状态字段、AI建议字段、子条目状态字段、反馈区
- 不含节点的生命周期状态、待裁决标记
- 自包含：一张表/一份结构化正文包含全部架构内容
- 标注数据来源：文件头部标注"数据来源：{AI工作文件列表及版本}"

**关键约束**：AI 工作文件是**权威数据源**。人类阅读文件是**派生视图**，不承载状态，不作为下游 Skill 的输入。任何对架构内容的修改必须发生在 AI 工作文件中，然后重新生成人类阅读文件。

### 5.3 AI 工作文件 vs 人类阅读文件

| | AI 工作文件 | 人类阅读文件 |
|------|-----------|------------|
| **格式** | §11 完整格式（索引+元数据+状态+反馈区+正文） | 纯架构内容（表单或结构化正文） |
| **文件数** | 单文件或多文件（按域拆分） | 通常单文件（全量合并） |
| **内容** | 增量、带状态、可追溯 | 快照、干净、可读 |
| **谁写** | AI（通过 Skill 运行） | AI（从工作文件生成，按人类指令或同步触发） |
| **谁读** | AI（Step Start 入口判定、设计材料加载） | 人类（浏览、审阅、决策） |
| **版本** | 每次 AI 运行递增次版本 | 按生成批次标注数据来源版本 |

## 六、单文件 vs 多文件

### 6.1 上下文占用分析

机制的核心是 `grep 定位 + 索引发现 + 逐级缩小`。grep 不消耗上下文窗口，最终读到 context 里的内容行数在单文件和多文件模式下是一样的。

**场景对比**：

AI 要处理 `@node-supplier` 这一个节点：
- 单文件：context已有业务域索引（15行）→ grep 定位 → Read ~10行 → 消耗 ~10行
- 多文件：context已有根索引（~18行）→ grep 定位文件 → Read ~10行 → 消耗 ~10行
- **完全一样。**

AI 要做跨域扫描（"找出所有来源引擎为空的构件"）：
- 单文件：`grep -n '\*\*来源模型\*\*：—' 目标文件` → 逐行Read上下文 ~150行
- 多文件：逐文件 `grep -rn '\*\*来源模型\*\*：—' 域目录/` → 逐行Read上下文 ~150行
- **还是一样。** grep 不占 context，Read 的行数相同。

**结论：对 AI 上下文占用，单文件和多文件没有实质区别。** 多文件的收益不在于减少上下文占用量。

### 6.2 多文件的真实收益

| 收益 | 是否真实 | 说明 |
|------|---------|------|
| **并行写隔离** | ✅ | 不同文件的写回在 Git 层面物理隔离，不会冲突 |
| **人类可管理性** | ✅ | 一个域一个文件，打开不卡，导航直观 |
| **域独立生命周期** | ✅ | 归档/废弃一个域 = 删除一个文件 |
| Git 冲突规避 | ⚠️ | 真实，但当前串行运行模型下基本不存在此场景 |
| 减少 AI 上下文 | ❌ | grep 不占 context，Read 的行数相同 |

### 6.3 并行写隔离是架构性优势

当前运行模型是人类串行调用 Skill，但不代表永远如此。如果架构在规范层面就关闭了并行可能性（单文件强制），将来要并行时需要同时改规范和实现。如果规范允许多文件作为一种模式，当前串行可用，将来并行也可以直接受益。

多文件模式不是上下文优化策略，而是**组织和协作优化策略**。在 §11 中应诚实陈述。

## 七、文件拆分粒度：三层结构的讨论

### 7.1 规模估算

```
15 域 × 10 E2E项目 × 20 构件 = 3000 构件节点
加上文档资产引用、活动节点 → 5000~8000 行
```

### 7.2 三种拆分粒度

**方案A：域级文件（前两层合并）**

```
23-eos-output-architecture/
  ├── procurement.md            ← 一个域 = 一个文件（10个E2E项目，200+构件，2000行+）
  ├── manufacturing.md
  └── ...
```

问题：并行隔离不够。同一个域内的不同 E2E 项目**恰恰是最可能被并行处理的**——它们共享同一个域语境，OR 可能同时到达。两个 Skill 实例分别处理同一个域的两个不同 E2E 项目 → 写同一个文件 → 冲突。

**方案B：E2E项目级文件（三层独立）**

```
23-eos-output-architecture/
  ├── procurement/
  │   ├── prod-procurement.md
  │   ├── prod-supplier-management.md
  │   └── ...（~10个文件）
  └── ...
```

150 个项目文件。问题：
- 目录臃肿：150 + 15 + 1 = 166+ 文件
- 索引维护链长：写回一个项目 → 更新域索引 → 更新根索引，三步级联
- 文件过小：60 行的文件，索引行比内容行还多
- AI 路由开销：根索引→域索引→项目文件三层
- 人类浏览：在文件系统中翻 15 个目录找目标

**150 个 60 行文件的管理负担 > 1 个 5000 行文件的导航负担。**

### 7.3 最终方案：域级文件为默认，按需下钻

```
默认（简单情况）：
23-eos-output-architecture/
  ├── 23-index.md                ← 根索引
  ├── procurement.md             ← 一个域一个文件
  ├── manufacturing.md
  ├── it.md
  └── ...（~15个文件）

按需升级（极少数多E2E项目的域，如流程与IT）：
23-eos-output-architecture/
  ├── 23-index.md
  ├── procurement.md             ← 普通域，单文件
  ├── it/                        ← 升级为目录
  │   ├── index.md
  │   ├── prod-business-engine.md
  │   ├── prod-public-component.md
  │   ├── prod-gov-arch.md
  │   └── prod-gov-data.md
  └── ...
```

**拆分粒度不预设。** 默认一个域一个文件。当域内 E2E 项目数量或节点数量超过阈值时，域可升级为目录，内部按项目拆分。文件即并行隔离边界。

## 八、三层结构详细方案

### 8.1 目录与文件结构

```
23-eos-output-architecture/           ← 资产根目录
│
├── 23-index.md                       ← 根索引（唯一入口，AI常驻context）
│
├── procurement.md                    ← 普通域，单文件
├── manufacturing.md
│
├── it/                               ← 多E2E项目的域，升级为目录
│   ├── index.md                      ← 域索引
│   ├── prod-business-engine.md       ← E2E项目文件
│   ├── prod-public-component.md
│   ├── prod-gov-arch.md
│   └── prod-gov-data.md
└── ...（其余域）
```

| 层级 | 实体 | 默认数量 | 粒度 | 职责 |
|------|------|---------|------|------|
| 层1 | 域 | ~15 | 业务域 | 默认一个域一个文件；复杂域升级为目录 |
| 层2 | E2E项目 | 域内1~10 | E2E项目 | 仅域升级为目录后才有独立文件 |
| 层3 | 构件→文档→活动节点 | 每文件 | 构件/文档 | 文件内部内容 |

### 8.2 升级与降级规则

| 规则 | 条件 | 操作 |
|------|------|------|
| 默认 | — | 一个域一个文件 |
| 升级 | 域内 E2E 项目 > 5 或 节点数 > 500 | 域文件升级为域目录，域内按项目拆分文件，新建域索引 |
| 降级 | 域内节点数 < 50 或 全部已归档 | 域目录降级为域文件，子文件合并 |
| 项目文件拆分 | 单项目文件 > 200 行 | 按构件组拆分为子文件 |
| 项目文件合并 | 单项目文件 < 10 行 且 无待处理 | 合并到同域内相邻文件 |
| 域归档 | 域内全部节点已废弃 且 无待处理 | 域文件/目录移入 `archived/`，根索引标记已归档 |

### 8.3 并行隔离

```
默认（域级文件）：
  不同域的写回 → 不同文件 → 隔离 ✅
  同一域的写回 → 串行（当前模型下不存在同一域内并行场景）

升级后（项目级文件）：
  同域内不同E2E项目的写回 → 不同文件 → 隔离 ✅
```

**规范只定义"文件就是并行隔离边界"，不强制粒度。粒度由人类根据域的实际复杂度决定。**

### 8.5 AI 读取路径

### 8.6 AI 写回协议

```
Step 1 · 定位目标文件
  从AI可以处理节点中获取所在文件路径

Step 2 · 加载目标文件
  Read 目标域文件/项目文件（200~500行，全量加载也不大）

Step 3 · 执行写回
  Edit 修改文件内容（节点行/确认状态/文档引用）

Step 4 · 更新文件自身
  - 更新 **文档版本**（递增次版本）
  - 更新 **修订日期**
  - 更新 **HEAD @上次 AI 运行**（提交后回填）
  - 更新"AI最近变更"表
  - 更新"AI可以处理节点"分节
  - 更新项目/构件索引行

Step 5 · 级联更新域索引（仅在域升级为目录时）
  Read {domain}/index.md
  → 更新对应行（节点数/待处理/最后更新）

Step 6 · 级联更新根索引
  Read 23-index.md
  → 更新对应域行（总节点数/待处理/最后更新）
  → 追加"AI最近变更"记录
  → 更新"AI可以处理节点"聚合分节

Step 7 · 提交
  git add 域文件 + 域索引（如有）+ 根索引
  git commit（单次提交）
  → 回填各文件的 HEAD 字段
```

| 约束 | 说明 |
|------|------|
| **事务性** | 一次写回 = 一次 git commit。文件 + 索引在同一次提交中更新 |
| **并行安全** | 不同文件的写回 → Git 层面无冲突 |
| **索引不阻塞并行** | 两个实例同时写不同文件 → 各自更新根索引 → 冲突概率低 |

## 十、开放问题

1. **人类阅读文件的触发方式**：默认是"人类指令"还是"AI写回后自动"？不同资产文件可能有不同的偏好。
2. **引用展开策略**：人类阅读文件中，`@doc-*` 是保留 ID 还是展开为文档名称？是否需要脚注机制？
3. **26号资产的填充**：26 号资产当前为空骨架。在表单化23号资产之前，是否需要先填充26号资产？
4. **HEAD 回填机制**：git commit 后才能获取 hash，但文件头需要记录 hash。当前方案是 commit 后回填 → amend 或第二次 commit。是否有更简洁的方案？
5. **多文件模式的事务边界**：一次写回更新多个文件（域文件/项目文件 + 域索引 + 根索引），但索引更新可能与其他实例的写回产生 Git 冲突。冲突处理策略——AI 自动 rebase，还是标记为人类处理？
