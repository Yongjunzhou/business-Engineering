# 报告库出件的连带：随章落实，不另开批（2026-10-13 用户定）

## 用户原话

> "对于十二章及后续章的变动，在重写12章及后章节时再随着改动。"

## 规则

1. **某号研究报告判有连带后，不立"批"、不提前预改**——把影响写成**随章取料单**：`claude-memory/pending-align-textbook-to-NN.md`，其中 **§五「随哪一章」表**逐章列出"这一章要改什么"。
2. **执行点＝该章入口文件（`pending-chN-revision-35.md`）§〇 开工单里的"★ NN 号随章影响"一行**。理由：**人只发一句 `开工第N章`**，agent 自读入口文件——要求写在这里，才在"执行它的那一次会话里"被读到；写在别处（报告、台账、记忆正文）都可能被跳过。
3. **连带件与该章同批**：框架 §三 章行／`00-目录.md`／`00-案例设定.md` 对应行／`19-附录.md` 对应条／`00-主线与各章支撑.md` §三 章卡／`00-三条线索.md` 收束句／训侧对应单元／该章派生件与 `成书/build` 重生成——**一并随该章落地**，不单独排批。
4. **教训（为何要立这条）**：本仓库此前的做法是"出报告 → 立批 → 批 1 台账／批 2 正文／批 3 依赖章…"。批序的问题是把**同一章要改的东西拆散在几批里**，且**批号与章号不同源**，容易漏、也容易在章被重写时作废。改为"随章"后，**一章一次改完，取料单只作料源清单**。

## 与既有机制的关系

- 与 **`pending-align-textbook-to-37.md`** 的关系：37 号那时立的是"批 0~批 6"；**38 号起改为随章**。37 号的批序**已完成的部分照旧**，未完成部分**按"随章"并入各章开工单**（ch14／ch15／ch16／ch17／ch18 的 37 号料源已在各自入口文件里，与 38 号随章影响并列）。
- 与 **手册七阶段** 的关系：随章影响**不另立阶段**——它是阶段一"读解基础 ⑤ 指定的旧料"与阶段二"原料清单"的**取料来源之一**；该章收工时随批更新连带件。

## 六 ★ 边界：两条（2026-10-15 同日两令，合起来才完整）

> 令一（原话）：「**你把与第一～十三章的给修改了，有关十四章及后续章节的修改，后续随重写它们时再一同考虑。**」
> 令二（原话，同日续）：「**十四章及后续章节需要重写，而之前的章节已经被重写过了，因此，要你发现的与前面十三章相关的问题都改了。**」

**两令合成一条边界**：**分两侧看，判据是"这一侧还会不会再重写"。**

- **第14~18章（待重写侧）**：凡属它们的东西——**新术语立户（如附录 A 加条）、为它们做的计数与台账连带、报告库取料源的改动**——**不得提前落进已定稿的件**；一律**随该章重写同批**（理由＝那些章还没重写，早落会落两遍）。
- **第1~13章（已定稿侧）**：**凡在这些章里查出的问题，必须现在就改净**——它们已各自走完七阶段并落库，不会再重写；"等以后"对这一侧不成立。

**六条硬口径**：

1. **判据是"还会不会再重写"，不是"这件共享不共享"**——共享件（`19-附录.md`／`00-三条线索.md`／`00-全书框架.md`／`00-案例设定.md`）**两侧都能落**，落什么按上面两侧判。
2. **不许把第14~18章的新东西提前立户**——哪怕它顺手、哪怕只加一行（本轮实例：为 ch14 立的 `T-214 系统分解结构（SBS）`）。
3. **不许以"顺手销旧账"为名越界**——旧账要销，但**销在它所属的那一侧**；"顺手"是越界最常见的入口（本轮实例：立 T-214 时顺手改了两处计数与另一份台账）。
4. **前十三章侧的问题不许挂账过夜**——查出来就改（与 [`feedback-根本改与仔细查.md`](feedback-根本改与仔细查.md) 同源，那里说的是"改法不打折"，这里补的是"改期不后拖"）；本轮按令二一次改净。
5. **越界改动要按 HEAD 干净回退**（判据＝`git diff` 对该文件无差异），不得"改一半留一半"；回退本身进当轮记忆。
6. **框架的"计划侧"记录不受两侧限制**——六条口径、批次与落点、**进度陈述的按实测回正**，记的是"将来怎么做"或"现在实际是什么"，应当即时落。

**适用范围**：`03-架构师是个怎样的物种/` 下的正文与共享元文件（框架／目录／三条线索／主线支撑／案例设定／方法论的底座／风格参考／19-附录）＋训侧派生件。
