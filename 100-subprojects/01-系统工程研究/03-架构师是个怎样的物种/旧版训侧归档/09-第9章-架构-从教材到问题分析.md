## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：什么算"架构"？为什么"画一张框图"不算做架构？系统、架构、架构描述三个词差在哪、为什么架构"不长什么样"？"业务架构、数据架构、应用架构、技术架构"是一个架构还是四个架构？架构描述怎么组织，才能让硬件、软件、客户、监管各取所需？为什么"约束即解放"？架构用约束换来了什么自由？架构师的核心能力是什么？

### 核心概念

1. **架构**（architecture）：系统在其环境中的基本概念或属性，体现在其元素、关系以及设计和演化的原则之中（ISO/IEC/IEEE 42010:2011）。它是系统**不可还原的涵义**——"去掉就不是这个系统"的那组决定。三判据辨认：不可再分 / 不可缺失 / 不可替代。
2. **架构描述**（architecture description）：对架构的表达——按"相关方 → 关注点 → 视点 → 视图"组织起来的制品集合（ISO 42010）。把涵义写下来给人看的东西，**一套制品，不是一张图**。

### 对立概念

| 核心概念 | 对立面 | 问什么 |
|---|---|---|
| 架构 | 详细设计 | 不可还原（去掉就不是它） vs 可还原（改了还是它）——三判据划界 |
| 架构 | 一张图 / 架构图 | 系统里不可还原的决定（真实存在、没有视觉形态） vs 架构描述（纸上的、会过时的）——图可以烂掉，决策可以活着 |
| 架构 | 技术选型 | 技术选型是"概念或属性"的一种体现，不是全部 |
| 架构 | 架构风格 / 模式 | 微服务/事件驱动/分层=决策的套路（结构体系选择）；具体系统的不可还原决定才是架构本身 |
| 系统 | 架构 | 指称（实际存在的那个东西） vs 涵义（不可还原的本质）——系统有生命周期，架构作为教训继续存在 |
| 架构描述 | 单张视图 | 视图是描述的组成部分；架构描述还包括原则、决策记录——不是一张总图 |
| 视图的"不完整" | 视图的"完整" | 刻意不完整=设计目的（剥离不关心的、保留本质）；完整画全=糊在一张图上对任何人没用 |
| 约束（积极自由） | 枷锁（消极自由） | 架构只约束"不改会灾难"的决定、回收积极自由 vs 限制所有事——管得最准好过管得最多 |
| 设计准则 | 演进准则 | 怎么造（约束创建过程） vs 怎么变（约束演化过程）——缺一个，系统要么一改就坏要么建出来就不对 |
| 元素 | 关系 | 元素是名词（看得见、好数）；关系是动词（被漏掉）——系统的秘密藏在关系里 |
| 架构 | 概要定义（第6章） | 概要定义是架构的一种描述；架构是概要定义背后那些"去掉就不是它"的决定 |
| 视点 | 视图 | 怎么看的规则（镜头设置） vs 按规则画出来的产物（照片）——一张照片服从一套规则 |

### 关联概念（近界 · 辨析）

- **架构 × 概要定义（第6章）**：第6章那棵树的枝干（概要定义）管结构、管承接；架构是那棵树里不可还原的部分——"概要定义是架构的一种描述；架构是概要定义背后那些'去掉就不是它'的决定"。
- **架构 × 评审（第7章）**：评审拿"目标"去照的，恰恰包括架构——架构评审，审的是架构描述是否对得起系统的不可还原涵义（这组决定是不是真的不可还原、原则能不能兜住未来变化、相关方关注点有没有都被看到）。
- **架构 × 架构决策（第11章，预告）**：一个决定之所以"去掉就不是这个系统"，是因为改它的代价大到几乎不可逆——不可逆意味着成本曲线在后期爆炸、做错了很难回头。于是架构的另一个名字浮现：**架构，是对不可逆决策的提前投资**。
- **架构 × 概念的定义（第1章）**：概念=从无限细节里提取可操作的本质；视图=架构的概念化切片——架构描述的"刻意不完整"就是第1章"概念"定义在架构层的重演。
- **架构 × 弗雷格模型（第1章）**：符号/涵义/指称 ↔ 架构描述/架构/系统——涵义不等于指称；架构描述≠架构。
- **架构 × 涌现属性（第2章）**：涌现属性来自元素之间的关系，不来自单个元素——架构层推论：可靠性瓶颈在交互模式。
- **架构描述 × ISO 42010 链条**：相关方 → 关注点 → 视点 → 视图 → 架构描述 → 架构 → 系统——"谁想看 → 关心什么 → 按什么规则看 → 看到什么 → 拼成完整描述 → 表达哪个涵义 → 属于哪个系统"。
- **相关方 × 关注点**：相关方=对系统有利益关系的任何个人/团队/组织（不只是用户）；关注点=对系统的任何兴趣（功能/非功能/约束）——关注点天然冲突，不可消除只能权衡。
- **视点 × 视图（相机比喻）**：视点=拍摄规则（角度/镜头/滤镜），视图=照片——一张照片服从一套拍摄规则，一套规则可以拍出很多张照片。
- **4+1 视图模型 × 场景**：场景不是第五个视图，是胶水——拿一条真实使用场景横着穿过去，检验四个视图是否互相矛盾。
- **架构框架 × 视点**：4+1 / C4 / TOGAF / Zachman = 预定义的视点集合；框架是"适配"的选择不是"对错"的选择，价值=大家用同一套语言。
- **康威定律 × 逆康威定律**：系统结构=组织沟通结构的副本；想让系统有某种结构，就先让团队有对应的组织结构——构件边界就是团队边界。
- **架构 × 心智模型**：架构压缩信息（保真压缩），提供共享心智模型——新成员入门材料、跨团队责任边界、决策共同语言。
- **架构的回报四维度 × 认知/决策/变更/组织**：压缩信息（心智模型）/ 划定解空间（削减决策量）/ 免疫系统（预判·吸收·学习）/ 团队边界（康威定律）。

### 核心原理

1. **图≠架构原理**：架构和图不在同一个世界——图是纸上的、可见的、会过时的；架构是系统里那组不可还原的决定，真实存在但不会因为你没更新一张图就消失。
2. **图烂决策活原理**：图可以烂掉，决策可以活着——老周团队其实一直在守那组决定，只是从没把它们写下来过；"变的只是细节（上传间隔），没变的是那组更底层的决定"。
3. **基本=地基原理**：fundamental 来自拉丁语 fundamentum（地基）——地基在建筑最底层承托一切，地基一动整栋楼都要动，地基决定楼能盖多高、多稳。
4. **环境决定基本原理**：架构不是孤立地描述一个盒子，而是描述这个盒子"放在什么环境里"——同一个温控设备，放在实验室台架和放在冷链运输里，"什么算基本"就变了（环境定义了哪些属性才算基本）。
5. **三判据原理**：不可再分（去掉它就不再是它）/ 不可缺失（缺少它系统就垮）/ 不可替代（换掉它性质就变）——三问都答"是"，才是架构；"架构决策和普通实现决策的分界线，就在这里：改它要花多大代价、影响多大范围、是不是几乎不可逆"。
6. **关系承载秘密原理**：系统的涌现属性来自关系，不来自单个元素；可靠性瓶颈通常不在单个组件，而在组件之间的交互模式——老周那张图只画了一根箭头，等于只画了元素，没画关系；M3 架构里最硬的秘密全在关系里（每一跳断了谁负责补、谁负责告警）。
7. **免疫系统原理**：设计准则（怎么造）+ 演进准则（怎么变）= 免疫系统——既定义"什么是自我"，又主动防御变化；缺一个，系统要么一改就坏，要么建出来就不对。
8. **分布式单体原理**：没有演进准则的微服务会退化成分布式单体——服务越来越多、耦合越来越紧，最终变成分布在不同进程里的单体应用；名字还叫微服务，本质已经塌了。
9. **架构是学习系统原理**：每次架构层面的变更失误，都应沉淀为一条架构原则的更新——"为什么这个接口契约的设计没有预见到这种使用场景"下次变成原则的一部分，免疫系统一直在长。
10. **系统≠架构原理**：系统有生命周期（会报废、会换代、会被拆掉）；架构（那组不可还原的决定）在系统消失之后，还可能作为经验、教训、下一代产品的设计前提继续存在——架构活的时间往往比系统本身长。
11. **一架构多描述原理**：同一个架构可以有无数种描述（框图/数据流图/时序图/合规视图都在描述同一个 M3 架构）；反过来也成立——同一张图可能根本没描述对架构（只画元素没画关系没画原则）。
12. **架构不长什么样原理**："长什么样"是一个视觉范畴的问题，架构是一个逻辑范畴的存在——一组基本决策及其衍生的约束关系，真实存在但不可直接视见；只有投影，没有"原图"。
13. **一个系统一个架构原理**：一个系统只有一个架构；所有"XX架构"都是对同一个架构从不同角度、不同抽象层次上的描述——它们是视图，不是多个独立的架构（"就像一副骨骼，可以拍 X 光、CT 切片，却是同一副骨骼"）。
14. **两套维度原理**："XX架构"来自两套独立的分类维度——关注域（按"看什么"切：业务/数据/应用/技术）+ 抽象层次（按"多详细"切：概念/逻辑/物理）；任何一个架构视图都同时落在某个"关注域 × 抽象层次"的交叉点上。
15. **架构风格=套路原理**：微服务/事件驱动/分层=架构决策的套路（结构体系的选择），相当于建筑里的框架结构/剪力墙结构/钢结构——这是结构体系选择，不是建筑本身；选微服务只是选了"怎么组织元素和关系"的风格。
16. **描述没对齐原理**：三个人三个答案，不是有三个架构，是三个人从三个不同的视角看同一个 M3 架构，却从没把三个视角对齐过——视图之间对不上，不是架构有多个，是描述没有统一。
17. **表达原理**：涵义锁在脑子里没有用——M3 的架构再清晰，如果只存在于老周一个人的脑子里，它就不产生任何协作价值；架构必须被表达出来，才能被共享、被讨论、被检查、被传承；架构描述就是这个"表达"。
18. **关注点天然冲突原理**：相关方的关注点是宽泛的、多样的、且相互冲突的（ISO 42010 原文 "broad, varied, and conflicting"）——架构不是找一个让所有关注点都满意的解，而是"在互相冲突的关注点之间，做出一个有意识的权衡"。
19. **权衡前提原理**：关注点冲突不可消除，只能权衡；权衡有一个前提——得先能看到每个方面；看不见安全，就不会为安全取舍；看不见运维，就不会为可运维取舍。
20. **相机比喻原理**：视点=拍摄规则（角度、镜头、滤镜），视图=照片（产物）；一张照片服从一套拍摄规则，一套规则可以拍出很多张照片。
21. **刻意不完整原理**：每个视图都是刻意的"不完整"——逻辑视图不展示部署，物理视图不展示类关系；"完整地画出系统的每一面"等于把所有关注点糊在一张图上，对任何人都没用；视图的价值恰恰在剥离掉你不关心的部分、只保留本质——视图就是架构的概念化切片。
22. **视图完备性原理**：视图的完备性由相关方及其关注点决定，不由方法论决定——把"我们需要几个视图"这个方法论之争，变成"我们的相关方是谁、他们关心什么"这个可以具体讨论的项目分析。
23. **场景是胶水原理**：4+1 的场景不是第五个视图，而是胶水——拿一条真实的使用场景横着穿过去，检验四个视图是否互相矛盾；走不通，说明四个视图之间藏着矛盾。
24. **框架适配原理**：框架是"适配"的选择，不是"对错"的选择——软件常用 4+1/C4，企业架构常用 TOGAF/Zachman；框架的价值在于"大家用同一套语言"，让不同项目可积累、可比较、可复用。
25. **压缩信息原理**：架构=保真压缩（不是丢信息）——不需要一次记住全部，但需要的时候能定位到；7±2 认知容量装不下 500 个服务、上千张表、上万个接口；处理任何具体问题只需关心系统的一小部分。
26. **共享心智模型原理**：新成员加入时架构是最有效的入门材料、跨团队协作时架构定义各团队的责任边界、决策讨论时架构提供共同的语言——老周团队"三个人三个答案"本质就是没有共享心智模型。
27. **划定解空间原理**：架构的作用不是给出所有答案，而是划定哪些答案是可接受的——没有架构时每次加需求都要重新争论，选择空间无穷大、选择瘫痪；架构削减的不是工作量，是决策量。
28. **康威定律原理**：任何组织设计出来的系统，其结构都是该组织沟通结构的副本；逆康威定律=想让系统有某种结构，就先让团队有对应的组织结构——构件边界就是团队边界；"数据链路"被切成两层，中间就出现了一个没人认领的缝（固件和云端互相推卸重连责任）。
29. **约束即解放原理**：消极自由（freedom from，不受约束——我想怎么做都行）vs 积极自由（freedom to，有能力高效做成——我知道怎么做是对的）——没有架构时你拥有消极自由但丧失了积极自由（每个决策都要重推上下文：7 个数据库×3 种访问模式=21 种可能）；架构约束回收的是积极自由——管得最准好过管得最多。
30. **架构师核心能力原理**：架构师的核心能力不是"做出正确的决策"，而是"识别哪些决策如果不正确，后果会很严重"——对不重要的事情不决策，本身就是一种好的架构决策。
31. **架构师的理论原理**："什么是重要的"本身就需要判断，判断依据是你对这个系统的理论（靠什么成功 / 最大压力在哪 / 什么做错最致命）——同一个 M3，两套理论，两套架构图、两组优先投入；没有理论支撑的架构，像没有物理学原理的工程。

### 本章判据（七把尺子）

1. **架构三问判据**：这个决定"去掉还是这个系统吗 / 缺少系统垮吗 / 换掉性质变吗"——三问都答"是"，才是架构；答"否"的，是详细设计，不是架构。
2. **三个词三层判据**：系统（指称，实际存在的那个东西）≠ 架构（涵义，不可还原的本质）≠ 架构描述（对涵义的表达）。图过时了 ≠ 架构过时了——决策可以一直有效。
3. **一个系统一个架构判据**："业务/数据/应用/技术"是关注域视角，"概念/逻辑/物理"是描述层次，"微服务/事件驱动"是架构风格——都不是多个架构。
4. **架构描述组织链判据**：相关方 → 关注点 → 视点（怎么看的规则）→ 视图（产出的切片）→ 组合成完整架构描述。每个视图要能说出"它在回答谁的什么问题"。
5. **关注点冲突判据**：相关方的关注点是宽泛、多样、且相互冲突的——冲突不可消除，只能权衡；权衡的前提是能看到每个方面。
6. **约束即解放判据**：架构只约束"不改会灾难"的决定，把团队从重复决策里解放出来，回收积极自由。"管得最准"好过"管得最多"。
7. **免疫系统判据**：设计准则管"怎么造"，演进准则管"怎么变"；缺一个，系统要么一改就坏，要么建出来就不对。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"架构"（系统在其环境中的基本概念或属性，体现在元素、关系以及设计演进原则中——ISO 42010）并说出"不可还原的涵义"。
2. 能说出架构三判据（不可再分 / 不可缺失 / 不可替代）并用通俗问法判断（去掉还是它吗 / 缺了垮吗 / 换了变质吗）。
3. 能定义"架构描述"（对架构的表达，按相关方→关注点→视点→视图组织的制品集合，不是一张图）。
4. 能辨析 系统 / 架构 / 架构描述（指称≠涵义≠符号；系统会消失、架构作为经验教训继续存在）。
5. 能说出 ISO 42010 定义逐词拆解的五个分量（基本 / 概念或属性 / 在它的环境中 / 元素·关系·原则 / 设计·演进准则）。
6. 能说出架构的三个载体——元素（组成部分）、关系（连接）、原则（约束设计与演化的规则）。
7. 能定义"设计准则"与"演进准则"（怎么造 vs 怎么变）。
8. 能定义"相关方 / 关注点"并说出关注点天然冲突。
9. 能定义"视点 / 视图"（怎么看的规则 vs 按规则画出来的产物；相机比喻）。
10. 能定义"架构框架"（预定义的视点集合：4+1 / C4 / TOGAF / Zachman）。
11. 能辨析 业务/数据/应用/技术架构（关注域视角）vs 概念/逻辑/物理架构（抽象层次）vs 微服务/事件驱动架构（架构风格/决策套路）。
12. 能说出"一个系统只有一个架构"及理由（XX架构=视图不是多个架构；骨骼 X 光/CT 切片比喻）。
13. 能定义"消极自由 / 积极自由"（freedom from / freedom to）。
14. 能说出架构回报四维度（认知 / 决策 / 变更 / 组织）。
15. 能定义"康威定律"（系统结构=组织沟通结构的副本；构件边界就是团队边界）。

### 原理层（应能解释为什么）

1. 能解释为什么"画一张框图"不算做架构（图是架构描述；架构是系统里那组不可还原的决定）。
2. 能解释为什么图会过时但决策可以活着（图是投影、决定是实体；老周团队一直在守没写下来的老规矩）。
3. 能解释为什么"基本"要用三判据检验（不可再分/不可缺失/不可替代；"去掉就不是它"）。
4. 能解释为什么环境决定什么算"基本"（同一设备放实验室台架 vs 冷链运输，架构不同）。
5. 能解释为什么系统的秘密藏在关系里（涌现属性来自关系；可靠性瓶颈在交互模式）。
6. 能解释为什么设计准则+演进准则=免疫系统（缺一个，系统要么一改就坏要么建出来就不对；分布式单体）。
7. 能解释为什么系统≠架构（系统有生命周期；架构在系统消失后还能作为经验教训继续存在）。
8. 能解释为什么同一个架构可以有无数种描述、同一张图可能根本没描述对架构。
9. 能解释为什么架构"不长什么样"（视觉范畴 vs 逻辑范畴；只有投影没有原图）。
10. 能解释为什么"一个系统只有一个架构"（XX架构=视图不是多个架构；一副骨骼的多种影像）。
11. 能解释为什么"三个人三个答案"是描述没对齐，不是架构有多个。
12. 能解释为什么架构必须被表达（涵义锁在脑子里没有用；被共享/讨论/检查/传承）。
13. 能解释为什么关注点天然冲突、不可消除只能权衡（监管加密拖慢链路 vs 老板快上线积技术债）。
14. 能解释为什么权衡的前提是看到每个方面（看不见安全就不会为安全取舍）。
15. 能解释为什么每个视图是刻意的"不完整"（完整糊一张图对任何人没用；剥离不关心的保留本质）。
16. 能解释为什么视图完备性由相关方决定不由方法论决定（把"几个视图"变成"相关方是谁、关心什么"）。
17. 能解释为什么场景是 4+1 的胶水（横穿四个视图验证一致性；走不通说明藏着矛盾）。
18. 能解释为什么框架是适配的选择不是对错的选择（同一套语言，可积累可比较可复用）。
19. 能解释为什么架构是保真压缩（7±2；500 服务×200 接口 vs 12 域×每域 5-8 构件；需要时能定位到）。
20. 能解释为什么架构削减的是决策量不是工作量（把无穷的选择收敛成可管理的框）。
21. 能解释为什么构件边界就是团队边界（康威定律+逆康威定律；数据链路切成两层出现没人认领的缝）。
22. 能解释为什么约束即解放（消极自由=没人拦但每个决策重推上下文；积极自由=常规问题有标准答案）。
23. 能解释为什么架构师的核心能力是识别"哪些决策不正确后果会很严重"（对不重要的事情不决策也是好的架构决策）。
24. 能解释为什么"什么是重要的"需要判断（架构师的理论：靠什么成功/最大压力/什么做错最致命；两个架构师两套理论两套图）。

### 判据层（应会用）

1. **架构三问判据**：拿一个决定/概念来，先问三问——去掉还是这个系统吗？缺少系统垮吗？换掉性质变吗？三问都"是"→架构；答"否"→详细设计。
2. **三个词三层判据**：讨论架构时，先分清说的是系统、架构、还是架构描述；"图过时了"≠"架构过时了"——决策可以一直有效。
3. **一个系统一个架构判据**：看到"XX架构"，先归类它是关注域视角 / 描述层次 / 架构风格中的哪一种，再检查各视图是否对得上。
4. **架构描述组织链判据**：组织架构描述时走链——相关方→关注点→视点→视图；每个视图能说出"在回答谁的什么问题"；有没有重要相关方的核心关注点被遗漏。
5. **关注点冲突判据**：面对多相关方，先摆出每个相关方的核心关注点，承认冲突，再做有意识的权衡——"找一个都满意的解"是伪目标。
6. **约束即解放判据**：评估架构约束时问"它约束的是不是'不改会灾难'的决定"；只约束要命的，剩下交给执行者自由发挥；管得最准好过管得最多。
7. **免疫系统判据**：检验架构完整性时问"设计准则和演进准则齐了吗"；只有设计准则=一改就坏，只有演进准则=建出来就不对。

| 21 N5 | "架构=元素清单/模块清单（数出系统有哪些部件）。" | 系统的行为是涌现的（emergent）——来自元素之间的关系，不在单个部件；可靠性瓶颈通常在组件交互模式（教科书级共识：架构关心关系不关心孤立部件） | 架构三问（关系载体） | Sommerville《Software Engineering》架构章（涌现行为/关系）；arXiv 2403.16740（systems-of-systems 涌现行为） |
| 22 N6 | "架构评审开了、图走了个过场，就算审过架构。" | 架构评审"走过场"是业界公认反模式——没有对准决策与场景、只对着图走流程，评审是橡皮图章；有意义的评审用真实场景穿视图、审决策与不可还原涵义 | 架构描述组织链（场景胶水）+ 关注点冲突 | OrbusSoftware《5 Signs your Enterprise Architecture Reviews are a Farce》；RyanFrantz《Architecture Reviews》；vibgrate《Rubber-Stamp Reviews: Ceremony Without Value》 |
| 23 N7 | "约束少=自由大，架构约束是给团队上枷锁。" | "自由是有边界的"——有意的约束产出更优代码（intentional constraints）；没有约束的团队"给了全部自由反而不动"，有边界的平台让建造者更会造（platform constraints） | 约束即解放（消极 vs 积极自由） | DEV《How Intentional Constraints Lead to Superior Code》；Braingl《The Power of Platform Constraints》；Software Architecture Gathering 2026《Now We've Given Them Every Freedom and They Still Don't Do What We Want》 |

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 架构三问 + "架构是决定不是图"（识别） | 1/2/3/4/8/14/15 + N1 | 脱口而出："架构=系统在其环境中的基本概念或属性，体现在元素/关系/设计演进原则中；三问=去掉还是它吗/缺了垮吗/换了变质吗，三问都'是'才是架构；架构和图不在同一个世界——图可以烂掉，决策可以活着" |
| ★2 | 三个词三层（系统≠架构≠架构描述） | 7/14/18/19 + N1/N4 | "系统=指称（实物）、架构=涵义（不可还原的本质）、架构描述=符号（写下来给人看）；图过时了≠架构过时了；只有投影没有原图；系统会消失架构作为教训继续存在" |
| ★3 | 一个系统一个架构（关注域/层次/风格三分） | 4/5/6 + N2/N3 | "业务/数据/应用/技术=关注域视角、概念/逻辑/物理=描述层次、微服务/事件驱动=架构风格（决策套路）——都不是多个架构；一个系统只有一个架构，各视图必须对得上（一副骨骼的 X 光/CT 切片）" |
| ★4 | 关系承载 + 场景是胶水（架构描述怎么组织） | 8/10/12/13 + N5/N6 | "系统秘密藏在关系里（涌现/交互模式）；相关方→关注点→视点→视图组织描述；每个视图是刻意的'不完整'；拿一条真实场景横穿视图验证对得上——走不通就是四个系统" |
| ★5 | 约束即解放 + 架构师的核心能力 | 11/17 + N7 | "消极自由 vs 积极自由：架构约束回收积极自由——管得最准好过管得最多；架构师的核心能力是识别'哪些决策不正确后果会很严重'，对不重要的事情不决策本身是好的架构决策" |
| ★6 | 免疫系统（设计准则+演进准则） | 15/16 + N4 | "设计准则管怎么造、演进准则管怎么变；缺一个，系统要么一改就坏要么建出来就不对；没有演进准则的微服务退化成分布式单体" |
| ★7 | 关注点天然冲突 + 权衡 | 12/16 + N6 | "相关方关注点宽泛多样且相互冲突——不可消除只能权衡；权衡前提=先看到每个方面；架构不是找让所有关注点满意的解，是在冲突之间做有意识的权衡" |

### 纠错红线十条

1. **先表态后翻案**：先问"架构不就是要画张图吗""画了图不就是做了架构吗""业务架构和架构不是一个东西吗""约束少了不是更灵活吗"，再翻——不让结论先入。
2. **反转精确不造新误解**：不说"架构图没用/不该画图"（画图是落盘，只是不等于架构）；不说"视图越多越好"（完备性由相关方决定，不由方法论决定）；不说"约束越多越好"（只约束要命的地方，管得最准好过管得最多）。
3. **判据配机制**：每条反转都有"为什么"（图是投影决定是实体 / 涌现来自关系 / 关注点冲突不可消除只能权衡 / 场景验证一致性 / 消极自由 vs 积极自由 / 康威定律）和"怎么当场验证"（七把尺子）。
4. **归责到可对照动作**：不归咎"老周/李工/阿凯/Ada"，落到"三问跑了吗 / 相关方表摆出来了吗 / 每个视图能说出在回答谁的什么问题吗 / 一条真实场景穿过去了吗 / 设计准则和演进准则齐了吗 / 约束的是不是要命的决定"这类可查动作。
5. **教机制不教断言**：教"为什么图会过时决策活着、为什么架构不长什么样、为什么关系比元素要紧、为什么场景是胶水、为什么约束即解放"，不教"老周说得对"。
6. **先立尺子再翻案**：先给七把尺子（架构三问 / 三个词三层 / 一个系统一个架构 / 架构描述组织链 / 关注点冲突 / 约束即解放 / 免疫系统），再翻案例。
7. **拉开强度层次**：★★★ 常识（架构=图 / 画图=做架构 / 图过时=架构过时 / 四个架构 / 约束=枷锁 / 视图越全越好）重点翻，★★ 次之。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（拿一个系统跑三问 / 摆相关方-关注点表 / 拿一条真实场景穿现有架构图 / 核对设计准则和演进准则齐不齐 / 列出三条约束各自解放了什么）。
9. **单一权威不另立标准**：判据引用书七把尺子 + ISO/IEC/IEEE 42010 + Kruchten 4+1，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给部门最近讨论/维护的一个系统做"架构体检"

> 目标：用七把尺子检查一个系统/一次架构讨论是否把架构与架构描述分开、是否组织起让相关方各取所需的描述，产出三件可执行改进。
> 场景：回部门落地。时长：1~2 小时内完成一次体检，两周后复查一至两项。

1. **识别（尺1 · 架构三问判据）**：挑一个正在做/讨论的系统，跑三问——去掉它还是这个系统吗？缺了它系统垮吗？换掉它性质变吗？三问都"是"的，就是系统的不可还原涵义（架构）。产出：不可还原涵义一句话。
2. **分三个词（尺2 · 三个词三层判据）**：把最近一次架构讨论里的"架构"用词逐条分类——说的是系统（指称）、架构（涵义）还是架构描述（符号）？混了几层？产出：用词混层清单。
3. **归类 XX 架构（尺3 · 一个系统一个架构判据）**：找齐团队所有叫"XX架构"的图/文档，各自归入——关注域视角（业务/数据/应用/技术）/ 描述层次（概念/逻辑/物理）/ 架构风格（微服务/事件驱动）？产出：分类表 + 是否被当成多个架构的判定。
4. **走组织链（尺4 · 架构描述组织链判据）**：手头的架构描述走完"相关方→关注点→视点→视图"了吗？每个视图能说出"它在回答谁的什么问题"吗？产出：组织链缺口清单。
5. **摆冲突（尺5 · 关注点冲突判据）**：摆出系统相关方清单和每个相关方的核心关注点（≥5 个）——有没有哪个关注点你从来没考虑过？冲突被显式权衡过吗？产出：相关方-关注点表 + 冲突清单。
6. **量约束（尺6 · 约束即解放判据）**：写出系统三条架构约束，每条约束分别把团队从什么重复决策里解放出来？约束的是不是"不改会灾难"的决定？产出：约束-解放对照表。
7. **查免疫系统（尺7 · 免疫系统判据）**：设计准则（怎么造）和演进准则（怎么变）各有哪些？缺一类吗？有"一改就坏"或"建出来就不对"的征兆吗？产出：原则清单 + 缺口。

**卡住怎么判断**：任一尺子打不出勾，就是该尺子说的缺口——找到第一个"否"就能开工。产出三件最该改进事项（每条 = 一个可检查动作）。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 系统的"不可还原涵义"一句话说得出来吗？ | □ | 说不出来 → 三问没跑过，团队守着一个说不清本质的系统 |
| 最近一次架构讨论里"架构"指的都是同一个东西吗？ | □ | 混层 → 系统/架构/架构描述没分开，各说各话 |
| 所有"XX架构"图/文档分类过（关注域/层次/风格）吗？ | □ | 没分类 → "四个架构"幻觉，没人检查视图对得上 |
| 架构描述走完相关方→关注点→视点→视图了吗？ | □ | 只有一张总图 → 每个相关方看不到自己该看的那一面 |
| 相关方清单和核心关注点摆出来过吗（≥5 个）？ | □ | 没摆 → 看不见安全就不会为安全取舍，权衡无从谈起 |
| 有拿一条真实场景横穿各视图验证对得上吗？ | □ | 没有 → 视图之间藏着矛盾，一场事故才暴露 |
| 架构约束写下来了吗？约束的是要命的决定吗？ | □ | 只约束琐碎 → 该解放的没解放，该钉死的没钉死 |

| 设计准则和演进准则齐吗？ | □ | 只有设计 → 一改就坏（分布式单体前兆）；只有演进 → 建出来就不对 |
| 把"老规矩"写下来过吗？标出哪些是架构哪些是习惯？ | □ | 没写 → 图烂了规矩还在，但没人知道哪条是架构 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身 · 破题）**
"架构评审会，冰链老周把四层方块图投到屏幕上：硬件层、固件层、云端层、App 层，一根'温度数据'箭头从传感器一路画到 App。十分钟讲完，散会。三个月后三个问题先后找上门——改上传间隔没人能答影响什么、断电补传两个团队互相推、'M3 到底是什么系统'三个人三个答案。老周翻出那张图想维护一版，盯着看了很久，忽然意识到：这张图从来没描述过真正的 M3。——什么算'架构'？为什么'画一张框图'不算做架构？"
追问：① 三判据：不可再分（去掉它还是这个系统吗）/不可缺失（缺了它系统垮吗）/不可替代（换掉它性质变吗）——老周那张图为什么过不了？M3 的什么能过（"断链即报废的疫苗能从出库一路撑到接入冷库、全程可追溯"）？上传间隔改成 5 分钟为什么不是架构（改了 M3 还是 M3），数据所有权归云端还是追溯域为什么是？② 图≠架构：图是纸上的、可见的、会过时的；架构是系统里那组不可还原的决定，真实存在但不会因为你没更新一张图就消失——为什么"图可以烂掉，决策可以活着"？"变的是细节（上传间隔），没变的是那组更底层的决定"，凭什么这么分？③ 反身：你们团队最近一次架构讨论，说的是"架构"还是"架构图"？哪个是实体，哪个是投影？

**Q2（见树见林② · 概念关系 · 真悖论收束）**
"请给出 系统 / 架构 / 架构描述 的关系（一句话）。再把'业务架构、数据架构、应用架构、技术架构'放进去——它们是多个架构吗？微服务架构呢？"
追问：① 弗雷格三层：符号（架构描述）→ 涵义（架构）→ 指称（系统）——为什么架构"不长什么样"？宪法/DNA/组织架构——你能画出来的为什么永远是描述不是本质？② 一个系统一个架构：一副骨骼可以拍正面 X 光、侧面 X 光、横切 CT 切片——为什么是同一副骨骼的影像，不是多副骨骼？业务/数据/应用/技术=关注域视角，概念/逻辑/物理=描述层次，微服务/事件驱动=架构风格（决策套路）——三类各是什么？③ 架构描述组织链：相关方→关注点→视点→视图→组合成完整架构描述——为什么"给司机看固件的内存布局没有意义，给疾控中心看 App 的界面层级也没有意义"（不同的人关心不同的东西）？④ 真悖论收束："架构=一张框图（我们画了架构图，架构工作完成了）" vs "架构=系统里不可还原的决定（图只是架构描述，画图不算做架构）"——两个都像，靠什么判据分清？⑤ 三个人三个答案：硬件/软件/客户看到的是同一个 M3 的三个视图，为什么对不上不是"三个架构"而是"描述没有统一"？

**Q3（三判据 · 元素与关系 · 真悖论收束）**
"老周的架构图画了四层方块和一根'温度数据'箭头。改上传间隔没人能答影响什么、断电补传两个团队互相推——他们在图里找依据，图里没有答案。老周说：'我把四层都画出来了，架构不就这样？'——画了元素，为什么还不算架构？系统的秘密藏在哪？"
追问：① 元素 vs 关系：元素是名词（看得见、好数），关系是动词（被漏掉）；系统的涌现属性来自关系不来自单个元素（第2章讲过：每个发动机都正常、每块机翼都达标，飞机未必能飞）——为什么可靠性瓶颈通常在组件之间的交互模式（传感器→固件→云端某环重传超时），不在单个组件？② 关系承载"断"：M3 架构要回答"数据从传感器出发经过固件、云端、追溯平台最终到达谁的眼睛？每一跳之间如果断了，谁负责补、谁负责告警"——这些"跳"和"断"就是关系；老周那张图只画了一根箭头，等于只画了元素没画关系——为什么 M3 架构里最硬的秘密全在关系里？③ 真悖论收束："把元素画全=架构完整（四层都画了，模块清单齐了）" vs "关系才是架构的秘密（涌现来自关系，画一根箭头等于没画关系）"——两个都对，靠什么判据分清？④ 反身：你们系统的架构图画的是元素还是关系？断了一条"跳"，谁负责补、谁负责告警，图里答得出来吗？

**Q4（三个词三层 · 系统≠架构 · 真悖论收束）**
"老周翻出三个月没更新的架构图，想维护一版新的。图是旧的，系统是新的——图旧的那三个月，M3 温控箱一直在正常工作：温度一直在采集、一直在上传、冷链一直在被追溯。如果图就是架构，架构早该和系统脱节了。可 M3 的'根本逻辑'并没变。'变的是细节（上传间隔），没变的是那组更底层的决定。'——架构到底长什么样？为什么系统会消失，架构还在？"
追问：① 系统≠架构：系统有生命周期——会报废、会换代、会被拆掉；架构（那组不可还原的决定）在系统消失之后，还可能作为经验、教训、下一代产品的设计前提继续存在——为什么架构活的时间往往比系统本身长？② 架构不长什么样："长什么样"是视觉范畴的问题，架构是逻辑范畴的存在——一组基本决策及其约束关系，真实存在但不可直接视见；如果有人问"给我看一下你们系统的架构"，他能得到的永远是一组视图（边界图、构件图、数据模型），而不是一张叫"架构"的图——为什么不存在这样一张图？③ 真悖论收束："架构是系统的（M3 的架构属于 M3——系统的不可还原涵义，系统没了它也没了）" vs "架构比系统活得长（系统会报废，那组决定作为经验教训继续存在）"——两个都对，靠什么判据分清？④ 免疫系统：架构定义最后那半句——"设计和演化的原则"：设计准则管"怎么造"、演进准则管"怎么变"，两者合起来才是免疫系统——为什么缺一个，系统要么一改就坏（只有设计准则），要么建出来就不对（只有演进准则）？没有演进准则的微服务为什么退化成"分布式单体"？⑤ 反身：你们上一代系统/产品退役时，它的"架构"还在吗？那组决定被写下来传承了吗，还是跟着老员工退休了？

**Q5（约束即解放 · 架构师核心能力 · 真悖论收束）**
"自由主义者抗议：'我们想要灵活，想要敏捷，架构把我们绑死了！'老周以前也这么想——定了数据所有权、定了断链刚性、定了兼容规则，这不是给团队上枷锁吗？——架构到底是约束还是解放？"
追问：① 两种自由：消极自由（freedom from，不受约束——我想怎么做都行，没人拦着你）vs 积极自由（freedom to，有能力高效做成——我知道怎么做是对的）——为什么没有架构时你有消极自由却丧失了积极自由（每个决策都要重推上下文：7 个数据库×3 种访问模式=21 种可能）？② 管得最准好过管得最多：好的架构不是"管得最多"，是"管得最准"——只约束那些不改就会造成灾难的东西，剩下的交给执行者自由发挥——为什么"对不重要的事情不决策，本身就是一种好的架构决策"？改采集间隔不用开会讨论、加新传感器不用重新吵架构——这是哪来的自由？③ 真悖论收束："约束越少越灵活（架构是给团队上枷锁，敏捷被绑死）" vs "约束即解放（架构只约束要命的决定，把团队从无穷的重复决策里解放出来）"——两个都对，靠什么判据分清？④ 反身：列出你们系统三条架构约束，每条分别把团队从什么重复决策里解放了出来？如果有一条答不出"解放了什么"，它可能只是枷锁不是架构。

### 第二组 · 落地与实践（5 题）

**Q6（三判据 · 案例进展① · 识别不可还原）**
"冰链老周把三个人拉到会议室：'我们到底守着一个什么样的系统？'小林：'M3 就是个温度记录仪加个箱子，能调温、能记录、能上传。你说的系统不就是这些功能的集合吗？'老周摇头：'如果是功能的集合，加个摄像头记录装卸过程也只是加个功能，M3 还是 M3——可加上摄像头，M3 就变味了。'他在纸上写：断链即报废的疫苗，能从出库一路撑到接入冷库，全程可追溯。小赵盯着那行字：'你这不是 M3 的功能，这是 M3 为什么存在的理由。'——为什么问'少了什么 M3 就不是 M3'，能筛出真正的架构？"
追问：① 三问 vs 数模块："一问模块，你会数出十个；一问'少了什么不是它'，你会筛出那三四个真正要命的。"——为什么"要命的才是架构"？功能集合和不可还原涵义差在哪（加摄像头=加功能但变味）？② 判据落地：用三问检验——温度上传间隔（三问过得了吗？）、数据所有权归追溯域（三问全中？）、加摄像头记录装卸过程（三问过得了吗？）——哪个是架构，哪个是功能？③ 反身：用三问检验你们系统最近一次"加个功能"——它改的是功能还是不可还原的涵义？你们团队问过"少了什么它不是它"吗？

**Q7（案例进展② · 图烂决策活 · 真悖论收束）**
"老周无意间听到云端阿凯和新人小陈的一段对话：'补传的数据，还是归追溯库吧？按老规矩，温度数据归属追溯域，谁都不许随便改字段。''那必须的。数据所有权是定死的——传感器只管采，云端只管传，追溯平台管存管管看，这个边界动不得。'老周愣住了：他翻出那张三个月没更新的架构图——图上根本没有'数据所有权'这回事，图里只有四层方块和一根箭头。可这两个人刚刚遵守了一条图里从来没有画出来过的决定。——架构到底是图，还是老规矩？"
追问：① 图烂决策活：老规矩（数据所有权归追溯域、断链必须实时告警、固件升级不能毁已出厂的箱子）才是 M3 的架构——图早就烂了，规矩一直活着；"图描述的是长得像的东西，规矩描述的是'少了它 M3 就不是 M3'的东西"——为什么？② 真悖论收束："架构=架构图（画图才是做架构，图过时了架构就过时了）" vs "架构=团队真正在守的决定（老规矩才是架构，从没人写下来过）"——两个都对，靠什么判据分清？③ 没写下来比画不好更要命：小林低头写了个字："所以问题不是'图过时了'，是'这些要命的规矩从没被写下来过'。图过时了可以再画，规矩要是丢了，M3 就真的散了。"——为什么"没写下来"比"画得不好"更要命？④ 反身：你们团队有没有"从没写下来、但大家都在守"的规矩？把它们写下来，标出哪些是不可还原的（架构），哪些只是习惯（非架构）。

**Q8（案例进展③ · 场景是胶水 · 真悖论收束）**
"恒信架构师李工把合同审批系统画成四张图：业务架构图、数据架构图、应用架构图、技术架构图——挂满一面墙。Ada 站住看了五分钟，问：'李工，合同审批里一份合同，在这四张图里分别是什么？'李工：'业务里是从发起、法务初审、财务校验、业务终审到归档的一条流程；数据里是合同主表+审批记录+附件三个实体；应用里是审批引擎里的一个流程实例；技术里……呃，技术架构我没画合同。'Ada：'就凭这最后一句，你的四张图是四个系统。'——一份合同，为什么四张图对不上，就是四个系统？"
追问：① 关注域视角必须对得上：业务架构里那份合同走到'法务初审'，数据架构里'审批记录'这个实体就得有'法务初审'这条记录，技术架构里就必须有支撑它的服务——为什么"同一个词'合同'，在四个图里指了四种东西"才是四张图对不上的原因？② 场景是胶水：拿一条真实场景横着穿过去（'法务老张在 App 上审批一份 500 万的合同'——业务架构走哪条流程？数据架构动哪些表？应用架构调哪个服务？技术架构跑在哪台机器上？）——一条场景走不完四张图，四张图就是四个系统；为什么"场景不是第五个视图，是胶水——验证其余四个视图是否互相矛盾"？③ 真悖论收束："模板没错（业务/数据/应用/技术四个架构各画各的，我是按标准模板画的）" vs "一个系统只有一个架构（四个是对同一架构的关注域视角，必须对得上）"——两个都对，靠什么判据分清？④ 反身：拿你们团队所有叫"XX架构"的图/文档，用一条真实使用场景横着穿过去——这条场景在各张图里走得通吗？走不通的地方，就是"多个架构"的病根。

**Q9（相关方冲突 · 组织链 · 免疫系统 · 案例进展④）**
"老周把'老规矩'投影出来，给全团队过了一遍——那不是一张图，是一份清单：M3 不可还原的涵义 + 设计准则（怎么造 M3）+ 演进准则（M3 怎么变才不散架）。小林问：'客户想看架构，我们给他看什么？'老周掏出手机，给疾控中心看追溯链路视图、给司机看状态视图、给维修看结构视图、给监管看合规视图。'这四样，没有一样是老周那张四层方块图。'——为什么同一个 M3，要给不同的人看不同的东西？"
追问：① 相关方→关注点→视点→视图：疾控关心可追溯性、司机关心可用性、维修关心可维修性、监管关心合规性、老板关心成本与进度——为什么这些关注点天然冲突（监管要更多加密和留存→拖慢数据链路增加成本；老板要快上线→积累技术债牺牲可维修性）？架构不是找让所有关注点都满意的解，而是在冲突之间做有意识的权衡——为什么权衡的前提是"得先能看到每个方面"（看不见安全就不会为安全取舍）？② 视图是刻意的"不完整"：逻辑视图不展示部署，物理视图不展示类关系——为什么"完整地画出系统的每一面=把所有关注点糊在一张图上=对任何人都没用"？为什么视图的价值恰恰在"剥离掉你不关心的部分，只保留本质"（给疾控看 App 界面层级没有意义）？③ 免疫系统：老周那份清单里有设计准则（温度数据归属追溯域、断链检测是刚性边界、追溯链路上每个环节都可独立验证）和演进准则（新增传感器类型不得破坏已有追溯链路、固件升级必须向后兼容已出厂设备、云端采集协议变更先过追溯完整性评审）——为什么缺一类，系统要么一改就坏（只有设计准则）要么建出来就不对（只有演进准则）？④ 反身：你们系统给客户/监管/运维/老板各看什么？有没有一个相关方的核心关注点你从来没摆出来过？

**Q10（落地生根 · 回部门"架构体检"）**
"结合你们部门现状，用七把尺子（架构三问 / 三个词三层 / 一个系统一个架构 / 架构描述组织链 / 关注点冲突 / 约束即解放 / 免疫系统）给最近讨论或维护的一个系统做一次'架构体检'——给出最该改进的三个事项，每个落到一个动作。"
追问：先做哪把尺子？为什么？两周后回来报告什么？

  - Q3 元素画全 vs 关系藏秘："把元素画全=架构完整（四层都画了，模块清单齐了）" vs "关系才是架构的秘密（涌现来自关系，画一根箭头等于没画关系）" → 判据 = 架构三问（关系断了系统就垮；三问在"关系"上过不去就是没画到点）；
  - Q4 架构属于系统 vs 架构比系统活："架构是系统的（系统没了它也没了）" vs "架构比系统活得长（那组决定作为经验教训继续存在）" → 判据 = 三个词三层（涵义≠指称；系统有生命周期，架构作为涵义可传承）；
  - Q5 约束=枷锁 vs 约束即解放："约束越少越灵活（架构是给团队上枷锁）" vs "约束即解放（架构只约束要命的决定，把团队从重复决策里解放出来）" → 判据 = 消极自由 vs 积极自由（只约束"不改会灾难"的决定，其余放手——管得最准好过管得最多）；
  - Q7 架构=图 vs 架构=老规矩："架构=架构图（画图才是做架构，图过时了架构就过时了）" vs "架构=团队真正在守的决定（老规矩才是架构，从没人写下来过）" → 判据 = 三个词三层（图烂决策活；规矩描述"少了它就不是它"，图描述"长得像什么"）；
  - Q8 模板没错 vs 一个系统一个架构："模板没错（四个架构各画各的）" vs "一个系统只有一个架构（四个是对同一架构的关注域视角，必须对得上）" → 判据 = 一个系统一个架构 + 场景胶水（一条真实场景走不完四张图，四张图就是四个系统）。
