## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：评审、验证、确认三个词到底差在哪？为什么中文看起来像近亲？三个看门人各拿什么参照、什么证据、什么时机？为什么评审对目标而不是核对需求？为什么"测试通过"不等于"验证通过"？确认为什么能兜住隐含需求？"测试全过、没人用"的病根在哪？三个看门人怎么接力，构成一条需求到上线的三关？

### 核心概念

1. **评审**（review，ISO 9000:2015 §3.11.2）：对客体实现**所规定目标**的适宜性、充分性或有效性的**确定**——动作=确定（判断）、证据=不要求客观证据、时机=事前 / 事中、参照=目标。三问：适宜性（对症吗）→ 充分性（够全吗）→ 有效性（管用吗）。
2. **验证**（verification，§3.8.12）：通过提供**客观证据**，对**规定需求**已得到满足的**认定**——动作=认定（证明）、证据=必须客观证据、时机=对结果证实、参照=规定需求。三要素：对照规定需求 + 客观证据 + 做出认定。
3. **确认**（validation，§3.8.13）：通过提供**客观证据**，对**特定的预期用途或应用要求**已得到满足的**认定**——动作=认定（证明）、证据=必须客观证据、时机=真实或模拟场景中证实、参照=预期用途。UAT = 真实用户 + 真实任务 + 真实场景。

### 对立概念

| 核心概念 | 对立面 | 问什么 |
|---|---|---|
| 评审 | 验证 | 确定 vs 认定（判断 vs 证明）；对目标 vs 对需求；不要求证据 vs 必须证据 |
| 验证 | 确认 | 对规定需求 vs 对预期用途；参照在文档里 vs 参照在场景里；射程够不着隐含 vs 兜得住隐含 |
| 评审 | 复盘 | 把关 vs 改进；干活之前/之中 vs 事后总结；IEEE 1028 五类 vs 敏捷实践 |
| 验证 | 测试 | 验证 = 对照 + 证据 + 认定 vs 测试 = 提供客观证据的手段之一；测试报告是验证的输入不是验证本身 |
| 验证 | 检验 | 盯"规定需求"（一条需求可能含多条特性）vs 盯"特性"（单条可测量特性）——粒度不同 |

### 关联概念（近界 · 辨析）

- **三者 × 翻译伪朋友（第1章）**：review / verification / validation 三个英文词源、构词、归属完全不同，中文翻译恰好都带"评/验/认"字，看起来像近亲——第三种词汇病的教科书案例；ISO 9000 里它们根本不在同一组词（评审在 3.11"有关确定的术语"，验证确认在 3.8"有关规范的术语"），糊了四十年。
- **三者 × 规定需求（第4章）**：规定需求是评审的对象（需求评审审的就是它）、验证的参照（验证对照的就是它）、验收与责任的依据（争议时以它为准）——同一个词，三个看门人都绕不开它；它没成文，三个看门人就全都闭门。
- **验证 × 可验证（第4章 需求质量六性）**："规定需求可验证"不是标准直接写的，是从"验证要求客观证据 + 验证以规定需求为参照"推出来的——可验证是规定需求当验证参照的资格证。
- **验证 × 符合性分析（第6章）**：符合性分析 = 设计层的验证（文档评审式）；测试 = 实现层的验证（试验式）——都满足验证三要素，只是证据不同；同一个动作在"看它对不对"时是评审的输入、在"证明它满足需求"时是验证的证据。
- **验证 × V 模型（第3章）**：左右镜像——需求从哪一级分解下去，验证就从哪一级收回来；"需求在哪一级被规定，验证就在哪一级证明"。
- **确认 × 隐含需求（第3/4章）**：隐含需求像冰山，水面下占了大半；验证是量吃水线的尺子（只管浮在水面上），确认是把船开进那片水域的试航（水下撞没撞到，试航时才知道）。
- **确认 × 预期用途**：三构成 = 目标用户（给谁用）+ 使用场景 / 任务（用来干什么）+ 环境与条件（什么情况下用）；使用条件可以是真实的或模拟的（ISO 9000 注 3）——给灰度发布、仿真测试合法性。
- **确认 × 工程系统（第2章）**：技术系统上线了 ≠ 工程系统成功；确认问的正是"整个社会技术系统能转起来吗"。
- **评审 × 目标**：目标具体化配方 = 对象 + 时限 + 可衡量结果；检验三问（通过标准 / 可观察判定 / 看什么裁决）；通过标准会前定、会后逐条打勾。
- **三个看门人 × 质量程度三步法（第3章）**：三步——确定特性值 → 与需求比对（接收准则）→ 认定满足程度；第三步的"认定"动作正是验证和确认——没有验证确认，连"感觉"都算不上，因为没人认定。

### 核心原理

1. **翻译伪朋友原理**：三个英文词源、构词、归属完全不同，中文因"一个动词 + 一个形近字"看起来像近亲；标准里评审在 3.11"有关确定的术语"组、验证确认在 3.8"有关规范的术语"组——"确定"和"认定"是两种动作，判断和证明是两回事。
2. **参照不同原理**：三个看门人看向三个不同的参照物——评审对目标（objective，要实现的结果）、验证对规定需求（specified requirement，明示成文）、确认对预期用途（intended use，谁用·怎么用·什么条件下用）；目标在最上层、规定需求在中间、客体在最下面、预期用途在旁边的场景层。
3. **动作分家原理**：评审动作是"确定"（主动调查，从"没有结论"到"有结论"）；验证确认动作是"认定"（结果已经在了，去证实它）——一个判、一个证；判靠判断力、证靠客观证据；这就是评审不要求证据、验证确认必须证据的原因。
4. **五维全不同原理**：定义 / 参照 / 动作 / 证据 / 时机五个维度全部不同，没有一维是"差不多"——"参照不同"可以只是修辞，五维全不同才是硬分家。
5. **评审三问原理**：适宜性（对症吗）→ 充分性（够全吗）→ 有效性（管用吗）层层递进，一个都不能跳过——方向不对做得再全白费、覆盖不全方向对也翻车、前两个过了还要看结果说话；三问不是同一个会里一次问完，评审是"一个动作"不是"开一次会"。
6. **评审以目标为参照三理由原理**：① 需求本身可能是错的（谁来审需求本身——需求评审的本质是审需求对业务目标是否适宜充分有效）；② 否则评审和验证就重复（标准不会为同一件事分两组）；③ 满足所有需求 ≠ 达成目标（要求是"路"，目标是"目的地"）。
7. **偏离更远原理**：需求满足得越彻底、目标的偏离走得越远——评审的价值是每隔一段问一句"我们做的这些需求，还朝那个目标吗"；最失败的评审不是没查出问题，而是把评审做成了验证。
8. **目标具体化原理**：抽象目标评不了（"做出高质量的产品"），具体目标评得了（"月底对账时间 < 2 小时"）；配方 = 对象 + 时限 + 可衡量结果；检验三问答得上才开会；通过标准会前定、会后逐条打勾；目标分层级，评审挂可判定那一层（战略目标负责让人相信值得做，操作目标负责让评审开得下去）。
9. **系统性评审三属性原理**：团队参与、评审结果文档化、评审过程文档化——缺一个就是"非系统性评审"，说人话：没记录的评审不算评审，最多算聊天；评审的职责是主动暴露问题不是汇报成果，问题要被人看见、被追踪、被验证已解决，就必须落纸。
10. **五类评审原理**：管理评审（评估项目状态）/ 技术评审（对照规格识别技术偏差）/ 检查（最正式、逐行检测、缺陷检出率最高）/ 走查（作者引导、同行熟悉产品）/ 审计（独立于开发方、核实符合合同与标准）——谱系从轻到重，但无论轻重三属性不变：有团队、有结论、有记录。
11. **评审五大目的原理**：质量把关 / 风险识别 / 对齐共识 / 决策推进 / 经验沉淀——五条里最容易被轻视的是决策推进（开完会没下文的评审，前三件事全白做）；决策推进落地三动作：明确结论（通过 / 有条件通过 / 不通过）+ 有条件通过写明条件、复核人、期限 + 记录留档；评审的终点不是散会，是"有一个字面结论、有一份记录、有下一步谁负责"。
12. **验证三要素原理**：对照规定需求 + 提供客观证据 + 做出认定，缺一个都不算验证——口头"大概要快一点"无法验证；"我认为满足"不算验证；"差不多吧"不是验证；验证的输出是结论（已验证 / 未验证），不是"跑完了"。
13. **可验证推论原理**：ISO 9000 定义规定需求时只说"被明示的、成文的"，并没有说"可验证"——"可验证"是从"验证要求客观证据 + 验证以规定需求为参照"推出来的，是规定需求当验证参照的资格证；口头那句"大概要快一点"连被验证的资格都没有。
14. **测试≠验证原理**：测试只是提供客观证据的手段之一（ISO 9000 注 1：试验结果、变换方法计算、文件评审等）；"测试通过率 96%"是测试结果、是证据的一种，96% 意味着 4% 的用例没过或没写，这 4% 对应的需求是否满足测试没有给出证据；测试报告是验证的输入不是验证本身——别把验证窄化成"跑测试"，也别把"跑测试"升级成"验证过了"。
15. **检验 vs 验证粒度原理**：检验（inspection）是"对特性进行测量、检查、试验，与规定要求比较，判定合格与否"——听起来和验证几乎一样，区别在粒度：检验盯着"特性"（温度波动 ≤±0.5℃ 这种单条），验证盯着"规定需求"（一条需求可能含多条特性）。
16. **V 模型镜像原理**：需求从哪一级分解下去，验证就从哪一级收回来——"需求在哪一级被规定，验证就在哪一级证明"；恒信"金额 ≥ 500 万触发重点审"分解到系统需求层、分配到审批引擎、落进金额校验函数，三级分解对应三级回收；只做最后一次性验证等于让所有分解白做，中间断掉的层级恰恰是缺陷藏身的地方。
17. **符合性分析归位原理**：符合性分析 = 设计层的验证（文档评审式）；测试 = 实现层的验证（试验式）——都满足验证三要素，只是证据不同；第6章说"验证把符合性分析纳入更完整的框架"，现在框架在这儿了。
18. **验证射程原理**：验证的参照是规定需求——规定意味着明示、成文；没写进文档的需求，验证够不着，因为验证的尺子在文档里，没文档 = 没参照；隐含需求不在验证射程内。
19. **确认共享三要素不同参照原理**：确认和验证共享同一套三要素（对照 / 证据 / 认定），唯一区别在第一个要素——验证对照"规定需求"（文档），确认对照"特定的预期用途"（场景）；就这一个词的区别，决定了两个看门人完全不同的射程和命运。
20. **预期用途三构成原理**：预期用途由目标用户（给谁用）+ 使用场景 / 任务（用来干什么）+ 环境与条件（什么情况下用）三样东西构成；使用条件可以是真实的或模拟的（ISO 9000 注 3）——给灰度发布、仿真测试合法性；M3 的预期用途浓缩在"全程温度不断链"这六个字里。
21. **参照在场景原理**：验证的参照在文档里，确认的参照在场景里——预期用途不是一份文档，是一种真实使用情境；真实场景自带答案：对不上账、断档 30 秒、待办卡在离职审批人手里，全是看得见的缺陷。
22. **冰山原理**：隐含需求像冰山，水面下的部分占了大半；传递到下游的只能是浮出水面的部分（明示成文）；验证是量吃水线的尺子（只管浮在水面上的部分），确认是把船开进那片水域的试航（水下撞没撞到，试航时才知道）；隐含需求不会自己开口，就靠把船开进真实水域让水下部分自己撞出声来。
23. **因果链原理**：只做验证不做确认 → 隐含需求系统性漏失 → 测试全过、没人用——三段因果：隐含需求没进文档（真实存在但验证够不着）→ 只做验证的团队让所有没写进文档的需求漏在体系外（连"被检验"的机会都没有）→ 上线后功能全对、测试全绿，但用户处处别扭、行动上"不用"；确认的存在价值恰恰建立在非明示需求上——如果所有需求都能写下来被验证，确认就不需要存在了。
24. **显影原理**：确认把"漏掉的隐含需求"变成"可发现的缺陷"——隐性缺失看不见，显影出来的缺陷看得见；章首李工的 UAT 报告里没有一条缺陷，不是因为没有缺陷，是因为他把产品放进了一个造不出缺陷的场景（测试环境），缺陷无处显影。
25. **UAT 本质原理**：UAT 不是"让业务方点一遍测试环境"，而是"真实用户 + 真实任务 + 真实场景"的确认；让业务方当测试员、替测试团队跑用例，是把确认做成了验证——前一种 UAT 测的还是需求，后一种 UAT 测的是场景。
26. **确认手段谱系原理**：按成本排谱系——仿真测试最便宜（模拟场景）、灰度发布折中（一小部分真实用户 + 真实流量先跑）、试运行最重（全部真实场景）；灰度是确认不是缩小版的验证；别把"灰度没出问题"读成"验证过了"，要读成"确认初步通过了，剩下 90% 的真实场景还没当裁判"；冰山下面不只有隐含，还有必须履行的（强制）需求。
27. **确认时机原理**：确认常在设计开发形式结束之后，它锚定"产品"不锚定"需求"；它站在工程系统的门口——技术系统上线了 ≠ 工程系统成功，确认问的正是"整个社会技术系统能转起来吗"。
28. **六类评审原理**：需求 / 设计 / 代码 / 测试 / 发布 / 复盘六类评审把"把关"从终点挪到全程；问题越早发现修复成本越低——需求阶段缺陷修复成本是 1，发布后是 30~70 倍；每类评审的通过标准都是一组可勾选的硬条件（全部由"数字 + 动作"构成，没有"质量要好"这种形容词）；评审的尺子不是评审会当天造出来的，是方案出生时就该有的。
29. **评审≠复盘原理**：评审管"把关"（干活之前/之中，判断适宜/充分/有效），复盘管"改进"（干完了，事后总结，绕回起点驱动下一轮）——复盘不在 IEEE 1028 五类里，也不是 ISO 9000 的"评审"；复盘的通过标准同样要会前定（负责人 + 截止日期、关闭率 ≥ 80%、按根因归类、记录归档）；复盘的价值一半在诊断、一半在闭环。
30. **三关接力原理**：三个看门人不是三座孤立的门——评审（开工前·方向）→ 验证（交付时·需求）→ 确认（交给用户·用途）；这是第3章"质量程度三步法"第三步的落地；缺任何一关后果不同：缺评审=需求错了没人发现白做、缺验证=做错了没人知道返工、缺确认=做对了也没人用白做——三个看门人各看一处，谁也替不了谁。
31. **因果不是运气原理**："测试全过、没人用"不是运气问题是因果问题——"验证做了，其余没做"，三个看门人只来了一个，剩下两个在等一场事故；验收不是一句话，是三个看门人依次签字。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "评审、验证、确认差不多，都是把关。"
2. "评审就是开会过一遍需求 / 逐条核对需求清单。"
3. "评审以需求为参照更省事，需求是现成的文档。"
4. "评审目标太抽象，评不了。"
5. "评审就是读文档 / 把证据念一遍。"
6. "没记录的评审也是评审。"
7. "评审会开完就散，没有下文也行。"
8. "测试全绿 = 验证过了。"
9. "验证就是跑测试。"
10. "测试通过率 96% 就是验证通过率 96%。"
11. "验证最后做一次就行。"
12. "UAT 跑了 = 确认过了 / 让业务方点一遍测试环境就是 UAT。"
13. "确认是验证的加强版，范围更大而已。"
14. "隐含需求写进文档后就能被验证。"
15. "测试全过、没人用是运气问题 / 执行问题。"
16. "灰度没出问题 = 验证过了。"
17. "复盘也是评审，都带'评'字。"
18. "满足所有需求 = 达成目标。"

### 本章判据（七把尺子）

1. **三把尺子判据**：评审对目标（方向对不对）、验证对规定需求（做对了吗）、确认对预期用途（做对的东西了吗）。
2. **评审三问判据**：适宜性（对症吗）→ 充分性（够全吗）→ 有效性（管用吗），层层递进；目标具体化配方 = 对象 + 时限 + 可衡量结果；通过标准会前定、会后逐条打勾。
3. **评审三属性判据**：团队参与、评审结果文档化、评审过程文档化——没记录的评审不算评审，最多算聊天。
4. **验证三要素判据**：对照规定需求 + 提供客观证据 + 做出认定；测试只是提供证据的手段之一；逐级回收（单元 → 集成 → 系统）。
5. **确认三要素判据**：对照预期用途 + 客观证据 + 认定；参照在场景里不在文档里；UAT = 真实用户 + 真实任务 + 真实场景。
6. **因果链判据**：只做验证不做确认 → 隐含需求系统性漏失 → 测试全过、没人用；确认的存在价值建立在非明示需求上。
7. **评审≠复盘判据**：评审管把关（过程关卡），复盘管改进（事后回顾），复盘不在 IEEE 1028 五类里。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"评审"（对目标 / 适宜充分有效 / 动作是确定 / 不要求客观证据）并说出它的对立（验证）。
2. 能定义"验证"（对照规定需求 / 客观证据 / 认定）并说出三要素。
3. 能定义"确认"（对照预期用途 / 客观证据 / 认定）并说出预期用途三构成。
4. 能辨析 评审 × 验证——确定 vs 认定（判断 vs 证明）、对目标 vs 对需求、证据要求不同。
5. 能辨析 验证 × 确认——参照在文档里 vs 参照在场景里；验证射程够不着隐含 vs 确认兜得住隐含。
6. 能辨析 评审 × 复盘——把关 vs 改进、干活之前/之中 vs 事后总结、IEEE 1028 五类 vs 敏捷实践。
7. 能辨析 验证 × 测试——验证 = 对照 + 证据 + 认定 vs 测试 = 提供证据的手段之一；测试报告是验证的输入不是验证本身。
8. 能辨析 验证 × 检验——盯"规定需求" vs 盯"特性"，粒度不同。
9. 能说出"翻译伪朋友"在评审/验证/确认上的体现（三个英文词源不同、在 ISO 9000 不同术语组，中文形近字糊住分家）。
10. 能说出三个参照（目标 / 规定需求 / 预期用途）及它们在开发世界三层图里的位置（目标最上层、规定需求中间、客体最下、预期用途场景层）。
11. 能定义"目标具体化配方"（对象 + 时限 + 可衡量结果）与检验三问（通过标准 / 可观察判定 / 看什么裁决）。
12. 能定义"预期用途三构成"（目标用户 / 使用场景任务 / 环境与条件）。
13. 能说出"六类评审"（需求 / 设计 / 代码 / 测试 / 发布 / 复盘）与"五类做法"（管理 / 技术 / 检查 / 走查 / 审计）。
14. 能说出"三关接力"（评审开工前 · 方向 → 验证交付时 · 需求 → 确认交给用户 · 用途）。
15. 能辨析 规定需求 × 隐含需求——明示成文（验证的参照）vs 惯例默认没写（确认的射程）；含强制需求也在冰山下面。

### 原理层（应能解释为什么）

1. 能解释为什么三个词在中文里看起来像近亲（翻译伪朋友——英文词源不同，ISO 9000 分组不同，"确定"和"认定"是两种动作）。
2. 能解释为什么"参照不同"是决定性差异（评审对目标 / 验证对需求 / 确认对用途——尤其目标 vs 用途的区别：目标驱动需求推导，用途在真实场景里才现形）。
3. 能解释为什么评审动作是"确定"、验证确认是"认定"（判靠判断力、证靠客观证据；判断可以不依赖证据，证明不行）。
4. 能解释评审三问为什么层层递进（方向不对做得再全白费；覆盖不全方向对也翻车；前两个过了还要看结果说话）。
5. 能解释为什么评审以目标为参照而不是需求（三理由：需求可能错 / 否则与验证重复 / 满足所有需求 ≠ 达成目标）。
6. 能解释"需求满足得越彻底、目标的偏离走得越远"（目标错了需求再对也是白做；评审是整条链上唯一抬头看目标的环节）。
7. 能解释为什么目标必须具体化才能评审（抽象目标评不了；对象 + 时限 + 可衡量结果；检验三问；通过标准会前定）。
8. 能解释为什么评审必须记录（主动暴露问题要被人看见、被追踪、被验证已解决；不记录的问题下次评审没人记得它存在过）。
9. 能解释为什么"测试通过"不等于"验证通过"（测试是证据手段之一；96% 意味着 4% 没证据；测试报告是输入不是验证本身）。
10. 能解释为什么规定需求"可验证"（从验证定义推出来的资格证，呼应第4章需求质量六性）。
11. 能解释为什么验证要逐级回收（V 模型左右镜像——需求在哪一级被规定，验证就在哪一级证明；只做最后一次性验证让分解白做）。
12. 能解释为什么符合性分析是验证的一种（文档评审式证据；同一动作在不同门里是评审输入或验证证据）。
13. 能解释为什么验证够不着隐含需求（参照是规定需求，尺子在文档里，没文档 = 没参照）。
14. 能解释为什么确认能兜住隐含需求（参照在场景里；真实场景自带答案；冰山比喻——验证量吃水线、确认开船试航）。
15. 能解释为什么确认与验证共享三要素却命运不同（唯一区别在第一个要素——文档 vs 场景）。
16. 能解释为什么"只做验证不做确认 → 测试全过没人用"（因果链三段；确认价值建立在非明示需求上；确认把隐性缺失显影成缺陷证据）。
17. 能解释为什么 UAT 必须是真实用户 + 真实任务 + 真实场景（让业务方当测试员是把确认做成了验证）。
18. 能解释为什么灰度发布是确认不是缩小版的验证（注 3 真实或模拟使用条件；放 10% 真实流量 = 真实场景当裁判）。
19. 能解释为什么六类评审要洒全程（把关从终点挪到全程；需求阶段缺陷修复成本 1、发布后 30~70 倍）。
20. 能解释为什么复盘不是评审（评审管把关、复盘管改进；复盘绕回起点驱动下一轮）。
21. 能解释为什么三个看门人谁也替不了谁（三关缺任何一关后果不同：白做 / 返工 / 没人用）。
22. 能解释为什么"测试全过、没人用"是因果不是运气（验证做了其余没做 = 在等一场事故；验收是三个看门人依次签字）。

### 判据层（应会用）

1. **三把尺子判据**：一个"把关"动作拿来，先问它对什么参照——目标（评审）、规定需求（验证）、预期用途（确认）？说不出参照，就是三个词糊成一个。
2. **评审三问判据**：适宜 / 充分 / 有效三问过了吗？目标具体化了吗（对象 + 时限 + 可衡量结果）？通过标准会前定了吗、会后逐条打勾吗？
3. **评审三属性判据**：有团队参与吗？有结论吗？有记录吗？——没记录的评审不算评审，最多算聊天。
4. **验证三要素判据**：对照规定需求吗？有客观证据吗？有结论吗（已验证 / 未验证）？证据覆盖全部规定需求吗（96% 是缺口不是 100%）？
5. **确认三要素判据**：对照预期用途吗？真实用户 + 真实任务 + 真实场景齐吗？隐含需求在真实场景里显现并处理了吗？
6. **因果链判据**：你们只做验证没做确认吗？有没有"测试全过、没人用"的症状（对不上账 / 没人用 / 卡死 / 抱怨）？
7. **评审≠复盘判据**：这个活动是在把关（干活之前/之中判断适宜充分有效）还是在改进（干完后总结、驱动下一轮）？通过标准会前定了吗？

### 纠错红线十条

1. **先表态后翻案**：先问"三个词不就是把关吗""测试全绿难道不算验证""UAT 跑了还不算确认"，再翻——不让结论先入。
2. **反转精确不造新误解**：不说"验证不重要"（验证证明做对了，不可或缺）；不说"评审就是挑毛病"（五大目的：质量把关/风险识别/对齐共识/决策推进/经验沉淀）；不说"测试没用"（测试是验证的证据手段之一，别把手段当目的也别把手段贬成无用）。
3. **判据配机制**：每条反转都有"为什么"（翻译伪朋友糊分家 / 判靠判断力证靠客观证据 / 需求在哪一级被规定验证就在哪一级证明 / 真实场景自带答案 / 因果不是运气）和"怎么当场验证"（七把尺子）。
4. **归责到可对照动作**：不归咎"李工/小林/老周"，落到"这次'把关'对什么参照 / 目标具体化了吗 / 通过标准会前定了吗 / 证据覆盖全部规定需求吗 / 真实用户+任务+场景齐吗 / 只做验证没做确认吗 / 复盘有行动项闭环吗"这类可查动作。
5. **教机制不教断言**：教"为什么验证够不着隐含、为什么 UAT 要真实场景、为什么评审对目标、为什么没记录不算评审"，不教"Ada 说得对"。
6. **先立尺子再翻案**：先给七把尺子（三把尺子 / 评审三问 / 评审三属性 / 验证三要素 / 确认三要素 / 因果链 / 评审≠复盘），再翻案例。
7. **拉开强度层次**：★★★ 常识（三词差不多 / 逐条核对=评审 / 测试全绿=验证过 / UAT 跑了=确认过 / 没人用是运气 / 隐含写进文档就能验）重点翻，★★ 次之。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（找出最近一次评审的通过标准 / 看 UAT 用的是不是真实数据真实时间点 / 走一遍三关体检）。
9. **单一权威不另立标准**：判据引用书七把尺子 + ISO 9000 定义，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给部门最近一次上线 / 验收做"三关体检"

> 目标：用七把尺子检查一次上线 / 验收的三个看门人（评审 / 验证 / 确认）各就各位没有，产出三件可执行改进。
> 场景：回部门落地。时长：2 小时内完成一次体检，两周后复查一至两项。

1. **查三把尺子（尺1 · 三把尺子判据）**：这次上线/验收，"把关"动作各对什么参照——评审对目标了吗？验证对规定需求了吗？确认对预期用途了吗？有没有三个词糊成一个（都是"把关"）的地方？产出：三关各自的参照一句话。
2. **查评审（尺2 · 评审三问 + 尺3 · 评审三属性）**：评审会通过标准是**会前定**的还是会上现想的？目标具体化了吗（对象 + 时限 + 可衡量结果）？会后逐条打勾了吗？这次评审有没有结论（通过 / 有条件通过 / 不通过）、有记录、有下一步谁负责？产出：通过标准一句话 + 三属性打勾。
3. **查验证（尺4 · 验证三要素）**：验证三要素齐吗——对照（需求成文了吗）、证据（有客观证据吗）、认定（有结论吗）？证据覆盖**全部**规定需求吗（通过率 96% 的 4% 有没有说法）？测试是不是被当成了验证本身？逐级回收了吗（单元→集成→系统），还是只做了系统级？产出：三要素打勾 + 缺口清单。
4. **查确认（尺5 · 确认三要素）**：确认是"真实用户 + 真实任务 + 真实场景"吗？用的是真实数据、真实时间点、真实并发吗？还是让业务方在测试环境点了一圈？隐含需求（对不上账 / 卡死 / 没人用的场景）在真实场景里显现并处理了吗？产出：UAT 场景三问打勾 + 漏掉的真实场景清单。
5. **查因果链（尺6 · 因果链判据）**：有没有"只做验证没做确认"的迹象——功能全对、测试全绿，但用户用起来别扭、对不上账、没人用？把隐性缺失显影成缺陷了吗？产出：症状清单（对不上账 / 卡死 / 抱怨 / 弃用）。
6. **查复盘（尺7 · 评审≠复盘判据）**：最近一次复盘是"把关"还是"改进"？有行动项、负责人、截止日期、闭环吗？还是开完会没有下文？产出：复盘是改进还是把关的判定 + 行动项闭环率。

**卡住怎么判断**：任一尺子打不出勾，就是该尺子说的缺口——不用全打完，找到第一个"否"就能开工。产出三件最该改进事项（每条 = 一个可检查动作）。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 这次"把关"能说清对什么参照（目标/需求/用途）？ | □ | 三词糊成一个 → 验收时说不清哪一关过了 |
| 评审通过标准会前定、会后逐条打勾？ | □ | 会后现想 → 大家连"过没过"都没共识，会开了白开 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身 · 破题）**
"Ada 对李工竖起三根手指：'你把三件事当成一件事办了——评审、验证、确认。'三个词在中文里看起来像近亲，它们到底差在哪？"
追问：① 翻译伪朋友：review / verification / validation 三个英文词源、构词、归属完全不同，ISO 9000 里还不在同一组词（评审在 3.11"有关确定的术语"，验证确认在 3.8"有关规范的术语"）——"确定"和"认定"是两种动作，判断和证明是两回事，为什么中文形近字把这个分家糊了四十年？② 三把尺子：评审对目标、验证对规定需求、确认对预期用途——三个参照各回答什么问题（方向对不对 / 做对了吗 / 做对的东西了吗）？③ 反身：你们最近一次"验收签字"，是三个看门人依次签字，还是三个词糊成一个签了？

**Q2（见树见林② · 概念关系 · 真悖论收束）**
"请给出 评审、验证、确认 的关系（一句话）。再把'参照'放进去——三个参照（目标 / 规定需求 / 预期用途）各在哪一层？为什么说'参照不同'是决定性差异？"
追问：① 五维对比（定义 / 参照 / 动作 / 证据 / 时机）——哪一维全不同？② 动作分家：评审动作是"确定"（主动调查）、验证确认是"认定"（证实）——为什么"判靠判断力、证靠客观证据"直接决定了评审不要求证据、验证确认必须证据？③ 真悖论收束："评审、验证、确认都是把关（它们都叫把关）" vs "三个词是三把完全不同的尺子（翻译伪朋友）"——两个都对，靠什么判据分清？④ 目标 vs 预期用途：目标驱动需求推导、用途在真实场景里才现形——这两个参照为什么不是一回事？

**Q3（评审对目标 · 真悖论收束）**
"小林的评审会开了一下午：逐条念需求、逐条打勾——'有编号✓、有来源✓、可测吗✓'，三十条划满对勾，宣布'评审通过'。小赵：'你只核对清单有没有写——那是验证的姿势。评审要对目标。'——评审为什么不以需求为参照？"
追问：① 三理由——需求本身可能错（谁来审需求本身）/ 否则评审和验证就重复（标准不会为同一件事分两组）/ 满足所有需求 ≠ 达成目标（要求是路、目标是目的地）？② 真悖论收束："评审就是逐条核对需求（我们天天这么干，现成的文档一条条对最省事）" vs "评审对目标（核对需求是验证的姿势，需求满足得越彻底目标偏离得越远）"——两个都对，靠什么判据分清？③ 目标具体化：目标 = 对象 + 时限 + 可衡量结果——为什么"月底对账时间 ≤ 2 小时"评得了、"系统能上线"评不了？④ 反身：你们最近一次评审，通过标准是会后现想的吗？评审问的是"这需求对吗"还是"这些需求还朝那个目标吗"？

**Q4（验证三要素 · 测试≠验证 · 真悖论收束）**
"李工亮出 UAT 报告：'测试用例通过率 96%，P0/P1 清零，验收合格，可以上线。'Ada：'你验证的是按需求做对了——可测试全绿不等于验证过了。'——测试和验证差在哪？"
追问：① 验证三要素：对照规定需求 + 客观证据 + 认定——缺一个都不算验证；"口头大概要快一点"缺对照、"我认为满足"缺证据、"差不多吧"缺认定？② 测试只是证据手段之一（ISO 9000 注 1：试验结果 / 变换方法计算 / 文件评审），测试报告是验证的输入不是验证本身——96% 意味着 4% 的用例没过或没写，这 4% 对应的需求是否满足，测试没有给出证据？③ 真悖论收束："测试全绿 = 验证过了（测试不就是验证吗）" vs "测试只是证据之一、验证要对全部规定需求做认定（96% 是缺口不是 100%）"——两个都对，靠什么判据分清？④ 反身：你们说"测试全绿"的时候，验证三要素齐了吗？缺的是哪一条？

**Q5（确认三要素 · UAT 本质 · 真悖论收束）**
"章首李工让法务、财务、业务'在测试环境点了一圈'，说'业务方点了，确认过了'。Ada：'那是让业务方当测试员。'——确认到底是什么？为什么 UAT 跑了不等于确认过了？"
追问：① 确认 = 对照预期用途 + 客观证据 + 认定；UAT = 真实用户 + 真实任务 + 真实场景——前一种 UAT 测的还是需求、后一种 UAT 测的是场景，差别在哪？② 参照在场景里：验证的参照在文档里（明示成文可复制）、确认的参照在场景里（真实使用情境）——为什么真实场景自带答案（对不上账、断档 30 秒、卡在离职审批人手里全是看得见的缺陷）？③ 真悖论收束："让业务方点测试环境 = 确认（用户都参与验收了）" vs "让业务方当测试员 = 把确认做成验证（对照的还是需求清单）"——两个都像，靠什么判据分清？④ 隐含需求像冰山：验证是量吃水线的尺子只管浮面、确认是把船开进真实水域试航——为什么很多隐含需求写不下来（顺手/直觉/动效/节奏/惯例），只有真实场景能裁决？

### 第二组 · 落地与实践（5 题）

**Q6（评审对目标 · 判据运用 · 案例进展①）**
"重开上线评审会前，Ada 没讲方案，先写了三条目标：月底对账一致率 100% + 对账时间 ≤ 2 小时；法务合规：电子签章审批链完整可追溯；业务可用：3 个工作日完成一次发起归档。李工对着'法务合规'忽然卡住：'这条变更当初是口头定的，需求清单里没有，方案里也没有。'——Ada 为什么先定目标再评审？"
追问：① 如果只核对需求清单，李工会说"全部覆盖，通过"——可尺子不是需求清单是"法务合规"这个目标，目标一摆出来就发现"这条变更连需求都不是"——评审对目标的实操威力在哪？② 目标具体化三成分（对象 + 时限 + 可衡量结果）+ 检验三问（通过标准 / 可观察判定 / 看什么裁决）——三条目标各满足吗？③ 通过标准会前定、会后逐条打勾——为什么"会前定"让评审有尺子、"会上现想"等于没有尺子？④ 反身：你们最近一次上线评审，通过标准是"系统能上线"这种评不了的，还是三条可打勾的目标？

**Q7（评审 vs 复盘 · 判据运用 · 案例进展⑤ + 辨析）**
"恒信月底对账对不上，复盘会产出了两条行动项：'变更必须先过评审对目标一关'和'UAT 改真实场景跑'，各配负责人和期限。Ada：'复盘的价值，一半在诊断，一半在闭环。'——复盘和评审是一回事吗？"
追问：① 评审管把关（干活之前/之中，判断适宜/充分/有效）、复盘管改进（干完了，事后总结，绕回起点驱动下一轮）——复盘不在 IEEE 1028 五类里、也不是 ISO 9000 的"评审"，为什么？② 复盘的通过标准同样要会前定：负责人 + 截止日期、关闭率 ≥ 80%、按根因归类（而非甩锅）、记录归档——"只诊断不闭环"的复盘是把同样的错再复一遍，你们团队怎么防？③ 复盘绕回起点，把上一轮教训变成下一轮评审的目标——这条"改进→把关"的回路在第13章治理里叫"事件触发"，为什么复盘是那个事件源？④ 反身：你们最近一次复盘，产出的是"我们很努力"还是"下一轮改什么、谁改、何时改完"？

**Q8（确认·UAT · 判据运用 · 案例进展③ · 真悖论收束）**
"Ada 复盘那次 UAT，连问三问：月底对账用的是真实数据还是造的 20 条（没有一条是 25 号之后的）？在真实月底时间点、真实并发下做的吗（不是周二下午三个人轮流点）？电子签章审批链'谁审谁签'验证过吗（没排进 UAT）？三问都是'否'。Ada 合上文件夹：'你把确认做成了验证。'——这三问各在考确认的什么？"
追问：① 三问对应预期用途三构成——目标用户（法务/财务/业务，不是 IT 测试员）、使用场景/任务（月底对账、电子签章、审批人休假交接）、环境与条件（月末高峰并发、弱网、休假交接）——哪一问最容易被"造不出缺陷的测试环境"带过？② 确认不能后补到上线后——"上线后补确认，就叫上线事故"；把三个真实场景排进下一轮 UAT，用真实数据、真实任务、真实时间点——为什么？③ 真悖论收束："UAT 是确认（用户验收测试嘛）" vs "那次 UAT 是验证（对照的还是需求清单）"——两个都像，靠什么判据分清？④ 反身：你们一次"UAT 通过"，数据是真的吗？时间点是真实的吗？真实场景里会现形的隐含需求，有几个是测试用例提前发现的？

**Q9（确认射程 · 因果链 · 案例进展④ · 真悖论收束）**
"M3 交付前跑真实运输：疫苗装箱、上真实的疫苗运输车、跑出库→运输→到达全程。第一天晚上，车厢过减速带时温度记录仪振动断电重启，断档 30 秒。测试台架复现不了——台架没有颠簸；测试用例里只有'温度记录连续'，没有'振动下温度记录连续'。老周：'用例全过，说明不了上路能过。'——这句话在说什么？"
追问：① 断档 30 秒是验证的错还是确认的错（测试用例没写好 = 执行问题）？——验证的参照是需求文档（没写"振动下连续"=不在射程内）、确认的参照是真实场景（"疫苗能不能安全送到"=场景里现形），断档 30 秒是场景里显影出来的隐含需求？② 真悖论收束："这是测试用例没写好（执行问题，改用例就行）" vs "这是测试环境里没有路（场景问题，台架替代不了那辆会颠的车）"——两个都像，靠什么判据分清？③ 因果链三段：隐含需求没进文档 → 只做验证的团队让它在体系外漏着 → 上线后处处别扭（功能全对、测试全绿、没人用/对不上）——为什么这是因果不是运气？④ 反身：你们有没有"用例全过、一上路就露馅"的经历？那个露馅，是缺了哪一关？

**Q10（落地生根 · 回部门"三关体检"）**
"结合你们部门现状，用七把尺子（三把尺子 / 评审三问 / 评审三属性 / 验证三要素 / 确认三要素 / 因果链 / 评审≠复盘）给最近一次上线 / 验收做一次'三关体检'——给出最该改进的三个事项，每个落到一个动作。"
追问：先做哪把尺子？为什么？两周后回来报告什么？

  - Q3 核对需求 vs 评审对目标："评审就是逐条核对需求（现成的文档一条条对最省事）" vs "评审对目标（核对需求是验证的姿势，需求满足越彻底目标偏离越远）" → 判据 = 评审三问（适宜/充分/有效）+ 目标具体化（对象+时限+可衡量结果）；
  - Q4 测试全绿 vs 验证通过："测试全绿 = 验证过了（测试不就是验证吗）" vs "测试只是证据之一、验证要对全部规定需求做认定（96% 是缺口不是 100%）" → 判据 = 验证三要素（对照/证据/认定 + 证据覆盖全部规定需求）；
  - Q5 业务方点了 vs 确认过了："让业务方点测试环境 = 确认（用户都参与验收了）" vs "让业务方当测试员 = 把确认做成验证（对照的还是需求清单）" → 判据 = 确认三要素（真实用户 + 真实任务 + 真实场景）；
  - Q8 UAT 是确认 vs 那次 UAT 是验证："UAT 是确认（用户验收测试嘛）" vs "那次 UAT 是验证（对照的还是需求清单）" → 判据 = 确认三要素（真实数据/真实时间点/真实并发，测场景不测需求）；
  - Q9 执行问题 vs 场景问题："这是测试用例没写好（执行问题，改用例就行）" vs "这是测试环境里没有路（场景问题，台架替代不了那辆会颠的车）" → 判据 = 验证射程在文档 / 确认射程在场景（断档 30 秒是场景里显影的隐含需求）。
- **设题九检全过**：①无直觉能秒答（每题翻案）；②追问链齐（机制/判据/归责/反身）；③概念锚点在导读给足；④题面依据全在书内（UAT 96%/月底对账三问/断档 30 秒/三条目标/复盘两条行动项）；⑤靶子皆"从没怀疑"的常识；⑥每题落回判据或动作；⑦全部"信了相反"非知识盲区；⑧案例细节全写进题面（造的数据 20 条 / 周二下午三个人轮流点 / 减速带断档 30 秒 / 三条目标数字——前提自证）；⑨六处升级为真悖论收束。
