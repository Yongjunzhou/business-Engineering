## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：一个产品开发流程从哪到哪——需求、设计开发、质量三兄弟怎么互相定义、拆不掉？"质量好"和"等级高"被多少人当成同一个词？

### 核心概念

1. **需求**（requirement）：明示的、通常隐含的或必须履行的需要或期望（ISO 9000:2015 §3.6.4）。
2. **设计开发**（design and development）：将客体的需求转换为对其更详细的需求的一组过程（§3.4.8）。
3. **质量**（quality）：客体的一组固有特性满足需求的程度（§3.6.2）。
4. **承重构件 · 客体**（object）：可感知或可想象的任何事物——被设计的东西（§3.6.1）。
5. **承重构件 · 特性**（characteristic）：可区分的特征——需求落到特性上才可测量、可验证（§3.10.1）。

### 对立概念

| 核心概念 | 对立面 | 问什么 |
|---|---|---|
| 需求 | 点子 / 创意 | 点子不表述为需求，就进不了设计开发的流程 |
| 设计开发 | 走流程 | 输入输出同样详细，没发生设计开发 |
| 质量 | 等级 | 高档车可以是差质量，低档车可以是好质量 |
| 基座三角 | 三个并列概念 | 三定义互相引用、拆不掉，不是并列关系 |

### 关联概念（近界 · 辨析）

- **需要 → 期望 → 需求**：三个量级；需求 = 需要或期望 × 呈现方式。
- **需求 ≠ 目标**：目标回答"为什么做"，需求回答"做成什么样"。
- **设计（阶段）vs 开发（阶段）vs 设计开发（完整过程）**：别拆成"设计+开发"两件事。
- **需求开发（8.2）vs 设计开发（8.3）**：看"特性是否被规定"。
- **符合性 → 质量 → 等级**：三个近亲，回答三个不同的问题。
- **固有特性 vs 赋予特性**：价格/品牌/交付时间是赋予特性，不算质量。
- **验证 / 确认（第7章预告）**：验证对照"规定需求"，确认对照"预期用途"。

### 核心原理

1. **三形态并列原理**：明示、通常隐含、必须履行三种形态都是需求、没有主次——隐含需求漏了是缺陷，不是"没写文档所以不算"。
2. **两维度交叉原理**：需要/期望是内容，明示/隐含/必须履行是呈现方式；两个维度交叉才是需求的完整图景。
3. **需求 ≠ 目标原理**：目标定方向、可激励人；需求定规格、必须可判定。
4. **可转化四闸门原理**：完整、无歧义、不冲突、隐含需求已识别——起点没收好，转化的是错误需求，终点越完美偏离越远。
5. **起点之前是研究原理**：需求通常是研究的结果；点子 →（研究）→ 确定的需求 → 设计开发，链条不能跳。
6. **更详细是唯一判定标准原理**：设计开发 = 需求变详细；输入输出同样详细 = 没发生设计开发。
7. **更详细 ≠ 更窄原理**：输入的"低温设备"一句，输出是几十条规格——"更详细"是信息量的扩张。
8. **递归原理**：一个项目可有多个设计开发阶段，每级执行同一个 3.4.8，直到需求足以支撑实现与验证。
9. **终点 = 可实现原理**：可验证是循环倒置（验证的参照 = 规定需求 = 设计开发的输出）；"可实现"是定义内部唯一的自然终止条件。
10. **八方案原理**：技术/物料采购/制造/测试/交付/部署/操作/运维——终点由最后一个配齐的方案决定，不由第一个完成的技术方案决定；只到技术方案，下游连环空转。
11. **三层次可实现原理**：原理可实现（纸面）→ 方案可实现（设计开发终点）→ 事实可实现（验证确认裁决）；设计开发交付的是声明，不是事实。
12. **需求开发/设计开发同构原理**：都是需求转化，是同一认知活动的不同阶段；实用判据 = 特性是否被规定。
13. **质量 = 程度非除法原理**：满足是一次判定，不是一道除法——两边不同质，除不了。
14. **程度三步原理**：确定特性值 → 与需求比对 → 认定满足程度；单项是二元、整体是程度；接收准则提前写好，程度才可认定。
15. **等级 ≠ 质量原理**：一个回答"按哪套需求分类"，一个回答"满足到什么程度"；等级高 ≠ 质量好。
16. **关键特性不能摊平原理**：8.3.5 d 关键特性一票否决；加权平均把安全失分摊平 = "精确的错误"。
17. **质量 vs 进度 = 需求内讧原理**：质量不是时间的函数；进度本身就是一种需求——冲突是同一份需求集合内部打架。
18. **四步解法原理**：判真伪 → 用需求谈判（走正式变更）→ 分清可妥协与不可妥协 → 度量环节可缩不可砍。
19. **剪裁 = 变更原理**：与相关方一起剪裁（排序、留痕、挂账）才是变更；单方面砍叫偷换；剪裁是暂存不是销毁。
20. **基座三角原理**：定标尺 → 造标尺 → 读标尺；三定义互相引用、角色不可替代；需求+质量是元概念，设计开发是架在中间的桥。
21. **基座推出方法原理**：V 模型为什么是 V、IPD 为什么有 TR/DCP、为什么需求要追溯矩阵、为什么变更要控制——都能从三角推出来。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "质量 = 做得比人强、指标压过竞品。"（× 等级 ≠ 质量）
2. "设计开发 = 做出技术方案，后面的测试、采购、生产、交付自然会有。"（× 八方案，止于可实现）
3. "需求 = 用户说出来的。"（× 三形态并列，隐含/强制漏掉是缺陷）
4. "客户没说要，我们就不用做。"（× 隐含需求是需求）
5. "需求 = 目标，'成为精度第一'就是需求。"（× 目标定方向，需求定规格）
6. "技术方案完成了，设计开发就结束了。"（× 止于可实现）
7. "可验证了，设计开发就完成了。"（× 循环倒置）
8. "设计开发 = 画图 / 创意活动。"（× 是需求转化）
9. "更详细 = 更窄，做细就是把范围做小。"（× 信息量扩张）
10. "特性越多、越高，质量越好。"（× 过度设计）
11. "质量能打分，85 分很精确。"（× 程度是形容词；关键特性不能摊平）
12. "等级高 = 质量好，高档货质量就好。"（× 等级 ≠ 质量）
13. "多给我三个月，质量就自动变好。"（× 质量不是时间的函数）
14. "质量 vs 进度，只能二选一。"（× 需求集合内部打架）
15. "先交付，验证确认后补。"（× 可缩不可砍）
16. "口头'差不多就行'改需求没问题。"（× 需求被悄悄偷换）
17. "和客户一起砍需求 = 降低质量。"（× 一起剪裁是变更，单方面砍才叫偷换）

### 本章判据（六把尺子）

1. **起点判据**：需求"可转化"——完整、无歧义、不冲突、隐含需求已识别；起点没收好，转化的是错误需求。
2. **终点判据**：设计开发止于"可实现"——"还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束。" 终点由最后一个配齐的方案决定。
3. **质量是"吻合度"不是"除法"**：特性超出需求范围 = 过度设计，只加成本不加质量；砍过度设计是唯一既省时间又不伤质量的操作。
4. **质量 vs 进度 = 需求集合内部打架**：判真伪 → 走正式变更 → 验证可缩不可砍；正道是与相关方一起剪裁需求（排序、留痕、挂账）。
5. **等级 ≠ 质量 ≠ 符合性**：一个回答"按哪套需求分类"，一个回答"满足到什么程度"，一个回答"满足了吗"。
6. **基座三角**：定标尺 → 造标尺 → 读标尺；需求与质量是元概念，设计开发是架在中间的桥。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"需求"（三形态一句话）并各举一例。
2. 能辨析 需要 / 期望 / 需求 三个量级（内容 × 呈现方式两维度交叉）。
3. 能辨析 需求 ≠ 目标（为什么做 vs 做成什么样）。
4. 能说出"可转化"四道闸门（完整/无歧义/不冲突/隐含已识别）及最易被忽略的一条。
5. 能说出"起点之前是研究"链条（点子 → 研究 → 确定的需求 → 设计开发）。
6. 能定义"设计开发"并拆出四个构件（客体/需求/转换/更详细）。
7. 能辨析 设计 / 开发 / 设计开发 三词。
8. 能解释"更详细"是唯一判定标准及"更详细 ≠ 更窄"。
9. 能说出设计开发在项目内的递归（概念 → 系统 → 部件 → 工艺）。
10. 能列出八个方案及各自的条款落点/下游环节。
11. 能说出三层"可实现"（原理/方案/事实）各由谁给、设计开发交付的是声明不是事实。
12. 能辨析 需求开发（8.2）vs 设计开发（8.3）——看"特性是否被规定"。
13. 能定义"质量"并拆出三个关键词（固有/满足/程度）。
14. 能辨析 符合性 / 质量 / 等级 三近亲（各回答什么问题）。
15. 能说出"程度三步"（确定特性值 → 比对 → 认定）与接收准则的作用。
16. 能定义"过度设计"并解释它为何只加成本不加质量。
17. 能画出"基座三角"（定标尺 → 造标尺 → 读标尺）并说出两个承重构件（客体/特性）。

### 原理层（应能解释为什么）

1. 能解释为什么三种形态并列、隐含需求漏掉是缺陷。
2. 能解释为什么"把三个词糊成一个 = 把最重要的一半需求扔出视野"。
3. 能解释为什么"目标可以激励人，需求必须可判定"。
4. 能解释为什么起点没收好 → 终点越完美偏离越远。
5. 能解释为什么设计开发不始于点子、而始于被研究确认过的需求。
6. 能解释为什么"输入输出同样详细 = 没发生设计开发"。
7. 能解释为什么"可验证"不能当设计开发终点（循环倒置 + 区分不了完成与未完成）。
8. 能解释为什么终点由"最后一个配齐的方案"决定、只到技术方案会连环空转。
9. 能解释为什么设计开发交付的是声明不是事实（三层次可实现）。
10. 能解释"特性是否被规定"为什么能划开需求开发与设计开发。
11. 能解释为什么质量是"认定"不是"计算"、满足是判定不是除法。
12. 能解释单项二元 / 整体程度的不对称及接收准则的作用。
13. 能解释为什么等级高 ≠ 质量好（高档车可以是差质量）。
14. 能解释为什么关键特性不能被摊平、"精确的错误"错在哪。
15. 能解释为什么质量 vs 进度是需求集合内部打架、不是两个系统拔河。
16. 能解释为什么"与相关方一起剪裁 = 变更、单方面砍 = 偷换"，剪下来的需求是挂账不是消失。
17. 能解释为什么基座三角互相引用拆不掉、需求+质量是元概念而设计开发是桥。
18. 能解释为什么每个主流方法（V 模型/IPD/追溯矩阵/变更控制）都能从三角推出"为什么长这样"。

### 判据层（应会用）

1. **起点判据**：四闸门逐条打勾；最弱一条要能说出会造成什么后果。
2. **终点判据**："还有哪个环节会在执行时反问'这到底怎么做'？"——有，设计开发就没结束。
3. **质量吻合度**：特性超出需求范围 = 过度设计，只加成本不加质量。
4. **进度判据**：质量 vs 进度 = 需求集合内部打架；判真伪 → 正式变更 → 验证可缩不可砍。
5. **等级判据**：等级 ≠ 质量 ≠ 符合性，各回答一个不同的问题。
6. **三角判据**：定标尺 → 造标尺 → 读标尺；三定义互相引用、拆不掉。

## 第 4 步 · 辑误成饵：陷阱清单（病 → 药 → 判据）+ 网搜印证

### 陷阱靶子清单

**A 类 · 书的"病"直接成靶（17 条）**

| # | 病（常识断言） | 药（反转） | 判据（可操作标准） | 强度 |

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 质量三关键词（固有/满足/程度）+ 等级 ≠ 质量 + 过度设计判据 | 1/10/11/12/18/20 + N1/N2/N6 | 脱口而出："质量 = 固有特性满足需求的程度；超出需求范围 = 过度设计，只加成本不加质量" |
| ★2 | 设计开发四构件 + 止于可实现 + 八方案 | 2/6/7/8/9/19 + N4 | "还有哪个环节会在执行时反问'这到底怎么做'？"成为口头禅 |
| ★3 | 需求三形态 + 可转化四闸门 + 起点之前是研究 | 3/4/5/17 + N3 | 报出四闸门；"客户没说要 ≠ 不用做"脱口而出 |
| ★4 | 质量 vs 进度 = 需求内讧 + 四步解法 + 剪裁即变更 | 13/14/15/16 + N5 | "进度本身是需求；与相关方一起剪裁才叫变更，单方面砍叫偷换" |
| ★5 | 程度三步 + 接收准则 + 关键特性不摊平 | 10/11 + N6 | "没有接收准则，程度只能感觉、不能认定" |

### 纠错红线十条

1. **先表态后翻案**：先让学员说出判断（"质量绝对没问题，你信吗"），再翻，不让结论先入。
2. **反转精确不造新误解**：过度设计反转不过头——只砍"超出需求范围"的，不否定精益求精；质量 vs 进度反转不说"进度不重要"。
3. **判据配机制**：每条反转都要有"为什么"（机制）和"怎么当场验证"（判据）。
4. **归责到可对照动作**：不归咎"小林不行"，落到"研究做没做 / 接收准则写没写 / 变更走没走正式"这类可查动作。
5. **教机制不教断言**：教"为什么可验证是循环倒置"，不教"可验证是错的"。
6. **先立尺子再翻案**：先给判据（起点/终点/质量），再翻冰链 M3 案例。
7. **拉开强度层次**：★★★ 常识（质量=指标 / 技术方案完=完成 / 先交付后补）重点翻，★★ 次之。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"。
9. **单一权威不另立标准**：判据引用书六把尺子，不发明新尺子。
10. **网搜当佐证**：N1~N6 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给部门最近一次交付做基座体检

> 目标：用六把尺子检查"要什么 → 做成什么样 → 做得好不好"链条上的缺口，产出三件可执行改进。
> 场景：回部门落地。时长：2 小时内完成一次体检，两周后复查一至两项。

1. **查起点（尺1 · 起点判据）**：最近一次交付的需求规格，四闸门（完整/无歧义/不冲突/隐含已识别）逐条打勾；最弱的一条是哪条？隐含需求当初靠什么挖到（调研/访谈/竞品分析）？产出：四格打勾表 + 最弱一条一句。
2. **查终点（尺2 · 终点判据）**：把下游环节列一遍（采购/生产/测试/交付/部署/操作/运维）——"还有哪个环节会在执行时反问'这到底怎么做'？"答不上的，就是没配齐的方案。产出：缺的方案清单。
3. **查接收准则（尺3 · 质量吻合度）**：测试方案里有提前写好的接收准则吗（判什么 / 用什么测 / 测多久 / 结论记在哪）？没有 → "质量好"只能感觉、不能认定。产出：一行结论。
4. **查过度设计（尺3 延伸）**：有没有特性超出需求范围、只加成本不加质量？砍掉它，省时间且不伤质量。产出：一行过度设计清单。
5. **查进度冲突（尺4 · 进度判据）**：最近一次"质量 vs 进度"冲突怎么解决的？先判真伪了吗？走正式变更了吗？和谁一起剪裁的？剪下来的需求挂账了吗？产出：三问答案。
6. **查三概念（尺5 · 等级判据）**：你们说"质量好 / 等级高 / 符合要求"时，是三个概念还是一个？有没有把"降需求"说成"降质量"？产出：一行词汇体检。

**卡住怎么判断**：任一尺子打不出勾，就是该尺子说的缺口——不用全打完，找到第一个"否"就能开工。产出三件最该改进事项（每条 = 一个可检查动作）。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 需求规格四闸门全过？ | □ | 起点没收好，终点越完美偏离越远 |
| "还有哪个环节反问'这到底怎么做'？" | □ | 设计开发没结束，下游连环空转 |
| 测试方案有接收准则？ | □ | 程度只能"感觉"，不能"认定" |
| 没有超出需求范围的特性？ | □ | 那是过度设计，只加成本不加质量 |
| 进度冲突走了正式变更？ | □ | 口头改需求，需求被悄悄偷换 |
| "质量/等级/符合性"三概念分清？ | □ | 词汇病——把降需求说成降质量 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身）**
"小林把参数对比表拍在桌上：温度精度 ±0.3℃（竞品 ±0.5℃）、保温 72 小时（竞品 48 小时）、还轻 2 公斤——他说『质量绝对没问题』。质量到底是什么？用定义里的三个关键词说清：他比出来的这一堆，是质量的哪部分、哪部分不是？"
追问：① 他其实说错了哪个字——想说『质量高』还是『等级高』？"高档车可以是差质量"为什么成立？② 需求只要 ±0.5℃，他把精度做到 ±0.3℃——超出需求范围的那一段，是质量加分还是过度设计？③ 反身：你们最近一次说『质量好』，是拿参数和竞品比，还是拿特性和需求比？比的时候有接收准则吗？

**Q2（见树见林② · 概念关系）**
"请给出 需求、设计开发、质量 三者的关系（一句口诀：定标尺 → 造标尺 → 读标尺），并解释：为什么三个定义互相引用、拆不掉？"
追问：① 客体、特性两个"承重构件"为什么是三角内部的横梁——抽掉任何一个，哪个定义悬空？② 三者的层级完全平级吗？"基座"的最底层是哪两个元概念，设计开发站在什么位置？③ 反身：你们项目里"要什么 / 做成什么样 / 做得好不好"三个问题分别由谁回答？三个答案互相引用吗？

**Q3（起点判据 · 需求）**
"设计开发从哪一刻开始？『需求 = 用户说出来的』——对吗？"
追问：① 明示、通常隐含、必须履行三种形态是并列的——隐含需求漏了为什么是缺陷、不是『没写文档所以不算』？② 需要、期望、需求三个量级怎么分？『我们要成为冷链行业的精度第一』是需求吗——需求和目标差在哪？③ "可转化"四道闸门，哪个最容易被忽略？起点没收好，为什么是『终点越完美，偏离越远』？

**Q4（终点判据 · 设计开发）**
"设计开发什么时候算结束？为什么不能拿『可验证』当终点？"
追问：① "可验证"为什么是循环倒置——验证的参照（规定需求）是谁的输出？② 技术方案做完了为什么不算结束？"还有哪个环节会在执行时反问『这到底怎么做』"——八个方案还缺几个？③ 三层"可实现"（原理/方案/事实）各是谁给的？设计开发交付的是事实还是声明？

**Q5（质量 vs 进度 · 机制）**
"『多给我三个月，质量就自动变好』——对吗？『质量 vs 进度』的冲突，本质是什么？"
追问：① 质量为什么不是时间的函数？『进度本身是一种需求』——那冲突是谁和谁在打？② 四步解法：第一步判真伪、第二步用需求谈判不用质量谈判、第三步分清可妥协与不可妥协、第四步度量可缩不可砍——每一步在防什么？③ 砍掉超出需求范围的『过度设计』，为什么是唯一既省时间又不伤质量的操作？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 起点判据）**
"小林立项时跳过研究，从『把精度做上去就能赢』的点子直接开工——七周后方案被推倒，销售小冯问『你立项前做过市场调研吗』。起点判据在哪一道闸门上放他过去的？"
追问：① 点子、研究、需求、设计开发的链条，哪一环断了？"合同里没写这条"为什么不是理由？② 客户自己都说不出口的需求——小冯拜访的三个疾控中心开口就问『能不能塞进疫苗运输车』，这个隐含需求怎么才会被主动挖到？③ 反身：你们最近一次大返工，是起点问题（需求没收好）还是终点问题（方案没做透）？当时的调研受控存档了吗？

**Q7（判据运用 · 终点判据）**
"M3 技术方案很漂亮：双压缩机冗余、±0.3℃ 恒温控制、全数字监控。但采购问『按什么型号采、合格准则是什么』、车间问『装配工艺文件呢』、测试问『判据是什么』、交付问『怎么装怎么培训』——七个『没有』。你用什么一句话当场判出『设计开发没结束』？"
追问：① 判据那句口诀怎么用："还有哪个环节会在执行时反问『这到底怎么做』"？② 八个方案对软件长什么样——恒信合同审批系统的"八方案"换成哪几个名字（数据/接口/部署/安全……）？③ 反身：你们宣布"设计完成"的那一刻，测试方案、交付方案里写好了接收准则吗？

**Q8（判据运用 · 质量程度 · 打分）**
"小赵给 M3 打了 85 分：温度控制 92、保温 88、外壳做工 90、重量 70，加权平均。老周问她：『你把断电告警放进去了吗？』——质量能打分吗？这个 85 分错在哪？"
追问：① "程度"是认定出来的不是计算出来的——接收准则（提前写好的标尺）缺了，程度为什么只能"感觉"不能"认定"？② 单项是二元（符合/不符合）、整体是程度（差/好/优秀）——关键特性为什么不能被平均分摊平？断电告警是平均分里的一项吗？③ 老周说"这 85 分是精确的错误"——什么前提下分数才不是假的（需求完整/特性规定完整/证据可靠）？

**Q9（判据运用 · 质量 vs 进度）**
"进度不够，小林去找刘主任：砍掉『箱门单手打开』，刘主任说『不行，护士经常一手抱孩子一手开箱』；降『App 实时推送』为两小时同步，刘主任同意但『断电告警必须保留』；砍『重量轻 2 公斤』，刘主任说『这条本来就是你们销售自己吹出来的』。三十分钟需求重排——这和单方面砍需求差在哪？"
追问：① 为什么和顾客一起剪裁才叫变更、单方面砍叫偷换？需求的所有权在谁手里？② 口头『差不多就行』为什么是最危险的变更形式——需求被悄悄偷换，验证和确认在跟一个什么靶子打？③ "进度冲突是隐含需求的显影剂"——平时问『你还有什么要求』他答『没有了』，今天为什么十分钟全说了？剪下来的需求是"挂账"不是"消失"，挂账用来干嘛？
