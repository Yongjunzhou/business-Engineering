## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：需求的"标尺"从哪来——需求工程、需求开发、需求管理是什么关系？为什么"加强需求管理"救不了恒信？规定需求为什么是验证的参照？ConOps 在整条链的什么位置？

### 核心概念

1. **需求工程**（requirements engineering）：需求开发 + 需求管理（总称，两大子过程并列）。
2. **需求开发**（requirements development）：把需要与期望**转化**为规定需求——获取、分析、规格、验证。管"生"。
3. **需求管理**（requirements management）：对规定需求进行**基线化治理**——基线、变更、追溯、状态度量。管"养"。
4. **规定需求**（specified requirement）：被明示的、以成文信息记录的需求——**验证的参照**。
5. **运行概念 ConOps**（concept of operations）：系统怎么被用的叙事文档（IEEE 1362）——分析之后、规格之前。
6. **需求管理计划 RMP**（requirements management plan）：项目级"怎么管需求"的执行计划——程序文件的项目版。

### 对立概念

| 核心概念 | 对立面 | 问什么 |
|---|---|---|
| 需求开发 | 需求管理 | 创造性 vs 控制性；造血 vs 防腐——并列不是包含 |
| 规定需求 | 口头明示 | 说了不等于规定——成文 + 具体 + 可验证 |
| ConOps | SRS | 讲"故事" vs 讲"条款"；问题域 vs 解空间 |
| 需求工程 | 需求管理 | 总称 vs 子过程——需求工程 ≠ 需求管理 |

### 关联概念（近界 · 辨析）

- **需要 → 期望 → 需求 → 规定需求**：四个量级阶梯，混用的代价是需求工程里最贵的一种模糊。
- **需求开发 × 设计开发（第3章）**：都是需求转化；看"特性是否被规定"划开；ch4"分解"是第6章同构动作。
- **ConOps × SRS × 设计**：问题域 → 解空间 → 设计；ConOps 是那道桥。
- **验证 × 确认（第7章展开）**：对照规定需求 vs 用户意图。
- **基线 × 版本（第12章展开）**：版本是刻度、基线是参照。
- **程序文件 × RMP**：组织级"怎么管需求" vs 项目级执行计划。
- **需求管理 × 配置管理（第12章）**：需求基线是配置信息的一种。

### 核心原理

1. **并列原理**：需求工程 = 需求开发 + 需求管理，并列不是包含（CMMI REQM/RD 并列、IEEE 29148 同样）。
2. **生养原理**：开发管"生"、管理管"养"——需求是开发出来的，不是管出来的。
3. **清源修渠原理**：先清源（开发）、再修渠（管理），顺序不能反；管理再严，来源没摸清、分析没做透，一样出烂需求。
4. **欠账二分原理**：开发欠账 = 源头脏（再好的管理只是把脏水存进干净罐子）；管理欠账 = 过程乱（再好的开发被无序变更慢慢腐蚀）。
5. **循环原理**：需求开发四活动是循环不是直线——需求天然是渐进的，每一步都可能推翻前一步的假设。
6. **无来源不入池原理**：获取的判据 = 每条需求有没有来源——"无来源需求不得入需求池"。
7. **规定需求枢纽原理**：规定需求是验证的参照——没有它，验证（verification）无从谈起。
8. **六性互撑原理**：六性不是六个并列形容词——无歧义是可验证前提、可验证是规定需求门槛、可追溯是影响分析地图、有优先级是剪裁操作基础。
9. **可追溯最贵原理**：六性里最常被牺牲的是"可追溯"——不立刻显形，需求变更时才显形。
10. **双关分离原理**：验证对照规定需求、确认对照用户意图——"写对了吗" vs "是要的吗"，必须分开。
11. **隐含需求原理**：隐含需求不会自己开口——需主动挖、显性化、写进规格、变成规定需求；验证够不着它、只有确认兜得住。
12. **顺序原理**：ConOps 在分析之后、规格之前——先讲清系统怎么被用，才谈得上必须做什么。
13. **可画图原理**：让不熟悉系统的人读完 ConOps 能画出流程图——画得出来，ConOps 合格；画不出来，故事没讲清。
14. **闭环原理**：CR → 影响分析 → CCB → 实施 → 再验证 → 关闭；任何一环断，变更就成了"查无实据"的暗改。
15. **可判定原理**：变更控制每一步都要可判定——"以什么标准"必须写死，否则流程就是摆设。
16. **基线分界原理**：基线是分界线——线左是开发的产物（还在流动）、线右进入管理（一切改动走变更控制）；从基线出发一切变更可描述，离开基线一切变化不可言说。
17. **基线追溯一体原理**：基线给"变"参照原点、追溯给"变"影响地图——一体两面，缺一失效。
18. **铰链原理**：需求开发与管理的接口咬合在"批准 → 基线"处——批准前需求流动（开发负责）、批准后一切变更走 CR（管理负责）；铰链不咬合，需求在中间断层。
19. **成本原理**：同一缺陷需求阶段修复成本为 1、发布后 30~70 倍——需求工程投入是给下游省十倍百倍返工钱。
20. **追溯链原理**：没有文档的环节，就是不可追溯的环节——裁掉文档不是省事，是把追溯链砍断。
21. **RMP 项目化原理**：RMP 是程序文件的项目版——把"组织怎么管需求"翻译成"这个项目怎么管需求"。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "需求乱，是因为管理没跟上；把需求管理做好，需求就稳了。"（× 需求工程 = 开发 + 管理；需求是开发出来的）
2. "需求管理包含需求开发，管好需求自然就开发好了。"（× 并列不是包含）
3. "客户说了'页面要快一点'，这就是需求。"（× 是明示需求，不是规定需求——没成文、不可验证）
4. "ConOps 是给运营部门看的故事，跟开发没关系。"（× 是问题域到解空间的桥；跳过它 SRS 条款悬空）
5. "需求变更多，说明需求管理没做好。"（× 先分清"需求变了"还是"当初没说清楚"——后者是开发欠账）
6. "验证和确认是一回事，都是确认需求没问题。"（× 验证对照规定需求、确认对照用户意图）
7. "版本文件名改一改，就是需求管理。"（× 那是版本不是基线；没有基线，变更不可描述）
8. "需求分析就是开会讨论一下需求。"（× 分析有四项具体动作，每项有可检验产出）
9. "写需求文档就是抄用户的话。"（× 那是获取的原始记录；规格说明要把分析结果写成可验证条文）
10. "SRS 六章里'验证方法'那章最容易被砍。"（× 那正是"规定需求可验证"的落点；没有验收标准，需求退化成愿望）
11. "跳过 ConOps 直接写 SRS，也能把需求写全。"（× 三百条 SRS 里有一半需要改写；顺序反了）
12. "需求文档越全越好，写十几份才算工程。"（× 骨架五份不可省，其余按项目规模裁剪）
13. "没有文档的环节，口头说说就够了。"（× 没有文档的环节，就是不可追溯的环节）
14. "变更是坏事，需求应该一步到位。"（× 需求天然是渐进的；变更控制不是阻止变更，是让变更留下痕迹）
15. "需求变更少了，说明需求管理做好了。"（× 变更失控率降七成不是需求变少，是每次变更都留下了痕迹）
16. "管理做严了，烂需求也能被过滤掉。"（× 开发欠账管理管不了——管理管的是已经说清楚的需求）

### 本章判据（六把尺子）

1. **并列判据**：需求工程 = 需求开发 + 需求管理（并列）——开发管"生"（创造），管理管"养"（控制）。
2. **规定需求判据**：规定需求 = 验证的参照——被明示的、成文的需求；不能设计测试证明的，还不是规定需求。
3. **ConOps 位置判据**：ConOps 在分析之后、规格之前——先讲清系统怎么被用（故事），才谈得上必须做什么（条款）。
4. **验证/确认判据**：验证对照规定需求，确认对照用户意图——"写对了吗" vs "是要的吗"，必须分开。
5. **变更三铁律**：无 CR 不得变更，不分析不得上会，验证通过方可关闭。
6. **骨架五份判据**：SRS、需求池、RTM、评审报告、基线——五份缺一份，需求工程链就有断点。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"需求工程"并说出两大子过程（并列不是包含）。
2. 能定义"需求开发"（获取/分析/规格/验证四活动）并说出它管"生"。
3. 能定义"需求管理"（基线/变更/追溯/状态度量四活动）并说出它管"养"。
4. 能辨析 需求工程 / 需求开发 / 需求管理 三者关系（总称 ⊃ 两并列子过程；管理不包含开发）。
5. 能定义"规定需求"并给出可操作判据（能设计测试证明）。
6. 能辨析 需要 / 期望 / 需求 / 规定需求 四个量级。
7. 能定义"运行概念 ConOps"并说出它的位置（分析之后、规格之前）。
8. 能辨析 ConOps vs SRS（故事 vs 条款；问题域 vs 解空间）。
9. 能说出需求开发四活动各自做什么、典型输出。
10. 能说出需求管理四活动各自解决什么问题。
11. 能画出变更控制闭环（CR → 影响分析 → CCB → 实施 → 再验证 → 关闭）。
12. 能定义"基线"（被批准冻结的参照）并辨析 版本 ≠ 基线。
13. 能定义"需求管理计划 RMP"并辨析 程序文件 vs RMP。
14. 能背出需求质量六性并说出每性的互撑关系。
15. 能说出骨架五份文档及各自不可省的职责。

### 原理层（应能解释为什么）

1. 能解释为什么"需求管理包含需求开发"是错的（把创造包进控制，模糊"需求是开发出来的"）。
2. 能解释为什么先清源（开发）再修渠（管理）、顺序不能反。
3. 能解释开发欠账 vs 管理欠账后果为何不同（源头脏 vs 过程乱）。
4. 能解释为什么四活动是循环不是直线（需求天然渐进，每一步可能推翻前一步的假设）。
5. 能解释为什么"无来源需求不得入需求池"。
6. 能解释为什么规定需求是验证的参照（没有它验证无从谈起）。
7. 能解释为什么验证和确认必须分开（写得很正确但完全不是用户要的 = 需求开发最常见的失败）。
8. 能解释为什么隐含需求不会自己开口、为什么只有确认兜得住（验证对照规定需求，够不着没写出来的）。
9. 能解释为什么 ConOps 在分析之后、规格之前（跳过 = 从问题域直接跳到解空间，桥没了）。
10. 能解释为什么"先写条款后补故事"顺序反了（需求规格的问题往往要到 ConOps 里才看得出来）。
11. 能解释变更控制为什么是需求管理的核心战场（大多数团队的需求管理问题都出在这里）。
12. 能解释为什么变更控制每一步必须可判定（"以什么标准"必须写死，否则流程是摆设）。
13. 能解释为什么基线是分界线（从基线出发一切变更可描述，离开基线一切变化不可言说）。
14. 能解释基线和追溯为什么一体两面（参照原点 + 影响地图）。
15. 能解释六性里为什么"可追溯"最常被牺牲（不立刻显形，变更时才显形）。
16. 能解释为什么骨架五份不可省（裁掉文档不是省事，是把追溯链砍断）。
17. 能解释"批准 → 基线"为什么是整条需求工程的铰链。
18. 能解释需求阶段修复成本 1、发布后 30~70 倍的经济理由。

### 判据层（应会用）

1. **并列判据**：需求工程 = 开发 + 管理；看到"广义的需求管理包含开发"能当场指出错。
2. **规定需求判据**：能设计测试证明 → 规定需求；只能"感觉" → 还不是。
3. **ConOps 位置判据**：先讲清系统怎么被用，才谈得上必须做什么。
4. **验证/确认判据**：对照规定需求（写对了吗）vs 对照用户意图（是要的吗）。
5. **变更三铁律**：无 CR 不得变更；不分析不得上会；验证通过方可关闭。
6. **骨架五份判据**：SRS、需求池、RTM、评审报告、基线——任缺一份，需求工程链有断点。

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 需求工程 = 开发 + 管理（并列）+ 生养 + 清源修渠 | 1/2/16/18 + N2/N3 | 脱口而出："需求工程 = 需求开发 + 需求管理，并列不是包含；需求是开发出来的，不是管出来的；先清源、再修渠" |
| ★2 | 规定需求三要件（成文 + 具体 + 可验证）+ 验证参照 | 3/11/19 + N5 | "能设计测试证明才是规定需求；客户说了不等于规定" |
| ★3 | 验证 vs 确认双参照 | 5 + N5 | "验证对照规定需求（写对了吗），确认对照用户意图（是要的吗）" |
| ★4 | 基线 vs 版本 + 变更闭环三铁律 | 6/14/15 | "版本是刻度、基线是参照；无 CR 不得变更，不分析不得上会，验证通过方可关闭" |
| ★5 | 骨架五份 + 追溯链 + 可追溯最贵 | 12/13 + N1 | "没有文档的环节，就是不可追溯的环节；裁掉文档不是省事，是把追溯链砍断" |
| ★6 | ConOps 位置（分析之后、规格之前） | 9/10 + N6 | "ConOps 讲'故事'、SRS 讲'条款'——先讲清怎么被用，才谈得上必须做什么" |
| ★7 | 隐含需求主动挖 + 获取判据 | 17/20 + N4/N7 | "隐含需求不会自己开口；无来源需求不得入需求池" |

### 纠错红线十条

1. **先表态后翻案**：先让学员说出判断（"加强需求管理，你信吗"），再翻，不让结论先入。
2. **反转精确不造新误解**：反转不说"管理不重要"——管理管"养"也必要，只是管不了"生"的欠账；不说"文档越多越好"——是"骨架五份不可省"，其余按规模裁剪。
3. **判据配机制**：每条反转都要有"为什么"（机制）和"怎么当场验证"（判据）。
4. **归责到可对照动作**：不归咎"Ada 没管好"，落到"调研做没做 / 分析四动作做没做 / 基线建没建 / 变更走没走 CR"这类可查动作。
5. **教机制不教断言**：教"为什么并列不是包含、为什么规定需求是验证的参照"，不教"需求管理是错的"。
6. **先立尺子再翻案**：先给判据（并列 / 规定需求 / ConOps 位置 / 验证确认 / 三铁律 / 骨架五份），再翻恒信案例。
7. **拉开强度层次**：★★★ 常识（加强需求管理 / 客户说了就是需求 / 验证确认一回事 / 版本文件名=管理 / 无文档环节口头够了）重点翻，★★ 次之。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"。
9. **单一权威不另立标准**：判据引用书六把尺子，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给部门最近一次需求做"标尺体检"

> 目标：用六把尺子检查"要什么 → 说清了没 → 养得住没"链条上的缺口，产出三件可执行改进。
> 场景：回部门落地。时长：2 小时内完成一次体检，两周后复查一至两项。

1. **查并列（尺1 · 并列判据）**：你们说"需求乱"时，说的是开发欠账（没调研 / 没分析 / 没写可验证规格）还是管理欠账（没基线 / 没变更流程 / 没追溯）？最近一次混乱属于哪张单子？产出：欠账二分一句。
2. **查规定需求（尺2 · 规定需求判据）**：拿一条你们最近的需求——"能设计测试证明吗"？不能 → 那还是明示需求、不是规定需求，验证无从参照。产出：改写后的一条可验证条文。
3. **查 ConOps（尺3 · ConOps 位置判据）**：写 SRS 前，有人写过"系统怎么被用"的叙事吗？让不熟悉系统的人读完，能画出流程图吗？画不出来 → 条款悬空。产出：一句话答案。
4. **查验证确认（尺4 · 验证/确认判据）**：最近一次需求评审，"对照规定需求写对了吗"和"对照用户意图是要的吗"两道关都过了吗？只过一道 → 缺的那道是隐患。产出：一行结论。
5. **查变更闭环（尺5 · 变更三铁律）**：最近一次需求变更——有 CR 吗？影响分析做了吗？CCB 有结论吗？再验证了吗？关闭记录了吗？哪一环断了？产出：断环清单。
6. **查骨架五份（尺6 · 骨架五份判据）**：SRS / 需求池 / RTM / 评审报告 / 基线，缺哪份？缺的那份让哪个问题答不上来？产出：缺口 + 后果。

**卡住怎么判断**：任一尺子打不出勾，就是该尺子说的缺口——不用全打完，找到第一个"否"就能开工。产出三件最该改进事项（每条 = 一个可检查动作）。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 需求开发四活动走完（获取 / 分析 / 规格 / 验证）？ | □ | 开发欠账——管理管不了没说清的需求 |
| 每条需求能设计测试证明？ | □ | 那还不是规定需求，验证无从参照 |
| 写 SRS 前有 ConOps（能画出流程图）？ | □ | 条款悬空——需求规格的问题要到 ConOps 里才看得出来 |
| 需求评审验证 / 确认两道关都过？ | □ | 只验证不确认→写得很对但没人要；只确认不验证→要但没法执行 |
| 变更走闭环五步（CR → 影响分析 → CCB → 再验证 → 关闭）？ | □ | 任何一环断 = 查无实据的暗改 |
| 骨架五份齐（SRS / 需求池 / RTM / 评审报告 / 基线）？ | □ | 裁掉文档 = 砍断追溯链，变更时只能靠记忆和运气 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身）**
"IT 总监拍板：『需求最近改一版崩一版——我们要加强需求管理。』Ada 反问：『需求为什么会变？变之前，需求开发做到位了吗？』需求管理、需求开发、需求工程，这三个词到底是什么关系？『加强需求管理』为什么救不了恒信？"
追问：① "需求管理包含需求开发"错在哪——两个词各是什么性质的活动（创造性 / 控制性）？② 开发管"生"、管理管"养"——"养"能不能替"生"？管理再严，为什么照样出烂需求？③ 反身：你们最近一次说"要加强需求管理"的时候，做的是开发的事，还是管理的事？

**Q2（见树见林② · 概念关系）**
"请给出 需求工程、需求开发、需求管理 三者的关系（一句话），再把 规定需求、ConOps 放进整条链——它们分别在什么位置？"
追问：① "需求工程 ⊃ 需求管理 ⊃ 需求开发"——这个式子对吗？错在哪？② 规定需求是验证的参照——它站在链的哪一段（开发输出、管理输入）？③ ConOps 为什么不能在流程最前、也不能在最后，而偏偏在"分析之后、规格之前"？

**Q3（规定需求 · 概念层）**
"客户说：『页面要快一点。』——这算不算一条需求？『算』和『不算』都对，差在哪？"
追问：① 明示需求 vs 规定需求差在哪三个要件（成文 / 具体 / 可验证）？② "能设计测试证明"为什么是规定需求的判据——"要快一点"为什么测不了？③ 把"重要合同要审批"澄清成"金额 ≥ 500 万或三年期以上"——这是从需求开发的哪一步（获取 / 分析 / 规格）走出来的？

**Q4（ConOps · 概念层）**
"法务负责人翻了两页 SRS 就发问：『审批通过后自动通知相关方——哪个相关方？审批链上有几个人？通知不到会怎样？』三百条条款为什么悬空？ConOps 和 SRS 到底差在哪？"
追问：① ConOps 讲"故事"、SRS 讲"条款"——"故事"比"条款"多了什么（上下文 / 场景 / 异常 / 应急 / 角色）？② 为什么 ConOps 必须在"分析之后、规格之前"——跳过它，等于从什么跳到什么（问题域 → 解空间）？③ "让不熟悉系统的人读完能画出流程图"——你们写完 SRS 后，有人能画出来吗？画不出来说明缺了什么？

**Q5（验证 vs 确认 · 概念层）**
"把需求写得很正确、但完全不是用户要的东西——这是需求开发最常见的失败。怎么防？『验证』和『确认』为什么必须分开？"
追问：① 验证对照规定需求（写对了吗）、确认对照用户意图（是要的吗）——各自问的问题是什么？② 只验证不确认 vs 只确认不验证，各自死于什么？③ 隐含需求为什么只能靠确认兜得住（验证对照规定需求，够不着没写出来的）？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 恒信困境 · 欠账二分）**
"恒信『改一版崩一版』，IT 总监说加强需求管理，Ada 翻了三个月变更记录：一大半『变更』根本不是需求变了，是当初没说清楚。你们最近一次『需求乱』，是需求变了，还是当初没说清楚？"
追问：① 开发欠账 vs 管理欠账怎么分——两张单子各装什么？② "先清源（开发）、再修渠（管理）"——恒信先补什么、后建什么？③ 反身：你们最近一次需求混乱，属于哪张单子？当时做了什么、没做什么？

**Q7（判据运用 · 隐含需求）**
"财务随口一句：『月底要对账，合同 25 号之后签的能不能算到下个月？』——这句话暴露了什么？为什么访谈三次、每次问『还有别的吗』都答『没有了』，这句却出现在随口闲聊里？"
追问：① 隐含需求为什么不会自己开口——它靠什么被挖到（访谈随口一句 / 业务流程惯例 / 前代产品教训）？② 挖出来之后要做什么（显性化 → 写进规格 → 变成规定需求）？不做会怎样（验证够不着，只有确认兜得住）？③ 反身：你们最近一次返工，是不是某条"大家都懂、没人写"的隐含需求漏了？

**Q8（判据运用 · 变更控制闭环）**
"电子签章的合同也要走审批流——这是一条 CR。影响分析经 RTM 反查发现 3 处模块、CCB 通过、实施、再验证、关闭，六份记录。你们团队最近一次需求变更，走到哪一步停的？"
追问：① 闭环五步（CR → 影响分析 → CCB → 再验证 → 关闭）——每一步"必须可判定"的关卡是什么？② 任何一环断了，这条变更就成了什么（查无实据的暗改）？③ 口头改需求为什么是最危险的变更形式（没有凭证）？④ 反身：你们最近一次变更，有 CR 吗？影响分析做了吗？关闭了吗？

**Q9（判据运用 · 骨架五份 + 追溯）**
"合同需求改了六版，版本靠文件名管：『合同需求 v2.doc』『合同需求 最终版 v3.doc』『合同需求 真最终版 v4.doc』。李工承认：『我们不是需求变太多，是根本没建基线。』——文件名和基线差在哪？"
追问：① 版本是刻度、基线是参照——"每一次变更说不清从什么变到什么"，缺的是哪个？② 追溯矩阵 RTM 的终极检验：任取一条需求双向走通（往上游知道从哪来、往下游知道影响谁）——没有基线，RTM 建得起来吗？③ 骨架五份（SRS / 需求池 / RTM / 评审报告 / 基线）缺一份，需求工程链哪里有断点？④ 反身：你们的需求基线在哪？最近一次变更"从什么变到什么"说得清吗？

**Q10（落地生根 · 回部门标尺体检）**
"结合你们部门现状，用六把尺子（并列判据 / 规定需求判据 / ConOps 位置 / 验证确认 / 变更三铁律 / 骨架五份）给最近一次需求做一次标尺体检——给出最该改进的三个事项，每个落到一个动作。"
追问：先做哪把尺子？为什么？两周后回来报告什么？

  - Q8 拦住变更 vs 留痕变更："变更控制 = 阻止变更" vs "变更控制 = 让变更说得清" → 判据 = 无 CR 不得变更（可追溯性）；
  - Q9 轻文档 vs 骨架五份："敏捷要快速响应，文档是浪费" vs "没有文档环节不可追溯" → 判据 = 追溯链（骨架五份不可省）。
