## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：配置是"参数文件"吗？为什么说配置是实体"被记录下来的样子"，而不是参数本身？配置项、配置、配置信息三个词怎么解耦？版本和基线差在哪？"版本顺着流、基线垂直切"是什么意思？为什么"没有基线，变化就不可言说"？变更控制是怎么守住基线的门的？配置管理和第11章的架构决策是什么关系？为什么说决策记录是决策的"基线化"？配置管理到底为了什么——为什么它是"不可逆决策的守护者"？

### 核心概念

1. **配置**（configuration）：实体被记录在配置信息里、相互关联的功能特性与物理特性——实体"被记录下来的样子"。三个隐形过滤器：类别边界（只认功能+物理特性）/ 记录边界（被配置信息记录） / 关联边界（相互关联的整体）。配 + 置 = 组合成形。参数是零件，配置是装好的整机。
2. **版本**（version）：配置项的初始发布，或其后基于完整构建的重新发布——时间轴上的演进刻度，回答"走到第几步"。SemVer 主.次.修订；Rev A/B/C 是更细粒度的修订。
3. **基线**（baseline）：经批准、确立了产品在某一时点的特性、作为全生命周期各项活动参照的配置信息——被批准冻结的参照。三特征：被批准（资格）/ 被冻结（状态）/ 作参照（用途）。

### 对立概念

| 核心概念 | 对立面 | 问什么 |
|---|---|---|
| 配置 | 参数文件（parameter file） | 整机 vs 零件——参数只是记录形态的图纸，形态才是配置；把配置当参数=拿零件清单当整机图纸 |
| 配置 | 实体的全部客观特性 | 特性客观存在，配置是"被管理起来的那部分特性"——三个隐形过滤器切出来的子集 |
| 配置项 | 配置 / 配置信息 | 对象 vs 属性 vs 记录——体检里的"人 / 身高体重 / 体检档案"；三者围着同一产品转但不是同一层 |
| 版本 | 变体（variant） | 时间（先后因果）vs 空间（并存差异）——正交：标准版/医疗加强版是几副样子，v1.0→v2.4 是走到第几步 |
| 版本 | 修订（revision） | 对外整体编号（粗，发布到第几代）vs 内部变更次数（细，改了几次） |
| 版本 | 基线 | 刻度（流动，只描述位置）vs 参照（冻结，制造分界）——里程桩 vs 收费站 |
| 基线 | 流动状态 | 受控 vs 自由——线左版本自由流动，线右任何变化必须走变更控制 |
| 基线 | 快照（snapshot） | 记录 vs "批准 + 冻结 + 参照"三合一——快照是"拍了张照"，基线是"盖章定格" |
| 基线 | 发布（release） | 参照 vs 交付动作——发布的东西通常取自基线，但两者不是一个概念 |
| 配置管理 | 版本管理 | 四大活动 vs 单一活动——缺了基线和变更控制，版本也管不住 |
| 配置管理 | 文档管理 | 代码/固件/硬件/数据/图纸都可立基线 vs 只文档——配置管理不是文档管理 |
| 治理 | 配置管理 | 谁有资格批准基线、谁有资格裁决变更 vs 流程守护——配置管理是治理的一只手 |

### 关联概念（近界 · 辨析）

- **配置 × 配置项 × 配置信息 × 实体**：ISO 10007 三词互相引用形成循环定义；引入不依赖任何配置术语的锚点"实体"来解耦——配置项=被管起来的实体（对象）、配置=实体被记录的形态（属性）、配置信息=记录形态的资料（记录）。
- **配置 × 变与不变的分离**：核心资产只写一遍，变化的部分外置——"改一个参数就要改代码、重编译、重发布"=变与不变没分离的信号。
- **版本 × SemVer × 修订**：主.次.修订三段升级规则；修订（Rev A/B/C）与版本同一个思想的两个粒度。
- **基线 × 需求管理基线（第4章）**：第4章结论"基线是变更的出发原点"；本章把原点推广到所有配置项——固件、硬件、代码、图纸、数据。
- **配置项 × 设计树（第6章）**：枝干=概要定义、叶子=详细定义，两个配置项分别纳入基线——结构改了走重一点的变更、内容改了走轻一点的变更。
- **配置 × 老规矩（第9章）**：章首老规矩"固件升级必须向后兼容已出厂的箱子"；配置管理让老规矩落在具体节点时自带记录。
- **配置管理 × 架构决策（第11章）**：守护者——同构表四行（决策记录↔配置信息 / 不可逆决策识别↔基线冻结 / 推迟决策↔变与不变的分离 / 变更影响分析↔变更控制）。
- **契约链 × 设计链（第6章）× ISO 15288**：需求→方案→实现每对相邻环节都是局部甲乙方（需方-供方协议）；基线=每一级契约的冻结端，版本=交付端。
- **运行/部署配置 × 部署**：同一套代码 + 不同环境参数 = 不同可复现的运行形态——部署的本质就是给某个版本配上某个环境。
- **配置管理 × 治理（第13章）**："谁有资格批准基线、谁有资格裁决变更"超出配置管理本身，是治理的领地。

### 核心原理

1. **近邻混用原理**：参数和配置长得像（都跟"可变的东西"有关）、其实不是一层（参数是单个的值，配置是一整套被记录的形态）——糊在一起用就出事；第1章词汇病的又一次现场。
2. **循环定义解耦原理**：配置/配置项/配置信息三词彼此定义、首尾相连形成环；解耦=往环里引入不依赖任何配置术语的锚点"实体"，让三个概念全部锚定在实体上，彼此不再互引。
3. **组合成形原理**：配置的本质是"组合成形"——con-（共同）+ figurare（塑造成形）；配（配合、匹配）+ 置（放置、安设）。天然"多体"概念，单个孤立的东西没有配置可言。
4. **从多到一原理**：多个组件、多个特性，经过"配"与"置"塑成一个整体形态——即时结果（as-designed / as-built）；这个形态被正式批准冻结成基线——正式结果；最终落地成可运行可交付的实例——交付结果。"从多到一"，就是 configuration 的全部旅程。
5. **三个隐形过滤器原理**：类别边界（只认功能特性+物理特性）/ 记录边界（只有被配置信息规定/记录下来的特性才算配置）/ 关联边界（相互关联的整体不是零散清单）——三个过滤器把"实体的全部特性"和"配置"切开。
6. **记录优先原理**：特性客观存在，配置是"被管理起来的那部分特性"——先有记录，才谈得上"被记录的样子"；没被写下来，就无从核对、无从追溯。
7. **参数零件整机原理**：参数是零件，配置是装好的整机——改一个参数，是让整机的"形态"变了；变了之后，这台箱子采出来的温度记录，含义都跟着变。
8. **版本刻度原理**：版本是把"连续的时间"切成"可指认的格子"的那把刀——变化是连续的，沟通必须离散；版本回答"走到第几步"。
9. **版本四用途原理**：追踪演进 / 回溯 / 并行 / 复现——版本号是沟通的最小公约数。
10. **基线三特征原理**：被批准（资格）+ 被冻结（状态）+ 作参照（用途）——批准是资格、冻结是状态、参照是用途，一个都不能少；从"流动状态"升级为"受控状态"需要一个有权威的动作。
11. **横竖分工原理**：版本与时间同向（尺子上的刻度，只描述位置，不改变时间轴性质）；基线垂直插入时间（横在路中间的闸门，制造分界，改变时间轴性质——无约束→有约束，质变）。版本是流动的，基线是冻结的。
12. **原点原理**：没有基线，变化就不可言说——要描述一个变化必须有"从哪变起"的原点；没有原点，像在茫茫大海上说"我在动"，却没有岸标。
13. **变更控制循环原理**：配置管理的核心循环=冻结 → 变更 → 再冻结；基线建立后任何变化都是"对基线的偏离"，必须走 CR → 影响评估 → CCB 批准 → 实施 → 建立新基线。
14. **四活动循环原理**：配置标识（是什么）→ 配置控制（怎么变）→ 状态记录（现在什么样）→ 配置审计（实物与记录一致吗）——循环咬合：标识立基线、控制管变更、记录写状态、审计回查实物与记录，发现不一致回到标识修正。
15. **三问原理**：配置管理的核心目的=让三个问题在任何时刻都有答案——应该是什么（as-designed）/ 实际是什么（as-built）/ 怎么变成这样的（变更历史）；四个活动就是这三个问题答案的生产线。
16. **变与不变分离原理**：变的东西不写死在不变的东西里——核心资产（代码、逻辑、功能）只写一遍，变化的部分（参数、开关、选项）外置；推迟决策不是不决策，是让"还可能变的东西"保持可替换。
17. **守护原理**：配置管理是架构决策的守护者——识别出不可逆，所以把它冻结成参照，不让它被随手改掉；高不可逆的决策一旦批准就冻结成基线，此后谁要动它必须走变更控制。
18. **尺子变流程原理**：第11章的三问是个人尺子，配置管理的变更控制是组织流程——个人尺子靠自觉，流程靠结构；尺子变成流程，才是守护。
19. **契约链原理**：链上每一对相邻环节都是一组局部的"甲方-乙方"关系；配置管理给契约链每一环提供两个东西——基线是冻结端，版本是交付端；甲方批准基线、乙方交付版本、验收通过又成下一环的基线。
20. **契约每级重复原理**：需求阶段有功能基线、实现阶段有产品基线——基线和版本不是某一级专属，而是每一级都重复出现的通用机制，只因视角不同看起来"属于"不同的人。
21. **技术契约 vs 商务契约原理**：开发链内部的"甲乙方"是技术契约（要求-兑现，管"对不对得上"）；完整的外部甲乙方多一层商务契约（法律合同、付款、责任，管"赔不赔得起"）——机制同构，勿混为一谈。
22. **类型级 vs 实例级原理**：同一设计号的多个实体选一个——类型级（按型号管）不是配置，实例级（按序列号管）是配置；判定标准=选 A 还是选 B，产品的特性/形态变了吗？
23. **三条铁律原理**：产品开发是协作→协作需要共同事实；产品开发是长周期→长周期需要组织记忆；产品要担责→担责需要可答的账——配置管理不是锦上添花，背后是三条绕不过去的铁律。
24. **可剪裁原理**：配置管理是可剪裁的——配置管理的复杂度应该与产品的责任等级匹配；"版本可指认、变更可追溯"这条底线谁也不能省。
25. **精确召回原理**：可追溯=精确召回——批次追溯查得清，只召回受影响的那一批；查不清，只能全量召回——差一个数量级的钱。
26. **变体 × 版本 = 基线原理**：配置提供"内容"、版本提供"位置"、批准提供"资格"——三者齐备才成一个基线；动态主循环=配置变了 → 版本升了 → 批准冻结 → 新基线形成、旧基线退役。
27. **四洞原理**：不是做了版本号就等于做了配置管理——标识/控制/状态记录/审计四大活动一个都不能少；冰链固件事故四个活动四个洞。
28. **冻结非死锁原理**：基线可以变更，但必须走变更控制，改完建立新基线——"冻结"不是"死锁"；随意改基线等于把参照系拆了。
29. **组织资产原理**：配置信息是组织唯一带不走的资产——不随人员流动而消失；人一走，知识就蒸发，配置信息留下来。
30. **保险丝原理**：配置管理是第11章那些不可逆决策的保险丝——决策做对了，靠它守住；决策做错了，靠它让你早发现、早止损。
31. **决策基线化原理**：决策记录六问把一次决策从"当事人脑子里的知识"变成"组织的资产"；配置信息做的是同一件事——让每一条关键信息落在某一份配置信息里，而不是某个人的脑子里。

### 本章判据（十三把尺子）

1. **配置三问**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？三问全"是"，才是配置。参数文件只是记录形态的图纸，形态才是配置。
2. **变与不变的分离**：核心资产只写一遍，变化的部分外置——"改一个参数就要改代码、重编译、重发布"，是变与不变没分离的信号。
3. **配置项/配置/配置信息三分离**：配置项是"被管的那个东西"，配置是"它被记录下来的该有的样子"，配置信息是"记录它的那些资料"——都锚定在"实体"上。
4. **版本是刻度**：版本回答"走到第几步"；一个版本号必须能精确对应到"哪一次完整构建"（文件名不算）。
5. **基线三特征**：被批准（有权威的盖章）+ 被冻结（任何人不能随意改）+ 作参照（全生命周期拿它对照）——三问全"是"才是基线。
6. **版本顺着流、基线垂直切**：版本沿时间轴排开（流动），基线垂直插入切断时间（受控）；把版本当基线，等于把里程桩当收费站。
7. **没有基线，变化就不可言说**：任何变更必须能回答"从什么基线变到什么基线"；答不出，就还没有基线。
8. **变更控制循环**：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线——基线建立后，任何变化必须走这条线。
9. **配置管理四大活动**：配置标识（是什么）→ 配置控制（怎么变）→ 状态记录（现在什么样）→ 配置审计（实物与记录一致吗）——一个都不能少。
10. **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。
11. **配置管理守护架构决策**：决策记录↔配置信息、不可逆决策识别↔基线冻结、推迟决策↔变与不变的分离、变更影响分析↔变更控制——第11章的尺子，第12章给它们配了流程。
12. **契约链**：需求对方案、方案对实现，每一对相邻环节都是局部甲乙方——基线是每一级契约的冻结端，版本是交付端。
13. **配置 × 版本 × 基线三分工**：变体管空间（有几种形态）、版本管时间（走到第几步）、基线管资格（哪一版被盖章）——配置提供"内容"，版本提供"位置"，批准提供"资格"；三者齐备，才成一个基线。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"配置"（实体被记录在配置信息里、相互关联的功能特性与物理特性——实体"被记录下来的样子"）并说出配置三问。
2. 能定义"配置项"（被组织选定、纳入配置管理范围的实体——被管起来的那个东西）。
3. 能定义"配置信息"（记录实体功能与物理特性的资料——记录它的那些资料）。
4. 能说出配置项/配置/配置信息三者关系并解释为什么需要"实体"锚点解耦循环定义。
5. 能说出三个隐形过滤器（类别边界 / 记录边界 / 关联边界）并各举一例。
6. 能解释"参数是零件，配置是装好的整机"，并说出为什么改一个参数会改变整机形态。
7. 能定义"版本"（配置项的初始发布或其后基于完整构建的重新发布——时间轴上的演进刻度）并说出版本四用途（追踪演进/回溯/并行/复现）。
8. 能说出 SemVer 主.次.修订三段各何时升级，并辨析 版本 × 修订（Rev A/B/C）。
9. 能定义"基线"（经批准、确立了产品某一时点特性、作全生命周期参照的配置信息）并说出三特征（被批准/被冻结/作参照）。
10. 能说出三种正式基线（功能/分配/产品）各对应哪一配置环节、回答什么问题。
11. 能解释"版本顺着流、基线垂直切"（里程桩 vs 收费站；横管流动、竖管冻结）。
12. 能定义"变体"（空间维度上的形态差异，与版本正交）并辨析 版本 × 变体 × 修订。
13. 能说出"配置提供内容、版本提供位置、批准提供资格——三者齐备才成基线"及动态主循环（配置变→版本升→批准冻结→新基线形成旧基线退役）。
14. 能说出变更控制循环五步（CR → 影响评估 → CCB → 实施 → 新基线）及各环节解决的问题。
15. 能说出配置管理四大活动（标识/控制/状态记录/审计）各管什么、各解决什么问题。
16. 能说出配置管理核心目的三问（应该是什么/实际是什么/怎么变成这样的）及三个答案各由哪个活动生产。
17. 能定义"契约链"（每对相邻环节都是局部甲乙方；基线=冻结端、版本=交付端）并辨析 技术契约 × 商务契约。
18. 能辨析 类型级 vs 实例级 配置管理粒度（看选谁是否改变特性形态）。
19. 能说出配置管理三条铁律（协作共同事实/长周期组织记忆/担责可答账）与"可剪裁"原则（复杂度与责任等级匹配）。
20. 能说出配置管理守护架构决策的同构表四行（决策记录↔配置信息 / 不可逆识别↔基线冻结 / 推迟决策↔变与不变分离 / 影响分析↔变更控制）。

### 原理层（应能解释为什么）

1. 能解释为什么"配置 ≠ 参数文件"（参数是单个值，配置是一整套被记录的形态；参数只是记录形态的图纸，形态才是配置）。
2. 能解释为什么三个术语会循环定义、为什么"实体"锚点能解耦（三个概念全部锚定在实体上，彼此不再互引）。
3. 能解释为什么配置的本质是"组合成形"（con-共同 + figurare 塑造成形；配+置=搭配并安置成形；天然多体概念）。
4. 能解释三个隐形过滤器怎么把配置从全部特性里切出来（类别/记录/关联三个边界）。
5. 能解释为什么"记录"是配置的前提（没被写下来就无从核对、无从追溯——先有记录才谈得上"被记录的样子"）。
6. 能解释为什么"改一个参数"会让整机形态变、历史记录含义变（案例进展①小林的反问）。
7. 能解释为什么版本是把连续时间切成可指认格子的刀（变化连续、沟通离散；"改过17次其中第9次动了采集算法"没法说）。
8. 能解释为什么基线三特征缺一不可（批准是资格、冻结是状态、参照是用途；从流动升级为受控需要一个有权威的动作）。
9. 能解释为什么"版本顺着流、基线垂直切"（刻度只描述位置不改变时间轴性质；闸门制造分界改变时间轴性质——质变）。
10. 能解释为什么"没有基线，变化就不可言说"（要描述变化必须有"从哪变起"的原点；海上说"我在动"没有岸标）。
11. 能解释为什么变更控制是基线的守护者（基线是变更控制的前提，变更控制是基线的守护者；冻结→变更→再冻结是每次循环的支点）。
12. 能解释为什么四大活动一个都不能少（标识立基线/控制管变更/状态记录写状态/审计回查实物与记录；循环咬合）。
13. 能解释为什么配置管理让三问任何时刻有答案（四个活动=三个问题答案的生产线）。
14. 能解释为什么配置管理是架构决策的守护者（识别不可逆→冻结成基线→此后走变更控制；李工改编号/阿凯直连被拦住）。
15. 能解释为什么"尺子变成流程才是守护"（第11章三问是个人尺子靠自觉，变更控制是组织流程靠结构；一个人扛不住那么多"顺手改动"的记忆）。
16. 能解释为什么契约链每一级都有基线和版本（要求逐级冻结为基线、兑现逐级交付为版本；每级重复的通用机制不是某级专属）。
17. 能解释为什么类型级/实例级判定看"选谁是否改变特性形态"（医疗冷链安全关键行业按单件管理）。
18. 能解释为什么三条铁律让配置管理绕不过去（协作/长周期/担责是产品开发的固有属性）。
19. 能解释为什么配置管理可剪裁、底线不能省（复杂度与责任等级匹配；内部工具 vs 医疗冷链配的流程不该一样，但"版本可指认、变更可追溯"谁也不能省）。
20. 能解释为什么"精确召回"值一个数量级的钱（批次追溯查得清→召回三千台；查不清→召回全部在役五千台）。

### 判据层（应会用）

1. **配置三问**：一个东西拿来，先问三句——被记录了吗？是功能/物理特性吗？和其他特性关联成整体了吗？三句全"是"才是配置；参数文件只是图纸，形态才是配置。
2. **变与不变的分离**：改一个参数就要改代码、重编译、重发布 → 变与不变没分离；把可变部分外置（参数/开关/选项不写死在核心资产里）。
3. **三分离判据**：问"它是谁"→配置项；问"它什么样"→配置；问"拿什么核对"→配置信息——三者都锚定"实体"，不是同一层的东西。
4. **版本是刻度**：这个编号能精确对应到"哪一次完整构建"吗？能——是版本；不能（只有文件名）——它还不算版本。
5. **基线三特征**：被批准了吗？被冻结了吗？全生命周期拿它作参照吗？三问全"是"才是基线。
6. **版本顺着流、基线垂直切**：把版本当基线 = 把里程桩当收费站——版本告诉你走到哪一步，基线告诉你哪一步被盖章。
7. **没有基线不可言说**：任何变更必须能回答"从什么基线变到什么基线"；答不出，就还没有基线。
8. **变更控制循环**：基线建立后，任何变化必须走 CR → 影响评估 → CCB → 实施 → 新基线；"顺手改动"必须先说出来。
9. **四大活动**：标识/控制/状态记录/审计各打一个"有/缺/半吊子"——不是做了版本号就等于做了配置管理。
10. **三问**：应该是什么 / 实际是什么 / 怎么变成这样的——任何时刻都答得出，配置管理就成立了。
11. **守护判据**：高不可逆的决策，一旦批准就冻结成基线，此后谁要动它必须走变更控制。
12. **契约链**：画出需求→方案→实现，每对相邻环节标"基线（冻结端）"与"版本（交付端）"。
13. **三分工**：问"有几种形态"→变体；问"改到第几版"→版本；问"这个版本的这个形态"→基线。

| 21 N5 | "配置管理是大公司负担，小团队敏捷用不上。" | 精益 CM / 让 SCM 敏捷——CM 可剪裁到"够用档"，底线=版本可指认、变更可追溯；不做 CM 的"敏捷"是把查不清的返工留到事后 | 可剪裁（三条铁律） | Softhouse《Lean CM》；StickyMinds《Making SCM Agile》；Wiley《Adapting Configuration Management for Agile Teams: Balancing Sustainability and Speed》 |
| 22 N6 | "可追溯 = 数据里有 ID/条码就行。" | 追溯靠"标识 + 记录 + 审计"的组合，不是加个字段——需求追溯是链不是 ID；ID 只回答"是哪一个"，不回答"怎么变成这样" | 三问判据 + 四大活动 | OMG SysML 17 议题《Requirement ID should be immutable》；VTT《Requirements identification practices...》；ScienceDirect《Requirement Traceability》 |
| 23 N7 | "配置管理是文档/文员的活，跟开发无关。" | CM 不是文档（不是"记录意图"），是让系统各配置项在受控状态下演进的工程实践——代码、固件、硬件都参与 | 四大活动判据 + 守护判据 | The Register《So you think you know all about configuration management》；DemystifyingPLM《5 Configuration Management Myths That Undermine PLM》；Chris Siebenmann《Configuration management is not documentation》 |

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 配置三问 + "参数是零件、配置是装好的整机" | 1/2/4/19 + N2 | 脱口而出："配置=实体被记录下来的形态；三问=被记录了吗/功能物理特性吗/关联成整体了吗；参数是零件、配置是整机——改一个参数，整机形态就变，历史记录含义都跟着变" |
| ★2 | 配置项/配置/配置信息三分离 + 实体锚点 | 1/4 + N2 | "配置项=被管起来的实体（对象）、配置=实体被记录的形态（属性）、配置信息=记录形态的资料（记录）——都锚定实体；文档既是配置信息又是配置项，两个层面不冲突" |
| ★3 | 版本是刻度 + 版本四用途 + 版本判据 | 7/12/19 + N1/N3 | "版本=初始发布或基于完整构建的重新发布，回答走到第几步；版本号必须精确对应到哪一次完整构建——文件名不算" |
| ★4 | 基线三特征 + 版本顺着流基线垂直切 + 冻结非死锁 | 6/8 + N4 | "基线=被批准冻结的参照（批准是资格/冻结是状态/参照是用途）；版本顺着流、基线垂直切——里程桩顺着路排、收费站横在路中间；基线能改但必须走变更控制，冻结不是死锁" |
| ★5 | 没有基线变化不可言说 + 变更控制循环 + 三问 | 5/9/13 + N1/N6 | "没有基线，变化就不可言说——要描述变化必须有'从哪变起'的原点；基线建立后任何变化必须走 CR→影响评估→CCB→实施→新基线；配置管理让三问（应该是什么/实际是什么/怎么变成这样）任何时刻有答案" |
| ★6 | 四大活动 + 四洞 + 可剪裁 + 三条铁律 | 5/10/14/15 + N5/N7 | "标识/控制/状态记录/审计一个都不能少——不是做了版本号就等于做了配置管理；配置管理可剪裁，但'版本可指认、变更可追溯'是底线；三条铁律=协作要共同事实/长周期要组织记忆/担责要可答的账" |
| ★7 | 守护者 + 契约链 + 决策基线化 | 16/17/18 + N7 | "配置管理是架构决策的守护者——识别不可逆→冻结成基线→此后走变更控制；契约链每级都是局部甲乙方（基线=冻结端、版本=交付端）；决策记录六问把决策从个人知识变组织资产，配置信息做同一件事" |

### 纠错红线十条

1. **先表态后翻案**：先问"版本号不是有吗""配置不就是设置页吗""git 历史不是都在吗""基线不能改吧"，再翻——不让结论先入。
2. **反转精确不造新误解**：不说"配置管理就是隆重地建一堆文档/开会"（可剪裁、复杂度与责任等级匹配）；不说"基线神圣不可侵犯"（基线可变更，走变更控制）；不说"版本没用"（版本解决演进/回溯/并行/复现，只是不解决"参照"）。
3. **判据配机制**：每条反转都有"为什么"（参数零件整机 / 实体锚点解耦 / 连续切离散 / 原点不可言说 / 尺子变流程 / 组织资产）和"怎么当场验证"（十三把尺子）。
4. **归责到可对照动作**：不归咎"老周/小王/李工"，落到"配置三问验过了吗 / 版本号能对应到哪次完整构建吗 / 基线三特征齐吗 / 变更走 CR 吗 / 四个活动各打什么分 / 这批记录哪一问答得出"这类可查动作。
5. **教机制不教断言**：教"为什么配置是形态不是参数、为什么版本只是刻度、为什么没有基线变化不可言说、为什么尺子要变流程"，不教"小林说得对"。
6. **先立尺子再翻案**：先给十三把尺子（配置三问 / 变与不变分离 / 三分离 / 版本是刻度 / 基线三特征 / 垂直切 / 不可言说 / 变更控制 / 四大活动 / 三问 / 守护 / 契约链 / 三分工），再翻案例。
7. **拉开强度层次**：★★★ 常识（配置=参数 / 版本管理好=配置管理好 / 有版本号就有基线 / 版本号=文件名 / 基线不能改 / git 历史=基线 / 小团队负担 / 变更控制拖交付）重点翻，★★ 次之。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（找产品里一个参数跑配置三问 / 查最大配置项有没有基线 / 用四大活动给团队打分 / 画出契约链标冻结端交付端 / 回部门配置管理体检）。
9. **单一权威不另立标准**：判据引用书十三把尺子 + ISO 10007 / ISO 24765 / ISO 15288 / SemVer，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给部门产品做一次"配置管理体检"

> 目标：用十三把尺子检查一次"让产品说得清"的能力现状，产出三件可执行改进。
> 场景：回部门落地。时长：1~2 小时内完成一次体检，两周后复查一至两项。

1. **配置三问（尺1）**：从你们产品里挑一个"客户/用户能改的参数"，跑三问——被记录了吗（记录边界）？是功能/物理特性吗（类别边界）？和其他特性关联成整体了吗（关联边界）？产出：它是"配置"还是"配置信息里的一个条目"的判定。
2. **查变与不变分离（尺2）**：改这个参数，要不要动代码、重编译、重发布？要——变与不变没分离的信号；核心资产该外置哪些可变部分？产出：外置缺口清单。
3. **查三分离（尺3）**：列出你们产品五个配置项（代码/固件/文档/数据/硬件），每个标"该不该纳入配置管理"，再问：它有没有对应的"配置"（该有的形态）和"配置信息"（记录形态的资料）？产出：配置项清单 + 配置信息缺口。
4. **查版本是刻度（尺4）**：挑最大的配置项，问：有版本号吗？版本号能对应到"哪一次完整构建"吗（哪个代码提交编译、包含哪几条变更）？产出：版本可指认现状。
5. **查基线三特征（尺5）**：它有没有基线——被批准（有权威盖章）？被冻结（任何人不能随意改）？作参照（全生命周期拿它对照）？产出：基线现状（有/没有/半吊子）。
6. **查垂直切（尺6）**：画出产品的版本链（时间轴），在上面标应该竖切的几个"基线点"——它们该在哪些里程碑建立（需求批准→功能基线、分配定案→分配基线、产品定型→产品基线）？产出：基线点清单。
7. **查不可言说（尺7）**：找最近一次变更，问：答得出"从什么基线变到什么基线"吗？答不出——还没有基线。产出：没有基线导致"说不清"的场景清单。
8. **查变更控制（尺8）**：找最近一次变更，对照五步走一遍——变更申请（CR）/影响评估（影响谁）/CCB 批准（批不批）/实施/建立新基线——哪一步被跳过了？跳过的那一步，代价是什么？产出：变更控制缺口。
9. **查四大活动（尺9）**：用四大活动给团队打分——配置标识（说不清"产品是什么"）/配置控制（变更失控）/状态记录（设计与实物对不上账）/配置审计（复现不了、责任推诿），各打"有/缺/半吊子"。产出：四个活动四张成绩单。
10. **查三问（尺10）**：拿一个在役产品，问三问——应该是什么（as-designed）/实际是什么（as-built）/怎么变成这样的（变更历史），三问都答得出吗？答不出的那一问，缺哪个活动？产出：三问缺口。
11. **查守护（尺11）**：对照第11章，找出你们系统里高不可逆的决策（数据模型/编号规则/数据所有权）——它们被冻结成基线了吗？谁要动它必须走变更控制吗？产出：守护缺口。
12. **查契约链（尺12）**：画出开发链三层（需求→设计→实现），标出每层"基线（冻结端）"和"版本（交付端）"分别是什么。产出：契约链地图。
13. **查三分工（尺13）**：问"有几种形态"（变体）/"改到第几版"（版本）/"这个版本的这个形态"（基线）——你们把三者分开了吗？产出：三概念混用点。

**卡住怎么判断**：任一尺子打不出勾，就是该尺子说的缺口——不用全打完，找到第一个"否"就能开工。产出三件最该改进事项（每条 = 一个可检查动作）。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 产品里"客户能改的参数"用配置三问验过了吗？ | □ | 没验 → 把"配置信息里的条目"当"配置"，追溯时"这台箱子当时是什么样"答不上来 |

| 变体/版本/基线三概念分开用了吗？ | □ | 混用 → "医疗加强版 v2.4"说不清是变体还是版本还是基线 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身 · 破题）**
"小赵指着 App 设置页上的开关和数字框，给新来的测试员讲解：'这就是咱们的配置。温度上报间隔、超温告警阈值、断电告警开关……客户能改的，都在这页。改参数不用动固件、不用重编译，服务端一推就行。'——小赵指的那一页，是配置吗？什么才算'配置'？"
追问：① 配置三问：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？三问全"是"才是配置？② 参数 vs 配置：上报间隔这个参数是"配置信息里的一个条目"；配置是"上报间隔、告警阈值、断链判定逻辑、采集算法关联在一起塑成的 M3 行为形态"——为什么"参数是零件，配置是装好的整机"？③ 案例进展①：老周问"那页设置到底是不是配置"，小林反问他"你改那个告警阈值，改的是什么"——改一个参数，为什么整台箱子的"形态"就变了、采出来的温度记录含义都跟着变？④ 反身：你们产品里"客户能改的参数"，用配置三问逐个验一遍——有几个是配置，几个只是配置信息里的条目？

**Q2（见树见林② · 概念关系）**
"请给出 配置 / 配置项 / 配置信息 / 参数 / 实体 的关系（一句话），再把 版本 / 变体 / 修订 / 基线 放进去——两组概念各管什么？为什么说'配置提供内容、版本提供位置、批准提供资格'？"
追问：① 三词解耦：ISO 10007 三个术语互相定义、首尾相连成环——为什么引入"实体"做锚点就能解耦？② 辨析：设计图纸既是"配置信息"又是"配置项"——两个层面怎么不冲突？③ 变体×版本：标准版/医疗加强版/工业版是变体（空间、并存），v1.0→v2.4 是版本（时间、先后）——正交；"医疗加强版 v2.4"这个形态被批准冻结，怎么就成了基线？④ 口诀：配置提供"内容"、版本提供"位置"、批准提供"资格"——三者齐备才成一个基线，为什么一个都不能少？

**Q3（版本是刻度 · 真悖论收束）**
"老周说：'我们有版本号啊。v2.1、v2.2、v2.3，都标着呢。升级也走流程了，小赵也验证过了。怎么就不算配置管理了？'——版本号有了、流程走了、验证过了，为什么疾控审计还是查不清？版本管理和配置管理，到底差在哪？"
追问：① 版本是刻度：版本回答"走到第几步"，它没回答"哪一版是'被批准、被冻结、作参照'的"——版本只是时间轴上的刻度？② 版本四用途：追踪演进/回溯/并行/复现——版本解决这四个问题，但解决不了"参照"问题；缺了基线和变更控制，版本也管不住？③ 真悖论收束："版本管理做好了=配置管理做好了（版本号有、流程走了、验证过了）" vs "配置管理=标识+控制+状态记录+审计四大活动（版本只是刻度，缺了基线和变更控制，版本也管不住）"——两个都对，靠什么判据分清？④ 反身：你们团队"版本管理"和"配置管理"是分开的吗？版本号能对应到"哪一次完整构建"吗？

**Q4（基线三特征 · 版本顺着流基线垂直切 · 真悖论收束）**
"老周看着版本链：'v2.3 都发布三个月了，还不是基线？'小林：'版本只是刻度，基线才是参照。'——版本和基线差在哪？'版本顺着流、基线垂直切'是什么意思？基线一旦建立，是不是就永远不能改了？"
追问：① 三特征：被批准（资格，有权威的盖章）/被冻结（状态，任何人不能随意改）/作参照（用途，全生命周期拿它对照）——为什么一个都不能少？② 横竖分工：版本与时间同向（尺子上的刻度，流动，只描述位置，不改变时间轴性质）；基线垂直插入时间（横在路中间的闸门，冻结，制造分界，改变时间轴性质）——为什么"把版本当基线=把里程桩当收费站"？③ 真悖论收束："基线一旦建立就永远不能改（神圣不可侵犯，是配置管理里少数动不得的东西）" vs "基线可以变更（必须走变更控制，改完建立新基线，冻结不是死锁）"——两个都对，靠什么判据分清？④ 反身：你们产品"哪一版被批准、被冻结、全生命周期拿它对照"？答不出——你们只有版本链，没有基线？

**Q5（没有基线变化就不可言说 · 真悖论收束）**
"疾控审计员问：'这批疫苗四月运输，全程温度记录正常。你们要证明——这批记录，是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？'老周说：'查一下当时跑的固件版本。'结果查不清。小林：'没有基线，变化就不可言说。'——为什么？git 历史里不是什么都查得到吗？"
追问：① 原点：要描述一个变化，必须有"从哪变起"的原点——"从 v1.0 变到 v1.1"这句话有意义，是因为 v1.0 是所有人都认的、被冻结的、不会动的原点；没有原点，像在茫茫大海上说"我在动"，却没有岸标？② 对照：git 历史是记录（流水账），基线是被批准、被冻结、被全项目认可的参照——没有批准动作，历史只是流水账？③ 真悖论收束："没有基线变化也说得清（git 历史都在，diff 一查就知道改了什么）" vs "离开基线，一切变化都不可言说（没有'从什么变起'的原点，每一步都查无实据）"——两个都对，靠什么判据分清？④ 三问：配置管理核心目的三问——应该是什么（as-designed）/实际是什么（as-built）/怎么变成这样的（变更历史）——老周答不上的"这批记录是哪一版固件采的"，是哪一问？

### 第二组 · 落地与实践（5 题）

**Q6（四大活动 · 配置三问 · 案例进展①③）**
"冰链那次审计，老周复盘：固件升级'走了流程'、版本号'都有'、小赵也'验证过了'——可追溯链还是断了。用配置管理的尺子，那场事故四个洞各缺什么？哪一洞最关键？"
追问：① 四大活动对照：配置标识（固件是配置项，但从没立过基线）/配置控制（"走了流程"但没有影响评估——没问采集逻辑变没变）/状态记录（只有一句"已推送 v2.3"，没有哪台箱子哪个时间升到哪一版的台账）/配置审计（从没抽查实物与记录一致）——四个洞哪个最关键？② 影响评估：修丢读数的 bug 动的是采集算法——影响评估一问，为什么"固件行为变化，历史温度记录的采集与判定逻辑随之变化"就该被写进评估单？③ 合规升级（案例进展③）：老周这次升级 v2.4 走完 CR→影响评估→CCB→实施→建立新基线——每一步拦住或显形了什么？为什么"版本号只是刻度，基线是参照，流程是守护，三样都有，变化才说得清"？④ 反身：用四大活动诊断你们团队——标识/控制/状态记录/审计，各打一个"有/缺/半吊子"？缺的那一洞，最近一次追溯里断在哪？

**Q7（版本是刻度 · 案例进展② · 真悖论收束）**
"恒信小王把部署包扔进日期文件夹：'2026-05-18'里躺着'合同系统_final.zip'和'合同系统_final_2.zip'，分不清哪个是哪个。李工：'我们有版本号啊。'Ada：'你连'版本'都算不上。'——文件名不算版本，什么才算？'版本是回滚的地址'是什么意思？"
追问：① 版本判据：一个编号能精确对应到"哪一次完整构建"（哪个代码提交编译出来的、包含哪几条变更）吗？不能——它连版本都算不上？② 回滚地址：出问题要回滚，"回滚到哪"都指不出来——日期文件夹为什么既没地址、也没参照？③ 真悖论收束："文件名=版本（final_2.zip 也是版本号，至少能区分新旧两个包）" vs "版本必须精确对应到完整构建（final_2 既不知道哪次构建、也不知道有没有经批准、更不知道和上一版差在哪）"——两个都对，靠什么判据分清？④ 同病复发：第4章合同需求靠"v2.doc""最终版 v3.doc"管版本，现在是系统部署靠"final_2.zip"管版本——同一个病，换了个文件后缀再犯一遍，为什么文件命名永远管不住版本？

**Q8（契约链 · 真悖论收束）**
"Ada 说：'配置管理给契约链每一级都配了两样东西——基线是每一级契约的冻结端，版本是交付端。'李工：'可我们日常就一句话：按基线开发，提交版本。这不是说基线和版本各有归属吗？'——契约链的基线和版本，到底是某一级专属，还是每级都重复？"
追问：① 契约链：需求→方案→实现，链上每一对相邻环节都是一组局部的"甲方-乙方"关系——甲方把要求冻结成基线、乙方按基线开发、乙方产出的版本交付甲方验收、验收通过又成为下一环的基线，机制怎么逐级重复？② 真悖论收束："基线对甲方、版本对乙方——基线和版本各有归属（需求阶段有功能基线、实现阶段有产品基线，'属于'不同的人）" vs "基线和版本在每一层都在（契约链每一级都重复同一通用机制，只因视角不同看起来'属于'不同的人）"——两个都对，靠什么判据分清？③ 边界：开发链内部的"甲乙方"是技术契约（要求-兑现，管"对不对得上"）；完整的外部甲乙方多一层商务契约（法律合同、付款、责任，管"赔不赔得起"）——为什么"把'合同'和'契约链'当成一回事"是越界？④ 反身：画出你们开发链三层（需求→设计→实现），每层的"基线（冻结端）"和"版本（交付端）"分别是什么？

**Q9（守护架构决策 · 案例进展④ · 真悖论收束）**
"编号事故复盘会上，李工说：'如果当时有这套东西，我改编号规则会先填 CR。影响评估一查——编号规则被财务、台账、审计、电子签章四个下游引用；评估单上会写"该变更影响全部历史合同数据，不可逆性高"——这一行字写出来，我当天就不敢"今天就能上"了。'——第11章说改字段前三问是一把个人尺子，配置管理把它变成了什么？为什么说配置管理是第11章那些不可逆决策的保险丝？"
追问：① 同构表：决策记录↔配置信息 / 不可逆决策识别↔基线冻结 / 推迟决策↔变与不变的分离 / 变更影响分析↔变更控制——四行各对什么？② 尺子变流程：第11章三问是个人尺子（靠自觉），配置管理的变更控制是组织流程（靠结构）——为什么"个人尺子靠自觉，流程靠结构"是守护的本质？你不是自觉不够，是一个人扛不住那么多"顺手改动"的记忆？③ 真悖论收束："配置管理是文员的活、是文档的活（负担，跟核心决策无关）" vs "配置管理是第11章那些不可逆决策的保险丝（决策做对了靠它守住、做错了靠它让你早发现早止损）"——两个都对，靠什么判据分清？④ 决策基线化："决策记录是决策的配置信息"——第11章的六问记录把决策从"当事人脑子里的知识"变成"组织的资产"，配置管理怎么把这件个人动作变成组织级动作？

  - Q4 基线不能改 vs 基线可变更："基线一旦建立就永远不能改（神圣不可侵犯）" vs "基线可以变更（必须走变更控制，改完建立新基线，冻结不是死锁）" → 判据 = 变更控制循环（基线建立后任何变化必须走 CR→影响评估→CCB→实施→新基线）；
  - Q5 git 历史说得清 vs 离开基线不可言说："没有基线变化也说得清（git 历史都在，diff 一查就知道改了什么）" vs "离开基线一切变化都不可言说（没有'从什么变起'的原点）" → 判据 = 没有基线不可言说（git 历史是记录，基线是被批准冻结的参照；任何变更必须能回答"从什么基线变到什么基线"）；
  - Q7 文件名=版本 vs 版本=完整构建："文件名=版本（final_2.zip 也是版本号，能区分新旧）" vs "版本必须精确对应到完整构建（final_2 既不知道哪次构建、也没经批准）" → 判据 = 版本是刻度（能对应到哪一次完整构建才是版本，文件名不算）；
  - Q8 基线版本各有归属 vs 每级都重复："基线对甲方、版本对乙方（各有归属，需求阶段功能基线、实现阶段产品基线）" vs "基线和版本在每一层都在（契约链每级都重复同一机制）" → 判据 = 契约链（甲方冻结基线、乙方交付版本，验收通过又成下一环基线——每级重复的通用机制）；
  - Q9 文员的活 vs 不可逆决策的保险丝："配置管理是文员的活、是文档的活（负担）" vs "配置管理是第11章那些不可逆决策的保险丝（做对了守住、做错了早止损）" → 判据 = 守护（高不可逆决策被批准后冻结成基线，此后谁动它必须走变更控制）。
