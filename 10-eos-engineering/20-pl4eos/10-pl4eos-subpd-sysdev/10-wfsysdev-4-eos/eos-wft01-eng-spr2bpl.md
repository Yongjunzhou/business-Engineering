# 平台能力规范化的相关方需求 → 平台能力业务流程框架
**SKILL 指南ID**: wft01-eng-spr2bpl

> **概述**：接收FR-ENG 规范化的相关方需求节点，经前置校验、材料加载和反馈处理后，将非结构化平台能力需求转化为 bpl-eng 场景业务方案。bpl-eng 是流程与IT域中**业务配置人员**围绕一项可独立配置、治理并验收的平台能力场景形成的端到端业务。每个 bpl-eng 只有一个主责能力域；主责能力域可以是引擎，也可以是平台共享能力域。一个能力域可包含多个 bpl-eng，多个引擎可消费同一共享 bpl-eng，但不得重复定义共享 CU。本 Skill 的职责是**设计**——完成 规范化的相关方需求→**业务流程框架**（eng 链 01 层）：框架定义（bpl-eng 归组/边界/能力链）+ 分解（名称级识别→配置信息组（框架说明））+ 分配（配置信息组→CU 承接，含收敛判定）+ 分析（完备性）；框架说明定位**结构判定级**，操作活动定义留 wft02-eng（业务流程概要）展开。
>
> **输入 → 输出**：FR-ENG 规范化的相关方需求节点 条目（≤10 条）/ 有反馈的 bpl-eng 节点 → **业务流程框架**（bpl-eng 场景业务方案：能力链 + 配置信息组（框架说明，业务流程框架末级节点）+ CU 承接关系 + 补充 FR-ENG 材料）+ 规范化的相关方需求 推进为 `已分配` + bpl-eng 推进为 `可以详细定义`
>
> **适用场景**：瀑布式系统设计第1步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>

## 一、职责定位

**一句话**：本章说明本 Skill 的定位——要达成什么（1.1 目的与目标）、与上下游如何衔接（1.2）。

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台能力相关方——「你听懂了这项平台能力需要配置或治理什么、完成后能得到什么可验收结果」。把非结构化的 FR-ENG 规范化的相关方需求节点 转化为结构化的 **业务流程框架**（eng 链 01 层）——bpl-eng 平台能力场景业务方案，并完成**设计**——框架定义（场景/边界/能力链）+ 分解（名称级识别→配置信息组（框架说明））+ 分配（配置信息组→CU 承接）+ 分析（完备性），识别场景所需 CU、共享依赖及能力链缺口。框架说明为**结构判定级**（配置什么/运行期提供什么），操作活动定义留 wft02-eng（业务流程概要）展开。

> **三层定位（按 EOS 流水线系统设计规范 §8.1）**：本 Skill 属于第1层（流水线设计）活动——在 EOS 流水线设计层将平台能力需求转化为 bpl-eng 方案；产出物经 wft02-eng→wft05-eng 完整链条后（02 业务流程概要/03 系统需求框架/04 系统需求概要/05 平台产品架构），以设计规范/AI SKILL 形态交付第2层（构件开发），最终由第3层 EOS 开发者（确认者/用户）使用。本 Skill 的执行分工按 EOS 流水线系统设计规范 §8.3：流水线开发者（主导者/审核者）审核 AI 的 bpl-eng 方案并决策变更路径，AI（执行者）执行标准操作流程，EOS 开发者（确认者/用户）确认交付物可用性。

**目标**：

1. **推断生成平台能力场景业务节点**——以`主责能力域 + 配置/治理目标 + 可独立验收结果`为归组锚点，匹配已有 bpl-eng 或新建；主责能力域分为`引擎专属`和`平台共享`两类
2. **识别配置信息组（框架说明）**——从场景业务按"可以运行的能力"名称级识别候选、分解为配置信息组（框架说明），每个配置信息组 = 一个可以运行的能力（判据见 §3.3.1），直接产出配置信息组清单 + 每条框架性说明（§2.3.2，结构判定级）；配置信息组即**业务流程框架末级节点**（PL5，P0 产品树末级），不展开操作活动定义（那是 wft02-eng）；CU 是 bpl-eng 的细分节点——配置信息组（PL5）与 bpl-biz 下辖输出文档（PL5）的层级关系完全对称
3. **分配配置信息组到 CU 承接**——逐组找 CU 承接（1:1），执行收敛判定（复用/新增/拆分/合并，§3.3.2）与对照 25 盘存的骨架判定（复用/改进/新增），输出 CU 承接关系，为 wft02-eng 业务流程概要提供起点
4. **装配 R 上下文**——从 规范化的相关方需求 触发来源与 23/24 资产装配业务运行对象、配置角色、触发事件、状态影响（§3.2.2），支撑 CU 来源判定与追溯链前端锚点
5. **基于能力链补充引擎需求**——检查"配置/治理意图→系统处理要求→运行期制品/构件/功能→可用性确认"的能力链闭合性；检出实质能力缺口时生成补充 FR-ENG 材料。若仅"配置完成后如何判定能力可用"不明确，则标记澄清项，不生成补充材料
6. **建立追溯链**——保留 `FR-ENG 规范化的相关方需求节点 → bpl-eng主责能力域 → 配置信息组（框架说明） → CU承接` 的追溯链，记录提供能力、消费方和复用范围
7. **判断路径归属**——将 FR-BIZ、NFR、业务配置实例需求及时路由到对应路径，避免 eng 路径替业务链或非功能路径做方案

本 Skill 负责：

1. **接收**——接收流水线开发者选中的一批 FR-ENG 规范化的相关方需求节点 条目（≤10 条），校验输入为FR-ENG 规范化的相关方需求节点、状态为 `待处理`；状态/类型不符时退出并提示路由
2. **溯源**——识别每条 规范化的相关方需求 的主责能力域、配置/治理目标和可独立验收结果，判定为引擎专属或平台共享
3. **归组**——按三元组匹配已有 bpl-eng；同一能力域中的不同独立场景分别建 bpl-eng。跨场景共享能力通过`依赖bpl-eng`引用，不在消费引擎下复制共享 CU
4. **分解**——从场景业务按"可以运行的能力"名称级识别配置信息组候选、分解为配置信息组（框架说明），每个配置信息组 = 一个可以运行的能力（分解判据见 §3.3.1），标注每个配置信息组的来源与证据
5. **分配**——逐条匹配 CU 承接（1:1），执行收敛判定（复用/新增/拆分/合并）与对照 25 盘存的骨架判定（复用/改进/新增）+ 引擎归属判定（§3.3.2）；不定义配置信息组内容、配置要素或运行期构件
6. **装配 R 上下文**——从 规范化的相关方需求 触发来源与 23/24 资产装配业务运行对象/配置角色/触发事件/状态影响（§3.2.2），写入 bpl-eng 节点
7. **补需**——检出配置/治理意图、系统处理要求或运行期制品等实质缺口时生成补充 FR-ENG 材料；仅能力可用判据不明确时输出澄清项
8. **推进**——流水线开发者确认后 bpl-eng → `可以详细定义`，对应 规范化的相关方需求 → `已分配`
9. **回修**——接收 wft02-eng 退回的 `需wft01修订` bpl-eng，读取缺失说明，按流水线开发者的改进方案修订 bpl-eng（走 Phase B 分解分配重识别），流水线开发者确认后重新推进为 `可以详细定义`

本 Skill 不负责：

1. FR-BIZ 业务需求的场景业务与输出文档设计（→ `wft01-biz`）
2. NFR 分类与量化（→ `wft01-nfr` / `wft04-nfr`）
3. 配置信息组的操作活动定义（配置操作/系统处理/运行期能力）（→ `wft02-eng` 业务流程概要）
4. 系统需求框架（功能表单+框架说明）（→ `wft03-eng`）；系统需求概要（功能表单组件及其业务）（→ `wft04-eng`）
5. 前后端组件、接口和实现边界设计（→ `wft05-eng`）
6. 引擎/CU 模型的详细定义（→ `wft02-eng` 业务流程概要，25 记录）；本 Skill 做分解分配设计（名称级识别→配置信息组（框架说明）→CU 承接），不做操作活动定义（配置操作/系统处理/运行期能力）、依赖与状态迁移的详细定义

### 1.2 与上下游的衔接

**上游 规范化的相关方需求预处理**：只消费已进入 `01-*.md`、类型=`FR-ENG`、状态=`待处理` 的规范化的相关方需求节点。wft03-biz 产生的 FR-ENG 候选线索只是候选材料，必须先经流水线开发者确认，并完整通过 or00→or01→or02→or03 转化为FR-ENG 规范化的相关方需求节点，才能进入本 Skill；不得从缺口材料或状态表 A 直接启动 wft01-eng。

**交付链条**（按 EOS 流水线系统设计规范 §8.1 三层框架）：本 Skill 产出（**业务流程框架**——bpl-eng 场景业务方案）→ wft02-eng（业务流程概要）→ wft03-eng（系统需求框架）→ wft04-eng（系统需求概要）→ wft05-eng（平台产品架构）→ **第2层交付**（设计规范/AI SKILL 形态交付至 EOS 设计空间）→ **第3层使用**（EOS 开发者使用交付物对 EOS 进行系统设计）。本 Skill 处于第1层起点——完成平台能力场景框架设计后，由下游链路逐步转化为可执行的流水线构件。

**① 设计产物——bpl-eng 场景业务与能力载体**

### 2.1 引擎场景业务（bpl-eng）

**一句话**：本节讲引擎场景业务（bpl-eng）——定义与分类（2.1.1）、节点要素与职责边界（2.1.2）；完备性判据见 §三 3.4。

#### 2.1.1 定义与分类

bpl-eng 是 FR-ENG 在相关方需求层的结构化表达，末级节点为**场景业务**（bpl-eng 架构末级）。角色为流程与IT域的**业务配置人员**，bpl-eng 架构树上无需角色层做分组维度。bpl-eng 下的 P0 产品树细分（对齐 91 §3.1 P0 PL 树）：CU（PL4，可独立选配的配置单元）→ 配置信息组（PL5，P0 产品树末级节点，可独立交付/验收的能力单元）。

> **◆ 角色层次注记**：此处的"业务配置人员"是目标系统（EOS）中的第3层用户角色，是 bpl-eng 场景业务的需求锚点。本 Skill 本身是第1层（流水线设计）活动，其执行者按 EOS 流水线系统设计规范 §8.3 为流水线开发者（主导者/审核者）、AI（执行者）和 EOS 开发者（确认者/用户）——后者的 EOS 开发者角色与被设计系统中的"业务配置人员"是不同概念，切勿混淆。

**一个独立能力场景 = 一个 bpl-eng**：归组锚点为`主责能力域 + 配置/治理目标 + 可独立验收结果`。主责能力域可以是业务引擎，也可以是权限、审计、版本、发布、调度、通知等平台共享能力域。一个能力域可包含多个 bpl-eng；多个引擎可依赖同一共享 bpl-eng。bpl-eng 在 R 视角是业务配置人员的 SL5/PL5 场景业务，在 P0 视角对应主责能力域下的能力场景，CU 是其细分节点，配置信息组是 P0 产品树末级节点（PL5）。

共享技术能力若没有独立配置/治理活动和可验收结果，不建立 bpl-eng；其需求由 NFR 约束或平台架构决策进入 wft05-eng，形成公共构件或平台服务组件。

> **与 bpl-biz 的对称性**：bpl-eng 与 bpl-biz 在架构层级上完全同构——同为 SL5 末级节点（场景业务）、同有下辖细分（bpl-eng：CU[PL4]→配置信息组[PL5]；bpl-biz：输出文档[PL5]，配置信息组对应输出文档、CU 对应 WBS）、同为角色端到端职责闭环。区别仅在于场景业务的产出物不是业务文档，而是**可用的平台能力**。

**FR-ENG 规范化的相关方需求节点 的五种类型**（不是 bpl-eng 的分类——一个 bpl-eng 可承接多种类型的 规范化的相关方需求）：

| 类型 | 触发源 | 场景自然终点 |
|------|--------|--------------|
| 配置生成类 | 配置人员提出或维护引擎配置 | 配置通过系统校验并在运行期制品/构件/功能中生效 |
| 构件扩展类 | 业务页面需要新增按钮、右键、图表、钻取等构件能力 | 目标布局组件可渲染并使用该构件 |
| 布局组件扩展类 | 现有布局组件无法承载业务操作方式 | 新/扩展布局组件能力可被对应引擎或业务页面调用 |
| 横切治理类 | 权限、审计、版本、发布、回滚、监控等治理需要 | 横切规则对目标业务对象或运行期能力稳定生效 |
| 运行支撑类 | 业务运行页需要引擎能力调用、状态处理或异常恢复 | 引擎能力可被业务页面调用并产生可追溯结果 |

AI 根据 规范化的相关方需求 语义判定类型，作为 规范化的相关方需求 的能力诉求特征标注——不用于划分 bpl-eng 边界。

### 2.2 能力链

**一句话**：本节讲能力链——bpl-eng 是否闭合的判断依据：定义与构成（2.2.1）。

#### 2.2.1 定义与构成

能力链是 wft01-eng 判断 bpl-eng 是否闭合的业务链类比物。它不展开业务输出文档，而是描述平台能力从一个引擎的配置意图到运行期生效的最小闭环。

```text
配置/治理意图
  → 系统处理要求
  → 运行期制品/构件/功能
  → 可用性确认
```

各段含义：

| 段 | 说明 | wft01-eng 粒度 |
|----|------|----------------|
| 配置/治理意图 | 需要配置或治理哪类平台能力 | 名称级表达 |
| 系统处理要求 | 系统至少要校验、保存、发布、装载或控制什么 | 只描述能力要求，不写实现 |
| 运行期制品/构件/功能 | 91 规范中的物理表、功能表单、菜单入口、配置页面或页面组件上的构件等 | 名称级，不设计构件 |
| 可用性确认 | 何种结果代表平台能力可用——即业务配置人员完成配置后，运行期业务人员可使用该能力的判定标准 | 作为场景终点 |

> **能力链实例**（以"流程节点配置"场景为例）：
> ```text
> 配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认
>   ↓               ↓               ↓                    ↓
>   配置流程节点    校验节点参数     流程按钮绑定到业务表单   流程按钮可用、节点跳转正常
>   和流转规则      保存规则配置     页面、发布后装载生效
> ```
> 注：能力链在 `02-*.md` bpl-eng 节点中以一句陈述呈现，不展开为箭头的细分项。此处的展开是为了帮助 AI 理解各段的具体含义。

> **触发来源不在此链中，但它驱动能力链第一段**：触发来源（R／P 业务运行对象 / 平台治理对象 / 构件缺口 / 布局组件缺口 / 横切能力阶段）是 规范化的相关方需求 级上下文信息，标注在 规范化的相关方需求→引擎的追溯链中（§2.1.2），不属于能力链的闭合段。触发来源不构成闭合段，但**驱动**能力链第一段的配置意图——构件缺口/布局组件缺口 → 推断需要新的构件配置/布局组件配置 CU（§3.3.2 来源类型 `构件缺口推断`/`布局组件缺口推断`）；横切能力阶段 → 治理配置意图。五种 FR-ENG 规范化的相关方需求节点 类型在能力链上的起点映射：配置生成类/横切治理类 = 配置意图直接驱动；构件扩展类/布局组件扩展类 = 运行期缺口驱动配置意图；运行支撑类 = 能力调用需求驱动。能力链本身只关注"配置侧→运行期可用"，即业务配置人员从打开配置页面到能力可用的完整闭环。

每个名称级识别出的配置信息组候选至少记录：

#### 2.4.1 定义与记录字段

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲设计的逻辑——为什么用场景业务承接需求（3.1 转换原理）、怎么从 规范化的相关方需求 提取要素（3.2）、怎么分解分配（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四。

### 3.1 转换原理：为什么用场景业务承接 FR-ENG

**原始需求是零散表述，相关方需求要结构化**。FR-ENG 规范化的相关方需求节点 是用户口吻的逐条能力诉求（如"需要配置流程节点和流转规则，发布后能在业务表单上使用"），只有语义、没有架构位置——它属于哪个引擎、由谁主责配置、怎样独立验收，都需要设计出来。本 Skill 的转换正是把原始需求层面（`01-*.md`）的 FR-ENG 规范化的相关方需求节点，变成业务流程框架架构层面（`02-*.md`）的 bpl-eng 节点。

**承接单位 = 场景业务（bpl-eng），因为它是"可独立配置、治理并验收"的需求自然单位**。一条能力需求总是"某主责能力域对某项平台能力做一段可独立验收的事"。把 规范化的相关方需求 归入"主责能力域 + 配置/治理目标 + 可独立验收结果"（归组三元组，§2.1.1），需求就获得架构位置——归组锚点是**可独立验收的能力场景而非引擎**：同一引擎的不同配置/治理目标若可独立验收，分别建 bpl-eng（v7.0 起取消"一引擎一 bpl-eng"）；把场景细化为"配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认"的能力链（§2.2），需求就有了可落地的平台能力形态。能力链同时保证**端到端完整性**——规范化的相关方需求 只提一个环节时（如只提配置意图），能力链要求把其他环节补齐（系统处理、运行期可用），缺的进入完备性检查、生成补充 FR-ENG 材料（§5.5），不让能力需求"悬在半截"。归组三元组同时保证**场景可独立验收**——每条 规范化的相关方需求 都落到一个能独立判定"配置完成、能力可用"的场景，不依附其他场景。

**分解分配 + 补全，不是转录**。本 Skill 不只复述 规范化的相关方需求 已说的，还识别其指向的平台能力意图（§1.1 目的）并做分解分配设计——配置信息组候选（名称级识别）拆成配置信息组（框架说明）、配置信息组逐一找到 CU 承接（含收敛判定）。识别出的是"规范化的相关方需求 蕴含的能力"；识别不出、但能力链闭合必需的，进完备性检查补全，不脑补节点（§3.2.3 能力场景范围完整性检查）。

**bpl-eng 通过补充 FR-ENG 规范化的相关方需求节点 渐进收敛到闭合能力链**。能力场景边界定义（§3.2.3）要求场景范围=规范化的相关方需求 显式覆盖的范围、不脑补节点——因此初次创建的 bpl-eng 常只覆盖闭环的一段。缺口不脑补节点，而是经完备性检查生成补充 FR-ENG 材料（§5.5）→ 经 规范化的相关方需求预处理链返回为新一轮 FR-ENG 规范化的相关方需求节点 → Phase A 宿主匹配归入该 bpl-eng（§5.4.1）→ Phase B 修订（§3.2.4）→ 版本递增（§4.1 上游变更）。多轮循环后 bpl-eng 收敛到闭合能力链。这是本 Skill 的核心运行模型：**边界收敛与能力链闭合互为镜像**，由"补充 FR-ENG 规范化的相关方需求节点"这条回路衔接。缺口在能力链闭合检查（§5.5）发现，经补充 FR-ENG 规范化的相关方需求节点 回路**单向补回**能力链——缺口就是缺口，不脑补节点。

**缺口必须区分"需求侧可锚定"与"需求侧无锚"，只有后者才回 bpl-eng**。缺口 CU 能否在分配中承接，取决于其场景身份能否由需求侧（框架层）锚定。需求侧锚有四类：`规范化的相关方需求明示`/`规范化的相关方需求隐含`/`构件缺口推断`/`布局组件缺口推断`——能落到其一，场景身份可定位（它在能力场景的哪个位置、承担什么配置/治理职责、与已有 CU 的先后关系均可读出），分配时按收敛判定新增候选（标 `[推断]`，人机确认，§3.3.2），追溯链 规范化的相关方需求→bpl-eng→CU 成立。**25 盘存是资产，不是需求源**——`同类引擎推断`/`模型线索推断` 等资产侧提示不构成身份锚（§3.3.3）。若缺口 CU **需求侧无锚**（框架层缺失、链不隐含、无缺口证据）——分解分配无法定位其场景身份，且 CU 承接必须能追溯 bpl-eng 与 规范化的相关方需求（追溯矩阵），先于 规范化的相关方需求/bpl-eng 存在的 CU 会断裂追溯链——此时须经补充 FR-ENG 规范化的相关方需求节点 回路（§5.5）单向补回框架，待身份带回后再分解分配。

**闭合形态唯一（能力链），五种 规范化的相关方需求 类型不改变它**。eng 路径没有 biz 的 D/PCA 双闭合形态——所有 bpl-eng 都按能力链四段闭合（§2.2）。五种 FR-ENG 规范化的相关方需求节点 类型（§2.1.1）是 规范化的相关方需求 级能力诉求特征标注，不划分 bpl-eng 边界：同一 bpl-eng 可承接多种类型（如流程节点配置场景同时承接配置生成类与运行支撑类），闭合检查形态不受类型影响。

**分配结果是设计结论，引擎权威归 bpl-eng**。本 Skill 做分解分配，CU 承接（含目标引擎归属）是**设计结论**而非候选建议。判定依据：bpl-eng 主责能力域（归组锚点，规范化的相关方需求 业务语义，§3.2.1）与 CU 承接的引擎归属（CU 功能特征匹配 25 引擎清单，§3.3.2）均由本 Skill 判定——属 **bpl-eng 权威**，wft02-eng 详设时发现分解分配缺陷（配置信息组无法在该 CU 下展开详设、引擎归属错判、承接缺失）退回 `需wft01修订`，不静默改。下游只校验详设可行性——可消费性不足经出口闸门（wft02-eng §3.4 运行期能力可消费）反馈，不改 bpl-eng 设计。

**新增/改进引擎、CU 是设计内容，落地走文档结对骨架，执行为人机协同**。做分解分配不是从 规范化的相关方需求 语义列举名称，而是**对照 25 盘存（引擎清单 + CU 类型线索，含组织已有归档资产）逐配置信息组候选判定复用 / 改进 / 新增、逐配置信息组判定 CU 承接（复用/新增/拆分/合并）**——这是文档结对设计（通用设计规范 §2.3）骨架阶段"每条末级同步在下层方案中找承接节点（复用/改进/新增）"在 eng 路径的落地：复用 = 25 已有类型承接；改进 = 扩展已有类型能力边界；新增 = 盘存无承接、需设计新 CU 类型（操作活动定义由 wft02-eng 展开）；拆分/合并 = 配置信息组在 CU 间的重划。新增引擎的判定发生在主责能力域层面——规范化的相关方需求 语义需要现有引擎承载不了的新操作模式时，主责能力域 = 新引擎候选（名称级写入 bpl-eng，引擎 CU 结构由 wft02-eng 详设）。判定是**设计内容而非机械规则**，执行方式为**人机协同**：AI 基于对新增需求与已有资产的语义理解提出建议方案并附判据理由（为什么新增/改进、对照盘存为何无承接），流水线开发者审核、思考、决策、反馈，AI 落实后记录进 25——**25 是记录层，不裁决**；盘存中的组织已有资产由人类整理记录（非本 Skill 设计），本 Skill 读盘存时按复用对待。

**这套原理方法为什么可行**：它以**可验证性**为锚——每个设计决策都追问"下游能否验证、追溯是否完整、变更能否传播"。归组锚点选"可独立验收结果"（=bpl-eng 的性能指标，不可独立判定则不成为场景）；能力链四段是"配置→生效"的微闭环，缺一段即不可交付或不可验证；"边界=规范化的相关方需求 显式覆盖、不脑补节点"把设计完整性让渡给补充 规范化的相关方需求 回路，**追溯完整性永远优先**——无 规范化的相关方需求 锚点的节点不可追溯、下游无法验证、变更不传播，一次脑补污染整条链；权威归信息最全的一方且只归其信息全的部分（分解分配在 wft01 定，详设可行性在 wft02 验）。判据全部可机械判定（三元组一致 / 能力链缺段 / 分解分组 / 收敛判定 / 五关系 / 证据强度排序），操作全部有明确输入输出与执行模式（§5 Step 布局表），原理→判据→操作三层一一咬合，且与 91 规范、biz 路径同一套协议运转。

### 3.2 场景业务要素提取规则

**一句话**：本节讲从 规范化的相关方需求 提取 bpl-eng 要素的规则——能力域确定（3.2.1）、R 上下文装配（3.2.2）、能力场景边界定义（3.2.3）、Phase B 场景匹配检查（3.2.4）。Phase B（修订已有 bpl-eng）与 Phase C（新建 bpl-eng）共用以下规则——先看 3.2.5 的 B/C 分工差异表，再读细节更顺。

#### 3.2.1 能力域确定

逐条 规范化的相关方需求 提取以下要素：

| 提取项 | 说明 |
|--------|------|
| 触发来源 | 业务运行对象 / 平台治理对象 / 构件缺口 / 布局组件缺口 / 横切能力阶段（规范化的相关方需求 级上下文信息，标注在 规范化的相关方需求→引擎追溯链中，不用于 bpl-eng 边界划分） |
| 能力诉求 | 需要平台提供什么能力 |
| 运行期结果 | 期望生成或增强什么制品、构件或功能 |
| 主责类型 | `引擎专属` / `平台共享` |
| 主责能力域 | 实体、流程、工单等引擎，或权限、审计、版本、发布、调度、通知等共享能力域 |
| 配置/治理目标 | 本场景要完成的独立配置或治理目标 |
| 可独立验收结果 | 不依附其他场景也能判断完成与否的结果 |
| 依赖能力 | 本场景消费的其他 bpl-eng 或无需建立 bpl-eng 的技术能力 |

路由规则：

| 情况 | 处理 |
|------|------|
| 规范化的相关方需求 实际要求业务输出文档或业务流程 | 退回 `wft01-biz` |
| 规范化的相关方需求 实际是性能、安全、可用性等约束 | 退回 nfr 路径 |
| 规范化的相关方需求 只是具体业务配置数据 | 标记为业务配置实例，不进入 eng 设计 |
| 规范化的相关方需求 描述可独立配置、治理和验收的引擎能力 | 进入相应引擎专属 bpl-eng |
| 规范化的相关方需求 描述跨引擎复用且可独立配置、治理和验收的能力 | 进入平台共享 bpl-eng；消费引擎建立依赖引用 |
| 规范化的相关方需求 描述无独立配置场景的公共技术能力 | 转为 NFR 约束或 wft05-eng 平台组件线索，不建立 bpl-eng |
| 规范化的相关方需求 同时包含多个可独立验收结果 | 按结果拆分为多个 bpl-eng，并建立依赖；无法拆分时标记 `[需裁决]` |

#### 3.2.2 R 上下文装配

Phase C 新建 bpl-eng 时，从 规范化的相关方需求 触发来源和 24 资产装配 R 上下文（概念见 §2.5）：

1. **定位 R 产品/场景**：从 规范化的相关方需求 触发来源提取业务运行对象或治理对象，匹配 23/24 资产中的 R 产品/场景节点。
2. **提取配置/支撑角色**：从 bpl-eng 的场景边界陈述中提取配置人员或支撑角色。
3. **确定触发事件与状态影响**：从 规范化的相关方需求 触发来源与能力链的"可用性确认"段分别提取。
4. **装配触发追溯链**：`R／P 业务运行对象/治理对象/构件缺口/布局组件缺口/横切阶段 → bpl-eng → 配置信息组（框架说明） → CU 承接`。

若 R 上下文信息不足，标注 `[推断]` 并记录缺失项；若缺失到无法判断 CU 来源，标记 `需澄清` 或退回 规范化的相关方需求预处理。

#### 3.2.3 能力场景边界定义

Phase C 新建 bpl-eng 时，按`主责能力域 + 配置/治理目标 + 可独立验收结果`定义边界。主责能力域已有其他 bpl-eng，不妨碍新建不同的独立能力场景。

**判定主责能力域**：先判断能力是否具有独立配置/治理活动和验收结果，再判断主责类型。跨引擎复用不等于拆到各引擎；具有独立场景时归入平台共享能力域，消费引擎仅建立依赖。

**追踪自然终点**：终点 = 规范化的相关方需求 语义显式覆盖的最后一个配置/治理动作/状态，不得在终点之后扩展。仅因 规范化的相关方需求 到此为止而缺失的环节不脑补节点——进入完备性检查的缺口清单（§5.5），由补充 FR-ENG 规范化的相关方需求节点 回路渐进补齐（§3.1）。

**定义能力场景闭环**：bpl-eng 的边界是一次可独立完成和验收的配置/治理业务。AI 需回答以下问题：

1. 配置人员要配置什么？（配置要素清单——从 规范化的相关方需求 中提取）
2. 系统要怎么处理？（校验/保存/发布/装载——从 规范化的相关方需求 中提取，不足的进入缺口清单）
3. 配置后产出什么运行期能力？（制品/构件/功能——从 规范化的相关方需求 中提取）
4. 怎么算配置完成、能力可用？（可用性确认标准）

**能力场景范围完整性检查**：

| 判据 | 通过标准 | 不通过处理 |
|------|----------|------------|
| 主责能力域唯一 | 一个 bpl-eng 只有一个主责能力域，依赖方不改变主责 | 拆分场景或标记待裁决 |
| 独立验收 | 配置/治理目标具有独立完成标准 | 合并到其他 bpl-eng 或降为依赖 |
| 共享复用 | 共享 CU 只在共享 bpl-eng 定义一次 | 消费方删除重复 CU，建立依赖 |
| 能力链闭合 | 配置意图能走到运行期可用 | 缺口进入补充 FR-ENG 材料 |
| 终点明确 | 能说清"何时算配置完成、能力可用" | 标记 `需澄清` |
| 不替代 biz | 不新增业务输出文档、不重做业务场景 | 退回 biz 路径 |

输出**场景边界陈述**：`业务配置人员针对「<主责能力域>」完成<配置/治理目标>，经<系统处理>形成<运行期产出>，达到<独立验收标准>后场景完成；<消费方>通过依赖关系复用该能力。`

边界定义完成后，按 §2.1.2 完整要素组装 bpl-eng 节点写入 `02-*.md`。

#### 3.2.4 Phase B 场景匹配检查

Phase B 修订已有 bpl-eng 时，按三元组检查本轮 规范化的相关方需求 是否属于该能力场景。

1. 提取主责能力域、配置/治理目标和独立验收结果
2. 三元组一致 → 归入该 bpl-eng（进入 CU 承接关系检测 §3.3.4）
3. 仅主责能力域一致但目标或验收结果不同 → 匹配该能力域下其他 bpl-eng 或新建 bpl-eng
4. 属于共享依赖 → 关联共享 bpl-eng，不向当前 bpl-eng 复制共享 CU

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| 场景匹配 | 三元组一致 | 进入 CU 承接关系检测（§3.3.4）+ 输出变更影响声明 |
| 同域不同场景 | 主责能力域相同，但目标或验收结果不同 | 匹配其他 bpl-eng 或触发 Phase C 新建 |
| 共享依赖 | 能力由已有共享 bpl-eng 提供 | 写入依赖关系和消费方，不复制 CU |
| 主责不匹配 | 规范化的相关方需求 归属其他能力域 | 退回待聚合池，重新匹配或新建 |

#### 3.2.5 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 bpl-eng | Phase C 新建 bpl-eng |
|------|----------------------|-------------------|
| 判定范围 | bpl-eng 已承接的全部 规范化的相关方需求 + 本轮新 规范化的相关方需求 | 待聚合池本组 规范化的相关方需求 |
| 引擎锚点 | 以已有引擎的能力链为基线，仅扫描本轮新 规范化的相关方需求 是否引入新链段 | 从零构建引擎的能力链 |
| 归组 | 执行场景匹配检查（§3.2.4）——三元组一致才归入 | 执行能力场景边界定义（§3.2.3）——同域不同独立场景分别新建 |
| 要素提取 | 在基线基础上增量合并（CU 承接关系检测见 §3.3.4） | 全量提取 |
| CU 重识别 | 合并重识别可能导致已有 CU 承接的归属变更——标记 `[CU归属变更]` 并附变更原因 | 无此问题 |
| 变更传播 | 需输出变更影响声明（§4.2） | 写"首版，无变更" |

### 3.3 分解与分配规则

**一句话**：本节讲分解分配的规则——分解规则（3.3.1）、分配与收敛判定（3.3.2）、来源类型与证据强度（3.3.3）、Phase B CU 承接关系检测（3.3.4）。Phase B（修订已有 bpl-eng）与 Phase C（新建 bpl-eng）共用以下规则。

#### 3.3.1 分解规则（名称级识别 → 配置信息组（框架说明））

**名称级识别**：从当前操作范围内的全部 规范化的相关方需求 中识别可能触及的配置单元候选（名称级线索）。去重/收敛后形成配置信息组候选清单，每个候选 → 能力链上一个配置节点。多条 规范化的相关方需求 指向同一配置信息组时归入同一候选（要素收敛）。

**分解为配置信息组（框架说明）**：逐候选，按"可以运行的能力"识别配置信息组（§2.3.2）——每个配置信息组 = 一个可以运行的能力，回答"这组配置运行期产出/驱动什么"。产出为**配置信息组清单 + 每条框架性说明**（配置什么、运行期提供什么，结构判定级），**不展开操作活动定义**（配置操作/系统处理/运行期能力——那是 wft02-eng 业务流程概要）。分组判据（自 wft02-eng §2.2.1 迁入）：① 分组锚定**可以运行的能力**，不按字段技术关系；② 单字段即可提供一项能力则单字段成组，能力不可独立则合并；③ 可运行能力含业务人员可操作能力与系统侧运行行为两类——**可独立验证是组结构的下游属性**（组先能运行，才谈得上被验证/被消费）。**能力→操作衔接**：分组锚定的"可以运行的能力"在 wft02-eng 展开为**操作活动定义**（配置操作/系统处理/运行期能力，[wft02-eng §2.2.1](eos-wft02-eng-bpl2bpd.md)）——本 Skill 只给结构判定级框架说明，不展开操作步骤（能力在 02 展开，边界以"组 = 一个可运行能力"为锚，不被 02 的操作分解反推）。

**粒度判断**：对配置信息组候选判定 `可展开` / `过粗待拆` / `过细待并` / `边界待确认`——粒度过粗（`过粗待拆`）→ 分配时触发拆分；过细（`过细待并`）→ 触发合并（§3.3.2）。

#### 3.3.2 分配与收敛判定（配置信息组 → CU 承接）

**分配**：每个配置信息组（框架说明）（1:1）找到一个 CU 承接；同属一个 CU 的配置信息组构成该 CU 的能力点集合。分配时判定目标引擎/能力域——从 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景) 动态读取引擎清单与 CU 类型线索（每次运行时读取、不缓存），根据配置信息组能力特征匹配目标引擎。

**收敛判定**（"找一个 CU 承接"的决策，含对照 25 盘存的骨架判定）：

| 判定 | 条件 | 动作 |
|------|------|------|
| 确认既有 | 配置信息组能力已由既有 CU 承接（本 bpl-eng 基线或 25 已有类型），能力边界一致 | 归入该 CU，标注 `复用` |
| 扩展既有 | 既有 CU 主体一致，但配置信息组新增能力边界 | 归入并标注 `改进`（扩展 25 类型能力边界） |
| 新增 CU | 无可复用 CU，且 25 盘存无承接类型 | 设计新 CU 类型（走 25 类型模板，标 `[推断]`，人机协同设计决策点——AI 附判据理由，流水线开发者审核决策；操作活动定义由 wft02-eng 展开） |
| 拆分 CU | 候选 `过粗待拆`——配置信息组能力可独立、不共享一个 CU | 配置信息组分散到多个 CU（同一候选拆成多个 CU），标注 `拆分` |
| 合并 CU | 候选/配置信息组 `过细待并`——须同页配置、共同生成一个运行期能力 | 归入同一 CU，标注 `合并` |
| 占位 CU | 25 或引擎模型已有预定义能力，但本轮 bpl-eng 未触发 | 保留名称，占位不进入承接范围 |
| 退回上游 | 配置信息组需求侧无锚（§3.1 缺口锚定边界） | 不进承接，生成补充 FR-ENG（§5.5），待身份带回后再分配 |

> **骨架判定**（对照 25 盘存，与收敛判定并行标注 `[推断]`）：`复用` = 25 已有类型承接；`改进` = 扩展已有类型能力边界；`新增` = 盘存无承接、需设计新 CU 类型。判定是**人机协同设计决策点**而非机械规则：AI 基于对新增需求与已有资产的语义理解提出建议并附判据理由（为什么新增/改进、对照盘存为何无承接），流水线开发者审核、思考、决策、反馈，AI 落实后记录进 25——**25 是记录层，不裁决**；组织已有资产由人类整理记录（非本 Skill 设计），本 Skill 读盘存时按复用对待。

#### 3.3.3 CU 来源类型与证据强度

对每个配置信息组候选逐项判定要素并标注。标注字段见 §2.3.1。

**来源类型定义**（配置信息组候选/CU）：来源类型分两类——**需求侧来源（身份锚）**（来自 规范化的相关方需求 业务语义或业务侧缺口证据，能定位场景身份）与**资产侧参照（非身份锚）**（来自 25 盘存/同类模式，只提示可参考，不构成需求证据、不能单独支撑缺口 CU 承接，本 Skill §3.1 缺口锚定边界）。

| 来源类型 | 性质 | 含义（含示例） |
|----------|------|---------------|
| `规范化的相关方需求明示` | 需求侧 | 规范化的相关方需求 文本中直接说出该 CU。如"需要配置流程节点" → "流程节点配置"CU |
| `规范化的相关方需求隐含` | 需求侧 | 规范化的相关方需求 未直接说出，但不推出该 CU 则能力链存在逻辑缺口。如"流程发布后需支持回滚" → 必然需要"回滚配置"CU |
| `构件缺口推断` | 需求侧 | 规范化的相关方需求 描述业务页面需要某构件能力，但现有构件无法满足 → 推断需要新的构件配置 CU |
| `布局组件缺口推断` | 需求侧 | 规范化的相关方需求 描述页面操作方式现有布局组件无法承载 → 推断需要新的布局组件配置 CU |
| `同类引擎推断` | 资产侧（模式参照） | 同引擎类型已有 bpl-eng 的类似 CU 模式，当前 规范化的相关方需求 场景与之高度相似时推断 |
| `模型线索推断` | 资产侧（复用承接） | 复用承接标记——规范化的相关方需求 场景需要该能力（需求侧已锚定）时，25 资产存在与能力域匹配的现成 CU 定义承接 |

> **推断标注**：非 `规范化的相关方需求明示` 来源均为推断来源，标注 `[推断]`；其中资产侧参照（`同类引擎推断`/`模型线索推断`）不构成需求证据，不得单独作为缺口 CU 的承接依据——需求必须由需求侧来源给出（§3.1 缺口锚定边界）。

#### 3.3.4 Phase B CU 承接关系检测

Phase B 修订已有 bpl-eng 时，边界检查通过后，将本轮提取的配置信息组候选/配置信息组（框架说明）与 bpl-eng 已有 CU 承接关系比对。比对锚点为**CU 承接名称+目标引擎匹配**（对应配置信息组）。关系检测与对照盘存的骨架判定（§3.3.2）是两个并行维度：关系检测管承接与 bpl-eng 基线的新旧关系（下表），骨架判定管承接与 25 盘存的承接方式（复用/改进/新增）——两者并行标注，不互相替代。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | CU 承接匹配 + 引擎相同 + 至少一个来源非 `规范化的相关方需求明示` | 来源升级（`规范化的相关方需求隐含`→`规范化的相关方需求明示`、`构件缺口推断`→`规范化的相关方需求明示`、`布局组件缺口推断`→`规范化的相关方需求明示`、`同类引擎推断`→`规范化的相关方需求明示`、`模型线索推断`→`规范化的相关方需求明示`），内部细分结论=`确认` |
| 无新增 | CU 承接匹配 + 引擎相同 + 所有来源已为 `规范化的相关方需求明示` | 追加 规范化的相关方需求 引用 + 增量合并新 规范化的相关方需求 中的候选理由/粒度判断（如有新内容），内部细分结论=`改进` |
| 引擎归属变更 | CU 承接匹配 + **引擎不同**（合并重识别导致） | 更新已有 CU 承接的目标引擎 + 内部细分结论=`引擎归属变更` + 变更原因。不新增 CU |
| 补充 | CU 承接不匹配 | 新增到 CU 承接关系，来源=`规范化的相关方需求明示`，内部细分结论=`新增` |
| 过时 | 基线已有 CU 承接 **未被**本轮提取覆盖（引擎配置范围变更后，基线中某些 CU 不再落入新的能力链追踪范围） | 内部细分结论=`过时` + 追加说明"引擎配置范围变更后未落入新的能力链追踪范围，请确认是否移除"。保留该 CU 承接（不删除）——移除是架构决策，由流水线开发者反馈触发 |

关系检测前先基于**全部 规范化的相关方需求 重新识别目标引擎**——新 规范化的相关方需求 可能改变 CU 特征导致引擎归属变更（表中 `引擎归属变更` 行）。来源证据强度只升不降：`规范化的相关方需求隐含`/`构件缺口推断`/`布局组件缺口推断`/`同类引擎推断`/`模型线索推断` → `规范化的相关方需求明示`，在 `确认` 行触发（资产侧 `同类引擎推断`/`模型线索推断` 升级为 `规范化的相关方需求明示` 须伴随需求侧证据——新 规范化的相关方需求 显式说出该 CU；单独的资产侧提示不得升级）。

`[调整]` 是与关系类型正交的叠加标记：已有 CU 承接的名称/能力域/粒度判断变化，在关系标记之外叠加 `[调整]`。**配置能力扩展**（CU 配置信息组内容/配置要素/系统处理/运行期能力的变化）不构成 wft01 的收敛判定项——由 wft02-eng 详设修订时以 `[调整]` 标注（[wft02-eng §3.3.3](eos-wft02-eng-bpl2bpd.md)）。

## 四、bpl-eng 节点演进：生命周期与变更传播

**一句话**：本章讲 bpl-eng 节点设计与确认后的演进机制——生命周期（4.1，节点状态四态主线 + 上游变更分流 + 本 Skill 写回范围）与变更传播（4.2，修订后写变更影响声明告诉下游 wft02-eng）。

### 4.1 bpl-eng 节点生命周期

bpl-eng 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射按 §A.6 通用六态自声明：`待确认方案`/`可以详细定义`/`待补充详细定义`/`需wft01修订` 见下方主线流转与写回范围，`在详细定义`/`已详细定义` 由 wft02-eng 写入并推进。并行推进规则（资产线与 bpd-eng 线互不阻塞）见 91 规范 §A.6。分解分配已内化于本 Skill，交接状态反映 wft02-eng 的详细定义活动（DP1 定案）。

**主线流转**（wft01-eng ←→ wft02-eng）：

```
待确认方案 ──流水线开发者确认──→ 可以详细定义 ──wft02锁定──→ 在详细定义 ──wft02完成──→ 已详细定义
     ↑                        ↑                         │
     │                        │               wft02退回  │
     │                        │                         ↓
     └─── wft01修订 ────── 需wft01修订 ←───────────────┘
```

**上游变更**（新 规范化的相关方需求 汇入触发 bpl-eng 修订）：

```
可以详细定义 ──新规范化的相关方需求修订──→ 可以详细定义（版本递增，wft02 未消费）
在详细定义   ──新规范化的相关方需求修订──→ 在详细定义（版本递增，wft02 增量处理）
已详细定义   ──新规范化的相关方需求修订──→ 待补充详细定义 ──wft02补全──→ 已详细定义
```

**本 Skill 的写回范围**：`待确认方案` / `可以详细定义` / `待补充详细定义` / `需wft01修订`。`在详细定义` 和 `已详细定义` 由 wft02-eng 写入和推进。

下游退回 `需wft01修订` 时：读取 wft02-eng 的缺失说明 → 按流水线开发者的改进方案修订 bpl-eng（走 Phase B 修订流程，含分解分配重识别）→ 流水线开发者确认 → bpl-eng → `可以详细定义`。

| 3 | 场景业务设计 | Phase A 路由 / B 修订 / C 新建 + R 装配 + 名称级识别分解配置信息组 + 分配配置信息组到 CU 承接 | **有**——设计决策审核（分解分组/分配收敛判定、骨架判定、引擎归属），对话反馈 | 统一（AI 产出带判据理由）+ 对话 | bpl-eng 节点方案（能力链 + 配置信息组（框架说明） + CU 承接关系） | `01/02` |

| 5 | 资产写回与落账 | 23/25 写回 + 推进 规范化的相关方需求 + 提交基线 | 无（AI 自动，写回已确认节点） | 统一 | 23 引擎引用 + 25 CU 承接引用 + 规范化的相关方需求→已分配 | `23/25/01/02` |
| Step End | 运行结束输出 | 三区摘要输出 + 等待人类反馈 | **有**——查看摘要、对话反馈 | 对话 | 人类下一步操作提示 | — |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话 = AI 输出后需要你说句话（反馈或确认）才继续。Step 1/3/4/5 为运行内自动步骤——其中 **Step 3 是设计步骤（人机协同交互密度最高处）**：AI 基于对新增需求与已有资产的语义理解产出方案并附判据理由，人类在 Step End/Step 2 对设计决策（分解分组/分配收敛判定、骨架判定、引擎归属）审核、思考、决策、反馈，AI 落实；Step 2 / Step End 为人机交互步骤（对话反馈，见 §5.3）。

**反馈机制一句话**：反馈走**自然语言对话**（AI 产出方案后不结束对话，§5.3）；跨轮余留反馈由 AI 标 `[修改]`/`[驳回]` 入"待反馈处理"分节（§5.3 状态机）；人类线下修订经 Step Start 变更感知（git diff，§5.1 变更感知）检出后纳入"待反馈处理"分节；AI 每轮写回提交基线（§5.6），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

### 5.1 Step Start

**一句话**：先变更感知（检出人类线下修订并纳入待反馈分节），再按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策路由（退回优先 → 反馈处理 → 新输入），无待处理对象即退出。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来流水线开发者或 EOS 开发者是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 规范化的相关方需求）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

**入口判定**（在变更感知后执行）：读取 `01-*.md`/`02-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表，再按以下顺序处理：

| # | 入口条件 | 检测方式 | 对应分节 |
|---|---------|---------|---------|
| ① | **有新输入** | AI可以处理节点「待 wft01-eng 处理」分节非空 | §11.7 |
| ② | **有待处理反馈** | AI可以处理节点「待反馈处理」分节含本 Skill 产出节点 | §11.7 |
| ③ | **有下游退回节点** | AI可以处理节点「待下游退回处理」分节含状态为 `需wft01修订` 的节点 | §11.7 |

三类均不满足 → 输出"无待处理对象"→ **退出**。

#### 5.1.1 输入校验

入口检测通过后进行输入校验。以下校验中逻辑上不可能的条件为硬退出（输出提示后退出），数量/归属模糊条件为软提示（输出提示后由流水线开发者选择继续或退出）：

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 规范化的相关方需求 状态不是 `待处理` | 状态不符（硬退出） | 输出不合格条目及当前状态 → **退出** |
| 规范化的相关方需求 类型不是 FR-ENG（含 FR-BIZ） | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft01-biz` → **退出** |
| 规范化的相关方需求 类型不是 FR-ENG（含 NFR） | 类型不匹配（硬退出） | 输出类型分布，提示走 `wft01-nfr` → **退出** |
| 规范化的相关方需求 为业务配置实例 | 实例标记（硬退出） | 标记并提示不进入 eng 设计 → **退出** |
| 规范化的相关方需求 是 wft03-biz 线索但未转规范化的相关方需求节点 | 未正式化（硬退出） | 输出"输入未正式化"，提示先确认并写入 `01-*.md` → **退出** |
| 规范化的相关方需求 无法判定唯一主责能力域或独立验收结果 | 归属/边界不明（硬退出） | 输出归属/边界不明条目，标记 `需澄清` → **退出** |
| 规范化的相关方需求 >10 条 | 数量超限（软提示） | 输出超限提示 → 流水线开发者确认后继续或退出 |
| 规范化的相关方需求 跨多个引擎 | 引擎混杂（软提示） | 输出引擎混杂提示 → 流水线开发者确认拆分后继续或退出 |

> 软提示不强制退出，由人类选择继续或退出；硬退出为逻辑上不可能的条件，输出后退出（§A.4.5）。

#### 5.1.2 退回优先（§A.4.3 门禁）

存在 `需wft01修订` 的 bpl-eng 节点（来自"待下游退回处理"分节）：
- 检查流水线开发者是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注 `[修改]`/`[同意]` 或下游 Skill 产出的具体改进指引）
- 已提供 → 通过门禁，读取 wft02-eng 的缺失说明，按流水线开发者的改进方案走 Phase B 修订（§5.4.2），流水线开发者确认后推进为 `可以详细定义`
- 未提供 → 输出 wft02-eng 的缺失说明 + 提示提供改进方案 → **退出**

#### 5.1.3 反馈处理

存在"待反馈处理"分节中的 bpl-eng 节点（条目确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`，标记定义与写入者见 §5.3）→ 进入 Step 2 处理（§5.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 规范化的相关方需求，Step End 时提示。

#### 5.1.4 新 规范化的相关方需求 路由

有未处理的 规范化的相关方需求条目（来自"待 wft01-eng 处理"分节）→ 进入 Step 1→Step 3，逐条执行 Phase A 溯源与路由（§5.4.1），归入已有 bpl-eng（→Phase B）或待聚合池（→Phase C）。

**执行顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 bpl-eng 的边界/能力链/分解分配（配置信息组（框架说明）/CU 承接）。Step 3 的 Phase A 宿主匹配必须基于 Step 2 修改后的最新 bpl-eng 内容，不得使用缓存旧状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类反馈的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `01-*.md`/`02-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.6），保证下一轮 diff 只含人类变更。

**本 Skill 的条目**：场景边界 + 能力链 + R 上下文 + 每个配置信息组候选 + 每个配置信息组（框架说明）+ 每条 CU 承接 + 每条补充 FR-ENG 材料。各条目的 `确认状态` 字段位于 `02-*.md` bpl-eng 节点块各条目正文中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.3）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.6），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

**触发条件**：Step Start 检出 `需wft01修订` bpl-eng，或上一轮 Step End 的反馈等待中人类提出修改意见。

**处理规则**：

1. 从当前轮次对话上下文或退回缺失说明中读取人类反馈意图
2. **逐条处理**（按人类反馈内容）：
   - AI 输出方案后人类直接回复修改意见 → 在当前轮次继续对话处理，不重新走 Step Start
   - wft02 退回的 `需wft01修订` → 下一轮 Skill 调用时走 Step Start 退回优先
3. 修改后检查是否仍满足该 bpl-eng 所承接的 FR-ENG 规范化的相关方需求节点 需求
4. 修改导致结构性变更（边界/能力链/分解分配重组）→ 按需重入 Step 3
5. 全部条目获流水线开发者认可 → bpl-eng → `可以详细定义`

按 [91 规范 §A.5.3](91-eos-biz-eng-spec.md#a53-ai-处理流程) 的流程处理人类自然语言反馈：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足 FR-ENG 规范化的相关方需求节点 需求 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 推进 bpl-eng 至 `可以详细定义` → **提交基线并更新 HEAD（机制见 §5.6，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

> **原则**：反馈处理不是对流水线开发者标注的机械执行，而是以 规范化的相关方需求 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解流水线开发者反馈在 规范化的相关方需求 需求语境中的含义，再执行修订，最后检查修订后的 bpl-eng 是否仍满足 规范化的相关方需求 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 本 Skill 的锚点是 FR-ENG 规范化的相关方需求节点——反馈处理以 规范化的相关方需求 需求理解为锚，不脱离 规范化的相关方需求 文本内容自行修订 |

### 5.4 Step 3 · 场景业务设计

#### 5.4.1 Phase A：规范化的相关方需求 溯源与路由

对每条新 规范化的相关方需求 执行溯源提取（触发来源 + 能力诉求 + 运行期结果 + 主能力域，详见 §3.2.1）。先判定路径归属——实际为业务输出文档/流程→退回 `wft01-biz`，实际为性能/安全等约束→退回 nfr 路径，仅为业务配置数据→标记不进入 eng 设计。路径确认后，逐条按主能力域（引擎）做宿主匹配：

| 条件 | 路由 |
|------|------|
| 规范化的相关方需求 的主责能力域、配置/治理目标和独立验收结果均命中已有 bpl-eng | 归入该 bpl-eng → Phase B |
| 规范化的相关方需求 的主能力域尚无对应 bpl-eng | 进入待聚合池 → Phase C |

待聚合池按**主能力域（引擎）**分组。此阶段仅粗略分组，配置信息组候选去重和完整分解分配在 Phase C 执行。

#### 5.4.2 Phase B：修订已有 bpl-eng

1. **要素提取**：从本轮 规范化的相关方需求 提取触发来源（规范化的相关方需求 级上下文）、能力诉求、运行期结果和主能力域（详见 §3.2.1）。先提取后检查——主引擎不一致时退回待聚合池
2. **场景匹配检查**：确认 规范化的相关方需求 与 bpl-eng 的主责能力域、目标和验收结果一致（详见 §3.2.4）
3. **分解分配重识别**：从本轮 规范化的相关方需求 对涉及的配置信息组候选重新分解（候选→配置信息组（框架说明），§3.3.1）、重分配 CU 承接（收敛判定，§3.3.2），再执行 CU 承接关系检测——比对已有基线，判定确认/无新增/引擎归属变更/补充/过时（详见 §3.3.4）
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 bpl-eng 节点末尾（详见 §4.2）

#### 5.4.3 Phase C：新建 bpl-eng

1. **确定引擎** → 从 规范化的相关方需求 语义提取主能力域（详见 §3.2.1）
2. **装配 R 上下文** → 从 规范化的相关方需求 触发来源与 23/24 资产装配业务运行对象/配置角色/触发事件/状态影响（详见 §3.2.2）
3. **定义能力场景范围** → 判定配置/治理目标→系统处理→运行期产出→独立验收，输出场景边界陈述（详见 §3.2.3）
4. **构建能力链** → 按配置→处理→运行期→可用确认排列，标注依赖关系（详见 §2.2）
5. **分解** → 识别配置信息组候选清单（名称级 CU 候选）+ 逐节点分解为配置信息组（框架说明）（按"可以运行的能力"识别，§3.3.1，含粒度判断与来源类型标注）
6. **分配** → 逐配置信息组找 CU 承接（1:1），执行收敛判定（复用/新增/拆分/合并，§3.3.2）+ 对照 25 盘存骨架判定 + 来源类型标注（§3.3.3）
7. **标注 规范化的相关方需求 类型** → 逐条 规范化的相关方需求 判定其 FR-ENG 规范化的相关方需求节点 类型（配置生成类 / 构件扩展类 / 布局组件扩展类 / 横切治理类 / 运行支撑类，详见 §2.1.1），作为 规范化的相关方需求 级能力诉求特征——不用于划分 bpl-eng 边界
8. **组装 bpl-eng** → 引擎名称 + 场景边界陈述 + 能力链 + R 上下文 + 配置信息组候选 + 配置信息组（框架说明）+ CU 承接关系 + 推理依据，写入 `02-*.md`（完整要素见 §2.1.2）

### 5.5 Step 4 · FR-ENG 需求增补

Step 4 按每个 bpl-eng 实例独立执行。新建 bpl-eng → 全量检查；修订已有 bpl-eng → 仅当分解分配拓扑变化（新增/过时/引擎归属变更/拆分合并）时重验闭合，要素机械检查始终针对变更文档执行。

**1. 能力链闭合检查**

- 逐 bpl-eng 检查能力链四段闭合（四段定义见 §2.2.1）：配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认

- 可用性确认段缺失（缺少"何时算配置完成、能力可用"）→ 缺口类型 = `澄清项`
- 配置信息组候选 `过粗待拆` → 缺口类型 = `拆分建议`，交流水线开发者裁决
- 缺口 → 进入「补充 FR-ENG 材料生成」。不因缺口脑补节点——缺口就是缺口
