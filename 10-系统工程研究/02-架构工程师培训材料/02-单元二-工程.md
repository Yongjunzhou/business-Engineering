## 一、单元导读

### 主题

这一章回答全书最基础的问题：**我们到底在做什么——是工程，还是包装成工程的手艺**。它给出两样能当场用的东西：**一句定义**（工程 = 科学原理 × 判断创造，在约束下，用系统方法，造出有用且安全的东西），和**一条判据**（试金石——换个人、换团队，用同样的需求和约束，还能不能同等交付质量相当的成果）。

本章的骨架是一条从下往上垒的定义链：**工程 → 它的四样 → 它的四层 → 它的成色 → 它的两种系统**。四样是料（科学原理 × 判断创造）／框（约束）／路（系统方法）／果（有用且安全），缺"料"是空谈、缺"框"是失控、缺"路"是碰运气、缺"果"是自娱自乐。四层是工程科学 → 方法论 → 工具与实践 → 价值与伦理，每一层都是一道把交付从人身上挪走的关，缺哪一层就有一样东西重新落回某个人身上。成色看六面（有结构／有方法（含判断）／可重复／全覆盖／受控／可验证）。两种系统是**工程系统包含技术系统**——技术只是内核，承诺的是整个社会技术系统能运转。验收那一头挂着两把不可互推的尺子：**验证对规定需求**（做对了吗）、**确认对预期用途**（做对了东西吗）。

本章的**根概念（承重柱）只有一个：工程**——试金石、四层、六面、两种系统全由它导出，它却不由这些概念定义；约束与判断创造是定义内部的构成，不是根。全章的主张一句：**工程是把交付从人身上挪到方法上的一次转移，挪得走的是方法，挪不走的是判断。**

### 开场破题（对应章首误解现场）

念出恒信集团 IT 部那场季度会：上半年最后一天，系统架构师罗建站在投影前——"各位，我们敏捷转型成功了。双周迭代、CI/CD 全绿、自动化测试覆盖率 80%。按 IEEE 610.12 那三个词——systematic、disciplined、quantifiable（中译：系统化的、规范的、可度量的）——我们一条不缺。我们已经是工程化团队了。"会议室里响起稀稀拉拉的掌声。

产品开发经理曹峰接过话头："系统上线了，指标也全绿——我们交付的东西跑起来了，工程就算成了。"运维王默低头看了一眼手机：监控上，月末高峰的曲线又拱了起来，他想起上个月那场事故，想说什么，又忍住了。掌声落下去之后，只有需求分析师顾言低声问了一句："那……上个月上线那次事故，是为什么？"罗建愣了一下："那是人手不够，临时赶工。跟工程化没关系。"

让各组表态：罗建说得对不对？（他说的每一样都真——迭代真的双周、流水线真的全绿、覆盖率真的 80%。）那问题在哪？为什么"每一样都真"，这个团队还是出事了？曹峰那句"上线了工程就算成了"，又漏了哪一层？如果坐在这间会议室里你也会点头，那点头的到底是什么直觉？

### 本单元要反转的直觉

- **有流程、有工具、有测试、有敏捷，就是在做工程**（× 敏捷与 CI/CD 只占方法论和工具与实践两层；工程还有工程科学、价值与伦理）
- **用了敏捷 + CI/CD + 测试，就是在做软件工程**（× 那两层齐了不等于四层齐了；工程化没做，不看流程多完整，看压力面前会不会为质量让路）
- **系统上线了、指标全绿，工程就算成了**（× 上线只是技术系统的完成点；工程系统看"被用起来"——人会用、流程顺、组织撑得住）
- **事故是"工程之外"的意外**（× 事故恰恰是"不是工程"的证据——为进度砍可靠性、还不留记录）
- **试金石测的是这个团队牛不牛**（× 它测可复制性，不测能力高低；问的是"你不在的时候，团队还牛不牛"）
- **约束是工程的附加项，越少越好**（× 约束是定义的一部分；没有约束就没有判断的空间，约束越多判断越值钱）
- **完全可复现才是工程的极致**（× 纯可复现是算法；工程是可复现的方法 × 不可复现的判断）
- **工程就是科学的应用，科学比工程高一级**（× 一个求真，一个求有用；科学家研究现存的世界，工程师创造从未存在的世界）
- **工程的对立面就是科学**（× 工程没有单一对立面：认识论对科学、方法论对手艺、目标对艺术）
- **手艺是贬义词，工程化就是把老手艺人废掉**（× 手艺不是贬义词；工程化是把个人能力变成组织能力）
- **上了 CI/CD、有了自动化测试，就不是手艺了**（× 载体换了、方法没换；靠三条隐藏命令跑起来的流水线仍是手艺）
- **方法论就是工程**（× 方法论只是工程从上往下立起的第二层）
- **系统化就是把流程固化成算法、让机器自动跑**（× 系统化是"有章法的判断"，算法化是"确定性执行"；本章的"机械化"专指 algorithmic）
- **流程越繁琐，系统化程度越高 / 有流程就有工程**（× 系统化的本质是可检查，不是多；流程化不等于工程化）
- **自动化程度越高越安全、越接近工程 / 自动化了人就不用判断了**（× 判断被提纯，不是被消灭；自动化还拿走了人阻止事故的能力——工程要"错误可见"，自动化追求"零错误"）
- **微服务每个都健康，系统就是健康的**（× 涌现属性：调用链、数据一致性、超时熔断没人管，上线必出事）
- **需求全部验证通过了，这个系统就成了**（× 验证对规定需求、确认对预期用途，不可互推）
- **软件看不见摸不着，应该算概念系统**（× 它有运行环境、有生存周期，本身是技术系统；加上人、流程、组织才是工程系统）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 工程是什么、四样各管什么、约束凭什么不算麻烦（破题 · 概念本身，从章首季度会切入）→ Q2 工程、方法论、工程化、工程系统、系统工程五个词怎么串（概念关系：方法＜方法论＜工程、工程系统⊃技术系统、递归两层）→ Q3 三个对立面都对，凭什么一条判据把它和手艺分开（真悖论 · 无单一对立面与试金石，落石军请假两周）→ Q4 工具与流程都齐了还缺什么、一次妥协怎么就判成失守（真悖论 · 四层缺层回落与失守三问，落三起事故与"先上再说"）→ Q5 自动化程度越高，是越接近工程还是越远离（真悖论 · 系统化≠算法化，落 737 MAX 那两道关）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 三条隐藏命令与两个环境变量究竟坏在哪（判据运用 · 试金石落到具体物件，落王默与小张）→ Q7 给恒信的敏捷转型按六面打分，缺的是"差一点"还是"差一半"（判据运用 · 工程化成色与系统化自问）→ Q8 部件全对、系统为什么未必对；"上线"为什么不算工程成功（判据运用 · 元工程与涌现、工程系统与技术系统、验证与确认）→ **Q9 方法时刻·反记忆崇拜 + 转述**（规则 15：亲手给一个"××工程"立可检验定义，把它量到最近一次交付上；含**三五句转述给完全外行**；跨域变体：换到冰链 M3 判据变不变）→ Q10 回部门工程成色体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章是**恒信主、冰链镜**的强镜照章：恒信那边是**把技术系统当工程系统验收**——部署好了、模块全上线、指标全绿，法务还是线下签、财务还是手工台账、业务还是走邮件（§2.4.4）；冰链那边是**手艺一条、工程一条同时在场**——石军几十年的判断全在脑子里，他一请假，一个批次出问题产线没人能定位（§2.3.2），而小张把那些"该查哪里"逐条抄进清单、抄不下去的圈出来注一句"只在人身上"（§2.3.2），小周问的是"箱子什么时候算成了——不是下线那刻，是装进冷链车、温度被全程追溯、断链真告警了"（§2.4.3）。两边的病灶是同一处：**判断只在人身上、验收只看设备跑起来**；两边的解药也是同一件：**把判断显性化成可教、可查、可检的东西，把验收参照换成"被用起来"**。这正是本章"工程系统包含技术系统"与"可复现才算工程"两条判据不挑行业的现场证明。本章的承重柱是**工程**：四样、四层、六面、两种系统都是它的展开，两组都能拿"料／框／路／果缺哪一样、缺哪一层、换个人还成不成"核自己的交付。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜"我们已经是工程化团队了"——工程到底是什么？**
"恒信集团 IT 部的季度会，上半年最后一天。罗建站在投影前：『我们敏捷转型成功了。双周迭代、CI/CD 全绿、自动化测试覆盖率 80%。按 IEEE 610.12 那三个词——systematic、disciplined、quantifiable（中译：系统化的、规范的、可度量的）——我们一条不缺。我们已经是工程化团队了。』产品开发经理曹峰接过话头：『系统上线了，指标也全绿——我们交付的东西跑起来了，工程就算成了。』散会后顾言低声问：『那……上个月上线那次事故，是为什么？』罗建答：『那是人手不够，临时赶工。跟工程化没关系。』——**工程到底是什么？那句定义里每一样各管什么？为什么"约束"不是麻烦，而是定义的一部分？**"

追问：① 定义的四样各是"料／框／路／果"的哪一个？缺哪一样会变成空谈、失控、碰运气、自娱自乐？系统方法保证的那三个"可"（可计划／可度量／可复现）为什么相互咬合？② 罗建那三个形容词，是在给谁下定义——工程，还是软件工程？它们说的是定义，还是工程化的过程表现？③ "从哪来"：1941 ECPD 那份最早的工程定义里同时写着哪两条？1979 ABET、2019 INCOSE 又怎么说——凭什么说三家几十年走到了同一个内核？engineering 那个词从哪个拉丁词来、本义是什么？④ 反身：你部门最常用的那个"××工程"（信息工程、管理工程、数据工程……），你现在能当场答全这四样吗？

**Q2｜工程、方法论、工程化、工程系统、系统工程——这五个词怎么串？**
"请画出 **工程、方法论、工程化、工程系统、系统工程** 五个词的关系，并回答三件事：方法论在工程里占哪一层？工程化的六个方面各自出自哪三个英文词？系统工程不造任何部件，凭什么叫『元工程』？"

追问：① 方法、方法论、工程三个词差在哪（一条具体做法／关于怎么组织工作与选方法的系统学说／完整的人类实践）？瀑布、敏捷、CMMI 落哪一层？② systematic（系统化）、systemic（系统性）、algorithmic（算法化）各回答什么问题？本章说的"机械化"专指哪一个？③ 工程系统与技术系统是什么关系？软件算不算概念系统——它加上什么才是工程系统？"系统"这个词递归了几层，软件工程内部会不会也长出"软件系统工程"？④ 反身：你们部门那套"流程"，落在链上的哪一环——系统化、工程化、流程化，还是信息化？录完之后有人核对吗、出错查得到记录吗？

**Q3｜三个对立面都对，凭什么一条判据就能把它和手艺分开？**
"有人说工程的对立面是科学，有人说对立面是手艺，有人说对立面是艺术。**三个说法都对吗？如果都对，凭什么一条判据就能把工程和手艺分开？**"

追问：① 三个维度各问什么（发现还是创造／可复现还是依赖个人／满足用户还是表达自我）？② 试金石测的是能力高低还是可复制性？团队交接、招聘、复盘三处各怎么问？③ 为什么说"手艺不是贬义词"——冰链石军请假两周、回来十分钟定位，这条案例按试金石量出来的是什么？小张那句"这张单子换个人拿着，还能不能做出同样的判定"问的是哪一样东西？④ 反身：你团队里最值钱的那个人请两周假，交付还维持得住吗？

**Q4｜工具与流程都齐了，还缺什么？一次妥协怎么就判成了失守？**
"敏捷、CI/CD、测试都齐了，还缺什么？有人说不缺——工具和流程都上了；有人说缺两层——工程科学和价值与伦理。**缺了到底会怎样？又怎么判断一次妥协是失守，还是客观原因？**"

追问：① 四层各是什么？缺哪一层，就有哪一样东西重新落回某个人身上——这四句话你各说得出吗？判断与底线为什么不是一回事？② "前三层缺了是不专业，第四层缺了是会出事"——为什么第四层最致命？泰坦尼克号、挑战者号、737 MAX 三起事故缺的是哪一层？③ 失守三问是哪三句？为什么说"客观原因不会专门留记录"？④ 反身：你们最近一次"先上再说"，三问答得出几个"是"？

**Q5｜自动化程度越高，是越接近工程，还是越远离工程？**
"既然算法化是『确定性执行、无需判断』，而工程是『有章法的判断』——**自动化程度越高，是越接近工程，还是越远离工程？**"

追问：① 系统化有哪几个可操作的特征？判一份流程是系统化还是装饰，问哪三句？"给软件加一个新功能"那两套做法，差别落在哪一句上？② 系统化的目的到底是消灭不确定性，还是把不确定性纳入可控范围？敏捷为什么"高度系统化，却一点谈不上算法化"？③ 自动化拿走了什么、又提纯了什么？737 MAX 的 MCAS 那两道关——权限关与能力关——各是什么？④ "工程要错误可见，自动化追求零错误"，这句为什么能推出"消灭判断就是消灭工程"？⑤ 反身：你们那个全自动的发布或对账流程，人手上还剩哪几类判断？

### 第二组 · 落地与实践

**Q6｜三条隐藏命令、两个环境变量，究竟坏在哪？**
"§2.4.5 项目一：换个团队来运维恒信的 CI/CD，能一样跑吗？王默摇头：换个人来，光那三条隐藏命令就够他找一天；还有两个环境变量，写在某个人的备忘录里，不在任何文档里。他说这一项他认——按 §2.2.4 那条判据量，这个团队不合格。**这三条命令、两个环境变量，究竟坏在哪——坏在没写文档，还是坏在别处？**"

追问：① 按试金石量，这是不合格的人，还是不合格的工程？王默认下的那一项，认的到底是哪一件事？② 载体换了（从脑子换成脚本），手艺变了吗？凭什么说"工具不会自动把人从手艺变成工程，可复现才会"？③ 小张把石军那些"该查哪里"逐条抄下来，抄得下去的写进清单、抄不下去的圈出来注一句"只在人身上"——她那张单子的判据是哪一句？④ 反身：把你这周的三次口头交接写下来，有几次是"只在人身上"？

**Q7｜给恒信的敏捷转型按六面打分：缺的是"差一点"，还是"差一半"？**
"给恒信的敏捷转型打分：有结构、有方法（含判断）、可重复、全覆盖、受控、可验证——**哪几样缺？缺的是『差一点』，还是『差一半』？**"

追问：① 六面各出自 systematic、disciplined、quantifiable 的哪一个？"受控"和"可验证"各自要什么才算有（有基线、有变更控制／有证据、可检查、可度量）？② 那个"先上再说"的接口，六面里缺哪几面？③ 系统化三问照上去，"换个执行者，结果还稳定吗"为什么答不上来——这一问和项目一那句"换个人还能不能交付"是同一件事吗？④ 反身：拿这六面给你们最近一次上线打分，哪一面最不敢写？

**Q8｜部件全对，为什么系统未必对？"上线"为什么不算工程成功？**
"法务、财务、业务三个模块单看都能验收，集成那天还是出了事。**部件全对，为什么系统未必对？『系统上线了』为什么不算工程成功？**"

### Q1 "我们已经是工程化团队了"——工程到底是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "罗建说得对：有 CI/CD、有测试、有覆盖率，就是工程化；事故是人手不够，跟工程化没关系。" | 正是要翻的——把"有流程有工具"当"在做工程"、把"事故"当"工程之外" |
| 中 | 能背出"工程 = 四样"，但说不清恒信缺哪一样，也不关心这句定义是从哪来的 | 定义是背的，判据没上手——没落到打勾，也没落到溯源 |
| 好 | "四样逐条打勾：料——容量评估被砍，'为什么能行'没依据；框——月末高峰这个约束没人识别、没人命名、没人立项；路——CI/CD 在，但变更受控不在；果——系统上线了，可新流程没人用。事故不是意外，是缺价值与伦理那一层的证据。那三个形容词出自 IEEE 610.12 的软件工程定义、讲的是工程化的过程表现，不是工程的定义。约束之所以不是麻烦，是因为没有约束就没有判断的空间。" | 定义 + 判据 + 出处分辨 + 案例全咬合，能当场给恒信下结论 |

**产品侧 vs IT侧**：产品组打勾"冰链 M3——硬件、固件、云端、App 全跑通，但冷链流程没进、没人按流程用"；IT 组打勾"恒信——CI/CD 在、变更受控不在、'有用'没人验收"。曹峰那句"指标全绿 = 工程成了"，两边都能在自己部门找到同一个版本（"样机跑了 = 产品成功"／"部署上线 = 项目成功"）——**四样是诊断清单，不是贴标签**。

**反转话术**（对应 §2.1.1 / §2.2.1 / §2.2.2 / §2.2.3）：罗建那句话错在一处最要紧的地方——他把"有方法论、有工具"当成了"在做工程"。工程有一句硬核定义，本书对 ECPD、ABET、INCOSE、IEEE 610.12 几份权威定义的**凝练**（不是任何标准的原文）：**工程 = 科学原理 × 判断创造，在约束下，用系统方法，造出有用且安全的东西。** 四样各司其职：科学原理 × 判断创造是"料"，约束是"框"，系统方法是"路"，有用且安全是"果"——缺了料是空谈，缺了框是失控，缺了路是碰运气，缺了果是自娱自乐。那个"×"不是装饰：判断创造是把原理用活的动作（选哪个模型、怎么取舍、何时偏离标准做法），它不单独占位，却贯穿每一步。**约束尤其要翻**：它不是工程的附加项，是定义的一部分——1941 年 ECPD 那份最早的工程定义里，就同时写着"运行经济性"和"生命财产安全"；没有约束，就没有判断的空间，**约束越多，判断越值钱**（防过头一句：无意义的限制、纯官僚式的流程不产生判断价值，那只是限制，不是约束）。定义不是本书发明的：ECPD 1941 → ABET 1979 → INCOSE 2019，年代不同、领域不同，却走到同一个内核（科学原理／判断创造／约束权衡／造福目的／系统方法）；IEEE 610.12-1990 那条只从软件一侧贡献"系统方法"一面，而且它定义的是软件工程——原话是 *the application of engineering to software*（中译：把工程应用于软件），把"工程"当已知概念引用。engineering 这个词来自拉丁 *ingenium*（中译：天生的才智、巧思）——它一开始就不是"科学的应用"。会后顾言给的那张白板打勾最见分量：王默报了三年数据，"约束"那一格是空的——"报警只是数据，约束要有人识别、有人命名、有人立项，写成一条有人守的规则才算数"。

**参考答案要点**：定义与四样见 §2.2.1／§2.2.2；四家权威定义与出处分辨见 §2.2.3；试金石见 §2.2.4；案例进展①（四样给恒信打勾、王默"我报的是数据，不是约束"、郑亮"没人用就等于没交付"）；章首误解现场见 §2.1.1。

### Q2 工程、方法论、工程化、工程系统、系统工程——这五个词怎么串？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 把五词排成一条包含线（工程 ⊂ 方法论 ⊂ 工程化 ⊂ 工程系统 ⊂ 系统工程），或当成同义词堆在一起 | 关系结构错——方法论是工程的一层、工程化是"做起来是什么样"、两种系统是包含关系、系统工程是"工程之上的工程" |
| 中 | 说得出"系统工程 = 元工程"，但工程化六面的出处与工程系统 ⊃ 技术系统没接上 | 元工程对了，出处三词与包含关系缺 |
| 好 | "方法＜方法论＜工程（一条具体做法＜系统学说＜完整的人类实践）；方法论只是工程从上往下立起的第二层；工程化六面出自 systematic（有结构／有方法含判断／可重复／全覆盖）、disciplined（受控）、quantifiable（可验证）；系统工程不造部件、只造整体，把总需求分解分配、定义接口、完成集成、再做两道判定，所以在工程之上，叫元工程；工程系统包含技术系统，技术系统是内核，软件本身只是技术系统，加上用户、业务流程、运维组织才是工程系统；'系统'是递归的——软件足够大，内部也长出'软件系统工程'。" | 四层关系 + 六面出处 + 元工程 + 包含与递归全到位 |

**产品侧 vs IT侧**：产品组答"M3 温控箱＝技术系统（硬件／固件／云端／App），进了冷链流程、法规义务、批次追溯才算工程系统"；IT 组答"合同审批平台部署上线＝技术系统，法务财务业务真用起来才算工程系统"。两边都容易漏"软件工程内部也需要系统思维"——**软件足够大时，接口契约、集成测试、端到端验证这些活自己会长出来**。

**反转话术**（对应 §2.3.3 / §2.3.4 / §2.4.1 / §2.4.3）：先分三个最容易混的词——**方法**是一条具体做法，**方法论**是"关于怎么组织工作、怎么选方法的系统学说"（瀑布、敏捷、CMMI），**工程**比前两个都大，方法论只是它的一部分。工程从上往下立着四层：工程科学（依据什么）→ 方法论（怎么组织）→ 工具与实践（用什么做）→ 价值与伦理（为了什么）。工程化讲的是"做起来是什么样"，那句出处要分辨清楚：IEEE 610.12 的三个形容词出自对**软件工程**的定义，讲的是"工程化的过程表现"，不是工程本身的定义——严谨的说法是"据 IEEE 610.12 对软件工程的定义，工程化的过程表现为……"。三个词各展开一面：systematic 展开成有结构、有方法（含判断）、可重复、全覆盖；disciplined 展开成"受控"（有基线、有变更控制）；quantifiable 展开成"可验证"（有证据、可检查、可度量）。系统工程为什么不造部件：**它把总需求分解分配给各部件工程、定义接口、在系统层面完成集成，再做两道判定（系统级验证与系统级确认）**——所以叫*meta-engineering*（中译：元工程），工程之上的工程。下面这条包含关系最常被弄错：**工程系统包含技术系统**。技术系统只由人工技术组件构成、人只是使用者；工程系统是被设计或改造的、与预期运行环境交互、达成预期目的、遵守适用约束的系统——人、产品、服务、信息、流程甚至自然元素都算。软件为什么不算概念系统：它有运行环境、有生存周期，**本身仍是技术系统**；加上用户、业务流程和运维组织，才是工程系统。

**参考答案要点**：方法／方法论／工程见 §2.3.3；四层见 §2.3.3；工程化三词与六面见 §2.3.4；系统工程与递归见 §2.4.1；工程系统与技术系统、软件不归概念系统见 §2.4.3；概念档案见书末附录 B（工程完整九格）与附录 A（T-13／T-17／T-19／T-20／T-22）。

### Q3 三个对立面都对，凭什么一条判据就能把它和手艺分开？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "对立面当然是科学，其他说法都不对"——或反过来"各有各的说法，说不清" | 正是要翻的——一个词只许有一个对手 |
| 中 | 三个维度报得出，但试金石的用途只说到"判断谁厉害" | 维度对了，判据读歪——试金石测可复制性，不测能力高低 |
| 好 | "三个都对，因为它们站在不同维度：认识论对科学（发现还是创造）、方法论对手艺（可复现还是依赖个人）、目标对艺术（满足用户还是表达自我）。和手艺分开靠试金石：换个人、换团队，同样的需求与约束还能不能同等交付——能是工程，不能是手艺；它测的是可复制性，问的是'你不在的时候团队还牛不牛'。石军请假两周、产线没人能定位，回来十分钟找出问题——这就是手艺，而经验丰富的老工程师本身仍是最值钱的资产：工程化不是把人废掉，是把个人能力变成组织能力。" | 三维 + 判据 + 手艺不是贬义 + 案例定性全到位 |

**产品侧 vs IT侧**：产品组举"老师傅手感：哪种工况要降额全在他脑子里"；IT 组举"那套只有某个人跑得起来的 CI/CD（三条隐藏命令、某个人备忘录里的两个环境变量）"。两边都是同一把尺子——**它测的不是"你牛不牛"，是"你不在的时候，团队还牛不牛"**。

**反转话术**（对应 §2.3.1 / §2.3.2 / §2.2.4）：一个反直觉的答案——**工程没有单一对立面**，它的对立面取决于你站在哪个维度看：认识论维度对手科学（科学问"世界是什么"，工程问"应该造出什么"；科学家的失败可贵，工程师的失败是灾难）；方法论维度对手艺（可复现 vs 依赖个人）；目标维度对艺术（满足用户 vs 表达自我——好不好看是加分项，能不能用是及格线）。理解这一条，就不会再用"有没有用代码"来判断"是不是工程"。三个对手里最实用的是手艺，因为它直接给出"你在不在做工程"的判断，用就是试金石：**换个人、换团队，用同样的需求和约束，能不能交付质量相当的成果？能，是工程；不能，那是手艺——哪怕它碰巧也用了代码、图纸或电路。** 石军那段是标准样本：车间里没有一份完整测试方案，可"该查哪里"全在他脑子里；他请两周假，一个批次出问题产线愣是没人能定位，他回来十分钟找出问题。**石军在，质量在；石军不在，质量跟着走**——这就是手艺。但这里要拦住一个偷换：手艺不是贬义词，一个经验丰富的老工程师本身就是最值钱的资产；工程化不是要把他废掉，而是把他的判断显性化成可教的规则、可查的文档、可检验的标准——**把个人能力变成组织能力**。小张那张清单问得最准："这张单子换个人拿着，还能不能做出同样的判定？能，它是方法：为什么这么判、依据写没写下来，都查得到；不能，它是手艺：每一次都得回来问同一个人。"

**参考答案要点**：三维对立面见 §2.3.1；试金石与三处用法见 §2.2.4；不是手艺、石军与小张见 §2.3.2；"手艺不是贬义词、工程化是显性化"见 §2.3.2／书练习 8。

### Q4 工具与流程都齐了，还缺什么？一次妥协怎么就判成了失守？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "工具和流程都齐了就不缺什么；上个月那次事故是人手不够、临时赶工。" | 正是要翻的——把四层当两层、把失守当意外 |
| 中 | "工程有四层，缺一层不行。"结论对，但缺层各回落谁、失守三问怎么用没给出来 | 四层说出了，机制与判据缺 |
| 好 | "四层同时在场才算工程：工程科学／方法论／工具与实践／价值与伦理，缺哪一层就有一样东西重新落回某个人身上——缺工程科学只能靠老师傅直觉，缺方法论做法师徒相传，缺工具与实践落地全靠个人技巧，缺价值与伦理松不松手全靠某个人的良心。敏捷 + CI/CD + 测试只占第二、三层；前三层缺了是不专业，第四层缺了是会出事——泰坦尼克号、挑战者号、737 MAX 的共同点不是'不会做'，是'做的时候没守住'。判一次妥协是失守还是客观原因，问三句：利益相关方知不知情／有没有评审／有没有记录；客观原因不会专门留记录。" | 四层 + 回落机制 + 事故同型 + 失守三问全到位 |

**产品侧 vs IT侧**：产品组举"为了赶上市砍掉可靠性测试、砍掉降额验证"；IT 组举"为了月底上线砍掉容量评估"。两边都是同一个标准动作——**为了进度，悄悄牺牲可靠性需求，而且没有让任何利益相关方知情**。

**反转话术**（对应 §2.3.3 / 案例进展③）：工程不是方法论。四层里每一层都是一道把交付从人身上挪走的关：缺工程科学，没人能回答"为什么这样能行"，只能靠某位老师傅的直觉；缺方法论，做法只能师徒相传；缺工具与实践，方法论悬在半空；缺价值与伦理，压力面前松不松手全靠某个人的良心。判断与底线要分开：**判断是动作**，四层里层层都有；**底线是界限**（安全、可靠、负责），只有第四层守着。恒信那个"先上再说"的接口就是现成的样子：容量评估被砍，缺的是工程科学；变更没有控制、没有基线，"受控"这一项不及格；为进度让掉可靠性还不留记录，缺的是价值与伦理。三起事故同型：泰坦尼克号号称"不沉之船"，救生艇数量按"不会沉"的假设配；挑战者号的 O 形环低温会失效，工程师提过反对、管理层也知情，风险被"合理化"；737 MAX 的 MCAS 设计缺陷在进度与市场压力下没有被认真对待。**共同点不是"不会做"，是"做的时候没守住"**——技术和检查都在场，缺的只有价值与伦理这一层。所以前三层缺了是"不专业"，第四层缺了是"会出事"。那怎么判一次妥协是失守而不是客观原因？问三句：利益相关方知不知情？有没有评审？有没有记录？——**客观原因不会专门留记录，失守恰恰发生在"没有记录"的地方**。案例进展③里顾言按这三句对一遍："没有。没有。冲刺计划上写过一行，后来又划掉了。一条不占。"苏婷那句认得更直："评估在计划里排过，可月底要上，罗建说先上再说……结果，没来得及。"

**参考答案要点**：四层与缺层回落见 §2.3.3；判断与底线之分见 §2.3.3；三起事故与失守三问见 §2.3.3；案例进展③（苏婷认账、顾言对三问）见 §2.3.3 后；"有组织的赌博"见 §2.3.3。

### Q5 自动化程度越高，是越接近工程，还是越远离工程？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "自动化越高越省人、越安全，所以越接近工程。" | 正是要翻的——把"没人操作"当"没有风险" |
| 中 | "系统化≠算法化，所以自动化未必好。"结论对，但提纯与两道关没给出 | 分界对了，机制缺——为什么自动化反而把判断推到了最难处 |
| 好 | "系统化有结构、有方法（含判断）、可重复、全覆盖；判它是系统化还是装饰问三句：每步有明确输入输出吗／有可检验检查点吗／换个执行者结果还稳定吗。系统化的目的不是消灭不确定性，是把不确定性纳入可控范围（检查点、评审、测试、反馈回路）——敏捷高度系统化，却一点谈不上算法化。自动化把判断提纯：执行给机器，人剩下异常怎么处置、边界在哪里、目标有没有变；同时它拿走人阻止事故的能力——737 MAX 的 MCAS 两道关：权限上机器优先于人、留给人的反应时间极短，能力上长期不接管会失去情境意识。所以工程要'错误可见'、自动化追求'零错误'，方向相反——消灭判断，就是消灭工程。" | 四特征三问 + 目的 + 提纯 + 两道关 + 分野全到位 |

**产品侧 vs IT侧**：产品组举"全自动测试流水线、自动降额策略"；IT 组举"全自动发布、自动对账"。两边都要翻"自动化越高越工程"——**剩下的不是"不用判断"，是判断密度最高的那一档**。

**反转话术**（对应 §2.3.4 / §2.3.3 末注）：先分三个译成中文都像"系统的"的词：**systematic（系统化）**答"怎么做事"——有章法、可检查、可复现；**systemic（系统性）**答"怎么看问题"——有全局、看部分间关系与涌现；**algorithmic（算法化）**答"能否自动执行"——确定性执行、无需判断。本章说的"机械化"，专指 algorithmic。系统化本身拆到底有这几个可操作特征：有结构（分解为清晰步骤与阶段）、有方法（含判断——每步有标准与检查点，但不是机械执行）、可重复（过程本身能重复执行）、全覆盖（从需求到退役无遗漏）。判一份流程是系统化还是装饰，问三句：每一步有明确的输入和输出吗？每一步有可检验的检查点吗？换个执行者，结果还稳定吗？——**系统化的本质不是"多"，是可检查；流程是载体，可检查才是目的**。它管的不只是"做没做"，而是"做没做对、能不能证明做对了"。系统化的目的从来不是消灭不确定性：需求会变、环境会变、人会犯错，它做的是把不确定性纳入可控范围（检查点、评审、测试、反馈回路）——敏捷就是典型，流程完整、每一步都依赖人的判断，**高度系统化，却一点谈不上算法化**。再进一层看自动化，它做两件事：**一是把判断提纯**——执行交给机器，人手上剩下最难的判断（异常怎么处置、边界在哪里、目标有没有变）；**二是拿走人阻止事故的能力**——737 MAX 的 MCAS 本为防失速而自动接管，两次坠毁中飞行员都没能在有限时间内夺回控制权，两道关：权限上机器优先于人、留给人的反应时间极短；能力上长期不接管会失去情境意识，就算把控制权交回给你也不知道怎么接。合起来就是分野：**工程要"错误可见"，自动化追求"零错误"（把错误掩盖掉），方向相反；全自动的终点是消灭判断，而消灭判断，就是消灭工程。**

**参考答案要点**：三词辨析与出处说明见 §2.3.4；系统化四特征与三问、加功能正反例见 §2.3.4；六面与"不是清单是关卡"见 §2.3.4；自动化两件事与"错误可见 vs 零错误"见 §2.3.4；737 MAX 两道关与事故出处见 §2.3.3 末注／§2.3.4。

### Q7 给恒信的敏捷转型按六面打分：缺的是"差一点"，还是"差一半"？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "敏捷都上了、覆盖率 80%，还打什么分——六面肯定全过。" | 正是要翻的——把"上了"当"有"，把清单当打勾 |
| 中 | "受控、可验证这两面肯定不行。"结论对，但六面出处、系统化三问与"差一半"的定性没接上 | 打勾对了，出处与定性缺 |
| 好 | "六面各出自 systematic（有结构／有方法含判断／可重复／全覆盖）、disciplined（受控：有基线、有变更控制）、quantifiable（可验证：有证据、可检查、可度量）。恒信：有结构、有方法、可重复沾了边；全覆盖（容量测试被砍）、受控（先上再说）、可验证（没有容量验证）三面不及格——这不是'差一点'，是差一半。系统化三问照上去，第三问'换个执行者结果还稳定吗'答不上来：可检查没立住，差的就是那另一半（这一问属系统化自问，'换个人还能不能交付'是项目一的事）。" | 六面出处 + 逐面打勾 + 三问 + "差一半"全到位 |

**产品侧 vs IT侧**：产品组打"全覆盖、受控"最容易叉——批次追溯没做、降额规则没写进作业指导书；IT 组打"受控、可验证"最容易叉——没有基线、没有变更控制、没有容量验证。两边都要翻"六面是清单"——**它是关卡：缺一样就是"差一点"，而工程里"差一点"往往就是事故**。

**反转话术**（对应 §2.3.4 / §2.4.5 项目三·项目四）：工程化的完整图景要把三个词都展开：systematic 展开成有结构、有方法（含判断）、可重复、全覆盖；disciplined 展开成"受控"（有基线、有变更控制）；quantifiable 展开成"可验证"（有证据、可检查、可度量）。六面逐面打勾就是给一个团队的工程化定成色。恒信打下来是什么样？有结构、有方法、可重复，前几样沾了边（注意口径：**"可重复"只指过程本身能重复执行**，"换个人还能不能交付"是项目一的事，别混成一问）；全覆盖——容量测试被砍，不及格；受控——"先上再说"，不及格；可验证——没有容量验证，不及格。所以结论不是"差一点"，是差一半。再用系统化三问照一遍：每一步有输入输出吗？有检查点吗？换执行者稳定吗？——**最后一句答不上来**，系统化的"可检查"没立住，差的就是那另一半。这里还有一条链要说清：系统化 → 工程化 → 流程化 → 信息化，系统化是方法底子，加纪律与可验证是工程化，再固化是流程化，系统承载是信息化；反直觉的是**流程化不等于工程化**——工单录入有固定流程，可录完没人核对、出错查不到记录，那仍是即兴。

**参考答案要点**：三词与六面（含出处列）见 §2.3.4；"可重复"释义与"不是清单是关卡"见 §2.3.4；系统化三问见 §2.3.4；链与"流程化≠工程化"见 §2.3.4；恒信逐面结论见 §2.4.5 项目三、项目四。

### Q8 部件全对，为什么系统未必对？"上线"为什么不算工程成功？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "模块都验收过了，系统怎么会不对？出事是运气不好。"／"上线了当然就是成功了。" | 正是要翻的——把部件的和当整体、把技术系统的完成点当工程的成败 |
| 中 | "系统工程管整体，所以是整合没做好。"结论对，涌现依据、两种系统、两把尺子没给全 | 方向对了，机制与判据缺 |
| 好 | "系统工程不造部件、只造整体：分解分配 → 定义接口 → 系统级集成 → 两道判定；它交付的是接口契约、集成方案、系统级验证与确认方案这些'缝'。涌现的依据在标准里：§3.46 给'系统'下的定义就是'合在一起呈现出单个构成部分所不具备的既定行为或意义'，§5.2.1 说系统属性'源自或涌现于'部件及其关系。恒信按技术系统看上线＝成功，按工程系统看法务线下签、财务手工台账、业务走邮件＝失败，差的是人／流程／组织／数据；工程系统还要答退役那两问（安全关停、数据迁移），技术系统不问。两道判定只做了一道：验证对规定需求、确认对预期用途，需求全过而没人用，一样是失败。" | 元工程 + 涌现依据 + 两种系统 + 两把尺子全到位 |

**产品侧 vs IT侧**：产品组举"M3 的硬件、固件、云端、App 各自达标，可箱子进了冷链才叫成了——温度全程可追溯、断链真告警"；IT 组举"三个模块各自能验收，数据定义对不齐、跨部门断点没人管"。两边都是同一件事——**这些'缝'不属于任何一个部件，却决定整体成不成立**。

**反转话术**（对应 §2.4.1 / §2.4.2 / §2.4.3 / §2.4.4）：**单个部件都合格，不等于整体合格。** 这叫涌现属性（*emergent behavior / emergent property*，中译：涌现行为／涌现属性）——每个发动机都正常、每块机翼都达标，飞机未必能飞。这不是本书的发明：标准给"系统"下的定义就是这件事，*arrangement of parts or elements that together exhibit a stated behaviour or meaning that the individual constituents do not*（中译：各部分或各元素的安排，它们合在一起呈现出单个构成部分所不具备的既定行为或意义）；§5.2.1 那句话说系统作为整体的属性"源自或涌现于"部件及其属性、以及部件之间与系统及其环境之间的关系。为什么它在工程里无处不在？因为工程把一个大问题拆成许多小问题、分给许多人做——系统工程的职责就是守住那些"部分之和的溢出"：**接口、定义、时序**（接口契约、数据定义、时序依赖），它们不属于任何一个部件，却决定整体成不成立。所以系统工程叫元工程：不造任何部件，负责把部件整合成整体。再往上一条线是两种系统：**技术系统是设备的集合，工程系统是整个社会技术系统**——技术子系统、人的子系统、组织子系统耦合在一起，边界画在"整个运行环境"上，不是画在设备的壳上；工程系统还有生存周期，要为"退役"做设计（安全关停、数据迁移），这两问技术系统不问。恒信就是现成样本：按技术系统看，部署好了、服务器跑起来了、模块全上线；按工程系统看，采购流程没改、法务不习惯电子签、财务数据没清洗、审批权责没理清——**砸了几千万，最后发现"系统"根本没被用起来**。最后一道分辨是两把尺子：**验证对规定需求**（做对了吗），**确认对预期用途**（做对了东西吗），两句只差一个词——*The system was built right.*（中译：系统被正确地建造了）／*The right system was built.*（中译：被建造的是正确的系统）——不可互推，全部需求验证通过，确认仍可能失败。

**参考答案要点**：元工程与"缝"见 §2.4.1；涌现属性与 §3.46／§5.2.1 见 §2.4.2；工程系统与技术系统、退役两问、机场与 M3 见 §2.4.3；验收参照与验证／确认（§3.54 注 1／§3.55 注 1、ISO 9000:2026 §3.11.12／§3.11.14）见 §2.4.4；项目五、项目六见 §2.4.5。

### Q9 亲手给一个"××工程"立一句可检验的定义，再转述给外行（方法时刻 · 规则 15 · 含转述）

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 只会说"我们这个工程有流程、有工具"，写不出一句能拿去判陌生项目的定义；转述没做或做成了念定义 | 背了词，没把词当尺子 |
| 中 | 写出了定义的四格，但"框"或"路"格只能举例、给不出判据；转述做了，卡住的词没圈出来 | 判据立了一半；卡壳处没当成缺口 |
| 好 | "定义写全四格：料（依据什么原理、为什么能行）／框（成本、工期、资源、风险、法规、物理极限各是什么）／路（需求→设计→实现→验证→维护怎么走）／果（谁用、用来干什么、怎么算安全）；再用试金石量最近一次交付，落到具体一处（哪几条命令、哪一个环境变量、哪一段部署顺序只在某人身上）；缺的层点到名。转述'工程≠手艺'卡在'可复现'或'用起来'上——卡住处正是四问答不齐的那一问。换到冰链 M3，判据不变。" | 立定义 + 当场量 + 缺层 + 转述缺口 + 跨域对照全到位 |

**产品侧 vs IT侧**：产品组量"我的工艺工程"——料是材料与公差依据，框是产线节拍与法规，路是作业指导书，果是客户认的"全程没断链"；IT 组量"我的数据工程/信息工程"——料是模型与算法依据，框是工期与合规，路是需求到上线的检查点，果是"业务真在用"。两边立出的定义结构相同；转述"工程≠手艺"时，产品组卡在"什么时候下线算成了"、IT 组卡在"什么叫用起来"——**卡住处就是缺口**。**这就是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"；判据不挑行业。**

**反转话术**（对应方法底座时刻 = 反记忆崇拜 → 判据主义 + 转述 = 压缩测试）：罗建记住了"工程化"这个词，却从没用对过它——这就是第1章说的"见过"：他背得出那三个形容词，却答不出"它不是什么"（§2.1.3）。判据主义就是反它的那味药：**不给没有判据的定义**。所以你亲手立的这句定义，必须能被第三个人拿去判一个陌生项目——四格里哪一格只能举例、举不出判据，那一格就是你还"见过而未拥有"的地方。第二件事把它量到真实交付上：**换个人、换团队，同样的需求与约束，还能不能同等交付？** 答案不许停在"大概能"，要落到具体物件——哪几条命令、哪个环境变量、哪一段部署顺序只在某人身上（§2.2.4／§2.4.5 项目一）。第三件事是 v2.1 规则 15 新增的形态：**转述是压缩测试**——把"工程 ≠ 手艺"用三五句话讲给一个完全不做工程的人，讲不清说明结构没成型，**卡壳处即概念最薄处**（书练习 12 问的就是这一句）。跨域变体：把这套判据换到冰链 M3 上——石军几十年手艺、小周"按技术系统看我们把箱子做完了、按工程系统看才交了一半"、小张那张"换个人还判不判得出来"的清单——**判据没变：可复现、判断留人、被用起来。** 同一个判据、两个世界，这正是"概念不挑行业"的现场证明。反身：你部门宣布"我们工程化了"的时候，手上有一条可检验判据，还是只贴了"敏捷/CI/CD"的标签？

**参考答案要点**：方法底座时刻（反记忆崇拜 → 判据主义）见 `00-案例设定.md` §三 第2章行；"见过而未拥有"见 §2.1.3；试金石见 §2.2.4；案例进展①（事后给四样打勾）与项目一（三条隐藏命令）见 §2.4.5；转述＝压缩测试见书练习 12 与第1章 §1.4.4；跨域对照见 `00-案例设定.md` §四 工程／工程系统行（恒信"上线≠工程成功" ↔ 冰链"温控箱＝工程系统物证"）。

### Q10 给你们的部门做一次工程成色体检

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强测试、要上 CI/CD、要把文档补起来。" | 没落到任何一条判据，不可检查 |
| 中 | 用一条判据查出缺口（如"我们的流水线换个人跑不起来"），但六项目只照了一面 | 有判据，但只照了一面 |
| 好 | 按六项目逐项过（试金石／层次／成色／系统化自问／整合／验收参照），挑出最不合格的一项 + 一个可检查动作（如"把验收的参照从'系统上线'换成'系统被用起来'，下周约法务、财务各真用一次"），说清先查哪一项、两周后报告什么 | 体检完整，动作可执行，有复查机制 |

**产品侧 vs IT侧**：两组各给自己部门体检——体检表本身是同一份（六项目 + 九条判据），这正是"工程系统包含技术系统"与"试金石不挑行业"的现场证明。

**反转话术**（对应 §2.4.5）：这一章的判据不是彼此孤立的：试金石测可复制，层次测完整，工程化的成色测过程，系统化自问测可检查，系统工程（元工程）测整合，验证与确认测验收——**合起来，才是一次完整的量**。恒信量下来项项不合格，但这不是说它一无是处：它的方法论和工具是真的，缺的在别处；书里给的那条建议只有一句——**先把"验收的参照"从"系统上线"换成"系统被用起来"，再谈敏捷转型成功。否则，这套流程与工具只会让"不会出事"的错觉维持得更久。** 体检时最容易漏的是两格：**"缝"没人认领**（接口契约、数据定义、时序依赖三样各归谁管）与**确认根本没做**（验收记录里只有验证、没有"做对了东西吗"这一问）。**答不出的那一项，就是最该补的那一项**——不必六项全做完，找到第一个答不出的就能开工。最后一句留给王默：散会时他在运维台账上添了一栏"这条曲线归谁"——以前它只活在监控屏上，他嘴上念叨、从不上纸；这回他把它写下来了，**写下来，别人才接得住**。

**参考答案要点**：六项目与那条建议见 §2.4.5；判据九条见 §2.2.2（定义四样）／§2.2.4（试金石）／§2.3.3（层次、失守三问）／§2.3.4（成色、系统化自问、自动化两问）／§2.4.1~2（整合与涌现）／§2.4.4（验收两把尺子）；作业指南见本件 §五；练习 1~12 见书附录 D，答案要点见 `19-附录.md` 附录 E 第2章块。

## 五、课后作业

1. **书练习（试金石 · 与题卡同源）**：用试金石检验你们团队最近交付的一个系统——换三个人来做，能交付质量相当的成果吗？如果不能，缺的是**哪一层**（工程科学／方法论／工具与实践／价值与伦理）？（书练习 1）

3. **书练习（转述 · 方法时刻延伸）**：用三句话把"工程 ≠ 手艺"讲给一个完全不懂工程的人（比如你的家人）——卡在哪个词上？那个词就是你概念最薄的地方。（书练习 12）
4. **回部门落地**：结合现状，用本章六项目给你们最近交付的一个系统做一次工程成色体检——给出最该改的三件事，每件落到**一个动作 + 一条判据**。**两周后回来报告**：哪一件改成了、哪一件还卡着、卡在哪条判据上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，半天完成一次体检，两周后复查一格（判据只用本章那九条，不另立标准）：
>
> 1. **挑交付（先立对象）**：从最近三个月里挑一次"上线了却没被用起来"或"上线出了事"的交付——不是挑最难的，是挑最像"我们已经是工程化团队"的那一次。**话术**："这一次，我们当时是按'上线'算成的，还是按'被用起来'算成的？"
> 2. **项目一 · 试金石（可复制性）**：问"换个人、换团队，用同样的需求和约束，能交付质量相当吗"；答不上来的地方写成具体物件——哪几条命令、哪几个环境变量、哪一段部署顺序只在某人身上。**话术**："这个人走了，交付还能维持吗？"
> 3. **项目二 · 层次（完整性）**：工程科学（"为什么这样能行"有依据吗、压测能复现吗）／方法论（敏捷在不在）／工具与实践（CI/CD 在不在）／价值与伦理（赶进度时安全需求会不会让位）——缺哪一层，写下"这样东西现在落在谁身上"。
> 4. **项目三 · 成色（过程）**：有结构／有方法（含判断）／可重复／全覆盖／受控／可验证，六面各打勾或打叉；打叉的写一句"要什么才算有"（受控＝有基线、有变更控制；可验证＝有证据、可检查）。
> 5. **项目四 · 系统化自问（可检查）**：每一步有明确输入输出吗／每一步有可检验的检查点吗／换个执行者结果还稳定吗——最后一句最难，答不上的写下那一处。**话术**："流程图上画得都对，可换个人走一遍，结果一样吗？"
> 6. **项目五 · 整合（缝归谁）**：把接口契约、数据定义、时序依赖三样摆出来，各问一句"这一条归谁管"；没人认领的，就是"缝"。
> 7. **项目六 · 验收参照（两把尺子）**：把验收记录分成两堆——验证（对规定需求）与确认（对预期用途）；再按技术系统与工程系统各看一遍，两个答案不一致时，指认差的是人、流程、组织还是数据。
> 8. **摘三件（产出）**：从六项里挑三件最该改的，每件写成"一个动作 + 一条判据"（例：把"换个人还能不能运维"写成上线前必答的一问，判据＝新人按文档独立完成一次发布、不求助）。
>
> 卡住时：试金石答不上来——手艺还在人身上，不是文档问题；层次答不出缺哪一层——先把"这样东西落在谁身上"写清，落点就是缺的那层；六面里"受控、可验证"都打叉——缺的是关卡不是清单，"差一点"在工程里往往就是事故；系统化三问里第三问答不上——可检查没立住；验收只有验证没有确认——验收参照用错了，拿"上线"当"成功"。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 一句话定义报得出，四样各说得出管什么？ | □ | 只有名词没有定义：料、框、路、果缺了哪一样 |
| 换个团队、换个人，同样的需求与约束能交付质量相当？ | □ | 手艺还在人身上——写下具体是哪几处 |
| 工程科学这一层有依据吗（容量评估、压测结论能复现）？ | □ | 只能靠某位老师傅的直觉，别人学不走 |
| 方法论这一层在不在（需求→设计→实现→验证→维护）？ | □ | 做法师徒相传，人走了做法跟着走 |
| 工具与实践在不在？ | □ | 方法论悬在半空，落地全靠个人技巧 |
| 价值与伦理：赶进度时，安全需求会让位吗？ | □ | 压力面前松不松手全靠某个人的良心 |
| 一次妥协，利益相关方知情吗、有评审吗、有记录吗？ | □ | 失守就发生在"没有记录"的地方 |
| 每一步有明确输入输出吗、有可检验检查点吗？ | □ | 那不是系统化，只是一张流程图 |
| 换个执行者，结果还稳定吗？ | □ | 可检查没立住，只是可重复地做同一件靠人的事 |
| 接口、数据定义、时序这三样"缝"，各归谁管？ | □ | 涌现属性在缝里等着，部件全对 ≠ 系统对 |
| 验收记录里，验证与确认各占几条？ | □ | 只做了验证；"做对了东西吗"这一问没问过 |
| 按工程系统看，人会用、流程顺、组织撑得住吗？ | □ | 拿"上线"当"成功"，砸了钱没人用 |

## 附：术语与引文口径（本件用词）

- **工程（engineering）**：*科学原理 × 判断创造，在约束下，用系统方法，造出有用且安全的东西*——本句是本书对 ECPD／ABET／INCOSE／IEEE 610.12 的**凝练，不是任何标准的原文**（§2.2.1 术语注）；本件引用时一律标"本书凝练"，不写成"标准说"。
- **试金石**：本书命名（熟语式命名，不进标题、不写画面句，首现把判据说全一次）；本件一律写"试金石——换个人、换团队，用同样的需求和约束，还能不能同等交付质量相当的成果"。
- **四层**：**工程科学 → 方法论 → 工具与实践 → 价值与伦理**，一律按此序、此名；不简写成"价值层"单独顶替"价值与伦理"这一层。
- **工程化**：说的是"工程做起来是什么样"——六面（有结构／有方法（含判断）／可重复／全覆盖／受控／可验证）；三个出处词 systematic／disciplined／quantifiable 出自 IEEE 610.12 对**软件工程**的定义，属**过程特征**，不是工程的定义。
- **系统化／系统性／算法化**：systematic（怎么做事）／systemic（怎么看问题）／algorithmic（能否自动执行）；本章说的"**机械化**"专指 algorithmic（算法化），不写成"系统化就是机械化"。
- **工程系统（engineered system）／技术系统（technical system）／涌现属性（emergent behavior · emergent property）**：工程系统是被设计或改造、与预期运行环境交互、达成预期目的、遵守适用约束的系统（INCOSE 2019；本件带年代引用，不写成"标准说"）；技术系统仅由人工技术组件构成、人只是使用者；涌现属性指单个构成部分不具备、合起来才呈现的既定行为或意义。
- **验证（verification）／确认（validation）**：验证对**规定需求**（做对了吗），确认对**预期用途**（做对了东西吗），不可互推；两句英文只差一个词——*The system was built right.*（中译：系统被正确地建造了）／*The right system was built.*（中译：被建造的是正确的系统）。
- **元工程（meta-engineering）**：系统工程＝构建复杂系统的工程，不造部件、只造整体，故称"工程之上的工程"；本件不写"总工程""顶层工程"。
