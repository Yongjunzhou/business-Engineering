## 二、核心结论（供后续章取用）

1. **决策有定义、权衡没有**：`architecture decision`／`architecture rationale` 定义句在 **42010:2022 §5.2.12**（概念章），**第 3 章无词条**；`trade-off` 四份正本均无定义句，定义性表述落在 **tradespace**（42020 §8.4.6 NOTE 2／§9.4.8 NOTE 3）。
2. **决策＝一组选择**（选择对象见 §5.2.12 EXAMPLE 1）；**理据六项含 alternatives and trade-offs considered**——权衡由理据进决策档案。
3. **权衡三对＋一**：解内／解间／与现状／与未被提出的其他解（§8.4.6 e) 1)2)3)）；典型清单见 §8.4.6 NOTE 4；**tradespace 常无完全满足解**；**权重非必需**（§9.4.5 NOTE 2）。
4. **两侧互补**：概念化侧技术视角（§8.4.6 NOTE 1）↔ 评估侧价值视角（§9.4.8 NOTE 2）。
5. **拍板通常在架构过程之外**（§5.7、§8.4.7 NOTE 7）→ 决策管理过程（15288 §6.3.3）；**评估不含处置决定**（42030 §3.4 Note 1）。
6. **记录**：AD **shall** 记关键决策；13 条选择准则、11 项内容（42010 §6.10.1）；理据四处（§6.10.2）；**标准未给"关键"的判据**＝本书自定处。
7. **现行版与在途**：**42020 与 42030 均已立 AWI 项目**（阶段 20.00，生效日 2026-05-22，题名改 *Enterprise, systems and software — …*）；42010、15288 未查到在途项目。判据仍以 2019／2022／2023 现行为准。

## 四、2026-10-13 追加：架构决策的"目的／意义／价值"底层逻辑（面谈分析，供 ch12 取用）

**四条不对称，推出四问**（我的定性，各配正本锚点）：

1. **信息不对称**（承诺作出时信息最不全、兑现时信息最全）→ 故须**记录理据**：15288 §6.3.3.1 NOTE 1 逐字 *Key study data (e.g. assumptions and decision rationale) are typically managed to inform decision-makers, re-justify the decision in the future, and support future decision-making.*（中译：关键研究数据（如假设与决策理据）通常被管理起来，以告知决策者、在将来**重新证成**该决策，并支撑未来的决策。）
2. **责任不对称**（判断在个人、后果在组织）→ 故须记**决策权威或所有者**：42010 §6.10.1 第 3 项＋42020 §6.2 c)（有理由支撑的决策由**适当权威**作出并传达）。
3. **目标不对称**（多个目标不可兼得）→ 故**理据必含权衡**：42010 §5.2.12 六项内容项之 *alternatives and trade-offs considered*。
4. **承诺不对称**（收窄设计空间的收益即时、改起来的代价延后且高昂）→ 故**只记关键决策、且要留出设计空间**：42010 §6.10.1 十三准则里"*likely to be costly to change*"（中译：改起来很可能代价高昂）与"*highly sensitive to changes*"（中译：对变更高度敏感）；反向约束是 15288 §5.4／42020 §5.6 的 *as design-agnostic as possible*（中译：尽可能与设计无关）与 *maximum flexibility in the design tradespace*（中译：设计权衡空间的最大灵活性）。

**三问判据（本书自定，须与十三准则对表）**：一条选择若满足以下任一条，即属"关键"——（a）它一旦定了会**约束下游多个专业的选择**；（b）它**事后改起来的代价远高于当时定它的代价**；（c）**别人必须知道它才能正确工作**。三问皆有正本对应项，（a）≈影响关键相关方与进入下游计划、（b）≈代价与不可逆一组、（c）≈关系与追溯项（§6.10.1 第 5、6 项）。

**产品研发领域的特殊性**（我的定性，落 ch12 时用）：研发是"在信息最不全时作最贵承诺"的活动；并行度高（多专业须以边界冻结为前提）、外购比例高（决策即采购与技术路线锁定）、验证周期长（安全关键件与认证件**不可回滚**）；平台型产品（如 EOS）的架构决策直接兑成**变更边际成本**——哪些事一种产品做一次、哪些每个订单都要做。四者叠加，使决策记录成为研发领域**唯一可持续的责任与知识载体**（对应本书四案例的失效形态：误导／演进失控／漏检／架构未识别）。

## 五、2026-10-13 追加：架构决策 ↔ 架构定义 的关系（面谈分析，供 ch11／ch12 接缝取用）

**身份不对称**：「架构定义（architecture definition）」在正本里是**过程名**（15288:2023 §6.4.4 system architecture definition process；42020:2019 是它的过程细化：三核心过程 §8／§9／§10＋两并行过程 §6／§7；15288 §6.4.4.3 NOTE 1 明写 42020 三核心过程之对应）；「架构决策」是**概念名**（42010:2022 §5.2.12 定义句＋§5.2.9 是 AD 元素）。故二者不是两个概念的关系，而是**过程与过程中的取值**的关系。

**四条关系**：① **包含**——15288 §6.4.4.1 目的句三动词 *generate… select one or more… and express*（中译：生成……选出一个或多个……并表达），"select" 即决策站位；② **宾语**——§5.2.12 EXAMPLE 1 首项即 *Selection of architecture concepts*（中译：架构概念的选择），定义的产出正是决策的宾语之一；③ **分层**——定义产出＝基本概念或属性＋管控原则（§3.2），决策与理据＝**AD 元素**（§5.2.9），§6.10.1 NOTE 1 *An AD expresses decisions about an architecture.*（中译：架构描述表达关于某架构的决策）；**决策进记录不改变定义的产出种类**；④ **时序**——定义多轮迭代（42020 §8.3 b)），决策在概念化阶段即捕获（§8.4.8 g)），但**拍板通常在定义之外**（§5.7／§8.4.7 NOTE 7）。

**标准自己的分工**：15288:2023 **§5.9 NOTE 2** 逐字——*Practices, conventions, principles, and concepts for system architecture definition are specified by the ISO/IEC/IEEE 420x0 family…*（中译：系统架构定义的做法、惯例、原则与概念由 ISO/IEC/IEEE 420x0 族规定：42020 给过程（治理／管理／概念化／评估／细化）、42030 给评估框架、42010 给描述的原则与概念）。

**本书口径的接缝（定案脊柱四环，框架 ch11 行已立）**：①判断 → ②立成概念·属性·原则 → ③**选定并背书** → ④下游必须依据它。**ch11（定义）走到②**（产出三张清单）；**③＝架构决策（ch12）**；④＝架构描述与治理（ch13／ch16）。一句话：**定义给出"可选项"，决策把它定成一个；没有③，②只是三张清单，管不住下游；没有②，③无从选起。**

**三条不许混**：① 把决策当定义（"选了 A 方案"＝"架构就是 A"）→ 把架构降为方案、锁死设计空间，违 15288 §5.9 的 *design-agnostic as possible* 与 42020 §5.6 的 *maximum flexibility in the design tradespace*；② 把定义当决策（出清单不留痕）→ 违 42010 §6.10.2 shall，且失去 §6.10.1 NOTE 3"理据失效时可重作决策"的依据；③ 把决策塞进定义产出（三张清单加第四类）→ 内容侧与描述侧缝成一条，触本书禁词表与 37 号警戒。

**一处桥接**：§5.2.12 EXAMPLE 1 含 *choice of range of implementation technologies or other realizations to be considered*（中译：所要考虑的实现技术范围或其他实现方式的选择）——**决策划定后续设计能选什么**，即 42020 §E.2.1 的架构即约束（architecture as constraint），可作 ch12→ch14 的过渡锚点。

## 六、2026-10-13 追加：架构决策 ↔ 架构权衡 的关系（面谈分析，供 ch12 取用）

**方向**：**权衡是决策的输入，决策是权衡的落点**，且标准把"权衡必入理据"写成硬要求——42010 §5.2.12 理据六项含 *alternatives and trade-offs considered*（中译：考虑过的备选与权衡），§6.10.2 又规定关键决策的理据是 **shall**；故**理据里不写权衡＝未兑现该 shall**。反向上，决策冻结权衡状态，**改决策＝重开权衡**（42030 §4.3.1 权衡在评估综合时可被重新审视；42010 §6.10.1 NOTE 3 理据失效时决策须重作）。

**过程上的两段各占**：权衡在 42020 §8.4.6（技术侧）与 §9.4.8（价值侧）；而 **trade space 与备选的识别也在决策管理过程内**（15288 §6.3.3.3 b) 3) *Identify the trade space and alternatives.*（中译：识别权衡空间与备选。））——同一件事在两个过程里各有一段，不是两件事。

**五个不对称**：① 定义——决策有定义句（§5.2.12），权衡无定义句（可用的是 tradespace，42020 §8.4.6 NOTE 2）；② 回答——权衡答"此消彼长得到什么失去什么"，决策答"取哪一条、谁背书"；③ 对象——权衡在"解 ↔ 目标／关注点"之间，决策的对象是做法（概念／元素／框架／分层／技术／战术／模式／风格／实现范围／选项集）；④ 结论——权衡可以没有结论（§9.4.5 NOTE 2：把权衡摆给相关方即可，权重非必需），决策必须有结论（15288 §6.3.3.2 c) 选定优先路线）；⑤ 主体与代价——权衡由架构师／评估者做、便宜可反复可定性；决策由有权限者作（42020 §6.2 c)）、昂贵且收窄设计空间。

**互为条件**：权衡无决策 → 选择留给下游或分析瘫痪（42030 §3.4 Note 1：处置不在评估范围）；决策无权衡 → 理据缺项、备选无法区分，选择退化为偏好。**一句话机制：权衡是筛子的刃，决策是筛子的柄**——§9.4.7 b) 剔除相似且不具区分度者；§9.4.8 b) NOTE 1 权衡完全相同者不予考察、须考察跨越 tradespace 的一组；§9.4.8 e) 选出最佳。

**三处易混边界**：① **"暂不决定"不是决策**——标准的合法落点是**已知问题／未决议题**（42010 §6.7 d) NOTE 2 *Open issues can lead to decisions to be made.*（中译：未决议题可导致待作的决策。）），故本书"显式推迟"应记入未决议题，不记成一条决策；② **"现状照旧"是备选之一**（42020 §9.4.7 NOTE 2、§8.4.6 NOTE 4），"什么都不做"也要进权衡、也要被决策，不能以"没决策"逃掉；③ **对象不同但有交点**——交点在 §8.4.7 c) 候选架构间的权衡，与 §5.2.12 EXAMPLE 1 的 *choice of option sets to be considered*（中译：所要考虑的选项集的选择），即**"把谁摆上桌"本身就是一条决策**。

**压成一句**：权衡给决策的是**可比较性**，决策给权衡的是**终结性**，理据是把二者钉在一起的那颗钉子。ch12 骨架即此关系：`12.2` 权衡 → `12.3` 筛与选 → `12.4` 排序与时机 → `12.5` 记录（决策与理据）；旧稿"不可逆"只作排序与时机、不作准入（已裁）。

## 七、2026-10-13 追加：架构决策 ↔ 技术决策 ↔ 项目决策（面谈分析，供 ch12 取用）

**零命中声明**：四份正本**都不给这三个词下定义**。`technical decisions` 见于 15288:2023 **§5.7.5**（*…reduce the risks that arise from technical decisions and actions.*（中译：……降低由技术决策与行动所产生的风险。））与 **§6.4.2**（*management decisions, and technical decisions*（中译：管理决策与技术决策））；`project decisions` 见于 42020 §9.4.9 g)（*organization and project decisions and milestone determinations*（中译：组织与项目决策以及里程碑判定））与 15288 §6.3.4 注；`project decision makers`（中译：项目决策者）见于 42030 §D.2.1。**标准唯一的制度接口**是 15288 **§6.3.3.3 a) 1) NOTE 1**：决策管理策略须含 *the identification of decision categories and a prioritization scheme*（中译：决策类别与优先排序方案的识别）——**分类要你做，分法不替你定**；故三分法＝本书自定（须显式声明）。

**三种决策的户口**：① **架构决策**——定义句 42010 §5.2.12，记录 AD（§5.2.9／§6.10），判据＝13 条选择准则；② **技术决策**——语境是某解／元素的实现与可行性，判据＝技术性能、关键质量特性、可生产性（15288 §6.3.3.1 NOTE 1 准则清单里的技术项），记录＝设计描述与分析报告（§6.4.5）；③ **项目决策**——语境是交付承诺（范围-进度-成本-资源-风险），判据＝成本影响、进度影响、项目约束、法规影响、风险（同上），制度化形态是**决策门**（§5.5：*They give rise to the primary decision gates of the life cycle.*（中译：它们产生生命周期的主要决策门。））与授权推进（§6.3.2 任务 4)），记录＝项目计划、状态与里程碑记录（§6.3.3.3 c) 3)）。

**三分法的真判据＝三个变量（不是"内容是否技术"）**：42010 §5.2.12 EXAMPLE 1 同时含 *choice of underlying technology*（中译：底层技术的选择）与 *choice of business processes*（中译：业务流程的选择），故**按内容分域分不出来**。真分界：① **语境**（架构＝架构目标与关切；技术＝实现可行性与达标；项目＝交付承诺）；② **牵连面**（架构＝下游多专业的选择空间，§5.2.12 三类牵连＋42020 §5.6／§E.2.1；技术＝本元素；项目＝范围／进度／成本／资源）；③ **账本**（改它要重开谁的账：下游前提→架构；本模块→技术；里程碑与资源→项目）。

**三条关系**：① **同源**——一个决策事件常是三者的切片（选数据库：架构侧"归属唯一怎么落"／技术侧"哪个产品什么版本"／项目侧"何时采购、谁实施、集成窗口够不够"）；42030 §D.2.1 一条链上三种角色同时在场。② **互为输入**——架构→技术：划定设计空间（§5.2.12 的 *choice of range of implementation technologies…*（中译：所要考虑的实现技术范围或其他实现方式的选择）），技术→架构：设计定义过程反馈分配、划分与对齐（15288 §6.4.5.3／42020 §5.6）；架构→项目：构成 WBS、关键链、质量门判定跟踪的基础（§6.10.1 第 8 准则），项目→架构：成本进度资源进评估判据。**三者共用同一个决策管理过程**（15288 §6.3.3）——过程一个，类别不同。③ **权属不同层**——架构由**适当权威**作出并传达（42020 §6.2 c)），战略级可**升级**企业决策论坛（§6.4.4 e)）；技术在设计与开发执行层；项目在项目管理层（§6.3.2 授权推进）。

**四条易混与判法**：① 技术选型被当架构决策——同层可替换、不动下游前提者属技术；锁定实现技术范围或承载某条基本概念者属架构；② 架构决策被降格为技术决策（把"归属唯一"做成"用哪个事务隔离级别"）；③ 项目决策被当架构决策（因交期砍拓扑）——**两条要分别记**：项目侧记约束与代价，架构侧记内容与影响；④ 三者只记结论不记类别 → 下游分不清哪条是前提、哪条是取舍。

**ch12 用法**：`12.4 排序与时机`——三类的时机不同（项目有日历＝决策门／架构有换手点＝不给下游留返工／技术有收敛度＝信息够了就定），故"什么时候做"不止一把尺；`12.5 记录`——**ADR 只承载架构决策**，技术进设计描述、项目进计划与里程碑记录；"所有决策都写进 ADR"是越界。**一条分派判据（本书自定）**：这条决策若错了，要重开的是"下游多专业前提"→架构；"本元素实现"→技术；"交付承诺"→项目。

## 十四、2026-10-13 追加：架构目标是什么、与"系统目标"什么关系（面谈分析，供 ch11／ch12 取用）

**标准实际使用的三串"目标"（不可混）**：① **上层侧**——enterprise objectives（42020 §6.4.3 任务要求 examine current and future enterprise objectives）、mission objectives、business/mission drivers、organizational goals and objectives（附录 G.1：*Architecture governance has oversight of the architecture objectives … to ensure their consistency with organizational goals and objectives*（中译：架构治理对架构目标有监督……以保证其与组织目标的一致性））；② **架构侧**——`architecture objectives`（42020 §5.4／§8.2 b)／§8.4.4／§8.4.6 e)／§9.1／§9.4.7 i)；15288 §6.4.4.3 b) 2)）；③ **集合侧**——`architecture collection objectives`（42020 §6.4.3／§7.2，治理与管理层，**不是单个架构的目标**）。**"系统目标"这个总称标准不用**，它按主体分别说。

**可用定义性表述**：42020 **§5.4** 逐字——*Conceptualization specifies the objectives of the architecture and the quality measures that can be used in the assessment of its value. … These architecture objectives are based on the problem/opportunity identification and definition that occurs in this process.*（中译：概念化规定了架构的目标，以及可用于评估其价值的质量度量；这些架构目标基于本过程中发生的问题／机会识别与定义。）；**§8.2 b)** 成果逐字——*Architecture objectives that address the key stakeholder concerns are established.*（中译：应对关键相关方关注点的架构目标被确立。）；**§8.4.4 任务 f)** 逐字——*Identify and define architecture objectives that address the problem(s) and opportunities with respect to the stakeholder concerns, requirements or quality attributes, or that take advantage of identified opportunities.*（中译：识别并定义架构目标——它们就相关方关注点、需求或质量属性应对问题与机会，或利用已识别的机会。）→ 本报告归拢（④）：**架构目标＝"这份架构凭什么算立住了"的可判定表述：以关键相关方关切为源、以关键成功准则为形、以评估准则为用。**

**与系统目标的关系三条**：① **派生**——系统目标在上，架构目标由它＋关切派生（§8.4.4 的位置在"刻画问题空间"之后、"合成潜在解"之前；§5.4 明说基于问题／机会识别与定义）；42020 §8.4.4 NOTE 2／§8.4.6 h) NOTE 7 另分 **ends objectives（目的目标·问题侧）** 与 **means objectives（手段目标·解侧）**，架构目标**横跨两侧**（既承接 ends，又对 means 提约束）。② **互相约束**——架构目标不得与系统目标相抵（案例：合同审批候选 C′ 因"与目的正面相抵"被淘汰）；反向，系统目标要经架构目标检验可行性（§8.2 e)：*Tradeoffs among architecture objectives and feasibility limitations are identified…*（中译：架构目标与可行性限制之间的权衡被识别……））。③ **不同层**（下表，④定性）：

| | 系统目标 | 架构目标 |
|---|---|---|
| 主语 | 系统／产品（用户要的结果） | 这份架构（概念／属性／原则要守住什么） |
| 判据形态 | 结果值（活性 ≥95%、对账 ≤2 h） | 守住与否（挂到 K／P／G 上）＋可转评估准则 |
| 兑现时点 | 交付与使用期 | 设计与演化期 |
| 谁定 | 业务方／用户／组织（架构师有质询权无改写权） | 架构师确立并请相关方确认（§8.4.4；§9.4.3 g) 验证） |

**判别尺三问**：① 主语是谁？② 能不能挂到 K／P／G 上（"去掉它的后果"写得出来吗）？③ 是否必须先定一个取值才可判（若是，那是属性值／评估准则，不是目标本身）。

**★ 一条操作化（本次新得）**：37 号四套示例的 K／P／G 三张清单，**每一行都带"去掉它／不共享的后果"一列——那一列就是架构目标的反面表述**（保住它＝达成架构目标）。故本书**不必为"架构目标"另立一张表**，它就住在 K／P／G 的"去掉它的后果"栏里。

**三条常见误读**：① 把系统目标抄成架构目标（→ 不可判定："架构要保证到站活性 ≥95%"没法判）；② 把**架构集合目标**（治理层）当单个架构的目标；③ 把关键成功准则当目标本身——42020 把两者放在同一条活动（§8.4.4）里，关系是**目标→准则**（准则让目标可判），不是同义。

**一处口径待核（登记，勿擅改）**：`00-案例设定.md` 的 M3／恒信"目标"是**系统目标**口径（到站活性 ≥95%、对账 ≤2 h、逐笔 100%）；而 37 号四套示例的"目标（每条带关键成功准则）"是**架构目标**口径（HUD 共形精度／不误导／可维修；EOS 贯通即设计保证／语义唯一；M3 的 K／P／G 亦然）。两者并存不算错（正是两层分野的现场），**但若要全书齐一，宜在各处标明是哪一层**——**未裁定**。

## 十五、2026-10-13 追加：决策前的候选集里可以有不满足关切的候选项吗（面谈分析，供 ch11／ch12 取用）

**答：可以，而且标准把"不完全满足"当作常态。** 14 条引文逐字实测全过（量具 `.work-38/verify_candidates.py`）。

**三条标准依据（逐字）**：
1. 42020 **§8.4.5 NOTE 6**——*The solution might not be addressing the entire problem or all aspects of the problem. Therefore, it is important to understand where the solutions fall short and the tradeoffs that are to be considered when choosing among alternative solutions.*（中译：解可能并不应对整个问题或问题的所有方面；因此重要的是理解各解**在哪里差一截**，以及在备选之间作选择时要考虑的权衡。）同组 NOTE 5（每个解可有不同目的陈述）、NOTE 9（各解可能应对问题的不同方面）。
2. 42020 **§8.4.6 NOTE 2**——*The tradespace often does not include a solution that will completely satisfy the architecture objectives and stakeholder concerns.*（中译：tradespace 往往并不包含能**完全满足**架构目标与相关方关注点的解。）
3. 42020 **§9.4.8 b) NOTE 1**——筛选判据**不是"是否满足"，而是"是否凸显权衡、是否跨越 tradespace"**：*Alternatives that don't "highlight" the tradeoff criteria are screened. Two alternatives that present the exact same tradeoffs are not examined. A set of alternatives that "span" the tradespace is also examined.*（中译：不"凸显"权衡准则的备选会被筛掉；权衡完全相同的两条不予考察；还会考察一组"跨越"tradespace 的备选。）

**三条硬约束（"可以留"≠"可以糊涂地留"）**：
① **差距必须已知**：§8.4.5 f) 为每个解刻画优劣势与权衡；§8.4.6 c) 6) *Determine remaining gaps or shortfalls after implementing the proposed solutions.*（中译：确定实施所提各解之后仍然剩下的缺口或不足。）
② **必须可区分**：§9.4.7 b) 剔除的是"彼此相似且不具区分度"者（*Eliminate alternatives that are similar to each other and that do not provide a discriminating case…*（中译：剔除彼此相似、就评估目标与准则不具区分情形的备选。））；备选不够时还要再造（§9.4.7 a) NOTE 3）。
③ **强制项另算**：不满足强制项者**可以留**（*It is sometimes better to eliminate … earlier … However, it could also be helpful to see how far off these are from meeting the mandates and imperatives.*（中译：有时宜早筛掉不满足强制项的备选……然而，看看它们离满足强制项还差多远也可能有助益。）），但**要选它就得走减免／豁免／改需求**（§9.4.8 d) NOTE 4；§9.4.10 f) NOTE：*if a promising architecture with high stakeholder value does not close*（中译：若一个高价值、前景好的架构收不了口）即与相关方讨论放宽需求）。→ **"能不能留"与"能不能选"是两件事。**

**两条结构性要点**：① **完整性是"集合"的性质，不是"个体"的性质**——§8.4.5 d) 要求审"问题因—缓解策略"的关系以 *assure the completeness of the potential solution(s)*（中译：确保潜在解的完备性），而 NOTE 6 明说单个解可以只应对一部分；② **现状天然是"不满足关切"的候选**（否则就不必改），标准仍要求把它摆上桌（§9.4.7 NOTE 2、§8.4.6 NOTE 4）——**这就是最硬的反证**。

**与本书 ch11 口径对接**：ch11 的"**候选四道准入**（有类可归·有物可依·有径可循·**有辨可评**）"里，**"有辨可评"正是 §9.4.7 b)／§9.4.8 b) 的"可区分"要求**，**四道准入没有一条是"满足全部关切"**——本书口径与标准自洽，**不需要改**。另须分清**两个"准入"**：**内容准入**（哪些内容进三张清单，＝ch11 的目的必要性／承重测试）与**候选准入**（哪条方案摆上桌，＝四道准入）。

**反面风险三条（候选不满足关切何时有害）**：① **凑数的假备选**（straw man）——它与其他候选不具区分度（§9.4.7 b) 会筛掉），若仍写进决策记录，被否理由也是假的，未来无用（42010 §6.10.1 NOTE 3 要求被否备选将来"理据失效时可重作决策"）；② **用"不满足者"占位，掩盖"根本没有可行解"**——此时正解是回上游改需求或议减免（§9.4.10 f) NOTE），不是硬选一个差得多的；③ **把不满足强制项者当正常候选比**——应先筛（§9.4.8 d) NOTE 5），否则评估成本白花且结论不可用。

**一句话判据（④本报告定性）**：候选的合格线是"**可区分 ＋ 差距已知（差在哪、差多少、能否补）**"，不是"满足全部关切"；**若候选都满足全部关切，就不存在权衡，也就不需要决策了**。

## 十七、2026-10-13 追加：对架构决策的误解（14 条，4 条为书内已登记）

| **开发** | "这个我改个字段就行" | **一次代码变更** | 改字段可能是数据模型级的架构决策〔书内已登记〕 |
| **流程／工具** | "ADR 写了吗？这个季度几篇？" | **文档产出** | shall 只管 **essential**；记录的价值在 *re-justify the decision in the future*（中译：在将来重新证成该决策）（15288 §6.3.3.1 NOTE 1） |

**二、五条"制度性误解"（不是概念错，是制度错——业界独有的一层）**

1. **把决策当交付物**：以 ADR 数量、台账美观度当绩效。→ 正本：记录是手段（15288 §6.3.3.1 NOTE 1 三用途）；§6.10.1 NOTE 2 明说**清单不以求全为意图**。现象：**写的都是小事，大事在群里口头定了**。
2. **把决策会当决策**：会议开了＝决策完成了。→ 正本：有理由支撑的决策由**适当权威**作出并传达（42020 §6.2 c)）；治理决策还须升级与复核（§6.4.4 d)~f)）。现象：会而不决、决而不记、记而不署名。
3. **把架构评审当决策**：评审通过＝决策生效。→ 正本：评审/评估产出判断与建议，**处置在评估范围之外**（42030 §3.4 Note 1）。现象：评审之前的走廊共识才是真决策，而它没有记录。
4. **决策权与责任错配**：知道细节的人无权，有权的人不见细节；架构师沦为"决策文书的抄写员"或"背锅人"。→ 正本：11 项第 3 项**决策权威或所有者**；15288 策略含 roles／responsibilities／accountabilities／authorities；42020 §8.4.6 NOTE 1 明说创造者未必精确、**常由不同人做**。
5. **把决策外包给工具与模板**：ADR 工具链、Wiki 模板、工单流。→ 正本：标准给的是**内容项与关系项**，不给模板（本报告 §7.3 已立）。现象：**模板齐了、判断没了**（填表主义）。

**另两条业界高发型**：⑥ **平台／配置型产品里决策在"配置"里悄悄发生**（EOS 的"配置绕过引擎"）——把决策误当使用方式（正本：§5.2.12 的"选项集选择"）；⑦ **跨组织决策无归属**（供应商／客户／第三方接口）——用"细化出来的"掩盖（合同审批案例；正本：§6.10.1 第 3 项＋G9 类原则）。

**三、三条业界激励来源（为什么这些误解顽固）**：① **可交付物导向**——文档、图、代码可验收，判断不能，于是把决策做成"可数的产物"；② **个人问责缺失**——集体决策免责，于是无人署名；③ **节奏压迫**——迭代要求"先做出来再说"，于是决策被推到**无法再推**的时刻，而那时代价最高。

**★ 一条汉语业界特有的错位（本书可用）**：中文"决策"自带"拍板、定案"义项，与 42010 §5.2.12 的 *decision* ＝**一组选择**错位——**同一个词，中文听成动作、英文说的是对象**。本书 T-74 已把"架构决策"定名为"选错了要花大代价才能改对的选择"（并注明三标志是代理、准入看目的必要性），正是对这个错位的处置。

**四、标准自己登记的业界现象（可直接引）**：① 42010 附录 A.2 四种隐喻（*architecture as blueprint／literature／language／decision*，中译：架构即蓝图／文献／语言／决策）——**业界对架构的想象本身分四种**，误解常源于只取一种；② 42020 §E.2.1 加第七种（架构即约束）；③ 42020 附录 H 把标准映射到 TOGAF／PEAF／GERAM／DoDAF——**行业框架里"决策"没有统一位置**；④ 15288 §6.3.3.3 a) 1) 要求决策管理策略含**决策类别**——业界普遍缺这一栏，故既不筛也不分；⑤ 42010 §6.10.1 的 13 条选择准则——业界普遍没有判据，结果**要么全记、要么不记**。

**五、业界证据线索（标题级，未经原文核，用时须取正本）**：SEAA 2016 *Busting Software Architecture Beliefs: A Survey on Success Factors in Architecture Decision Making*（对业界关于架构决策成功要素的认知作了调查）；*Architecture Decision Records in Practice: An Action Research Study*（2024）；*Architecture Decision Records: Adoption, Impact, and Developer Engagement in Open-Source Software*（ICSA 2026）；Thoughtworks 关于"谁应参与软件架构决策"的讨论（Andrew Harmel-Law）。

**收束一句**：**业界的误解不是"不懂标准"，而是四个角色把决策分别理解成会议、图纸、代码和文档**——四者都不是正本说的"一组选择＋一份牵连＋一条理由＋一个署名"。**一句现场判据：会议散了、图纸归档了、代码合了、模板填了——此时问"这条决策谁署名？改它要重开谁的账？"，答不上来，就是误解现场。**
