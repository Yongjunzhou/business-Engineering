# 架构清单不依赖候选做法（用户裁决，2026-11-13）

## 裁决

用户对「定义架构清单要先有候选做法（两个以上）」这一说法**判「不采纳」**，含把「做法」改称「候选架构／实现路子」的退让版本。**该主张整条撤回，不作为定义过程的前置，也不算必备产品数据。**

理由由用户两问逼出、最后以裁决收口：先是「有点荒唐吧」（定「它是什么」不该先有两套实现），再是「鸡和蛋」（方案是架构的一次合规实现，拿方案定架构即循环）。我给出的两版辩解——「候选做法≠设计，在设计之前就能说」与「用的是关于实现空间的知识而非实现产物」——**均不被采纳**。

## 撤回的具体内容（前几答里以此为枢纽的说法）

- 「必须有候选做法集（D7）」——从必备产品数据里删去；
- 「步 2 立候选做法是整条链的枢纽」——该地位撤销；
- 「8 进 4 出」中的第 8 样、以及「判定句里加来路栏」的替代方案——一并撤；
- 「候选做法不循环」的论证（知识／产物之辨）——留作存史，不作口径。

## 仍然成立、不受影响的部分

- 判定句、落点、未覆盖声明三项输出不变。
- 标准方面的事实不变：42020 §8.4.5／§8.4.7 有候选架构与解空间综合，但**无一条 shall 要求必须有两个做法**；15288 §6.4.4.1 的「生成备选方案、选一个或多个」是过程目的句，不是义务条款。

## 生成逻辑的更正（本轮，用户判「不应该是这样的逻辑」）

前几答把清单当成「候选 → 比较 → 提取」的产物，方向错了；清单是**「判据 → 因子 → 条目」+ 覆盖反查**长出来的：

- 链条：目的 → 架构目标 → 关键成功准则 → 因子 → 条目；
- 生成：每条准则拆成可判的因子，对每个因子问「实体上必须有哪几条不可省的说法，这个因子才有着落」，答案即条目（划类的概念／定线的属性／禁许的原则）；
- 反查：每个因子至少一条条目，每条条目指得回一个因子或准则编号；指不回即不属此清单。

**三条随之：**
1. 不需要候选做法——条目被因子逼出，不被差异比出；
2. 「跨做法成立」不是动作，是因子归属的副产品：因子属目的层，条目真从因子逼出便天然跨做法；只在某一版成立的条目会因「指不回因子」被反查挡掉；
3. **走样检验降为校验，不是生成逻辑**——它只能否（这条不该留），不能生（这条应当有）。先前记「准入只剩走样检验一道判据」亦过重，已撤。

「换了做法还成立吗」仍移出定义过程，落到事后核对（变更、评审、基线更换）。
