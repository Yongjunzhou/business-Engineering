### 四 主线

**台账登记句（2026-10-08 阶段一确认；不改，只作台账口径）**：开发产品就是开发产品数据——开发全程没有一件实物可摸，你亲手造的是产品数据，实物只是它被复制出来的结果；数据质量决定上限不决定达成；产品数据是协作的对象、职责的落点，也是四性兼备的资产：产品会死，数据体系活着。

**正文主线（第三版，2026-10-25；请裁）**：

> **开发产品，"产品"是对象，不是产物——交出去的还是关于它的需求，一层比一层细，细到别人照着就能造；这一整套，就是产品数据。**

**为什么前两版不对（留痕）**：第一版「造的不是箱子，是那份写下来的东西」——箱子是冰链实物的替身，且把通用判断绑在案例物上（恒信没有箱子、软件没有车间）。第二版「不是一件能摸的东西，是一份能照着做、照着验的东西」——撤了替身，却只是把标题换个说法再说一遍，且"能照着做、能照着验"落到第3章"写到能造、能验"的地盘上。**两版共同的病：只说了结论（造的是数据），没有说定义给的根据。** 第三版把根据放进来——依据是设计开发的定义句本身。

**根据（ISO 9000:2026 §3.3.11，逐字取正本；本书术语作"需求"，不作"要求"）**

> set of processes that transform requirements for an object into more detailed requirements for that object
> 将某一客体（object）的需求转换为该客体更详细需求的一组过程。

三注（同条，正本）：

- **注 1**：输入的需求往往是研究成果，**表述比输出的需求更宽泛、更概括**；这些需求**通常按特性（characteristic）来定义**；一个项目中可以有**若干个设计开发阶段**。
- **注 2**：**"设计"与"开发"两词、以及"设计和开发"这一术语，有时作同义词用，有时用以指称整个设计和开发的不同阶段。**
- **注 3**：可加限定语表明设计与开发的对象（产品／服务／过程）。

**由此读出四层内涵**

1. **语法层**：定义句里两个 `for an object`——产品是**对象（客体）**，不是**产物**。"开发产品"读的是"以产品为对象做翻译"，不是"生产出产品"。石军在章首把它读成了后者，这就是本章误解现场的根。
2. **产物层**：输入是需求，输出还是需求，只是更细。**开发的产物天然是数据**——"开发产品就是开发产品数据"不是本书的主张，是定义句的直接推论；本书只是把它说到明处。
3. **词义层**：标准自己承认这组词摇摆（注 2：有时同义、有时指不同阶段）。这是全书"概念失败"的活样本；本章必须交代一句本书取哪一读（与第3章一致：取"一组过程"），另两种用法出现在哪儿一并说清。**"设计"给的是"该是什么"，"开发"给的是"怎么造得出来"；两样交出去的都是规定，不是物。**
4. **递归层**：一个项目中可以有若干阶段（注 1 末句）→ 第3章"每一级都在写细一层"、第6章"逐对接力"、本章"读到哪一级都还是需求"，都是这一句的下游。

**气脉句（问句，不含本书术语）**：**「两年定义、两周造出第一批——那两年到底在造什么？」**（24 汉字；嫌长可缩成「开发两年，到底造出了什么？」）

**兑现形态（章末拿到的一件东西）**：**一张三行的点数单**——造的是哪几份／每份谁认／缺哪一份，哪一关就接不上。读者回工位能把手上项目填一遍。

|---|---|---|---|
| ① | 约 25%（第一块末） | 你造的是那份写下来的东西，箱子是照它复制出来的——石军"数据是文档"的直觉当场翻过来 | 那这份东西长到什么程度，才算造完了？ |
| ② | 约 60%（第三块末／第四块交界） | 造完的标准是"下一层接得住"（可定位、可承接、可追溯）；它的成色就是产品的成色——上限，不是达成 | 那它归谁？箱子报废了，它还在不在？ |
| ③ | 约 90%（第五块末／小结前） | 数据有主（职责挂在工件上）、是资产（产品会死，数据体系活着）；**上线不等于数据归位** | ——（气脉在此答完） |

**定死项（写作时逐句对表，互抵为零）**

1. **五个词的层级**：产品 ⊃ 产品数据 ⊃ 配置项（受控的那部分）；文档＝容器；架构描述＝设计数据的一类，与设计描述平级。
2. **全称与简称**：题面作"开发数据"，正文首次给全称"开发产品就是开发产品数据"，此后简称照旧。
3. **两句话不许混**："开发 = 定义生成"（成立，限设计态）／"产品就是数据"（不成立）。
4. **数词**：两个存在／两个域／三个态／六类数据／五把尺子／四个资产条件——全章一套，不许换说法重数。
5. **"数据质量决定上限、不决定达成"**：正说一次，重说留给反转或小结，且必须升级（从"是上限"推到"所以开发阶段的质量怎么量"）。
6. **"产品会死，数据体系活着"**：一个字不改。
7. **"需求"与"要求"**：requirement **一律作"需求"**，"要求"是 demand、不用来指 requirement（2026-09-28 用户裁；见 `术语口径-需求与要求.md`）。**本章现文 §7.3.1 把引文写成"要求"，并加了一句"引文里的'要求'就是本书的需求"——这是那条裁明令作废的做法，本轮必须改。**

**唯一的重说处**：认知反转重说"你造的是数据"。第一次（第一块）是知识——他知道有两个存在；第二次（反转）必须是认账——"我第一次觉得，产品是我造出来的"。深不下去就删。

### 六 内容概要（讲什么，5 簇）

**簇一｜产品有两个存在**（约 1,800 字）
物理存在与信息存在；实物是信息存在的复制品；产品数据＝形式化的信息表示；四条边界（≠文档／≠配置项／≠产品／≠架构本身）各压到两三句，只给"文档""配置项"两处场面。
**不讲**：产品与服务的定义辨析、IPD 产品包、property／characteristic／attribute 三层术语学。

**簇二｜开发＝把定义造全**（约 1,900 字）
设计开发的定义仍是"更详细的需求"，不是实物；设计态里开发 ≡ 定义生成；两域三态（表一张）；软件没有独立制造环节（一段，冰链／恒信对照一次即可）。
**不讲**：三态怎么演化、数字孪生怎么建——只留"信息域跟上物理域"一句。

**簇三｜那棵树得让下一层接住**（约 2,000 字）
接回第6章那棵树：可定位、可承接、可追溯；实现方案是最重的一类（八个方案压成一张表或一段，只举物料那一支的冰链例子）。
**不讲**：树怎么长、三形态怎么分、链上谁做承接（第6章已尽）；八个方案逐条解释。

**簇四｜成色怎么量**（约 1,900 字）
数据质量决定上限不决定达成（多环相乘）；五把尺子（准确性／完整性／一致性／现时性／可信度）各一句＋一个冰链例子；缺陷沿工位放大（流水线：流动的是产品数据）。
**不讲**：精益七大浪费表、ISO/IEC 25012 的十五项、质量定义与"等级≠质量"（第3章）。

**簇五｜归谁，留不留得住**（约 1,700 字）

**不讲**：三角色责任矩阵、三维价值评价表（归第9、18章）；数字化转型五维度。

## 七 阶段三稿·第二版（2026-10-25 重做；**标题清单与三本账已获用户认可 2026-10-25**；四项待裁待裁）

> **为什么重做**：第一版把"终点"当成 `7.4` 里的一节（`方案配齐，才算做完了`），结果 `7.3 开发交出来的是需求` 与 `7.4 做完了没有` **两遍回答同一个问题**（交出来的是什么）——正是手册 §1.3.1 判据②"第二次走同一片地形"。用户一句"设计开发的终点是可实现的需求呢"把病点破：**终点不是补丁，是这一章的中轴**——开发走到"可实现"就停，停下来交出去的那一份，才是产品数据。本稿据此重排：终点升成 `7.3` 整块，`7.4` 只答"那份东西由什么组成"。

### 一 本章的内涵，与气脉重立（第六稿，2026-10-25）

**先把本章到底讲什么说清——四层，一层比一层深**

| 层 | 内容 | 落在哪块 |
|---|---|---|
| **一·对象** | 开发不产实物，产的是"这东西该是什么"的规定——那份规定就是产品数据 | `7.2`／`7.3` |
| **二·性质** | 它不是文档（容器）、不是配置项（受控的那部分）、不是产品本身、也不是架构；它是产品在信息域里的整个存在 | `7.2`／`7.4` |
| **三·价值** | 它定产品能有多好（上限，不保达成）；组织不是围着会议协作、是围着它协作；缺陷只能落到一份数据上 | `7.5`／`7.6` |
| **四·继承** | 实物一次性、会被消耗；数据可复制、可共同持有、可继承——**开发造的是产品里唯一能继承的那一部分** | `7.7` |

**内涵一句话**：**产品数据是产品的"可继承形态"**——开发之所以称得上"造产品"，正因为开发造的是产品里唯一能被复制、被共同持有、被下一代接着用的那一部分。这也解释了全书那句签名字：产品会死，数据体系活着。

**于是气脉只能是"身份问题"**：前六稿都在问侧面的东西——问"造什么"（对象）、问"做完没有"（终点）、问"文档凭什么"（一点）、问"留下什么"（继承），每一条都只撑到一块或两块。**本章真正的两难是：手上这些图纸、BOM、报告，凭什么跟"产品"平起平坐？** 读者心里它们是"资料"，本章说它们是"产品"。

**定稿建议**：「**图纸、BOM、验证报告——这些凭什么算产品？**」（18 汉字）

**六块各证一条**（这才叫撑满全章）：

| 块 | 证哪一条 | 答法 |
|---|---|---|
| `7.2` | 凭什么算产品（一） | 产品有两个存在；开发造的是信息那一个，实物是照它复制出来的 |
| `7.3` | 凭什么算产品（二） | 开发的定义就是"把需求写细"，细到可实现为止——它交出去的本来就是需求，不是东西 |
| `7.4` | 凭什么算产品（三） | 它有确定的组成：六类数据、每个下游一份方案、每一条都有落点——不是散落的资料 |
| `7.5` | 凭什么算产品（四） | 它定产品能有多好：多环相乘，数据质量定上限 |
| `7.6` | 凭什么算产品（五） | 它担得起责任：每份有唯一主人，缺陷只能落到一份数据上 |
| `7.7` | 凭什么算产品（六） | 它活得比产品久：能跨代接着用——这才是"产品"里真正被继承的那部分 |

**五关复核**：①**前提可核**——图纸、BOM、验证报告都是案例里真实存在的东西（BOM 与图纸对不上、三个版本的需求文档、季昭按哪一版验）；②**不自我反证**——句子的错前提（"这些是资料"）是读者的，不是事实断言，问的是**它凭什么升级**；③**求的是身份，不是名词**——问"凭什么算"，不是问"叫什么"；④**答案本章独有**——不是第3章的终点、不是第15章的版本管理，而是"两个存在＋复制关系＋上限＋问责＋可继承"这一整套；⑤**撑到九成**——后三块（成色、归属、继承）全在这条延长线上：能定上限、能担责、能继承，才配叫产品。

**前六稿的病根（一次记清，不再重犯）**：一～五稿都在问**过程**（造什么、做完没有、交了什么），六稿才回到**身份**——而本章的章题本身就是一句身份断言，气脉必须是读者对这句断言的不服。

### 二 骨架三案（重新构思后）

**甲案（建议）**：**终点驱动**——七块。`7.1` 一个答不上"做完了没有"的现场 → `7.2` 你造的是哪一半 → `7.3` 什么时候算做完 → `7.4` 做完的那份东西由什么组成 → `7.5` 它有多可信 → `7.6` 出了事找谁 → `7.7` 能留多久。

**乙案**：**对象驱动**——六块（把 `7.5` 质量并入 `7.4`）。缺陷：`7.4` 要同时装"六类＋八方案＋落点＋五把尺＋缺陷放大"约 3,400 字，全章最重的一块，且"组成"与"可信"是两问，混一块读者认不出地形。

**丙案**：**时间线驱动**——一份数据的一生（写下→接住→验住→存住）。缺陷：`验住` 在本章只到"能验"，真正的验证在第8章；且四段式会把"终点"埋到第二段，读者到 40% 还不知道"做完了没有"凭什么判。

**判据三条**：① **位置感**——甲案 `7.2`（约 15%）就把"你造的是数据、实物是复制品"翻过来；② **无复走**——甲案六块各答一问，`7.3`（性质/判据）与 `7.4`（组成/形态）切开后，不再两遍回答"交出来的是什么"；③ **分类图与顺序**——甲案没有分类图，块序即论证序。
