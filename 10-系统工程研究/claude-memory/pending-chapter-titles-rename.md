## 八、ch15 题面定案 ＋「配置管理 ↔ 需求工程」的边界（2026-10-14 用户裁，提交 `a332684a`）

**边界与各自目的（本轮答复的定稿口径；ch15 重写时进 `15.1.2` 承诺段）**：

| | 第4章 需求工程 | 第15章 配置管理 |
|---|---|---|
| 对象 | **规定需求这一份产品数据**（需求开发＝获取／分析／规格／校核；需求管理＝基线管理／变更控制／可追溯性／状态与度量） | **一切被选定为配置项的东西**——固件、硬件、代码、图纸、数据、需求规格书……（现文 L100） |
| 目的 | 把模糊的诉求做成**能当依据用的规定需求**，并让它**一直是那一份**（ch4 主线原话） | **让变化说得清**——任何时刻都答得出"它应该是什么／它实际是什么／它是怎么变成这样的"（ISO 10007 目的句＋现文 13.4.3 **配置管理三问**） |
| 判据 | 能否当依据（明示与可采、评审；书里说"需求文档只能评审"） | 能否对上账（三问；**版本顺着流、基线垂直切**） |
| 变更控制 | **需求侧闭环**：CR → 影响分析 → CCB 评审 → 实施 → **再验证** → 关闭（ch4 §4.2.6；附录 A **T-88**） | **机制推广**：**冻结 → 变更 → 再冻结**，适用于所有配置项；"从什么变到什么"由基线提供（现文 L378） |
| 追溯 | 需求→设计→验证的**追溯矩阵**（影响分析靠它反查） | **状态记录＋配置审计**（哪台设备哪一版固件、谁批的） |

**起因**：用户判「**本章的标题，设计定义：xxx……应该需要修改，避免让人误解对设计的定义**」。

**两处诊断（都不是措辞洁癖）**：
1. **主词「设计定义」首读作"对设计的定义"**——中文"X定义"默认读作"对 X 的定义"（"架构定义"同一坑：`10-第10章` 正文已当面拆过「架构定义不是'给架构下定义'」）。更要紧的是：**给"设计／设计开发"下定义这件事第3章 `§3.2.4` 已经做完**（ISO 9000:2026 §3.3.11 逐字＋更具体·更可实现·更可验证三条判据），章题摆在 ch14 会让人以为要补这件事，**抢前序章的活**（撞框架 §五 第 23 条共识④"不抢邻章的词"）。
2. **副题"从架构到设计描述"是"从…到…"式，易读成接力**——本章地基恰是"**不是接力，是递归里的一个换手点**"（旧 `16.2.1`，一字不动）。

**裁定**：第14章题面＝**`架构与设计：种类不是粒度`**（11 汉字）。**取舍口径**：**主词换成两个正本概念名**（*architecture*／*design*，15288:2023 §3.5／§3.13；也正是本章正本脊柱 24 号报告的题域），**副题直取本章第一命题**（框架 §三 ch14 行"反直觉核心命题"首句）——**两处一并解决**：不再读成"对设计的定义"，也不再读成接力；且与 ch10~13「架构X：一句判断」族**仍以"架构"起头**，同时标记中篇的转折（从架构这一侧交到设计这一侧）。

**落杀二案**：**乙** `架构与设计：约束与依从`（10 汉字，副题给两头动作，承诺性更强，代价＝"依从"单看略生）／**丙** `设计定义：架构交出去的那一段`（13 汉字，保留正本过程名，代价＝"对设计的定义"那一读法只被压小、未消掉）。
