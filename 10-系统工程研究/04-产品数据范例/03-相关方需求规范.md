# 03 · 相关方需求规范

> **性质**：**口径件**——文档3 相关方需求的**栏、门与承接唯一性**只此一处。名字取《相关方需求规范》（*Stakeholder Requirements Rulebook*）。
> **适用边界**：**只管文档3**。文档5 系统需求、文档15 构件需求的条目形态归各自规范，**不自动继承本规范**；将来若要统一，改名并扩适用，不在这里悄悄扩。
> **户口三分**：条目形态与唯一性 → 本文｜关切到需求的转换规则与不成立判定 → 48 号卡3｜工序（七个阶段・逐阶段确认・四年工程师・收工三写）与通则（三要素・三类・指标两型・体例・文风・资产・数三档・构造规则）→ 规程 4.2・4.5~4.11｜进度与打回 → 00 号台账。**冲突判据**：条目形态以本文为准，转换以卡3 为准，工序与通则以规程为准。
> **一条分界**：**业务的身份＝（主角色，触发事件）这一对；需求挂在业务上，不挂 IPO**。IPO 去重后会被多条业务共用，需求若挂 IPO 就同时被几条业务承接，唯一性当场破；挂业务则不受去重影响。

## 1 概述

**是什么**：把“谁、在什么事件下、要什么、到什么程度”写成一条条**可判真假**的相关方需求，并让每条恰好落一条端到端业务（坐标一对）。它是文档2 的关切与文档4 的业务之间那一段：关切在这里长成条目，条目在下一份按坐标长成场景。

**不是**：

| 近邻 | 分界 |
|---|---|
| 关切（文档2） | 关切是方面（“断链可判性”），需求是条目（谁・何时・要什么・到什么程度）；关切不等于需求，一条关切可出多条需求 |
| 业务／场景（文档4） | 这里只给坐标（主角色・触发事件）与落点（一次交接），不写 IPO 链、不写活动、不写确认准则 |
| 系统需求（文档5） | 这里用相关方语言（要什么），不换量纲、不写验证方法；换语言与挂验证是文档5 的事 |
| 约束与原则（文档9） | 跨业务、无触发的要求（可配置、数据不可改、全链留痕）不是本册条目——它们是约束或原则，不占需求号 |

**三条内容规矩**：① **三要素齐**（名称・描述・指标；指标至少一条度量型）——通则见规程 4.5，本文不重复；② **可判真假、不暗示实现**——出现型号、协议、算法即拆成“要求”与“建议实现”，后者不入表（细则见 48 号卡3）；③ **来源只挂上游**——问题号或关切号，**不挂业务号**（上游不挂下游的账）。

| 词 | 定义 | 出处 |

## 3 表的张数与字段写法

### 3.1 十一栏

| 栏 | 写法 | 不成立 |
|---|---|---|
| 号 | 1、2、3…；冻结不复用；一个号一条 | 一号两条；复用旧号 |
| 需求名称 | 名词短语（“超温判定与责任人通知”） | 一句话、带指标、带方案 |
| 需求描述 | 一句可判真假：谁・何时・要什么・到什么程度；不暗示实现 | 形容词；“要可靠”；出现技术名 |
| 性能指标 | 带单位与值或值域；**至少一条度量型** | 只有门槛型（0／100%）；无单位 |
| 初步验收方式 | 一句可执行的核法（抽几票・走一遍・实测一次） | 写“按规范验收” |
| 需求种类 | 功能性／质量特性／易实现性（按“谁在问”分） | 空着；与系统需求的类混用 |
| 来源 | 问题号或关切号，至少一个 | 空着；写下产业务号 |
| **主角色** | 文档2 的一个岗位名；取该业务的业务主，或**需求提出者及其代理者** | 群体（“客户”）、部门名、系统名、两个以上角色 |
| **触发事件** | 一个**可判定的到达事件**（见 3.2），一个事件 | 时段（“在运期间”）、状态（“离线时”）、条件（“超 8℃”）、两个事件 |
| 谁来认 | 岗位名，可多个，主认者标（主）；与「主角色」并列，重合时同名写两遍 | 写人名；只写部门 |
| 由哪档场景确认 | 由文档4 回填（正常／异常／应急）；**质量特性行写“不适用（非业务判据）”** | 空着；拿别档充数 |

### 3.2 触发事件

**三件齐了才算一个触发事件**：谁接到（一个主角色）｜接到什么（一个输入载体：单据・通知・告警・任务・批次・样本・退役件）｜何时算接到（到达某处／某状态成立并持续超门槛／某时点到来）。检验：交给没参与的人问“现在这条业务开始了吗”，答得出且唯一。

**四类来源**：外部交付（承运方接到装车任务）｜状态变化（温度越限并持续超门槛、联网恢复）｜人工发起（货主提出索赔、监管发出抽检通知、司机报障）｜时间事件（资质到期日到来、复核周期到点，须落到“到点要处理的那批东西”上）。**与四个近邻的分界**：I 是到达的那个东西，触发是到达这件事｜条件进事件，不单独当触发｜时段与状态判不了开始｜活动在业务内发生，触发让业务开始。

**词表**：触发事件进受控词表（文档3 的 §3.3），一行一个触发类型，同义只留一种，新事件先进表。**归并两条**：同一主角色下行为本质相同的触发归并成一类，来源与目的不同的分属两类。**本册细则**：同一状态机的进入与退出算一条业务的两端（断网与恢复），目的不同者除外。

### 3.3 落点与判据

| 规矩 | 判法 | 罚则 |
|---|---|---|
| 落点唯一：一条功能性需求只约束**一次交接** | 被违反时在哪个时刻、由谁、看什么证据能判出？答案必须唯一 | 拆条 |
| 判据独立：同一坐标下两条需求各有独立的初步验收方式 | 同一个验收方式能一次判完的，是一条不是两条 | 并条 |
| 下界：每个交接至少有一条需求指着 | 没有需求指着的交接，说明没人要或业务切错了 | 回核业务 |

### 3.4 唯一性的核法

**坐标归并表**（文档3 末尾的机械产物）：主角色｜触发事件（词表行）｜需求号集合｜业务暂名（{谓语}{宾语}）｜条数｜落哪一节。**三条可核条件**：需求号在全表只出现一次｜行数＝业务数｜每行有暂名并能定位一节。文档4 开工直接拿它当输入，不再判主角色与业务。

### 3.5 拆并守恒

拆并时（主角色，触发事件）对的集合变化必须登记：**拆分不得凭空产生新坐标对**——新坐标对即新需求，走承接档并说明为什么没有现成的。需求号发布后不复用；拆出的新条在原号后加“之一／之二”或在表末续号，同册取一，不许混用。

## 5 验收准则与判定结论

### 5.1 准则的正反两面

| 判否 | 判法 | 不成立的处置 |
|---|---|---|
| ① 坐标缺或有两值 | 功能性・易实现性行各有且仅有一个主角色、一个触发事件 | 退回补或拆条；质量特性行按 3.1 写“不适用” |
| ② 触发不是事件 | 触发事件栏能过“现在这条业务开始了吗”一测 | 退回改写；改不成的转约束或原则 |
| ③ 落点不唯一 | 每条功能性需求按“一测”判得出唯一交接 | 退回拆条 |
| ④ 归并表有重号或行数不符 | 需求号在归并表只出现一次；行数＝业务数＝文档4 的业务数 | 退回查哪条没拆干净 |

### 5.2 判定结论的取值

结论只有三值：成立／缺口待补／违例，逐条判，末尾一句计数。

### 5.3 判定结论的处置

退回补或拆条的，执笔当场改，改完由评审复核；改不动的写清解锁人与时机，落 00 号台账该文档那一行；与该份规范相抵的记违例，交元流水线开发者裁。

### 5.4 所管数据的题面与表达

须按下列各条管本册所管数据（文档3）的题面与文字表达，本册不另立判据：题面按《逐章修订手册》§2.6 三道关、§2.13 自足、§2.7.2 标题与正文的分工；文字表达按《风格参考》§6.4、§6.7、§6.8 与编制规程 4.9 的文风八忌。

交稿前须走编制规程 4.2 的第六阶段（题面与表达），不得跳过，也不得以“下一份再改”挂账。该阶段交三张清单：两页题面（本册一页、数据一页；一行为一题：级别｜题面｜汉字数｜九项打勾｜⑧ 带的词）、表达清单（表外散文句逐句：句｜犯哪一忌｜改后句）、件名与节题符合性对照（见《编制规范》4.1 那张表）。

机械读数须为硬违规 0：`python 03-架构师是个怎样的物种/00-标题-形式关.py <数据文件>`。读者关须另开一只代理，只给题面、不给背景，让它复述每节讲什么。改题或改句后须重跑读数。

合格的标志：机械读数硬违规 0；两页题面的九项逐条有勾、⑧ 填出词；读者复述得出来；表达清单每行有改后句或判为可留，无未处置行。

不合格的处置：题面或表达有一条不过，退回改题或改句，改完重跑；数据尚未建的，写“待建”并注明与那份数据同批做。

## 6 下游用法与错法

### 6.1 下游取用的字段

| 下游 | 关系 | 谁做 |
|---|---|---|
| 文档4 生命周期概念 | **参照**（不派生需求）：坐标归并表＋词表交给它建业务树 | 文档4 读入 |
| 文档5 系统需求 | **转换**（`transform`，`1:N` 允）；主角色与指标作它的上游 | 文档5 读入 |
| 文档15 构件需求 | 按系统需求再往下分 | 文档15 读入 |

### 6.2 下游不得代补条目

**不设同批**：本文与上下游只有“被读入”一条边，回填（由哪档场景确认）由文档4 出表、本文下次修订时自己照抄。下游发现本文缺条或缺触发，落 00 号台账打回那一行，本文择时改；下游不得替本文补条、不改描述。

### 6.3 错法清单

| 错法 | 判例库 |
|---|---|
| 群体当主角色（“客户”“各方”） | 判例库第 25 条 |
| 拿时段或状态当触发（“在运期间”“离线时”） | 判例库第 25 条 |
| 一条需求里用“或／和／分别／各”并联两个角色或两个事件 | 暂无判例 |
| 坐标写不出又硬凑一个 | 暂无判例 |
| 落点两个却留一条（“输入与输出都要”混写） | 暂无判例 |
| 同一交接上两条需求却只有一个验收方式 | 判例库第 8 条 |
| 拿关切原文当需求 | 暂无判例 |
| 把平台级不变量写成需求（应转约束或原则） | 判例库第 23 条 |
| 拆条时凭空多出一个坐标对而不登记承接档 | 暂无判例 |
