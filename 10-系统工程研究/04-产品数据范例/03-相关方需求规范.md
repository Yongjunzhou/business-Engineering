# 03 · 相关方需求规范

## 1 概述

这份数据是产品开发过程中产品数据清单里的第三份，上承第二份《相关方与关切》与第一份《问题与机会清单》，下交第四份《生命周期概念》与第五份《系统需求》。下文写「文档2」「文档4」，都指那份清单里的第几份。

它装四样取值：相关方需求，三类同住一张表；触发类型；候选端到端业务与候选末级节点，各按坐标对计列；关切与承接它的需求之间的对账。料由文档2 的关切与文档1 的问题、机会，加需求调研记录里的原始需求汇总而来，不由别的产品数据变来。

| 近邻件名 | 分界一句 |
|---|---|
| 产品数据本身 | 那份文件装取值，一个数据项一个事实或一个号；本册只写字段名与写法判法，一个真条目、一个真取值都不装 |
| 同号过程记录件 | 与本体同号的过程与交付记录件装门、留痕与未完项，该件随数据 v0.31 同批立；本体装取值，本册管字段与判定；该件的题名与九节题同按元规范 8.1 核 |
| 编制规程 | 规程管工序与通则：七个阶段怎么走、取用与留下的资产、体例与文风、取料与标档、留痕九节；本册管这一份的表与字段、合格判定 |
| 48 号第3卡 | 卡上给转换规则与不成立判定的正本，含输入两件、五步、输出形态四栏、三条不成立判定与一条常见错误；本册写它们落在哪一字段、看哪一个数据项、数什么。卡改了依卡号回查本册，本册写错也依卡号回到卡上 |
| 判例库 | 库中一条一行记已犯过的错法与自查查法；本册只列错法名并挂条号，不展开案例 |
| 24 号 | 逐件推进的登记处，记进度与打回；本册只在打回台账与该件的「门」列登记，不向它取条目 |

依据：读 48 号第3卡（相关方需求集）——输入两件、五步、输出形态四栏、三条不成立判定、一条常见错误。引 15288 三处：§3.36 给需求的定义句、§5.9 给概念到需求的三层演进、§6.4.2 给这一过程的目的、预期结果与活动任务。上游两份产品数据：文档2 供关切与角色，文档1 沿卡3 步骤④的「问题编号」供来源；其余输入是资产与原料，逐处见 4.1。

一条分界：需求挂在端到端业务上，不挂 IPO。IPO 去重后被几条业务共用，需求若挂 IPO 就同时被几条业务承接，唯一性当场破；挂业务则不受去重影响。

## 3 表的张数与字段写法

### 3.1 表的张数与级次

形态：平面表与坐标对并存。平面表三张：需求主表、触发事件词表、关切对账表；另有两处坐标对清单，即业务候选清单与节点候选清单，按主表「主角色・被度对象」与「触发事件・质量特性」两栏归并得出，业务暂名一个数据项人定，不作数据表计；两处清单的字段表见 3.2.4 与 3.2.5。

三类需求同住需求主表，按需求种类那一栏分开：功能性行的两栏写主角色与触发事件，非功能行的两栏写被度对象与质量特性。两栏名各含一个「・」；「层·角色」的「·」是另一个字符，核表头时按字符核，不按字形核。

| 表的名称 | 记录单位 | 编号号段 |
|---|---|---|
| 需求主表 | 一条相关方需求 | 编号 1 至 N，三类共用 |
| 触发事件词表 | 一个触发类型 | 触发类型编号，T 加两位数字，从 T01 起 |
| 关切对账表 | 一条关切 | 不编号，一行按关切编号定位 |

词表是受控表：一条功能性需求的触发事件必须先在该表有一行。业务候选清单由主表功能性行按那两栏的值归并得出，主角色与触发事件照主表逐字取；要人定的只有业务暂名。

表间挂靠三处：主表的功能性行所写编号须在词表查得到；两处清单按主表那两栏归并出承接需求编号与需求条数；关切对账的承接需求指回主表。主表不写候选号与正式号，正式号回填在下游那一侧。

号段与唯一性：编号 1 至 N，按条目在取料中出现的次序编，冻结不复用；一条需求凭号唯一，一条业务与一个末级节点凭那一对值唯一；主表一行凭那一对值与描述所指那件事唯一——同一对值下说同一件事的并作一行，说两件事的分作两行。原始需求的拆解在调研记录里做完，并列写就并按并列次序编号；取料之后才补拆的条目在表末续号，不用「之一／之二」。需求不得占号不占行（规程 4.5）：三样缺一即不是需求，不许只留一个号。

承接两条路：功能性行那两栏写一个岗与一个触发类型编号，各写一个；同一状态机的两端在一数据项里写两个编号、顿号连，除此不算写两个。非功能行那两栏写一个被度对象与一项质量特性，也各写一个。写混两种、空着，都不成立。号不进主表：业务候选号与节点候选号留在两处清单里，由清单按那一对值归并。

末级节点四条判据：单一对象、单一质量特性、通过线可判、不再下分。末级节点与通用特性表的清册由文档5 立。本册只列节点候选清单，五列，见 3.2.5。

落点三条：一条功能性需求只约束一次交接；同一坐标下两条需求各有独立的初步验收方式，能一次判完的是一条不是两条；每个交接至少有一条需求指着，没有的说明业务切错了，回核文档4 的 IPO 表。

拆解两条界：一是按承接单位拆，一条原始需求占两个承接单位就拆成并列两条；二是按谁在问拆，同一件事两个主人各说了一句，拆两条、各归一类，两主条的性能指标与初步验收方式各写各的。拆的是需求，不拆业务：端到端业务由文档4 立，本册只提候选，不得为装下需求多造一对坐标。拆完仍有一处对不上的，转约束或原则，落文档9，不入本册。拆解增行不改栏，故不入 4.2 的转换表。

同一状态机的进入与退出并作一条业务，如断网与恢复：词表分两行，主表那一个数据项写两个触发类型编号、顿号连，业务候选清单照它归并，条数按并后计。

拆并守恒：拆解不得凭空产生新的坐标对；产生新坐标对即新需求，走承接档并写明为什么没有现成的。

两处清单都是按主表那两栏归并出来的：业务候选清单按功能性行归并，见 3.2.4；节点候选清单按非功能行归并，见 3.2.5。两处清单的承接需求编号与需求条数由主表归并得来，不另取值，对得上与否照 R17、R18、R21、R22 判；要人定的只有业务暂名，生命周期节取文档4 的第 1 级族员，文档4 未立时写〈待定〉。

### 3.2 逐表的字段写法

本节字段名以本册为准。主表的七栏（需求名称、性能指标、需求种类、主角色・被度对象、触发事件・质量特性、认领的岗位、场景确认档）、业务候选清单七栏、节点候选清单五栏，48 号卡3 上都没有，须落打回台账第 93 行①、由元流水线开发者裁后同批补卡；补卡之前按本册写，不另行改卡。卡3 的两栏作「陈述句」与「来源」，本册作「需求描述」与「需求来源」，两处是改名，卡、3.2、数据与规程 5.4 之三的点名表四处同批改，落第 93 行②；规程那一行现写号、需求名称、需求描述、性能指标、初步验收方式、需求种类、来源、主角色、触发事件、谁来认、由哪档场景确认，其中号、来源、主角色、触发事件、谁来认、由哪档场景确认六个名与本册不同字。

#### 3.2.1 需求主表

| 字段名 | 写法 | 不成立 |
|---|---|---|
| 编号 | 阿拉伯数字 1 至 N，按条目在取料中出现的次序编；冻结不复用，一个号一条；补拆的条目在表末续号 | 跳号或改号；复用旧号；一号两条；同一份里两种拆号法混用 |
| 需求名称 | 名词短语，读到名称即知所指 | 一句完整描述；带指标；名称里出现阿拉伯数字或型号码；带括注 |
| 需求描述 | 一句可判真假：谁、何时、要什么、到什么程度；不暗示实现 | 出现可靠、及时、尽量一类评价词；出现产品名、型号、协议名或算法名；照抄关切说明或问题原话整句；一句话里写两件分属不同一对值的事 |
| 性能指标 | 三到四个量，每量带单位与值或值域；至少一个度量型，其余可为门槛型；取不到的量标〈待定〉 | 只有一两个量；超过四个量；全是门槛型；无单位；写满足要求 |
| 初步验收方式 | 一句可执行的核法：抽几票、走一遍、实测一次，指得出核什么 | 写按规范验收；写验收时看；一数据项内要两套互不相干的核法才算并两件事，同一票先取后核不算 |
| 需求种类 | 三值之一：功能性需求／通用质量特性需求／易实现性需求，按分类三问判：客户与使用者问做不做得到要它做的事即功能性；客户就使用环境与使用方式问用不用得下、活不活得下去即通用质量特性；承制方问比现有多容易造，答得出更少专用件、更少工时、更少产线改造、更低成本即易实现性。一个特性两个主人拆两条 | 空着；答不出问者是谁；写质量特性漏通用；与系统需求的类混用；拿名称判而不拿问者判；易实现性行写不出一条容易度量，全是 0 处与 100% 的门槛量 |
| 需求来源 | 上游的号：关切编号、问题编号、机会编号、调研记录条号，四类至少一处；同一件事在文档2 关切表或文档1 问题表已立户的，本栏须同时挂那个号；条号照抄调研记录里的条号，回记录核那一条带被访岗位、时点与原话；号在前份或调研记录里查得到；多处并列写 | 空着；写下产业务号；挂查不到的号；写名称不写号；同一件事在文档2 关切表或文档1 问题表已立户而本栏未挂那个号 |
| 主角色・被度对象 | 按需求种类取一样：功能性行写文档2 相关方表的一个岗，写「层·角色」；非功能行写一个名词，取需求描述里被度的那一个，一类东西一个名 | 空着；功能性行写群体或部门名，或一个数据项两个岗；非功能行一数据项里两个对象；与描述对不上 |
| 触发事件・质量特性 | 按需求种类取一样：功能性行写一个触发类型编号，取词表里查得到的一个，同一状态机两端写两个编号并用顿号连；非功能行写通用特性表里的一名，未立时写〈待回填〉 | 空着；功能性行写时段或写词表查不到的号；同一状态机两端分作两行；非功能行写表外的名或一条写两项 |
| 认领的岗位 | 一个或几个文档2 相关方表的岗，写「层·角色」，多个用顿号连；主认者标（主）；可与该业务的主角色重合 | 写人名；只写部门；一个岗都没有；主认者标了两个；岗在文档2 相关方表查不到 |
| 场景确认档 | 由文档4 回填三档之一：正常／异常／应急，只对运行一节的业务；文档4 未立、或该业务不在运行一节时写〈待定〉并写转文档5 与文档9 的落点；非功能需求写「不适用（非业务判据）」 | 功能性行既未回填也未写〈待定〉；拿别档充数；非功能行空着或也填一档 |

两栏名里的「・」是列名的一部分，不是表名与字段名之间的分隔。

### 5.2 判定结论与不过的处置

按 5.1 五条逐条判到每条记录——主表一行、词表一行、业务候选清单一行、关切对账一行、节点候选清单一行，各算一条记录。判过就是过，交付件不记成立、缺口待补、违例这类状态，也不给计数。逐条的判断依据留在工作件的评审记录里，数据不摆。24 号进度台账该文档那一行的「门」列只记一句「按本册 5.1 逐条判过」与读数几处；那一列是台账的列名，取规程的件名，数据里对应的节题作验收准则与判定结论，两处不是两套判据。这一段落在同号过程记录件第 1 条，该件随数据 v0.31 同批立。

### 5.3 判不过的两条路

只剩两条路。一条改到过：本份执笔当场改，改完由评审复核，不另立时机；判该条不适用而改作不入表的，也归这条，由评审提、元流水线开发者定，改动落 24 号打回台账。另一条挂进未完项：只收当场改不动的四类——须实测才得的量、须上游答复的条款号、须立册才有的户名与号、须另开一只代理的复核；写谁办、几时办、落 24 号哪一行，交稿前在同号过程记录件的未完项一节逐行写清。不留第三种状态：判不过又不在这两条里，就是漏改。

本册不设题面与表达专节：所管数据的题面与表达按《产品数据规范编制规范》8.1 的三问与 8.2 的七条自核。
