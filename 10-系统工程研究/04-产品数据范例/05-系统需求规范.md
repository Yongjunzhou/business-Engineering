# 05 · 系统需求规范

> **性质**：**口径件**——文档5 系统需求的**栏、门与写法**只此一处。名字取《系统需求规范》（*System Requirements Rulebook*）。
> **适用边界**：**只管文档5**。构件需求（文档15）另立；文档15 沿用本文的验证三格并加「验收载体」一栏，不整册继承。
> **户口三分**：栏与门 → 本文｜转换与不成立判定 → 48 号卡3／卡4（相关方需求集・系统需求集）｜工序与通则（七个阶段・逐阶段确认・体例・文风・资产・数三档・构造规则）→ 规程 4.2・4.5~4.11｜进度与打回 → 00 号台账。**冲突判据**：形态以本文为准，转换以卡3／卡4 为准，工序与通则以规程为准。
> **一条分界**：**验证（verification）≠ 确认（validation）**。本文的每条需求只作**验证**的参照——“是否按规定需求造对”；**确认**的参照是文档4 的运行概念——“在预期用途里够不够用”。两把尺子不互换，不许拿确认准则充当验证通过线。

---

## 1 概述

**是什么**：把相关方需求**换语言、换量纲**，写成一条条可测、可验、可分配的**系统需求**；每条指回上游、挂验证三格、标主落平台。它是序程侧真正动手时看的那一册。

**不是**：

| 近邻 | 分界 |
|---|---|
| 相关方需求（文档3） | 这里不写“谁要、什么时候、为什么”；那三样留在上游，本文只写“系统须做到什么、到多少” |
| 架构目标（文档6） | 这里不写方向句与准则；指标是验收线，不是判定架构成败的尺 |
| 设计描述（文档16） | 这里不写怎么做；出现型号、协议、算法即违 |
| 构件需求（文档15） | 这里不分到构件、不写验收载体；分配在文档11，切叶在文档15 |

**三条转化规矩**：① **换语言与量纲**——上游的“要一份我方自己能核的记录”转成“记录链式签名、单条可独立验真”；上游一条可出多条（`1:N` 允），每条都写清承自。② **不暗示实现**——写出选型即拆成“要求”与“建议实现”，建议实现不入表。③ **每条指回上游**——承自栏必填，可多条；无来源的不写。

**类不换**：类栏用**技术类名**（功能・性能・质量・可靠性・接口・过程・兼容・安全…，可并写如“功能＋性能”）——它与文档3 的“三类（功能性・质量特性・易实现性，按谁在问分）”**不是一套，不许互换**。文档3 的类判“谁在问”，本文的类判“技术上算什么”。

## 2 术语

通用词只指路到《产品数据规范编制规范》第 3 章。本册特有的词：

| 词 | 定义 | 出处 |
|---|---|---|
| 承自 | 指回上游相关方需求的号，可多条；衍生需求标「衍生」并写推出依据 | 本文 3.1；48 号卡4 |
| 验证三格 | 方法（四值）｜验什么（七值）｜通过线（一条可判的线），三格缺一即不合 | 本文 3.1；15288 §6.4.9.3 注 |
| 通过线 | 验证三格的第三格，一条可判的线；不叫“成功准则”，那与文档6 的关键成功准则同名不同物 | 本文 3.1 |
| 主落平台 | 实物平台或信息平台，一个主承担；两平台分担时写“主承担〔平台〕＋参与〔平台〕”，主承担必填 | 本文 3.1 |
| 设计约束 | 强制型关切（法规・合同）落成的约束，表下专列，不占需求号 | 本文 3.1 |
| 两量分家 | 判定门槛与响应时延两类量必须分开写，混成一句验时判不出哪一格没达标 | 本文 3.2 |
| 变体需求 | 客户差异，不进本表，按三条去向处置 | 本文 3.3 |

## 3 表的张数与字段写法

### 3.1 六栏

| 栏 | 写法 | 不成立 |
|---|---|---|
| 号 | 系统需求1、2…；**冻结后不复用**；一条一件事 | 一号两条；跳号 |
| 陈述（可测量） | “系统须…”，带单位与值或值域；一句一条 | 形容词、复述上游原句、写选型 |
| 类＋设计约束 | 类写技术类名（可并写）；**设计约束单列**，不占需求号，列在本表下方专列并注来源 | 把设计约束混进需求行；类栏空着 |
| 承自 | 指上游相关方需求的号，可多条（`需求1；需求5、8`）；**衍生需求标「衍生」并写推出依据** | 空着；或只写“上游” |
| 验证三格 | 方法（四值：检查・分析・演示・测试）｜验什么（实际系统・模型・实物模型・原型・程序・计划・文档等）｜**通过线**（一条可判的线） | 三格缺一格；通过线写“达标”“满足要求” |
| 主落平台 | **实物平台／信息平台，一个主承担**；两平台分担时写“主承担〔平台〕＋参与〔平台〕”，主承担必填 | 空着；写“两平台都做”而无主承担 |

### 3.2 两量分家

一条系统需求里若同时含**判定门槛**与**响应时延**两类量，必须分开写（两行或同一行两段写清）：例“超温判定门槛 ≥N min；判定到通知 ≤30 s（p95）”。混成一句的，验的时候判不出是哪一格没达标。

### 3.3 变体需求不进（三条去向）

客户差异不写进本表，按性质归三条去向之一：

| 去向 | 什么性质 | 落到哪 |
|---|---|---|
| 进上游 | 是客户真正要的能力 | 回文档3 补一条相关方需求，再由它转一条系统需求 |
| 进配置点 | 平台能配出来的差异 | 文档11 的配置点与配置登记三件 |
| 升级平台变更 | 撞平台级不变量（温区・告警指标・判定算法・封包规则・留痕机制） | 文档9 的原则与文档13 的决策，走的不是配置 |

## 5 验收准则与判定结论

### 5.1 准则的正反两面

| 判否 | 判法 | 不成立的处置 |
|---|---|---|
| ① 双向追溯断 | 每条系统需求有承自；每条相关方需求至少被一条承接，或注明“本阶段不承接＋理由” | 退回补；只在真不承接时写理由 |
| ② 验证三格不齐 | 三格齐、方法取四值之一、验什么取七值之一、通过线可判 | 退回补 |
| ③ 主落平台空 | 每条有主承担（可带参与） | 退回；无法定位的分到两位或退文档11 |
| ④ 设计约束混入 | 约束已在表下专列、注了来源 | 退回拆开 |
| ⑤ 变体需求进表 | 表内无客户差异条目；有则已按三条去向判过 | 退回按去向处置 |

### 5.2 判定结论的取值

结论只有三值：成立／缺口待补／违例，逐条判，末尾给计数。

### 5.3 判定结论的处置

退回补或拆开的，执笔当场改，改完由评审复核；改不动的写清解锁人与时机，落 00 号台账该文档那一行；与该份规范相抵的记违例，交元流水线开发者裁。

### 5.4 所管数据的题面与表达

须按下列各条管本册所管数据（文档5）的题面与文字表达，本册不另立判据：题面按《逐章修订手册》§2.6 三道关、§2.13 自足、§2.7.2 标题与正文的分序；文字表达按《风格参考》§6.4、§6.7、§6.8 与编制规程 4.9 的文风八忌。

交稿前须走编制规程 4.2 的第六阶段（题面与表达），不得跳过，也不得以“下一份再改”挂账。该阶段交三张清单：两页题面（本册一页、数据一页；一行为一题：级别｜题面｜汉字数｜九项打勾｜⑧ 带的词）、表达清单（表外散文句逐句：句｜犯哪一忌｜改后句）、件名与节题符合性对照（见《编制规范》4.1 那张表）。

机械读数须为硬违规 0：`python 03-架构师是个怎样的物种/00-标题-形式关.py <数据文件>`。读者关须另开一只代理，只给题面、不给背景，让它复述每节讲什么。改题或改句后须重跑读数。

合格的标志：机械读数硬违规 0；两页题面的九项逐条有勾、⑧ 填出词；读者复述得出来；表达清单每行有改后句或判为可留，无未处置行。

不合格的处置：题面或表达有一条不过，退回改题或改句，改完重跑；数据尚未建的，写“待建”并注明与那份数据同批做。

## 6 下游用法与错法

### 6.1 下游取用的字段

| 下游 | 关系 | 谁做 |
|---|---|---|
| 文档6 架构目标 | 目标取坐标与「为谁」，判的是架构成败，不用本文的通过线 | 文档6 读入 |
| 文档9 架构内容 | 内容来路引本文的号 | 文档9 读入 |
| 文档11 位与分配 | **主落平台是分配的第一刀** | 文档11 读入 |
| 文档14 系统分解结构 | 切法须与主落平台一致 | 文档14 读入 |
| 文档15 构件需求 | 承自本文的号；沿用验证三格，**加「验收载体」一栏** | 文档15 读入 |

### 6.2 下游不得代补条目

**不设同批**；下游发现本表缺条或缺通过线，落 00 号台账打回那一行，本表择时改；下游不得替本表补条、不改陈述。

### 6.3 错法清单

| 错法 | 判例库 |
|---|---|
| 照抄上游原句（没换语言） | 判例库第 26 条 |
| 写选型（“采用北斗双通道”） | 判例库第 23 条 |
| 把客户差异当系统需求塞进来 | 判例库第 10 条 |
| 主落平台写“两平台” | 暂无判例 |
| 验证三格写“测试・验证是否满足”而无通过线 | 暂无判例 |
| 拿文档4 的确认准则当通过线 | 暂无判例 |
| 设计约束混进需求行 | 判例库第 12 条 |
| 类栏留空或与文档3 的三类混用 | 暂无判例 |
| 一条需求混两类量纲 | 判例库第 25 条 |
