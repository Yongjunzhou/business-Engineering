2026-09-19 修 `.tools/md2pdf/md2pdf.js`：转出的 PDF 里文档内锚点（目录、交叉引用）点不动。

**根因**：`mdSlugify` 末步用 `\s+`→`-`，把**连续空白压成一个**连字符；GitHub（github-slugger）是**逐空格替换**。凡标题里含「被剔除的标点夹在空格之间」者两边就不一致，典型 `## 第一部分 · 要点摘要`——「·」被剔除后剩两个空格，GitHub 得 `第一部分--要点摘要`（两连字符），本工具只得一个。于是目录里手写的 `#第一部分--要点摘要` 找不到目标元素，链接被静默丢掉。改为 `/ /g` 即一致。

**附带修**：同名标题原先 id 直接重复（无效 HTML），且指向第 2 处及以后的锚点无目标。现按 GitHub 约定顺次取 `slug`、`slug-1`、`slug-2`…。

**一条被证伪的猜想（留痕防复发）**：曾判断是「Chromium 打印 PDF 时不为非 ASCII 命名目标生成链接注解」，据此把标题 id 改成 ASCII 顺序 id 并改写 href。**这是错的**——隔离实验（裸 HTML → puppeteer → `page.pdf`，一个 ASCII 目标对一个中文目标）显示中文 id 照常落地：注解 `/Dest` 与 Catalog `/Dests` 表里都是**百分号转义名**（如 `/%E7%AC%AC...`），链接可用；PDF 里“链接不可用”的真凶只是 slug 不匹配。该改造已撤。
> 那次误判的起因是首轮对照实验设计有缺陷：测试文档里的中文锚点**本身**就写成了与 slug 规则不符的形式，于是「中文」与「slug 不匹配」两个变量混在一起，我误记成了前者。**教训：定位「锚点失效」时，先验证 href 与目标 id 逐字相等，再谈别的。**

**验证方法（可复用）**：`pypdf` 读 PDF，逐页取 `/Annots` 里的 `/Dest`，比对 Catalog 的 `/Dests` 表——注解存在但目标不在表里即为悬空。修复后 61 号两份材料稿各得 2 条内部链接注解（此前 0 条），全部可解析。

**未做**：仓库中**早先转好的 PDF**（含 50 号教材子项目那批）仍是旧锚点行为，要享内跳需用修复后的工具重转。相关 [[feedback-no-pdf-for-drafts]]。
