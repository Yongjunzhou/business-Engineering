2026-07-28 以 91 规范第十一章（§11.1~§11.12）审查并修复 [23-eos-output-architecture.md](20-pl4eos/80-pl4eos-2-eosdata/23-eos-output-architecture.md)，版本 v2.0→v2.1（commit 351bd4a + 06a7daa）。

**关键设计决策**：

- **F6 反馈区删除（方案A，用户批准）**：删除全部 57 个节点的 `###### 反馈区` 空表。§11 的设计哲学是"**文档即当前状态，git 即历史**"——人类反馈内容的文档落点只有两处：`确认状态` 字段冒号后（结构化）+ 节点块自由文本（git diff 兜底）；反馈历史轨迹由 git commit 承载，不在文档建表。反馈区是规范外的第三通道，冗余。
- **F3 悬空候选节点 → `[需裁决]`**：归属裁定类问题（如 @node-budget/@node-fixed-asset 的域归属）按 §11.8 属于"涉及架构边界裁定、AI 无法自主决定"，应从"空确认状态 + AI建议"改写为 `确认状态：[需裁决]：{待决事项}`，使反馈机制自洽。
- **F5 未强行改 23**：`STR引用` 的 `STR-F-GOV-###` 看似违反 §11.5 的 `@srf-` 前缀，但核查发现 **02 号资产权威源用的就是 `STR-F-GOV-###`**，23 的引用是对的。真正的不一致在 **§11.5 `@srf-` 前缀约定 vs 02 号资产 `STR-F-` 实际格式**——跨文档问题，留作待办，未在 23 内强行改名以免改坏追溯链。

**修复范围**：F1~F4/F6/F7/F8 已落实；O1（平台配置构件来源模型大面积为 "—"）属业务数据补全，无业务依据不代填，留观察项，已将特有字段口径软化为"自研或尚未识别时为 —"。
