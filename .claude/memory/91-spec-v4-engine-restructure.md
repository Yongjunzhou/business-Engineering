# 91 规范 v4.0 引擎体系收敛（2026-07-10 讨论定稿并写入）

## 核心结论：文档不是引擎概念，是实体组装模式

**文档 = 封面实体（DocumentCover 表一行，全系统一张表）+ 正文实体（1:1）+ 支持信息（→其他文档的多对多引用）+ 处理配置（wft03-biz 定义）**

封面和正文都是普通实体，由实体引擎生成物理表。正文被各引擎按需转化为功能表单（台账/指标/看板/项目/WBS/计划/流程/工单等形态），封面由功能引擎表单能力转为封面表单，两者由功能引擎的组装能力按 1:1 主子关系组装。

## 正式文档 vs 轻量文档（2026-07-10 讨论追加）

- **正式文档**（有封面）：有独立于正文 CRUD 的生命周期（审批/派发/版本追溯/独立状态变迁）——采购申请单、指标文档、看板文档
- **轻量文档**（无封面）：CRUD 即全部生命周期——会议纪要、技术规范、参考文档
- 三类设计规则：R1 正文始终存在（1 行 = 1 文档内容条目实例）、R2 封面按需、R3 存在封面时严格 1:1 + derived_from
- **R4**：场景业务中第一个有任务类型的输出文档，任务类型必然是计划（唯一自启动任务类型）
- **R5**：三角互触发——计划完成可触发流程/工单，流程节点可触发工单/计划，工单完成可触发流程/计划
- **R6**：计划是唯一自启动类型；流程和工单靠上游任务触发
- 任务模式与节点仅适用于正式文档

## PCA 策划阶段："计划清单"为总调度表（2026-07-10 讨论追加）

- PCA 的 P 阶段所有输出文档的任务类型都是计划（自启动，策划→发布），由角色职责或上一轮 A→P 闭环驱动
- 计划清单是 P 阶段的"总调度表"——正文第 1 条为"策划本次计划清单及其余清单"，指向文档自身任务节点，不递归；后续条目分别对应各清单的策划任务
- D 和 PCA 在 wft01/02/03-biz 的处理逻辑上完全同构——都是场景业务→输出文档序列→每个文档有封面+正文+任务+引用

## 场景业务类型保留

D（执行类）/PCA（管理类）作为场景业务语义分类保留，影响 wft02-biz/wft03-biz 的引擎推断偏好，但不作为 DocumentCover 表的数据库字段。

## 任务模式与节点的三层职责（2026-07-10 讨论追加）

| Skill | 职责 | 语言层 |
|-------|------|--------|
| **wft01-biz** | 判定任务模式（流程/工单/计划）；捕获 OR 已有节点 + 推断缺失节点（OR明确→原样捕获，OR只提模式→判定模式+`[待wft02推断]`，OR缺失→推断模式`[推断]`+`[待wft02推断]`）| **业务语言**——"部门经理审批，通过后到财务" |
| **wft02-biz** | 消费 wft01 节点（业务语言）→映射到引擎 CU 候选（引擎语言）；补充系统自动节点和异常路径 | **引擎语言**——"@flow-cu-node-config：角色=部门经理，动作=[通过→财务审批, 驳回→申请人]" |
| **wft03-biz** | 消费 wft02 CU 候选 → 生成具体引擎 CU 配置需求 | **配置规格**——"@flow-cu-definition + @flow-cu-node-config × 3" |

核心洞察：不是"节点归哪个 Skill"，而是"节点有业务语言层和引擎语言层"——wft01 用业务方听得懂的话供人类确认，wft02 转化为引擎能执行的 CU 规格。

## Biz 三 Skill 职责（最终版）

| Skill | 职责 |
|-------|------|
| **wft01-biz** | 基于OR推断定义场景业务节点和输出文档（含封面模式判定正式/轻量 + 正式文档的任务模式与主要节点，业务语言），基于端到端补充业务需求——"向业务方证明我听懂了" |
| **wft02-biz** | 生成A2+Bn产品业务架构；正式文档的封面字段+正文结构+转化引擎+引用；将 wft01 的业务节点转化为引擎 CU 候选（引擎语言）——"设计方案" |
| **wft03-biz** | 消费 wft02 的 CU 候选→生成菜单树/场景业务/内容/任务节点/引用各层具体 CU 配置需求——"出配置" |
