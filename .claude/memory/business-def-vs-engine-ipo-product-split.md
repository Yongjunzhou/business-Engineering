**「业务定义类 IPO / 业务引擎类 IPO」是 EOS 的产物架构二分，不是需求分类轴**（2026-09-10 定并写入 `01-pl4eos-spec` §2.7.6）：

- 业务定义类 IPO → **配置方案组件**（1 主定义组件 + 7 类子组件）；业务引擎类 IPO → **前后端组件**（1 能力主组件 + 5 类承接组件）。两处明文"**禁止跨类生成**"。
- 对应 **94 §2.5【配置方案】/ §2.6【前后端组件方案】**两棵**产物**树（94 v1.7 起两章结构：各产品数据的分解结构）。
- `业务定义类型`（流程定义 / 表单定义 / 指标定义 / 台账定义 / 工单定义 / 计划定义）＝**产物类型口径**，是**配置方案树的第一层**，**不是系统需求树（94 §2.3.1）的第一层**。

**Why**：此前 `01-pl4eos-spec` §4.4 与 `05-eos-system-requirement-summary-architecture.md` 把 `业务定义类型 → 具体业务定义` 当作**系统需求树的第一层组织口径**——即把产物树的轴搬进了需求树（**串层**，不是"口径过时"）。原始文档其实一直只说它是"产品级默认规则"（[2026-06-16 重构摘要 §三.2]），而通用规范 §1126 的原则始终是"按**系统职责**组织"。

**How to apply**：写/审 系统需求（05、wft03、§4.4）时，**分类维度一律用系统职责**；遇到"业务定义类型 / 引擎能力类型 / 流程定义 / 表单定义"这类词，先判它在说**产物去向**（合法，§2.7.6）还是在说**需求分层**（串层，改掉）。
