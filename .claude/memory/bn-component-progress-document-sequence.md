## 四层进度模型

```
L1 产品/项目进度 ──→ 聚合其各构件进度
      ↑
L2 构件进度     ──→ 聚合其产品数据文档序列（01→09）
      ↑
L3 文档整体进度  ──→ 文档生命周期状态在状态链中的位置
      ↑
L4 文档条目进度  ──→ 08 追溯矩阵中的追溯链完成度
```

每层自下而上聚合，上层不关心下层的内部细节。

**Why:** 构件的端到端业务 = 从需求提出到需求满足（[[end_to_end_business_framework]]），而流水线设计子线的唯一可交付物载体正是 01→09 文档序列。文档自身又有生命周期状态机，文档内的条目通过追溯矩阵建立跨层引用。四层递进是这个结构链的自然展开。

---

## L1：产品/项目进度

**数据源**：23 号资产中该 E2E 项目（`@prod-*`）下属的所有构件（`@node-*`）

**计算**：

```
产品进度% = Σ(构件_i进度 × 权重_i) / Σ权重_i
```

权重可等权或按构件在工作量/关键路径上的占比设定。

---

## L2：构件进度

**数据源**：08 追溯矩阵中该构件的全文档序列（01→09 中适用的文档）

**计算**：

```
构件进度% = Σ(文档_j进度 × 权重_j) / Σ(适用文档的权重_j)
```

"不适用"的判断依据：
- 平台配置构件 vs 自研引擎构件的文档序列可能有差异
- 某些构件可能跳过特定文档（如纯配置构件不需要 07-PA 的代码级设计）

---

## L3：文档整体进度

**数据源**：各文档自身的生命周期状态队列（如 04-BA 的 `1.1 BA节点状态队列`）

**计算**：

```
文档进度 = 当前状态在状态链中的位置 / 状态链总长度
```

示例（04-BA）：
```
待确认方案(1/7) → 迭代中(2/7) → 待资产写回(3/7) → 资产写回中(4/7) → 待架构映射(5/7) → 已架构映射(6/7) → 已验证冻结(7/7)
```

文档类型差异直接编码在状态链中：
- 索引类（08）：链长=1（日更批算，一次完成）
- 架构类（02/04/05/07）：链长≈7，含 Phase A→Phase B 完整流转
- 详细定义类（03/06）：链长较短，紧跟架构类之后
- 验证类（09）：链长取决于发现问题数

---

## L4：文档条目进度

**数据源**：08 追溯矩阵（[[#追溯矩阵08作为进度显示层]]）

**计算**：

```
条目进度 = 已完成追溯链节数 / 总追溯链节数
```

一条 OR 条目的完整追溯链：`OR → STR → BA → SR → PA`（5 节）
一个 BA IPO 的完整追溯链：`STR-D → BA → SR → PA`（4 节）

08 的关系块（`4.1~4.4`）提供所有链节的状态。

---

## 追溯矩阵（08）作为 L4 数据源

08 承载所有层间映射关系（OR→STR / STR→BA / BA→SR / SR→PA），是 L4 条目进度的**唯一数据源**，间接支撑 L1~L3 的聚合计算。

### 日更批算策略

- **频率**：每天一次全量重建
- **方式**：遍历 01~07 的全部内部引用链 → 重建 08 各关系块 → 四层进度自动可得
- **免同步**：各 wft Skill 只维护自己产出文档的内部引用，不需要维护 08 写回逻辑
- **始终一致**：日更重建 = 08 永远是当日文档集的完整快照

---

## 四个生命周期状态的位置

| 层 | 生命周期状态在哪 | 状态机定义在哪 |
|------|---------|---------|
| L1 产品/项目 | 23 号资产 E2E 项目行 | 聚合计算，无独立状态机 |
| L2 构件 | 23 号资产 `@node-*` 行 | 构件级三字段（生命周期+AI建议+人类决策） |
| L3 文档 | 各文档自身状态队列 | 各文档 `1.` 区状态队列 + 活动锁 |
| L4 文档条目 | 08 追溯矩阵关系行 | 关系状态（已建立/待补链/断链） |
