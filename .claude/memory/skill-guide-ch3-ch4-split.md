## 一、分家的尺子（本轮的主要产出，可推广）

**第三章＝Y 的方案侧视图，说的是静态**：这一级是什么、来历（93 §3.3 的四个来源之一）、构建规则、形态边界、本任务拿它作什么用。
**第四章＝转换的动态**：从 X 的哪里推、跟谁比、判什么、怎么处置。

判据落在句子上：**带动作的归第四章**（"节点不存在时新建""或合并或新建""逐节点定复用→改进→新增""与已有节点作分析"），**不带动作的归第三章**（"R／P 两棵树各有一份节点，同值、不共享""本任务以此作定位与对账域""本任务以此作分片与复用宿主范围"）。

配套的一条：**「取自 X 的『某属性』」不算 93 §3.3 的四个来历**（承袭／本任务产出／AI 建议+人类确认／目标组织级）——① ② ④ 的节点由本任务造，来历就是「本任务产出」，属性从哪儿来是机制、归第四章。**「取自 X 的『某节点』」（⑤⑥⑦）保留**——末三级整段来自上游，那是它的来历。

## 二、abr 第四章的四条收法

- **六步收五步**：撤「第一步 · 取根上的三个属性」——该步每一句都被 §4.1 注二与表4-2 的「取根上哪个属性」列说过，是同一事实的第三遍。撤后 4.2.1 长干枝起头改写为「根上的三个属性值在 Y 上逐级落位」。
- **表4-1 撤「关系」列**：三行 X 侧全是「整段搬入」（常量），四行 Y 侧全是表4-2 第二列已说的话。上一轮已裁定「常量不占列、进注说全」，只落了注、没撤列，本轮撤。
- **表4-1 改 Y 级序**：原序 Y 列读作 ⑤⑥⑦①②③④，与 图3-1／表3-1／表3-2／表4-2／表4-3 的升序读法相左。改后两条注对调（先说 Y 的 ①②③④ 无对应，再说整段搬入）。
- **表4-3 收三行**：原第一行「⑤ 挂到哪个 ④ 下」自陈"随长干枝落定"、表下首句又说一遍"这一步不再判"，并进表前那句，表只留 ⑤ 并入/新建 ＋ ⑥ ＋ ⑦。
- **表4-1 注二整条撤**（人类 2026-09-20 追认）：注二先是被纠错（原句"本任务对它们不改名、不重排、不增减"把"新建"这一路的走法写成了通例——本文档里末三级是**会**被合并与改动的，见表4-3 ⑥⑦、§1.3 条2／条3、§3.1 注），随即**整条撤掉**。理由是它压根不该在这儿：与 [94 §1.4](94-eos-sys-dev-dbs.md)「两侧的 ⑤⑥⑦ 都是同一批节点…整段搬入、无映射；这两处的活是长干枝，并对 ⑤⑥⑦ 逐级判定其落位」**近乎逐字**——那是树级承接规则的正文，93 §4.1 把它划归 94 §1.2~§1.4 并写明 SKILL"引用、不重述"。是我上一轮把表4-1 的「关系」列收进正文时误收的（下次遇到"常量进正文"，先问一句：**这个常量是本任务的判定，还是权威的树级关系**——后者只有撤掉才不越界）。

  **「整段搬入」不设术语**：家 = 94 §1.4／§2.2，93 §2.3／§3.3／§4.2 与 abp §1.4 都在引用。abr 剩四处**使用**（§4.2.3 首句、表4-3 ⑤ 处置栏、正文两处），**都不是定义、都留**；只有正文那句"该 ④ 下没有承接它的文档，就新建一张，X 的三级整段搬入"的收尾与表4-3 同一格重复（同段"各定复用、改进还是新增"亦然），未收。

另撤 ch4 里的 ④ 注前半「**④ 是本任务的新建与修订单位**」（与表3-2 ④ 同说），留后半「三项人类确认都挂在 ④ 上」——人类确认是过程里的事，第四章是它的操作面。

## 四、4.2 五个步名重起（人类 2026-09-20 定）

原五名"长干枝／聚出角色职责／把末三级挂到 E2E职责下／整这条 E2E职责／并不完时出缺口"的毛病：一列里三种句式（动宾／「把」字句／条件分句）、标题带指代（"整**这条** E2E职责"——标题会被抽进目录单独读，指代兑现不了）、口语与自造动词顶替说不清的动作（"整""聚出""并不完"在 91／93／94 里都查不到），而与 §5.1 的 Step 名体例（动作的名词化）不一致；「并不完时出缺口」还名实不符（名说"并"、文说"闭环走完没有"）。

人类定名：**由属性生成干枝／聚类生成角色职责／生成末三级节点／确定文档序列与属性／识别并补充需求缺口**。

**唯一改字**：4.2.4 的「属性」被我换成「实现方式」（**确定文档序列与实现方式**）——「属性」在本链是**专词**，指业务文档带的五个坐标（94 §2.1.1「五个坐标作为本级的属性」、abr §2「文档的五个属性，不占级位」）；该步产出的是文档序列与**业务文档实现方式**（封面模式／正文实体类型／支撑引擎候选），93 §3.3 管这后一类叫**要素**。用「属性」= 同一个词两个含义，正是规则四要治的病。**人类 2026-09-20 定用「实现方式」——理由：比「要素」更直观**（备选「确定文档序列与要素」作废）。

**未跟的一处**：§5.1.3 正文里那两个内联小名仍是「**长干枝**」「**末三级落位**」，与新节题不同名——同一件事在第四、五两章各叫各的。未动，待裁。

**93 §3.4 的标题体例**（人类 2026-09-20 点头，已落）：照 §3.5「Step N · 动作名」的样，在「转换过程」那条应含后补一句——**一节一步，标题写「第 N 步 · 动作名」**：动作名取该步的产出名，名词化、不带指代、不用「把」字句与条件分句——标题会被抽进目录单独读，读者从标题要能看出这一步产出什么。**未写长度限制**（我原先引 00-doc-conventions §13.2 的"2~6 字"，但人类定名是 7~9 字、§5.1 自己的「覆盖检查与补充原始需求」也是 11 字，故不写）。

**93 自身的散句圈号也扫了**（同轮，四处）：§3.3 形态边界注（⑤ ⑥ ⑦ 三级 → 业务文档、任务节点、用例场景）、§3.3 末（「05 的枝梢＝⑤ 用例场景功能」→「系统需求框架的枝梢＝用例场景功能」）、§4.3 链尾注与两条尾（「需求-方案对③」「06→07」「07 平台构成框架」「叶 ⑥ IPO功能」→ 按规则四写两端文档名「系统需求 → 平台构成」与各本名）。剩 §2.3 那条"级位编号 ①…"与规则四自己引 ⑤⑥⑦ 的两处是**符号自身的引用**，放行；§3.3 末端【待回填】把 ①②③… 当**列表序号**用那一处性质不同，未动。

**连带发现的冲突（未裁）**：§1.4 术语表写着"编号写作需求-方案对①/②/③"，而 §2.4 规则四要求正文"按两端文档称呼"——按规则四扫完之后，§1.4 那个记法在正文里已无用处，是留是retire待裁。

**§5.1.3 的两个内联小名不改**（我先前报过、后自己撤回）：§5.1.3 的「长干枝」覆盖 §4.2.1＋§4.2.2 两步、「末三级落位」对齐 §4.2.3，是**比章题粗一档的伞名**，不是同一件事的两个名字；两处粒度不对齐，本来就不该同名。
