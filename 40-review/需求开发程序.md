## 1 目的

规范需求的获取、分析、规格说明与验证活动,将干系人的**需要(need)与期望(expectation)**转化为清晰、完整、可验证的**规定需求(specified requirement)**,以《需求规格说明书》(SRS)为载体交付,为后续实现、测试与需求管理提供可靠依据。

## 2 适用范围

适用于本公司产品研发项目中,从需求提出到需求批准的需求开发全过程。

**本程序不包含需求管理活动**(需求基线化后的基线、变更、追溯、状态与度量),该部分由《需求管理程序》规定;本程序以批准记录(QR-12)为终点,批准后的需求交付《需求管理程序》管辖。

## 3 引用文件

## 4 术语与定义

| 术语 | 定义 |
|---|---|
| 需求 requirement | 明示的、通常隐含的或必须履行的需要或期望(ISO 9000:2015 §3.6.4) |
| 需要 need / 期望 expectation | 需求的两种来源;需要为基本诉求,期望为理想诉求 |
| 规定需求 specified requirement | 被明示的需求,即 SRS 中的条文;**验证的参照** |
| 验证 verification | 对照规定需求,确认需求表述正确、完整、可测(见 7.10) |
| 确认 validation | 对照用户意图,确认需求确实是用户要的(见 7.11) |
| 运行概念 ConOps | 从用户/运营视角描述系统将如何被使用的文档(问题域) |
| 干系人 | 影响需求或受需求影响的个人、组织 |

## 5 职责

| 角色 | 主要职责 |
|---|---|
| 需求负责人 | 执行需求获取、分析(QR-01~05);牵头编制运行概念(QR-06);编制规格(QR-07~09);组织确认(QR-11) |
| 干系人 | 提供需要与期望;参与调研与评审;确认需求(QR-11);签署批准(QR-12) |
| 评审主持人 | 组织需求评审会,出具评审报告(QR-10) |
| 开发/测试代表 | 参与评审,确认需求可实现、可测试 |
| 项目经理(PM) | 资源保障;参与评审;推动批准流程 |

## 6 输入与前置条件

### 6.1 输入

- 客户合同/订单、市场信息、法规标准、内部改进建议;
- 干系人(用户、客户、监管、运营)的诉求。

### 6.2 管辖边界

- 本程序覆盖:获取 → 分析 → 运行概念 → 规格说明 → 验证(验证 = 评审 QR-10 + 确认 QR-11);
- 本程序**终点**:需求批准记录(QR-12);
- 批准后的需求基线化及其后续管理,移交《需求管理程序》。

### 6.3 文档流转主线

```
QR-01/02(获取)→ QR-03/04/05(分析)→ QR-06(运行概念)→ QR-07/08/09(规格)→ QR-10/11/12(验证)
支撑:QRS-01~04 贯穿获取与分析,作为运行概念与 SRS 的编制依据
```

### 6.4 文档构成

- **受控记录 12 份**(QR-01 ~ QR-12):见第 7 章;
- **支撑性文档 4 份**(QRS-01 ~ QRS-04):见 7.13~7.16,不作为独立受控记录,由需求负责人随项目归档,可作为附件。

## 7 输出文档管理要求(以过程活动呈现)

每份文档按过程活动五要素描述:**何时 / 谁 / 做什么 / 以什么标准 / 输出·流转**。

### 7.1 QR-01 干系人登记册

| 活动要素 | 内容 |
|---|---|
| 何时 | 项目启动时、需求获取开始前;新增干系人时更新 |
| 谁 | 需求负责人 |
| 做什么 | 识别影响或受需求影响的所有角色,登记角色/组织/影响力/关注度/职责 |
| 以什么标准 | 评审、确认环节关键干系人覆盖 100%,遗漏即不符合 |
| 输出·流转 | QR-01;作为 QR-02 调研对象清单、QR-10/11 评审确认名单的依据 |

### 7.2 QR-02 访谈调研记录

| 活动要素 | 内容 |
|---|---|
| 何时 | 访谈/问卷/观察等获取活动当日 |
| 谁 | 需求负责人(对象:干系人) |
| 做什么 | 按提纲开展调研,记录对象/时间/原始问答/结论/待跟进事项;同步收集竞品信息与用户故事素材 |
| 以什么标准 | 记录须含对象、时间、原始记录、结论、待跟进五项,当日整理归档 |
| 输出·流转 | QR-02;流入 QR-03 需求池;作为追溯矩阵"来源"的底账 |

### 7.3 QR-03 需求池

| 活动要素 | 内容 |
|---|---|
| 何时 | 从需求获取开始,持续维护 |
| 谁 | 需求负责人 |
| 做什么 | 汇总所有需求,统一编号、分类、标记来源/优先级/状态 |
| 以什么标准 | 每条需求唯一编号;无来源的需求不得入池;进入 SRS 的需求必须出自本池 |
| 输出·流转 | QR-03;作为 QR-04 优先级排序与 QR-06 运行概念的综合素材 |

### 7.4 QR-04 优先级排序表

| 活动要素 | 内容 |
|---|---|
| 何时 | 需求分析阶段;信息变化时可重排 |
| 谁 | 需求负责人,与干系人协商 |
| 做什么 | 用 MoSCoW 或 Kano 方法对需求排序,并写明排序理由 |
| 以什么标准 | 排序须经干系人确认;无理由的排序视为无效 |
| 输出·流转 | QR-04;决定 QR-06 运行概念的场景重点与 QR-07 SRS 的编排顺序 |

### 7.5 QR-05 业务规则清单

| 活动要素 | 内容 |
|---|---|
| 何时 | 需求获取与分析阶段持续收集 |
| 谁 | 需求负责人;业务/合规干系人确认 |
| 做什么 | 识别法规、政策、业务惯例等约束,登记编号/内容/来源/范围/违反后果 |
| 以什么标准 | 涉法规规则必须标注出处;遗漏导致返工,由责任人在追溯中说明 |
| 输出·流转 | QR-05;作为运行概念中异常/边界场景的依据,嵌入 QR-07 SRS 相关条文 |

### 7.6 QR-06 运行概念(ConOps)

| 活动要素 | 内容 |
|---|---|
| 何时 | 需求获取与分析成果(QR-01~05)齐备后、SRS 编制前;重大需求变化时更新 |
| 谁 | 需求负责人牵头;用户/运营干系人深度参与 |
| 做什么 | 综合获取与分析成果,按 IEEE 1362 编制:引言(目的/范围/读者)、系统概述(要解决的问题/运行目标)、运行环境(物理/组织/技术)、运行场景(正常/异常/应急,逐步叙述)、干系人与角色、运行支持(部署/培训/维护/升级) |
| 以什么标准 | 覆盖运行环境、场景、角色、运行支持四项;场景须含异常与应急情形;经干系人确认 |
| 输出·流转 | QR-06;作为 QR-07 SRS 条文的场景依据(问题域 → 解空间) |

### 7.7 QR-07 需求规格说明书(SRS)

| 活动要素 | 内容 |
|---|---|
| 何时 | QR-03/04/05/06 齐备后,规格阶段启动;评审通过后版本化 |
| 谁 | 需求负责人主笔;开发、测试、干系人参与评审 |
| 做什么 | 将运行概念中的场景翻译为需求条文,编制六章(引言/总体描述/功能需求/非功能需求/外部接口/验证方法),功能需求逐条编号 REQ-xxx;引用术语表(QR-08);建立追溯矩阵初版(QR-09) |
| 以什么标准 | 每条需求完整、一致、无歧义、可验证、可追溯、有优先级;禁止"快速/大约/友好"等不可验证表述 |
| 输出·流转 | QR-07;→ QR-10 评审 → QR-11 确认 → QR-12 批准 → 移交《需求管理程序》 |

### 7.8 QR-08 术语表

| 活动要素 | 内容 |
|---|---|
| 何时 | 规格阶段建立,随项目维护 |
| 谁 | 需求负责人 |
| 做什么 | 收录 SRS 中全部专业术语,给出定义、同义词、出处 |
| 以什么标准 | SRS 中出现的术语收录率 100%;同一术语定义唯一 |
| 输出·流转 | QR-08;SRS 全文引用 |

### 7.9 QR-09 需求追溯矩阵(初版)

| 活动要素 | 内容 |
|---|---|
| 何时 | 规格阶段建立初版;移交《需求管理程序》后由其在管理阶段持续维护 |
| 谁 | 需求负责人 |
| 做什么 | 登记需求↔来源(干系人/业务目标/法规/竞品)的对应关系及状态 |
| 以什么标准 | 需求与其来源一一对应;无来源需求不得进入 SRS |
| 输出·流转 | QR-09 初版;随 SRS 一并移交,作为变更影响分析(QR-17)与覆盖核查的依据 |

### 7.10 QR-10 需求评审报告(验证 verification)

| 活动要素 | 内容 |
|---|---|
| 何时 | QR-07 完成后 5 个工作日内组织评审 |
| 谁 | 评审主持人;参加人:需求负责人、开发、测试、相关干系人(名单取自 QR-01) |
| 做什么 | **对照规定需求**逐条核查正确性、完整性、一致性、可测性,记录意见与缺陷,给出评审结论 |
| 以什么标准 | 结论三选一:通过 / 有条件通过 / 重审;有条件通过须限期整改并复审 |
| 输出·流转 | QR-10;通过后进入 QR-11 确认 |

### 7.11 QR-11 验证·确认记录(确认 validation)

| 活动要素 | 内容 |
|---|---|
| 何时 | 评审通过后、批准前 |
| 谁 | 需求负责人组织;干系人参与并签字 |
| 做什么 | **对照用户真实意图**确认需求确实是用户要的:记录核对项、核对方法(原型演示/走查/测试)、结果、干系人确认意见 |
| 以什么标准 | 与评审(QR-10,查"表述对不对")明确区分——本记录查"是不是用户要的";未确认不得进入批准 |
| 输出·流转 | QR-11;确认通过后进入 QR-12 批准 |

### 7.12 QR-12 需求批准记录

| 活动要素 | 内容 |
|---|---|
| 何时 | 评审与确认均通过后,本程序终点 |
| 谁 | 干系人代表签字批准 |
| 做什么 | 批准 SRS 版本,记录批准人、签字、日期、意见 |
| 以什么标准 | 未经批准不得移交基线化;批准人须为有权的干系人代表 |
| 输出·流转 | QR-12;随 SRS 移交《需求管理程序》,作为建立需求基线(QR-14)的前提 |

### 7.13 QRS-01 竞品分析报告

| 活动要素 | 内容 |
|---|---|
| 何时 | 需求获取期,一次性完成 |
| 谁 | 需求负责人/产品角色 |
| 做什么 | 对比同类产品功能与体验,形成功能矩阵与优劣分析,提炼可借鉴/可规避点 |
| 以什么标准 | 结论须区分"竞品有"与"用户要",不得直接作为需求来源 |
| 输出·流转 | QRS-01;作为 QR-06 运行概念与 QR-07 SRS 的参考附件 |

### 7.14 QRS-02 用户故事·场景

| 活动要素 | 内容 |
|---|---|
| 何时 | 获取与早期分析阶段 |
| 谁 | 需求负责人,与用户共创 |
| 做什么 | 以"作为\<角色\>,想要\<能力\>,以便\<价值\>"描述需求雏形,附验收标准初稿 |
| 以什么标准 | 角色、目标、价值三要素齐全;转化入需求池(QR-03)后方可进入 SRS |
| 输出·流转 | QRS-02;流入 QR-03 需求池,作为 QR-06 运行概念的场景素材 |

### 7.15 QRS-03 原型·需求模型

| 活动要素 | 内容 |
|---|---|
| 何时 | 分析阶段,与干系人确认需求时 |
| 谁 | 需求负责人/设计角色 |
| 做什么 | 制作线框图、交互原型、用例图、流程图等,将抽象需求可视化 |
| 以什么标准 | 原型能表达需求核心交互;评审确认后作为 SRS 描述依据 |
| 输出·流转 | QRS-03;作为 QR-11 确认活动的主要核对工具 |

### 7.16 QRS-04 可行性分析报告

| 活动要素 | 内容 |
|---|---|
| 何时 | 分析阶段,进入规格说明前 |
| 谁 | 需求负责人,技术/财务角色参与 |
| 做什么 | 评估技术、经济、时间资源、法律合规可行性,给出风险与建议 |
| 以什么标准 | 不可行需求须在进入规格前剔除;结论须有依据 |
| 输出·流转 | QRS-04;支撑 QR-03 需求池的筛选与 QR-04 优先级决策 |

## 8 文档关联与流向
